# 02 · 生命周期（Lifetimes）

> demo: `cargo run --bin 02_lifetimes`

## 1. 设计动机

所有权回答"谁拥有"，借用回答"谁能看"。但借用还有一个问题：**引用指向的值，在引用还活着的时候会不会已经被释放？** 悬垂引用（dangling reference）是 C/C++ 最难查的 bug 之一。生命周期（lifetime）就是给"引用有效的时间范围"命名，让编译器检查。

## 2. 机制拆解

每个引用都有一个生命周期——它"活着"的时间范围。Rust 编译器通过**借用检查**保证：

```text
引用不能活得比它指向的值更久
```

- 生命周期标注 `'a` 只是给编译器看的"名字"，不产生任何运行时开销
- **省略规则（elision）**：绝大多数情况不用写，编译器自动推断
- 生命周期约束只出现在**函数签名**（输入引用与输出引用的关系），函数体内部编译器自己推

```rust
// 显式标注：返回的 &str 活得和参数 x 一样久
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

## 3. 代码验证（demos/02_lifetimes.rs）

demo 演示：返回引用必须标注生命周期（否则编译器不知道返回谁的生命周期）；
以及**悬垂引用被拒绝**的示例。

## 4. 代价与取舍

| 代价 | 说明 |
|------|------|
| 学习门槛 | 生命周期是 Rust 最难的概念之一 |
| 标注噪音 | 复杂结构（自引用、图）里 `'a` 满天飞 |
| 保守性 | 借用检查是保守的：有些安全代码被拒绝（需重构） |

**换来的**：悬垂引用在编译期被消灭；`longest` 这类函数签名自带"契约"信息。

## 5. 对 Tenet 的启示

- ✅ **吸收"引用不能比指向的值活得更久"的规则意识**：Tenet 解释器里的环境链
  （Env 的 parent 指针）由引用计数保证——父环境一定比子环境活得久，
  这正是生命周期规则的运行时版本
- ✅ **吸收"签名即契约"**：Tenet 的函数签名 `fn f(a: int) -> int` 显式写出参数和返回类型，
  与 Rust 在签名里暴露生命周期同理——把"契约"摆在明面上
- ❌ **拒绝生命周期标注语法**：对教学语言是纯粹的复杂度；用引用计数 + 无自引用结构替代

**一句话**：Rust 把"引用能活多久"变成类型系统的一部分；
Tenet 用「环境树 + Rc」让生命周期问题根本不存在。
