# API 契约写作标准

这个标准用于说明 API、协议或接口契约。它回答的核心问题是：客户端可以依赖什么，服务端实际实现了什么，错误和状态变化如何表现，版本变化会破坏谁。

它不是仓库模板，也不是让每节都写满的清单。与本契约无关的部分删除，读者需要的信息不要拆到无法导航的零散文件中。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 我本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 我本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 我本人没有读到源码，但来源材料陈述了该事实；来源可能是引述源码的文档、他人整理的笔记或任务给定材料 | 命令、配置项、路径、指标名、阈值 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- **选档顺序**：先问「我本人读到源码了吗」→ 是则用 `源码确认`；否则问「我本人执行并看到输出了吗」→ 是则用 `运行确认`。两者都否、但来源材料有明确陈述 → 用 `来源确认`。
- **不要用 `源码确认` 标注你只是转述的内容**。这正是 `来源确认` 要解决的问题：区分「作者亲自核对了源码」与「作者转述了一份声称来自源码的材料」。
- `来源确认` 的结论来自材料，作者不对其真实性负责，但必须负责标注它未经本人核对；需要读者据此行动时，配一个可自行复核的命令。
- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”“服务监听 `:9100`（来源确认，材料「Metrics endpoint」）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中出现的 `[measured: …]`、截图数字或他人记录的性能数据，一律标 `来源确认`，并在紧邻处写明「非本机运行结果」。这是最容易误标的一类。
- **引用格式**：有行号时写 `<文件>:<行号>`；只有文件名时写 `<文件名>`；只有材料时写「材料「<小节标题>」」。三者都没有时写 `未验证`。**不得编造行号。**
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。正文中的说明性括号不属于占位，但不得以括号代替应写的内容。
- **待验证清单格式**：集中收纳未验证项时使用固定列名，使不同文档可比较：

  | 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
  | --- | --- | --- | --- |
  | V1 | <待确认的结论> | <缺什么证据：无源码 / 无环境 / 材料未给> | <可执行的命令或动作> → <看到什么算确认、看到什么算否定> |

- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 契约定位

先给结论：

- 接口名称、协议类型和消费方
- 文档是规范性契约还是当前实现参考
- 一句话说明该接口解决什么问题
- 本契约不覆盖哪些内容
- 与相邻接口、服务或系统的边界

## 接口种类与章节取舍

| 接口种类 | 判定依据 | 章节取舍 |
| --- | --- | --- |
| 网络接口 | 有独立部署的服务与客户端 | 全部章节 |
| 消息/事件接口 | 有 topic、生产者与消费者 | 全部章节，重试与幂等按投递语义写 |
| 进程内接口 | 同进程调用，无传输层 | 只写签名、默认值、前置条件、哨兵值、异常分类、确定性；传输/超时/重试/版本写「不适用」 |

不适用章节必须写「不适用」并给理由，不留空、不省略。

## 权威来源与所有权

说明哪些来源具有最高权威，避免实现和文档互相矛盾：

- 服务代码位置
- schema、OpenAPI/AsyncAPI 或 protobuf 文件
- 契约测试和集成测试位置
- 接口负责人或维护模块
- 当规范与实现不一致时，应记录差异而不是擅自改写规范

同一接口存在多份实现时，以「被真实调用方导入或调用的那一份」为权威实现，并在文档中写明其余实现与它的关系（别名、旧版、重复实现）及差异。缺少这条说明时，文档视为未完成（依据：以调用点 `源码确认` 为准）。

## 接口入口

列出可访问入口和调用前提：

- base URL、端口、域名或消息 topic
- 请求使用的协议、序列化和认证方式
- 开发、测试、生产环境的差异
- 如何确认入口可用

## 操作或消息清单

对 HTTP/RPC 接口或消息事件逐项说明：

- 方法、路径或操作名
- 用途和典型调用方
- 请求字段、响应字段和主要约束
- 是否同步返回、异步返回或需要轮询/回调
- 限流、超时、大小和配额限制

不要复制完整 OpenAPI 内容。字段细节可以链接到 schema，文档解释接口语义、状态和错误行为。

## 数据与消息结构

当字段含义不能从类型直接看出时说明：

- 字段名、类型、必填性和默认值
- 字段的业务含义和取值约束
- 日期时间、枚举、单位、编码和 null 语义
- 分页、排序、过滤和批量操作约定
- 请求校验失败时的具体表现

## 认证、授权与安全

覆盖调用方真正需要知道的内容：

- 认证方式、token 过期和刷新方式
- 权限或 scope 要求
- 敏感字段如何处理
- 传输安全和信任边界

## 错误与失败语义

错误不能只列一个 HTTP 状态码。说明：

- 传输错误、校验错误、业务错误和权限错误的区分方式
- 错误响应的结构和可读诊断信息
- 哪些操作可以安全重试，哪些不能
- 幂等键、重试上限、退避和超时默认值
- 部分成功、批量失败和补偿操作的约定

## 状态与生命周期

如果接口涉及任务、作业、订单或会话，用状态表说明：

- 合法状态集合
- 每个合法转移的事件和调用方
- 非法转移会发生什么
- 状态由谁创建、谁推进、谁清理
- 并发写入、过期、取消和中断时的保证

## 版本与兼容性

说明版本策略：

- 当前支持哪些版本
- 新增字段和可选字段是否视为兼容
- 哪些变更属于破坏性变更
- 弃用字段、移除接口和迁移路径如何公布
- 旧客户端与新服务端的行为差异

## 示例调用流

给出一条真实端到端调用路径：

1. 调用方准备请求和认证
2. 请求到达后的校验、路由和权限检查
3. 核心处理逻辑和状态变化
4. 成功响应或错误返回
5. 客户端重试或恢复路径

示例必须来自代码、测试或实际运行记录。示例若未实际运行，标注 `未验证` 并给出复现命令。

## 无 schema 时的写法

没有 OpenAPI / protobuf / JSON Schema 可对照时，不因此停止写作：

- 以源码中的函数签名、类型定义和默认值为权威，标注 `源码确认`。
- 写出前置条件、哨兵值、异常来源；这些往往只存在于注释或代码分支中。
- 开头声明“本文以源码为权威，无机器可读 schema 可对照”。
- 需要运行才能确认的内容（实际状态码、超时值、并发行为）标注 `未验证` 并给出验证命令。

## 实现映射与验证

把文档结论对应到代码入口：

- 请求处理入口和核心函数
- 校验、状态机或事务所在位置
- 集成测试或契约测试
- 可复现的 curl、脚本或测试命令

## 示例

以下示例用同一条结论「`POST /<资源>` 在状态冲突时返回 409，其中仅一类错误可重试」演示两种证据条件下的写法。示例为说明性内容，不对应任何真实仓库。

### 证据可用：读到源码并跑通请求

错误分类与可重试性：

| HTTP 状态 | 错误码 | 分类 | 可重试性 | 依据 |
| --- | --- | --- | --- | --- |
| 400 | `<参数错误码>` | 校验错误 | 不可重试 | `源码确认`，`<校验源码>:<行号>` |
| 401 | `<未认证错误码>` | 权限错误 | 不可重试 | `源码确认`，`<鉴权源码>:<行号>` |
| 409 | `<状态冲突错误码>` | 业务错误 | 可重试，重试前必须重新读取当前状态 | `源码确认`，`<状态机源码>:<行号>` |
| 409 | `<重复提交错误码>` | 业务错误 | 不可重试 | `源码确认`，`<幂等校验源码>:<行号>` |
| 503 | `<容量不足错误码>` | 传输/容量错误 | 可重试，按退避上限 | `源码确认`，`<限流中间件>:<行号>` |

冲突响应体（`运行确认`，`<请求脚本>`；字段含义 `源码确认`，`<响应构造源码>:<行号>`）：

```text
# 命令：<请求脚本> --method POST --path /<资源> --body <冲突请求体>
# 输出：[固定] HTTP 409
{
  "error": { "code": "<状态冲突错误码>", "message": "<可读诊断信息>", "retryable": false }
}
# 输出：[随环境/版本变化] 请求耗时 <数值> ms
```

无运行服务时无法确认：限流实际生效阈值与 `Retry-After` 头（`未验证`，验证动作 → 用 `<请求脚本>` 连续发起冲突请求并观察响应头）。

### 证据受限：只有二手材料

同一结论仅来自材料「<错误码清单小节>」（`来源确认`）：

| HTTP 状态 | 错误码 | 分类 | 可重试性 | 依据 |
| --- | --- | --- | --- | --- |
| 409 | `<状态冲突错误码>` | 业务错误 | 可重试 | `来源确认`，材料「<错误码清单小节>」，非本人核对源码 |

| 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
| --- | --- | --- | --- |
| V1 | 409 响应体的字段与错误码取值 | 无源码，材料未给响应体 | 发起一次真实冲突请求 → 返回 409 且含 `error.code` 即确认 |
| V2 | `<状态冲突错误码>` 是否真的可重试 | 材料只给结论，未给幂等语义 | 对同一冲突请求重试两次 → 第二次仍 409 即不可重试 |

对比可见：证据受限版本缺少错误分类的完整集合、响应体结构与可重试性的源码依据，读者不能据此实现客户端重试。
