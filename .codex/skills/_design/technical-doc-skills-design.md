# 技术文档类 Codex Skill 家族设计方案

## 目标

本设计用于生成一组 Codex skill，帮助 Codex 把某一类技术主题写成高质量、可验证、可维护的文档。

覆盖对象包括：

- 解释一个算法或数据结构
- 说明一门程序设计语言的语法、特性设计和原理
- 说明一个架构设计模式
- 解释或解剖一个系统、框架、项目代码库
- 说明 API 或协议契约
- 说明数据模型
- 记录设计决策
- 编写教程
- 编写运维 runbook

## 设计结论

1. 不使用一个覆盖所有技术文档的总 skill。
2. 使用一组窄范围 skill，让 Codex 根据名称和描述直接命中正确任务。
3. 首批建立核心 4 个，随后建立第二批 5 个，第三批补充 1 个（`documenting-changes`）；三批共 10 个 skill 均已落地并统一改为独立的写作标准，后续按真实写作需求继续验证和修正。
4. 每个 skill 保持独立可用，不依赖一个未必会加载的父 skill。
5. 每个 skill 都要求先确认读者、目的、文档类型和事实来源。
6. skill 及其 reference 是文档内容标准的核心；仓库已有文档只能作为事实素材和定位上下文，不能优先于 skill 的准确性、完整性和验证要求。

## Skill 列表

### 第一批

| Skill 名称 | 目标 |
| --- | --- |
| `explaining-algorithms` | 解释算法和数据结构，覆盖正确性、复杂度、实现、边界例和算法对比 |
| `explaining-systems` | 解释或解剖系统、框架、项目代码库，内部区分三种子模式 |
| `documenting-language-features` | 说明语言语法、特性设计、语义、交互和迁移影响 |
| `documenting-architecture-patterns` | 说明架构模式的上下文、结构、权衡、适用性和反模式 |

### 第二批

| Skill 名称 | 目标 |
| --- | --- |
| `documenting-api-contracts` | 说明 API、协议或接口契约，覆盖消息、错误、状态机、兼容性 |
| `documenting-data-models` | 说明实体、字段、类型、约束、关系、索引和迁移 |
| `documenting-design-decisions` | 以 ADR 或决策记录形式保存问题、候选方案、权衡和结论 |
| `documenting-tutorials` | 编写带前置知识、步骤、示例、练习和验证的教程 |
| `documenting-runbooks` | 编写诊断、修复、回滚和验证流程 |

第二批共 5 个 skill 已经建立。每个 skill 仍应按使用反馈逐个完善，真实素材出现后至少做一次行为级冒烟测试，再决定是否增加或收窄章节。

### 第三批（补充覆盖）

| Skill 名称 | 目标 |
| --- | --- |
| `documenting-changes` | 说明版本差异、迁移动作、破坏性变更、废弃与时间线 |

第三批用于填补一个真实覆盖缺口：本家族原 9 个 skill 均不负责「从一个版本到另一个版本发生了什么、需要做什么」。经全文检索确认，9 个 skill 的 SKILL.md 与 reference 中 `changelog`、`变更说明`、`升级指南`、`发布说明` 命中数为 0，即这类文档在族内无归宿，只能被 ADR（讲单次决策）或契约文档的版本章节（讲兼容性）部分吸收，产出的是侧面而非完整迁移路径。

因此新增第 10 个 skill。它与相邻 skill 的边界：只写「变了什么、怎么升级」，不写候选方案的理由（属 ADR）、不写系统架构（属 `explaining-systems`）、不重复接口字段与数据模型细节（链接过去）。

## 目录结构

### 当前仓库安装形式

如果安装在使用这些 skill 的项目中，目录通常位于：

```text
.codex/skills/
├── README.md                          ← 家族选型入口
├── explaining-algorithms/
├── explaining-systems/
├── documenting-language-features/
├── documenting-architecture-patterns/
├── documenting-api-contracts/
├── documenting-data-models/
├── documenting-design-decisions/
├── documenting-tutorials/
├── documenting-runbooks/
├── documenting-changes/
└── _design/                           ← 设计文档与质量门校验脚本
```

每个 skill 示例：

```text
explaining-systems/
├── SKILL.md
└── references/
    ├── system.md
    ├── framework.md
    └── project.md
```

### 可发布仓库形式

以后需要发布或跨项目安装时，改为一个仓库托管多个 skill：

```text
technical-doc-skills/
├── explaining-algorithms/
├── explaining-systems/
├── documenting-language-features/
└── documenting-architecture-patterns/
```

使用方式：

```bash
npx skills add owner/repo@explaining-algorithms -g -y
npx skills add owner/repo@explaining-systems -g -y
```

## Skill 命名与描述

命名规则：

- 使用小写字母、数字和连字符
- 使用动作式名称
- 名称短且说明真实能力
- 不把文档种类全部堆在一个名字里

示例描述：

```yaml
---
name: explaining-algorithms
description: >-
  解释一个算法或数据结构，并在必要时产出可验证的技术文档。
  覆盖问题定义、核心思想、正确性、复杂度、实现、边界例和算法对比。
  不适用于语言语法说明、架构模式说明或整个系统解释。
---
```

```yaml
---
name: explaining-systems
description: >-
  解释或解剖一个系统、框架或项目代码库。
  覆盖目标、模块边界、数据流、源码组织、入口点、运行方式、
  失败模式、扩展机制以及概念与代码的映射。
---
```

描述应足够精确，让相似任务不会误选。

## 每个 SKILL.md 的统一结构

所有 skill 的 `SKILL.md` 都采用以下章节，正文语言可以跟随项目使用中文：

1. `## 使用边界`——用于 / 不用于两组清单
2. `## 写作前确认`——读者、目的、权威来源、范围，以及**分支判定**（接口种类 / 模型类型 / 对象子模式 / 模式是否有落地）
3. `## 写作流程`——可执行步骤
4. `## 输出契约`——语言、位置与命名（含调用方路径优先级）、完整性、事实标注，以及本 skill 的降级模式
5. `## 写作质量门`——交付前逐条可判定
6. `## 相关资源`——指向 reference，并提示先读其中的「事实标注与证据规范」
7. `## 与其他 skill 的边界`——互斥路由与拆分规则

正文应短于详细标准，详细领域标准放在 `references/` 中，避免每次写作都加载全部内容。

**章节结构不属于文档内容结构。** 上面约束的是 `SKILL.md` 自身怎么写；至于 `SKILL.md` 要求**产出的文档**采用什么结构，本家族不作固定要求：

- 产出文档的章节由**内容决定**，reference 的章节清单是可选清单，不是填空模板（依据：`algorithm-standard.md` 开篇「它不是仓库模板，也不是强制填空清单」）。
- 因此各 skill 的 `SKILL.md` **不设**「必须覆盖的内容结构」一节。
- 早期版本曾要求 SKILL.md 声明「必须覆盖的内容结构」，该要求已废止：它与「结构由内容决定」直接冲突，且实测中导致产出文档逐条复刻 reference 目录（首轮代码冒烟测试中 `data-model.md` 11 个 reference 章节全部出现、`pattern.md` 编号与顺序完全一致）。若将来需要统一结构，必须同时修改 reference 的相应声明，不能只改一侧。

### 冲突优先级（硬规则）

`SKILL.md` 是 `references/` 的入口摘要，摘要时可能丢失条件。因此：

- `SKILL.md` 与 `references/` 冲突时，**以 reference 为准**。
- 这条规则必须写进每个 `SKILL.md` 的输出契约节，避免 agent 按被压缩后的无条件措辞执行。
- 编写质量门时，凡领域内存在分支（接口种类、模型类型、操作类型、子模式）的，质量门必须写成条件式，并允许「不适用」作为通过结果。

### 降级模式（硬规则）

当某类文档的权威来源在本环境不存在时（无运行环境、无 schema、无迁移、无版本机制、无可运行示例），skill 不得让 agent 在「违规」与「不写」之间二选一，必须给出降级路径：

- 只允许使用不依赖该来源的事实标签；
- 禁止任何需要该来源才能得出的结论；
- 文档开头声明本次采用的分辨模式；
- 待确认内容集中成节并给出验证动作。

目前已有降级模式的 skill：`explaining-systems`（源码模式）、`documenting-language-features`（规范模式）、`documenting-api-contracts`（源码模式）、`documenting-data-models`（无 schema 模式）、`documenting-runbooks`（源码模式）、`documenting-tutorials`（条件模式）、`documenting-architecture-patterns`（理论模式）。

## 公共技术文档契约

每个 skill 都必须保留一份精简公共契约，作为独立运行时也能生效的底线：

- 写作前明确读者、目的、非目标和事实来源
- 未验证的内容不得写成事实
- 猜测、假设、预期结果要显式标注
- 结论先给，再展开原因
- 文档描述当前状态，不把历史演进写成当前行为
- 文档不复制代码，只解释代码不直接表达的设计、权衡和约束
- 示例必须能复现，至少包含正常例、边界例或错误例
- 每个文档应能追溯到权威源码、规范、实验或文档
- 仓库有本地文档和索引时，可以作为定位和链接上下文，但不得用较低质量的结构替换本 skill 的标准
- 不为了覆盖所有可能场景而写出空洞章节
- 不得残留未填充的占位段落；不适用的章节写「不适用」并给理由
- 每个被报告的数字必须能追溯到命名的脚本、命令或来源

### 统一事实标签词表

全族使用同一套标签，不得各写各的。详细规则见各 reference 的「事实标注与证据规范」一节：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 作者本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 作者本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 作者本人没有读到源码，但来源材料陈述了该事实 | 命令、配置项、路径、指标名、阈值 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

**选档顺序**：先问「本人读到源码了吗」→ `源码确认`；否则问「本人执行并看到输出了吗」→ `运行确认`；两者都否但来源材料有明确陈述 → `来源确认`。

`来源确认` 这一档是为「有来源、但作者未亲自核对」准备的。缺少它时，作者只能二选一：要么用 `源码确认` 冒充实读（不诚实），要么用 `文档确认`——而 `文档确认` 明文「不得作为行为依据」，导致**在只有二手材料的环境里一个字都写不出来**。首轮代码冒烟测试中，执行者被迫自造「源码确认（未实测）」32 次、「未在本机运行」12 次，正是这一缺口的表现。

对早期版本中散布的「尚未实测」「生产验证」「测试环境验证」「迁移文件确认」「ORM 确认」「契约文件确认」「版本可能变化」等说法：统一收敛到上表。领域特有的来源（迁移文件、ORM、合同文件、生产环境）作为标签的**依据位置**写在括号里，或作为限定词附加，例如「`源码确认`（迁移文件 `003_add_col.sql`）」或「`运行确认`（测试环境）」，而不再新增标签名。

### 证据书写规范

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中的 `[measured: …]`、截图数字或他人记录的性能数据一律标 `来源确认`，并写明「非本机运行结果」。
- **引用格式**：有行号写 `<文件>:<行号>`；只有文件名写 `<文件名>`；只有材料写「材料「<小节标题>」」；三者都没有写 `未验证`。不得编造行号。
- **不适用**：某章节在本对象上不适用时，写「不适用」并给一句理由，不留空、不省略。
- **唯一权威**：同一实体、类型或接口存在多份定义时，必须写出唯一权威定义及其位置，并说明其余定义与它的差异。
- **待验证清单格式**：集中收纳未验证项时使用固定列名 `编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察`，使不同文档可比较。

## 第一批 skill 内容设计

> **覆盖范围**：本节覆盖第一批 4 个 skill；第二批 5 个见「第二批 skill 内容设计」一节，第三批 1 个见该节前的列表说明。三批合计 10 个 skill 现均有内容设计。

### `explaining-algorithms`

目标文档是“算法说明”，不是代码注释，也不是项目运行报告。

必须覆盖：

- 算法解决的问题和输入输出约束
- 核心思想和关键不变量
- 步骤、伪代码或真实实现对应关系
- 正确性论证、终止条件和失败前提
- 时间复杂度、空间复杂度、最好/最坏/期望情形
- 实现关键点和容易踩的坑
- 普通示例、边界示例和反例
- 变体、相近算法和适用限制

不依赖任何项目仓库的模板文件。已有 README、索引和同主题文章只用于定位链接与术语，文档结构、正确性论证、复杂度前提和实现映射仍以本 skill 标准为准。

### `explaining-systems`

这个 skill 不是写产品简介，而是“解释或解剖”。需要根据对象选择三种子模式。

`SKILL.md` 中应包含：

| 对象 | 适用问题 | Reference |
| --- | --- | --- |
| 系统 | 它整体做什么、模块如何协作、运行后如何表现 | `references/system.md` |
| 框架 | 设计思想、核心 API、内部实现和扩展方式 | `references/framework.md` |
| 项目代码库 | 仓库结构、入口点、改动路径和调试方式 | `references/project.md` |

#### `references/system.md`

系统写作标准覆盖：

- 系统目标、目标用户、目标和非目标
- 运行环境、部署拓扑、外部依赖
- 模块划分、职责和边界
- 请求、数据、控制流全链路
- 状态和生命周期
- 外部接口、配置、可观测性
- 不变量、失败模式、安全和性能约束
- 哪些结论来自源码、运行观察、文档或假设

#### `references/framework.md`

框架解剖写作标准覆盖：

- 框架解决什么问题，和普通库的区别
- 设计哲学和核心抽象
- 核心 API、入口和生命周期
- 插件、回调、装饰器、配置等扩展点
- 内部模块结构和依赖关系
- 一次典型调用如何穿过内部模块
- 框架替你做了什么、没做什么
- 源码关键位置、扩展方式和常见误用

#### `references/project.md`

项目代码库解剖写作标准覆盖：

- 项目目标、输入输出和验收标准
- 仓库顶层结构和目录职责
- 构建、运行和测试入口
- 主入口和端到端调用链
- 核心业务模块、工具模块和基础设施模块
- 增加一个功能通常需要改动哪些文件
- 配置、环境变量和数据流
- 调试方式和常见问题
- 文档与代码的对应关系

### `documenting-language-features`

目标文档是“语言特性说明”，不是 API 手册，也不是入门教程。

必须覆盖：

- 特性解决的设计问题
- 语法形态和合法约束
- 语义、求值、类型检查、作用域和运行时行为
- 与其他特性的组合和交互
- 为什么采用当前设计而不是其他方案
- 正例、错误例和边界例
- 性能、安全性、兼容性和迁移影响
- 常见误区和调试路径

### `documenting-architecture-patterns`

目标文档是“模式说明”，应说明模式适合什么问题以及为什么值得付出代价。

必须覆盖：

- 上下文、问题和冲突力量
- 参与者、职责和协作方式
- 结构、调用流或数据流
- 优点、代价和失效方式
- 适用场景和不适用场景
- 相近模式、变体和反模式
- 在该项目中的真实落地位置
- 演进与兼容（引入前后的变化、变更历史、退出代价、混布兼容）

## 第二批 skill 内容设计

第二批 5 个 skill 原先只有一句目标描述，本节按第一批的写法补齐。每个 skill 回答三个问题：**该领域必须回答哪些问题**、**哪些问题只有真实素材才能回答**、**素材缺失时如何降级**。

### `documenting-api-contracts`

必须回答：

- 消费方到底能依赖什么：哪些是承诺，哪些只是当前实现
- 接口属于哪一类（网络 / 消息 / 进程内），因为三类必答的问题不同
- 每个操作的消息形态、字段约束、默认值与可空性
- 错误分类与可重试性：传输错误、校验错误、业务错误、权限错误分别怎么表现
- 有状态接口的状态转移：合法事件、非法事件、非法转移的返回
- 幂等、超时、重试、并发行为；不涉及时要显式写「不适用」而不是省略
- 版本策略与破坏性变更范围

**只有真实素材才能回答**：字段的可空性与默认值（要读 schema 或源码）、非法转移的实际返回码（要读实现或运行）、幂等窗口与超时默认值（要读配置）、错误响应体结构（要读代码或运行）。

**降级**：无机器可读 schema 时走源码模式（签名与默认值取自源码，标注 `源码确认`，运行类结论标 `未验证`）；进程内接口把传输/超时/重试/版本写「不适用」；同一接口存在多份实现时先定唯一权威实现再写。

### `documenting-data-models`

必须回答：

- 存了什么：实体、字段、类型、默认值、可空性、业务含义
- 不变量：跨字段的蕴含或互斥、哨兵值（空值用哪个特殊值表示）
- 关系是真实存在的还是仅命名相似；删除与级联行为
- 唯一性、软删除、时间戳语义
- 索引与查询路径的对应关系，而不是罗列全部索引
- 数据生命周期：来源、写入频率、保留期、删除方式
- 迁移的兼容路径与回滚风险

**只有真实素材才能回答**：字段的真实类型与约束（schema 或类型定义）、索引是否存在（DDL）、不变量是否被代码强制（读写入路径）、保留策略的实际执行者（读到调度代码才算）。

**降级**：无 schema 时以代码类型定义为权威并声明「无 schema 可对照」；无迁移时显式写「当前无迁移」而不是留空；模型类型（关系型/湖仓/向量/文件集合）决定约束章节取舍，不适用项写「不适用」加理由。

### `documenting-design-decisions`

必须回答：

- 当时要解决什么问题，在什么真实约束下
- 认真考虑过哪些候选方案，各自的代价是什么
- 最终选了什么、不选什么，判断标准是什么
- 后果：立即得到什么、引入什么成本、哪些问题被推迟
- 失效信号、回退条件与验证方式
- 决策状态与它被哪条记录取代

**只有真实素材才能回答**：候选方案是否真被考虑过（要有讨论、文档、实验或代码可指）、约束是否真实（要有项目、实验或外部条件可指）、后果是否可观察（要有指标或结构变化可指）。

**降级**：决策未落地时走未落地模式（状态如实标注、写明阻塞，区分「已发生的影响」与「预期影响」）；确实只评估过一个方案时如实写「本次仅评估一个方案，未做对比」，**不虚构陪衬方案**——这是本领域最容易犯的错。

### `documenting-tutorials`

必须回答：

- 读者完成教程后能做成的**具体任务**，以及终点状态
- 前置条件，且每项可检查（命令或可观察状态）
- 分步动作、每步的预期结果与常见偏差
- 正常路径与至少一个常见失败路径
- 环境版本、安装方式、数据来源
- 如何判断教程成功完成

**只有真实素材才能回答**：实际命令输出（要运行）、失败路径的真实报错（要复现）、版本相关的输出（要运行）、依赖是否存在（要检查环境）。

**降级**：无运行环境时走条件模式，强制给出 `提交哈希 + 运行环境版本 + 数据/随机种子`；三要素不齐时**不硬称条件模式**，改为显式声明缺项并按条件模式组织，补齐项列为待验证第一项。预期输出必须标 `[固定]` 或 `[随环境/版本变化]`；他人记录的实测值不算 `运行确认`。

### `documenting-runbooks`

必须回答：

- 什么症状适用本 runbook，什么症状不适用
- 适用服务、环境、操作类型与操作时间范围
- 停止条件与升级路径
- 执行前检查：状态确认、备份、权限
- 诊断步骤，每步给出命令与判读规则
- 修复动作、顺序、并发约束与影响范围
- 回滚的适用范围、前置条件与失败升级路径
- 恢复验证：如何证明故障已结束

**只有真实素材才能回答**：真实命令与日志位置、告警阈值与持续时间、日志格式、备份机制与权限模型、破坏性操作的真实后果。**没有这些时，runbook 的可执行性无从谈起**——这正是它必须降级而不是硬写的原因。

**降级**：无可运行环境时走源码模式，只写能从源码/配置/脚本推导的步骤，全部标 `来源确认（未实测）`，**禁止任何破坏性命令**，未验证步骤集中成节并声明「执行前必须先在测试环境走一遍」。停止条件写成阈值式或明确的具体信号；无值班联系人时给出 owner 与 issue 入口。回滚仅对发布/迁移/配置类操作适用，纯诊断型写「不适用」加理由。

## 公共规则的组织方式

多个 skill 需要共享部分硬规则，但不能让安装后的 skill 依赖另一个未安装的 skill。

建议：

1. 每个 skill 自带一份精简公共清单。
2. 详细领域写作标准放在各自 `references/` 中。
3. 公共清单开始重复且体积变大后，在发布仓库建立共享源文件。
4. 通过发布或同步脚本把共享规则复制进各 skill，保证每个安装结果独立可用。

## 与 `technical-writing` 的关系

`technical-writing` 是通用文档写作规范，适合管理结构、措辞、事实、修订和风格。

本文设计的技术文档 skill 负责内容选择：

- 某类主题应回答哪些问题
- 哪些章节必须存在
- 示例和证据应达到什么质量

两者是叠加关系，不是替代关系：

- 先判断文档主题
- 再按该主题写作标准组织内容
- 最后按通用写作规则做结构、事实和语言检查

如果环境中已安装 `technical-writing`，可在 `SKILL.md` 中提示使用它做最终写作检查。`SKILL.md` 本身不能假设它一定存在。

## 验证方案

### 文件级验证

每个新建 skill 使用 Codex 的 `skill-creator` 校验脚本：

```bash
python /Users/minghui.liu/.codex/skills/.system/skill-creator/scripts/quick_validate.py <skill-path>
```

校验内容：

- `SKILL.md` 存在
- frontmatter 有 `name` 和 `description`
- 命名符合小写连字符规则
- 没有未完成的占位内容

### 产出文档的机械校验

文件级校验只保证 skill 自身格式合法，不检查它写出的文档。为此提供配套脚本，把可机械判定的质量门落地：

```bash
python .codex/skills/_design/check_doc_quality.py <文件或目录>
python .codex/skills/_design/check_doc_quality.py --only placeholder docs/
python .codex/skills/_design/check_doc_quality.py --json docs/
python .codex/skills/_design/check_doc_quality.py --allow-pending algorithms/ engineering/
```

检查项与对应质量门：

| 检查项 | 对应质量门 | 级别 |
| --- | --- | --- |
| `placeholder` 残留占位段落 | 完整性：不得残留未填充占位段落 | error |
| `legacy-label` 词表外标签 | 事实标注：统一词表 | warning |
| `untraceable-number` 无来源数字 | 证据书写：每个数字可追溯 | warning |
| `unmarked-output` 未标记输出 | 证据书写：预期输出须标 `[固定]` / `[随环境/版本变化]` | warning |

两条判定规则会被误用，实现时需保持：

- **`legacy-label` 只在「标签位」报告**：位于反引号内、句末、斜杠分隔的并列标签中，或列表/表格单元格的行首。自然叙述（如「注明哪些步骤在测试环境验证过」）不算使用旧标签——早期版本用子串匹配，对这类句子持续误报。
- **`placeholder` 只认「裸提示」**：括号内容包含说明性标记（`本文件`、`不适用`、`来源确认`、`见 …` 等）时视为说明性括号，不算占位；否则短句括号会被误判。

退出码 0 表示无 error。本脚本只是质量门的下限检查，不能替代人工判断内容正确性。

本 skill 家族自身应保持 `0 error / 0 warning` 通过，作为回归基线。

#### 骨架文档与待办占位

仓库中存在尚未开工的条目（29 个 `状态：⬜ 未开始` 的 README），它们用模板搭了骨架，括号内是写给作者的待办提问。这些占位在实现之前**不可能**填成真内容——强行填写会违反本家族「没有真实实现时不得虚构文件和函数」的原则。

因此脚本区分两种情况：

- **骨架文档**：状态行声明 `未开始` / `待实现` / `骨架`。加 `--allow-pending` 时其占位降为 warning，exit code 为 0。
- **非骨架文档**：状态为「已完成 / 理论文档」或没有状态行。其占位**始终**是 error，即使加了 `--allow-pending`。

这条区分是本规范的核心判断：**占位本身不是问题，占位出现在声称已完成的文档里才是问题**。默认（不加参数）保持严格模式，避免依赖开发者记得加 flag 才能发现真实缺陷。

不建议为通过检查而修改骨架文档内容；要么用 `--allow-pending` 承认它们是待办，要么等实现后再写。

### 行为级验证

用真实请求对每个 skill 做一次冒烟测试：

- 让 `explaining-algorithms` 解释一个尚未成文的真实算法或数据结构

检查产出是否满足：

- 结论可追溯
- 示例可复现
- 边界、限制、成本和错误路径没有被隐藏
- 文档没有虚构源码位置

根据冒烟测试结果调整写作标准，避免只凭想象扩充章节。

## 完成标准

- 每个 skill 都有独立可用的 `SKILL.md`
- 描述能精准匹配任务，不会互相误抢
- 每个领域写作标准都有明确必须回答的问题
- 公共契约能在每个 skill 中独立生效

- 每个 skill 给出降级模式，规定权威来源缺失时的可用标签与禁止结论
- 每个 skill 规定输出契约：语言、位置与命名、完整性、事实标注

- 每个 skill 的每条质量门可被第三方判定通过与不通过
- 校验脚本通过；有真实素材可用的 skill 至少一次行为级验证通过，无素材的 skill 在文档中显式标注「本仓库不可验证」
