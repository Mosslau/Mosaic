# 数据模型写作标准

这个标准用于说明实体、字段、约束、关系、索引和数据生命周期。它回答的核心问题是：系统保存了什么，字段如何取值，实体如何关联，改动 schema 会带来什么风险。

它不是仓库模板。不是每个数据库或模型都需要长篇说明；选择读者最需要的信息，其他内容链接到 schema、迁移和代码，但所有结论仍要可追溯。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 直接读到源码、配置或 schema 得到的结论 | 结构、签名、默认值、常量 |
| `运行确认` | 亲自执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出视为未实测。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 模型定位

先给结论：

- 数据模型服务什么业务问题
- 主要写入方和读取方
- 数据是事务性、分析性、向量性还是配置性
- 文档描述的是当前 schema 还是设计目标
- 与相邻模型或存储系统的边界

## 权威来源

列出事实来源和优先级：

- 数据库迁移文件
- ORM、schema 或类型定义
- 服务中实际读写该数据的代码
- 种子数据、测试数据和生产数据样本
- 数据治理或模型评审文档

## 实体与字段

对核心实体使用字段表说明：

- 字段名、数据库类型或语言类型
- 是否必填、默认值、可空性
- 唯一性、枚举、范围和其他校验
- 字段的业务含义
- 字段由谁写入、何时写入

字段说明应从 schema 或类型定义核对，不能只按名称猜语义。

### 唯一权威定义

同一实体或类型存在多份定义时，必须写出唯一权威定义及其位置，并说明其余定义的类型差异与消费方差异。缺少这条说明时，文档视为未完成。

### 数据结构不变量与哨兵值

内存模型或代码类型定义必须写出跨字段不变量与哨兵值，例如：

- 空结果用哪个特殊值表示（`null`、空集合、`float("inf")`、`-1`）
- 两个字段之间的蕴含或互斥关系

只列字段名与类型不足以让读者正确使用该结构（依据：`源码确认`，以类型定义与使用点的实际判断为准）。

## 关系

说明关系是否存在，以及如何建立：

- 一对多、多对多、可选关系和继承关系
- 关系使用外键、联合键、中间表还是隐式 id
- 删除、更新和级联行为
- 关系是否在应用层保证
- 循环引用和孤儿记录如何处理

## 约束与不变量

写清系统必须保持的规则：

- 唯一性约束及其边界
- 数值、长度、格式和业务规则校验
- 软删除、版本号、审计字段的语义
- 并发下由谁保证一致性
- 约束被违反时的可观察行为

## 索引与查询路径

不要罗列全部索引。说明：

- 主要查询和写入模式
- 每个索引支持哪个查询路径
- 复合索引的字段顺序
- 分区、分片、向量索引或全文索引
- 写入放大、热点和过期索引风险

## 数据生命周期

说明数据从产生到删除的路径：

- 数据来源和入口
- 数据更新频率和生命周期
- 归档、清理、TTL 和保留策略
- 软删除与硬删除的区别
- 导出、备份和恢复入口

## 存储与序列化

如果存储方式影响语义，说明：

- 数据库、表、集合或对象存储位置
- JSON、二进制、向量或其他序列化格式
- 字符集、时区、精度和数值范围
- 多环境 schema 差异

## 迁移与兼容

对每个相关迁移说明：

- 改动内容和前置条件
- 向后兼容方式：加列、默认值、双写、回填还是版本迁移
- 回滚路径和数据丢失风险
- 哪些服务版本在迁移期间同时读取数据
- 迁移完成后如何验证数据一致

### 非关系型迁移

湖仓与向量索引场景下，迁移不止“加列/双写/回填”：

- 表格式演进（如 Iceberg / Delta / Hudi）允许加列、改类型别名、重命名，但各引擎的兼容窗口不同，必须写明使用的表格式与引擎版本
- 向量索引在维度、距离度量或 embedding 模型变化时需要重建，必须写明重建期间的读写策略与回滚方式
- 分区策略变更通常需要重写历史数据，必须写明重写范围与验证方式（如行数、校验和）

判断某类迁移是否适用：先写出本模型的存储格式与引擎，再选择对应策略；格式未知时标注 `未验证`，不得套用关系型策略。

没有迁移时显式写「当前无迁移」；不得用留空或“暂不涉及”代替。

## 示例与验证

给出可复现检查方式：

- 查看 schema 或迁移的命令
- 查询种子数据验证关系的 SQL、脚本或 API
- 验证约束被违反时系统行为的测试
- 文档结论对应的代码位置
