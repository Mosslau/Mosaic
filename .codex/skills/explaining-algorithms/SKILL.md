# Explaining Algorithms

## 使用边界

此 skill 用于以下任务：

- 解释一个算法的设计动机和核心思想
- 说明一个数据结构的性质、操作和复杂度
- 为已有实验代码补充算法说明，或解释源码中的算法实现
- 对比两个相近算法并说明适用边界

此 skill 不用于：

- 解释语言语法、语言特性或框架 API
- 写系统架构总览
- 写软件项目 README
- 写通用教程或完整课程
- 把“按某仓库模板补标题”当成文档任务

## 写作前确认

开始正文前先确定以下信息，并把结论记录到工作笔记中：

- 读者：学习算法的人、实现者、代码评审者，还是工程负责人
- 文档目的：理解原理、复现实验、选型，还是维护实现
- 文档类型：理论学习文档、实验实现说明、源码算法注释，还是对比说明
- 对象事实：对象名称、版本或上下文中能唯一标识算法/数据结构的依据
- 事实来源：权威教材、论文、源码文件、测试、运行输出或实验代码
- 非目标：本算法文档明确不解释什么
- 交付形态：纯理论说明、源码实现说明、实验对照说明，还是选型对比

## 写作流程

1. 先确定写作对象是纯理论主题、已有实现、实验对照还是多个候选方案，再选择该文档必须回答的核心问题；不逐节填空。
2. 用源码、规范、测试或运行记录建立事实基线。已有 README 或同主题文档只作为事实线索和引用上下文，不能替代本 skill 的质量标准，也不能因为要适配仓库模板而降低准确性。
3. 如果对象已有实现，先读源码和测试再写；纯理论主题没有实现时，明确写成理论说明或“示例为示意”，不虚构文件和函数。
4. 在起草前加载 `references/algorithm-standard.md`，先读其中的「事实标注与证据规范」，只选择与当前任务相关的其余部分。
5. 按“结论先行”写作：文档、章节和段落先给结论，再给依据。
6. 对每个关键结论标注来源或验证方式，并把无法验证的内容写成“未验证”。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；专有名词、代码与命令保留原文。
- **位置与命名**：已有约定目录时写入其中；无约定时，单算法单文档用 `<算法名>.md`，与实现同目录的说明用 `README.md`；不得因此覆盖或改写他人文档。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**无实现模式（降级）**：对象是纯理论主题、没有真实实现时，不因此停止写作，也不得虚构文件与函数。改为：
全文开头声明「理论说明」；源码路径、函数名、测试文件一律不写；示例标注「示意代码，非项目实现」；
复杂度与正确性论证照常给出，但必须写明所依据的教材、论文或规范；把「实现中是否真的如此」列入「待验证清单」。

本 skill 的说法若与 `references/algorithm-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 文档开头一段说明目标是算法还是数据结构，并给出唯一标识，例如实现语言、论文版本、规范版本或源码路径
- 输入、输出和隐式假设都写出；读者读完后能判断该算法是否适用于自己的问题。判定方式：文档中存在明确的输入来源、输出形式，以及至少一条可被违反的前提（如“假设无负权边”）
- 核心思想压缩为一个句子，且该句子可被正确性论证或反例检验，不使用“高效且强大”这类无法判定的描述
- 正确性论证给出可检查的步骤或不变量；出现“实验跑通所以正确”“看起来对”即视为不合格
- 数据结构说明覆盖每个核心操作的前置/后置条件、维护的不变量和复杂度，不把数据模型与算法文档混为一类
- 复杂度说明写出前提：数据结构、稠密或稀疏、最好/最坏/平均/期望、是否含输入空间
- 有真实实现时，实现部分与真实代码位置对应；没有真实实现时，不得出现“文件 `impl.py` 会做某事”这类虚构表述
- 示例至少覆盖一个正常例和一个边界例或反例；每个示例可复现，或明确标注“示意代码，非项目实现”
- 每个被报告的数字、复杂度或耗时都能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入
- 明确写出局限、失效场景和相近算法的替代关系
- 来源记录区分教材/论文、官方文档、源码、测试/运行记录和未验证的假设

## 与其他 skill 的边界

- 若目标是完整系统、框架或代码库，改用 `explaining-systems`。
- 若目标是语言语法或语言特性设计，改用 `documenting-language-features`。
- 若目标是可复用的架构模式，改用 `documenting-architecture-patterns`。
- 若同一请求同时要求算法说明与系统/契约说明，按上述边界拆成多份文档，不合并成一篇。
- 若用户只是提问、不要求产出文档，直接用对话回答，不套用本 skill 的文档结构。
