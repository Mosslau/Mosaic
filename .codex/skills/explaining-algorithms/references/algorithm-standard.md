# 算法或数据结构说明写作标准

这个 reference 定义算法或数据结构文档应回答的核心问题。它不是仓库模板，也不是强制填空清单：只写当前任务需要的部分，未验证的内容不得通过章节形式伪装成事实。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 直接读到源码、配置或 schema 得到的结论 | 结构、签名、默认值、常量 |
| `运行确认` | 亲自执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出视为未实测。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 写作前选择结构

先判断文档类别：

| 文档类别 | 重点 |
| --- | --- |
| 原理学习 | 动机、证明、复杂度、直觉、后续算法 |
| 数据结构说明 | 操作集合、不变量、复杂度、实现约束 |
| 已有实现说明 | 真实文件、函数职责、边界处理、与替代实现对照 |
| 实验对照 | 实现差异、结果一致性和性能差异来源 |
| 选型说明 | 多个算法对比、代价、适用数据、失效场景 |
| 源码说明 | 文件入口、函数职责、状态变化、关键分支 |

## 标题与状态

标题使用具体算法名、问题名或数据结构名。文档开头需要给出：

- 对象类型：算法、算法族还是数据结构
- 对象名称和能唯一标识它的版本/上下文，例如语言实现、论文版本、规范版本或源码路径
- 文档状态：理论说明、现有实现说明、实验说明还是尚未完成的草稿
- 如果文档属于已有系列，保留必要的链接和状态，但不得因此放弃本节要求的准确性

已有仓库文章可以用于定位术语、链接和状态，不能作为结构优先级；本 reference 是本类文档的写作标准。

## 解决什么问题

写清楚以下内容，直到读者能判断“该不该用这个算法”：

- 输入是什么，来自哪里
- 输出是什么，如何判断成功
- 问题模型是什么，例如图、序列、概率分布或高维向量
- 隐式假设是什么，例如无负权边、数据可比较、特征独立
- 必须满足的约束是什么

## 核心思想一句话

用一个可验证的句子说明算法为什么有效。不要用营销式描述，例如“高效且强大”。应写成类似：

> 在累计代价上加入一个不高估的终点估计，让搜索优先朝目标方向扩展，同时保留最优性。

## 正式定义或推导

根据主题选择以下内容：

- 符号定义
- 状态、动作、转移或数据结构定义
- 关键公式和每个符号的含义
- 关键性质，例如最优性、可采纳性、收敛性、无偏性
- 推导或证明步骤，避免只写结论

如果使用数学记号，必须解释每个变量和前提。纯代码算法也可以使用伪代码，但伪代码要与实现语义一致。

## 数据结构专用标准

当对象是数据结构时，不能只给出“能做什么”的能力列表，还要回答调用方依赖的精确语义：

- 数据元素、键、值、容量、所有权和并发约束是什么
- 每个核心操作的前置条件、后置条件和异常/返回语义是什么
- 每次操作后维护了哪些结构不变量
- 遍历、修改、删除、扩容时是否会失效引用、游标或迭代器
- 相等、哈希、比较、复制和序列化是否有额外要求
- 时间、空间和摊还复杂度按操作分别给出，并注明假设
- 该数据结构与相关算法、容器或存储模型的边界在哪里

如果解释的是一种实现，还要给出该实现使用的底层结构、扩容策略和关键状态。

## 正确性论证

正确性不能写“实验跑通了所以正确”。根据算法类型选择：

- 不变量：循环开始前、过程中和结束后哪些性质恒成立
- 终止性：为什么不会无限循环
- 最优性：为什么返回结果不比任何可行解差
- 概率算法：说明误差界和随机性前提
- 学习算法：说明目标函数、收敛条件和评价方式

给出可检查的论证步骤，必要时配合小规模反例。

## 复杂度分析

复杂度必须给出前提：

- 数据结构是数组、链表、哈希表还是树
- 图是稠密还是稀疏，节点数和边数分别是什么
- 比较的是最好、最坏、平均还是期望情形
- 空间是额外空间还是包含输入空间
- 是否假设哈希 O(1)、浮点稳定或随机访问

如果可以，用表列出时间、空间和额外假设。

### 复杂度陈述样例

不合格：“该算法时间复杂度 O(n log n)。”

合格：“在数组存储、原地排序、元素两两可比较，且不计比较之外的操作开销的前提下，平均时间复杂度为 O(n log n)，最坏为 O(n²)；额外空间 O(log n)，不含输入数组本身。”

差别在于：合格版本写出了数据结构、最好/最坏/平均、空间是否含输入、以及被忽略的开销假设；读者据此能判断自己的场景是否落入该前提。

## 实现要点

实现部分只解释真实存在、已由源码或测试确认的行为，不虚构文件、函数或文件职责。重点解释代码中没有直接表达的决策：

- 为什么使用当前数据结构
- 初始化条件为什么这样设置
- 循环或递归的终止条件如何保证
- 哪些判断必须在弹出、写入或更新时执行
- 哪些边界条件容易漏
- 数值稳定性、溢出、精度和并发问题
- 真实实现中的入口、核心函数和测试文件在哪里；同一对象存在多份实现时，写明哪一份是权威实现，其余实现与它的差异

文档不应假设存在某种固定文件名组合，例如手写实现、演示、基线或框架对照必须分别放在某几个文件中。实际有哪些文件就解释哪些文件，没有实现的主题应明说“无实现”或“示例为示意”。

## 示例与边界例

示例必须具体、可复现、可验证。

至少覆盖：

- 正常例：展示算法典型路径或结果
- 边界例：空输入、单元素、无解、满容量、全相同等
- 错误例或反例：说明什么条件下算法不适用或返回非预期结果

代码示例应能直接运行，或标明所在文件和调用方式；纯理论示例要注明“示意代码，非项目实现”，避免被误读为源码事实。

## 与基线或框架对照

如果文档面向实验对照，加入对照结论：

- 实现 A 和实现 B 的接口差异
- 结果是否一致，如何验证
- 时间和性能差异的来源
- 替代实现额外做了什么，例如正则化、并行、数值稳定

对照表要给出指标名和测量方式，不使用无法核实的“更快”“更好”。

## 局限与延伸

明确说明：

- 算法在什么条件下退化
- 哪些约束会破坏正确性或性能
- 哪些问题是这个算法的自然延伸
- 与后续算法的关系

如果这是一个系列文档，应给出链接或章节位置。

## 来源与验证记录

文档末尾列出关键来源，并区分：

- 教材或论文
- 官方文档
- 仓库实现文件
- 实验运行记录
- 当前未验证的假设

引用必须是可检查的，不写无法定位的泛泛来源。如果没有运行实验，就不在来源中写“实验运行记录”。
