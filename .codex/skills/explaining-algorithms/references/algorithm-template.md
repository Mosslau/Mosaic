# 算法说明文档模板

这个 reference 用于组织算法文档。它是指引，不是强制填空清单：当前任务不需要的章节应删除，绝不能为了套模板而灌水。

## 写作前选择结构

先判断文档类别：

| 文档类别 | 重点 |
| --- | --- |
| 原理学习 | 动机、证明、复杂度、直觉、后续算法 |
| 手写实现 | 数据结构和实现步骤、边界处理、与框架对照 |
| 选型说明 | 多个算法对比、代价、适用数据、失效场景 |
| 源码说明 | 文件入口、函数职责、状态变化、关键分支 |

仓库已有 `TEMPLATE.md` 或相似 README 时，本地约定优先于本模板。

## 标题与状态

标题使用具体算法名或问题名。如果是仓库内文档，保留仓库使用的状态说明和对应路线章节，例如 MindSpring 的 `algorithms/` 约定。

## 解决什么问题

写清楚以下内容，直到读者能判断“该不该用这个算法”：

- 输入是什么，来自哪里
- 输出是什么，如何判断成功
- 问题模型是什么，例如图、序列、概率分布或高维向量
- 隐式假设是什么，例如无负权边、数据可比较、特征独立
- 必须满足的约束是什么

## 核心思想一句话

用一个可验证的句子说明算法为什么有效。不要用营销式描述，例如“高效且强大”。应写成类似：

> 在累计代价上加入一个不高估的终点估计，让搜索优先朝目标方向扩展，同时保留最优性。

## 正式定义或推导

根据主题选择以下内容：

- 符号定义
- 状态、动作、转移或数据结构定义
- 关键公式和每个符号的含义
- 关键性质，例如最优性、可采纳性、收敛性、无偏性
- 推导或证明步骤，避免只写结论

如果使用数学记号，必须解释每个变量和前提。纯代码算法也可以使用伪代码，但伪代码要与实现语义一致。

## 正确性论证

正确性不能写“实验跑通了所以正确”。根据算法类型选择：

- 不变量：循环开始前、过程中和结束后哪些性质恒成立
- 终止性：为什么不会无限循环
- 最优性：为什么返回结果不比任何可行解差
- 概率算法：说明误差界和随机性前提
- 学习算法：说明目标函数、收敛条件和评价方式

给出可检查的论证步骤，必要时配合小规模反例。

## 复杂度分析

复杂度必须给出前提：

- 数据结构是数组、链表、哈希表还是树
- 图是稠密还是稀疏，节点数和边数分别是什么
- 比较的是最好、最坏、平均还是期望情形
- 空间是额外空间还是包含输入空间
- 是否假设哈希 O(1)、浮点稳定或随机访问

如果可以，用表列出时间、空间和额外假设。

## 实现要点

实现部分应遵循仓库真实代码，不虚构文件。重点解释代码中没有直接表达的决策：

- 为什么使用当前数据结构
- 初始化条件为什么这样设置
- 循环或递归的终止条件如何保证
- 哪些判断必须在弹出、写入或更新时执行
- 哪些边界条件容易漏
- 数值稳定性、溢出、精度和并发问题

对于 MindSpring 的手写算法实验，还应区分 `impl.py`、`demo.py`、`baseline.py` 和 `framework.py` 的职责，不把所有实现细节混在一处。

## 示例与边界例

示例必须具体、可复现、可验证。

至少覆盖：

- 正常例：展示算法典型路径或结果
- 边界例：空输入、单元素、无解、满容量、全相同等
- 错误例或反例：说明什么条件下算法不适用或返回非预期结果

代码示例应能直接运行，或标明所在的仓库文件和调用方式。

## 与基线或框架对照

如果文档面向工程实验，加入对照结论：

- 手写实现和框架实现的接口差异
- 结果是否一致，如何验证
- 时间和性能差异的来源
- 框架额外做了什么，例如正则化、并行、数值稳定

对照表要给出指标名和测量方式，不使用无法核实的“更快”“更好”。

## 局限与延伸

明确说明：

- 算法在什么条件下退化
- 哪些约束会破坏正确性或性能
- 哪些问题是这个算法的自然延伸
- 与后续算法的关系

如果这是一个系列文档，应给出链接或章节位置。

## 来源与验证记录

文档末尾列出关键来源，并区分：

- 教材或论文
- 官方文档
- 仓库实现文件
- 实验运行记录
- 当前尚未验证的假设

引用必须是可检查的，不写无法定位的泛泛来源。
