# Runbook 写作标准

这个标准用于编写可执行的运维处置文档。它回答的核心问题是：什么症状适合使用这个 runbook，值班人员按什么顺序检查，修复和回滚如何安全执行，恢复后如何验证。

它不是仓库模板。runbook 描述当前系统真实可执行的流程；每个步骤都应能在目标环境运行，未实测部分必须单独标注。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 我本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 我本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 我本人没有读到源码，但来源材料陈述了该事实；来源可能是引述源码的文档、他人整理的笔记或任务给定材料 | 命令、配置项、路径、指标名、阈值；**仅当该材料的原始出处指向源码或配置时使用** |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据；材料的原始出处是发布说明、会议记录、内部 wiki 等非源码文档时用此档 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- **选档顺序**：先问「我本人读到源码了吗」→ 是则用 `源码确认`；否则问「我本人执行并看到输出了吗」→ 是则用 `运行确认`。两者都否、但来源材料有明确陈述 → 用 `来源确认`。
- **不要用 `源码确认` 标注你只是转述的内容**。这正是 `来源确认` 要解决的问题：区分「作者亲自核对了源码」与「作者转述了一份声称来自源码的材料」。
- `来源确认` 的结论来自材料，作者不对其真实性负责，但必须负责标注它未经本人核对；需要读者据此行动时，配一个可自行复核的命令。
- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”“服务监听 `:9100`（来源确认，材料「Metrics endpoint」）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。
- **同一个结论只给一个标签；不要用「标签 + 限定词」表达单标签装不下的意思**。当一条结论里有一部分已确认、另一部分未确认时，拆成两句分别标注，而不是叠在一句上。例：

  ```text
  不合格：清单里含 011_add_capture_mode.sql，属新增（来源确认，未验证）
  合  格：清单里含 011_add_capture_mode.sql（来源确认，材料「migrations 目录」）。其变更类别无法判定，因为看不到 DDL（未验证）。
  ```

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **未运行的命令**：在文档没有对应环境、或作者没有执行过命令时，命令照给，但必须紧跟 `未验证` 并注明「作者未运行」，必要时补一句为什么要给一条没跑过的命令（读者照做即可验证）。**不得让读者以为那是实测输出。**
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中出现的 `[measured: …]`、截图数字或他人记录的性能数据，一律标 `来源确认`，并在紧邻处写明「非本机运行结果」。这是最容易误标的一类。
- **引用格式**：有行号时写 `<文件>:<行号>`；只有文件名时写 `<文件名>`；只有材料时写「材料「<小节标题>」」。三者都没有时写 `未验证`。**不得编造行号。**
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。正文中的说明性括号不属于占位，但不得以括号代替应写的内容。
- **待验证清单格式**：集中收纳未验证项时使用固定列名，使不同文档可比较：

  | 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
  | --- | --- | --- | --- |
  | V1 | <待确认的结论> | <缺什么证据：无源码 / 无环境 / 材料未给> | <可执行的命令或动作> → <看到什么算确认、看到什么算否定> |

- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 目标与适用范围

先写读者最需要的判断：

- 本 runbook 解决的故障或操作
- 适用服务和环境
- 操作时间范围：本流程保持有效的版本区间或时段
- 不适用哪些症状或场景
- 谁负责执行和审批

## 触发条件与症状

用可观察信号描述何时使用：

- 告警名称、错误文本或日志片段
- 用户可见故障表现
- 指标、状态或输出中的异常
- 直接符合的继续执行，不符合的转向其他 runbook

## 源码模式（无运行环境时）

没有可运行环境时，不因此停止写作，也不得虚构流程：

- 只写能从源码、配置、脚本或部署文件推导出的步骤，全部标注 `来源确认（未实测）`。
- 禁止任何破坏性命令（重启、删数据、改配置、切流量）；这类步骤一律不写入。
- 把上述步骤集中放在「未验证步骤」一节，并在开头写明“本 runbook 尚未在真实环境验证，执行前必须先在测试环境走一遍”。
- 诊断所需的日志位置、指标名、配置项若来自源码推断，标注来源位置。

## 停止与升级条件

在处理前说明风险边界：

- 哪些情况下不能继续自动操作
- 哪些症状表明需要升级
- 升级对象和联系方式
- 是否允许修改生产数据、重启服务或变更配置

停止条件写成可判定的阈值形式：

```text
当 <指标> <比较符> <阈值> 持续 <时长> 时停止
```

无适用阈值时，写明停止所依赖的具体信号（例如“连续两次重试仍返回同一错误码”）。

升级对象写成角色或负责人入口；没有值班联系人时给出 owner 与 issue 链接，不写“联系运维”。

## 执行前检查

列出执行破坏性操作前必须确认的状态：

- 当前服务和数据状态
- 备份或快照是否存在
- 是否有正在运行的变更
- 需要哪些权限或访问方式
- 预期的停机时间和影响范围

## 诊断步骤

按顺序给出能缩小范围的检查：

- 查看日志、指标、追踪或状态的位置
- 具体命令、查询或文件路径
- 每个检查输出代表什么
- 找到根因后进入哪个修复流程

诊断步骤必须基于真实日志格式和命令，不写“检查服务状态”这类没有入口的空泛步骤。

## 修复与恢复

说明处置操作：

- 修复动作和前置条件
- 操作顺序和并发约束
- 重试、回滚或清理机制
- 对数据、外部依赖和下游系统的影响

如果修复需要多个系统配合，写明执行顺序和同步方式。

## 回滚

回滚仅对发布、迁移、配置变更类操作适用。纯诊断型 runbook 写「不适用（本 runbook 不改变系统状态）」并说明理由。

对发布、迁移或配置类操作说明：

- 回滚到哪个版本或配置
- 回滚前需要备份什么
- 回滚期间是否停止写入或流量
- 回滚后如何处理已写入的新数据
- 回滚失败时的升级路径

## 恢复验证

给出能证明故障已结束的检查：

- 关键指标或日志恢复正常
- 用户流程端到端可跑通
- 数据一致性和残留任务检查
- 服务健康检查通过
- 如何确认无需进一步处理

验证写成「命令 → 期望输出/断言」形式；只写“确认指标恢复正常”不合格。

## 事后记录

说明处置完成后应保存什么：

- 问题发生时间和根因证据
- 执行了哪些步骤
- 与预期流程的差异
- 是否需要补充告警、测试或文档

事后记录是新的记录，不修改已经发生的操作历史。

## 示例

以下示例用同一条结论「诊断定位到连接池耗尽，恢复验证确认活跃连接数回落」演示两种证据条件下的写法。示例为说明性内容，不对应任何真实仓库。

### 证据充分：可指向真实配置与运行

诊断步骤（`命令 → 判读规则`）：

- `<诊断命令>` → 判读规则：输出 `<活跃连接数>` 持续接近 `<连接上限>` 判定为连接池耗尽，进入「释放连接」修复流程；远小于上限则排除本 runbook（阈值 `源码确认`，`<配置项>:<行号>`）。

恢复验证（`命令 → 期望输出/断言`）：

```text
# 命令：<验证命令>
# 期望输出/断言：[固定] `<活跃连接数>` 小于 `<安全阈值>`
# 期望输出/断言：[随环境/版本变化] 当前值 <数值>
```

停止条件：

```text
当 <活跃连接数> 大于 <安全阈值> 持续 <时长> 时停止
```

其中 `<安全阈值>` 与 `<时长>` 取自 `<配置项>:<行号>`（`源码确认`）。

### 证据受限：只有二手材料

同一结论仅来自材料「<故障处置小节>」（`来源确认`）：材料称诊断用 `<诊断命令>`、`<活跃连接数>` 高即连接池耗尽，但未给出 `<连接上限>` 与 `<安全阈值>` 的取值。

诊断步骤（`命令 → 判读规则`）：`<诊断命令>` → 判读规则：`<活跃连接数>` 高即连接池耗尽（`来源确认`，材料「<故障处置小节>」）。

恢复验证（`命令 → 期望输出/断言`）：`<验证命令>` → 期望输出/断言：`<活跃连接数>` 回落（`未验证`，未实测，无可用环境）。

| 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
| --- | --- | --- | --- |
| V1 | `<活跃连接数>` 的安全阈值与停止时长 | 无源码、无环境，材料未给阈值 | 读取 `<配置项>:<行号>` 中的连接上限 → 见到具体上限即据其推导安全阈值 |
| V2 | `<诊断命令>` 的实际输出格式 | 材料只给命令，未给输出 | 在测试环境运行 `<诊断命令>` → 能按 `<活跃连接数>` 判读即确认 |

对比可见：证据受限版本没有可执行的阈值、命令入口与实测输出，值班人员无法判定何时停止或升级。
