# Explaining Systems

## 使用边界

此 skill 用于以下任务：

- 解释一个可运行系统的整体架构和端到端行为
- 解剖一个框架，说明设计思想、核心抽象和内部实现
- 解剖一个项目代码库，说明目录职责、入口点、运行方式和改动路径
- 从代码、运行结果和文档中验证架构结论

此 skill 不用于：

- 解释单个算法
- 写语言特性说明
- 单独讲解一个架构模式
- 只复述 README 内容，不做源码和运行验证

## 写作前确认

先判断解剖对象属于哪一种：

| 对象 | 判定依据 | 使用的 reference |
| --- | --- | --- |
| 系统 | 有部署、运行环境、组件协作和服务行为 | `references/system.md` |
| 框架 | 提供可复用抽象、API 和扩展点，强调如何被调用 | `references/framework.md` |
| 项目代码库 | 是一组仓库源码，重点是文件结构、入口和改动路径 | `references/project.md` |

判定顺序固定，不要凭感觉选：

1. 若对象是"供他人调用以扩展能力"的抽象集合，且使用方需要写扩展点（回调、插件、继承、中间件），选 **框架**。
2. 否则若对象需要部署、有运行环境、有组件间协作和运行时行为，选 **系统**。
3. 否则若对象是一组仓库源码、关注点是"从哪里改"，选 **项目代码库**。
4. 三种特征同时存在时：以读者的首要目的为准（选型/理解行为 → 系统；扩展能力 → 框架；接手改代码 → 项目），并在文档开头写明选择理由。
5. 仍无法判定时，向用户确认，不要同时套用多份 reference。

随后确认：

- 读者：用户、开发者、架构师还是维护者
- 文档目的：理解系统、改造框架、接手项目、排障还是选型
- 文档范围：只解释一个模块、一条链路还是整个对象
- 对象事实：路径、版本/提交、运行环境或文档声称覆盖的时间点
- 可验证来源：源码文件、运行命令、配置、测试、实际输出或现有文档
- 是否具备可运行环境；不具备时按「输出契约」走源码模式
- 不确定点：哪些结论目前只能标记为假设

## 写作流程

1. 先发现对象的真实入口和事实来源：README、配置、测试、脚本、部署文件及源码都可以提供线索，但不能替代源码和运行验证。
2. 按对象选择对应的 `references/` 写作标准；先读其中的「事实标注与证据规范」，仓库已有文档或模板只作为待验证素材，不能优先于本 skill 的准确性要求。
3. 从入口点开始追踪一条真实的端到端链路，而不是只按目录名猜模块职责。
4. 对每个模块或流程结论找到源码位置并验证。
5. 区分“从代码确认”“从运行确认”“从文档确认”和“未验证”四类陈述。
6. 按“对象做什么、怎么运行、怎么改、会怎么失败”组织内容；没有观察或运行能力的对象要给出源码路径和验证入口。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；专有名词、代码与命令保留原文。
- **位置与命名**：系统说明优先放在约定文档区；项目代码库解剖放在仓库根或该项目的 `README.md`/`ARCHITECTURE.md`；不得覆盖已有文档而不说明。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**源码模式（降级）**：当对象没有可运行环境时，不因此停止写作。改为：全文只用「来源确认（未实测）」这一种标签；不写任何需要运行才能得出的结论（吞吐、延迟、内存实测值）；在文档开头明确声明“本文基于源码阅读，未做运行验证”；把想验证但未验证的点集中列入「待验证入口」。

本 skill 的说法若与所选 `references/` 文件冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 文档开头一段写明对象名称、覆盖的版本或提交、以及所选子模式及其理由
- 不把 README 或目录名当作架构事实；出现“根据目录名可知其职责”即视为不合格
- 每个模块职责写成一句可被证伪的陈述，并给出源码位置；不出现“核心模块”这类无法区分的统称
- 至少有一条端到端链路可追踪到入口、各模块和代码位置，读者能按文档复现该链路的追踪过程
- 状态、数据流和调用流之间不矛盾；存在矛盾时必须在文档中指出并说明以哪个为准
- 扩展、部署、调试和失败场景各至少覆盖一条；无可运行环境时，改以源码路径和验证入口代替，并标注未实测
- 每条关键结论带事实标签；无法标注来源的内容一律标「未验证」
- 文档包含可执行的复现方式或清晰的源码入口；读者据此能自行验证至少一条结论

## 与其他 skill 的边界

- 若对象只是一个算法或数据结构，改用 `explaining-algorithms`。
- 若只讲一个可复用的设计模式而不解剖某个具体对象，改用 `documenting-architecture-patterns`。
- 若重点是接口字段、错误与状态机，改用 `documenting-api-contracts`；若重点是存储实体与迁移，改用 `documenting-data-models`。
- 若同一请求同时要求系统解释与接口/数据说明，拆成多份文档并互相链接，不合并成一篇。
- 若用户只是提问、不要求产出文档，直接用对话回答。
