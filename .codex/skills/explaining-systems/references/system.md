# 系统解释写作标准

这个标准用于解释一个可运行系统。它回答的核心问题是：这个系统做什么、为什么这样组成、运行时数据怎么流动、在真实环境会怎样失败和恢复。

它不是仓库模板。现有工程 README、模板或设计稿可以指出材料位置和意图，但不能替代对实际源码、配置和运行行为的验证。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 直接读到源码、配置或 schema 得到的结论 | 结构、签名、默认值、常量 |
| `运行确认` | 亲自执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出视为未实测。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 对象与版本

正文开始前先固定解剖对象，避免把“某个类似系统”写成当前系统：

- 系统名称、仓库路径/服务名和实际覆盖的版本或提交
- 文档描述的是当前实现、设计目标还是历史版本
- 主要入口、配置和部署位置
- 本说明覆盖的系统边界和不覆盖的模块
- 哪些外部文档声称的内容尚未在源码或运行中得到确认

## 系统定位

写清楚以下内容，让读者能判断这个系统与他关心的问题是否匹配：

- 系统目标
- 主要用户和典型使用场景
- 输入、输出和端到端结果
- 目标和非目标
- 与相邻系统的边界

## 运行环境与依赖

说明：

- 运行平台和部署形态
- 外部依赖，例如数据库、消息队列、GPU、对象存储
- 配置来源和环境变量
- 如何启动、停止和验证健康
- 资源需求和规模假设

## 模块划分

模块说明应给出：

- 模块名称和目录或服务位置
- 模块职责，职责描述要具体，不说“业务模块”
- 模块之间的依赖方向
- 各模块拥有的数据或状态
- 哪些模块是核心路径，哪些是辅助能力

画模块关系时，用文字架构图或结构化列表，并确保与代码入口一致。

## 端到端链路

选择一条真实链路进行解剖，通常从入口到持久化、输出或外部调用：

1. 入口在哪里，HTTP、消息、定时任务还是 CLI
2. 请求如何经过认证、校验和路由
3. 哪些模块被调用，调用顺序如何
4. 数据在每一步发生什么转换
5. 状态在哪里被读取和写入
6. 结果如何返回或触发后续动作

链路的每一步都应记录代码入口、配置项或可执行命令，不凭印象描述。

## 状态与生命周期

解释系统的重要状态：

- 配置状态和应用状态分别存在哪里
- 数据生命周期从产生到归档或删除
- 任务、作业、会话或连接的状态机
- 并发时状态由谁保证一致
- 重启、升级或回滚时状态如何处理

## 接口、配置与可观测性

覆盖：

- 对外接口和协议
- 核心配置项及其效果
- 日志、指标、追踪和告警入口
- 调试时从哪里读取当前状态
- 健康检查和容量观察方式

## 失败模式与恢复

不要只写优点。对每个关键依赖，说明：

- 失败时的表现
- 系统是否有重试、降级、缓存或熔断
- 数据是否会丢失或不一致
- 人工恢复或自动恢复路径
- 如何验证恢复完成

## 安全、性能与规模约束

根据系统性质选择说明：

- 认证、授权、敏感数据和信任边界
- 吞吐量、延迟、并发和资源瓶颈
- 扩展方式是横向还是纵向
- 当前实现没有支持的规模上限

## 无运行环境时的写法

当系统无法运行时，不因此停止写作，也不得虚构运行结论：

- 全文只使用 `源码确认`、`文档确认`、`设计意图`、`未验证` 四种标签；不使用 `运行确认`。
- 不写任何需要运行才能得出的结论，例如吞吐、延迟、内存实测值、实际日志形态。
- 文档开头声明“本文基于源码阅读，未做运行验证”。
- 把需要运行才能确认的点集中列入「待验证入口」，每条给出可执行的验证动作。

## 权威位置与下一步

列出：

- 系统级文档入口
- 主要服务的源码入口
- 配置和部署入口
- 测试或实验入口
- 如果读者想深入一个模块，下一步应阅读什么

## 待验证入口

本节集中列出本文未验证、但读者可以自行验证的结论。每条写成「待验证结论 → 验证动作 → 期望观察」，例如：

- 「缓存命中率决定了 P99 延迟」→ 运行 `<压测命令>` → 观察指标 `<名称>` 在命中率下降时是否同步上升
- 「配置项 A 会改变模块 B 的行为」→ 修改配置并运行 `<命令>` → 观察输出是否变化

无可运行环境时，本节不可省略：它是读者接手验证的入口，也是本文与已验证文档的边界。
