# 系统解释写作标准

这个标准用于解释一个可运行系统。它回答的核心问题是：这个系统做什么、为什么这样组成、运行时数据怎么流动、在真实环境会怎样失败和恢复。

它不是仓库模板。现有工程 README、模板或设计稿可以指出材料位置和意图，但不能替代对实际源码、配置和运行行为的验证。

## 对象与版本

正文开始前先固定解剖对象，避免把“某个类似系统”写成当前系统：

- 系统名称、仓库路径/服务名和实际覆盖的版本或提交
- 文档描述的是当前实现、设计目标还是历史版本
- 主要入口、配置和部署位置
- 本说明覆盖的系统边界和不覆盖的模块
- 哪些外部文档声称的内容尚未在源码或运行中得到确认

## 系统定位

写清楚以下内容，让读者能判断这个系统与他关心的问题是否匹配：

- 系统目标
- 主要用户和典型使用场景
- 输入、输出和端到端结果
- 目标和非目标
- 与相邻系统的边界

## 运行环境与依赖

说明：

- 运行平台和部署形态
- 外部依赖，例如数据库、消息队列、GPU、对象存储
- 配置来源和环境变量
- 如何启动、停止和验证健康
- 资源需求和规模假设

## 模块划分

模块说明应给出：

- 模块名称和目录或服务位置
- 模块职责，职责描述要具体，不说“业务模块”
- 模块之间的依赖方向
- 各模块拥有的数据或状态
- 哪些模块是核心路径，哪些是辅助能力

画模块关系时，用文字架构图或结构化列表，并确保与代码入口一致。

## 端到端链路

选择一条真实链路进行解剖，通常从入口到持久化、输出或外部调用：

1. 入口在哪里，HTTP、消息、定时任务还是 CLI
2. 请求如何经过认证、校验和路由
3. 哪些模块被调用，调用顺序如何
4. 数据在每一步发生什么转换
5. 状态在哪里被读取和写入
6. 结果如何返回或触发后续动作

链路的每一步都应记录代码入口、配置项或可执行命令，不凭印象描述。

## 状态与生命周期

解释系统的重要状态：

- 配置状态和应用状态分别存在哪里
- 数据生命周期从产生到归档或删除
- 任务、作业、会话或连接的状态机
- 并发时状态由谁保证一致
- 重启、升级或回滚时状态如何处理

## 接口、配置与可观测性

覆盖：

- 对外接口和协议
- 核心配置项及其效果
- 日志、指标、追踪和告警入口
- 调试时从哪里读取当前状态
- 健康检查和容量观察方式

## 失败模式与恢复

不要只写优点。对每个关键依赖，说明：

- 失败时的表现
- 系统是否有重试、降级、缓存或熔断
- 数据是否会丢失或不一致
- 人工恢复或自动恢复路径
- 如何验证恢复完成

## 安全、性能与规模约束

根据系统性质选择说明：

- 认证、授权、敏感数据和信任边界
- 吞吐量、延迟、并发和资源瓶颈
- 扩展方式是横向还是纵向
- 当前实现没有支持的规模上限

## 权威位置与下一步

列出：

- 系统级文档入口
- 主要服务的源码入口
- 配置和部署入口
- 测试或实验入口
- 如果读者想深入一个模块，下一步应阅读什么

## 事实标注

对关键结论使用可验证标签，例如“源码确认”“运行确认”“文档确认”“设计意图”“尚未验证”。不得把预期行为写成已验证行为。
