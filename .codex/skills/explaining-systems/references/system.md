# 系统解释写作标准

这个标准用于解释一个可运行系统。它回答的核心问题是：这个系统做什么、为什么这样组成、运行时数据怎么流动、在真实环境会怎样失败和恢复。

它不是仓库模板。现有工程 README、模板或设计稿可以指出材料位置和意图，但不能替代对实际源码、配置和运行行为的验证。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 我本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 我本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 我本人没有读到源码，但来源材料陈述了该事实；来源可能是引述源码的文档、他人整理的笔记或任务给定材料 | 命令、配置项、路径、指标名、阈值；**仅当该材料的原始出处指向源码或配置时使用** |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据；材料的原始出处是发布说明、会议记录、内部 wiki 等非源码文档时用此档 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- **选档顺序**：先问「我本人读到源码了吗」→ 是则用 `源码确认`；否则问「我本人执行并看到输出了吗」→ 是则用 `运行确认`。两者都否、但来源材料有明确陈述 → 用 `来源确认`。
- **不要用 `源码确认` 标注你只是转述的内容**。这正是 `来源确认` 要解决的问题：区分「作者亲自核对了源码」与「作者转述了一份声称来自源码的材料」。
- `来源确认` 的结论来自材料，作者不对其真实性负责，但必须负责标注它未经本人核对；需要读者据此行动时，配一个可自行复核的命令。
- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”“服务监听 `:9100`（来源确认，材料「Metrics endpoint」）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。
- **同一个结论只给一个标签；不要用「标签 + 限定词」表达单标签装不下的意思**。当一条结论里有一部分已确认、另一部分未确认时，拆成两句分别标注，而不是叠在一句上。例：

  ```text
  不合格：清单里含 011_add_capture_mode.sql，属新增（来源确认，未验证）
  合  格：清单里含 011_add_capture_mode.sql（来源确认，材料「migrations 目录」）。其变更类别无法判定，因为看不到 DDL（未验证）。
  ```

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **未运行的命令**：在文档没有对应环境、或作者没有执行过命令时，命令照给，但必须紧跟 `未验证` 并注明「作者未运行」，必要时补一句为什么要给一条没跑过的命令（读者照做即可验证）。**不得让读者以为那是实测输出。**
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中出现的 `[measured: …]`、截图数字或他人记录的性能数据，一律标 `来源确认`，并在紧邻处写明「非本机运行结果」。这是最容易误标的一类。
- **引用格式**：有行号时写 `<文件>:<行号>`；只有文件名时写 `<文件名>`；只有材料时写「材料「<小节标题>」」。三者都没有时写 `未验证`。**不得编造行号。**
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。正文中的说明性括号不属于占位，但不得以括号代替应写的内容。
- **待验证清单格式**：集中收纳未验证项时使用固定列名，使不同文档可比较：

  | 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
  | --- | --- | --- | --- |
  | V1 | <待确认的结论> | <缺什么证据：无源码 / 无环境 / 材料未给> | <可执行的命令或动作> → <看到什么算确认、看到什么算否定> |

- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 对象与版本

正文开始前先固定解剖对象，避免把“某个类似系统”写成当前系统：

- 系统名称、仓库路径/服务名和实际覆盖的版本或提交
- 文档描述的是当前实现、设计目标还是历史版本
- 主要入口、配置和部署位置
- 本说明覆盖的系统边界和不覆盖的模块
- 哪些外部文档声称的内容尚未在源码或运行中得到确认

## 系统定位

写清楚以下内容，让读者能判断这个系统与他关心的问题是否匹配：

- 系统目标
- 主要用户和典型使用场景
- 输入、输出和端到端结果
- 目标和非目标
- 与相邻系统的边界

## 运行环境与依赖

说明：

- 运行平台和部署形态
- 外部依赖，例如数据库、消息队列、GPU、对象存储
- 配置来源和环境变量
- 如何启动、停止和验证健康
- 资源需求和规模假设

## 模块划分

模块说明应给出：

- 模块名称和目录或服务位置
- 模块职责，职责描述要具体，不说“业务模块”
- 模块之间的依赖方向
- 各模块拥有的数据或状态
- 哪些模块是核心路径，哪些是辅助能力

画模块关系时，用文字架构图或结构化列表，并确保与代码入口一致。

## 端到端链路

选择一条真实链路进行解剖，通常从入口到持久化、输出或外部调用：

1. 入口在哪里，HTTP、消息、定时任务还是 CLI
2. 请求如何经过认证、校验和路由
3. 哪些模块被调用，调用顺序如何
4. 数据在每一步发生什么转换
5. 状态在哪里被读取和写入
6. 结果如何返回或触发后续动作

链路的每一步都应记录代码入口、配置项或可执行命令，不凭印象描述。

## 状态与生命周期

解释系统的重要状态：

- 配置状态和应用状态分别存在哪里
- 数据生命周期从产生到归档或删除
- 任务、作业、会话或连接的状态机
- 并发时状态由谁保证一致
- 重启、升级或回滚时状态如何处理

## 接口、配置与可观测性

覆盖：

- 对外接口和协议
- 核心配置项及其效果
- 日志、指标、追踪和告警入口
- 调试时从哪里读取当前状态
- 健康检查和容量观察方式

## 失败模式与恢复

不要只写优点。对每个关键依赖，说明：

- 失败时的表现
- 系统是否有重试、降级、缓存或熔断
- 数据是否会丢失或不一致
- 人工恢复或自动恢复路径
- 如何验证恢复完成

## 安全、性能与规模约束

根据系统性质选择说明：

- 认证、授权、敏感数据和信任边界
- 吞吐量、延迟、并发和资源瓶颈
- 扩展方式是横向还是纵向
- 当前实现没有支持的规模上限

## 无运行环境时的写法

当系统无法运行时，不因此停止写作，也不得虚构运行结论：

- 全文只使用 `源码确认`、`文档确认`、`设计意图`、`未验证` 四种标签；不使用 `运行确认`。
- 不写任何需要运行才能得出的结论，例如吞吐、延迟、内存实测值、实际日志形态。
- 文档开头声明“本文基于源码阅读，未做运行验证”。
- 把需要运行才能确认的点集中列入「待验证入口」，每条给出可执行的验证动作。

## 权威位置与下一步

列出：

- 系统级文档入口
- 主要服务的源码入口
- 配置和部署入口
- 测试或实验入口
- 如果读者想深入一个模块，下一步应阅读什么

## 待验证入口

本节集中列出本文未验证、但读者可以自行验证的结论。每条写成「待验证结论 → 验证动作 → 期望观察」，例如：

- 「缓存命中率决定了 P99 延迟」→ 运行 `<压测命令>` → 观察指标 `<名称>` 在命中率下降时是否同步上升
- 「配置项 A 会改变模块 B 的行为」→ 修改配置并运行 `<命令>` → 观察输出是否变化

无可运行环境时，本节不可省略：它是读者接手验证的入口，也是本文与已验证文档的边界。

## 示例

以下用同一结论演示两种证据条件下的写法差异。结论：模块 A 通过消息队列异步通知模块 B。

### 证据充分：可指向真实代码与运行

```markdown
模块 A 位于 `<模块目录A>`，模块 B 位于 `<模块目录B>`，A 只通过消息队列把事件异步通知给 B（源码确认，`<模块目录A>/<发布文件>.<扩展名>:<行号>`、`<模块目录B>/<订阅文件>.<扩展名>:<行号>`）。

- A 的投递调用位于 `<模块目录A>/<发布文件>.<扩展名>:<行号>`，使用队列客户端的 `publish`，且未出现对 B 的直接 import（源码确认）。
- B 的消费注册位于 `<模块目录B>/<订阅文件>.<扩展名>:<行号>`，订阅主题与 A 投递主题同名，主题常量定义于 `<配置文件>:<行号>`（源码确认）。
- 运行 `<启动命令>` 并触发一次 A 的写入，实际输出（运行确认）：
  # 输出：[随环境/版本变化]
  publish topic=<主题名>
  consume topic=<主题名> module=B
  # 退出码：0 [固定]
```

### 证据受限：只有二手材料

```markdown
设计材料称模块 A 通过消息队列把事件通知给模块 B（来源确认，材料「<小节标题>」），并给出主题名 `<主题名>`（来源确认，材料「<小节标题>」）。

- 材料未给出投递与订阅的代码位置，因此「A 不直接调用 B」无法确认（未验证）。
- 「B 确实消费该主题」仅有材料陈述，未经本人读码或运行核对（未验证）。

| 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
| --- | --- | --- | --- |
| V1 | A 与 B 之间不存在直接调用 | 无源码，材料未给调用点 | 在 `<模块目录A>` 检索对 `<模块目录B>` 的 import 或调用 → 无命中算确认，出现直接调用算否定 |
| V2 | B 实际消费 A 投递的主题 | 材料只声称，未给订阅位置 | 读 `<模块目录B>/<订阅文件>.<扩展名>` 并运行 `<启动命令>` → 日志出现该主题消费记录算确认 |
```

对照：证据受限版把「通过队列通知」限定为「材料如此陈述」，把「无直接调用」「B 实际消费」降为 `未验证` 与待验证项，不得写得与证据充分版一样肯定。
