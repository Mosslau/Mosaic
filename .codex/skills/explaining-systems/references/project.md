# 项目代码库解剖写作标准

这个标准用于解剖一个项目代码库，目标是让读者理解：这个项目怎么运行，代码怎么组织，想改一个功能或排查一个问题时应该从哪里下手。

它不是仓库模板。README 或类似本地文档只能作为线索和待核对声明，项目结构、行为与改动路径必须由真实源码、配置和可运行入口确认。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 直接读到源码、配置或 schema 得到的结论 | 结构、签名、默认值、常量 |
| `运行确认` | 亲自执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出视为未实测。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 对象与版本

开始前记录解剖对象：

- 项目名称、仓库路径和当前版本/提交
- 项目定位来自源码事实还是来自 README 愿景
- 文档覆盖目录边界和明确不覆盖的内容
- 是否有运行环境、依赖和数据可用于验证

## 项目定位

说明：

- 项目要解决什么问题
- 项目输入、输出和成功标准
- 项目是学习实验、生产系统还是原型
- 当前成熟度
- 与相邻项目或目录的关系

## 仓库结构

用一棵真实目录树解释项目。每个重要目录必须说明职责，不能只列目录名：

- 入口和主程序位置
- 业务代码位置
- 工具或基础设施代码位置
- 配置、数据、测试和文档位置
- 哪些目录是样例或临时内容

如果目录很大，选择与核心链路相关的部分详细解释，其余给出索引即可。

## 运行、构建与测试

给出可直接执行的步骤：

- 如何安装依赖
- 如何构建
- 如何运行
- 如何测试
- 需要哪些外部服务、环境变量、数据或硬件
- 如何验证运行结果符合预期

优先从项目的 `README.md`、`pyproject.toml`、Makefile、启动脚本和测试配置中确认，不写虚构命令。

## 端到端调用链

找到真实入口并追踪完整流程：

1. 用户或上游从哪里进入
2. CLI、服务、脚本或 notebook 的入口
3. 数据如何被读取、转换和输出
4. 核心模块按什么顺序被调用
5. 异常和失败在哪些位置可能发生

每条关键路径给出文件位置和关键函数。

## 核心业务模块

对代码库中决定项目价值的模块，深入解释：

- 模块解决什么问题
- 对外提供什么能力
- 内部依赖什么
- 最容易修改和最容易出错的部分
- 单元测试或集成测试覆盖在哪里

不同代码类别如果有不同职责，应按源码中的真实边界分开说明；不要把目录名、README 意图或“实验/生产”的预期直接写成模块行为。

## 改动路径

从实际任务出发，说明代码修改方式：

- 增加一个新输入格式需要改哪里
- 调整模型或接口需要改哪里
- 修复一个已知问题通常需要动哪些文件
- 新代码如何接入测试和文档

## 配置、数据与外部依赖

说明：

- 配置位置和主要配置项
- 依赖哪些库、服务和外部资源
- 数据从哪里来、存在哪里
- 调试环境、开发环境、生产环境差异

## 调试路径

解释项目实际调试方式：

- 日志在哪里输出
- 是否有断点推荐位置
- 哪些脚本适合缩小问题范围
- 常见报错与可能原因
- 如何对比预期结果和实际结果

## 文档与代码对应关系

最后建立导航：

- README 解释了什么
- 哪些模块缺少文档
- 现有文档是否与实际代码一致
- 新读者按什么顺序阅读代码

## 无运行环境时的写法

无法构建或运行时：只用 `源码确认`、`文档确认`、`设计意图`、`未验证` 标签；运行/构建/测试一节给出命令，但每条标注「未实测」，并说明需要的环境；不把 `pyproject.toml`、`package.json` 等声明的脚本直接写成可用命令。

## 同一实体多份定义的处理

同一类型、接口或配置在不同文件中被定义多次时，必须写出唯一权威定义及其位置，并说明其余定义与它的差异；不得只描述其中一份而不说明选择理由（依据：`源码确认`，以实际被调用方导入的那份为权威）。
