# 项目代码库解剖写作标准

这个标准用于解剖一个项目代码库，目标是让读者理解：这个项目怎么运行，代码怎么组织，想改一个功能或排查一个问题时应该从哪里下手。

它不是仓库模板。README 或类似本地文档只能作为线索和待核对声明，项目结构、行为与改动路径必须由真实源码、配置和可运行入口确认。

## 对象与版本

开始前记录解剖对象：

- 项目名称、仓库路径和当前版本/提交
- 项目定位来自源码事实还是来自 README 愿景
- 文档覆盖目录边界和明确不覆盖的内容
- 是否有运行环境、依赖和数据可用于验证

## 项目定位

说明：

- 项目要解决什么问题
- 项目输入、输出和成功标准
- 项目是学习实验、生产系统还是原型
- 当前成熟度
- 与相邻项目或目录的关系

## 仓库结构

用一棵真实目录树解释项目。每个重要目录必须说明职责，不能只列目录名：

- 入口和主程序位置
- 业务代码位置
- 工具或基础设施代码位置
- 配置、数据、测试和文档位置
- 哪些目录是样例或临时内容

如果目录很大，选择与核心链路相关的部分详细解释，其余给出索引即可。

## 运行、构建与测试

给出可直接执行的步骤：

- 如何安装依赖
- 如何构建
- 如何运行
- 如何测试
- 需要哪些外部服务、环境变量、数据或硬件
- 如何验证运行结果符合预期

优先从项目的 `README.md`、`pyproject.toml`、Makefile、启动脚本和测试配置中确认，不写虚构命令。

## 端到端调用链

找到真实入口并追踪完整流程：

1. 用户或上游从哪里进入
2. CLI、服务、脚本或 notebook 的入口
3. 数据如何被读取、转换和输出
4. 核心模块按什么顺序被调用
5. 异常和失败在哪些位置可能发生

每条关键路径给出文件位置和关键函数。

## 核心业务模块

对代码库中决定项目价值的模块，深入解释：

- 模块解决什么问题
- 对外提供什么能力
- 内部依赖什么
- 最容易修改和最容易出错的部分
- 单元测试或集成测试覆盖在哪里

不同代码类别如果有不同职责，应按源码中的真实边界分开说明；不要把目录名、README 意图或“实验/生产”的预期直接写成模块行为。

## 改动路径

从实际任务出发，说明代码修改方式：

- 增加一个新输入格式需要改哪里
- 调整模型或接口需要改哪里
- 修复一个已知问题通常需要动哪些文件
- 新代码如何接入测试和文档

## 配置、数据与外部依赖

说明：

- 配置位置和主要配置项
- 依赖哪些库、服务和外部资源
- 数据从哪里来、存在哪里
- 调试环境、开发环境、生产环境差异

## 调试路径

解释项目实际调试方式：

- 日志在哪里输出
- 是否有断点推荐位置
- 哪些脚本适合缩小问题范围
- 常见报错与可能原因
- 如何对比预期结果和实际结果

## 文档与代码对应关系

最后建立导航：

- README 解释了什么
- 哪些模块缺少文档
- 现有文档是否与实际代码一致
- 新读者按什么顺序阅读代码

## 事实标注

项目结构可以来自目录树，模块行为必须来自源码确认。若文档描述比代码新或旧，需要明确指出，不替代码“脑补”状态；README 声明、目录推测和实际验证必须分开标注。
