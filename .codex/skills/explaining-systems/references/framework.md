# 框架解剖写作标准

这个标准用于解剖一个可复用框架或库。它不能只写“怎么调用 API”，还要回答：框架的设计思想是什么，调用后内部发生了什么，扩展点在哪里，哪些能力由框架承担，哪些能力必须由使用方承担。

它也不是仓库模板。已有教程和项目文档可以提供入口，但“框架内部如何运行”的结论必须能追溯到源码、测试或可观察行为。

## 对象与版本

开始前记录解剖对象：

- 框架名称、版本/提交、语言和包管理器来源
- 文档覆盖的 API 版本和运行环境
- 文档描述的是官方语义、源码实现，还是某个项目中的使用方式
- 与普通库、平台、插件和框架内层模块的边界

## 定位与设计哲学

先写清楚：

- 框架解决什么问题
- 它和普通函数库、平台或业务系统的区别
- 框架主张的设计哲学，例如约定优于配置、显式优于隐式、单向数据流
- 面向的典型使用者和使用场景
- 框架边界，什么场景不应使用它

## 核心抽象

框架通常由少量核心抽象构成。对每个抽象说明：

- 抽象名称和概念含义
- 使用方提供什么，框架提供什么
- 生命周期何时创建、运行、销毁
- 在框架内部的职责
- 对应代码位置

例如：训练框架中的模型、数据集、优化器、调度器、回调；Web 框架中的应用、路由、中间件、请求上下文。

## 主流程解剖

选择一条最典型的流程，例如一次请求、一次训练、一次渲染或一次任务执行，追踪框架如何把它调度完成：

1. 使用方从哪里调用入口
2. 框架如何创建上下文和核心对象
3. 核心对象如何协作
4. 钩子、回调或扩展点何时触发
5. 框架在哪个阶段替使用方完成默认行为
6. 流程结束时如何清理资源或返回结果

主流程应给出源码入口和关键调用位置。

## API 与扩展点

说明使用方真正需要知道的最小 API：

- 必用 API 和生命周期顺序
- 可选 API 和高级能力
- 配置或声明式选项
- 扩展机制，例如继承、组合、回调、插件、中间件、装饰器
- 官方扩展和社区扩展的区别
- 版本更新时哪些 API 容易变化

不要复制框架的完整 API 文档，只保留本框架文档场景所需部分，并链接权威参考。

## 内部模块与依赖

解剖内部结构：

- 核心模块有哪些
- 模块之间如何依赖，是否允许循环依赖
- 公共抽象、内部实现和平台适配分别在哪里
- 框架如何隔离内核与插件
- 内部数据结构和状态由谁拥有

## 框架做了和没做的事

用明确清单区分职责：

- 框架负责的生命周期、调度、资源管理或默认策略
- 使用方必须提供的业务逻辑、数据格式或生命周期钩子
- 框架不负责的错误处理、安全、持久化或并发策略
- 框架默认行为在什么情况下会带来意外

## 运行机制与限制

解释关键运行机制：

- 初始化、执行、清理各阶段
- 线程、进程、异步任务或设备资源的组织方式
- 错误传播方式
- 性能开销主要来自哪里
- 哪些能力有明确边界，例如不支持的热更新、不保证的实时性

## 常见误用与调试路径

对使用者最有价值的部分：

- 调用顺序错误导致的典型问题
- 扩展点写错位置导致的典型问题
- 状态或生命周期误解导致的资源泄漏
- 如何定位“框架自动执行了没想到的行为”
- 调试时读取日志、状态或断点的位置

## 源码导航

列出：

- 框架仓库顶层目录结构
- 核心抽象的定义位置
- 主流程入口
- 扩展点接口
- 测试或示例目录

## 事实标注

框架行为必须尽量由源码确认。API 使用习惯可以来自文档，但“内部如何运行”不能只引用教程；无法确认的版本差异和内部实现要显式标注。
