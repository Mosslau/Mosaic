# Documenting Language Features

## 使用边界

此 skill 用于以下任务：

- 解释一个语法结构为什么这样设计
- 说明一个语言特性的语义和运行时行为
- 解剖编译、类型检查或执行阶段如何处理一个特性
- 解释多个特性如何组合、互相限制或产生歧义
- 说明版本变更、兼容性和迁移影响

此 skill 不用于：

- 写通用语言入门教程
- 为某个框架或库编写 API 使用手册
- 解释整个框架或系统
- 解释一个算法

## 写作前确认

开始前确认：

- 读者：语言使用者、框架作者、编译器实现者还是学习编程的人
- 文档目的：学会使用、理解设计、做兼容性判断，还是阅读实现
- 特性范围：语法、语义、类型系统、运行时、工具链还是生态惯例
- 权威来源：语言规范、官方参考、编译器源码、RFC、可运行实验或示例代码
- 材料边界：已有文章只用于定位术语和链接，不能替代规范或实验
- 是否具备可运行的解释器/编译器；不具备时按「输出契约」走规范模式

## 写作流程

1. 先读语言规范或官方资料，确认术语和精确行为，不以二手教程为准。
2. 如果目标环境已有相关文章，只把它当作补充线索和引用上下文，不为了匹配仓库文档风格而放弃本 skill 的验证要求。
3. 在起草前加载 `references/language-feature-standard.md`，先读其中的「事实标注与证据规范」。
4. 将“语言现状”“设计动机”“历史原因”分开写，不要混成同一层叙述。
5. 用最小可运行示例验证关键语义；不能运行的示例要说明错误来自哪一阶段。
6. 对边界行为给出编译、解释、执行或类型检查的可观察结果。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；语法、标识符与错误信息保留原文。
- **位置与命名**：按 `<语言或特性名>.md` 命名；已有语言文档目录时放入其中。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「规范确认（未实测）」，不得以留空或省略代替。

**规范模式（降级）**：无法实际运行示例时，不因此停止写作。改为：所有语义结论标注为「规范确认（版本 X）」或「源码确认」；示例标注「未在本机运行」；绝不写“实测输出为…”这类未发生的运行结论；把需要运行才能确认的行为集中列入「待验证清单」。

本 skill 的说法若与 `references/language-feature-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 文档开头一段写明语言、特性名、所依据的规范版本或实现版本，以及本文写的是规范行为、实现行为还是示例观察
- 特性动机和语法形式先讲清，再讲内部实现；顺序颠倒即结构不合格
- 语法一节给出至少一个合法例及其精确形态；只写“大致格式”不合格
- 语义一节说明求值顺序/时机、副作用或生命周期，以及编译期与运行期的分工
- 示例覆盖合法例、非法例和边界例各至少一个；每个示例标注运行的语言/工具版本与预期输出或错误
- 无法运行的示例说明原因并标注「未在本机运行」；不出现“实测输出为…”
- 特性与其他特性的交互至少给出一组可运行示例，或明确标注为未验证；只写“通常可以”不合格
- 设计权衡写出代价，不只列优点；每条代价能对应到一个可观察结果（报错形态、性能开销、可推断性下降）
- 每个被引用的版本行为都能追溯到规范条款、提案编号或可运行的命令；无法追溯的不得写入
- 不确定的语义不得写成确定结论

## 与其他 skill 的边界

- 若目标是框架或库的 API 用法，改用 `explaining-systems` 的框架子模式。
- 若目标是算法或数据结构，改用 `explaining-algorithms`。
- 若重点是接口字段与错误契约，改用 `documenting-api-contracts`。
- 若用户只是提问、不要求产出文档，直接用对话回答。
