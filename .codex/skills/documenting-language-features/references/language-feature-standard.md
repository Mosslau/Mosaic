# 语言特性说明写作标准

这个标准用于解释一门程序设计语言的语法、特性设计或原理。它回答的核心问题是：这个特性解决什么问题，怎么写合法，运行时或编译时怎么解释，为什么这样设计，会带来什么代价。

它不是仓库模板，也不是让每节都写满的清单。不相关的部分删除，留下能回答读者问题的内容。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 直接读到源码、配置或 schema 得到的结论 | 结构、签名、默认值、常量 |
| `运行确认` | 亲自执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出视为未实测。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 特性定位

先给结论，说明这个特性是什么、解决什么问题：

- 特性名称和典型使用场景
- 解决的核心问题
- 特性是语法糖、新语义、类型能力、运行时能力还是工具链能力
- 它替代了哪种旧写法
- 什么场景不应使用这个特性

## 语法与合法约束

描述精确语法，不要只给“大致格式”：

- 合法写法的形态
- 可省略部分、默认值和组合规则
- 标识符、作用域、类型、上下文等约束
- 哪些看起来合法但实际不合法
- 语法优先级、结合性、分号或括号规则

应使用具体代码片段说明语法，而不是只描述概念。

## 语义模型

解释代码执行或编译时的真实含义：

- 求值顺序和时机
- 值、引用、所有权、副作用和生命周期
- 类型推导、类型转换、错误处理和运行时检查
- 编译期与运行期的分工
- 特性是否引入隐式行为

例如闭包、async、泛型、trait、装饰器、宏、模式匹配等特性，必须说明其语义模型，不只是使用口诀。

## 运行时或编译阶段行为

根据主题说明：

- 编译器或解释器在哪个阶段处理该特性
- 是否生成额外对象、函数、检查或间接层
- 对启动、内存、并行、栈或异步运行的影响
- 热重载、JIT、AOT、解释执行等环境差异
- 工具链诊断：语法错误、类型错误、运行时异常分别在哪一阶段出现

## 与其他特性的交互

检查该特性与以下能力组合时的行为：

- 泛型、重载、继承或组合
- 并发、异步、锁和生命周期
- 异常、错误返回或取消
- 模块、包、可见性和导入
- 字符串、集合、数值和 I/O 等基础类型

交互必须给可运行示例，不能只写“通常可以”。

## 设计动机与权衡

解释设计选择：

- 作者或社区为什么引入这个特性
- 相比替代方案，它减少或增加了什么表达成本
- 它牺牲了什么，例如简单性、性能、可推断性、互操作性
- 当前设计留下的边界或已知痛点
- 相近语言如何选择不同设计

这一节属于“为什么”，不应写成“官方这么做，所以正确”。

## 示例

示例应覆盖：

- 最小正例，展示核心用法
- 最小反例或非法例，说明约束和诊断信息
- 边界例，例如空集合、嵌套、循环依赖、超长链、单例
- 真实场景中的合理用法

每个示例注明：

- 运行的语言或工具版本
- 预期输出或错误
- 示例来自规范、实验还是个人测试

## 版本、兼容与迁移

如果主题与版本相关：

- 特性在哪个版本引入
- 语法或行为是否有变化
- 启用或禁用是否需要 flags
- 旧代码是否仍然兼容
- 迁移旧写法时需要注意哪些行为变化

无法运行验证版本差异时，标注为 `未验证` 并给出应当运行的命令，不写成确定结论。

## 常见误区

列出该特性最容易写错或理解错的地方：

- 误以为语法等价于某种语义
- 忽略求值时机、所有权或生命周期
- 忽略与其他特性的组合规则
- 依赖未定义的求值顺序
- 在只兼容旧版本的环境使用新语法

## 示例标注样例

不合格：

```python
# 运行输出：3
```

合格：

```python
# 环境：CPython 3.11.4 / 规范版本：PEP 604
# 命令：python -c "print(len([1,2,3]))"
# 输出：3  [固定]
```

差别在于：合格版本给出运行环境、命令与标记；读错时读者能判断是版本问题还是文档问题。

## 权威来源

列出：

- 语言规范或官方参考
- 编译器源码或实现文档
- 原始提案、RFC 或设计记录
- 可用于验证语义的测试或示例

文档中的精确行为应优先来自规范或可运行实验。
