# 设计决策记录写作标准

这个标准用于记录 ADR 或设计决策。它回答的核心问题是：当时在什么约束下做了哪个决定，为什么选它而不选其他方案，采用后会得到什么、付出什么，将来如何判断这个决定是否仍合适。

它不是仓库模板。决策记录是历史性文档；已接受或已实现的决策不应被事后编辑，应通过新记录替换或补充。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 我本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 我本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 我本人没有读到源码，但来源材料陈述了该事实；来源可能是引述源码的文档、他人整理的笔记或任务给定材料 | 命令、配置项、路径、指标名、阈值；**仅当该材料的原始出处指向源码或配置时使用** |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据；材料的原始出处是发布说明、会议记录、内部 wiki 等非源码文档时用此档 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- **选档顺序**：先问「我本人读到源码了吗」→ 是则用 `源码确认`；否则问「我本人执行并看到输出了吗」→ 是则用 `运行确认`。两者都否、但来源材料有明确陈述 → 用 `来源确认`。
- **不要用 `源码确认` 标注你只是转述的内容**。这正是 `来源确认` 要解决的问题：区分「作者亲自核对了源码」与「作者转述了一份声称来自源码的材料」。
- `来源确认` 的结论来自材料，作者不对其真实性负责，但必须负责标注它未经本人核对；需要读者据此行动时，配一个可自行复核的命令。
- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”“服务监听 `:9100`（来源确认，材料「Metrics endpoint」）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。
- **同一个结论只给一个标签；不要用「标签 + 限定词」表达单标签装不下的意思**。当一条结论里有一部分已确认、另一部分未确认时，拆成两句分别标注，而不是叠在一句上。例：

  ```text
  不合格：清单里含 011_add_capture_mode.sql，属新增（来源确认，未验证）
  合  格：清单里含 011_add_capture_mode.sql（来源确认，材料「migrations 目录」）。其变更类别无法判定，因为看不到 DDL（未验证）。
  ```

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **未运行的命令**：在文档没有对应环境、或作者没有执行过命令时，命令照给，但必须紧跟 `未验证` 并注明「作者未运行」，必要时补一句为什么要给一条没跑过的命令（读者照做即可验证）。**不得让读者以为那是实测输出。**
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中出现的 `[measured: …]`、截图数字或他人记录的性能数据，一律标 `来源确认`，并在紧邻处写明「非本机运行结果」。这是最容易误标的一类。
- **引用格式**：有行号时写 `<文件>:<行号>`；只有文件名时写 `<文件名>`；只有材料时写「材料「<小节标题>」」。三者都没有时写 `未验证`。**不得编造行号。**
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。正文中的说明性括号不属于占位，但不得以括号代替应写的内容。
- **待验证清单格式**：集中收纳未验证项时使用固定列名，使不同文档可比较：

  | 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
  | --- | --- | --- | --- |
  | V1 | <待确认的结论> | <缺什么证据：无源码 / 无环境 / 材料未给> | <可执行的命令或动作> → <看到什么算确认、看到什么算否定> |

- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 决策标题与状态

标题使用具体问题，不使用“架构调整”这类无法判断范围的名称。

包含：

- 状态：提议、已接受、已实现、被推翻或已替换
- 记录日期
- 关联文档和代码位置
- 决策范围和影响模块

状态必须与事实一致。提议中的方案不能写成已接受决定。

### 编号与存放位置

编号是记录的稳定标识，必须可确定，不允许出现「两者皆可」：

1. 调用方显式指定的路径优先。
2. 仓库已有 ADR 目录（`adr/`、`decisions/`、`docs/adr/`、`docs/decisions/` 或等价的既有目录）→ 用该目录及其既有编号规则，不新建第二套。
3. 都没有 → 默认 `docs/adr/`；目录不存在时创建。
4. 文件名 `NNNN-<标题>.md`，`NNNN` 为四位零填充序号，取目录内最大序号加一。目录内无既有记录时用 `0001`，并在文件开头写一句「本仓库编号从此条开始」——这句话本身就是给后来者的编号依据。

编号一经分配不再更改；记录被推翻或替换时保留原编号，由新记录引用它。

## 背景与问题

说明为什么要做这个决定：

- 需要解决的问题或设计缺口
- 当前方案的失效信号
- 触发该决策的项目、实验或外部约束
- 问题边界，明确本决策不解决什么

问题描述必须具体，不能使用“为了更好的架构”这类无验证依据的表达。

## 约束与判断标准

列出真实约束和决策标准：

- 正确性、性能、安全、可维护性要求
- 仓库现状、技能范围、数据规模和部署条件
- 时间、硬件、预算或团队限制
- 哪些标准是硬条件，哪些只是偏好
- 后续如何验证决策满足标准

## 候选方案

只记录被认真考虑的候选方案：

- 方案名称和核心做法
- 每个方案解决什么问题
- 各自的直接成本、长期成本和失效方式
- 为什么最终没有选择

候选方案应有真实来源。不要编造只为了衬托最终答案的方案。

## 决策

用一段具体、可执行的文字说明最终选择：

- 选择了什么，不选择什么
- 采用哪个模式、接口、库、存储或流程
- 默认行为是什么，例外由谁处理
- 决策边界在哪里

## 后果

分别列出可观察影响：

- 立即获得的好处
- 引入的接口、状态、依赖或复杂度
- 哪些问题被推迟
- 失败模式、反模式和回退条件
- 团队、运维或后续开发受到的约束

不能只列好处。每个成本都应能对应到实际设计或运维结果。

## 替代决定的影响

如果最终选择发生变化，说明会出现什么不同：

- 回到候选方案 B 的触发条件
- 需要重做哪些模块、测试或迁移
- 兼容已有数据和旧接口的代价
- 何时应发布新决策而不是修改旧决策

## 验证与落实

说明决策如何落到真实系统：

- 代码、配置、测试或文档入口
- 验证指标和可复现命令
- 决策是否已经实现，还是只在设计中
- 如果尚未实现，当前阻塞是什么

## 相关决策

链接相关记录：

- 被本决策替换的旧决策
- 受本决策影响的架构或数据模型记录
- 本决策后续可能需要补充的记录

## 示例

以下片段针对同一决策——「任务队列用进程内队列还是外部消息服务」——展示被否候选方案及其成本、以及一项后果。二者差别只在作者手头有多少证据；示例为示意，占位名不代表任何真实仓库。

### 证据充分：候选可追溯到讨论、实验或代码

被否候选方案与成本：

- 被否候选 B「外部消息服务」：做法是把任务投递到独立消息服务，由消费者拉取；成本是需把现有直连调用改造为投递调用，并新增一个部署单元（`源码确认`，现有调用点见 `<投递模块>:<行号>`）。
- 该候选有真实来源：设计讨论记录了两种投递路径的比较，B 因新增部署单元与跨服务排障成本被否（`来源确认`，材料「投递方案讨论」）。

后果：

- 选择 A「进程内队列」后，故障范围限于单进程，进程重启时未完成任务丢失（`设计意图`：本决策不承诺跨重启持久化）。此后果可运行核对：

```
$ <针对性测试命令>
# 输出：断言通过 [固定]
```

说明：`[固定]` 表示断言与版本无关；若输出为耗时则标 `[随环境/版本变化]`。

### 证据受限：只有二手材料

同一决策只能依据二手材料复述，候选来源与后果都无法核实：

- 被否候选 B 只能记为「材料称当时比较过外部消息服务」（`来源确认`，材料「决策会议纪要」）。其成本无法定位到调用点，标 `未验证`。
- 后果项：材料称会新增一个部署单元，作者未见到清单，标 `未验证`。

| 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
| --- | --- | --- | --- |
| V1 | 现有直连调用点共几处 | 无源码，材料未给路径 | 在仓库搜索直连投递 API → 命中文件清单即为改造范围 |

### 不可接受的写法（对照）

- 被否候选 B「外部消息服务」：做法是「引入消息中间件以提升扩展性」，成本是「更复杂」。理由：没有讨论、实验或代码来源，成本也没有载体，属于为衬托最终答案而编造的陪衬选项，不是被认真考虑过的候选方案。

对比：证据充分版能指明候选的真实来源并把成本落到具体调用点；证据受限版只能复述材料并把成本记为 `未验证`；而编造陪衬选项无论证据多少都不允许写入。

## 来源与证据

列出支撑结论的来源：

- 代码、实验、压测或运行日志
- 规范、论文、官方文档或评审材料
- 讨论记录或决策会议
- 未验证的假设

决策结论必须可追溯，不能只写个人偏好。
