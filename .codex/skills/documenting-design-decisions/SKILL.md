# Documenting Design Decisions

## 使用边界

此 skill 用于以下任务：

- 记录一个已做或正在评估的设计决策
- 说明决策背景、候选方案和选择标准
- 记录决策的后果、失败模式和回退路径
- 补充或链接已有的 ADR、决策记录和架构评审

此 skill 不用于：

- 描述当前系统完整架构
- 解释某个算法
- 写语言特性说明
- 把尚未决策的想法写成已接受决定

## 写作前确认

开始前确认：

- 读者：项目作者、工程师、架构师还是后续维护者
- 决策状态：提议、已接受、已实现、被推翻还是已替换
- 决策范围：只影响一个模块、一个项目还是整个平台
- 真实候选方案：哪些方案被认真考虑过，各自的来源是什么；确实没有认真比较过其他方案时，如实写明“仅评估了一个方案”，不虚构候选
- 选择标准和证据来源：代码、实验、压测、文档还是个人经验
- 决策是否已经落地；未落地时记录当前阻塞

## 写作流程

1. 先确认目标环境是否已有 ADR 或决策记录位置；存在时只把它作为编号、链接和定位上下文，不能因为旧记录简略或仓库模板不同而降低本 skill 的标准。
2. 描述需要解决的问题和约束，不直接跳到最终方案。
3. 列出被认真考虑的候选方案及代价，不只写选中方案的优点；只评估过一个方案时如实说明。
4. 写清决策本身和判断标准，让读者能判断该决策是否仍然适用。
5. 说明后果、失败信号、回退条件和验证方式。
6. 说明决策如何落地：对应的代码、配置、测试或文档入口；未落地时写明阻塞。
7. 对已接受决策保持不可变；修正或替换应新增一条记录并链接旧记录。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；技术名词保留原文。
- **位置与命名**：已有 ADR 目录时按该目录编号规则命名（如 `NNNN-<标题>.md`）；无约定时用 `ADR-<序号>-<标题>.md` 或 `decisions/<标题>.md`。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**未落地模式（降级）**：决策尚未实现时，不因此停止记录，也不得把计划写成现状。状态写「已接受」或「提议」，
并在「验证与落实」一节写明当前阻塞、阻塞方与解除条件；后果一节区分「已发生的影响」与「预期影响」；不得写成「已实现」。
决策已被推翻或替换时同理：状态如实标注，并链接取代它的那条记录，不修改本条的内容。

本 skill 的说法若与 `references/design-decision-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 文档开头写明状态（提议/已接受/已实现/被推翻/已替换）、记录日期和决策范围；状态与事实一致
- 问题用现实约束说清，不出现“为了更好的架构”“需要灵活性”这类无验证依据的表达
- 候选方案各有来源：能对应到一次讨论、一份文档、一段代码或一次实验；无法对应则不写入
- 确实没有认真比较过其他方案时，显式写「本次仅评估一个方案，未做对比」，不编造陪衬方案
- 结论是一个具体决定，读者能据此行动；出现“应考虑”“后续再定”即不合格
- 代价与失效方式各至少一条，且能对应到实际设计或运维结果
- 回退路径写明触发条件和具体动作；无回退方案时写明“无回退方案，原因是…”
- 决策可追溯到可检查的来源：代码位置、实验命令与输出、压测数据或权威资料；只写“个人经验”不作为充分来源
- 落实一节写明对应代码/配置/测试/文档位置；未落地时写明阻塞
- 已接受决策未被事后编辑；修正通过新增记录并链接旧记录完成
- 新决策与相关旧决策的关系写出（替换、补充或并行）

## 与其他 skill 的边界

- 若目标是描述系统当前架构，改用 `explaining-systems`。
- 若目标是讲一个通用架构模式，改用 `documenting-architecture-patterns`。
- 若目标是接口字段或数据模型现状，分别改用 `documenting-api-contracts` / `documenting-data-models`。
- 若用户只是提问、不要求产出文档，直接用对话回答。
