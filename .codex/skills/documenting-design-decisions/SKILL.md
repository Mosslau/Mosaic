# Documenting Design Decisions

## 使用边界

此 skill 用于以下任务：

- 记录一个已做或正在评估的设计决策
- 说明决策背景、候选方案和选择标准
- 记录决策的后果、失败模式和回退路径
- 补充或链接已有的 ADR、决策记录和架构评审

此 skill 不用于：

- 描述当前系统完整架构
- 解释某个算法
- 写语言特性说明
- 把尚未决策的想法写成已接受决定

## 写作前确认

开始前确认：

- 读者：项目作者、工程师、架构师还是后续维护者
- 决策状态：提议、已接受、已实现、被推翻还是已替换
- 决策范围：只影响一个模块、一个项目还是整个平台
- 真实候选方案：哪些方案被认真考虑，哪些只是随口提及
- 选择标准和证据来源：代码、实验、压测、文档还是个人经验

## 写作流程

1. 先确认目标环境是否已有 ADR 或决策记录位置；存在时只把它作为编号、链接和定位上下文，不能因为旧记录简略或仓库模板不同而降低本 skill 的标准。
2. 描述需要解决的问题和约束，不直接跳到最终方案。
3. 列出被认真考虑的候选方案及代价，不只写选中方案的优点。
4. 写清决策本身和判断标准，让读者能判断该决策是否仍然适用。
5. 说明后果、失败信号、回退条件和验证方式。
6. 对已接受决策保持不可变；修正或替换应新增一条记录并链接旧记录。

## 写作质量门

最终交付前必须满足：

- 决策状态清晰，提议和已接受不混淆
- 问题能用现实约束说清，不用“需要灵活”这类空泛原因
- 候选方案有真实依据，不虚构没有考虑过的选项
- 结论是具体决定，不是“应考虑”或“后续再定”
- 代价、失效方式和回退路径都被说明
- 决策可追溯到代码、实验、压测或权威资料
- 历史决策不被事后改写
- 新决策与相关旧决策的关系清楚
