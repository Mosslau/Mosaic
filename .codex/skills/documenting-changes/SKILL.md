# Documenting Changes

## 使用边界

此 skill 用于以下任务：

- 说明两个版本之间发生了什么变化，以及为什么要升级
- 给出从旧版本到新版本的迁移步骤与顺序
- 标出破坏性变更及其影响范围
- 记录废弃、移除与它们的替代方案
- 说明升级期间的兼容窗口与回退方式

此 skill 不用于：

- 解释整个系统或框架的架构
- 记录一次设计取舍的候选方案与理由（那属于 ADR）
- 写接口字段手册或数据模型说明（只引用它们，不重复）
- 把提交记录按时间顺序罗列成清单
- 写营销式发布公告

## 写作前确认

先判定文档类型，它决定详略与必答问题：

| 类型 | 判定依据 | 重点 |
| --- | --- | --- |
| 版本变更说明 | 读者需要知道「变了什么、影响谁」 | 差异清单 + 影响范围 + 是否需要动作 |
| 迁移/升级指南 | 读者需要动手把系统从旧版换到新版 | 前置检查 + 分步动作 + 验证 + 回滚 |
| 破坏性变更通告 | 存在必须改代码或改配置才能继续工作的变更 | 变更点 + 受影响方 + 最小改法 + 截止版本 |
| 废弃说明 | 某能力被标记废弃但尚未移除 | 废弃时间线 + 替代方案 + 移除版本 |

随后确认：

- 读者：升级执行者、客户端开发者、运维还是决策者
- 起点与终点：从哪个版本到哪个版本，**两端都必须写明确**，不接受「最新版」
- 事实来源：变更日志、提交记录、迁移脚本、schema 差异、接口 diff、发布记录
- 是否存在权威变更清单；不存在时按「输出契约」走来源材料模式
- 兼容窗口：旧客户端与新服务端能否并存，并存多久
- 是否有回退路径；没有时写明原因

## 写作流程

1. 先确定版本区间与权威变更来源，不凭记忆列变更。
2. 建立差异清单：逐条对照旧版与新版，分出「新增 / 修改 / 废弃 / 移除」四类。
3. 对每条差异判定**是否需要读者动作**：需要动作的必须给出具体改法，不需要动作的明确写「无需动作」。
4. 标出破坏性变更，并写明受影响方与最小改法。
5. 如有迁移动作，写出分步流程、前置检查、验证方式与回滚路径。
6. 给出兼容窗口与时间线：哪些版本可共存、废弃项何时移除。
7. 对无法确认的条目按「来源材料模式」标注，不推测。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；版本号、标志名、命令与错误信息保留原文。
- **位置与命名**：按 `<产品或服务>-<起始版本>-to-<目标版本>.md` 命名；已有变更文档目录时放入其中。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**四种模式，按可得证据选择并在开头声明**：

- **完整模式**：能同时拿到旧版与新版（源码、schema、接口定义、可运行环境）。逐条差异用「源码确认」或「运行确认」标注。
- **单侧模式**：只有新版或只有旧版。差异只能从一侧加变更记录推导，全文标注「来源确认」，并写明缺哪一侧；不得把「新版有」直接写成「新增」——无法与另一侧对照时，类别写「无法判定」，不硬套四类。
- **来源材料模式**：只有变更日志、发布记录或他人整理的清单。只写材料确实记录的条目，全文标注「来源确认」；**材料未覆盖的版本照常写，但必须另设一节「来源冲突与覆盖缺口」说明哪一段没有来源**——不要因为来源不全就放弃写目标版本，也不要补写材料没说的条目。
- **无权威清单模式**：连变更记录都没有，只有提交历史。**不得把提交标题当作面向读者的变更说明**；只写能从提交内容确认的差异，逐条标注「来源确认」，并在开头声明"本文由提交历史推导，可能遗漏未提交或已压缩的历史"。

本 skill 的说法若与 `references/change-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 开头一段写明起点版本、终点版本、文档类型（变更说明/迁移指南/破坏性变更通告/废弃说明）与依据的权威来源
- **每条差异都归入五类之一**：新增、修改、废弃、移除、**无法判定**；「无法判定」是合法取值，必须写明缺哪一侧或缺什么证据，不得为凑四类而硬套
- **每条差异都标明是否需要读者动作**；需要动作的给出具体改法与影响范围，不需要动作的写明「无需动作」，类别无法判定且动作也未知的写「无法判定」
- 来源不完整或自相矛盾时，另设「来源冲突与覆盖缺口」一节记录缺口，**照常写目标版本区间**，不擅自裁定哪份来源为准
- 破坏性变更单独成节，逐条给出：变更点、受影响方、最小改法、截止版本
- 迁移步骤写成可执行序列，每步给出命令或改动位置与验证方式；破坏性步骤写明前置检查与备份
- 回滚一节存在：给出回滚目标版本、回滚前置条件与数据影响；无回退路径时写明原因
- 兼容窗口与时间线写出：可共存的版本、废弃项的移除版本；无兼容机制时声明「无兼容窗口」
- 版本区间两端明确，不出现「最新版」「当前版本」这类会随文档腐坏的表述
- 每条变更可追溯到变更日志、提交、迁移脚本或实际运行；无法追溯的不得写入
- 不把提交标题、内部工单标题直接当作面向读者的变更描述
- 引用接口或数据模型细节时链接到对应文档，不在此重复

## 与其他 skill 的边界

- 若重点是**一次设计取舍的候选与理由**，改用 `documenting-design-decisions`；变更文档只写「变了什么、怎么升级」。
- 若重点是**系统整体架构**，改用 `explaining-systems`。
- 若重点是**接口字段与错误契约**，改用 `documenting-api-contracts`，变更文档只写本次接口差异并链接过去。
- 若重点是**存储结构与迁移 DDL**，改用 `documenting-data-models`。
- 若重点是**让读者学会一个任务**，改用 `documenting-tutorials`；升级步骤是「照做即可」的流程，不是教学。
- 若重点是**故障处置**，改用 `documenting-runbooks`。
- 若同一请求同时要求变更说明与接口/数据细节，拆成多份文档并互相链接，不合并成一篇。
- 若用户只是提问、不要求产出文档，直接用对话回答。
