# 变更与升级说明写作标准

这个标准用于说明从一个版本到另一个版本发生了什么变化，以及读者需要做什么。它回答的核心问题是：变了什么，影响谁，谁必须动作，怎么动作，出错怎么退回。

它不是仓库模板，也不是让每节都写满的清单。一次只改了一个内部实现、读者无需任何动作的版本，正确写法就是一条「无破坏性变更，无需动作」。不要为了凑齐章节而制造变更。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 我本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 我本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 我本人没有读到源码，但来源材料陈述了该事实；来源可能是引述源码的文档、他人整理的笔记或任务给定材料 | 命令、配置项、路径、指标名、阈值；**仅当该材料的原始出处指向源码或配置时使用** |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据；材料的原始出处是发布说明、会议记录、内部 wiki 等非源码文档时用此档 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- **选档顺序**：先问「我本人读到源码了吗」→ 是则用 `源码确认`；否则问「我本人执行并看到输出了吗」→ 是则用 `运行确认`。两者都否、但来源材料有明确陈述 → 用 `来源确认`。
- **不要用 `源码确认` 标注你只是转述的内容**。这正是 `来源确认` 要解决的问题：区分「作者亲自核对了源码」与「作者转述了一份声称来自源码的材料」。
- `来源确认` 的结论来自材料，作者不对其真实性负责，但必须负责标注它未经本人核对；需要读者据此行动时，配一个可自行复核的命令。
- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”“服务监听 `:9100`（来源确认，材料「Metrics endpoint」）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。
- **同一个结论只给一个标签；不要用「标签 + 限定词」表达单标签装不下的意思**。当一条结论里有一部分已确认、另一部分未确认时，拆成两句分别标注，而不是叠在一句上。例：

  ```text
  不合格：清单里含 011_add_capture_mode.sql，属新增（来源确认，未验证）
  合  格：清单里含 011_add_capture_mode.sql（来源确认，材料「migrations 目录」）。其变更类别无法判定，因为看不到 DDL（未验证）。
  ```

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **未运行的命令**：在文档没有对应环境、或作者没有执行过命令时，命令照给，但必须紧跟 `未验证` 并注明「作者未运行」，必要时补一句为什么要给一条没跑过的命令（读者照做即可验证）。**不得让读者以为那是实测输出。**
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中出现的 `[measured: …]`、截图数字或他人记录的性能数据，一律标 `来源确认`，并在紧邻处写明「非本机运行结果」。这是最容易误标的一类。
- **引用格式**：有行号时写 `<文件>:<行号>`；只有文件名时写 `<文件名>`；只有材料时写「材料「<小节标题>」」。三者都没有时写 `未验证`。**不得编造行号。**
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。正文中的说明性括号不属于占位，但不得以括号代替应写的内容。
- **待验证清单格式**：集中收纳未验证项时使用固定列名，使不同文档可比较：

  | 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
  | --- | --- | --- | --- |
  | V1 | <待确认的结论> | <缺什么证据：无源码 / 无环境 / 材料未给> | <可执行的命令或动作> → <看到什么算确认、看到什么算否定> |

- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 变更定位

先给结论：

- 起点版本与终点版本（两端都必须写明，不接受「最新版」）
- 文档类型：版本变更说明、迁移/升级指南、破坏性变更通告还是废弃说明
- 一句话说明本次变化对读者的影响
- 本文件不覆盖什么（例如不含接口字段细节，链接到契约文档）
- 与相邻文档的关系：本次变更是否已有 ADR、是否改动 schema

## 权威来源

列出事实来源及其优先级：

- 变更日志、发布记录或 CHANGELOG
- 提交记录与合并请求（作为线索，不作为面向读者的描述）
- schema 差异、迁移脚本
- 接口定义差异（OpenAPI/protobuf 前后版本对比）
- 配置项差异与默认值变化
- 版本标记、镜像标签或发布产物清单

明确说明哪一份是权威；当来源之间冲突时记录差异，不擅自裁定。

## 差异清单

逐条列出差异，每条必须归入四类之一，并标明是否需要读者动作：

| # | 变更点 | 类别 | 是否需动作 | 影响范围 | 来源 |
| --- | --- | --- | --- | --- | --- |
| 1 | <改了什么> | 新增 / 修改 / 废弃 / 移除 / 无法判定 | 需要 / 无需 / 无法判定 | <哪些使用方受影响> | <来源与标签> |

规则：

- **类别取值五选一，第五类是「无法判定」**。单侧模式（只有新版或只有旧版）下，看到「新版有」但不知道旧版有没有，就不是「新增」；看不到 DDL、看不到实现时，也归不到四类里。这类条目必须写成「无法判定」并说明缺哪一侧或缺什么证据，**不塞进最接近的一类**。
- **「无法判定」是合法且必须使用的取值**，不是写作失败。它把不确定性显式交还给读者，比猜测归类更可用。
- 判定「新增 vs 修改」需要两侧对照：有旧版与新版 → 可比；只有一侧 → 无法判定。
- **「是否需动作」必须有明确取值**。写成「可能需要注意」不算——要么给出具体改法，要么写「无需动作」；类别无法判定的条目，若已知必须动作就写「需要」，否则写「无法判定」。
- 默认值变化、行为变化、性能变化都属于「修改」，且最容易漏，必须单列。

## 破坏性变更

单独成节。每条给出：

- 变更点与类别（移除 / 签名变化 / 默认值变化 / 语义变化）
- 受影响方：哪些调用方、配置、脚本或依赖会失效
- 最小改法：把旧写法改成什么，给出前后对照
- 截止版本：从哪个版本起旧写法不再可用
- 检测方式：读者如何自查是否受影响

没有破坏性变更时明确写「本次无破坏性变更」，不要省略本节。

## 迁移步骤

写成分步可执行序列，每步包含：

1. 前置检查：确认当前状态（命令或检查项）、需要备份什么
2. 动作：命令、配置改动或代码改动位置
3. 预期结果：命令输出或可观察状态，附 `[固定]` / `[随环境/版本变化]` 标记
4. 失败处理与停止条件

破坏性步骤必须写明备份、权限与不可逆点。步骤顺序不可依赖读者自行推断环境差异。

## 兼容窗口与时间线

说明：

- 旧客户端与新服务端、旧数据与新代码能否并存，并存多久
- 废弃项的移除版本与时间点
- 灰度或分阶段发布的顺序与暂停条件
- 无兼容机制时声明「无兼容窗口，必须同时升级」

## 回滚

给出：

- 回滚目标版本与触发条件
- 回滚前置条件（例如必须在数据写入前、必须无新格式数据）
- 回滚对已写入数据的影响，以及是否需要清理
- 回滚失败时的升级路径

无回退路径时写明原因，例如「新版已改写数据格式，回滚需先还原备份」。

## 验证升级成功

给出可判定的检查：

- 版本确认：如何确认运行的是目标版本
- 功能断言：关键路径的命令与期望结果
- 数据一致性：行数、校验和或对账方式
- 残留检查：是否有旧版本产物、旧配置或未完成任务

验证写成「命令 → 期望输出/断言」，不写「确认服务正常」这类无入口的步骤。

## 示例

以下是同一份「默认重试次数变更」在不同证据条件下的两种合格写法，差别在标签与结论强度，而非篇幅。

**有条件实测时（完整模式）**：

```text
## 破坏性变更

### D1：默认重试次数 3 → 1

- 变更点：客户端默认 `retry.max` 由 3 改为 1（源码确认，`client/config.py:41`）
- 受影响方：未显式设置 `retry.max` 的调用方；显式设置为 3 的不受影响
- 最小改法：在配置中显式声明 `retry.max: 3` 即可保持旧行为
- 截止版本：无（旧默认值不再恢复；显式声明始终有效）
- 检测方式：`grep -r "retry" <配置目录>` → 未出现 `retry.max` 即为受影响  [固定]

验证：`python -c "from client import config; print(config.retry_max)"` → 输出 `1`  [固定]
```

**只有变更日志时（来源材料模式）**：

```text
## 破坏性变更

### D1：默认重试次数变更

- 变更点：发布记录称默认重试次数由 3 改为 1（来源确认，材料「2026-01 发布说明」）
- 受影响方：未在配置中显式设置重试次数的调用方；具体判定方式未验证
- 最小改法：材料建议显式设置重试次数；应设为何值未在材料中说明（未验证）
- 截止版本：材料未说明（未验证）
- 检测方式：未验证——需按待验证清单 V2 在测试环境确认配置读取路径

本例中「由 3 改为 1」与「应显式设置为 3」都来自材料而非本人核对，因此标 `来源确认`；
「应设为何值」材料未给，标 `未验证`。**不得**把第二段写成第一段那样确定。
```

## 证据模式决策表

写作前先定模式，模式决定标签、类别判定与禁令。一张表查完，不要跨模式混用：

| 模式 | 判定依据 | 可用标签 | 类别怎么定 | 该模式下的禁令 |
| --- | --- | --- | --- | --- |
| 完整模式 | 旧版与新版都能拿到 | 源码确认 / 运行确认 | 两侧对照，四类正常判定 | 不得用「来源确认」代替已读到的源码 |
| 单侧模式 | 只有新版或只有旧版 | 来源确认 / 未验证 | 「新版有」不等于「新增」，无法对照时写**无法判定** | 不得把「新版有」写成「新增」；不得用四类硬套 |
| 来源材料模式 | 只有变更日志或发布记录 | 来源确认 / 未验证 | 材料写明类别的照抄并标来源；没写明的写**无法判定** | 材料未覆盖的版本不当作已变更；不补写材料没说的条目 |
| 无权威清单模式 | 只有提交历史 | 来源确认 / 未验证 | 从提交**实际做了什么**推导；无法判断的写**无法判定** | 不得把提交标题当变更描述；不得声称历史完整 |

补充规则：

- **来源不完整或自相矛盾时**（例如变更日志停在旧版本、或日志与接口定义冲突）：照常写目标版本区间，另设一节「来源冲突与覆盖缺口」记录缺口与冲突，不擅自裁定哪份为准。**不要因为来源不全就放弃写目标版本。**
- 无信息提交（`wip`、`fix tests`、`chore: bump`）不作为条目；但若它对应了接口或 schema 的实际变化，从变化反推条目，不从标题反推。
- 命令与输出在无环境时按「证据书写」的未运行命令规则处理：给命令、标 `未验证`、注明作者未运行。

## 禁用写法

- 按提交时间罗列提交标题，充当变更说明。
- 使用「优化」「改进」「修复若干问题」等无法核实的类别。
- 不写版本号，用「最新版」「当前版本」。
- 把接口字段表或数据模型细节抄进本文件。
- 声称「完全兼容」却没有给出验证方式。
