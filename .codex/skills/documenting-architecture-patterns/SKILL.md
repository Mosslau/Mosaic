# Documenting Architecture Patterns

## 使用边界

此 skill 用于以下任务：

- 解释一个架构模式解决什么问题
- 说明模式中的参与者、职责和协作方式
- 分析模式在当前系统中的落地位置
- 比较相近模式并解释适用边界
- 判断某个模式是否适合当前问题

此 skill 不用于：

- 描述某个系统实例的完整架构
- 解释一个具体算法
- 讲解语言特性
- 输出只含优点、没有代价的模式介绍

## 写作前确认

开始前确认：

- 读者：架构师、开发者、技术负责人还是系统维护者
- 文档目的：理解模式、评估是否采用、指导实现，还是审查现有设计
- 模式是理论模式还是项目中的具体实现
- 资料来自哪些权威来源
- 是否有真实系统代码、类、文件或调用链可以引用

## 写作流程

1. 先说明上下文和问题，不直接跳到结构图。
2. 列出冲突力量，解释模式为什么是权衡后的答案。
3. 说明参与者、结构、协作和运行流程。
4. 写出可观察的代价和失效方式，不能只讲好处。
5. 给出适用条件和不适用条件。
6. 如果文档涉及真实系统落地，把参与者映射到实际文件、类、模块或进程；纯理论模式则明确标注“理论说明/示意落地”。
7. 最后用权威资料和现有源码或架构文档验证结论；不能把个人理解和推测写成已验证事实。

## 写作质量门

最终交付前必须满足：

- 模式解决的问题能被识别
- 参与者职责没有彼此混淆
- 协作流程和调用关系清楚
- 优点、代价、复杂度和失效方式都被说明
- 适用和不适用的条件不是空泛建议
- 没有把模式名称当成架构事实
- 理论模式与系统实例、示意落地的边界清楚
- 与相近模式的边界清楚
