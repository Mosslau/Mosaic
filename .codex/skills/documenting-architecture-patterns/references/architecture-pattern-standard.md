# 架构模式说明写作标准

这个标准用于说明一个架构设计模式。它回答的核心问题是：在什么场景使用这个模式，模式由哪些参与者组成，它们如何协作，采用后会得到什么、付出什么，以及何时不应使用。

它不是仓库模板；即使文档所在项目已有架构目录约定，也不能让章节只停留在“按本地模板补标题”的层面。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 直接读到源码、配置或 schema 得到的结论 | 结构、签名、默认值、常量 |
| `运行确认` | 亲自执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出视为未实测。
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 模式名称与定位

先给结论：

- 模式名称和所属类别，例如创建型、结构型、行为型、企业集成、数据架构
- 一句话说明模式解决什么问题
- 主要使用场景
- 本模式不解决的问题

如果文档只讲理论，不要伪装成已经在一个真实系统中验证。

## 上下文与问题

描述模式出现前的现实问题：

- 系统面临哪些不变量、扩展点或协作需求
- 为什么直接、简单的方案会失效
- 哪些约束来自性能、可维护性、团队、部署或第三方依赖
- 问题出现的典型信号

问题必须具体，不使用“系统需要灵活性和可扩展性”这类无法验证的表述。

## 冲突力量

列出模式需要平衡的力量，并说明模式偏向哪一方：

- 简单性与灵活性
- 集中控制与局部自治
- 解耦与调用可追踪性
- 性能与一致性
- 演进能力与实现成本
- 约定一致性与自由扩展

每一种力量都应该能解释为真实设计选择，而不是堆概念。

## 参与者与职责

列出模式中的每个参与者：

- 名称和抽象角色
- 对外职责
- 内部持有的状态或依赖
- 创建、通信、销毁关系
- 在真实代码中对应的类、模块、服务或文件

避免把所有参与者都叫“核心组件”，职责必须可区分。

## 结构与协作

解释模式的结构和运行时协作：

- 静态结构：谁依赖谁，谁拥有谁
- 调用方向：谁发起请求，谁响应
- 数据方向：数据如何转换和传递
- 生命周期：参与者何时创建、注册、运行、清理
- 并发或分布式模式还要说明消息、锁、事务、幂等和故障传播

可以用文字架构图、类关系、序列列表或状态表表达，但不要使用无法核对的抽象架构图。

## 落地示意

如果文档面向具体项目，给出真实落地示意：

- 在哪个模块应用该模式
- 现有代码如何映射到参与者
- 当前实现是否严格遵循模式
- 哪些位置属于模式变体或例外
- 是否值得引入、已经引入或应该移除

若没有真实落地，明确说明示例只是示意，不是系统现状。

## 演进与兼容

若模式已落地，必须补写：

- 引入该模式前后，系统在哪些方面发生了变化（接口数量、间接层、部署单元、故障范围）
- 该模式经历过哪些版本或结构变更，每次变更的触发原因
- 替换或退出该模式的代价：需要重做哪些模块、迁移哪些数据、兼容哪些旧接口
- 什么信号出现时应当发布替换决策（链接到对应 ADR 或决策记录）

若为纯理论模式，直接写“无落地演进记录”，不得虚构变更历史。

## 优点与代价

分别列出：

- 采用后获得的可观察优点
- 直接增加的实现和维护成本
- 长期可能出现的复杂度
- 调试、测试、部署或运维难度
- 对团队协作和代码导航的影响

优点和代价都要给出可观察结果，例如接口数量、间接层、一致性保证、故障范围或扩展路径。

## 适用与不适用

给出具体判断条件：

- 满足什么条件时该考虑此模式
- 出现什么信号时不应强行套用
- 小规模实现时是否需要完整模式
- 何时应先用简单方案，再演进到模式

不适用条件要和适用条件一样具体。

## 失效方式与反模式

说明模式被误用时会怎样：

- 参与者职责失衡
- 过度抽象或虚假解耦
- 调用链难以追踪
- 生命周期或状态管理失控
- 扩展点过多导致无法理解
- 分布式模式下的一致性和幂等问题

给出可以识别的症状，帮助读者判断现有系统是否已经落入反模式。

## 相近模式与变体

与本模式比较：

- 解决同一问题的其他模式
- 看起来相似但目标不同的模式
- 本模式的常见变体
- 何时应切换或组合

比较应围绕可观察差异，而不是单纯罗列模式定义。

## 来源与验证

列出：

- 模式理论来源
- 真实项目中的代码或文档位置
- 架构评审、ADR 或设计决策记录
- 性能、可用性或复杂度验证结果

文档不得把个人建议写成已经验证的系统事实；每条关于落地的结论必须带事实标签，并指向真实文件、类或模块位置。
