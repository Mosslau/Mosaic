# Documenting Tutorials

## 使用边界

此 skill 用于以下任务：

- 编写让读者完成一个真实任务的教程
- 为仓库实验、工具或系统补充可跟随的动手教程
- 把已有笔记整理成带验证路径的学习材料
- 改写无法运行、步骤不连续的教程

此 skill 不用于：

- 写完整 API 参考或字段手册
- 解释系统或框架的整体架构
- 写营销式能力介绍
- 只列命令，不给预期结果和验证方式

## 写作前确认

开始前确认：

- 读者：入门者、实验复现者还是工具使用者
- 教程终点：读完能做哪个具体任务
- 教程时长和前置依赖：环境、数据、模型、硬件或账号
- 可复现方式：哪些步骤必须由实际运行验证
- 教程边界：什么内容应链接到参考文档而不是重复
- 是否具备可运行环境；不具备时按「输出契约」走条件模式

## 写作流程

1. 先运行一次目标任务，记录关键输出、报错和验证点。
2. 已有教程和笔记可作为事实线索与读者上下文，但不能替代码运行验证背书，也不应为适配本地仓库风格而让步骤不可复现。
3. 按任务步骤组织，不用章节堆砌背景知识。
4. 每步给出动作、预期结果和常见偏差；预期结果按「输出标记」规则标注。
5. 示例中的命令、代码和数据要与当前仓库版本一致。
6. 最后提供验证清单，读者能判断教程是否成功完成。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；命令、代码与输出保留原文。
- **位置与命名**：按 `<任务名>-tutorial.md` 命名；已有教程目录时放入其中。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**两种模式，必须二选一并在开头声明**：

- **已验证教程**：每个预期输出都由实际运行产生，并附上产生它的命令；标注「运行确认」。
- **条件教程**：无法在本机运行。必须给出 `提交哈希 + 运行环境版本 + 数据/随机种子` 三要素，全部步骤标注「来源确认」，并把需要运行才能确认的结果集中列入「待验证清单」。附带“明确复现条件”但缺少这三要素的，不算条件教程。

**三要素不齐时的出口**：只有环境版本、缺提交哈希或随机种子时，不要硬写成条件教程。改为在开头声明“本文不满足条件教程的构成条件，缺 <缺失项>”，按条件教程的组织方式书写，全篇标注「来源确认」并在「待验证清单」中把补齐三要素列为第一项。

**第三方实测值不算 `运行确认`**：来源材料里他人记录的 `[measured: …]`、截图数字、基准报告，一律标「来源确认」并写明「非本机运行结果」，不得写成验证结论。

**预期输出标记**：每个预期输出必须带标记之一 —— `[固定]` 表示与版本无关（如文件存在、断言通过、路径长度）；`[随环境/版本变化]` 表示可能漂移（如耗时、内存占用、日志时间戳）。无法判断时标 `[随环境/版本变化]`。

本 skill 的说法若与 `references/tutorial-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 第一段说明读者能完成的具体任务、所需前置条件，以及本教程属于已验证模式还是条件模式
- 前置条件逐项可检查，写成命令或可观察状态（如 `python --version` 输出满足某版本、某文件存在）
- 每一步给出：动作、命令或代码位置、预期结果、常见偏差；缺少预期结果即不合格
- 步骤之间只通过上一步的可复现产物连接；步骤首行写出「前置：上一步已生成 X」，不要求读者脑补隐含状态
- 每个预期输出带 `[固定]` 或 `[随环境/版本变化]` 标记；无标记即不合格
- 命令、代码、文件和路径与仓库现状一致，且每条命令能追到来源（README、Makefile、脚本或手动实验）
- 示例至少覆盖正常路径和一个常见失败路径，失败路径给出症状、原因和检查方式
- 环境版本、安装方式和数据来源齐全；条件模式还必须给出提交哈希与随机种子
- 「需要展开才能覆盖」的内容（完整 API、字段全集、架构细节）不写进正文，改为给出链接；无法给出链接时说明缺少哪份文档
- 教程终点是读者完成一个学习/复现任务；不得把生产故障处置流程写成教程（那属于 runbook）
- 每个被报告的输出或数字都能追溯到产生它的命令；无法追溯的不得写入

## 与其他 skill 的边界

- 若内容是生产故障的诊断与恢复流程，改用 `documenting-runbooks`。
- 若内容是接口字段手册，改用 `documenting-api-contracts`。
- 若内容是系统或框架的整体解释，改用 `explaining-systems`。
- 若用户只是提问、不要求产出文档，直接用对话回答。
