# 车联网与机器人数据域：从字节到闭环的技术增量

> 版本：v3 · 待评审
> 上游需求：[`../roadmap/车联网与机器人数据域需求.md`](../roadmap/车联网与机器人数据域需求.md)（模块 B 车联网 / 模块 C 机器人）
> 定位：在 `data-platform` D0–D12 与 `ai-platform` D0–D10 之上，回答**这两个域额外要建什么**；通用能力只引用，不重复设计。
> 边界：本文只定义"增量能力"与契约扩展；平台主链设计以 [`data-platform/通用数据平台建设路线.md`](data-platform/通用数据平台建设路线.md)、[`ai-platform/AI平台建设路线.md`](ai-platform/AI平台建设路线.md) 为准。

## 1. 这两个域特殊在哪

平台主干（消息、湖表、调度、指标、检索）对车联网和机器人同样适用。真正需要额外建设的部分，来自五条与"表格世界"不同的性质。

### 1.1 五条性质

| 性质 | 含义 | 它决定哪一层 |
|---|---|---|
| **① 不可自描述** | 字节没有字段名，必须靠外部字典 + 版本才能解释 | 接入（三个登记簿）、存储（raw 不可再生）、计算（codec 版本化）、血缘（位级） |
| **② 以物理资产为中心** | 一切数据挂在 VIN/SN 上，跨 10 年生命周期：出厂 → 使用 → 维修 → 残值 | 本体（设备/信号/字典）、训练（窗口样本）、标签（工单回填）、漂移（OTA） |
| **③ 闭环落在物理世界** | 动作有物理后果；结果回来得慢、缺、不可删 | 闭环（预测 ID 与归因）、评测（时间外推）、合规（安全记录不可删）、审批卡点 |
| **④ 空间是第一性的** | 位置、轨迹、地图不是可选标签，而是主键的一部分 | 接入（坐标系）、存储（时空索引）、计算（里程/围栏/路径）、训练（时空样本） |
| **⑤ 有在线时效** | 数据有"过期即废"的窗口：热失控、围栏、急停按秒算 | 在线规则与告警、边缘计算、状态存储 |

### 1.2 五条性质收敛成三条轴

五条性质不是五个并列话题，而是三条互相垂直的轴。**v1/v2 只写了轴 A，这是它不完整的原因。**

```text
轴 A · 数据流      ① ──→ 接入 → 存储 → 计算 → 训练 → 闭环
轴 B · 设备运行    ② ──→ 身份/孪生 → 边缘管理 → 回灌 → 运维闭环
轴 C · 时空表达    ④ ──→ 坐标系/地图 → 轨迹/索引 → 时空计算 → 时空样本
横切 · 在线        ⑤ ──→ 规则与告警（跨 A/B/C）
```

- **轴 A** 回答"字节怎么变成表、变成模型、变成结论"；
- **轴 B** 回答"设备怎么管、边缘怎么运维、模型怎么回到设备"；
- **轴 C** 回答"在哪、什么时候、长什么样"；
- **在线（⑤）** 不是第四条轴，而是横切层的时效约束：同一份数据在秒级和天级是两种用法。

三条轴缺一条，平台就只能做报表，不能做业务。

### 1.3 判定标准：什么算"多出来的"

一条能力算**通用**（进平台主干），当且仅当三条同时成立：

1. 不依赖具体协议与字典（CAN/DDS/MQTT 换掉也成立）；
2. 不依赖物理量或空间语义（电压/关节角/经纬度换成别的也成立）；
3. 对非车联网、非机器人的第三行业同样成立（例如工控、能源）。

不满足任意一条，就是**领域增量**。按此标准，两个域的增量分四块：

| 增量块 | 归属轴 | 归属方 | 说明 |
|---|---|---|---|
| 协议登记簿与编解码框架 | A | 平台自研（薄） | 框架通用，**codec 由设备团队提供** |
| 时序/大对象/信号处理 | A | 平台主干扩展 | 形态通用，**算子库特有** |
| 设备孪生 / 边缘 / 回灌 | B | 平台自研（薄）+ 运维 | **最容易被漏掉的一块** |
| 时空表达 / 在线告警 | C + 横切 | 平台自研 + 业务规则 | **最不可外包的一块** |

**一句话结论：不要为车联网和机器人各建一套平台。** 两者约 80% 同构，差异应收敛到「codec 插件 + 本体扩展 + 算子库 + 时空字典」，而不是两套接入链路。

## 2. 数据形态：四类，路径完全不同

| 类 | 车联网典型 | 机器人典型 | 单机日增 | 主要路径 |
|---|---|---|---|---|
| ① 高频定长帧 | CAN/CAN-FD 报文、BMS 电芯电压温度、国标类上报帧 | 关节角、IMU、里程计、电池、电机状态 | 1–50 GB（原始） | 边缘降采样 → 流式解码 → 长表 |
| ② 事件与状态 | DTC 故障码、碰撞/倾倒、离线、OTA 结果 | 急停、接管、任务起止、路径偏离、事故 | MB 级 | 常规消息管道 |
| ③ 大对象 | 事故图片、维修视频 | MCAP/rosbag 包、点云、遥操作录屏、地图切片 | 0.1–10 GB | 对象存储 + 索引表 |
| ④ 描述文件 | DBC/ARXML/ODX、车型配置、诊断库 | `.msg`/`.idl`、URDF、地图、标定参数 | KB 级 | **不进数据管道，进登记簿** |

关键：**第 ④ 类不是数据，是元数据，但它决定第 ① 类怎么解释。** 这是设备数据与表格接入最本质的差别。

## 3. 轴 A · 数据流

### 3.1 接入：三层，不是一层

现有 D3 是单层（SeaTunnel：源 → Kafka → Iceberg），对设备数据不够。需要拆成：

```text
设备/边缘                     传输                    平台
┌──────────────┐        ┌──────────────┐        ┌──────────────────┐
│ ① 接入代理    │        │ ② 消息与对象  │        │ ③ 解析与规范化    │
│ 协议适配      │  帧 →  │ Kafka         │  帧 →  │ 按登记簿解码      │
│ 断网缓存补传  │        │ 按 device_type│        │ 单位/量纲归一     │
│ 采样与触发    │  包 →  │ 分区          │  包 →  │ 三时间戳 + 质量   │
│ 本地 N 天留存 │        │ MinIO +       │        │ 位级血缘上报      │
│              │        │ manifest      │        │ 原始字节原样落 raw│
└──────────────┘        └──────────────┘        └──────────────────┘
```

四条不可协商的规则：

1. **原始字节原样落 raw zone，解析结果另存 parsed zone。** 平台的"湖为真相源"在这里含义变了：**raw 是不可再生的，parsed 才是可重算的**。
2. **大对象绝不进 Kafka。** 500 MB 的 MCAP 进消息队列是事故。走「预签名 URL + manifest 消息」。
3. **边缘必须采样。** 全量上传在容量上不成立（见 §11）。
4. **补传导致小时级乱序。** 通用平台的分钟级 watermark 会大量丢迟到数据，必须按 `event_time` 处理并允许长延迟窗口。

### 3.2 三个登记簿（本层真正的核心资产）

设备数据进入平台后有三样东西**不可逆地丢失**：

| 登记簿 | 解决什么 | 关键字段 | 谁维护 |
|---|---|---|---|
| **协议登记簿** | 同一条报文在不同协议版本下含义不同 | `protocol_id`、`version`、`dictionary_hash`、`codec_version`、信号位域表 | 设备/固件团队 |
| **设备-固件绑定** | 历史数据必须按"当时的" schema 解释 | `device_id`、`firmware_version`、`protocol_ref`、生效时间 | 设备管理 / OTA |
| **时钟登记簿** | 设备时钟无 NTP、掉电归零、边缘补传延迟 | `t_device`、`t_edge`、`t_ingest`、`clock_drift_ms`、`sync_source` | 平台，边缘上报 |

**这是整个设备数据域的第一性设计。** 解析代码谁都能写，登记簿只有组织有。三个登记簿不进 D1 契约层，后面 D4/D6/D7 全是错的且不可回溯修补。

### 3.3 协议族清单（codec 清单）

| 域 | 车内/机内 | 车-云 / 机-云 | 字典 |
|---|---|---|---|
| 车联网 | CAN 2.0B、CAN FD、LIN、Automotive Ethernet + SOME/IP、DoIP + UDS | MQTT（T-Box 主流）、HTTPS 批量、私有二进制帧 | DBC、ARXML、LDF、ODX/CDD |
| 机器人 | ROS 2 / DDS（RTPS over UDP）、下位机串口/CAN 私有帧、gRPC | WebSocket / gRPC 遥测与遥操作、对象存储回传 | `.msg`/`.idl`、URDF/SDF、地图与标定文件 |

两轮车以**私有 T-Box 协议 + MQTT** 为主，协议版本随固件迭代，登记簿的版本压力比四轮车更大。

### 3.4 设备身份与接入安全

- 一机一密：`device_id` + 设备证书（mTLS）或 AK/SK + HMAC；证书轮换与吊销。
- 消息幂等键：`device_id + boot_id + msg_seq`（掉电重启 seq 归零，必须带 boot_id）。
- 网关侧限流：单设备速率上限，防故障设备打爆集群。
- 百万级长连接的容量模型见 §11。

### 3.5 接入质量门禁

每条消息入湖前打标记，**不做丢弃**（丢弃等于伪造）：

| 标记 | 含义 | 阈值示例 |
|---|---|---|
| `lost_frame_ratio` | 窗口内丢帧率 | >5% 标 degraded |
| `clock_drift_ms` | 设备时钟与边缘时钟偏差 | >2s 标 suspect |
| `out_of_range` | 超出信号物理量程 | 计数不丢弃 |
| `late_arrival` | 迟到超过水位线 | 落 late 分区，不丢 |

### 3.6 存储：四区

| 区 | 存什么 | 不可变性 | 选型 | 保留 |
|---|---|---|---|---|
| **Raw** | 原始帧包、MCAP、点云、视频、事故包 | 只追加，WORM | MinIO + 对象锁 | 热 30–90 天 → 冷归档 |
| **Parsed** | 解码后的长表、大对象索引表 | 可按 codec 版本重建 | Iceberg + Parquet | 全量 |
| **Curated** | DWD/DWS、信号特征、事件、轨迹 | 可重算 | Iceberg | 全量 |
| **Serving** | 最新值、看板、API、孪生状态 | 可重建 | Doris + TSDB + KV | — |

三个硬决策：

- **信号用长表，不用宽表。** 一车 2000+ 信号、一机 500+ 话题，宽表列爆炸且随型号变。长表 `(device_id, signal_id, ts, value, quality)` + 按需透视。
- **MCAP/rosbag 整包存，不拆。** 索引另建：`(package_id, device_id, t_start, t_end, topics[], size, hash, path)`；按话题抽帧走离线任务。
- **时序双写。** Iceberg 做真相（可重算），TSDB（TDengine / ClickHouse / Doris 时序表）做查询加速（可重建）。

小文件治理从 P2 提到 P0：目标文件 128–512 MB，分区只到 `dt + device_type`，**不要按 device_id 分区**。

### 3.7 计算：五类，SQL 只覆盖两类

| 类型 | 例子 | 引擎 | 通用性 |
|---|---|---|---|
| 流式解码 | CAN 帧 → 信号，DDS 话题 → 状态 | Flink 有状态 UDF（RocksDB） | 领域（框架通用） |
| 批式回放 | MCAP → 训练/评测集 | Spark + 自研 reader | 领域（框架通用） |
| 信号处理 | 滤波、FFT、峰值检测、SOH 估算、里程积分 | **Python 算子运行时** | 形态通用，算子特有 |
| 关联聚合 | 信号 + 工单 + 车辆 + 地图 | SQL | 通用（已有） |
| 事件检测 | 倾倒、碰撞、越界、急停、路径偏离 | Flink CEP + 规则引擎 | 半通用 |

**关键判断：设备数据的计算往上走是"信号处理"，不是"SQL 聚合"。** Flink SQL 写不出 FFT，所以 D4 必须补一个可版本化的 Python 算子运行时——AI 平台 D7 训练也要用。

回放与重算是成本最高的一环：通用 backfill 重跑 SQL，这里**重跑 codec**，成本高一个量级。因此 `parsed` 表必须记录 `codec_version` 与 `protocol_version`，重算只跑变更版本的时间段。

### 3.8 训练：样本不是一行，是一个窗口

样本的基本单元是 `WindowRef`：

```text
WindowRef = {
  device_id, t_start, t_end,
  signals: [{signal_id, agg, sampling}],
  events:  [event_id],
  clips:   [clip_id],
  spatial: {crs, geohash, site_id},       // 见 §5
  label:   {type, value, label_ts, maturity},
  context: {firmware_version, protocol_version, model_id}
}
```

| 域 | 训练目标 | 特征（t0 之前） | 标签（t0 之后） |
|---|---|---|---|
| 车联网 | 故障诊断（SFT/RAG） | 故障码 + 遥测摘要 + 车型 | 技师维修记录 |
| 车联网 | 预测维护 | 30/60/90 天信号统计 + 里程 + 电池 | 未来 30 天是否报修 |
| 车联网 | 保修反欺诈 | 索赔 + 图片 + 历史工单 | 人工审核结论 |
| 机器人 | 异常诊断 | 日志 + 告警 + 任务上下文 | 处置记录 |
| 机器人 | 地图 QA | 地图版本 + 轨迹 + 事故点 | 人工判定"地图问题" |
| 机器人 | 调度偏好（DPO） | 任务/地图/状态 | 调度员选择的好/坏方案 |

三个必须处理的陷阱：

1. **标签成熟度**：工单 7–30 天才回填，且只有部分车会修。标签必须带 `maturity ∈ {pending, mature, expired}`，训练只用 `mature`。
2. **负样本不能靠"没报修"**：没修 ≠ 健康。需按车型/里程/区域做倾向采样 + 人工抽检。
3. **防泄漏要留 gap**：特征截止 `t0`，标签窗口 `[t0+gap, t0+N]`，`gap ≥ 1 天`。

车联网独有的漂移源：**OTA 会改变同一 `signal_id` 的量程、单位甚至含义**。数据卡必须记录 `firmware_version` 分布，特征按版本归一，训练集能按版本切片——否则模型在 OTA 后静默失效，通用平台的漂移监控看不出来。

### 3.9 闭环：预测 ID 与归因

```text
FeedbackEvent = {
  feedback_id, prediction_id, subject_ref,
  verdict,          // correct / wrong / partial / unknown
  reason_code,      // 数据错 / 检索错 / 推理错 / 动作错 / 业务变更
  actor, ts, evidence_ref
}
```

`prediction_id` 是整条链路的主键：**没有它，反馈无法归因，飞轮就是统计报表。**

| reason_code | 修哪里 | 典型信号 |
|---|---|---|
| 数据错 | 接入/解码/登记簿 | 同批次多设备同错、协议换版后突增 |
| 检索错 | 知识引擎/文档 | 引用不对、答非所问 |
| 推理错 | 模型/评测集 | 引用对但结论错 |
| 动作错 | Agent/工单规则 | 结论对但派错单 |
| 业务变更 | 本体/指标/规则 | 政策、保修条款变化 |

## 4. 轴 B · 设备运行

> v1/v2 的最大缺口之一：把设备当成"数据源"，而不是"要运维十年的资产"。

### 4.1 设备身份与生命周期

| 概念 | 说明 |
|---|---|
| 型号（model） | 产品维度：车型/机器人型号、配置、BOM |
| 实例（instance） | 单台设备：VIN/SN、出厂时间、所属客户 |
| 生命周期状态 | 制造 → 出厂 → 激活 → 在役 → 维修 → 退役 → 回收 |

**状态变更必须事件化**（`device_state_changed`），不能只存当前状态——否则"这台车去年是不是在保修期内"永远答不了。

契约 `DeviceRef`：`device_id`、`model_id`、`sn`、`status`、`valid_from`、`valid_to`、`owner_ref`。

### 4.2 数字孪生（last-known state）

每台设备要有一份"当前状态"：位置、电量、在线状态、固件版本、健康分、当前任务/工单。

为什么不能靠"查最新信号"：一个诊断请求要读 200 个信号的最新值，跨 200 个分区，慢且贵。必须维护**状态存储**（KV + 宽表），由流式任务持续折叠事件。

```text
状态 = fold(事件流)  +  定期快照
TwinSnapshot = { device_id, ts, state{}, source_event_ids[], version }
```

用途：告警判定、调度、客服查询、AI 上下文注入。

**验收**：状态更新 P95 延迟；状态与事件流的一致性（重放事件能重建出同一状态）。

### 4.3 边缘节点管理

v1 只写了"边缘采样"，把边缘当采集器。实际上边缘是**要运维的分布式系统**：

| 能力 | 说明 |
|---|---|
| 注册与心跳 | 边缘节点身份、在线状态、版本 |
| 配置下发 | 采样率、上传策略、规则包、模型包；按站点/车型/批次灰度 |
| 断网自治 | 本地规则 + 本地缓存 + 恢复补传（至少 24h 不丢） |
| 远程诊断 | 日志拉取、参数读取（只读，不下发控制指令） |

契约 `EdgeNode` / `EdgeConfig`：`node_id`、`config_version`、`rollout_scope`、`effective_at`。

### 4.4 模型与规则回灌

闭环的另一半。训练完不等于生效，还要：

```text
训练产物 → 打包 → 灰度 → 下发边缘 → 观测 → 全量 / 回滚
```

- 边缘载体：ONNX / TFLite（模型）、YAML 规则包、配置包。
- 契约 `ArtifactRef`：`artifact_id`、`type{model|rule|config}`、`version`、`target_scope`、`hash`。
- 回灌必须可回滚，且**回滚要有时间预算**（一次全量回滚 ≤ 15 分钟）。

**没有回灌，训练就是个离线玩具。**

### 4.5 设备侧运维闭环

设备离线率、故障率、版本分布 → 工单 → 修复 → 验证。这条回路接的是售后/运维系统，不是数据平台内部。

## 5. 轴 C · 时空表达

> v1/v2 的另一个大缺口：轨迹和地图完全没有技术设计。

### 5.1 坐标系与空间参考

| 坐标系 | 用在哪 | 坑 |
|---|---|---|
| WGS84 | GPS 原始、国际标准 | — |
| **GCJ-02** | 国内地图显示 | 与 WGS84 有数百米偏移，**必须显式转换，不能混用** |
| 局部栅格 / 站点坐标 | 机器人站点内部 | 每个站点一套，跨站点不可比 |
| `base_link` / TF 树 | 机器人本体 | 多层变换链，需 snapshotted TF |

契约 `SpatialRef`：`crs_id`、`epoch`、`transform_chain`。**所有空间数据必须带 `crs_id`**，无 `crs_id` 的坐标视为脏数据。

### 5.2 轨迹

| 环节 | 内容 |
|---|---|
| 建模 | 点序列：`(device_id, ts, lon, lat, speed, heading, accuracy, crs)` |
| 压缩 | 死区过滤 + Douglas-Peucker；静止段折叠为停留点 |
| 计算 | 里程、停留、围栏进出、路径匹配、急加速/急弯 |
| 存储 | 轨迹表 + 时空索引（见 5.4） |
| 生命周期 | 原始点 90 天 → 聚合后长期保留（里程/停留/围栏事件） |

容量提示：100 万车 × 30 秒一个点 = **28.8 亿点/天**。轨迹表必须按 `dt + geohash 前缀` 分区，否则查不动。

### 5.3 地图

| 域 | 地图形态 | 版本压力 |
|---|---|---|
| 车联网 | 路网、围栏多边形、POI | 围栏随渠道/政策变 |
| 机器人 | 栅格（PGM+YAML）、矢量、3D 点云、楼层拓扑 | 站点改造后必须回归 |

**地图版本与协议版本同理**：地图变了，历史轨迹和事故要按"当时的地图"解释。

契约 `MapRef`：`map_id`、`version`、`crs`、`hash`、`valid_from`、`valid_to`。轨迹/事件表存 `map_ref` 而不是"最新地图"。

### 5.4 时空索引与检索

| 能力 | 做法 |
|---|---|
| 空间索引 | GeoHash / H3 单元格列 + 分区裁剪；需要精确几何时走 PostGIS |
| 时空联合 | `dt + geohash` 双层分区；查询先裁剪分区再算几何 |
| 典型查询 | "过去 1 小时在 A 区的车"、"A 站点南门 30 米内的事故"、"某轨迹经过哪些围栏" |
| 多模态检索 | 视频/点云按 `(time, geohash, event_id)` 建索引，支持"找那次接管前 30 秒的视频" |

这一块通用平台完全没有：D2/D4 只认时间和分区键，不认空间。

### 5.5 时点查询（bi-temporal）

诊断必须回答："故障发生那一刻，这台车是什么配置、什么固件、属于谁、在哪个站点。"

需要双时间维表：

| 时间 | 含义 | 例子 |
|---|---|---|
| `valid_time` | 业务上何时生效 | 2025-03-01 起这辆车归属 A 门店 |
| `transaction_time` | 系统何时记录 | 2025-03-05 才补录进系统 |

契约 `AsOfQuery`：`entity_ref`、`valid_at`、`as_of`。所有维表（车型配置、固件、车主、站点归属）都用 SCD2，禁止覆盖更新。

### 5.6 时空样本与证据

- 训练样本的 `WindowRef` 带 `spatial` 字段（§3.8），保证"同一地点同类事件"能被切片。
- 证据链扩展：`EvidenceRef` 的 `locator` 支持 `(device, t_start, t_end, geohash)`，让"视频片段"可被时空定位，而不只是一个文件路径。

## 6. 在线与告警（横切）

### 6.1 四层时效

| 层 | 延迟 | 用途 | 归属 |
|---|---|---|---|
| L0 设备端 | <100 ms | 保护、急停 | 设备固件（**不做**） |
| L1 边缘 | <1 s | 本地告警、断网自治 | 边缘运行时（§4.3） |
| L2 平台流 | 1–10 s | 平台告警、围栏、热失控预警 | Flink CEP（D4） |
| L3 批 | 分钟+ | 统计、模型、复盘 | Spark（D4） |

需求文档已明确不做控制指令下发，所以平台侧上限是"告警 + 建议"，不是"控制"。

### 6.2 规则与状态机

- 规则形态：阈值 / 持续时长 / 组合条件 / 序列（A 之后 N 秒内 B）。
- **有状态**：离线判定 = 心跳缺失 N 秒；围栏 = 上一次位置 + 本次位置跨边界。
- 规则版本化与灰度：规则也是 `ArtifactRef`，可以下发边缘（§4.4）。

### 6.3 告警运营（与"事件检测"不是一回事）

| 能力 | 说明 |
|---|---|
| 去重 | 同设备同规则时间窗合并 |
| 抑制 | 父子告警、维护窗口、已知故障 |
| 分级 | P0（安全）/ P1（可用性）/ P2（体验） |
| 路由 | 派单、短信、机器人通知 |
| SLA | 响应时限、升级路径 |
| 质量指标 | 准确率、误报率、MTTA、MTTR、风暴抑制比 |

通用平台有"数据质量告警"，那是运维告警。**业务告警需要设备语义 + 设备状态 + 闭环到人**，这是增量。

## 11. 规模重估（与现有假设冲突）

现有数据平台规模假设是生产 **5 TB/天**，对车联网不成立：

| 场景 | 计算 | 日增 |
|---|---|---|
| 100 万车 × 50 MB 遥测 | 1e6 × 50 MB | **50 TB/天** |
| 10 万台机器人 × 2 GB（含包） | 1e5 × 2 GB | **200 TB/天** |
| 若 CAN 原始全量上传（1 GB/车/天） | 1e6 × 1 GB | **1 PB/天** |
| 轨迹点（30s 一个点） | 1e6 × 2880 | **28.8 亿点/天** |
| 心跳（30s 一次，100 万设备） | 1e6 / 30 | **3.3 万 msg/s** |

**结论**：不降采样就不成立。边缘策略必须是：

1. 原始全量本地留存 7–30 天，**事件触发**才全量回传；
2. 常传的是降采样信号（0.1–1 Hz）+ 分钟级统计特征；
3. 大对象按策略回传（事故/接管 100%，其余抽样）。

这条要写进与设备团队的 SLA，否则平台侧容量永远追不上。

## 13. 风险与坑

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | 做"万能解析引擎" | 协议无限长尾，做不完 | 只做 SPI + 登记簿，codec 外包 |

| 6 | 负样本用"没报修" | 模型学"谁会修车" | 倾向采样 + 抽检 |

## 14. 最小纵切（建议先跑这一条）

8 周、不碰真车真机，验证三条轴的最小闭环：

**轴 A（数据流）**

1. 边缘模拟器：10 车 × 50 信号 × 1 Hz（合成帧，带 DBC v1）+ 1 个合成 MCAP；
2. 原始帧落 raw → 解码落 Iceberg 长表 → Doris 查最新值；
3. **用 DBC v2 再解析一次，证明历史仍按 v1 解释**（最关键的一条）；
4. MCAP 包 → 索引表 → 按话题抽 Parquet。

**轴 C（时空）**

5. 轨迹点入库 → geohash 分区 → "某区域过去 1 小时的车"查询；
6. 一个围栏多边形 → 进出事件；
7. 地图 v1/v2 切换后，历史轨迹仍按 v1 解释。

**轴 B（设备 + 在线）**

8. 孪生状态：10 台设备的最新状态从事件流折叠出来；
9. 一条离线告警（心跳缺失 60s）+ 一条围栏告警，含去重与抑制；
10. 一个模型包下发到"边缘"（本地容器模拟）+ 回滚。

**收口**

11. 端到端查询：某设备某时段某信号 + 当前位置 + 最近告警 + 关联工单。

跑通 = 三轴设计成立；跑不通 = 抽象错了，早发现比晚发现便宜一个数量级。
