# Lakehouse 向量化数据湖

> 状态：⬜ 未开始
> 对应 roadmap 阶段：第 三 阶段
> 对应文档：`roadmap/大模型数据中心平台工程师.md`

## 目标

把 01/02 的「语料 + 向量」从**文件与向量库各管一摊**，升级为**湖仓统一管理**：端到端输入是「语料表 + embedding 表 + 增量批次」，输出是「一个可快照、可时间旅行、可演进 schema 的向量化数据湖，且向量索引与表数据同源同版本」。

一句话可检验目标：**同一份语料与其向量在湖仓里由同一次提交产生（同版本）；支持加列式的 schema evolution；能按快照 id 复现任意历史版本的数据与索引；小文件与分区布局有实测的成本影响数字。**

（本项目补的是**存储与版本层**：让"数据 + 向量"具备 ACID、时间旅行与增量读的能力。）

## 技术栈

- 表格式：Apache Iceberg（首选）或 Delta Lake（二选一，实施时记录选型理由与目录布局）
- 存储：本地文件系统起步，**对象存储（MinIO/S3）作为目标形态**（不作为则如实标注差异）
- 计算：PySpark 或 DuckDB/Trino 之一（按数据规模选择；小规模用 DuckDB 验证语义，规模化用 Spark）
- 向量索引：与表同目录管理的索引文件（如 faiss/ hnswlib 产物），或 Milvus 的外部索引；**索引必须记录「基于哪个快照构建」**
- 元数据与血缘：Iceberg 快照/清单 + 自建血缘表（表 → 快照 → 索引 → 消费方）
- 编排：Airflow 或脚本 + 幂等分区重写（与 01 同一套纪律）

## 系统架构

```text
语料表(ODS→DWD)          嵌入表(embedding)            向量索引
   │  写入(append/overwrite)  │  写入                        │ 构建
   ▼                         ▼                             ▼
┌──────────────────────────────────────────────────────────────┐
│            Iceberg / Delta 表格式（快照 + 清单 + 原子提交）      │
│   snapshot#1000 ──▶ #1001 ──▶ #1002   （父链，可时间旅行）      │
│   schema evolution：加列/改类型（不兼容变更 fail-fast）           │
└──────────────────────────────────────────────────────────────┘
        │                          │                        │
        ▼                          ▼                        ▼
  历史版本复现              增量读(自快照X以来)         索引与快照版本对齐
  (排查"上周的数")          (只处理变化分区)            (查询时校验同源)
        │
        ▼
  分区布局与小文件治理（compaction 决策 + 成本对比数字）
```

模块边界与关键决策：

| 模块 | 职责 | 关键设计点 |
|------|------|-----------|
| 表定义与演进 | 语料表、向量表、分区键 | 分区键要对齐主要查询谓词（按日期/语料来源）；schema 变更走兼容性校验 |
| 写入与提交 | append / 分区覆盖 | 重跑用**分区覆盖**保证幂等；提交是原子指针替换 |
| 索引一致性 | 索引基于快照构建并登记 | **索引必须记录 snapshotId**，查询前校验，防止"索引新、数据旧" |
| 增量读 | 比较两快照的清单差异 | 下游只处理变化分区（省扫描量与计算量） |
| 布局治理 | 小文件检测 + compaction | 给出「扫描字节数 / 文件数 / 合并收益」三组数字 |

## 复用的算法实验

- [迷你 RAG 检索增强生成](../../algorithms/05-generative/mini-rag/) —— 向量索引的构建与检索口径由它定义；本项目负责让索引产物**与表快照同版本**
- [K-Means 聚类](../../algorithms/02-statistical-ml/kmeans/) —— 语料/向量的分区与聚簇布局分析（分区键与聚簇列的选择依据）
- [PCA 主成分分析](../../algorithms/02-statistical-ml/pca/) —— 向量分布分析（决定是否值得做量化/降维压缩，以及压缩对检索召回的影响）
- 说明：本项目的重点是**表格式与版本语义**（工程侧），算法实验只提供"向量怎么来、怎么检索"的口径，不提供存储引擎实现

## 验收标准

- [ ] 语料表与向量表由 Iceberg/Delta 管理，能在本地（或对象存储）完成**原子提交**并产生快照链
- [ ] 能按 snapshotId 或时间点**复现历史版本**的数据与索引（读到与当时一致的条数与抽样内容）
- [ ] 支持 schema evolution：加列成功；删列/改类型被**拒绝并给出原因**（fail-fast）
- [ ] 能计算两个快照之间的增量分区列表，并据此做一次增量处理（只读变化分区）
- [ ] 向量索引登记了「基于哪个快照构建」，查询前校验通过；人为制造索引/数据版本不一致时**能被拦下**
- [ ] 小文件检测与 compaction 决策有实测数字：合并前后**文件数、扫描字节数、读收益比**
- [ ] 重跑幂等：同一分区整体覆盖两次，结果一致（条数与内容哈希不变）
- [ ] 依赖外部服务（对象存储、Spark 集群）的部分如实标注「未在本环境验证」与复现命令

## 实施笔记

- **2026-09（梳理阶段）**：把「索引与快照同源」列为硬验收——这是"向量化数据湖"相对"向量库 + 文件目录"的本质差异，也是线上最常见的坑（索引重建失败后，数据已前进、索引还停在旧版本）。另外刻意要求 compaction 的**收益数字**，避免治理变成拍脑袋。
- **2026-09（待验证假设）**：① Iceberg vs Delta——Iceberg 的隐藏分区与清单结构更适合教学演示「快照 + 清单」心智，暂定首选；② 是否需要对象存储——本地文件系统能验证全部表格式语义，但"对象存储上没有目录级事务"这一动机只有在 MinIO 上才真实，实施时尽量补上。
- **与 01/02 的接口约定**：01 产出的语料分片、02 产出的向量都是本项目的输入表；一旦本项目接管存储，02 的检索应改为**读湖仓表 + 索引**，而不是直连原始文件——这条迁移路径要在实施时验证一遍（否则会出现两套事实来源）。
