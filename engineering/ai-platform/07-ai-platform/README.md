# AI 数据中心平台端到端整合

> 状态：⬜ 未开始
> 对应 roadmap 阶段：第 七 阶段
> 对应文档：`roadmap/大模型数据中心平台工程师.md`

## 目标

把阶段一~六的交付物**集成为一个平台**并跑通一条端到端业务流：端到端输入是「一份原始语料 + 一个业务问题」，输出是「从数据接入 → 清洗 → 入库 → 检索 → 微调 → 推理 →（可选）Agent 托管 的全链产物，外加贯穿全程的监控、告警与成本账」。

一句话可检验目标：**一条命令（或一个 5 步清单）能在全新环境里把平台拉起来，然后跑通「投入新语料 → 问答质量更新」的完整闭环，并在同一屏看到链路健康、资源用量与本次闭环的成本。**

（阶段七**不引入新技术栈**：它是前六个阶段的**集成验收**——每条链路的接口、幂等与可观测性在整合时才会真正被检验。）

## 技术栈

- 容器化：每个阶段交付物各自 Dockerfile + `docker compose`（或 Helm chart）统一编排
- 接口契约：阶段一/二/三/五各暴露服务接口（HTTP 或 CLI），阶段七只做**编排与治理**，不重写内部实现
- 编排与调度：Airflow（或 DAG 编排器）编排数据流；阶段四的调度器负责 GPU 作业
- 存储与元数据：湖仓表（阶段三）+ 元数据库（作业/数据集/模型版本）
- 监控告警：Prometheus + Grafana（链路健康、队列、GPU、推理指标）+ Alertmanager 规则
- 成本：统一计费口径（存储 GB·天、GPU·秒、tokens），按租户/项目归集
- 治理：数据与模型版本台账、权限与审计（谁能读哪份数据、谁发布了哪个模型）
- 环境：单机 Docker Compose 起步；K8s 作为目标形态（阶段四的调度器可对接）

## 系统架构

```text
                        ┌───────────────────────────────┐
                        │     平台控制台 / 统一入口        │
                        │ 链路状态 · 作业提交 · 成本 · 版本 │
                        └───────────────────────────────┘
         ┌──────────────┬───────────────┼───────────────┬──────────────┐
         ▼              ▼               ▼               ▼              ▼
   ┌──────────┐  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
   │ 01 语料   │→ │ 03 湖仓   │→  │ 02 RAG   │→  │ 05 推理   │→  │ 06 Agent │
   │ 加工流水线 │  │ 向量化数据湖│   │ 知识库问答 │   │ 服务      │   │ 平台底座  │
   └──────────┘  └──────────┘   └──────────┘   └──────────┘   └──────────┘
         │              │               │             │              │
         └──────────────┴───────┬───────┴─────────────┴──────────────┘
                                ▼
                     ┌─────────────────────────┐
                     │ 04 GPU 调度 + 资源账本    │  ← 为微调/推理提供算力
                     └─────────────────────────┘
                                │
        ┌───────────────────────┼────────────────────────┐
        ▼                       ▼                        ▼
  监控告警(Prometheus/Grafana)  成本归集(存储/GPU/tokens)  版本与审计台账
```

集成顺序（**可增量推进**，这是阶段七的关键设计）：
先搭平台骨架（控制台 + compose + 监控）→ 每完成一个阶段就把其成果接进来（接口 + 健康检查 + 计费口径）→ 全部接入后跑一次「新语料 → 问答更新」的闭环验收。

| 模块 | 职责 | 关键设计点 |
|------|------|-----------|
| 统一编排 | 拉起/停止/升级各组件 | 一条命令可复现；组件版本可回滚 |
| 接口契约 | 各阶段服务对外接口 | 契约先定死（输入/输出/错误语义），内部实现可替换 |
| 链路追踪 | 跨组件 trace（一次问答经过哪些组件） | 断链要能定位到具体组件 |
| 监控告警 | 健康 + 资源 + 业务指标 | 告警规则要能真触发（演练一次） |
| 成本归集 | 三类口径统一 | 口径写清（含空转、排队、重试是否计费） |
| 治理台账 | 数据/模型版本与权限审计 | 「谁用了哪份数据、发布了哪个模型」可追溯 |

## 验收标准

- [ ] 一条命令（`make up` / `docker compose up`）在干净环境拉起全部已接入组件，且每个组件有健康检查
- [ ] 跑通端到端闭环：投入新语料 → 加工 → 入湖 → 重建索引 → 问答效果变化（给出**前后对比**的实测答案）
- [ ] 全链有跨组件 trace：任一次问答能列出经过的组件与各段耗时
- [ ] 监控可用：Grafana 至少覆盖链路健康、队列/资源、推理指标三类面板；**至少一条告警规则被真触发过一次**（演练记录）
- [ ] 成本可归集：一次闭环后输出「存储 / GPU·秒 / tokens → 租户 → 估算金额」，三类口径与各组件的计量事件对账一致
- [ ] 治理台账可用：能查到「某份数据被哪些作业使用、某个模型由哪次训练产出、谁发布了它」
- [ ] 组件可替换性验证：至少替换一个组件实现（如换 LLM 后端或换向量库）而**不改其他组件的代码**（证明契约有效）
- [ ] 未接入的部分（真实 GPU 集群、K8s 生产形态、真实对象存储）如实标注，并给出接入路线

## 实施笔记

- **2026-09（梳理阶段）**：阶段七的定义里最关键的一句是「**可增量推进**」——它不是"最后憋一个大招"，而是"骨架先行、逐个接入"。因此本 README 把「一条命令拉起」「契约先定死」「告警真触发一次」写进验收：这三条恰好是"集成"与"堆服务"的分界线。
- **2026-09（待验证假设）**：① 单机 Compose 能否承载所有组件（内存是主要约束，可能需要分批起 + 轻量替代件）；② 成本口径里"空转与重试是否计费"要先决策再实现（否则账对不上）；③ 06 Agent 平台仍在 Part 1 沉淀，整合时先按「可选组件」接入，不阻塞闭环。
- **与 languages/ 的边界（2026-09 明确）**：languages/ 承载**语言学习与工程纪律的语义层**（如 AI 平台控制面的任务/配额/模型/发布语义、湖仓与编排的口径语义）；本项目承载**真实系统的实现与真实指标**（真调度、真推理、真压测、真成本）。二者不重复：languages/ 讲"应该怎么做、为什么"，本项目交付"跑起来的系统与实测数字"。
