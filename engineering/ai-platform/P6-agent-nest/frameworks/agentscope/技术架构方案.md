## 1. 概述

### 1.1 背景与目标

建设一套企业级多租户 Agent 平台，满足四类核心诉求：

1. **多端接入**：Agent 能力可嵌入内部系统（iframe / JS-SDK）、企业微信工作台、飞书等 IM 渠道。
2. **集中治理**：平台管理员（Admin）统一管理模型 API Key、配置 Agent（提示词 / Skill / MCP / RAG）、维护 SkillsHub / MCPHub / RAGHub / 模型中心，并负责发布。
3. **发布即服务**：Admin 发布的 Agent，各租户用户可直接查看、启用、使用，无需自行配置。
4. **租户自治**：租户可在自己的工作空间内配置私有 Agent、Skill、MCP、RAG、模型，也可以引用公共 Hub 资源组合配置。

### 1.2 技术基座

平台基于 **AgentScope 2.0（Python 版）** 构建。关键技术判断：

> AgentScope 2.0 Python 版的 `agentscope.app` 模块本身就是一个生产级 FastAPI 服务，内置了 ChatService 装配器、RedisStorage（Agent/Session/Message/Credential 持久化）、RedisMessageBus（会话分布式锁、SSE、事件 replay、跨进程 inbox）、WorkspaceManager（Local/Docker/E2B 沙箱、MCP 客户端、Skills 加载）、知识库服务和定时任务。

因此平台**不自建运行时层**，而是：

- **控制面（Control Plane）全部自建**：租户、用户、RBAC、Hub 资源库、Agent 模板与发布、审计、计量、MCP 网关、渠道适配。
- **数据面（Data Plane）复用框架 + 扩展点注入**：通过 `create_app()` 预留的扩展点（身份解析覆盖、WorkspaceManager 子类、Middleware 工厂、Tool 工厂）注入多租户逻辑。

### 1.3 设计原则

| 原则 | 说明 |
|---|---|
| 不重复造轮子 | 会话、事件流、锁、凭证、状态恢复全部复用 agentscope.app；平台只做框架不管的事 |
| 控制面 / 数据面分离 | 控制面管"配置与治理"，数据面管"执行与会话"，两者通过"发布物化"单向同步 |
| 发布即物化 | Agent 发布时把模型凭证、Skill 文件、MCP 配置、RAG Collection 物化到运行时；运行时无状态、不连业务库 |
| 隔离边界收敛 | 框架内核只认 `user_id`；租户隔离在尽可能少的代码路径上强制（身份解析、Workspace 路径、向量 Collection 命名、MCP 网关） |
| 版本不可变 | 发布生成不可变快照；运行中的会话永远绑定发布时的版本，配置修改不影响存量会话 |
| 安全默认 | 高风险工具默认人工审批；API Key 加密存储、凭证不出网关；沙箱默认开启 |

### 1.4 术语表

| 术语 | 含义 |
|---|---|
| 控制面 | 自建的 FastAPI 管理服务，负责租户/Hub/发布/审计/计量 |
| 数据面 / 运行时 | 基于 agentscope.app 的 Agent 执行服务 |
| Hub | 平台级资源仓库，分全局 Hub（Admin 维护）与租户私有 Hub |
| 物化（Materialize） | 发布时把控制面配置转换为运行时可用实体（Credential、workspace 文件、MCP 配置、向量 Collection） |
| HarnessAgent | AgentScope 2.0 的 Agent 运行容器，封装工作区人格、状态恢复、上下文压缩等 |
| 会话锁 | RedisMessageBus 提供的 `session_run` 分布式锁，保证同一会话串行执行 |

### 2.2 两进程模型

| 进程 | 职责 | 状态 | 存储 |
|---|---|---|---|
| **control-plane** | 租户/用户/RBAC、Hub CRUD、Agent 模板与版本、发布物化、审计、计量、配额、MCP 网关、渠道适配器 | 有状态（业务数据） | PostgreSQL + MinIO（Skill 包/文档原件） |
| **runtime**（agentscope.app） | 会话管理、Agent 装配与执行、事件流/SSE、模型调用、工具执行、沙箱 | 无状态（状态全在 Redis） | Redis（框架托管） |

两个进程的职责边界：**控制面永远不参与单条消息的执行链路**；运行时永远不查询业务数据库。两者唯一的同步通道是"发布物化"（控制面 → 运行时的单向写入）。

### 2.3 关键交互流程

**流程一：Admin 发布 Agent（物化流）**

```
Admin → 控制面: 保存 Agent 配置（prompt/skill/mcp/rag/model 引用）
控制面: 生成 agent_release 不可变快照（版本号 + 配置 JSON + 资源锁定版本）
控制面 → 运行时 Redis:
  ① 模型：创建/复用 Credential 记录（API Key 加密）
  ② Skill：渲染 SKILL 文件包到 workspace basedir 的 skills/ 目录
  ③ MCP：写入 default_mcps 配置（endpoint 指向 MCP 网关，不含真实凭证）
  ④ RAG：确保 Milvus Collection tenant_{id}_{kb} 存在
控制面 → 控制面 DB: 写入 tenant_agent_bindings（可见范围）
```

**流程二：用户发起对话（执行流）**

```
用户 → 渠道/Web → API Gateway → runtime: POST /chat (Bearer 平台JWT)
runtime.auth: dependency_overrides[get_current_user_id] 解析 JWT
             → 提取 tenant_id/user_id/role 写入 contextvar
runtime.ChatService:
  ① 按 session 从 RedisStorage 恢复 AgentState（含历史、记忆）
  ② 装配：模型（chat_model_config→Credential 解析）+ Toolkit
        + Middleware（框架内置 + 租户配额/审计/权限中间件）
        + RAG 检索工具（租户 Collection 绑定）
  ③ 获取 session_run 分布式锁（同会话串行）
  ④ 驱动 reply_stream 事件流 → SSE 推送给调用方
  ⑤ 事件落 replay 日志（断线重连补流）、状态回写 RedisStorage
runtime → 计量消费者: 事件流中聚合 token 用量（异步）
```

**流程三：企微消息（渠道流）**

```
企微用户 → 企微服务器 → wecom-adapter Webhook
wecom-adapter: 消息解密 → 企微 UserID 映射平台 user_id/tenant_id
             → 代签平台 JWT → 调 runtime POST /chat
             → 消费 SSE 事件流 → 转换为企微消息/卡片 → 企微 API 回推
```

## 3. 核心架构决策（ADR）

### ADR-001：复用 agentscope.app 运行时，不自建 Runtime 集群

- **背景**：初版设计计划自建"AgentScope Runtime Service"，自行实现会话管理、SSE、事件总线、锁。
- **决策**：直接以 `agentscope.app` 为运行时基座，通过官方扩展点注入租户逻辑。
- **理由**：框架已提供 ChatService 装配、RedisStorage、RedisMessageBus（会话锁/replay/inbox）、WorkspaceManager、凭证解析；自建等于重写框架且需长期跟进上游演进。
- **影响**：原设计中的 `sessions` 表、Kafka 事件流、自研 SSE 网关全部删除；团队工作量收敛到控制面。
- **代价**：运行时行为受框架约束，需通过 M0 阶段 POC 验证扩展点满足全部隔离需求。

### ADR-002：控制面 / 数据面分离，发布时物化

- **决策**：控制面持有的 Hub 资源（Skill/MCP/RAG/模型）在**发布时刻**物化为运行时实体，运行时不在执行链路中回调控制面。
- **理由**：① 运行时无状态、可水平扩展、故障域隔离（控制面宕机不影响进行中的会话）；② 版本快照天然不可变；③ 执行链路延迟不叠加业务库查询。
- **影响**：Hub 资源的"修改"对已发布版本不生效，必须重新发布；这是特性而非缺陷（符合版本不可变原则）。

### ADR-003：租户隔离边界收敛在四条路径

AgentScope 内核只识别 `user_id`（Session/State/Workspace 均以此为粒度），`tenant_id` 不是框架原生概念。因此：

- **决策**：不试图让框架"感知租户"，而是把租户隔离强制收敛到四个自研组件：
  1. **身份解析**：`get_current_user_id` 覆盖 → JWT 提取 tenant_id 写入 contextvar；
  2. **Workspace 路径**：`TenantWorkspaceManager` 强制路径前缀 `tenants/{tenant_id}/`；
  3. **向量 Collection 命名**：统一入口强制 `tenant_{id}_` 前缀；
  4. **MCP 网关**：按 tenant_id 路由私有 MCP、注入对应凭证。
- **理由**：隔离逻辑分散在业务代码中必然出现绕过；收敛后可用少量代码审查 + 集成测试覆盖全部隔离面。
- **影响**：任何新增的资源类型必须在这四个组件之一中登记隔离策略，否则不允许上线（写入开发规范）。

### ADR-004：MCP 流量必须经过自建网关

- **背景**：框架的 MCP 权限策略不进入人工确认中间件，高风险 MCP 写操作无法在 Agent 侧审批；且私有 MCP 需要按租户注入凭证。
- **决策**：所有 MCP Server（全局与私有）均以 MCP 网关为唯一入口；Agent 配置的 MCP endpoint 一律指向网关。
- **网关职责**：协议代理（HTTP/SSE/Stdio 适配）、按租户注入凭证（真实 Key 不出网关）、高风险写操作审批（挂起-回调）、调用审计、限流。
- **影响**：`Agent 配置中的 ${{secrets.xxx}}` 语法只在网关侧解析；运行时永远接触不到明文凭证。

### ADR-005：权限五档映射框架权限模式

> 【已对照 AgentScope 2.0.6 源码 `permission/_types.py:18` 核实】框架权限模式为**五档** `DEFAULT / ACCEPT_EDITS / EXPLORE / BYPASS / DONT_ASK`，**并不存在名为 "manual" 的独立模式**——早期版本的三档假设（explore/manual/bypass）有误，"人工确认"对应的是 `DEFAULT` 模式（默认对每个操作 ASK）。

- **决策**：Agent 配置的 `permissions.mode` 映射框架内置的五档权限模式，通过 Middleware 工厂按 Agent 发布快照挂载。平台对外暴露的权限档与框架枚举的映射关系：

| 平台权限档 | 框架 `PermissionMode` | 语义 | 适用场景 |
|---|---|---|---|
| `explore`（只读探索） | `EXPLORE` | 只读工具/只读 bash 放行，修改类一律拒绝 | 数据分析、代码审查等只读 Agent |
| `confirm`（人工确认，**默认**） | `DEFAULT` | 每个操作默认 ASK，最安全 | 大多数生产 Agent，高风险操作逐次确认 |
| `auto_edit`（自动放行编辑） | `ACCEPT_EDITS` | 工作目录内的写文件/文件命令自动放行 | 受信工作目录内的开发迭代 Agent |
| `unattended`（无人值守） | `DONT_ASK` | 所有 ASK 转为 DENY，安全默认 | 定时任务 / 后台 Agent（用户不在场） |
| `sandbox_bypass`（沙箱全自动） | `BYPASS` | 跳过全部检查（**含安全 ASK**），仅 deny 规则兜底 | **仅限沙箱化、无真实凭证的 Agent** |

- **安全警告（BYPASS 红线）**：框架在 `BYPASS` 下**连安全 ASK 都不强制**——`rm -rf /`、写 `~/.bashrc`、命令注入模式等危险操作不会被拦截。因此 `sandbox_bypass` **禁止**用于任何持有真实凭证的生产 Agent；无人值守场景必须用 `unattended`（DONT_ASK）而非 BYPASS。
- **补充**：`allowed_tools` / `forbidden_command_patterns` 在租户权限中间件中实现（工具名白/黑名单 + Bash 命令正则拦截），MCP 工具的审批在网关侧兜底（ADR-004）。**注意**：正则黑名单是纵深防御的一层，**不构成安全边界**——它可被编码/变量拼接/间接调用绕过；真正的执行安全边界是沙箱隔离 + `EXPLORE`/`DONT_ASK` 模式。

## 4. 多租户设计

### 4.1 两级空间模型

| 层级 | 管理者 | 资源范围 | 可见性 |
|---|---|---|---|
| 全局空间（Global） | 平台 Admin | 公共模型、公共 Hub 资源、公共 Agent 模板 | 全部租户可见（只读引用） |
| 租户空间（Tenant） | 租户管理员 | 私有模型、私有 Hub 资源、私有 Agent | 仅本租户 |

数据表达：所有 Hub 资源表与 Agent 表以 `tenant_id IS NULL` 表示全局资源，`tenant_id = {id}` 表示租户私有。

### 4.2 身份与上下文传递

```
┌─────────────────────────────────────────────────────────┐
│ 平台 JWT（控制面签发，RS256）                             │
│ { sub: user_id, tenant_id, role, exp, jti }             │
└─────────────────────────────────────────────────────────┘
                │ Authorization: Bearer ...
                ▼
┌─────────────────────────────────────────────────────────┐
│ runtime: dependency_overrides[get_current_user_id]      │
│  ① 验签（控制面公钥，JWKS 端点定期拉取）                   │
│  ② tenant_ctx.set({tenant_id, user_id, role})           │
│  ③ return user_id  ← 框架内部只使用这个值                 │
└─────────────────────────────────────────────────────────┘
                │ contextvar（请求级）
                ▼
   TenantWorkspaceManager / Middleware工厂 / Tool工厂 / MCP网关
```

渠道用户（企微/飞书）不直接持有 JWT：渠道适配器维护「渠道用户 ↔ 平台用户」映射表，由适配器向控制面换取**受限 JWT**（仅聊天权限、短时效、绑定渠道标识）。

#### 4.2.1 非请求路径的 tenant 上下文（定时任务 / 后台触发）

`tenant_ctx` 是请求级 contextvar，由 `resolve_platform_user` 在处理 HTTP 请求时写入。但 Agent 装配不仅发生在 HTTP 请求内——**定时任务（schedule 触发）、idle-session 唤醒、渠道 Webhook 异步触发**等后台路径没有 HTTP 请求上下文，此时 `tenant_ctx.get()` 会拿到空值，导致租户隔离与配额中间件失效。

**设计：后台路径从 session 记录反查租户，而非依赖请求 contextvar。**

```
HTTP 请求路径:   resolve_platform_user → tenant_ctx.set()  ✓ 有请求上下文
后台触发路径:    无 HTTP 请求
                 → 装配时 tenant_ctx 为空
                 → 回退: 由 session_id 查 session 记录（Redis）
                        → 从 session 元数据直接读 tenant_id
                          （创建会话时已物化冗余，不回查 PG）
                 → 装入 tenant_ctx 后再进入装配链路
```

实现要点：

1. **统一入口**：中间件/工具工厂不直接读 `tenant_ctx.get()`，而是调用 `resolve_tenant_ctx(user_id, session_id)`——优先读 contextvar（请求路径快路径），为空时回退到 session 元数据反查（后台路径）。
2. **session 记录冗余 tenant_id**：创建会话时把 `tenant_id` 写入 session 元数据（Redis），后台路径一次反查即可，**不回查 PG**（保持"运行时不连业务库"原则——tenant_id 在会话创建时物化进 session 记录）。
3. **M0 验证项**：把"非 HTTP 触发的 Agent 装配能否正确获得 tenant_ctx"列为 M0 必测用例（已纳入 M0 任务 0.8b）。

### 4.3 Workspace 物理隔离

框架 WorkspaceManager 原生隔离粒度为 per_agent / per_session / per_user 三档；平台通过子类化叠加租户命名空间：

```
/data/workspaces/
├── global/                              # 全局资源物化区（只读挂载）
│   └── skills/{skill_name}/{version}/
└── tenants/
    └── {tenant_id}/
        ├── agents/{agent_id}/           # per_agent 工作区
        │   ├── AGENTS.md                # 物化生成的工作区人格
        │   ├── skills/                  # 发布时渲染的 Skill 文件
        │   ├── memory/
        │   └── sessions/{session_id}/   # per_session 子空间
        └── users/{user_id}/             # 用户级私有空间（草稿、上传文件）
```

隔离强制点（`TenantWorkspaceManager`）：

1. 任何路径解析结果必须落在 `tenants/{contextvar.tenant_id}/` 前缀内（resolve 后校验，防 `../` 穿越）；
2. 全局目录以只读方式合并视图；
3. 配额检查：单租户 workspace 总量、单 workspace 大小上限，超限拒绝并告警。

### 4.4 数据隔离矩阵

| 数据类型 | 存储 | 隔离机制 | 强制点 |
|---|---|---|---|
| 业务元数据（租户/用户/Hub/Agent/审计） | PostgreSQL | 行级 `tenant_id` + 应用层强制过滤（SQLAlchemy 全局 filter） | 控制面 Repository 基类 |
| 会话/消息/AgentState | Redis（框架托管） | 框架按 user_id 隔离；租户间天然隔离（user 属于唯一租户） | 身份解析（ADR-003-1） |
| 凭证（API Key） | Redis Credential 记录（密文） | 加密存储；按租户归属标记 | 控制面下发 + 网关解析 |
| 向量数据 | Milvus | Collection 命名 `tenant_{id}_{kb_name}`，统一访问入口 | RAG Tool 工厂（ADR-003-3） |
| 文件/Skill 包/知识库原件 | MinIO + workspace 磁盘 | Bucket 路径前缀 `tenants/{id}/` | Workspace 管理器 + 对象存储封装 |
| 代码执行 | 沙箱（Docker/E2B） | 每会话独立沙箱实例，网络策略按租户 | WorkspaceManager sandbox 配置 |
| 审计日志 | PostgreSQL（追加写） | 全量记录 tenant_id，租户仅可查自身 | 审计查询接口强制过滤 |

### 4.5 RBAC 权限模型

```
平台管理员(Admin)        租户管理员(TenantAdmin)        普通用户(User)
├─ 租户 CRUD/配额        ├─ 成员管理                    ├─ 使用已发布 Agent
├─ 全局 Hub 维护         ├─ 私有 Hub 维护               ├─ 创建个人 Agent（私有）
├─ 全局模型/凭证         ├─ 租户私有模型/凭证            ├─ 会话历史
├─ Agent 模板发布        ├─ 启用/停用公共 Agent          └─ 个人文件空间
├─ 全量审计              ├─ 租户内 Agent 创建/发布
└─ 系统配置              └─ 租户用量报表
```

实现要点：

- 权限判定全部在**控制面**完成（运行时只验 JWT 真伪，不做业务鉴权）；
- 渠道用户默认映射为 User 角色；
- 支持租户级自定义角色（v2.0，预留 `roles`/`permissions` 表结构）。

### 5.5 模型与凭证管理

| 项 | 设计 |
|---|---|

### 6.2 发布物化流程

```
┌─────────────┐   ┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ ① 校验      │ → │ ② 快照      │ → │ ③ 物化      │ → │ ④ 可见性    │
│ 引用完整性   │   │ 生成不可变   │   │ 写入运行时   │   │ 绑定租户    │
│ 权限/配额    │   │ release     │   │ 实体        │   │             │
└─────────────┘   └─────────────┘   └─────────────┘   └─────────────┘
```

① **校验**：所有 `ref` 存在且状态为 published；引用私有资源时校验归属；模型凭证存在。
② **快照**：`agent_releases` 写入完整解析后配置（版本全部锁定为具体值），生成版本号（semver 自增）。
③ **物化**（幂等，失败可重放）：
   - Credential：确保目标凭证记录存在于运行时存储（不重复创建，按内容哈希判等）；
   - Skill：从 MinIO 拉取文件包 → 写入 `tenants/{tid}/agents/{agent_id}/skills/`（public Agent 对每个启用租户物化一份视图，或采用共享只读层 + 租户覆盖层）；
   - MCP：写入该 Agent 的 default_mcps，endpoint 统一为网关地址；
   - RAG：校验 Collection 存在，缺失则创建空 Collection 并告警；
   - AGENTS.md：由 system_prompt + workspace_persona 渲染生成。
④ **绑定**：`tenant_agent_bindings` 写入（tenant_id, release_id, enabled, 租户覆盖项）。

### 6.3 版本与快照不变量

1. `agent_releases` 记录创建后**不可修改**（DB 层禁 UPDATE/DELETE，仅允许状态字段流转：published → deprecated）。
2. 会话创建时绑定 `release_id`，会话存续期间永远使用该版本快照执行。
3. 再次发布产生新版本；已启用租户的升级策略：`auto`（新会话用新版）/ `pin`（锁定当前版，需租户管理员确认升级）。
4. 资源下架（deprecate）不影响已物化的存量版本；强制下线需走"作废"流程并通知租户。

### 6.4 物化的撤销与回收（凭证吊销 / 资源下架）

发布物化只覆盖"写入"方向，本节定义反向语义——已物化到运行时的实体如何失效、回收。**核心原则：撤销与发布走同一条单向通道（控制面 → 运行时），运行时仍不回查控制面；撤销以"新快照 + 主动失效"两种方式实现，绝不原地修改存量 release。**

#### 6.4.1 撤销的两种触发与传播

| 触发 | 语义 | 传播动作 |
|---|---|---|
| **资源下架/更新**（Hub 资源 deprecate、Agent 改配置） | 产生**新 release**，旧 release 标记 `deprecated` | 走标准物化流写新实体；旧 release 按 §6.3 不可变保留，仅状态流转 |
| **凭证吊销 / 密钥轮换**（secrets 失效、API Key 泄露） | 不产新 release，属**安全事件**，需立即生效 | 控制面**主动失效**：删除/替换运行时 Redis 中对应 Credential 记录（按内容哈希定位） |

#### 6.4.2 凭证吊销的生效时序（安全关键）

凭证泄露等场景不能等"下次发布"，必须明确生效边界：

```
T0 控制面吊销凭证（secrets 标记 revoked）
T1 控制面 → 运行时 Redis:
     ① 删除/替换该 Credential 记录（物化时按内容哈希判等，反向同键定位）
     ② 写入失效标记 credential_revoked:{credential_id}（带 TTL）
T2 进行中的会话:
     - 当前 turn 已 resolve 出明文的，用到本轮结束（无法强撤内存中的明文）
     - 下一 turn 重新 resolve_credential → 命中失效标记/记录缺失 → 立即失败
       并返回明确错误（CREDENTIAL_REVOKED），不降级为旧值
T3 审计落库：吊销动作 + 受影响会话清单（按 credential_id 反查 tenant_agent_bindings）
```

- **存量会话处理**：新 turn 立即失效；当前 turn 不强行中断（避免半截输出），但审计标记"使用了已吊销凭证"。
- **不原地改 release**：凭证吊销不改 agent_releases 快照内容——快照里存的是 `credential_id` 引用，吊销作用于该引用指向的运行时实体，二者解耦。
- **联动过期挂起票据（三方叠加收口）**：凭证吊销时，必须**同时强制过期所有引用该 credential 的挂起审批票据**（`approval_tickets` 中 `status=pending` 且关联 Agent 使用该 credential 的记录）。否则会出现：某会话因高风险写操作挂起等待审批（最长 10 分钟），期间其模型凭证已被吊销，但挂起的 tool_call 仍可能在审批通过后带着旧凭证语境被执行——形成凭证滥用窗口。联动动作并入 T1：吊销 credential 的同时把相关 pending 票据置为 `expired`，网关侧对 expired 票据的回调一律拒绝。

#### 6.4.3 物化实体的回收

| 实体 | 回收机制 |
|---|---|
| Credential 记录 | 吊销时主动删除；孤儿记录（无 release 引用）由控制面定期对账清理 |
| Skill 文件（workspace skills/） | 新 release 物化时整体替换该 agent 的 skills 目录；`deprecated` 超 N 天且无活跃会话绑定的，由 TTL + 对账任务清理 |
| Milvus Collection | 知识库删除时显式 drop；孤儿 Collection（命名 `tenant_{id}_` 但无对应 KB 记录）定期对账 |
| 运行时 Redis 键 | 统一 `asrt:` 前缀 + TTL 治理；孤儿键由控制面对账任务扫描清理 |

#### 6.4.4 对账任务（Reconciler）

控制面后台周期任务，弥补"单向物化"不保证的最终一致性：

1. 以控制面 DB 为单一事实源，扫描运行时 Redis / Milvus / MinIO；
2. 找出"运行时存在但 DB 无对应有效 release/资源"的孤儿实体 → 清理并审计；
3. 找出"DB 有有效 release 但运行时缺失"的物化缺口 → 触发重放（物化幂等，可安全重放）；
4. 对账结果产出报告，异常（清理失败/重放失败）告警。

**对账周期与分级**：常规实体按 CronJob 每 15 分钟对账（见 §12.1）；**凭证类实体的吊销不走对账周期**——走 §6.4.2 的主动失效路径（即时生效），对账仅兜底凭证清理的遗漏项。即"15 分钟窗口"只适用于非凭证实体，凭证的失效时效不受对账周期约束。

```python
# runtime/auth.py
from contextvars import ContextVar
from fastapi import Header, HTTPException

tenant_ctx: ContextVar[dict] = ContextVar("tenant_ctx")

async def resolve_platform_user(authorization: str = Header(...)) -> str:
    payload = verify_jwt_with_jwks(authorization)      # 控制面 JWKS 验签
    tenant_ctx.set({
        "tenant_id": payload["tenant_id"],
        "user_id": payload["sub"],
        "role": payload.get("role", "user"),
        "jti": payload["jti"],
    })
    return payload["sub"]
```

```python
# runtime/factories.py —— 中间件工厂：配额 / 权限 / 审计
#
# 【已实证签名 · AgentScope 2.0.6 `app/_types.py`】工厂不接收 agent_record，
# 只接收 id。两种工厂的真实签名：
#   AgentMiddlewareFactory = (user_id, agent_id, session_id[, workspace])
#                            -> Awaitable[list[MiddlewareBase]]
#   AgentToolFactory       = (user_id, agent_id, session_id)
#                            -> Awaitable[list[ToolBase]]
# 因此「读取 release 快照」必须由工厂内部用 id 反查（见 load_release_snapshot），
# 而不能假设框架直接传入 agent 记录。
async def tenant_middleware_factory(
    user_id: str,
    agent_id: str,
    session_id: str,
    workspace,                       # WorkspaceBase；中间件工厂的可选第 4 参
):
    ctx = tenant_ctx.get()
    snapshot = await load_release_snapshot(agent_id)   # 用 id 反查（见下）
    return [
        TenantQuotaMiddleware(ctx["tenant_id"]),        # token/并发/时长配额，超限快速失败
        PermissionMiddleware(                            # 映射五档(见 ADR-005): 平台档 → 框架 PermissionMode
            mode=snapshot["runtime"]["permission_mode"],
            allowed_tools=snapshot["runtime"]["allowed_tools"],
            forbidden_patterns=snapshot["runtime"]["forbidden_command_patterns"],
        ),
        AuditMiddleware(ctx),                            # 工具调用/模型调用异步上报控制面
    ]

async def tenant_tool_factory(
    user_id: str,
    agent_id: str,
    session_id: str,                 # 工具工厂无 workspace 参数
):
    snapshot = await load_release_snapshot(agent_id)
    tools = []
    if snapshot["capabilities"].get("rags"):
        tools.append(make_kb_search_tool(              # RAG 检索工具
            collections=resolve_tenant_collections(snapshot),
```

### 7.3 会话生命周期

```
创建会话
  → 校验 agent 对该租户可见且已启用（控制面前置校验，runtime 不重复查）
  → 写入 chat_model_config（credential_id + model + 参数）
  → 绑定 release_id

对话（每 turn）
  → ChatService 从 RedisStorage 恢复 AgentState（历史、记忆、工作区指针）
  → 装配（模型 + Toolkit + Middleware + RAG 工具）
  → session_run 分布式锁（同会话串行；锁内执行）
  → reply_stream 事件流 → SSE 推送；事件写 replay 日志
  → turn 结束：状态回写、锁释放、用量事件异步上报

断线重连
  → 客户端携带 last_event_id 重连 SSE → 从 replay 日志补流

会话结束/过期
  → workspace 按 TTL 回收；Redis 键按 TTL 过期；计量日结
```

### 7.4 并发与扩缩容

- runtime 进程**完全无状态**：多副本共享同一 Redis，任意副本可处理任意请求；会话锁保证同会话跨副本串行。
- HPA 指标：活跃会话数（主）+ 平均 turn 时长（辅），不用 CPU（LLM 等待导致 CPU 失真）。
- 单副本建议容量：以 asyncio 并发模型估算，4C8G Pod 承载 50~100 并发会话（M0 压测校准）。

### 7.5 沙箱策略

| 环境 | 后端 | 说明 |
|---|---|---|
| 开发 | local | 本机直跑，仅开发用 |
| 测试/预发 | docker | Docker-in-Docker 或挂载 docker.sock，镜像白名单 |
| 生产 | e2b（优先）/ docker（备选） | 每会话独立实例；网络出向白名单（仅 MCP 网关、模型端点）；资源限额 CPU/内存/时长 |

## 8. MCP 网关设计

### 8.1 定位与职责

所有 MCP 流量的唯一入口，部署于控制面侧：

```
Agent（runtime） ──MCP/HTTP──▶ MCP 网关 ──▶ 上游 MCP Server
                                  │
   ① 协议适配：HTTP/SSE ⇄ Stdio（托管 stdio 进程）
   ② 凭证注入：按 tenant_id + mcp_name 从密钥库取真实凭证，注入请求头/环境变量
   ③ 风险审批：risk_level=write 的 tool call → 挂起 → 审批回调 → 放行/拒绝
   ④ 审计：全量记录（tenant, user, agent, tool, args摘要, 结果码, 耗时）
   ⑤ 限流熔断：按租户 + MCP 双维度限流；上游异常熔断降级
```

### 8.2 审批流（高风险写操作）

```
Agent 发起 tool_call（如 gitlab.merge_pr）
  → 网关识别 risk_level=write
  → 生成 approval_ticket，挂起请求（或返回 pending 结构化响应）
  → 推送审批卡片到发起人所在渠道（企微/飞书/Web）
  → 审批人点击 批准/拒绝
  → 网关收到回调：批准→携带票据放行执行；拒绝→返回拒绝错误给 Agent
  → 全程审计落库；票据 10 分钟过期
```

#### 8.2.1 挂起的资源与安全窗口（量化与收口）

审批挂起不是"免费等待"——它与凭证吊销（§6.4.2）、会话锁（§7.3）三方叠加，构成文档必须量化收口的资源/安全窗口：

**资源占用（锁 + 会话状态）**

挂起期间会话仍持有 `session_run` 分布式锁，且 AgentState 常驻 Redis。量化口径（纳入 M0 压测基线 0.9 实测校准）：

| 项 | 估算/口径 | 上限与告警 |
|---|---|---|
| 单挂起会话锁占用 | 1 个 `session_run:{sid}` 锁，最长持有 10 分钟（票据过期即释放） | 不设上限，但纳入锁竞争监控 |
| 挂起会话总数 | 峰值按"300 并发会话 × 预估挂起率"估算；M0 实测挂起率前按 ≤10%（≈30 个）规划 | 超阈值告警：`pending_approvals > 50` 触发 |
| 锁/内存泄漏兜底 | **票据过期必须显式释放会话锁**，不等 turn 自然结束 | 过期未释放 → 计为异常，告警 |

**安全窗口（凭证 × 挂起）**

- 挂起的 tool_call 在审批通过后才执行——若此期间模型凭证被吊销，§6.4.2 的"联动过期挂起票据"已收口（吊销即把相关 pending 票据置 expired，回调拒绝）。
- **审批通过时的再校验**：网关放行挂起的 tool_call 前，**重新校验**该 Agent 当前凭证仍有效（非仅校验票据未过期），防止"挂起期间凭证被降级/轮换"导致的越权执行。
- 审批人权限：只有该租户 TenantAdmin 或发起人本人可审批，审批动作落审计（含审批人 identity，防止自审高危操作——高危操作建议强制"他人审批"）。

### 8.3 凭证引用协议

Agent/Hub 配置中的 `${{secrets.xxx}}` 仅在网关侧解析：

- `secret_ref` 指向控制面密钥库条目（KMS 加密存储）；
- 网关按 `tenant_id + secret_ref` 取密文 → KMS 解密（内存中）→ 注入上游请求 → 用后即弃；
- 运行时、Agent、LLM 上下文任何环节都接触不到明文凭证。

## 9. 多端接入设计

### 9.1 统一对话 API

```http
POST /runtime/v1/chat
Authorization: Bearer {platform_jwt}
Content-Type: application/json

{
  "agent_id": "agent_001",
  "session_id": "sess_xxx",            // 可选；空=新会话
  "message": "请审查这个 PR",
  "context": { "pr_url": "https://..." },
  "stream": true
}
```

SSE 事件（直接透传框架事件流，渠道适配器按需转换）：

```
event: message      data: {"type":"text","content":"..."}
event: message      data: {"type":"tool_call","name":"...","input":{...}}
event: message      data: {"type":"tool_result","name":"...","output":"..."}
event: approval     data: {"ticket_id":"...","tool":"...","summary":"..."}   # 待审批
event: done         data: {"session_id":"...","usage":{"tokens":1234}}
event: error        data: {"code":"QUOTA_EXCEEDED","message":"..."}
```

断线重连：`GET /runtime/v1/sessions/{sid}/stream?last_event_id={n}` 从 replay 日志补流。

### 9.2 渠道适配器通用架构

```
┌────────────────────────────────────────────────────┐
│ Channel Adapter（每渠道一个 Deployment，共用骨架）    │
│                                                    │
│  Inbound:  Webhook 验签/解密 → 消息标准化            │
│  Identity: 渠道UserID ↔ 平台user_id 映射 → 换取受限JWT│
│  Session:  渠道会话 ↔ 平台session_id 映射（Redis）    │
│  Outbound: 消费 SSE → 渲染渠道消息（Markdown/卡片）   │
│  Approval: 审批卡片渲染 + 按钮回调 → 网关审批接口     │
└────────────────────────────────────────────────────┘
```

### 9.3 企业微信

- 自建应用，回调 URL 指向 `wecom-adapter /webhook`；处理 URL 验证、消息加解密（AES）。
- 用户映射：`wecom_userid → user_id`；首次消息触发静默建档（归属租户按企微 corpId 绑定）。
- 消息形态：文本/Markdown；审查结果等结构化输出用**模板卡片**；群聊中 @机器人 触发。
- 审批：模板卡片按钮回调 → 网关审批接口。
- 注意：评估 AgentScope 生态中已有的企微渠道扩展组件，优先复用、按需改造。

### 9.4 飞书

- 应用开启事件订阅（`im.message.receive_v1`），Webhook 指向 `feishu-adapter`。
- 富文本与消息卡片（Card）展示复杂结果（diff、评分表）；交互按钮（批准/拒绝/重试）。
- 用户映射：`open_id → user_id`，按租户（飞书租户）绑定。

### 9.5 内部系统嵌入

| 方式 | 适用 | 实现 |
|---|---|---|
| iframe | OA/ERP 快速嵌入 | `/embed/chat?agent_id=&ticket=`；ticket 为一次性换 JWT 凭证；支持主题参数（CSS 变量） |
| JS-SDK | 深度定制 | 提供 `@company/agent-sdk`：初始化（endpoint/token/容器）、`send()`、事件订阅（text/tool_call/approval/done）、UI 插槽 |
| Open API | 后端系统/流水线 | 直接调统一对话 API（服务账号 JWT，按租户配额计费） |

## 11. 安全设计

| 域 | 措施 |
|---|---|
| 认证 | 平台 JWT（RS256，JWKS 轮换）；渠道用户受限 JWT（短时效、窄权限）；服务账号 mTLS（可选） |
| 授权 | 控制面统一鉴权；运行时只验签不鉴权；Repository 基类强制 tenant 过滤 |
| 凭证安全 | API Key/Secret 经 KMS 加密存储；明文仅在 MCP 网关内存瞬时存在；禁止入日志（日志脱敏中间件） |
| 执行安全 | 生产沙箱强制 docker/e2b；网络出向白名单；`forbidden_command_patterns` 正则拦截；Skill 上架安全扫描 |
| 数据隔离 | ADR-003 四条强制路径 + 隔离性集成测试（跨租户访问用例作为上线门禁） |
| 审批 | 高风险 MCP 写操作强制人工审批（ADR-004） |
| 审计 | 管理操作 + 会话执行（工具调用、模型调用、审批）全量追加写，租户只可见自身 |
| 传输 | 全链路 TLS；Webhook 验签（企微 AES / 飞书 encrypt key） |
| 配额与防滥用 | 租户 token/并发/存储配额；网关限流熔断；API Gateway 全局限流 |

| # | 风险 | 等级 | 缓解 |

| R7 | 模型成本失控 | 中 | 租户配额硬限制 + 用量告警 + 计费报表 |
| R8 | 企微/飞书回调稳定性（重试、乱序） | 低 | 适配器幂等设计（消息 ID 去重） + 队列缓冲 |
