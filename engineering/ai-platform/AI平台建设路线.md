## 1. 设计目标与原则

**目标**：以「成熟开源集成 + 薄自研胶水」构建企业级 **AI 数据中心平台**——数据（语料/向量/湖仓）+ 算力（K8s/GPU）+ 模型（微调/推理）+ 应用（RAG/Agent）共栈，对标业界 AI 平台的能力集（Databricks / 阿里云 PAI / 腾讯云 TI-ONE 一类）。

**核心判断**：**不自研平台，集成平台。** 向量库、推理引擎、湖表格式、容器编排、调度框架、Agent 框架在开源生态里都有成熟实现；本平台的工作是把它们**装起来 + 打通 + 补齐契约**，只在"入口"和"开源之间缺失的粘合层"上自研。

### 1.1 四条建设原则

| 原则 | 含义 |
|---|---|
| 底层引擎能用成熟开源就不自研 | 向量库 / 推理引擎 / 湖表格式 / 调度框架 / GPU 编排，先找事实标准 |
| 系统入口必须自建 | 统一控制台 + 开放 API 是平台的用户契约；各组件自带 UI 只作内部运维面 |
| 其余自研只做"胶水" | 只写开源之间缺失的粘合层（§4：1 入口 + 6 胶水 + 1 内核），且必须薄 |
| 每个单元可验证 | 每个单元都有可测的验收条目与实测数字；不接受"基本可用" |

**技术栈基调**：**Python 为主**（数据 / 训练 / 推理 / 应用）· **Rust / Go 为辅**（Agent 内核、平台服务）· **SQL 贯穿**。

### 1.2 企业级判据

**结构判据**（判断架构是否成立）：

| 判据 | 不成立时的样子 |
|---|---|
| 资产身份统一（数据 / 向量 / 模型 / 索引同源同版本） | "索引新、数据旧"，答案不可复现 |
| 治理内建在链路里（版本 / 权限 / 审计 / 成本随作业走） | 事后补台账，对不上账 |
| Data 与 AI 共栈（语料 → 向量 → 模型 → 应用一条链） | 数据平台与模型平台各玩各的 |
| 契约先定死（组件可替换而不改他人代码） | 换一个组件要改全链路 |

**横切判据**（每个单元都要过线）：

| 判据 | 不过线的后果 |
|---|---|
| 多租户与配额 | 一个训练作业占满 GPU，平台瘫痪 |
| 发布治理（版本 / 回滚 / 审批） | 换一个模型版本直接污染线上 |
| SLA 与告警 | 队列积压、推理超时无人知 |
| 审计与合规 | 谁读了哪份数据、谁发布了哪个模型查不到 |
| 成本可算 | 平台变成 GPU 与 Token 的无主成本黑洞 |
| 开放 API | 平台无法嵌入企业流程 |

### 1.3 建设顺序哲学

**纵切优先、骨架先行、逐个接入**：不按技术分层逐个建（那样 8 个半成品直到末期才能跑通一条链），而是让每个单元都交付"一条能跑起来、能演示、有数字的链路"；集成单元（07）先搭骨架，每完成一个单元就把它的成果接进来。

另一条前置纪律：**契约先定死、接口可替换**——各单元在验收时即隐含"可被 07 集成"的接口要求（暴露服务接口 + 健康检查 + 幂等 + 计量事件）。

## 2. 总体架构

### 2.1 架构图（结构视图）

```text
┌─ 系统入口（自研，07）───────────────────────────────────────────────────┐
│  统一控制台（链路状态 / 作业提交 / 版本 / 成本）· 开放 API                │
├─ 控制面（07 集成层：编排 + 治理）───────────────────────────────────────┤
│  统一编排（DAG）· 接口契约层 · 链路追踪 · 监控告警 · 成本归集 · 治理台账   │
└──────────────────────────────┬──────────────────────────────────────────┘
                               │ 管控与事件（数据不经过控制面）
┌─ 数据面（单元 01 / 02 / 03 / 05 / 06）─────────────────────────────────┐
│  01 语料加工     03 湖仓 + 向量      02 检索问答                        │
│  05 训练 / 推理  06 Agent 底座 + 可插拔运行时                          │
└──────────────────────────────┬──────────────────────────────────────────┘
                               │
┌─ 算力（单元 04）──────────────┴──────────────────────────────────────────┐
│  K8s（kind/minikube → 生产集群）· Volcano（队列 / 优先级 / gang）· GPU Operator │
└──────────────────────────────┬──────────────────────────────────────────┘
┌─ 存储 ──────────────────────────────────────────────────────────────────┐
│  对象存储（MinIO/S3）· Iceberg 湖 · 向量库（Milvus；兜底 faiss）· PG · Redis │
└─────────────────────────────────────────────────────────────────────────┘

横切：契约 · 可观测性（Prometheus / Grafana / Alertmanager / Loki / OTel）· 权限与审计 · 成本 · 多租户
```

两条读图要点：

1. **数据面与控制面分离**：控制面只做编排与治理（提交、追踪、计量、台账），**数据的读写路径不经过控制面**；控制面挂了不影响已提交作业的运行与推理服务。
2. **算力层是共享底座**：04 不是"一个 Demo"，而是 05 的训练、05 的推理、06 的沙箱所依赖的**同一套 K8s + GPU 调度**；它与 data-platform 共用同一集群、不同队列（边界见 §3 末）。

### 2.2 端到端数据流视图

一条业务流的完整旅程——"一份原始语料 + 一个业务问题"进去，答案 + 账 + 台账出来：

```text
原始语料（HTML/PDF/Markdown/JSONL/Wiki）+ 业务问题
    │ ① 加工（01）：解析 → 清洗 → 去重（MinHash）→ 分片 → embedding
    ▼
语料分片 + 向量（稳定 id，可断点续跑）
    │ ② 入库（03）：Iceberg 原子提交，语料表与向量表**同一次提交产生**
    ▼
湖仓（表 + 索引同 snapshotId，可时间旅行）
    │ ③ 检索（02）：混合检索（稠密 + BM25）→ Rerank → 答案 + 逐条引用来源
    │ ④ 微调（05①）：LoRA / QLoRA → MLflow 记录指标与产物
    ▼
模型 / LoRA 版本
    │ ⑤ 推理（05②）：vLLM + OpenAI 兼容协议 + 量化 + 并发压测
    ▼
     │ ⑥ Agent（06）：RuntimePort 契约 + 底座共享（沙箱 / 工具 / 审批）
     ▼
业务出口（答案 + 引用 + Token/GPU·秒/存储成本账 + 数据与模型台账）

横切：每一跳的 trace / 计量事件 / 审计记录 → 07 的监控、成本与治理台账
```

两条读图要点：

1. **索引与数据同源同版本是硬约束**——向量索引必须记录"基于哪个 snapshotId 构建"，查询前校验；这是"答案可复现"的物理前提（03 的核心验收）。
2. **每一步都可被单独演示与单独验收**——01 出加工报告、02 出评测数字、03 出快照链、05 出压测数字、06 出门禁结果、07 出端到端闭环；这正是"纵切优先"的落地形态。

### 2.3 控制面与数据面

```text
控制面负责"管控"：决定谁提交、能不能跑、跑了多少、是否合规、花了多少。
数据面负责"执行"：语料加工、入库、检索、训练、推理、Agent 运行。
```

控制面的职责细分（由 07 集成层承载，各单元在验收时即需暴露所需接口）：

| 中心 | 职责 | 承载 |
|---|---|---|
| 编排中心 | 数据流 DAG 编排、作业提交、重跑 | Airflow（07） |
| 契约中心 | 服务接口契约、适配器、版本管理 | 契约层（07） |
| 可观测中心 | 链路 trace、指标、日志、告警 | Prometheus + Grafana + Loki + Alertmanager |
| 成本中心 | 存储 GB·天 / GPU·秒 / tokens 三类口径归集 | 成本归集（04/05/07） |
| 治理中心 | 数据 / 模型版本台账、权限与审计 | 台账（07）+ K8s RBAC / Vault |
| 评测中心 | 语料质量抽检、检索评测、推理压测基线 | 各单元的评测集与报告 |

数据面各组件的执行职责：

| 组件 | 职责 |
|---|---|
| 01 语料加工流水线 | 解析 / 清洗 / 去重 / 分片 / embedding，产出可复现的语料与向量 |
| 03 湖仓 | 语料表与向量表的原子提交、快照与时间旅行、增量读、布局治理 |
| 02 检索问答 | 混合检索 + Rerank + 引用溯源 + 评测集回归 |
| 05 训练 / 推理 | LoRA/QLoRA 微调与产物记录；OpenAI 兼容推理、量化、压测、计量 |
| 06 Agent 底座 | 公共层（会话 / 工具 / 沙箱 / 审批 / 可观测）+ 可插拔运行时（四框架 + 自研内核） |
| 04 算力层 | 作业排队与调度、GPU 分配、资源账本、GPU·秒计量 |

### 2.4 隔离与多租户模型（形状先定死）

平台会被多个团队共用。多租户模型回答一个问题：不同团队在同一个平台里怎么互相看不见、互不干扰？**前期不做隔离功能，但隔离的"形状"必须在架构期定死**——它是建集群、建表、建集合时的物理边界，后补等于全量迁移。

| 层 | 隔离单位 | 含义 |
|---|---|---|
| Kubernetes | namespace + 调度队列 | 一个团队 = 一个 namespace + 一个队列（配额与优先级挂在这里） |
| 湖仓 | Iceberg namespace | 一个团队的语料表 / 向量表放一个命名空间 |
| 向量库 | database / collection 前缀 | 一个团队一套集合族 |
| 模型与适配器 | MLflow experiment + 模型注册分组 | 一个团队一套实验与版本 |
| 贯穿维度 | 租户 ID | 成本、审计、配额一律按租户归集 |

两条边界说明：

1. **本模型只管"隔离"，不管"配额"**——配额（队列 / GPU / 存储）随 04 的调度与账本设计落地，验收为 A24（账本不变量）与 A29（成本按租户归集）。
2. **落地时点**：形状在架构期定死（本节的五层对齐），功能随 04/07 逐步落地；生产档（§2.6）要求配额真正强制。

### 2.5 可用性与容灾口径（组件能力口径）

**原则**：平台的可用性与容灾**建立在所选组件的原生能力之上，不自研容灾机制**。本节只确认一件事：每个组件都具备高可用与数据保护能力——从单机（`kind` / Compose）演进到生产 K8s 时，**不需要更换任何组件**。

| 组件 | 高可用（服务不死） | 容灾与数据保护（数据不丢、可恢复） |
|---|---|---|
| Kubernetes / Volcano | 控制面多副本（生产）；单机 kind 无 HA（如实标注） | 作业级重试；队列与调度状态在 etcd，随集群备份 |
| Iceberg + MinIO | MinIO 分布式多节点（纠删码） | Iceberg 快照与时间旅行；MinIO 版本控制 / 对象锁 |
| 向量库（Milvus） | 多副本（K8s Operator） | Backup 至对象存储；索引可从表 + 快照重建 |
| PostgreSQL | 主备流复制 | PITR（WAL 归档） |
| Redis | 哨兵 / Cluster | AOF / RDB 持久化 |
| vLLM / 推理服务 | 无状态，可多副本 + 前置 LB | 请求级重试；模型权重存对象存储 |
| Airflow | 多 scheduler / worker（生产） | 元数据库存于平台 PG，随其备份 |
| 自研件（控制台 / 契约层 / 成本 / 台账） | 无状态化设计，多副本 | 状态只存 PG / Redis / 对象存储，继承上表能力 |

两条约定：

1. **自研组件一律无状态**——状态只存 PostgreSQL / Redis / 对象存储，可用性与容灾能力随之继承，自研件自身不需要容灾设计。
2. **无 GPU 环境的降级口径**——组件能力不变，降级的是**"真实数字"**：无卡时用 mock / 资源注入完成逻辑层验证，并如实标注哪些结论未在真实卡上验证（A27 / A53）；统一备份策略与恢复演练留到生产化阶段，不在本期设计。

### 2.6 规模假设（三档口径）

架构里的每个数字（显存、队列深度、分区数、成本单价）都挂在规模上。本节给出**假设值**，随各单元的 A 编号验收回填。

| 维度 | 逻辑层验证（无 GPU） | 单机集成（当前目标） | 生产（目标形态） |
|---|---|---|---|
| 语料 / 向量 | 小样本（≤1GB）+ 放大系数 | 10GB 级原始文本 | TB 级语料 · 亿级向量 |
| 算力 | mock / 资源注入 | `kind`/minikube 单机 + 单卡或 mock | 多节点 K8s + 多卡队列（配额强制） |
| 推理并发 | 1（mock 引擎） | 并发梯度 1 / 4 / 8 / 16 | 64+，多模型 + 多 LoRA 适配器 |
| 编排 | Makefile / 手动 | Compose + Airflow 单机 | K8s + Airflow 多 worker |
| 租户 | 单租户 | 单租户（隔离形状就位，§2.4） | 多租户 + 配额与审计强制 |
| 评测 | 冒烟 | 评测集 ≥30 题（含负例）+ 并发梯度 ≥3 档 | 回归集 + 定期回归 |

三条约定：

1. **档位是"建设期"不是"业务天花板"**——当前按单机集成档建设，生产档在引入真实集群时按需扩容（组件不换，只换部署形态）。
2. **跨档先复核**——显存与批大小（05）、队列与配额（04）、compaction 与分区布局（03）都按档取值，换档前先复核这三项。
3. **回填责任**——当前档的实测数字由各单元的 A 编号验收产出（A6 / A20 / A29 / A35 等）；生产档假设在真实集群接入时由使用方书面确认。

## 3. 能力域与选型

平台能力划分为八大能力域，自下而上：

```text
┌─────────────────────────────────────────────────────────────────┐
│ ⑧ 平台控制面与运营  编排 · 契约 · 可观测 · 成本 · 台账            │
├─────────────────────────────────────────────────────────────────┤
│ ⑦ Agent 与运行时    底座（公共层）· 可插拔运行时 · 沙箱与审批      │
├─────────────────────────────────────────────────────────────────┤
│ ⑥ 检索与知识库      混合检索 · Rerank · 引用溯源 · 评测           │
├─────────────────────────────────────────────────────────────────┤
│ ⑤ 推理与服务        OpenAI 兼容 · 量化 · LoRA Serving · 压测      │
├─────────────────────────────────────────────────────────────────┤
│ ④ 训练与微调        LoRA/QLoRA · SFT · 实验与产物管理             │
├─────────────────────────────────────────────────────────────────┤
│ ③ 算力与调度        K8s · GPU 队列 / 优先级 / 配额 · 资源账本      │
├─────────────────────────────────────────────────────────────────┤
│ ② 存储与版本        湖仓（Iceberg）· 向量索引与快照对齐            │
├─────────────────────────────────────────────────────────────────┤
│ ① 数据与语料        解析 · 清洗 · 去重 · 分片 · embedding          │
└─────────────────────────────────────────────────────────────────┘
        横切：契约 · 可观测性 · 权限与审计 · 成本 · 多租户
```

**选型标准**：① 事实标准或顶级开源项目（Apache / Linux 基金会 / 被大厂背书）；② 社区活跃、近半年有 release；③ **Python 原生优先**（本平台主栈）；④ 与 `data-platform` 的基础设施可共用（对象存储 / 湖表格式 / K8s / 可观测栈）；⑤ 单元开工前**锁定版本并记入兼容矩阵**（期内冻结，半年一个升级窗口）。

> 选型时效：本章的版本号与活跃度判断每半年复查一次，随 §7 验证清单的执行同步更新。

### ① 数据与语料

**职责**：把原始多源文本变成可训练、可入库、可追溯的高质量语料——这是平台的"进口"。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 解析与清洗 | BeautifulSoup / trafilatura（HTML）、PyMuPDF（PDF）、regex + unicodedata | 自研解析插件（按格式） | 生态最广的 Python 解析栈 |
| 去重 | **MinHash + LSH（手写）** | SimHash / 现成库 | 手写实现是本仓库纪律（对照 SimHash 有实测对比） |
| 分片与词元 | tiktoken / HF tokenizers + 重叠窗口策略 | —— | 事实标准 |
| embedding | sentence-transformers（本地）| OpenAI 兼容 embedding 接口 | 本地可跑优先，在线依赖必须标注 |
| 分布式清洗 | PySpark | pandas（小批量）| 10GB 级需要分布式；小样本模式验证逻辑 |
| 编排 | Airflow（见 ⑧）| Makefile + 脚本（阶段早期）| 阶段七统一接入编排 |

**企业级要求**：加工报告与元数据表**逐项对账**（原始 → 清洗 → 去重 → 入库，各步剔除原因分类计数）；分片 id 稳定（可断点续跑、不重复入库）；去重幂等（同输入两次运行结果一致）。

### ② 存储与版本

**职责**：让"语料 + 向量"具备 ACID、时间旅行与增量读能力——**湖仓是版本真相源**。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 湖表格式 | **Apache Iceberg**（与 data-platform 统一） | Delta Lake（仅作对照实验） | 开放表格式事实标准；两平台共用一套湖避免双湖 |
| 对象存储 | MinIO / S3 兼容 | 本地文件系统（起步） | S3 事实标准 |
| 向量索引 | Milvus（见 ⑥）或与表同目录的索引产物（faiss/hnswlib） | —— | 索引必须记录 `snapshotId` |
| 计算 | PySpark | DuckDB / Trino（小规模验证语义） | 按数据规模选择 |

**关键认知**：**"表数据 + 向量索引"由同一次提交产生**是平台的核心不变量——它把"数据版本"和"索引版本"合成一个概念，之后所有"答案可复现"的承诺都挂在它上面。

**企业级要求**：原子提交与快照链；按 `snapshotId` 复现历史；schema evolution 兼容演进、不兼容变更 fail-fast；增量读（只处理变化分区）；小文件治理（文件数 / 扫描字节数 / 合并收益三组数字）；分区重跑幂等。

### ③ 算力与调度

**职责**：K8s 提供"容器与节点抽象"，**GPU 调度策略、队列与配额、资源账本**是本域要补的部分。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 容器编排 | Kubernetes（kind/minikube 单机起步 → 生产集群） | —— | 事实标准 |
| 批调度 | **Volcano**（队列 / 优先级 / gang scheduling） | K8s 原生调度 + 自研策略 | CNCF 项目；**必须做一次与原生调度的对比实验**（验收项） |
| GPU 抽象 | NVIDIA GPU Operator + DCGM exporter | `nvidia-device-plugin` mock（无卡时的逻辑验证） | 事实标准 |
| 作业形态 | `Job` / `PyTorchJob`；必要时自研 CRD | 直接 `kubectl apply` | 讲清"期望状态 + 控制器循环" |
| 成本计量 | GPU·秒 → 租户 / 项目（showback 或 chargeback 至少一种） | —— | —— |

**企业级要求**：资源账本不变量 `已分配 + 空闲 == 总量`；超额申请被拒且原因可读；优先级真的生效（有两次调度决策对比）；状态机与事件可查。

### ④ 训练与微调

**职责**：把"一次微调"做成可复现、可比较、产物可追溯的工程动作。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 微调方法 | **LoRA / QLoRA（PEFT）** | 全参 SFT（小模型） | 消费级显存可跑，事实标准 |
| 分布式训练 | DeepSpeed | 单卡 + 梯度累积 | 规模触发 |
| 实验与产物 | **MLflow**（指标 / 参数 / 产物 / 模型版本登记） | 自研台账表 | 事实标准 |

**企业级要求**：每次微调可复现（数据版本 + 超参 + 随机种子）；产物登记进台账（哪个模型由哪次训练产出）；与 ③ 的 GPU·秒计量对账。

### ⑤ 推理与服务

**职责**：把模型变成**接口兼容、可承载多模型、有真实压测数字、能算单位成本**的服务。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 推理引擎 | **vLLM**（continuous batching） | Triton Inference Server（多模型 / 非 LLM） | 事实标准；**选型理由要落文档** |
| 适配器服务 | LoRA Serving（基座 + 适配器热挂） | 每适配器独立进程 | 显存收益显著 |
| 量化 | GPTQ / AWQ 或 bitsandbytes（至少一种） | —— | 必须给出"量化前后"三组对比 |
| 服务协议 | **OpenAI 兼容子集**（`/v1/chat/completions`）+ 流式 SSE + 错误码 | 自研协议 | 换 `base_url` 即用是硬验收 |
| 压测 | locust / k6（并发梯度 1/4/8/16） | 自研脚本 | 必须给出 TTFT / TPOT / tokens/s / P95 |

**企业级要求**：限流与超时返回可预期错误码（不是挂死）；Token 计量与引擎侧计数可对账；无 GPU 时给出降级验证路径并**如实标注哪些数字未在真实卡上验证**。

### ⑥ 检索与知识库

**职责**：能回答、能溯源、能评测——核心不是"接一个大模型"，而是**检索质量 + 引用可溯源 + 端到端评测**。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 检索编排框架 | **LangChain**（只用其文档加载 / 检索链能力，不依赖 agent 能力） | LlamaIndex | 生态最广；不引入其 Agent 全家桶 |
| 向量库 | **Milvus** | Qdrant；**兜底** faiss / numpy 暴力检索 | 事实标准；兜底保证无服务时也能验证语义 |
| 检索策略 | **混合检索（稠密 + BM25）+ Rerank**（交叉编码器 / bge-reranker） | 纯向量检索（对照基线） | 必须有对比实测数字 |
| 服务接口 | FastAPI（`/ask`、`/documents`、`/healthz`）+ 结构化日志 | —— | —— |
| 评测 | 自建问题集（≥30 题，含"库中无依据"负例）+ Recall@k / MRR + 答案要点覆盖率 | RAGAS（参考） | 无评测不上线 |

**企业级要求**：答案逐条给出可点开的引用（`doc_id + chunk_id + 原文片段`）；负例必须回答"无依据"，**编造率为 0**；每次回答写全链 trace，错误回答可归因。

### ⑦ Agent 与运行时

**职责**：统一底座（接入 / 控制面 / AI 基础设施建一次）+ 可插拔运行时（四框架 + 自研内核）——让 Agent 从"孵化"到"归巢"全程有底座可依。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 平台底座（公共层） | PostgreSQL / Redis / Milvus·pgvector / MinIO / **Vault** / **模型网关** / **MCP 网关** / Prometheus·Grafana·Loki / 沙箱（E2B·OCI） | —— | 与平台其余部分共用，**只建一次**；模型网关与 Vault 是全仓库唯一实例 |
| 运行时契约 | **RuntimePort**（发布物化 / 事件流 / 审批挂起 / 隔离翻译） | —— | 平台自研契约，是本域的差异化核心 |
| 框架适配 | AgentScope、LangChain/LangGraph、OpenAI Codex、DeepSeek Harness | 按需增补 | 四框架接入证明契约可插拔 |
| 自研内核 | **agent-core（Rust + tokio，单二进制，HTTP/gRPC）** | —— | 不依赖任何框架独立验证循环设计 |
| 教学轨道 | tutorials（Python + Rust，s01–s20 双轨对齐） | —— | 沉淀方法论，不属平台运行时 |

**企业级要求**：同一底座至少服务 **2 种运行时**；AI 基础设施只建一次、全部运行时共享；多运行时共存时有**发布期能力校验**与统一可观测审计。

### ⑧ 平台控制面与运营

**职责**：把前七个单元"串成一个平台"，并提供入口。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 统一编排 | **Airflow**（DAG 编排数据流与集成任务） | 自研调度（不选）/ Dagster·Prefect | 生态最广；**与 data-platform 的 DolphinScheduler 分工见本节末** |
| 统一入口 | **自研控制台 + 开放 API**（链路状态 / 作业提交 / 版本 / 成本） | 各组件的自带 UI（仅运维面） | 入口是用户契约，必须自建 |
| 接口契约层 | **自研适配器 + 契约测试**（服务接口先定死） | —— | 组件可替换性靠它 |
| 链路追踪 | OpenTelemetry + Jaeger/Tempo（跨组件 trace） | Langfuse（LLM 侧补充） | 断链要能定位到具体组件 |
| 指标与告警 | **Prometheus + Grafana + Alertmanager** | —— | 三类面板 + 至少一条告警真触发过 |
| 日志 | Loki | ELK | —— |
| 成本归集 | 自研薄层（三类口径统一） | 云账单分析 | 见 §5.3 |
| 治理台账 | 自研薄层（数据 / 模型版本 + 权限审计） | MLflow + 自研混合 | 见 §4 |

**与 data-platform 的分工（必须写死，避免两套平台长成两套）**：

| 重叠能力 | 归属 |
|---|---|
| 对象存储 / 湖表格式（Iceberg） | **data-platform 拥有**，AI 平台消费同一套 |
| K8s 集群与 GPU 队列 | 共用集群；**GPU/训练/推理队列归 AI 平台**（04），数据任务队列归 data-platform |
| 编排 | **数据任务归 DolphinScheduler（data-platform），模型与集成任务归 Airflow（AI 平台）**；两者通过 API 互相触发，不互相替代 |
| 向量库 / 推理服务 / Agent | **AI 平台拥有**；data-platform 的 P5 若需推理与向量，复用本平台而非自建 |
| 模型出口 / LLM Gateway | **AI 平台拥有**（06 底座的模型网关，与 MCP 网关 / 沙箱 / 可观测一起只建一次）；**data-platform P5 作为调用方**——v2 已定稿 |
| 凭据管理 | **Vault = 唯一凭据源**（按平台分 path/policy）；K8s Secret 仅作**注入通道**；Nacos 只放非密钥配置——v2 已定稿（data-platform P1 以 K8s Secret 过渡，随 06 迁移） |

### 明确不选（避坑）

| 不选 | 原因 |
|---|---|
| 自研向量库 / 检索引擎 | Milvus + faiss 已足够；自研纯投入无差异 |

| 无评测的 RAG 上线 | 与"无评测集不上线"同级铁律 |

## 4. 自研边界

**入口（系统的脸面与用户契约，必须自建）**

| 自研块 | 为什么必须自研 | 复杂度 |
|---|---|---|
| **统一控制台 + 开放 API** | 组件各自 UI 口径不一；用户只应面对一个入口；开放 API 的鉴权 / 审计 / 版本契约必须自己掌握 | 中高（由 07 承载，随单元接入逐步扩展） |

**胶水（开源之间缺失的粘合层，必须薄）**

| 自研块 | 为什么必须自研 | 承载单元 | 复杂度 |
|---|---|---|---|
| **统一编排** | 六个单元各自能跑，但"数据流怎么串、失败怎么重跑"没有开源件能替你决定 | 07 | 中 |
| **接口契约层（适配器）** | 各单元接口形态不一；契约先定死才能"换组件不改他人代码" | 07 | 中 |
| **链路追踪** | 跨组件断链定位（一次问答经过哪些组件、各段耗时）是平台能力的证明 | 07 | 低–中 |
| **监控告警** | 三类面板 + 告警真触发；组件自带指标不足以回答"链路健康" | 04 / 05 / 07 | 低–中 |
| **成本归集** | 三类口径（存储 GB·天 / GPU·秒 / tokens）统一计量与归集，开源里没有现成的一套 | 04 / 05 / 07 | 中 |
| **治理台账** | "谁用了哪份数据、哪个模型由哪次训练产出、谁发布了它"必须自己记 | 07 | 中 |

**内核（差异化能力，必须自研）**

| 自研块 | 为什么必须自研 | 承载单元 | 复杂度 |
|---|---|---|---|
| **RuntimePort 契约 + agent-core（Rust + tokio）** | Agent 运行时的可插拔与隔离是平台差异化能力；框架适配层与自研内核实证同一契约（至少两个运行时） | 06 | 高（本平台最大单项自研） |

**底座（AI 基础设施，只建一次）**

| 自研块 | 为什么必须自研 | 承载单元 | 复杂度 |
|---|---|---|---|
| **模型网关（LLM Gateway）** | 所有运行时与应用的模型调用必须经同一出口：路由 / 鉴权 / **Token 计量** / 审计；全仓库只应有一处（v2 定稿：data-platform P5 作为调用方） | 06 | 中 |
| **MCP 网关 + 工具注册** | Agent 工具调用的统一入口与审计点 | 06 | 中 |
| **沙箱与隔离**（E2B / OCI） | 运行不可信代码的隔离面，安全边界必须自建 | 06 | 中高 |
| **凭据（Vault）+ 共享可观测** | Vault 为**唯一凭据源**（按平台分 path/policy）；Prometheus / Grafana / Loki 全平台共享 | 06 / 07 | 低–中 |

**后置自研件**（规模触发才启用，不计入常态边界；启用前需评审）：

| 自研块 | 触发条件 |
|---|---|
| 合成数据生成平台 | 训练数据不足、需要定向增广时 |
| 特征 / 模型商店 | 多团队复用同一批特征与模型时 |
| AI 治理引擎（自动化合规检查） | 合规审计要求规则化、自动化时 |

**其余一律不自研。**

## 5. 契约与规范

契约先定死是平台的地基——七个单元能被"集成"而不是"堆在一起"，靠的就是这一章。

### 5.1 服务接口契约

| 项 | 规范 |
|---|---|
| 传输形态 | HTTP/JSON 为主；批处理与工具链允许 CLI，但**必须同时提供 HTTP 入口**（否则 07 无法编排） |
| 推理协议 | 实现 **OpenAI 兼容子集**（`/v1/chat/completions` 等）——同一份官方 SDK 只改 `base_url` 即可调用 |
| 各单元最小接口 | 01/03：作业触发 + 状态查询；02：`/ask`、`/documents`、`/healthz`；05：OpenAI 兼容 + `/metrics`；06：RuntimePort 发布 / 事件流 / 审批挂起 |
| 健康检查 | 每个单元**必须**暴露 `/healthz`（07 的一条命令拉起与健康检查依赖它） |
| 错误语义 | 鉴权失败 / 限流 / 超时 / 参数错误各返回稳定错误码，不允许"挂死"或裸 500 |
| 版本 | 破坏性变更升版本，旧版本在一个迁移期内仍可用；接口变更走契约层适配器，不改调用方 |

### 5.2 资产契约

| 资产 | 契约 |
|---|---|
| 语料分片 | 稳定 id（`doc_id + 序号 + 内容哈希`）；重复运行得到相同分片 id 与相同向量 |
| 向量索引 | **必须记录"基于哪个 snapshotId 构建"**，查询前校验；不一致即拦下 |
| 表数据 | 语料表与向量表由**同一次提交**产生（同版本）；重跑用分区覆盖保证幂等 |
| 模型 / 适配器 | 每次微调登记：数据版本 + 超参 + 种子 + 指标 + 产物路径（MLflow） |
| 台账 | 数据 → 作业 → 模型 → 发布 四类关系可双向查询（谁用了哪份数据 / 哪个模型由哪次训练产出 / 谁发布了它） |

### 5.3 成本口径（三类，先决策再实现）

| 口径 | 计量方式 | 归集维度 |
|---|---|---|
| 存储 | GB·天 | 租户 / 数据集 |
| 算力 | GPU·秒（按作业实际占用） | 租户 / 项目 / 作业 |
| 推理 | prompt tokens + completion tokens（分别计价） | 租户 / API Key / 模型 |

**两条前置决策**（07 明确指出，必须先定后实现）：① **空转与排队是否计费**（排队不计、空转按占用计——需显式写死）；② 重试是否重复计费（按实际占用计，但要在报表中可区分）。

### 5.4 命名与目录规范

| 对象 | 规范 |
|---|---|
| 单元目录 | `NN-<短名>`（`01-text-corpus-pipeline` … `07-ai-platform`），编号即建设顺序 |
| 单元 README | 元信息头 3 行（状态 / 所属平台与单元 / 对应文档）+ 骨架段落，遵循 `engineering-docs` skill 的 L4 模板 |
| 平台级文档 | 中文文件名（本文件即 L2 + L3 合体形态） |
| 数据集 / 模型 / 索引 | `{tenant}_{domain}_{name}_{version}`；向量集合名与表名对齐 |
| Git | 平台团队的资产（契约、适配器、编排 DAG、部署清单）Git 版本化；大数据集与模型权重不进 Git |

### 5.5 编排与集成契约

| 规则 | 要求 |
|---|---|
| 可被 07 集成 | 每个单元交付时即需：容器化（Dockerfile / compose 或 Helm）+ `/healthz` + 幂等触发 + 计量事件 |
| DAG 输入输出 | 每个作业显式声明输入与输出资产（数据 / 模型 / 索引），供 07 组装与台账登记 |
| 幂等重跑 | 同一作业重跑两次结果一致；重跑前必须能定位上次的输入版本（快照 id / 数据版本） |
| 替换验证 | 每个单元至少验证一次"换实现不改他人代码"（07 的验收项，也是契约有效性的证明） |

## 6. 实施路线（单元 01–07）

七个单元 = 七个学习阶段 = 七条纵切链路。每个单元给出：**目标 → 装什么 → 做什么 → 交付物 → 验收（A 编号）→ 不做**。风险统一收 §9。

### 01 · AI 数据基础（3–4 周）

**目标**：在 10GB 级原始文本上跑通「解析 → 清洗 → 去重 → 分片 → embedding → 落库」全链，任何一步产出可按 id 复现。

**装什么**：Python 3.13 + PySpark（小样本模式可跑）+ SQLite/PostgreSQL（元数据表）+ MinHash/LSH（手写）+ tokenizer + embedding（本地模型或兼容接口）。

**做什么**：解析器分发（HTML/PDF/Markdown/JSONL/Wiki）；清洗规则可配置可回放；文档级近重复 + 分片级去重（阈值与保留规则入档）；token 分片 + 批量 embedding（可断点续跑）；加工报告与元数据表逐项对账。

**交付物**：语料分片 + 向量 + 加工报告（四类计数与剔除原因）+ 可复现命令清单。

**验收**：A1–A7。

**不做**：不做模型训练、不做检索服务、不做在线接口（那是 02/05 的事）。

### 02 · RAG 数据平台（3–4 周）

**目标**：对固定评测问题集能给出答案并逐条给出可点开的引用；库中无依据时明确回答"无依据"。

**装什么**：LangChain（仅检索链）+ Milvus 或 Qdrant（不可用时 faiss 兜底）+ 混合检索（稠密 + BM25）+ Rerank + FastAPI + OpenAI 兼容 LLM。

**做什么**：知识库装载（按文档 / 分片可追溯 id）；`/ask` 与服务接口；混合检索 + Rerank 消融对照；评测集（≥30 题，含负例）与指标；全链 trace。

**交付物**：问答服务（`/ask` `/documents` `/healthz`）+ 评测报告（检索命中率 / 答案要点覆盖率 / 编造率）+ 消融对比数字。

**验收**：A8–A14。

**不做**：不做微调（05）、不做 Agent、不做多模态检索。

### 03 · 向量化数据湖（2–3 周）

**目标**：同一份语料与其向量在湖仓里由**同一次提交**产生；支持 schema evolution；可按 snapshotId 复现历史数据与索引。

**装什么**：Iceberg（与 data-platform 统一）+ MinIO/S3（目标形态）+ PySpark 或 DuckDB + 向量索引产物（faiss/hnswlib）或 Milvus 外部索引。

**做什么**：语料表与向量表的原子提交与快照链；按 snapshotId 复现；schema evolution（加列通过、删列改类型 fail-fast）；快照间增量分区计算与增量处理；索引登记 snapshotId + 查询前校验；小文件检测与 compaction（三组数字）；分区重跑幂等。

**交付物**：湖仓表结构 + 索引与快照对齐机制 + compaction 实测数字 + 复现命令。

**验收**：A15–A22。

**不做**：不做实时流式入湖（data-platform 的领域）、不做多租户隔离（后续单元）。

### 04 · Kubernetes + GPU 调度（4–6 周）

**目标**：提交 N 个作业（含超额、优先级不同）后队列按策略出队、作业获得 GPU 并跑完，资源账本始终满足 `已分配 + 空闲 == 总量`，每个作业的 GPU·秒可归集到租户。

**装什么**：Docker + kind/minikube + Helm + Volcano（或原生调度对照）+ GPU Operator / DCGM exporter（无卡时 mock）+ Prometheus + Grafana。

**做什么**：作业提交与队列（`submit / status / queue / cost`）；配额与优先级策略（两次调度决策对比）；作业状态机与事件；三块 Grafana 面板与账本同源；GPU·秒计量与成本归集；无 GPU 环境的逻辑验证路径。

**交付物**：调度 Demo（`make up / submit / status / cost / make down`）+ 调度策略对比记录 + 资源账本与成本表 + 无 GPU 验证说明。

**验收**：A23–A30。

**不做**：不做多集群联邦调度、不做训练框架本身（05）、不做计费系统（只做 showback/chargeback 一种口径）。

### 05 · 训练与推理平台（4–6 周）

**目标**：① 完成一次可复现的 LoRA/QLoRA 微调并把产物登记进台账；② 推理服务接口兼容 OpenAI，在多并发压测下给出 TTFT / TPOT / tokens/s / P95 四个数字并能说明瓶颈。

**装什么**：PEFT（LoRA/QLoRA）+ MLflow + vLLM（或 Triton）+ 量化工具（GPTQ/AWQ/bitsandbytes 至少一种）+ FastAPI 服务层 + locust/k6 + Prometheus。

**做什么**：小模型 / 小数据集微调（数据版本 + 超参 + 种子入档）；LoRA Serving（基座 + 适配器热挂）；量化前后三组对比（显存 / 吞吐 / 质量抽样）；OpenAI 兼容子集 + 流式 SSE + 令牌校验 + 限流；并发梯度压测与瓶颈归因；Token 计量与 GPU·秒对账。

**交付物**：微调产物与 MLflow 记录 + OpenAI 兼容推理服务 + 压测报告（并发梯度四指标）+ 量化对比表 + 成本对账表。

**验收**：A31–A37。

**不做**：不做推理引擎内核优化、不做预训练、不做多机多卡并行（规模触发）。

### 06 · Agent 平台（6–8 周，Part 1 已完成）

**目标**：同一底座上，**至少两个运行时**（框架适配器 + 自研 agent-core）通过同一 RuntimePort 契约完成 Agent 的发布与运行。

**装什么**：平台底座（PostgreSQL / Redis / Milvus·pgvector / MinIO / Vault / **模型网关** / **MCP 网关** / Prometheus·Grafana·Loki / 沙箱 E2B·OCI）+ 四框架适配（AgentScope / LangChain·LangGraph / Codex / DeepSeek Harness）+ agent-core（Rust + tokio）。

**做什么**：
- **Part 1（沉淀，✅ 已完成 2026-09）**：research 方法论、tutorials 双轨（Python + Rust，s01–s20）、frameworks 四框架三件套 + agent-core 设计存档。
- **Part 2（实证，⏳ 当前）**：A 门禁（方案评审定稿、选定首个落地对象）→ agent-core mock-LLM 最小闭环主循环（B-1）→ agentscope 适配器真接 RuntimePort（B-2，M0 门禁全过）。
- **Part 3（规模化，⏳）**：第二个运行时接入、AI 基础设施全运行时共享、多运行时共存 + 发布期能力校验 + 统一可观测审计。

**交付物**：RuntimePort 契约 + agent-core 二进制 + 至少两个运行时适配器 + 底座部署清单 + 门禁记录。

**验收**：A38–A45（A38–A40 已达成）。

**不做**：不做通用工作流引擎、不做模型训练、不做每个框架的全功能覆盖（只覆盖能力矩阵点亮的行）。

### 07 · AI 数据中心平台整合（4–8 周）

**目标**：一条命令在干净环境拉起全部已接入组件，跑通「投入新语料 → 问答质量更新」闭环，并在同一屏看到链路健康、资源用量与本次闭环成本。

**装什么**：**不引入新技术栈**——把前六个单元的交付物容器化后统一编排（Airflow + compose/Helm + 监控告警 + 台账）。

**做什么**：平台骨架（控制台 + 编排 + 监控）；逐单元接入（接口 + 健康检查 + 计量口径）；端到端闭环与前后对比；跨组件 trace；三类面板 + 一条告警真触发；成本归集；治理台账；组件可替换性验证。

**交付物**：一条命令拉起 + 端到端闭环记录（前后对比）+ trace 样例 + Grafana 面板 + 告警演练记录 + 成本表 + 台账查询 + 可替换性验证记录。

**验收**：A46–A53。

**不做**：不做真实 GPU 集群的运维（无卡部分如实标注 + 给接入路线）、不做多云、不做商业计费。

| 3 | **单机内存打穿**（07 一条命令拉起全部组件） | 分批起 + 轻量替代件；监控面板先看内存与队列；给最小可用组合（骨架 + 单链） |
| 4 | **成本口径未定就实现**（空转与重试是否计费） | 实现前先写死两条前置决策（§5.3），否则三类口径对不上账 |
| 5 | **契约漂移**（各单元自造接口，07 集成时才发现不通） | 契约先定死（§5）+ 每单元的"可被 07 集成"要求（健康检查 / 幂等 / 计量事件）+ A52 可替换性验证 |
| 6 | **06 的 Part 1 越做越重、迟迟不实证** | A 门禁作为硬门禁：评审定稿 + 选定首个落地对象后才进 Part 2；Part 1 只做沉淀不做扩张 |
| 7 | **与 data-platform 重叠导致两套平台**（湖仓 / 向量 / GPU / 推理 / 模型出口） | §3 的分工表写死归属；重叠处先定"谁拥有"，未定前两边都不新增对方实现 |
| 8 | **RAG 质量自说自话**（没有评测就上线） | 评测集门槛（≥30 题含负例）+ 编造率为 0 + 消融对照；无评测不上线 |
| 9 | **靠"接一个模型"冒充平台能力** | 每个单元都必须有**自己的**实测数字（报告 / 快照链 / 账本 / 压测 / 门禁），文档不算交付 |
| 10 | **版本漂移**（多个组件的长期 OPEX） | 单元开工前锁定版本 + 兼容矩阵；半年一个升级窗口，升级即回归对应 A 编号 |

### 关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 编排 | **AI 平台用 Airflow；数据任务留给 data-platform 的 DolphinScheduler** | Python 原生 + ML 生态（训练/评测管道）；两个平台各用一套会分裂，故按"数据任务 vs 模型任务"划界并允许互相触发 |
| 向量库 | **Milvus**（faiss 兜底） | 事实标准 + 本地可兜底；Qdrant 作为备选保留但不并行维护 |
| 湖表格式 | **Iceberg（与 data-platform 统一）** | 两平台一套湖，避免双湖与双份血缘 |
| GPU 调度 | **Volcano**（与原生调度做一次对比） | 队列 / 优先级 / gang scheduling 是真实需求；对比实验保留为验收项 |
| 推理引擎 | **vLLM** | continuous batching 事实标准；Triton 仅作为多模型/非 LLM 的备选 |
| Agent 路线 | **底座 + RuntimePort + 四框架适配 + 自研内核** | 不做框架全家桶，用适配证明契约、用内核证明设计 |
| GPU 来源 | 本地卡优先；无卡按逻辑层推进 | 真实数字可以等，链路与契约不能等 |
