## 1. 项目定位：从零实现 Agent Harness

这个项目不是一个“已经封装好的 Agent SDK”，而是一套教学型 Agent Harness 原型。它从最小的 LLM 工具调用循环开始，每一章只引入一个新的运行时机制，最终在 s20 把所有机制组合起来。

项目的核心判断是：

```text
Agent Product = Model + Harness
```

- **Model** 负责理解任务、制定下一步动作、选择工具以及解释结果。
- **Harness** 负责把模型的决定变成真实动作，并把真实世界的结果再次交给模型。

因此，模型本身没有改变，真正逐步增加的是模型周围的运行时能力：

```text
工具 → 权限 → Hooks → Todo → Subagent → Skills
→ Context Compact → Memory → 动态 Prompt → Error Recovery
→ Task → Background → Cron → Teams → Protocols
→ Autonomous Agents → Worktree → MCP → 综合 Harness
```

## 2. 永远不变的核心：Agent Loop

所有章节都围绕同一个循环展开：

```text
┌──────────────┐
│ 用户输入     │
└──────┬───────┘
       ↓
┌──────────────┐
│ LLM 推理     │ ← system prompt + message history + tool schemas
└──────┬───────┘
       │
       ├── 没有 tool_use ──→ 输出最终答案，结束本轮
       │
       └── 有 tool_use
              ↓
       ┌──────────────┐
       │ Hook/权限    │
       └──────┬───────┘
              ↓
       ┌──────────────┐
       │ 执行工具     │
       └──────┬───────┘
              ↓
       ┌──────────────┐
       │ tool_result  │
       │ 回灌 history  │
       └──────┬───────┘
              └────────→ 再次调用 LLM
```

最小形式可以概括为：

```python
while True:
    response = client.messages.create(
        model=MODEL,
        system=SYSTEM,
        messages=messages,
        tools=TOOLS,
        max_tokens=8000,
    )

    messages.append({
        "role": "assistant",
        "content": response.content,
    })

    if response.stop_reason != "tool_use":
        return

    results = []
    for block in response.content:
        if block.type == "tool_use":
            output = execute_tool(block.name, block.input)
            results.append({
                "type": "tool_result",
                "tool_use_id": block.id,
                "content": output,
            })

    messages.append({
        "role": "user",
        "content": results,
    })
```

这里最重要的不是 `while True` 本身，而是消息协议：

1. 模型的 assistant 消息中出现 `tool_use`。
2. Harness 必须执行对应工具。
3. Harness 必须用相同的 `tool_use_id` 生成 `tool_result`。
4. `tool_result` 必须作为下一条 user 消息回灌。
5. 模型根据结果决定下一步，或者结束。

后续章节虽然加入了权限、压缩、后台、团队等大量代码，但并没有改变这条主线。变化的是“调用 LLM 前后做什么”和“工具执行前后做什么”。

## 3. s01–s20 总览

| 阶段 | 章节 | 新增机制 | 解决的问题 |
|---|---|---|---|
| 基础循环 | s01 | Agent Loop | 模型只能输出命令，不能真正执行并继续推理 |
| 工具系统 | s02 | 多工具与文件工具 | 只有 Bash 不安全、不稳定、不易表达 |
| 安全控制 | s03 | Permission | 工具可能执行危险操作 |
| 生命周期 | s04 | Hooks | 权限、日志、摘要等逻辑会污染主循环 |
| 规划 | s05 | TodoWrite | Agent 容易忘记目标、漂移或重复工作 |
| 上下文隔离 | s06 | Subagent | 大任务需要独立上下文和专门角色 |
| 知识按需加载 | s07 | Skills | 所有知识一次性塞入 prompt 会浪费上下文 |
| 上下文治理 | s08 | Context Compact | 长对话和大工具输出会超过上下文窗口 |
| 跨会话知识 | s09 | Memory | 每次会话都从零开始，无法积累偏好和事实 |
| Prompt 工程 | s10 | Dynamic System Prompt | system prompt 需要随运行时状态变化 |
| 稳定性 | s11 | Error Recovery | 限流、过载、截断、超长会导致 Agent 直接崩溃 |
| 持久任务 | s12 | Task System | Todo 只适合当前会话，无法表达持久依赖图 |
| 并发执行 | s13 | Background Tasks | 慢命令会阻塞 Agent 主循环 |
| 定时触发 | s14 | Cron Scheduler | Agent 只能被动等待用户输入 |
| 多 Agent | s15 | Agent Teams | 单个 Agent 无法高效并行处理大任务 |
| 协作协议 | s16 | Team Protocols | 队友退出、计划审批、请求响应缺少可靠协议 |
| 自组织 | s17 | Autonomous Agents | 队友需要有人手动分配任务，无法自主工作 |
| 文件隔离 | s18 | Worktree Isolation | 多个 Agent 修改同一目录会互相覆盖 |
| 外部插件 | s19 | MCP Plugin | 工具能力需要从外部服务器动态接入 |
| 综合实现 | s20 | Comprehensive Harness | 把全部机制放回同一个 Agent Loop |

# 4. 逐章详解

## s01：Agent Loop —— 一个循环让模型持续行动

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s01_agent_loop/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s01_agent_loop/src/main.rs`

### 4.1 实现了什么

s01 实现了最小可运行 Agent：

- 接收用户输入；
- 把用户输入、system prompt 和 Bash 工具定义发送给 Anthropic-compatible API；
- 识别模型返回的 `tool_use`；
- 执行模型请求的 Shell 命令；
- 把命令输出包装为 `tool_result`；
- 继续调用模型，直到模型不再请求工具。

### 4.2 如何实现

Python 版本主要有三个部分：

1. `run_bash(command)` 使用 subprocess 执行命令，并捕获 stdout/stderr。
2. `agent_loop(messages)` 维护消息历史，围绕 `client.messages.create()` 运行循环。
3. `main()` 提供交互式 REPL，把每次用户输入追加到 history。

核心判断是 `response.stop_reason == "tool_use"`。如果模型没有请求工具，就认为本轮完成。

一个 assistant 回复可能同时包含文字和多个 `tool_use` block，因此代码会遍历全部 block，并为每个 tool_use 生成对应的 tool_result。

### 4.3 这一章的关键学习点

- LLM 输出不是执行结果，必须有 Harness 执行工具。
- Agent 的“自主性”来自“执行结果再次回到模型”，而不是一次性生成一大段文本。
- `tool_use_id` 是工具调用与结果之间的关联键。
- Agent Loop 的内核非常小，复杂性会出现在周围的工程机制中。

### 4.4 局限

s01 直接执行模型生成的 Shell 命令，几乎没有安全边界。因此它只适合临时目录或教学环境，不能直接用于生产环境。s02 引入更结构化的工具，s03 再引入权限系统。

## s02：Tool Use —— 从一个 Bash 变成工具注册表

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s02_tool_use/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s02_tool_use/src/main.rs`

### 4.5 实现了什么

s02 把工具从单一 Bash 扩展成显式工具集合：

- `bash`
- `read_file`
- `write_file`
- `edit_file`
- `glob`

这使模型可以用结构化参数表达意图，而不是所有事情都拼接成 Shell 字符串。

### 4.6 如何实现

Python 版本定义了对应的处理函数：

- `run_bash(command)`
- `run_read(path, limit=None)`
- `run_write(path, content)`
- `run_edit(path, old_text, new_text)`
- `run_glob(pattern)`

然后用 `TOOL_HANDLERS` 做名称到函数的映射：

```python
TOOL_HANDLERS = {
    "bash": run_bash,
    "read_file": run_read,
    "write_file": run_write,
    "edit_file": run_edit,
    "glob": run_glob,
}
```

主循环不再写死“如果是 Bash 就调用 `run_bash`”，而是按 `block.name` 查表：

```python
handler = TOOL_HANDLERS.get(block.name)
output = handler(**block.input)
```

文件工具统一经过 `safe_path()`：

1. 把相对路径解释为 workspace 下的路径；
2. 解析真实路径；
3. 检查结果是否仍位于 workspace 内；
4. 越界就拒绝。

### 4.7 这一章的关键学习点

- 工具定义是模型可见的 schema，工具 handler 是 Harness 内部的实现。
- “模型能看到什么工具”和“程序实际注册了什么 handler”必须保持一致。
- 工具注册表是后续权限、Hooks、MCP 动态工具池的基础。
- 路径安全要在工具层统一处理，不能只依赖 system prompt 提醒模型。

## s03：Permission —— 在工具真正执行前增加安全闸门

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s03_permission/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s03_permission/src/main.rs`

### 4.8 实现了什么

s03 为工具调用增加权限判断，形成三层防护：

1. **deny list**：明确禁止的命令或操作直接拒绝。
2. **规则判断**：根据工具名和参数判断是否需要确认。
3. **用户确认**：危险操作交给用户做最终决定。

典型需要确认的操作包括删除文件、覆盖写入、修改代码、执行高风险 Shell 命令等。

### 4.9 如何实现

Python 版本的关键函数：

- `check_deny_list(command)`：检查命令是否命中禁止规则。
- `check_rules(tool_name, args)`：基于工具与参数判断风险。
- `ask_user(tool_name, args, reason)`：交互式询问用户。
- `check_permission(block)`：把以上逻辑串起来。

主循环在调用 handler 之前先检查：

```text
tool_use
  ↓
check_permission
  ├─ denied → 生成错误 tool_result
  ├─ ask user → 用户拒绝 → 生成拒绝 tool_result
  └─ allowed → 执行 handler
```

权限拒绝不会让 Agent Loop 崩溃，而是作为普通 `tool_result` 回灌模型，例如：

```text
Permission denied: user rejected write_file
```

模型可以据此调整策略，而不是陷入“程序异常退出”。

### 4.10 这一章的关键学习点

- 权限是工具执行管线的一部分，而不是 system prompt 中的一句提示。
- 拒绝也要结构化地反馈给模型。
- deny、规则和人工确认是不同层次，不能只依赖其中一种。
- 工具越多，集中式权限入口越重要。

## s04：Hooks —— 把横切逻辑从主循环中抽出来

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s04_hooks/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s04_hooks/src/main.rs`

### 4.11 实现了什么

s04 引入生命周期 Hooks，把权限、日志、大输出处理、上下文注入和停止摘要等逻辑从 Agent Loop 中拆出去。

Python 版本支持的主要事件：

- `UserPromptSubmit`
- `PreToolUse`
- `PostToolUse`
- `Stop`

### 4.12 如何实现

注册与触发机制由两个函数组成：

```python
def register_hook(event, callback): ...
def trigger_hooks(event, *args): ...
```

典型 hook：

- `permission_hook(block)`：在 PreToolUse 阶段执行权限检查。
- `log_hook(block)`：记录工具调用。
- `large_output_hook(block, output)`：检测超大工具结果。
- `context_inject_hook(query)`：在用户输入进入模型前注入额外上下文。
- `summary_hook(messages)`：Agent 停止时生成摘要或统计信息。

执行流程由原来的：

```text
解析 tool_use → 执行工具 → tool_result
```

变成：

```text
解析 tool_use
  → PreToolUse hooks
  → 权限判断
  → 执行工具
  → PostToolUse hooks
  → tool_result
```

### 4.13 这一章的关键学习点

- Hook 是运行时扩展点。
- 权限不是唯一用途，日志、审计、指标、上下文注入都可以复用同一机制。
- 主循环应该尽量保持稳定，新增能力优先通过注册 hook 接入。
- 这为 s20 把众多机制统一到一条工具管线中打下基础。

## s05：TodoWrite —— 给 Agent 一个会话内的显式计划

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s05_todo_write/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s05_todo_write/src/main.rs`

### 4.14 实现了什么

s05 增加 `todo_write` 工具，用于维护当前会话的计划：

- `pending`
- `in_progress`
- `completed`

Todo 适合描述当前 Agent 正在做的工作，例如：

```text
1. 阅读项目结构       completed
2. 分析核心模块       in_progress
3. 输出分析报告       pending
```

### 4.15 如何实现

Python 版本新增：

- `_normalize_todos(todos)`：校验并规范化输入。
- `run_todo_write(todos)`：更新全局 todo 状态。
- `todo_write` 工具 schema。

状态通常保存在进程内存中，不是跨会话的任务数据库。工具 handler 仍然通过 `TOOL_HANDLERS` 注册，因此 Agent Loop 不需要专门为 todo 写一套分支。

system prompt 增加了“复杂任务先规划”的指导。Hooks 还会跟踪 Todo 是否长时间没有更新，并在连续多轮不更新时注入 reminder，提醒模型重新检查计划。

### 4.16 Todo 与 Task 的区别

- Todo 是**当前会话的轻量计划**，强调“我这轮要完成什么”。
- s12 Task 是**持久任务对象**，强调跨会话、依赖关系、认领者和团队协作。

### 4.17 这一章的关键学习点

- 规划不是模型天然可靠的能力，Harness 可以提供外部状态。
- Todo 不执行任务，只帮助 Agent 保持方向。
- 计划状态最好结构化，而不是只写在自然语言中。

## s06：Subagent —— 用独立上下文委派子任务

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s06_subagent/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s06_subagent/src/main.rs`

### 4.18 实现了什么

s06 增加 `task` 工具，使主 Agent 能启动一次性的子 Agent：

- 子 Agent 使用新的 `messages` 上下文；
- 子 Agent 使用单独的 system prompt；
- 子 Agent 使用受限工具集合；
- 子 Agent 完成后只返回摘要给父 Agent；
- 子 Agent 不能继续递归创建子 Agent。

### 4.19 如何实现

`spawn_subagent(description)` 大致流程如下：

```text
父 Agent 调用 task(description)
  ↓
创建新的 messages = [{role: "user", content: description}]
  ↓
使用 SUB_SYSTEM 和 SUB_TOOLS 调用 LLM
  ↓
子 Agent 自己运行一个受限 Agent Loop
  ↓
子 Agent 完成后提取文本结果
  ↓
把结果作为 task 工具的输出返回父 Agent
```

子 Agent 工具列表通常不包含 `task`，从机制上防止递归爆炸。实现还设置了最大轮数；如果子 Agent 没有正常返回最终文本，会从已有 assistant/tool_result 内容中提取一个 fallback 摘要。

这是同步阻塞式委派：父 Agent 调用 `task` 后等待子 Agent 完成。s15 的 teammate 则是持久、可通信的另一种并行协作模型。

### 4.20 这一章的关键学习点

- 子代理的核心价值是上下文隔离，不只是“多一个模型调用”。
- 父 Agent 不需要知道子 Agent 的全部中间过程，只需要最终摘要。
- 限制工具集合和轮数是控制递归、成本和风险的重要手段。

## s07：Skill Loading —— 让知识按需加载

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s07_skill_loading/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s07_skill_loading/src/main.rs`
- 示例 Skill：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/skills`

### 4.21 实现了什么

s07 引入 Skill 机制。每个 Skill 是一个目录，通常包含 `SKILL.md`，用于描述某一类任务的专业知识、流程和工具使用方法。

实现目标是：

- 启动时扫描 Skill；
- 只把 Skill 的名称和简介放进 system prompt；
- 模型真正需要时才加载全文；
- 避免把所有知识一次性塞入上下文。

### 4.22 如何实现

核心函数：

- `_parse_frontmatter(text)`：解析 `SKILL.md` 顶部 YAML frontmatter。
- `scan_skills()`：遍历 `skills/*/SKILL.md`，构建 catalog。
- `list_skills()`：返回可用 Skill 列表。
- `load_skill(name)`：按名称读取 Skill 正文。

模型首先看到的是类似以下信息：

```text
Available skills:
- agent-builder: build and debug agent harnesses
- code-review: review code changes
- mcp-builder: create MCP integrations
- pdf: work with PDF files
```

当模型调用 `load_skill("code-review")` 时，Harness 才把对应的完整 Markdown 内容加载出来。

### 4.23 这一章的关键学习点

- Skill catalog 是低成本索引，Skill body 是高成本知识。
- 按需加载可以降低 system prompt 体积。
- Skill 是 Prompt/知识层能力，不需要改变 Agent Loop。
- Skill 的动态发现也要求 system prompt 能反映真实运行时状态，这会在 s10 进一步抽象。

## s08：Context Compact —— 四层治理上下文

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s08_context_compact/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s08_context_compact/src/main.rs`

### 4.24 实现了什么

s08 解决长对话、大工具输出导致的上下文膨胀问题。它实现了四层压缩：

1. 裁剪旧消息；
2. 对旧工具结果做占位化处理；
3. 将超大工具结果写入磁盘；
4. 调用 LLM 生成历史摘要。

同时增加了 `compact` 类能力以及 context-too-long 时的 reactive compact。

### 4.25 为什么不能简单删除消息

Anthropic tool-use 协议要求消息结构保持合法：

- assistant 中的 `tool_use` 必须有对应的 `tool_result`；
- `tool_result` 必须紧跟在对应的 tool_use 之后形成合法配对；
- 不能只删除其中一半，否则下一次 API 请求可能返回 400。

因此压缩不仅是“删旧消息”，还要维护 tool-use/tool-result 的完整性。

### 4.26 如何实现

典型辅助函数包括：

- `estimate_size(messages)`：估算当前历史大小。
- `collect_tool_results(messages)`：定位工具结果。
- `persist_large_output(tool_use_id, output)`：把大结果写入 `.task_outputs` 或对应目录。
- `tool_result_budget(messages)`：控制工具结果总预算。
- `snip_compact(messages)`：保留头尾、裁剪中间历史。
- `micro_compact(messages)`：将旧的长工具结果替换为简短引用。
- `summarize_history(messages)`：调用 LLM 生成历史摘要。
- `compact_history(messages)`：完成完整压缩。
- `reactive_compact(messages)`：响应 prompt-too-long 的更激进压缩。

可以把压缩过程看成：

```text
原始 history
  ↓
控制 tool_result 总大小
  ↓
裁剪旧消息
  ↓
压缩旧工具输出
  ↓
大结果落盘，history 留引用
  ↓
LLM 总结旧历史
  ↓
保留最近的完整 tool-use/tool-result 对
```

### 4.27 这一章的关键学习点

- 上下文管理是 Agent Harness 的核心能力，不是简单的字符串截断。
- 工具结果通常比用户消息更容易产生大量 token，因此应优先治理。
- 压缩算法必须兼顾语义保留和 API 消息协议合法性。
- 大结果落盘让模型可以“知道结果存在”，而不必把全部内容长期留在上下文里。

## s11：Error Recovery —— 错误不是结束，而是恢复路径

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s11_error_recovery/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s11_error_recovery/src/main.rs`

### 4.35 实现了什么

s11 为 LLM 调用增加生产级错误恢复，重点覆盖三类故障：

| 故障 | 处理方式 |
|---|---|
| 输出被 `max_tokens` 截断 | 提高 token 上限，必要时请求续写 |
| 上下文过长 | reactive compact 后重试 |
| 429/529 临时故障 | 指数退避、抖动、必要时切换备用模型 |

### 4.36 路径一：输出截断

第一次遇到 `stop_reason == "max_tokens"` 时，代码通常不把截断输出写入 history，而是把 `max_tokens` 从 8K 提升到更大的值，例如 64K，然后重试原始请求。

如果扩大 token 后仍然截断，则：

1. 保存已经生成的 assistant 内容；
2. 追加续写提示；
3. 要求模型从中断位置继续，不要重复总结；
4. 设置最大续写次数，避免无限循环。

### 4.37 路径二：上下文超限

当 API 报告 prompt/context 太长时：

1. 检查是否已经做过 reactive compact；
2. 如果没有，则执行更激进的压缩；
3. 保留最近的关键消息和合法工具调用对；
4. 压缩后重试；
5. 如果仍然超限，则退出并向用户报告，而不是无限重试。

### 4.38 路径三：429/529

使用指数退避加随机抖动：

```text
delay = min(base * 2^attempt, max_delay) + jitter
```

具体实现通过 `retry_delay()` 和 `with_retry()` 组织。若连续遇到 529 过载，并且配置了 `FALLBACK_MODEL_ID`，可以把当前模型切换到备用模型。

### 4.39 这一章的关键学习点

- 错误恢复应按故障类型分类，而不是所有异常统一重试。
- 重试前必须判断请求是否幂等、history 是否应该改变。
- 无限重试本身就是一种故障，因此每条恢复路径都要有上限。
- 可靠性机制通常包住 LLM 调用，而不改变工具执行协议。

## s17：Autonomous Agents —— 队友自动找任务、认领任务、继续工作

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s17_autonomous_agents/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s17_autonomous_agents/src/main.rs`

### 4.58 实现了什么

s17 让队友具备自治生命周期：

```text
WORK → IDLE → SHUTDOWN
```

队友完成当前工作后，如果没有新消息，不是直接退出，而是进入 idle cycle：

- 扫描任务板；
- 找出未完成、无 owner、依赖已完成的任务；
- 自动认领一个任务；
- 执行任务；
- 完成后继续扫描。

### 4.59 如何实现

核心函数包括：

- `scan_unclaimed_tasks()`：查询可认领任务。
- `idle_poll(...)`：在 idle 状态轮询邮箱和任务板。
- `spawn_teammate_thread(...)`：启动自治队友。
- 任务 claim/complete 复用 s12 的任务系统。

自治循环大致是：

```text
while not shutdown:
    读取 mailbox
    如果有协议消息：处理协议
    如果有普通消息：执行消息驱动任务
    如果当前有任务：继续 WORK
    否则：
        扫描 task board
        找到可执行任务 → claim → WORK
        没找到 → sleep 后继续 IDLE
```

上下文压缩后需要重新注入 Agent 身份、角色和职责，否则压缩可能把“我是哪个队友、我的权限是什么”这类身份信息裁掉。

### 4.60 这一章的关键学习点

- 自治 Agent 的关键是“唤醒机制 + 任务发现 + 任务认领”，不只是一个更长的 while 循环。
- Idle 是一种有意义的生命周期状态，不等于退出。
- 多个 Agent 同时扫描任务板时，claim 必须具有竞争安全语义。
- 压缩、重启、消息恢复后都要保留 Agent 身份。

- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s18_worktree_isolation/src/main.rs`

### 4.61 实现了什么

s18 将任务与 Git worktree 绑定，让多个 Agent 可以在不同目录同时修改项目而不互相覆盖。

能力包括：

- 创建 worktree；
- 将 worktree 与 task 绑定；
- 工具在对应 worktree 的 `cwd` 中执行；
- 保留或删除 worktree；
- 删除前检查未提交改动；
- 写入事件日志。

### 4.62 如何实现

核心流程：

```text
create_worktree(name, task_id)
  ↓
执行 git worktree add
  ↓
创建独立分支/目录
  ↓
把 task.worktree 写入任务记录
  ↓
队友 claim 任务
  ↓
bash/read/write 自动使用该 worktree 作为 cwd
```

删除时通常分两种情况：

- 没有未提交改动：允许清理；
- 有未提交改动：默认拒绝，除非显式指定 discard。

### 4.63 为什么 worktree 不是简单复制目录

复制目录会丢失 Git 分支语义，并可能产生重复、过时的文件。`git worktree` 使用 Git 原生机制管理多个工作目录，适合并行开发、审查和回滚。

### 4.64 这一章的关键学习点

- 多 Agent 协作必须隔离文件写入边界。
- “任务的 owner”和“任务的 cwd”应该是两个明确状态。
- 工具层传递 `cwd` 是关键，否则 worktree 只存在于元数据里，实际操作仍会落在主目录。
- 清理动作需要保护未提交工作，避免 Agent 误删成果。

## s19：MCP Plugin —— 把外部服务器工具动态接入工具池

实现文件：

- Python：`/Users/ninebot/code/mosslau/AgentNest/tutorials/python/s19_mcp_plugin/code.py`
- Rust：`/Users/ninebot/code/mosslau/AgentNest/tutorials/rust/s19_mcp_plugin/src/main.rs`
- 配置示例：项目中的 `.mcp.json` 及各章相关配置

### 4.65 实现了什么

s19 引入 MCP（Model Context Protocol）插件机制，使 Agent 可以连接外部工具服务器：

- 从配置读取 MCP server；
- 连接 server；
- 动态发现 server 提供的工具；
- 将外部工具加入统一工具池；
- 调用时通过统一的 tool_use/tool_result 协议回灌。

教学版本使用 `MCPClient` 和 mock server 演示机制，重点是工具池组装，而不是实现完整网络协议。

### 4.66 如何实现

连接流程：

```text
connect_mcp("docs")
  ↓
MCPClient 连接/初始化 server
  ↓
tools/list
  ↓
得到外部工具 schema
  ↓
normalize_mcp_name()
  ↓
注册为 mcp__docs__<tool>
  ↓
assemble_tool_pool()
```

外部工具名称统一规范化为：

```text
mcp__server__tool
```

这样可以避免不同 MCP server 之间的工具名冲突，并且让工具来源一眼可见。

s19 的核心函数通常包括：

- `MCPClient`：封装连接与调用。
- `normalize_mcp_name(name)`：规范化工具名。
- `connect_mcp(name)`：建立连接并发现能力。
- `assemble_tool_pool()`：把内置工具与 MCP 工具合并。

### 4.67 与 s20 的区别

s19 主要展示“如何连接和动态发现工具”。s20 才将 MCP 工具纳入完整的权限和 Hooks 管线。因此，s19 的工具接入重点是插件化，s20 的重点是统一治理。

### 4.68 这一章的关键学习点

- MCP 工具应该像内置工具一样进入统一 tool schema。
- 动态工具池需要动态更新 system prompt。
- 外部工具不能绕开权限、日志和审计。
- 工具命名空间是插件生态中非常重要的隔离机制。

### 4.70 S20 的工具池

每轮可以通过 `assemble_tool_pool()` 组装：

```text
BUILTIN_TOOLS + CONNECTED_MCP_TOOLS
BUILTIN_HANDLERS + MCP_HANDLERS
```

内置工具包括文件、Shell、Todo、Task、团队、Worktree、Cron、Skill 和 MCP 连接等能力。连接 MCP server 后，下一轮工具池会动态出现类似：

```text
mcp__docs__search
mcp__deploy__deploy
```

### 4.71 S20 的完整执行顺序

一轮 Agent 运行可以展开成如下步骤：

```text
1. 接收用户消息、后台通知或 Cron 消息
2. 触发 UserPromptSubmit hooks
3. 收集 teammate inbox
4. 收集 background task 完成结果
5. 更新 Memory / Task / Team / MCP 等运行时 context
6. 组装或命中 system prompt cache
7. 对 messages 执行 context preparation/compact
8. 根据当前状态组装工具池
9. 调用 LLM，并通过 Recovery 包装
10. 把 assistant 回复加入 history
11. 如果没有 tool_use，触发 Stop hooks，输出结果
12. 如果有 tool_use，逐个处理：
    12.1 判断是否应放入后台
    12.2 触发 PreToolUse hooks
    12.3 检查权限
    12.4 执行内置工具、Subagent 或 MCP 工具
    12.5 触发 PostToolUse hooks
    12.6 生成 tool_result 或 background placeholder
13. 将 tool_result 回灌 history
14. 回到第 1 步，继续调用 LLM
```

### 4.72 S20 中的权限管线

MCP 工具不会获得特殊待遇。所有工具都经过统一入口：

```text
tool_use
  ↓
PreToolUse
  ↓
permission_hook
  ├─ deny → tool_result(error)
  ├─ ask → user reject → tool_result(error)
  └─ allow
       ↓
   background decision
       ↓
   handler/MCP call
       ↓
   PostToolUse
       ↓
   tool_result
```

这体现了综合 Harness 的核心思想：外部插件也必须接受同样的安全和审计规则。

### 4.73 S20 中的两层计划

S20 同时保留：

1. `todo_write`：当前 Agent 的会话级计划。
2. Task graph：跨会话、可依赖、可认领、可被队友消费的持久任务。

二者不是重复功能：Todo 管“当前思路”，Task 管“可协作的工作对象”。

### 4.74 S20 中的两种 delegation

- `task`：一次性 Subagent，独立上下文，返回最终摘要。
- `spawn_teammate`：持久队友，使用 MessageBus，支持计划审批、任务认领、idle 自治和 worktree 隔离。

### 4.75 S20 中的上下文与恢复

调用模型前先准备上下文：

```text
tool_result_budget
  → snip_compact
  → micro_compact
  → compact_history
```

调用模型时再执行恢复：

- 429：指数退避重试；
- 529：指数退避，必要时切备用模型；
- `max_tokens`：先提升 token，再续写；
- prompt too long：reactive compact 后重试。

### 4.76 S20 中的外部事件

主 Agent 不只由用户输入驱动，还会被以下事件唤醒：

- 后台任务完成；
- Cron 到点；
- 队友发来消息；
- 队友提交计划或请求审批；
- 任务状态发生变化。

这些事件最终都转换为消息、通知或状态更新，再进入同一个 Agent Loop。

### 4.77 S20 的本质

s20 说明了一个重要结论：

```python
while True:
    response = LLM(messages, tools)
    if not has_tool_use(response.content):
        return
    results = execute_tools(response.content)
    messages.append(tool_results)
```

这一段仍然没有变。复杂性来自围绕它的 Harness：

- 运行前组装什么 prompt；
- 暴露哪些工具；
- 工具执行前是否授权；
- 工具是否放后台；
- 结果如何回灌和压缩；
- 出错是否恢复；
- 队友如何通信；
- 任务如何持久化；
- 外部工具如何接入；
- 目录如何隔离。

# 5. S20 完整工具执行管线

把上述机制统一起来，最终的工具调用管线可以写成：

```text
                 ┌──────────────────────────────┐
                 │ LLM 返回 assistant content  │
                 └──────────────┬───────────────┘
                                ↓
                    解析 text / tool_use blocks
                                ↓
                 ┌──────────────────────────────┐
                 │ should_run_background ?      │
                 └──────────────┬───────────────┘
                         yes     │      no
                         ↓        │       ↓
                后台 placeholder  │   PreToolUse hooks
                                  │       ↓
                                  │   permission
                                  │       ↓
                                  │   handler dispatch
                                  │       ├─ builtin tool
                                  │       ├─ subagent
                                  │       ├─ teammate/protocol
                                  │       ├─ task/cron/worktree
                                  │       └─ MCP tool
                                  │       ↓
                                  │   PostToolUse hooks
                                  │       ↓
                                  └── tool_result
                                            ↓
                              追加 user tool_result message
                                            ↓
                              收集后台完成通知/队友消息
                                            ↓
                              compact + 更新动态 prompt
                                            ↓
                                       再次调用 LLM
```

其中每类机制的职责边界是：

| 层 | 职责 |
|---|---|
| LLM | 决策、规划、选择工具、理解结果 |
| Prompt | 告诉模型当前身份、规则、工具和可用知识 |
| Tool schema | 把 Harness 能力声明给模型 |
| Permission | 判断当前动作是否允许 |
| Hooks | 承载日志、审计、注入、统计等横切逻辑 |
| Handler | 真正执行内置工具或外部插件 |
| Message history | 保存模型与环境之间的结构化交互 |
| Compact | 控制 history 大小并保持协议合法 |
| Recovery | 在 LLM/API 故障时重试、压缩或切换模型 |
| Task/Team | 支持持久工作和多 Agent 协作 |
| Background/Cron | 让 Agent 异步运行并被未来事件唤醒 |
| Worktree | 隔离并行代码修改 |
| Memory/Skills | 分别提供持久知识和按需知识 |

# 9. 设计上的重要结论

## 9.1 Agent 的核心不是“一个更大的 Prompt”

Prompt 只能指导模型，不能替代：

- 工具执行；
- 权限判断；
- 状态持久化；
- 并发调度；
- 错误恢复；
- 消息协议；
- 文件隔离。

这些能力必须由 Harness 提供。

## 9.2 工具调用协议是所有机制的连接点

无论是：

- 内置文件工具；
- 子 Agent；
- Task；
- Cron；
- Worktree；
- MCP；

最终都可以表现为：

```text
tool_use → handler → tool_result
```

因此新增能力最自然的方式是注册一个工具，而不是修改主循环的核心逻辑。

## 9.3 外部事件也应该回到同一个 Loop

后台完成、Cron 到点、队友消息都不需要创建另一套 Agent 大脑。它们只需要转换成：

- 新的 user message；
- `<task_notification>`；
- mailbox 注入；
- 状态更新；

然后复用已有的 Prompt、工具、权限、压缩和恢复路径。

## 9.4 生产化的重点是边界

从 s01 到 s20，最重要的工程化改进不是让模型“更聪明”，而是为模型行动增加边界：

- workspace 边界；
- 权限边界；
- 工具边界；
- 上下文边界；
- 任务边界；
- Agent 身份边界；
- Worktree 文件边界；
- MCP server 边界。

## 9.5 状态机比自然语言更可靠

Todo、Task、Protocol、Team lifecycle、Cron job 和 Worktree 都使用结构化状态。自然语言适合让模型理解，结构化状态适合让 Harness 判断。

## 最终结论

这个项目最值得掌握的不是某个具体函数，而是它的递进式架构：

```text
一个模型
+ 一个稳定的 Agent Loop
+ 一组结构化工具
+ 一套权限与 Hook 管线
+ 一套上下文/记忆系统
+ 一套任务/并发/调度系统
+ 一套多 Agent 协议
+ 一套隔离与插件机制
= 可持续演进的 Agent Harness
```
