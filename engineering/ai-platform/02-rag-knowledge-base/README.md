# 企业知识库问答系统

> 状态：⬜ 未开始
> 对应 roadmap 阶段：第 二 阶段
> 对应文档：`roadmap/大模型数据中心平台工程师.md`

## 目标

在 01 产出的语料与向量之上，做一个**能回答、能溯源、能评测**的知识库问答系统：端到端输入是「用户问题 + 知识库（文档/工单/手册）」，输出是「答案 + **引用来源（文档 id + 分片 id + 原文片段）** + 检索命中的证据链」。

一句话可检验目标：**对一组固定的评测问题集，系统能给出答案并逐条给出可点开的引用来源；当知识库里没有依据时，系统明确回答"无依据"而不是编造。**

（本项目的核心不是"接一个大模型"，而是**检索质量 + 引用可溯源 + 端到端评测**这三件工程事。）

## 技术栈

- 语言与运行时：Python 3.13
- 编排框架：LangChain 或 LlamaIndex（二选一，实施时记录选型理由；两者只用其「检索链/文档加载」能力，不依赖其 agent 能力）
- 向量库：Milvus 或 Qdrant（Docker 单机；本机不可用时先用 `faiss` 或 `numpy` 暴力检索兜底，并如实标注）
- 检索：稠密向量检索 + 稀疏（BM25）**混合检索** + **Rerank**（交叉编码器或 `bge-reranker`）
- 生成：OpenAI 兼容 LLM 接口（本地 vLLM 或在线 API，二选一，标注环境）
- 评测：自建问题集（问题 + 标准答案要点 + 依据文档）、检索命中率（Recall@k / MRR）与答案要点覆盖率
- 服务：FastAPI（`/ask`、`/documents`、`/healthz`）+ 结构化日志

## 系统架构

```text
用户问题 ──▶ ┌────────────┐   ┌───────────────┐   ┌──────────────┐
             │ 查询改写/扩写│ → │ 混合检索        │ → │ Rerank 重排   │
             └────────────┘   │ 稠密 + BM25     │   │ top-k 精排    │
                              └───────────────┘   └──────────────┘
                                     ▲                    │
             ┌───────────────┐       │                    ▼
             │ 向量库(语料/向量)│───────┘            ┌──────────────┐
             │ 来自 01 / 03   │                    │ 生成 + 引用拼装│
             └───────────────┘                    └──────────────┘
                                                          │
                                                          ▼
                                      答案 + 引用来源（doc_id / chunk_id / 原文）
                                                          │
                                            ┌─────────────┴─────────────┐
                                            ▼                           ▼
                                    评测集打分（离线）             在线服务 + 日志（FastAPI）
```

模块边界与关键决策：

| 模块 | 职责 | 关键设计点 |
|------|------|-----------|
| 混合检索 | 稠密 + 稀疏召回，合并去重 | 两路召回要能**分别看到命中来源**（否则无法解释"为什么答错"） |
| Rerank | 精排 top-k | 与召回解耦：rerank 变了不影响索引 |
| 生成与引用 | 用 top-k 上下文生成答案，**逐句标注依据** | 上下文不足时必须输出「无依据」，而不是补全 |
| 评测 | 固定问题集 + 命中率 + 要点覆盖率 | 评测集入库版本化，改语料必须重跑 |
| 服务 | HTTP 接口 + 日志 | 每次回答记录「问题/召回/精排/生成/引用」全链 trace，用于复盘 |

## 复用的算法实验

- [迷你 RAG 检索增强生成](../../../algorithms/05-generative/mini-rag/) —— **本项目的算法内核**：切分、向量化、相似度检索与「把检索结果拼进提示」的完整链路；本项目的混合检索与引用溯源都是它的工程化放大
- [注意力机制](../../../algorithms/04-transformer/attention/) —— 交叉编码器 Rerank 的打分本质（query-document 交互），理解它才知道 rerank 为什么比向量点积准
- [K-Means 聚类](../../../algorithms/02-statistical-ml/kmeans/) —— 知识库主题覆盖度分析（语料偏科会让某类问题系统性答不出来）
- [PCA 主成分分析](../../../algorithms/02-statistical-ml/pca/) —— 向量空间可视化抽检（检索失败时，先看向量空间是否把语义相近的文档分开了）

## 验收标准

- [ ] 知识库能装进 01/03 产出的语料与向量，并提供按文档、分片的可追溯 id
- [ ] `/ask` 返回答案 + **逐条引用来源**（doc_id + chunk_id + 原文片段），前端/CLI 可点开核对
- [ ] 评测集（≥30 题，含「知识库无依据」的负例）上给出**检索命中率与答案要点覆盖率**的实测数字
- [ ] 负例（库里没有答案）时系统输出「无依据」，编造率为 0（人工核对全部负例）
- [ ] 混合检索 vs 纯向量检索有对比实测（命中率提升有数字），Rerank 开关有对比实测
- [ ] 每次回答写全链 trace（问题/召回/精排/生成/引用），可据此复盘一次错误回答的归因
- [ ] 依赖外部服务（Milvus/Qdrant、LLM 接口）的部分如实标注环境与复现命令

## 实施笔记

- **2026-09（梳理阶段）**：把「引用溯源」写进验收标准而不是当加分项——企业知识库的价值在**可核对**，没有引用的答案在业务上不可用。同时刻意加入「负例不编造」这一条，它是 RAG 与「纯聊天」的分界线。
- **2026-09（待验证假设）**：① 向量库选 Milvus 还是 Qdrant——先看本机 Docker 可用性，不可用则用 faiss 兜底并把「真实向量库路径」标为未验证；② LLM 走本地还是在线——评测集必须能在两种后端上跑，因此生成层要抽象成接口（便于对比与替换）。
- **与 01 的接口约定**：01 产出的分片 id 必须稳定（`doc_id + 序号 + 内容哈希`），本项目直接把它作为引用 id；如果 01 改了口径，本项目需重跑索引与评测。
