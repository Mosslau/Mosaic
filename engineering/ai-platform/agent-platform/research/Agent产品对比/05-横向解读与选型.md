# 四款产品横向对比 · 解读与选型

> **13 维总览对比表见 [README.md](README.md)**——本文不重复表格，只保留表外的深度解读、强度评级与选型建议。
> 
> 产品详情：01-ClaudeCode / 02-Codex / 03-DeepSeekHarness / 04-Dify

---

## 1. 关键差异解读

### 1.1 定位光谱：工具 → 框架 → 平台

四款定位光谱见 [README.md](README.md) §一（单一事实源）。选型第一问不是"哪个强"，而是"**谁在用**"：开发者自己写代码 → 工具；团队要自建系统 → 框架；业务团队要搭应用 → 平台。

### 1.2 模型绑定：自由度 vs 生态深度

- 绑定单厂商（CC→Claude、Codex→OpenAI）：永远跟最新模型能力同步，但被锁定
- 模型无关（dsh）或多 Provider（Dify）：自由，但要自己处理模型差异
- 判断标准：你的团队是"押注一个模型生态"还是"需要多模型兜底/对比"

### 1.3 编排范式：最大分野

> 自由度高 → 探索型任务强（CC/Codex/dsh）；确定性高 → 流程型/合规型任务强（Dify）
> 
> 折中选项是 dsh：循环可替换，能把"自由循环"换成"图驱动"

```text
Claude Code / Codex：隐式自由循环 —— 模型自己决定下一步，边界靠预算/权限/硬编码约束
dsh：              可替换的 turn/step 循环 —— 循环本身是插件，事件接缝可插任意策略
Dify：             显式图编排 —— 收敛路径在工作流 DAG 上画死，只有 Agent 节点内部是隐式循环
```

### 1.4 记忆系统：三层模型

四款产品的记忆可归纳为三层：**项目规范**（CLAUDE.md/AGENTS.md，每会话注入）→ **会话事实**（dsh 事件日志 / Codex checkpoint）→ **长期目标**（Codex goal / Dify 知识库）。差异在第三层的成熟度：Codex 的 goal 是"跨会话循环"的最成熟实践，dsh 的事件日志是"事实记忆"的最严格实现。

### 1.5 工具与治理：MCP 是共同语言

MCP 是四款产品的共同工具协议。差异在**治理**：CC 靠 PreToolUse hooks 拦截、Codex 靠沙箱权限判定、dsh 靠 tools 管道（pre-execute 校验）、Dify 靠平台工具节点配置——拦截点位置决定你能在循环的哪个环节施加策略。

### 1.6 安全强度评级（主观评分）

> 强度为编者主观评分：Codex 把安全放进运行时（沙箱），其余靠策略/配置。

| 产品 | 安全机制 | 强度 |
|:--|:--|:--|
| **Codex** | workspace-write 沙箱 + 网络隔离 + Computer Use | ★★★★★ |
| **Claude Code** | 权限匹配（allow/deny/ask）+ hooks 拦截 + 审批 | ★★★★ |
| **dsh** | sandbox/guard 插件（可插拔，强度取决于配置） | ★★★ |
| **Dify** | 平台级多租户 + RBAC + 审批流 | ★★★★（应用层） |

**评分维度**：

- ① 运行时强制——安全边界由运行时强制（沙箱/网络隔离）还是靠模型自觉与策略配置；
- ② 拦截粒度——权限匹配 / hooks / 工具瀑布的拦截精细度；
- ③ 审批链——敏感操作是否必须显式升级审批；
- ④ 数据边界——多租户隔离与私有化能力。

### 1.7 可观测强度评级（主观评分）

> 强度为编者主观评分：dsh 是架构级保证（不可重建的模型输入不存在），其余是尽力记录。

| 产品 | 机制 | 强度 |
|:--|:--|:--|
| **dsh** | 事件日志单一事实源 + "model-visible means logged" 不变式 | ★★★★★ |
| **Codex** | checkpoint 回滚重放 + history.jsonl | ★★★★ |
| **Claude Code** | hooks 日志 + /status + 会话恢复 | ★★★ |
| **Dify** | 平台级 LLMOps（日志/评估/标注/成本） | ★★★★（运维向） |

**评分维度**：

- ① 架构级重建——模型可见内容能否从日志/快照**必然**重建（不变式保证 vs 尽力记录）；
- ② 回放/回滚——是否支持任意一步复现或回退；
- ③ 日志完备性——事件、token 用量、成本记录的粒度；
- ④ 运维向——是否有平台级评估/标注/成本追踪（LLMOps）。

### 1.8 开源与定制

dsh（MIT）是唯一**完全开源可深度定制**者（改循环都行）；Dify 开源社区版 + 企业版（应用层可扩展）；CC/Codex 闭源，靠官方 hooks/API 扩展。定制自由度的排序：**dsh > Dify > CC/Codex**（评分维度：① 许可自由度——MIT / 带例外开源 / 闭源；② 修改深度——能否替换循环内核与核心组件；③ 扩展机制——插件系统 / hooks+API / 平台边界内配置）。

## 2. 选型建议（按场景）

> 框架级完整选型矩阵（含开源许可）见 [../Agent主流开发框架/06-选型速查.md](../Agent主流开发框架/06-选型速查.md)。

| 场景 | 推荐 | 理由 |
|:--|:--|:--|
| 个人深度编码 | Claude Code 或 Codex | 体验成熟、生态全 |
| OpenAI 生态 + 安全沙箱 | Codex | 沙箱/可重放/goal 预算 |
| Claude 生态 + 细粒度控制 | Claude Code | 17 hooks 事件控制最细 |
| 自建 Agent 底座/引擎 | dsh | 唯一完全开源、loop 可替换、可观测最强 |
| 业务团队搭应用 | Dify | 零代码 + LLMOps + 多租户 |
| 企业合规强治理 | dsh 底座 + 显式工作流 | 事件日志可审计 + 收敛路径画死 |
| 混合多模型 | dsh / Dify | 模型无关 / 多 Provider |

---

## 3. 一句话总结

**要快用 CC/Codex，要稳用 Dify，要自己造用 dsh**——三者不是替代关系，而是"工具 → 平台 → 底座"的互补光谱；真正决定上限的是你对 Agent Loop 的理解（见 [../AgentLoop演进与设计/README.md](../AgentLoop演进与设计/README.md)）。
