## 1. 起点：原始 ReAct 解剖

ReAct（**Re**asoning + **Act**ing，Yao et al., 2022）的原始形态**不是一套系统，而是一个提示词模板**：

```text
问题：xxx

Thought 1: 我需要查一下今天北京的天气
Action 1: search[北京天气]
Observation 1: 晴，25°C

Thought 2: 用户还想知道要不要带伞
Action 2: search[北京 降雨概率]
Observation 2: 20%

Thought 3: 信息够了，可以回答
Answer: 北京今天晴，25°C，降雨概率低，不用带伞。
```

**循环机制**：把 "Thought / Action / Observation" 文本拼进提示词 → 让 LLM 生成下一段 → 解析出 Action → 执行 → 把 Observation 拼回去 → 再来一轮。

**历史功绩**：把"推理"和"行动"交织在一起，让模型边想边做——这是 agent 思想的奠基。

**14 个硬伤 → 现代解决方案对照表**（14 维是早期"七局限"分析——循环归属模型/无状态/无停止判定/工具自由文本/无错误恢复/无可观测/无治理——的系统化扩展）：

| # | ReAct 的硬伤 | 对应现代演进 |
|---|---|---|
| 1 | 循环介质是文本，动作靠正则解析 | 维度 1 事件驱动结构化循环 |
| 2 | 会话就是一段越来越长的提示词 | 维度 2 会话即日志 |
| 3 | 上下文零管理，窗口小只能跑几步 | 维度 3 上下文工程 |
| 4 | 一次只执行一个动作，无法并行 | 维度 4 并发调度 |
| 5 | 工具失败 = 错误文本拼回去"看运气" | 维度 5 系统性错误恢复 |
| 6 | 模型直接执行一切动作，无权限守门 | 维度 6 安全守门 |
| 7 | 单 agent 单循环，无法委派 | 维度 7 多 agent 编排 |
| 8 | 模型既是规划者又是执行者，人无法干预 | 维度 8 混合控制 |
| 9 | 规划是隐式的（每步只决定下一步） | 维度 9 显式 Plan-and-Execute |
| 10 | "执行完"就算完，无验证环节 | 维度 10 反思与验证闭环 |
| 11 | 无记忆：上下文丢了就全忘 | 维度 11 记忆分层 |
| 12 | 无协议，工具是私有代码，不可组合 | 维度 12 协议化互操作 |
| 13 | 成本不可控（越长越贵，无上限） | 维度 13 成本预算治理 |
| 14 | 工具集固定写死，不可扩展 | 维度 14 工具动态扩展 |

## 2. 14 个演进维度详解（六组）

> 14 个维度按关注点分为六组：**A 循环结构化 / B 上下文与记忆 / C 执行与调度 / D 可靠性与安全 / E 认知与规划 / F 组织与生态**。每组给出"旧 → 新"的本质转变与代表性现代实现。

### A 组：循环本身的结构化（维度 1、2）

**维度 1：从"文本往返"到"事件驱动的结构化循环"**

| | 原始 ReAct | 现代（DSH / CC / CX） |
|---|---|---|
| 循环介质 | 提示词文本标签 | turn/step 分层 + 事件日志 + 类型化消息 |
| 工具调用 | 正则解析 Action 文本 | 原生 function calling（结构化参数） |
| 状态 | 无 | turn/step 显式生命周期（`agent/status` = idle/running） |

- DSH：每个动作记成类型化事件（`tool/call`、`tool/result`、`step/start`…共 13 种：`turn/start`、`turn/end`、`step/start`、`step/end`、`user/message`、`assistant/chunk`、`assistant/message`、`tool/call`、`tool/result`、`request/context`、`request/header`、`todo/write`、`session/end-seed`）；
- CC：收敛成 5 类消息协议（System / Assistant / User / Stream / Result）。
- **本质**：动作从文本变为带 schema 的数据，循环可观测、可重放、可程序化消费。

**维度 2：从"对话即提示词"到"会话即日志，可持久化可恢复"**

```text
事件日志（唯一事实源）                 模型看到的消息（派生视图）
turn/start      ──────────────┐
user/message    ──────────────┤
assistant/chunk ── derive ────┼──► deriveMessages() → 请求
tool/call       ──────────────┤
tool/result     ──────────────┘
```

由此获得三个 ReAct 没有的能力：**resume**（崩溃/中断后从日志恢复）、**fork**（从事件点分支）、**审计**（日志既是状态又是轨迹）。
- 实例：DSH 的 `SessionEvent` log + `resume()`；CC 的 session_id 恢复"读过的文件、做过的分析"。

### B 组：上下文与记忆（维度 3、11）

**维度 3：上下文管理从"塞满为止"到"一等公民"**

| 机制 | 解决什么 | 实例 |
|---|---|---|
| 自动压缩（compaction） | 历史太长 → 总结旧轮次 | DSH compaction 插件（带锁、崩溃检测）；CC auto-compaction（`compact_boundary` + CLAUDE.md 摘要指令） |
| Prompt caching / KV cache 感知 | 稳定前缀每轮重付 | CC 显式 prompt caching；DSH"前缀字节不变才命中 KV Cache" |
| 子代理隔离转录 | 子任务全转录塞爆主上下文 | CC/DSH subagent：父代理只收最终结果 |
| 按需工具加载 | 工具 schema 也占上下文 | CC 的 ToolSearch |
| Token 预算 | 控制放多少历史 | Dify 的 TokenBufferMemory |

**维度 11：记忆分层体系（短期 / 中期 / 长期）**

| 层级 | 载体 | 作用 | 实例 |
|---|---|---|---|
| 短期 | 上下文窗口 + 压缩摘要 | 当前任务推理材料 | TokenBufferMemory、compaction 摘要 |
| 中期 | 事件日志 / checkpoint / 会话持久化 | 可恢复可重放的工作记忆 | DSH session log + resume；CC session_id |
| 长期 | 常驻指令 / 跨会话提炼 / 记忆工具 | 跨会话不遗忘 | CLAUDE.md、CC condenser、CX memories read/write/mcp、DSH goal |

- **设计原则 1（读写分离）**：读侧（CLAUDE.md 注入、condenser 提炼）保证"该知道的永远在"；写侧（memories 工具、goal 状态）让 agent 主动持久化。
- **设计原则 2（可丢失性决定层级）**：丢了会坏事的放长期层；丢了能重算的放短期层，交给 compaction 处置。

### C 组：执行与调度（维度 4、14）

**维度 4：从"单工具串行"到"并发调度模型"**

- 只读/并行安全 → 并发（CC：`Read`/`Glob`/`Grep` 并发；DSH：parallel 滚动池，默认 `maxParallelToolCalls=10`）；
- 写操作/互斥 → 串行屏障（CC：`Edit`/`Write`/`Bash` 串行；DSH：exclusive 屏障）。
- **本质**：一个 turn 完成多个独立动作，深度不变、时长大幅缩短。

**维度 14：工具发现与动态扩展——工具从"写死的函数"到"动态生态"**

- 按需加载（CC ToolSearch，省上下文）；动态注册（插件市场：CC plugin / CX plugin / DSH dsh-plugin）；
- 技能（Skill）：复杂操作封装成可复用技能（DSH skill、CC skill）；MCP 服务器即插即用。

### D 组：可靠性与安全（维度 5、6、10、13）

**维度 5：错误处理从"看运气"到"系统性恢复"**

```text
① 工具失败      → 结构化错误结果进入管道（DSH 的 isError）
② 模型请求失败  → 独立重试层：llm-retry 按 provider 退避
③ 单轮失败      → turn 级错误边界：插件失败只结束 turn，不杀死 loop
④ 环境被拒      → 阶梯式重试：Codex orchestrator"审批→沙箱→被拒→升级沙箱重试（缓存，不重复审批）"
⑤ 进程崩溃      → 持久化 + resume
```

- **本质**："失败-修复-重试"从异常路径变成循环的正常组成部分——编码 agent 能跑几百轮的前提。

**维度 6：从"无权限"到"安全守门成为循环的一部分"**

```text
DSH 工具瀑布：pre-execute(allow/deny/ask) → 单调 guards → execute → post-execute → result
CC 权限系统：allowed_tools / disallowed_tools / permission_mode(default|acceptEdits|plan|dontAsk|auto|bypassPermissions)
Codex：审批 → 沙箱选择（Seatbelt / bwrap / Windows）→ 执行
```

- 关键细节：DSH 的 guard 是**单调的**（只能减少权限，防止监听器顺序把拒绝变回允许）——"安全不变量"。

**维度 10：反思与验证闭环——"执行完还要验证"**

```text
执行（行动） → 验证（我做得对吗？） → 通过 → 继续
                     │
                     └─ 不通过 → 反思（哪错了）→ 修正 → 重试
```

- 测试驱动（编码 agent 以"测试全绿"为完成条件）；结构化输出校验（CC `error_max_structured_output_retries`）；
- Reflexion 反思范式（失败经验写回记忆，带着教训重试）；后置 hooks（`PostToolUse`/`Stop`）。
- **本质**：ReAct 是"想到哪做到哪"，现代循环是"做一步验一步"。

**维度 13：成本预算治理——把"经济学"做进循环**

| 手段 | 干什么 | 实例 |
|---|---|---|
| 硬预算 | 达成本上限即终止 | CC `max_budget_usd` → `error_max_budget_usd` |
| 推理成本调节 | 简单任务低 effort | CC effort（low~max）、DSH reasoning-effort |
| 计量 | 每次请求记录用量 | DSH `request/header`；CC `total_cost_usd`/`usage` |
| 结构性省成本 | 缓存/隔离/按需加载/压缩 | prompt caching、subagent 隔离、ToolSearch、compaction |

### E 组：认知与规划（维度 8、9）

**维度 8：从"模型全权决策"到"混合控制 + 人机协同"**

- **Hooks**：`PreToolUse`（拦截/改写/阻止工具）、`UserPromptSubmit`（注入上下文）、`PreCompact`（压缩前存档）——进程内、不占模型上下文、可短路循环；
- **Steer / Inject**：DSH 的 `steer()` 在 step 边界插入纠偏，`inject()` 注入上下文不唤醒循环；
- **Plan 模式**：先只出计划不执行（CC `plan` 权限模式；DSH plan 为 logged state），人审后放开；
- **Ask-user**：循环内主动提问（CC `AskUserQuestion`）。

**维度 9：规划范式——从"隐式规划"到"显式 Plan-and-Execute"**

```text
ReAct（隐式规划）           Plan-and-Execute（显式两阶段）        现代混合
推理=规划=行动             ① 先产出完整计划（plan 阶段）          todo 清单（计划外部化）
每步只决定下一步            ② 再逐步执行（execute 阶段）           plan 权限模式（先审后执行）
无整体视野                  ③ 计划执行中可修订（replanning）      执行中动态重规划
```

- **todo 清单**（CC `TodoWrite`、DSH todo_write 与 `todo/write` 事件）：计划被**外部化**为结构化数据 → 可观测、可中断、可恢复；
- 辩证补充：reasoning 模型把"规划"再次内化，显式规划器收缩；但 todo 外部化仍是标配——它是可观测性与可恢复性的基础。

### F 组：组织与生态（维度 7、12）

**维度 7：从"单 agent 单循环"到"多 agent 编排原语"**

| 原语 | 干什么 | 实例 |
|---|---|---|
| Subagent | 委派独立子任务，隔离上下文 | CC/DSH 原生；DSH 支持 continuable（中途纠偏）、output schema、深度上限、工具过滤 |
| Workflow 脚本 | 模型写 JS 脚本 fan-out 子代理 | DSH workflow（worker_threads，meta 先校验后执行） |
| Fresh-agent 循环 | 每轮全新子会话，避免上下文污染 | DSH Ralph（workspace + 结构化 handoff 报告） |
| 长期目标 | 跨轮次持续同一目标 | DSH goal（一个 goal round = 一个 turn） |

**维度 12：协议化与互操作——loop 从"私有实现"走向"开放生态"**

```text
工具层   MCP（Model Context Protocol）   工具即插即用
agent层  ACP（Agent Client Protocol）    agent 可被外部系统调用（DSH acp 服务器）
hook层   CC / Codex hook 协议            DSH 两个兼容桥（dsh-hooks-claude-code / dsh-hooks-codex）
SDK层    CC Agent SDK / CX App-Server JSON-RPC / DSH sdk   程序化控制循环
```

- **本质**：同一个 loop 可换 provider、接任意 MCP 工具、被 ACP 驱动、复用跨生态 hook——可组合性大增。

## 3. 现代 Agent Loop 完整总图

把 14 个维度叠起来，一个现代 loop 长这样：

```text
   ┌──────────────────────── 外层策略（goal / Ralph / workflow / 预算上限）────────────────────────┐
   ▼                                                                                            │
┌──────────────────────────────────  TURN  ──────────────────────────────────┐                   │
│                                                                             │                   │
 用户输入 ──► step: 从事件日志派生消息（记忆：短期窗口 + 中期日志）              │                   │
   │             │                                                           │                   │
   │             ▼                                                           │                   │
   │        组装 system prompt + 工具schema(按需加载/MCP) + 历史               │                   │
   │             │  （prompt cache 命中前缀）                                 │                   │
   │             ▼                                                           │                   │
   │        LLM 推理 ──► 无工具调用? ──► 输出回答 ──► turn/end                 │                   │
   │             │                                                           │                   │
   │             ▼ 有工具调用                                                 │                   │
   │        权限守门（allow/deny/ask + guards + 审批）                         │                   │
   │             │                                                           │                   │
   │             ▼                                                           │                   │
   │        调度执行（并行池 / 串行屏障 + 沙箱）                                │                   │
   │             │  ← 失败？重试层 / 阶梯沙箱重试                               │                   │
   │             ▼                                                           │                   │
   │        结果回写事件日志（tool/result）                                    │                   │
   │             │                                                           │                   │
   │             ▼                                                           │                   │
   │        【验证】结果校验 / 测试 / 反思（Reflexion 教训写回记忆）              │                   │
   │             │  ← 未通过 → 修正重试                                        │                   │
   │             ▼                                                           │                   │
   │        上下文快满? → compaction 压缩旧轮次（短期→摘要）                    │                   │
   │             │                                                           │                   │
   └─────────────┴── 全程可被 hooks 拦截 / steer 注入 / cancel ──────────────┘                   │
                │                                                           │                   │
   协议层：MCP(工具) / ACP(被调用) / hook 兼容 / SDK(程序化控制)                │                   │
                │                                                           │                   │
  持久化（resume/fork）  子代理委派（隔离转录）  长期记忆（CLAUDE.md/condenser）◄── 继续下一轮 ────┘
```

## 4. ReAct 如何被吸收：step 语义内核

现代 loop **没有发明新循环**——它把 ReAct 的三个环节映射进工程结构：

| ReAct 环节 | 现代 loop 中的位置 | 工程化后的差异 |
|:--|:--|:--|
| **Thought**（推理） | `agent/request` 前的模型推理 | 受 pre-step 拦截（可改写/拒绝） |
| **Action**（行动） | `tool/call`（schema + 权限 + 沙箱） | 结构化、可校验、可审计 |
| **Observation**（观察） | `tool/result`（落事件日志） | 结构化回填 + 可重放 |
| **循环控制** | 引擎的 turn/step 驱动 | 不再由模型控制何时继续 |
| **Task Done** | `turn-stopping` 代码验证 | 不再由模型自评完成 |

**ReAct 是"让模型假装自己会循环"；现代 Agent Loop 是"让引擎真的管理循环，模型只做循环里的一步"**——所以现代系统的循环永远可控（可停、可回放、可审计），而 ReAct 的循环只能靠模型自觉。

### 4.1 同一任务的两种写法对照（修 CI 失败的 PR）

**ReAct 方式**（prompt 内循环）：
```text
Thought: 先看 CI 日志定位失败点
Action: read_file(pytest.log)
Observation: KeyError 在第 12 行
Thought: 修改 orders.py 修复
Action: edit_file(orders.py)
Observation: 已修改
Thought: 跑测试验证
Action: pytest orders/
Observation: 4 passed, 0 failed
Thought: 任务完成（模型自评）
```

**现代 loop 方式**（事件日志视角）：同一任务的完整实录（含权限/沙箱/预算标注）见 [03-标准设计.md](03-标准设计.md) §7.1，此处只留骨架：

```text
step1: request → read_file(pytest.log) → result: KeyError 第12行
step2: request → edit_file(orders.py) → result: 已修改
step3: request → pytest orders/ → result: 4 passed, 0 failed
turn-stopping: 代码验证 "pytest 全绿 AND lint 干净" → ✅ 达标
```

**对照要点**：
- 语义完全一样（想→做→看 三次），**差在工程外壳**
- 现代版每一步有日志（可重放）、有预算（硬边界）、工具受沙箱治理、停止由代码判定
- 同样的任务，现代版"跑错了能定位、能回滚、能审计"；ReAct 版"错了只能从头看对话猜"

### 4.2 四代演进：每一代工程化前一代的一个环节

| 代 | 把前一代的哪个环节工程化了 | 代表 |
|:--|:--|:--|
| ReAct | —（起点） | 提示词模式 |
| Tool-use / FC | **Action 工程化**：自由文本 → schema + 参数校验 | Function Calling、OpenAI 工具调用 |
| Agent loop | **循环工程化**：循环从 prompt 移到 harness，+ 记忆 + 状态 | Claude Code、Codex、早期框架 |
| turn/step Loop | **循环治理化**：事件日志 + 硬停止 + 沙箱 + 可重放 | dsh、企业级标准（见 [03-标准设计.md](03-标准设计.md)） |

## 5. 接棒者：Graph Engineering 对照（Loop → Graph）

> 演进链到 Loop 并未止步：Graph Engineering 把"自由循环"画死成显式图，成为确定性场景的接棒者（社区"Loop 时代终结？"讨论的焦点）。本文以 Loop 为底座研究，这里给出它与接棒者的完整对照与"何时用图、何时用循环"的正式判断（逐年时间线见 [README.md](README.md) §1）。

**核心对照**：

| 维度 | turn/step Loop（本文主对象） | Graph Engineering（LangGraph 式） |
|:--|:--|:--|
| **循环归属** | 引擎驱动，循环隐式——模型在 turn 内自由决定下一步 | **图显式定义**：节点 = 步骤/Agent，边 = 流转/回退/循环，收敛路径画死 |
| **状态管理** | 事件日志 + 代际压缩（append-only 事实流） | **Checkpointer 状态快照**：State 是一等公民，中断/恢复/重放基于快照 |
| **停止条件** | turn-stopping 代码验证 + 三硬边界 | 拓扑收敛（走完 = 结束），回退/分支在图上显式声明 |
| **调试/可回放** | 事件日志完整重建（model-visible means logged） | 任意执行点固化为可恢复快照（人机协同：中断 → 改 State → 恢复） |
| **自由 vs 确定** | 自由探索强，开放任务优势明显 | 确定性、可追踪、可验证，流程型任务优势明显 |
| **代表** | dsh / Claude Code / Codex | LangGraph（双层图 + checkpointer）、Dify 工作流 DAG |

**LangGraph 的双层图与 checkpointer（机制要点）**：LangGraph 与普通 DAG 的本质区别是 **State 是一等公民**——节点是"纯函数"（读 State 写 State），边是"转移"，Checkpointer 把任意执行点固化为可恢复快照；这使"人机协同"天然成立（中断 → 人工改 State → 恢复）。

**何时用图、何时用循环（正式判断）**：

| 任务形态 | 用哪种 | 理由 |
|:--|:--|:--|
| 路径明确、要稳定复现（合规/审批/固定业务流） | **Graph**（LangGraph 式显式图 / Dify 工作流） | 收敛由拓扑保证，分支回退显式，可审计可审批 |
| 任务开放、要自主探索（修 bug/研究/长任务） | **Loop**（turn/step harness） | 自由度换深度，探索型任务需要模型自主决策 |
| 折中 | Loop 内核 + 图编排外层 | 引擎保持自由循环，把固定段落画成图（dsh 可替换驱动 + Dify 式画布） |

**判断准则**：问"收敛路径是否可预画"——能画死 → Graph；画不死、靠探索 → Loop。二者不是替代而是接棒：**Loop 是底座，Graph 是确定性接棒者**（方法论见 [Agent工程范式演进.md](../Agent工程范式演进.md) 第五层；Dify 作为图产品化的细节见 [02-横向对比.md](02-横向对比.md) §3④）。
