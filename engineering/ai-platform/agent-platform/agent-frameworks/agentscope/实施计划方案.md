## 1. 概述

### 1.1 目标

在 20 周内交付一套可生产运营的企业级多租户 Agent 平台：支持 Web / 企微 / 飞书 / 内部系统嵌入多端接入；Admin 集中治理模型与 Hub 资源并发布 Agent；租户开箱使用公共 Agent 并可自建私有能力。

### 1.1.1 投入规模与启动前提（先回答"值不值得建"）

本计划全量投入约 **20 周 × 5.5~6 人 ≈ 600 人日**，外加基础设施（K8s/PG-HA/Redis Cluster/Milvus/MinIO/e2b，月成本可观）与外部依赖（企微/飞书资质、KMS、e2b 商务、渗透资源）。**600 人日是重投入，立项前必须确认业务规模假设成立，否则应裁剪或降级。**

**启动前提（Go 的业务侧判断，与技术门禁 M0 并列）：**

| 判断 | 通过 | 不通过 |
|---|---|---|
| 是否已有 **≥10 个真实租户**，或明确的**对外商业化**需求？ | 按本计划全量推进 | 进入下方"降级路径" |
| 多租户资源共享是否为**已验证的高频需求**（非设想）？ | 全量推进 | 先用轻量方案验证 |

**降级路径（业务规模不足时）：**

1. **轻量先行**：research/ 下的轻量方案（owner 驱动共享，约 2~4 人日，无 MCP 网关/计费/Agent 市场）先跑通真实业务，验证多租户共享是否高频。
2. **裁剪范围**：若确认多租户但规模有限，可裁剪 M3/M4 的可后置项——计费（4.3）、Agent 市场（4.1）后置到 v2.x，投入可降至约 400 人日。
3. **明确不做**：仅 3~5 个内部团队、无对外需求时，**不应**建设 MCP 网关审批流、计费、Agent 市场——这些是 600 人日中的主要成本，但对内部小场景无 ROI。

> 本条是为避免"为想象中的多租户需求过度建设"。技术门禁 M0 验证"能不能建"，本条验证"该不该按这个规模建"。两者都通过才进入 M1。

**降级路径的生效机制**：§3 总体里程碑与 §4 详细计划为全量（600 人日）版本。若经本条判断触发降级路径，里程碑与工期按裁剪项相应核减（如裁剪计费 4.3 + Agent 市场 4.1 约 200 人日），裁剪范围与调整后计划由变更管理流程（§10）评审确认后生效，不预先维护两套计划。

### 1.2 实施策略

1. **POC 先行（门禁制）**：AgentScope 2.0 扩展点能力是全部架构的地基，M0 验证不通过则不允许进入 M1，并触发架构回退预案（见 §6 R-1）。
2. **垂直切片交付**：每个阶段交付"可真实使用"的端到端能力（而非按层交付），尽早暴露集成风险。
3. **控制面优先，运行时做薄**：自建工作量集中在控制面；运行时只做扩展点装配，代码量刻意保持最小，降低对框架升级的敏感度。
4. **隔离性测试前置**：跨租户访问拦截用例从 M1 起就纳入 CI 门禁，而不是上线前补测。

### 1.3 前置条件

| 项 | 要求 | 责任方 | 时间 |
|---|---|---|---|
| AgentScope 2.0 版本锁定 | 确认生产使用的具体版本号并冻结 | 架构师 | M0 开始前 |
| 模型资源 | 至少 1 个可用的全局模型（GPT/Qwen/DeepSeek 任一）API Key | 采购/Admin | M0 第 1 周 |
| 基础设施 | K8s 集群（dev/staging/prod）、PostgreSQL、Redis、Milvus、MinIO 资源申请 | DevOps | M0 第 1 周 |
| 企微/飞书应用资质 | 企业管理员权限、自建应用创建权限 | 业务方 | M2 开始前 |
| 密钥管理 | KMS 或 Vault 可用 | 安全/DevOps | M1 开始前 |

## 2. 团队配置与角色

| 角色 | 人数 | 职责 |
|---|---|---|
| 架构师 / Tech Lead | 1 | 架构守护、框架扩展点研究、代码评审、ADR 决策 |
| 后端工程师 A（控制面方向） | 1.5 | 租户/Hub/发布/审计/计量/MCP 网关 |
| 后端工程师 B（运行时方向） | 1.5 | agentscope.app 集成、扩展点装配、渠道适配器、RAG |
| 前端工程师 | 1 | Admin 控制台、用户聊天端、embed 页面、JS-SDK |
| DevOps 工程师 | 0.5 | K8s、CI/CD、监控告警、沙箱集群 |
| QA 工程师 | 0.5 | 测试策略、隔离性/安全用例、自动化回归 |

> 前端在 M2 起为主要瓶颈（Admin 控制台页面量大），若进度紧张可在 M2~M3 临时增加 0.5 人力。

> **控制面人力提示**：ADR-001 决策"工作量收敛到控制面"，但控制面方向仅 1.5 人，却承载 12 张 PG 表 + MCP 网关 + 审批流 + 计量 + 计费 + 对账任务（§6.4.4 Reconciler）。这是人力配比的张力点——建议将控制面方向增至 **2 人**，或将计费（4.3）/Agent 市场（4.1）后置到 v2.x 以释放控制面带宽。若按 §1.1.1 降级路径裁剪范围，此张力自然缓解。

- 其余项允许有"已知绕过方案"的结论（例如官方 KB 抽象不满足则自研 RAG 工具，属预期内路径）。

| 4.11 | 运维交接：Runbook（常见故障处置）、告警响应流程、值班机制 | Runbook | 全员 | 2d |

**验收标准**：
- 300 并发会话压测下：首 token P95 ≤ 3s、SSE 断连率 < 1%、无跨租户数据泄露。
- 渗透测试高中危漏洞清零。
- 账单与计量明细可对账；灰度租户真实使用 2 周无 P1 故障。

## 5. 关键路径与依赖

```
M0(框架验证) ─门禁→ M1 ─→ M2 ─→ M3 ─→ M4
                          │      │
   关键路径：0.3/0.4/0.5/0.6 → 1.5 发布引擎 → 2.3 工作区隔离
             → 2.9 企微 → 3.1 MCP 网关 → 4.5 压测 → 4.10 上线
```

主要跨阶段依赖：

- 企微/飞书应用资质（外部依赖）必须不晚于 M2/M3 第 1 周就绪，否则渠道任务顺延；
- KMS/Vault 不晚于 M1 第 1 周就绪（阻塞凭证加密）；
- e2b 商务/资源不晚于 M4 第 1 周确定，否则沙箱走 docker 备选方案；
- 每个阶段的"验收测试"任务依赖该阶段全部开发任务完成，预留 buffer 不压缩。

## 9. 上线与运维交接

**上线 checklist（M4-W20）**：生产环境配置复核（密钥/域名/TLS）→ 数据迁移演练 → 监控告警联通 → 灰度租户开通 → 48h 观察 → 全量开放 → 发布公告。

**运维交接物**：

1. **Runbook**：含 12 个预设故障场景处置（Redis 不可用、MCP 上游挂掉、凭证过期、沙箱耗尽、锁僵死、SSE 雪崩、计量延迟等）；
2. **告警响应分级**：P1（全租户不可用/数据泄露嫌疑）15 分钟响应；P2（单租户/单渠道故障）2 小时；P3（性能退化）次日；
3. **例行维护**：凭证轮换（季度）、框架版本评估（每里程碑）、备份恢复演练（季度）、审计归档（月度）。

## 10. 变更与范围管理

- **基线**：本计划 + 架构方案 v1.0 为范围基线；里程碑验收标准变更需架构师 + 产品负责人双签。
- **变更流程**：需求方提变更单 → 影响评估（工期/架构/安全）→ 纳入下一里程碑或 backlog；不允许里程碑中途插入未经评估的需求。
- **阶段评审**：每个里程碑结束召开评审会，输出《里程碑验收报告》，确认或调整后序计划。
- **进度透明**：双周迭代 + 每周站会同步燃尽；R-1~R-7 风险每周复核状态。
