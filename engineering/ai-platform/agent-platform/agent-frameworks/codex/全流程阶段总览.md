
**三道关键门禁贯穿全程**：

```

 合规)        必过)
```

**关键路径**（任一延误即影响总工期）：
`0.3 驱动验证 → 1.4 Runner → 2.5 审批中心 → 3.1 MCP 网关 → 4.1 压测 → 4.5 上线`

## 阶段 0：立项准备（M0 之前，约 1~2 周）
| 项 | 内容 |
|---|---|
| **目标** | 拿到"开工许可"——业务 + 订阅合规 + 技术三前置都过 |
| **关键活动** | ① 业务规模确认（≥10 租户或对外商业化？见实施计划 §1.1.1）<br>② Codex 订阅与商用条款审查（服务端无人值守是否允许——Codex 特有前置）<br>③ M0 技术实证（本机/dev 实际驱动 codex CLI 跑通，而非静态分析）<br>④ 立项评审（向决策者陈述，争取资源） |
| **前置条件** | Codex 订阅、OpenAI API Key、商用条款法务确认、dev 基础设施（K8s/PG/Redis/MinIO）申请、KMS 排期 |
| **产出** | 立项决议 + 资源到位 + 《驱动验证报告》 |
| **门禁** | 业务判断通过 **且** 订阅合规 **且** M0 实证通过，才允许进 M1 |

> **当前状态**：架构方案 / 实施计划已定稿（可评审）。**下一步即启动本阶段的"M0 技术实证"**——重点验证"Codex 可被服务端驱动"（headless 可用性），这是本适配器与自研运行时（agent-core）的关键分野。

---

## 阶段 M0：技术验证（W1–W2，2 周）
| 项 | 内容 |
|---|---|
| **目标** | 验证"**Codex 可被服务端驱动**"这一关键风险，跑通沙箱 / goal / checkpoint / MCP 机制 |
| **关键任务** | 环境搭建(0.1)、订阅就绪(0.2)、**驱动验证(0.3，必过)**、沙箱行为(0.4)、goal 机制(0.5)、checkpoint(0.6)、MCP(0.7)、事件流原型(0.8)、压测基线(0.9) |
| **产出** | POC 报告 + 驱动验证清单 |
| **门禁（Go/No-Go）** | **0.3 必须通过**；0.4/0.5/0.6 必须通过或存在可接受绕过方案。0.3 失败 → 回退预案（CLI 管道方式再验证；仍失败则判定本适配器不成立，切换其他运行时适配器 agent-core / deepseek-harness） |
| **团队** | 后端 B 为主，后端 A / DevOps / QA / 架构师配合 |

## 阶段 M1：MVP（W3–W6，4 周）
| 项 | 内容 |
|---|---|
| **目标** | 单租户端到端闭环：提交任务 → Codex 服务端执行 → SSE 事件流 → 交付产物 |
| **关键交付** | 代码基座（control-plane + codex-runner）、JWT 认证、任务 API（SSE）、Runner v1（headless 驱动 + 工作区物化 + goal 预算）、事件流解析 v1、Agent 配置管理（AGENTS.md / config.toml 物化）、Web 任务页、Admin v1、CI/CD |
| **特点** | 此阶段**不做多租户隔离**，但所有表结构 / 代码路径预留 tenant_id（从第一天就存在，避免后期迁移） |
| **验收** | 单租户任务端到端交付 + 事件流实时可见 + goal 预算硬停止生效；凭证密文、日志无明文 |

---

## 阶段 M2：v1.0 多租户（W7–W10，4 周）
| 项 | 内容 |
|---|---|
| **目标** | 多租户隔离 + 审批中心 + 审计 + 密钥管理（首个可称"企业级"的版本） |
| **关键交付** | 租户体系（CRUD/角色）、进程级隔离（每任务独立容器 + 网络默认断开）、工作区隔离（tenants/{tid}/ + writable_roots）、隔离性测试套件（纳入 CI 红线）、审批中心（挂起/回调/过期 + Web 审批 UI）、密钥管理（KMS）、审计 v1、预算 × 配额双层闸门、Admin v2 |
| **验收** | 两租户任务互不可见（进程/工作区/凭证）+ 隔离套件 100% 通过；沙箱外敏感操作必须审批；管理操作 100% 落审计 |

---

## 阶段 M3：v1.5 生态与安全增强（W11–W14，4 周）
| 项 | 内容 |
|---|---|
| **目标** | MCP 网关 + Skills 市场 + checkpoint 重放服务 + 计量 |
| **关键交付** | MCP 网关 v1（凭证注入 / 写操作审批联动 / 审计限流）、MCPHub、SkillsHub（版本化 + 上架扫描 + 物化）、Plugins 白名单与子代理配额、checkpoint 重放服务（归档 + 只读重放 API）、计量底座（usage_records / usage_daily）、前端增量（管理页 / 复盘页 / 报表） |
| **验收** | 私有 MCP 写操作未审批挂起、批准后执行、全程审计；任意任务可经 checkpoint 重放复盘；用量报表与 OpenAI 账单误差 < 5% |

---

## 阶段 M4：v2.0 生产上线（W15–W18，4 周）
| 项 | 内容 |
|---|---|
| **目标** | 压测加固 + 渗透 + 灰度上线 + 运维交接 |
| **关键交付** | 50 并发压测调优、可观测性完善、安全渗透（跨租户越权 / 凭证泄露 / 审批绕过 / 归档越权）、归档与备份策略（checkpoint 冷热分层）、灰度上线（2 试点租户 → 全量）、Runbook |
| **验收** | 50 并发：任务创建 P95 ≤ 1s、首事件 P95 ≤ 10s、SSE 断连率 < 1%、无跨租户泄露；渗透高中危清零；灰度 2 周无 P1 故障 |

---

## 阶段 5：运营期（M4 之后）
| 项 | 内容 |
|---|---|
| **运维交接** | Runbook（8 个预设故障场景：容器启动失败 / 预算未触发硬停止 / history.jsonl 解析异常 / 审批超时风暴 / 凭证过期 / MCP 上游挂掉 / checkpoint 归档失败 / OpenAI 端点限流）、告警分级（P1 15min / P2 2h / P3 次日）、值班机制 |
| **例行维护** | 凭证轮换（季度）、Codex 版本评估（每里程碑 + 重放回归）、归档清理与冷热分层（月度）、审计归档（月度） |

## 各阶段速查表
| 阶段 | 周期 | 时间盒 | 一句话目标 | 门禁/验收 | 关键交付 |
|---|---|---|---|---|---|
| 0 立项 | 1~2 周 | 前期 | 业务+合规+技术三前置 | 业务判断 + 订阅合规 + M0 实证 | 立项决议 + 资源 |
| M0 验证 | 2 周 | W1–W2 | 验证 Codex 可被服务端驱动 | 0.3 必过 + 0.4/0.5/0.6 | POC 报告 |
| M1 MVP | 4 周 | W3–W6 | 单租户端到端 | 任务→SSE→交付闭环 | Runner + 事件流 + Web 任务页 |
| M2 v1.0 | 4 周 | W7–W10 | 多租户+审批+审计 | 隔离套件 100% + 审批生效 | 隔离 / 审批 / 审计 / 密钥 |
| M3 v1.5 | 4 周 | W11–W14 | 生态与安全 | MCP 审批 + 重放可复盘 | 网关 + 市场 + 计量 |
| M4 v2.0 | 4 周 | W15–W18 | 生产上线 | 渗透+压测+灰度 | 上线 + Runbook |
| 5 运营 | 持续 | 上线后 | 稳定运行 | 告警分级响应 | Runbook + 维护 |

**总计**：约 18 周建设期（M0~M4）+ 前期立项 1~2 周；团队 5.5~6 人；全量投入约 500 人日。
