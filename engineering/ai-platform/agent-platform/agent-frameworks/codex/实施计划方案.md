## 1. 概述
### 1.1 目标
在 18 周内交付一套可生产运营的"基于 Codex 的企业级编码 Agent 平台"：Codex 执行能力服务端化（API + SSE）、多租户隔离、可审批（沙箱外敏感操作）、可审计可重放（checkpoint 归档）、成本可控（goal token 预算硬边界）。

### 1.1.1 投入规模与启动前提（先回答"值不值得建"）
本计划全量投入约 **18 周 × 5.5~6 人 ≈ 500 人日**，外加 Codex 订阅与 OpenAI API 用量（按 token 计费，成本随任务量线性增长——goal 预算与租户配额是唯一硬闸门）与基础设施。**500 人日是重投入，立项前必须确认业务规模与订阅前提成立，否则应裁剪或切换路线。**

**启动前提（Go 的业务与合规判断，与技术门禁 M0 并列）：**

| 判断 | 通过 | 不通过 |
|---|---|---|
| 是否已有 **≥10 个真实租户**，或明确的**对外商业化**需求？ | 按本计划全量推进 | 降级：轻量先行（内部团队直接使用 Codex + AGENTS.md 验证价值，约 2~4 人日） |
| **Codex 订阅 / 商用条款**是否允许服务端无人值守、多用户代运行？ | 按本计划推进 | **本适配器不成立**，切换其他运行时适配器（agent-core 自研 / deepseek-harness） |
| M0 技术实证（**Codex 可被服务端驱动**）是否通过？ | 进 M1 | 回退预案（§6 R-1） |

> 前两条验证"该不该按这个规模建"，第三条验证"能不能建"。三者都通过才进入 M1。

### 1.2 实施策略
1. **POC 先行（门禁制）**：M0 的 0.3"Codex 可被服务端驱动"是全部架构的地基，不通过则不允许进入 M1，并触发架构回退预案（§6 R-1）。
2. **垂直切片交付**：每个阶段交付"可真实使用"的端到端能力（M1 就是"提交任务 → 执行 → SSE → 交付"闭环），尽早暴露集成风险。
3. **控制面为主、执行侧做薄**：Codex 是黑盒，执行侧只做进程编排与产物解析，代码量刻意保持最小，降低对 Codex 版本升级的敏感度。
4. **隔离性测试前置**：跨租户访问拦截用例从 M2 起纳入 CI 门禁，而不是上线前补测。
5. **订阅前提跟踪**：Codex 订阅 / 商用条款作为项目级风险条目，每周复核状态。

### 1.3 前置条件
| 项 | 要求 | 责任方 | 时间 |
|---|---|---|---|
| Codex 订阅 | OpenAI 账号 + Codex 访问权限（订阅方案与商用条款以 OpenAI 官方为准） | 采购 / Admin | M0 第 1 周 |
| OpenAI API Key | 计费 Key（token 用量结算） | 采购 / Admin | M0 第 1 周 |
| 商用条款审查 | 服务端无人值守、多用户代运行、数据 / 内容合规 | 法务 | M0 开始前 |
| 基础设施 | K8s（dev/staging/prod）、PostgreSQL、Redis、MinIO、KMS/Vault | DevOps | M0 第 1 周 |
| 任务模型资源 | OpenAI 系推理模型可用（模型绑定 OpenAI 生态，不承诺多模型路由） | 采购 | M0 第 2 周 |

## 4. 阶段详细计划
### M0 — 技术验证（W1–W2，2 周）
**目标**：验证"**Codex 可被服务端驱动**"这一关键风险，并跑通架构依赖的每一项 Codex 机制，消灭"假设性设计"。

| # | 任务 | 输出物 | 负责人 | 工时 |
|---|---|---|---|---|
| 0.1 | 环境搭建：dev K8s、PostgreSQL、Redis、MinIO、KMS | 可用 dev 环境 | DevOps | 2d |
| 0.2 | Codex 订阅与 OpenAI API Key 就绪 + 商用条款法务确认 | 就绪确认 | 采购 / 法务 | 2d |
| 0.3 | **【关键】验证 Codex 可被服务端驱动**：容器内运行 codex CLI、非交互输入注入、输出捕获、退出码语义、会话落盘（state_5.sqlite / history.jsonl 生成） | 驱动验证代码 + 记录 | 后端 B | 4d |
| 0.4 | 沙箱行为验证：workspace-write / writable_roots 生效、网络默认受限、升级操作可观测 | 验证记录 | 后端 B | 2d |
| 0.5 | goal 机制验证：create_goal 带预算 → 预算耗尽 hard stop；跨会话 get_goal 恢复 | 验证记录 | 后端 B | 2d |
| 0.6 | checkpoint 验证：分段落盘、重放 / 回滚可用性 | 验证记录 | 后端 B | 2d |
| 0.7 | MCP 接入验证：stdio / http MCP 工具调用 | 验证记录 | 后端 A | 1d |
| 0.8 | 事件流原型：history.jsonl 解析为结构化事件 | 原型代码 | 后端 B | 2d |
| 0.9 | 压测基线：并发任务、单任务 token 消耗、容器启动耗时、审批挂起率 | 压测报告 | QA + DevOps | 2d |
| 0.10 | 编写《驱动验证报告》，召开 M0 门禁评审 | 报告 + 评审结论 | 架构师 | 1d |

**门禁标准（Go/No-Go）**：

- **0.3 必须通过**：Codex 无法被服务端驱动（强制交互 / 无输出捕获 / 落盘不可控）→ 触发回退预案（§6 R-1）；
- 0.4 / 0.5 / 0.6 必须通过，或存在可接受的绕过方案；
- 其余项允许"已知限制"结论（如沙箱网络策略细节以实测为准）。

### M1 — MVP（W3–W6，4 周）
**目标**：单租户（platform 默认租户）端到端闭环：用户提交编码任务 → Codex 在服务端执行 → 事件流实时可见 → 交付产物。此阶段不做多租户隔离，但所有表结构和代码路径按多租户设计预留（tenant_id 字段从第一天就存在）。

| # | 任务 | 输出物 | 负责 | 工时 |
|---|---|---|---|---|
| 1.1 | 代码基座：control-plane 与 codex-runner 两个仓库/模块骨架 | 可构建部署的骨架 | 全员 | 3d |
| 1.2 | 用户与认证：JWT 签发（RS256 + JWKS）、登录 | 认证链路 | 后端 A | 3d |
| 1.3 | 任务 API：创建任务（agent_id + 目标 + 预算）→ 调度 → SSE 事件流 | 任务链路 | 后端 B | 5d |
| 1.4 | Runner v1：容器编排、codex headless 驱动、工作区模板物化（AGENTS.md / config.toml）、goal 创建与预算执行 | Runner v1 | 后端 B | 7d |
| 1.5 | 事件流解析 v1：history.jsonl → 结构化事件（plan_update / step / tool_result / goal_budget） | 事件流 v1 | 后端 B | 3d |
| 1.6 | Agent 配置管理：AGENTS.md 字段化模板 + config.toml 渲染 + 发布物化 v1 | 发布引擎 v1 | 后端 A | 5d |
| 1.7 | Web 端 v1：任务提交页、事件流 / 计划展示、结果页 | 前端 v1 | 前端 | 8d |
| 1.8 | Admin v1：Agent 配置表单、预算默认值 | Admin v1 | 前端 | 5d |
| 1.9 | CI/CD：镜像构建、staging 自动部署 | 流水线 | DevOps | 3d |
| 1.10 | M1 验收测试与修复 | 验收报告 | QA | 3d |

**验收标准**：

- 单租户提交编码任务，Codex 在服务端执行，Web 实时看到计划 / 工具调用 / 预算消耗事件流，任务完成交付产物；
- goal 预算硬停止生效（注入小预算验证超预算强制停止）；
- 凭证以密文落库 / 落 KMS，日志中无明文。

- 管理操作 100% 落审计；日志无明文凭证。

## 5. 关键路径与依赖
```
M0(0.3 驱动验证) ─门禁→ M1(1.4 Runner) → M2(2.5 审批中心) → M3(3.1 MCP 网关) → M4(4.5 上线)
   关键路径：0.3 → 1.4 → 2.5 → 3.1 → 4.1 压测 → 4.5 上线
```

主要跨阶段依赖：

- **Codex 订阅与商用条款审查必须 M0 第 1 周完成**（阻塞 0.3 与全部后续阶段）；
- KMS/Vault 不晚于 M1 第 1 周就绪（阻塞凭证加密）；
- OpenAI API Key 与模型配额不晚于 M0 第 2 周就绪；
- 每个阶段的"验收测试"任务依赖该阶段全部开发任务完成，预留 buffer 不压缩。

## 6. 风险管理
| # | 风险 | 阶段 | 概率/影响 | 应对 |
|---|---|---|---|---|
| R-1 | **Codex 无法被服务端驱动**（headless 不可用 / 强制交互 / 落盘不可控） | M0 | 中/极高 | **M0 门禁 0.3 必测**；预案① 换 CLI 管道方式再验证（stdin 注入 + stdout 解析 + 落盘文件校验）；预案② 判定本适配器不成立，切换其他运行时适配器（agent-core 自研 / deepseek-harness），工期以切换评估为准 |
| R-2 | Codex 订阅 / 商用条款变更（不允许无人值守、价格调整） | 全程 | 中/高 | 法务前置审查 + 条款快照锁定；预算模型预留订阅波动；评估 OpenAI 企业版 / API 路径 |
| R-3 | 模型绑定 OpenAI：数据出境 / 内容策略导致任务受限 | M1 起 | 中/高 | 数据合规评估；敏感任务数据脱敏；任务内容策略白名单 |
| R-4 | 黑盒限制：细粒度工具级审计 / 拦截不可达 | 全程 | 高/中 | 拦截外置（网关 + 产物解析，架构 ADR-001）；M0 明确可观测边界并写入架构文档 |
| R-5 | Codex 版本升级 Breaking Change（落盘格式 / 机制变化） | 全程 | 中/中 | 版本冻结；每里程碑评估升级；升级前必跑重放回归用例 |
| R-6 | 成本失控（token 消耗 / 订阅并发限制） | M1 起 | 中/高 | goal 预算硬停止 + 租户配额 + 用量告警（三层闸门） |
| R-7 | 沙箱对任务有摩擦（需系统级操作的任务无法完成） | M1 起 | 中/中 | 任务模板设计规避；审批升级路径兜底；文档明示能力边界 |
| R-8 | 审批挂起风暴（任务集体等待审批） | M2 起 | 中/中 | 审批超时自动拒绝并释放任务资源；挂起数告警；高危操作强制他人审批 |

## 9. 上线与运维交接
**上线 checklist（M4-W18）**：生产环境配置复核（密钥/域名/TLS）→ 归档与备份演练 → 监控告警联通 → 灰度租户开通 → 48h 观察 → 全量开放 → 发布公告。

**运维交接物**：

1. **Runbook**：含 8 个预设故障场景处置（任务容器启动失败、goal 预算未触发硬停止、history.jsonl 解析异常、审批超时风暴、凭证过期、MCP 上游挂掉、checkpoint 归档失败、OpenAI 端点限流）；
2. **告警响应分级**：P1（全平台不可用 / 数据泄露嫌疑）15 分钟响应；P2（单租户故障）2 小时；P3（性能退化）次日；
3. **例行维护**：凭证轮换（季度）、Codex 版本评估（每里程碑 + 重放回归）、归档清理与冷热分层（月度）、审计归档（月度）。

## 10. 变更与范围管理
- **基线**：本计划 + 架构方案 v0.1 为范围基线；里程碑验收标准变更需架构师 + 产品负责人双签。
- **变更流程**：需求方提变更单 → 影响评估（工期 / 架构 / 安全 / 成本）→ 纳入下一里程碑或 backlog；不允许里程碑中途插入未经评估的需求。
- **阶段评审**：每个里程碑结束召开评审会，输出《里程碑验收报告》，确认或调整后序计划。
- **成本红线**：任何变更不得取消 goal 预算硬边界或租户配额强制（这是平台成本可控的根基）。
