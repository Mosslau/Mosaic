## 1. 概述

### 1.1 背景与目标

dsh（DeepSeek Harness）的定位是 **"Everything is a Plugin" 的 Agent Harness**——它是"用来构建 Agent 的 Harness"，**不是成品**。其核心哲学：没有需要打补丁的特权核心，通过挂载插件扩展，注册是可回退的副作用（effect），插件卸载时自动解除。

本方案的目标：**以 dsh 为底座、以插件树为扩展机制，自建企业级多租户 Agent 平台引擎**。即不把 dsh 当作成品直接售卖，而是把它当作可深度定制的循环内核与可观测底座，在其上叠加平台控制面，交付给企业租户一套"可治理、可审计、可回放、可扩展"的 Agent 平台。平台要回答四类核心诉求：① **多租户治理**（隔离/配额/审批/审计/计量）；② **能力按需装卸**（goal/plan/todo/skill/subagent/sandbox/workflow/mcp 等以插件按需装配）；③ **最强可观测/可回放**（事件日志单一事实源，任何模型输入都能从日志重建）；④ **成本可控的长会话**（模型无关 + DeepSeek prefix-cache 优化）。

### 1.2 技术基座：为什么是 dsh

| 维度 | dsh 事实（素材快照 v0.1.1-rc.2） | 对平台的价值 |
|---|---|---|
| 形态 | Agent Harness（Web UI / headless / SDK），`npx @deepseek-ai/dsh web` 运行 | 自建平台引擎而非包装成品 |
| 插件机制 | Cordis 插件框架：Service / Event / Effect 三要素；注册是卸载即解除的可逆副作用 | 平台能力以插件挂载，不侵入核心 |
| 循环 | `Agent` 接口零循环依赖，`core/agent-loop` 默认 driver **可整体替换** | 平台可换循环策略而不动其他代码 |
| 事件日志 | 追加式 `SessionEvent` 日志 = 单一事实源；`deriveMessages()` 从日志投影模型历史 | 重放/恢复/审计/遥测同源，可观测性最强 |
| 许可 | **MIT 完全开源** | 可深度定制、可 fork、无商业锁 |
| 模型 | 模型无关（DeepSeek 优先） | 企业可自由选模型，不绑定厂商 |
| 长会话成本 | DeepSeek prefix-cache 优化 | 长会话 token 成本显著下降 |

**关键风险（必须正视）**：① developer preview，破坏性变更——M0 验证版本稳定性并锁定版本与插件快照；② 学习曲线陡（Cordis 概念）——团队专项培训；③ 生态建设中——关键能力自研平台插件补齐，社区插件按需引入并快照。

### 1.3 设计原则

| 原则 | 说明 |
|---|---|
| 不自建循环内核 | turn/step、事件日志、瀑布拦截、恢复机制全部复用 dsh；平台只做 dsh 不管的事（租户/治理/审批/计量） |
| 插件即能力 | 一切扩展以插件挂载；平台自身的租户/审批/配额/计量也做成插件，可装卸、卸载即解除 |
| 事件日志即事实 | 任何模型可见内容必须已落日志；审计/回放/恢复/计费全部从 SessionEvent 单一事实源派生 |
| 控制面 / 运行面分离 | 控制面管配置与治理，运行面（dsh 插件树）管执行；两者通过"发布物化"单向同步 |
| 作用域收敛隔离 | dsh 原生以 agent 作用域为边界（core/scope）；租户隔离收敛在"平台身份解析 + Session/Agent 命名 + 插件作用域"三条路径上强制 |
| 版本与快照不可变 | 锁定 dsh 版本 + 插件版本快照；平台 Agent 发布生成不可变快照，存量会话不受配置修改影响 |
| 安全默认 | 沙箱默认开启、高风险工具默认人工审批、密钥不出平台 |

### 1.4 术语表

| 术语 | 含义 |
|---|---|
| dsh / Harness | DeepSeek Harness，Everything is a Plugin 的 Agent Harness——构建 Agent 的框架容器，非成品 |
| 插件树 | boot 时按有序层组合的插件集合（Profile/Bundle/Patch）；Cordis 为驱动插件框架（Service/Event/Effect） |
| Session 事件 | `session/event`（turn/*、step/*、user/message、assistant/*、tool/*），持久事实，append-only |
| Agent 事件 | `agent/*`（inbox、step、status、request、validation、continuation），活体协调 |
| Capability 事件 | `fs/*`、`tools/*`、`telemetry/*`，策略/适配器接缝 |
| 瀑布拦截点 | agent/pre-step、agent/request、llm/stream、tools/pre-execute/execute/post-execute |
| deriveMessages | 从事件日志投影模型历史的派生函数 |
| 平台化扩展 | 标注为"【平台化扩展】"的部分：dsh 不提供，由平台自建（租户/API/审批/计费） |

**两个进程模型**（参照 agentscope 方案的"控制面/数据面分离"思路，dsh 侧为运行面）：

| 进程 | 职责 | 状态 | 存储 |
|---|---|---|---|
| **control-plane**（自建） | 租户/用户/RBAC、Agent 模板与发布、密钥、审批中心、审计、计量计费 | 有状态 | PostgreSQL + 对象存储 |
| **runtime**（dsh Harness） | 插件树装配、Agent 生命周期、turn/step 循环、事件日志、工具/沙箱执行 | 无状态（状态在事件日志 + 存储） | 事件日志存储（Redis/对象存储分层） |

### 2.2 插件树的平台化叠加方式

平台运行时 = **一个定制 profile**（基于内置 `web`/`headless` 模板扩展），通过四层 Patch 机制定制：`dsh --profile {platform} --dump-config` 可查看实际启动的整棵树，任何打印出来的行都可以用你自己的 patch 替换。层序：**profile 的 bundles → profile patch → home 级 patch → `--patch` 覆盖**。

平台定制点：① **选 profile**——在线交互用 `web` 模板扩展，批量/定时用 `headless`（无服务器单次运行器）；② **平台 bundle**——平台自研插件（多租户作用域、配额、审计转发、计量）打成 bundle 列入 profile；③ **home 级 patch**——按行 id 替换默认配置行（如替换默认 loop driver、compaction 策略）；④ **运行时 --patch**——租户/Agent 级覆盖（平台化扩展，用于灰度策略）。

## 3. 核心架构决策（ADR）

### ADR-001：以 dsh 为底座，不自建循环内核

- **背景**：初版设计曾计划自建 Agent Loop（turn/step、事件日志、恢复机制）。
- **决策**：直接以 dsh 的插件树为运行面底座；turn/step 生命周期、事件日志单一事实源、瀑布拦截、request-error 恢复全部复用 dsh。
- **理由**：① 事件日志单一事实源是"架构上不可能出现日志里重建不出来的模型输入"，自建要达到同等强度工程量大；② `Agent` 接口零循环依赖，循环本身可替换，自建价值低；③ MIT 开源可深度定制，不必重写。
- **影响**：团队工作量收敛到控制面与平台插件；运行时行为受 dsh 版本约束，需 M0 验证。
- **代价/风险**：dsh 是 developer preview，破坏性变更会传导到平台；必须锁定版本 + 插件快照并设升级门禁（见实施计划 R-1）。

### ADR-002：事件日志（SessionEvent）作为单一事实源

- **背景**：企业治理要求"任何模型输入都可追溯"，传统做法是分散的日志+审计双写，无法保证一致性。
- **决策**：以 dsh 追加式 `SessionEvent` 日志为唯一事实源；`deriveMessages()` 从日志投影模型历史；fork、resume、transcripts、遥测、持久化全部派生自同一条流。**平台审计 = 事件日志投影**，不另建"尽力而为"的审计链路。
- **理由**：dsh 的运行时不变式强制 "model-visible means logged"——到达模型请求的任何内容必须能从日志重建；`assistant/chunk` 保留原始流保证重放与 UI 保真，`assistant/message` 记录每次成功调用（含 usage 与 sourceEventSeqs）。
- **影响**：① 审计天然完整，不依赖双写一致性；② 事件存储成为核心资产，需设计分层归档（热/温/冷）；③ 计量（token 用量）从事件日志派生，与模型账单可对账。

### ADR-003：Loop 可替换，平台不绑定默认 driver

- **背景**：不同租户/任务对循环策略需求不同（严格审计型、快速迭代型、预算敏感型）。
- **决策**：平台面向 `Agent` 接口编程；`core/agent-loop` 默认 driver 可整体替换为平台自研 driver 或第三方 driver，UI、hooks、编排器均不感知。
- **理由**：dsh 的 `Agent` 接口零循环依赖，换 driver 不碰其他代码。
- **影响**：M0 需验证"换 driver 后事件域契约（session/*、agent/*、tools/*）不变"这一关键假设；事件日志语义是跨 driver 的稳定契约。

### ADR-004：插件即能力，按需装卸、快照锁定

- **背景**：dsh 的能力（goal/plan/todo/skill/subagent/sandbox/hooks/schedule/workflow/compaction/mcp/lsp/terminal/code-runtime/e2b/guard/acp/api/web 等）**全部是可装卸的插件**。
- **决策**：平台把"能力"建模为**插件清单**：每个 Agent 模板声明挂载哪些能力插件；平台发布时物化为确定的插件组合快照；卸载即解除副作用（registrations are effects that unwind when their plugin unloads）。
- **理由**：与"内置 + 钩子"模式不同，插件可装卸让能力面精确可控——安全敏感场景不挂 terminal/e2b，只读场景不挂写工具。
- **影响**：① 能力目录 = 插件清单（平台化扩展的"能力市场"）；② 插件版本必须随发布快照锁定，防止升级漂移；③ 新增能力 = 新增插件 + 快照回归。

### ADR-005：多租户以 Session/Agent 作用域为隔离边界

- **背景**：dsh 原生隔离粒度为 agent 作用域（core/scope 按 agent 作用域注册原语），无 `tenant_id` 概念；Agent 生命周期由 `AgentRegistry`（create/resume/register/get/list/roots）管理，Initiator 作用域按发起者隔离。
- **决策**：不试图让 dsh 感知租户，而是把租户隔离强制收敛到三条路径：
  1. **身份解析**（平台化扩展）：控制面签发 JWT → runtime 平台插件解析 tenant_id/user_id 写入上下文；
  2. **作用域命名**：Session/Agent id 携带租户前缀 `tenant_{id}_{agent_id}`，经 `SessionStore.enter()` + `AgentRegistry.enter()` 双检查并发进入唯一性（并发同 id 创建只有一个能进入，败者回滚）保证不串；
  3. **插件作用域**：平台自研插件（配额/审计/计量）在 `agent/*` 与 Capability 事件接缝上按作用域归属执行策略。
- **理由**：隔离逻辑收敛在少量代码路径上，可用代码审查 + 集成测试覆盖全部隔离面；不修改 dsh 核心。
- **影响**：任何新增资源类型必须在这三条路径之一登记隔离策略，否则不允许上线（写入开发规范）。

### ADR-006：事件日志重放/恢复能力是平台验收红线

- **决策**：把"任意 step 可从事件日志重建并重放"作为平台级验收项，贯穿 M0~M4 每个里程碑（详见实施计划）。dsh 的事件日志设计（append-only + deriveMessages + sourceEventSeqs）使重放成为架构特性而非附加功能。
- **影响**：M0 起建立"重放一致性测试"（日志投影 vs 实际会话行为逐事件比对），作为 CI 门禁。

## 4. 基于 dsh 真实机制的设计

### 4.1 插件树：Profile / Bundle / Patch

| 概念 | 机制（素材事实） | 平台用法 |
|---|---|---|
| **Profile** | 命名的组合（存在 Harness home），列出叠加的 bundles、树外插件、用户 `cordis.patch.yml`；`web` 与 `headless` 是内置模板 | 平台维护 `platform-web`、`platform-headless` 两个 profile |
| **Bundle** | Cordis 配置行 + 代码的分发格式，任何插入的东西都可被上层 patch 覆盖 | 平台插件打包为 bundle，随版本快照发布 |
| **Patch** | 按行 id 替换整个配置或插入新行；层序：profile bundles → profile patch → home patch → `--patch` | home 级 patch 固化基线，`--patch` 做租户灰度覆盖 |
| **dsh-base** | 每 profile 第一层：模型适配、工具、持久化、沙箱与审批策略、设置、凭据、遥测 | 平台不替换 base，只在其上叠加与覆盖 |

### 4.2 核心包职责（平台依赖的地基）

| 包 | 职责 | ctx key | 平台依赖点 |
|---|---|---|---|
| core/session | 追加式 `SessionEvent` 日志 + 内存存储 | `ctx.sessions` | 单一事实源、审计、回放 |
| core/system-prompt | Prompt 分区与工具 schema 组装 | `ctx.systemPrompt` | 租户级人格/技能注入的挂载点 |
| core/tools | 作用域工具注册 + 护栏执行管道 | `ctx.tools` | 租户工具白名单、审批拦截 |
| core/agent | `Agent` 接口、活体注册表、`agent/*` 事件 | `ctx.agents` | Agent 生命周期治理、作用域隔离 |
| core/agent-loop | 默认 driver（**可替换**） | `ctx.agentLoop` | 循环策略替换（ADR-003） |
| core/scope | 按 agent 作用域注册原语 | 库，无 key | 隔离边界基础 |
| llm/llm | 消息/流词汇 + 模型适配器接缝 | `ctx.llm` | 模型无关接入、路由、prefix-cache 优化 |

### 4.3 三层事件域（扩展点设计）

| 域 | 事件 | 用途 | 平台用法 |
|---|---|---|---|
| **Session 事件** | `session/event`（turn/*、step/*、user/message、assistant/*、tool/*） | 持久事实，append-only，**必须跨重载存活** | 审计、回放、计量、恢复（全部派生） |
| **Agent 事件** | `agent/*`（inbox、step、status、request、validation、continuation） | 活体协调：观察或拦截飞行中的工作 | 配额中间件、审批挂起、并发控制 |
| **Capability 事件** | `fs/*`、`tools/*`、`telemetry/*` | 把策略/适配器挂到接缝，不 import loop | 工具护栏、文件策略、遥测上报 |

**选域准则**（直接采用素材）：事实要跨重载存活 → Session 事件；要拦截飞行中的 Agent → `agent/*`；要给能力接缝挂策略 → capability 事件。

### 4.4 Turn / Step 生命周期（循环内核）

**一个 step = 一次模型请求 + 它调用的工具；一个 turn = 零或多个 step**——turn 打开于首个输入被认领，关闭于"无欠账"。

```text
turn/start
  claim 输入（next-step 输入 + 一条排队消息）
  组装 prompt 分区 + 工具 schema
  → agent/pre-step            # waterfall：拒绝(reject) 或 进入(enter)
  step/start
    输入以 user/message 追加 → 从日志派生模型历史（deriveMessages）
    agent/request → llm/stream → assistant/chunk* → assistant/message
    tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
  step/end
  · 工具还欠请求，或 next-step 输入到达 → claim → 下一 step
  → agent/turn-stopping       # 串行终检点
turn/end
```

平台治理语义：

- **step 是最小可审计单元**（一次请求 + 工具）——成本按 step 计、失败按 step 重试、审计按 step 追溯；
- **turn 是有界的**（有输入则开、无欠账则关）——配额/预算按 turn 结算，避免会话无限膨胀；
- 拒绝或首个 enter 为空 → 零 step 关 turn（日志记录这次尝试）；停止由代码验证而非模型自评（见 4.8 三硬边界）。

### 4.5 瀑布拦截点（策略挂载面）

监听者必须调 `next()` 委派；`agent/turn-stopping` 是串行、无 `next()`：

| 拦截点 | 拦截什么 | 平台策略挂载 |
|---|---|---|
| `agent/pre-step` | 模型这一步看什么 | 敏感信息过滤、租户上下文注入、compaction 压力检测 |
| `agent/request` | 请求构造 | 模型路由、token 上限、reasoning effort、租户配额 |
| `llm/stream` | 流式输出 | 用量采样、流审计 |
| `tools/pre-execute` → `execute` → `post-execute` | 工具执行前/中/后 | 权限与参数校验、高风险审批 → 沙箱强制、网络策略 → 结果审计、失败重试 |
| `agent/turn-stopping` | 是否结束（串行终检，无 `next()`） | 达标判定、三硬边界检查、交人通道 |

**pre-step 决策语义**（素材事实）：`{ kind: 'reject' }` 或 `{ kind: 'enter', messages }`——决定"模型这一步看到什么"；拒绝不保留已认领消息，插入的后续消息留给下一边界。

### 4.6 事件日志单一事实源 + deriveMessages

- **运行时不变式**："Model-visible means logged"——任何到达模型请求的内容必须能从日志重建；`deriveMessages()` 从日志投影模型历史，**fork、resume、transcripts、遥测、持久化全部派生自同一条流**；
- `assistant/chunk` 保留原始流（重放与 UI 保真）；`assistant/message` 记录每次成功调用（含 max-tokens 结束），空内容不进派生历史但事件保留用量与来源序列（sourceEventSeqs 精确指向构成它的 chunks）。

平台落地：审计查询、事故回放、账单对账均以 SessionEvent 为输入做投影，**不信任内存状态**。

### 4.7 失败恢复：request-error 瀑布 + compaction

- **agent/request-error 瀑布**：收到请求坐标 + 规范化失败事实 + 重试策略；监听者可返回 `{ kind: 'retry' }` 拥有恢复，否则保留原始错误；
- **compaction 插件**（dsh-compaction-basic）：用 `agent/pre-step` 做上下文压力检测、用 `agent/request-error` 处理规范溢出；触发后先做**工具结果剪枝**，再选**摘要**；剪枝或摘要推进了"代际替换"才开新重试 turn，否则原始错误保持权威；恢复窗口：**失败的 step 关闭之后、turn 关闭之前**。

平台落地：M0 验证 request-error 恢复语义与 compaction 代际推进；企业可在该接缝挂载自定义恢复策略（如重试降级到更小模型）。

### 4.8 三硬边界停止（代码验证，非模型自评）

| 硬边界 | 说明 | 平台化扩展 |
|---|---|---|
| **无进展检测** | 连续 N 轮无实质进展（无文件变更/无子目标达成）→ 停（判定见标准设计素材 §7.4） | 按 step 事件窗口的可编程检测 |
| **最大迭代** | 防死循环，超出即强制停止 | 按 turn/step 计数，租户级可配置 |
| **token 预算上限** | 成本硬边界 | 租户/Agent 双维度预算，超限由 `agent/turn-stopping` 强制停止并留档 |

### 4.9 AgentRegistry 生命周期（活体治理）

- **create/resume**：`ctx.agents.create()` / `resume()`（加载持久化会话，重铸作用域）——会话恢复、断线重连；
- **双检查进入**：`SessionStore.enter()` + `AgentRegistry.enter()`；并发同 id 创建只有一个进入，败者回滚——防并发重复启动；
- **register/get/list/roots**：注册表；roots = 无属主的活体根；运行时属主（`isOwnedBy`）与持久会话血缘独立——平台巡检孤儿活体、并发审计；
- **Initiator 作用域**：每个 driver 生命周期跑在发起者边界内，并行 driver 相互隔离——多租户并行任务隔离的天然基础；
- **AgentHandle**：`{ agent, dispose() }`——停 loop、等退出、注销、删会话、解作用域——平台 API 的"停止/删除"能力实现。

### 4.10 插件生态清单（能力目录）

素材快照的能力插件（全部可装卸）：goal（目标）、plan（计划）、todo、skill、subagent、sandbox、hooks、schedule（cron）、workflow、compaction（压缩）、mcp、lsp、terminal、code-runtime、e2b、spill、workspace、jobs、guard（护栏）、acp（Agent Client Protocol 桥）、api、web、client、sdk、boot、bundle、host。

平台能力目录（示例映射）：goal/plan/todo → 长任务治理；skill → 租户技能库；subagent/workflow → 子任务并行编排；terminal/code-runtime/e2b → 代码执行（沙箱策略按租户）；schedule → 定时任务（后台触发需处理非请求路径租户上下文）；compaction → 长会话成本治理；mcp → MCP 网关对接（§5.4）；guard/hooks → 护栏与预算；acp → 与外部 Agent 客户端互通。

## 5. 多租户与安全模型

### 5.1 租户隔离（三条强制路径，见 ADR-005）

```
路径① 身份解析【平台化扩展】:
  控制面签发 JWT { sub, tenant_id, role, exp, jti }
  → runtime 平台插件验签 → 写入请求上下文
路径② 作用域命名:
  Session/Agent id = "tenant_{tenant_id}_{agent_id}"
  → SessionStore.enter() + AgentRegistry.enter() 双检查唯一进入
路径③ 插件作用域:
  平台插件（配额/审计/计量）挂 agent/* 与 capability 事件，按作用域归属执行策略
```

**数据隔离矩阵**：

| 数据类型 | 存储 | 隔离机制 | 强制点 |
|---|---|---|---|
| 平台业务元数据（租户/用户/模板/发布） | PostgreSQL | 行级 `tenant_id` + 应用层强制过滤 | 控制面 Repository 基类 |
| SessionEvent 事件日志 | 事件存储（热 Redis / 冷对象存储） | 事件携带作用域归属；查询按作用域过滤 | 事件检索层 |
| 密钥/凭证 | 控制面密钥库（KMS 加密） | 按租户归属；明文不出平台 | 审批中心 + 网关 |
| 沙箱/代码执行 | 沙箱集群 | 每会话独立沙箱实例，网络策略按租户 | 平台 sandbox 插件 |
| 审计/计量 | PostgreSQL（追加写） | 全量记录 tenant_id | 审计查询强制过滤 |

### 5.2 审批【平台化扩展】

dsh-base 自带"审批策略"层；平台在其上建立企业审批中心：高风险工具调用（写操作/凭证相关）经 `tools/pre-execute` 拦截 → 生成审批票据 → 审批人（租户管理员/发起人）在 Web/IM 渠道审批 → 批准放行 / 拒绝返回错误 / 过期按拒绝处理 → 全程落审计（含审批人 identity），高危操作强制"他人审批"。

### 5.3 密钥与凭证【平台化扩展】

- 控制面密钥库（KMS 加密存储）统一管理模型 API Key、MCP 凭证；
- 发布物化时注入运行时，凭证不出平台边界；日志中无明文；
- 吊销走"新快照 + 主动失效"，不原地修改存量发布（对齐平台版本不可变原则）。

### 5.4 MCP 网关【平台化扩展】

dsh 的 mcp 插件负责 MCP 协议接入；平台侧增加 MCP 网关作为唯一入口：

```
Agent（dsh 插件树） ──MCP/HTTP──▶ MCP 网关 ──▶ 上游 MCP Server
  ① 协议适配（HTTP/SSE/Stdio 托管）  ③ 高风险写操作审批（挂起-回调）
  ② 按租户注入凭证（真实 Key 不出网关） ④ 全量审计 + 限流熔断
```

### 5.5 沙箱策略

| 环境 | 后端 | 说明 |
|---|---|---|
| 开发 | local | 本机直跑，仅开发用 |
| 测试/预发 | docker | 镜像白名单、资源限额 |
| 生产 | e2b（优先）/ docker（备选） | 每会话独立实例；网络出向白名单（仅 MCP 网关、模型端点） |

## 6. 可观测性与运维

### 6.1 事件日志即审计

- **审计完整性是架构特性**：`SessionEvent` append-only 保证所有模型输入/输出/工具调用/step 生命周期均有持久事实；
- **审计查询 = 事件投影**：按作用域/时间/step 过滤事件流，输出合规审计报告；
- **计量同源**：token 用量（assistant/message 的 usage）从事件派生，与模型账单对账（误差 <5% 为验收线）；
- **事故回放**：任意 step 可从日志重建现场；`assistant/chunk` 原始流保真 UI 重放。

### 6.2 遥测与告警

| 指标 | 来源 | 用途 |
|---|---|---|
| 成功率 / 平均 step 数 / 成本每任务 / 重试率 / 交人率 | 事件投影 | 平台健康度 |
| 事件写入延迟 / 存储增长 | telemetry/* 事件 | 存储容量规划 |
| 瀑布拦截命中率（审批/拒绝/过滤） | agent/* + tools/* | 治理有效性 |
| 沙箱隔离违规 / 凭证泄露扫描 | 平台插件 | 安全告警 |

### 6.3 事件存储分层

| 层 | 存储 | 保留策略 |
|---|---|---|
| 热（近期会话） | Redis/内存存储（core/session 默认） | 会话生命周期内 |
| 温（近 90 天） | 对象存储 + 索引 | 审计/回放 |
| 冷（归档） | 对象存储冷层 | 合规留存（按企业策略，如 1 年） |
