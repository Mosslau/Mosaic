# 企业级项目设计参考

- **文档类型**：跨项目设计参考（Handbook）
- **版本**：v1.0
- **日期**：2026-10-29
- **适用范围**：中大型、需长期维护、对稳定性有承诺的服务端项目
- **定位**：回答"一个企业级项目除了代码结构，还应该具备什么、每项怎么设计、怎么验收"

---

## 0. 怎么用这份文档

| 用法 | 场景 | 做法 |
|---|---|---|
| **设计评审清单** | 新方案/大改动的评审会 | 用附录 A 的 30 项逐条过一遍，缺项写进待办 |
| **新项目启动** | 从 0 到 1 | 按 §4 的 13 个能力域排期，先做"只做五件事"（§6） |
| **成熟度自评** | 季度复盘 | 对照 §5 的 L1–L4 定位当前级别，选下一级缺口 |
| **线上事故后复盘** | 事故根因分析 | 检查对应域是否有制度缺失（通常是可观测/发布/数据三域） |

**核心判断**：代码结构决定"好不好改"，13 个外部能力决定"敢不敢用"。

---

## 1. 全景：6 个内部结构 + 13 个外部能力

```
内部结构（决定可维护性）              外部能力（决定可信赖度）
├─ 1. 架构设计                       ├─ 1. 契约与演进
├─ 2. 封装与抽象                     ├─ 2. 数据与状态
├─ 3. 扩展性                         ├─ 3. 可靠性工程
├─ 4. 分层                           ├─ 4. 可观测与运维
├─ 5. 模块化                         ├─ 5. 安全与合规
└─ 6. 服务化                         ├─ 6. 性能与容量
                                     ├─ 7. 测试体系
                                     ├─ 8. 交付与发布
                                     ├─ 9. 配置与密钥
                                     ├─ 10. 文档与知识
                                     ├─ 11. 研发流程与治理
                                     ├─ 12. 成本与效率
                                     └─ 13. 团队与事故
```

**两者的关系**：内部结构做得好，改东西快；外部能力做得好，出问题能兜住。
**企业级的最低门槛**：内部结构达到"改动收敛"，外部能力达到 L3（§5）。

---

## 2. 内部结构（6 项，摘要）

> 这一层的详细设计见各项目的架构文档（如 [Python Runtime 重构计划](../python-agent-runtime/docs/Python-Agent-Runtime-重构计划.md)）。
> 此处只给**判据**，供评审时快速检查。

| # | 维度 | 判据（可检查） | 常见反例 |
|---|---|---|---|
| 1 | 架构设计 | 依赖方向单一；组合根唯一；有可执行的架构约束测试 | 函数内 import 绕过分层；两处手工装配 |
| 2 | 封装与抽象 | 抽象都有 ≥2 实现或测试替身；公共面无 `Any` | 每类一个 ABC；公共函数返回裸 `dict` |
| 3 | 扩展性 | 换实现改 ≤2 文件；加能力改 ≤3 文件 | 加一个 provider 要改 6 处 `if` |
| 4 | 分层 | 每层职责一句话说得清；无循环依赖 | "utils 层"人人依赖 |
| 5 | 模块化 | 单文件 ≤300 行；模块边界 = 变更边界 | 900 行的 `executor.py` |
| 6 | 服务化 | 进程模型清晰；无状态可扩；有探针与优雅停机 | API 里跑长任务；SIGTERM 直接杀 |

**内部结构的验收方式**：架构约束测试 + 静态度量（文件行数、`Any` 数、`except Exception` 数）+ 代码评审。

## 4. 逐域设计（13 域）

### 4.1 契约与演进

**目标**：任何一方升级，另一方不需要同时升级。

| 设计要点 | 具体做法 |
|---|---|
| 版本化 | 路径版本（`/v1`）+ 数据版本（`schema_version` 字段） |
| 加性演进 | 只加字段/事件，不删不改名；未知字段忽略 |
| 弃用政策 | `Deprecation` / `Sunset` 响应头 + 通知窗口（≥2 个发布周期或 90 天） |
| 兼容矩阵 | 滚动升级四象限（旧-旧 / 新-旧 / 旧-新 / 新-新）逐格验证 |
| 契约测试 | 每个端点/事件有快照测试，防"改了忘通知" |

**产物**：`docs/contracts/*.md`、`docs/deprecations.md`、契约快照测试
**验收**：旧客户端跑新服务不报错；任一弃用项都有替代方案与移除日期

---

### 4.2 数据与状态

**目标**：数据不丢、不乱、删得掉、恢复得了。

| 设计要点 | 具体做法 |
|---|---|
| 数据所有权 | 每类数据只有一个权威写入方（写进数据归属表） |
| 迁移 | 向前迁移 + 回滚脚本；expand → migrate → contract 三步，与发布解耦 |
| 生命周期 | 每张表/每个 Key 都有 TTL、归档或删除策略 |
| 一致性 | 幂等键；跨实体事务有明确边界；关键状态有对账任务 |
| 多租户 | Key/表/实例三级隔离，隔离级别写进文档 |
| 备份恢复 | 明确 RPO/RTO；每季度一次真实恢复演练 |

**产物**：数据归属表、`migrations/`、保留策略、演练记录
**验收**：能在 10 分钟内回滚一次迁移；能回答"这类数据多久删除"

---

### 4.3 可靠性工程

**目标**：单点故障不放大成全局故障。

| 设计要点 | 具体做法 |
|---|---|
| SLO + 错误预算 | 成功率/时延目标；预算耗尽 → 冻结功能发布 |
| 超时 | 每个外部调用都有上限（无超时=缺陷） |
| 重试 | 指数退避 + 抖动 + 只重试可重试错误（4xx 不重试） |
| 熔断/降级 | 连续失败快速拒绝；非核心链路可降级 |
| 限流/背压 | 429/503 + `Retry-After`；拒绝优于排队溢出 |
| 幂等 | 所有写操作可重复执行且结果一致 |
| 隔离 | 线程池/连接池/租户配额隔离，避免互相拖垮 |
| 演练 | 依赖故障注入、单 AZ 故障、容量突增 |

**产物**：`slo.md`、错误分类体系、故障演练记录、容灾预案
**验收**：随机杀一个依赖，核心链路错误率可控；单 AZ 故障不影响服务

---

### 4.4 可观测与运维

**目标**：5 分钟内知道"哪里坏了、影响多大"。

| 设计要点 | 具体做法 |
|---|---|
| 三支柱 | 结构化日志 + 指标 + 追踪，共享同一 request/trace id |
| 指标模型 | RED（QPS/错误/时延）+ USE（利用率/饱和度/错误） |
| 告警 | 分级（P1–P4）+ burn-rate（多窗口）+ 抑制与静默规则 |
| 看板 | 看板即代码（JSON 入库），服务级 + 租户级 |
| Runbook | 每个告警对应一份处置步骤，值班人可照做 |
| 复盘 | blameless；行动项有 owner 与期限 |

**产物**：OTel 接入、`alerts.yaml`、`dashboards/`、`runbook/*.md`、`postmortems/`
**验收**：值班人只靠看板和 Runbook 能定位一次 P2

---

### 4.5 安全与合规

**目标**：默认拒绝；一次事故不致命。

| 设计要点 | 具体做法 |
|---|---|
| 认证 | 服务间 mTLS 或 HMAC；用户侧 OIDC；无匿名内部接口 |
| 授权 | 最小权限 + 资源归属校验（每个读/写都校验 owner） |
| 密钥 | Secret Manager 注入；轮换不停机（双密钥并行） |
| 供应链 | 锁文件 + SBOM + 镜像签名 + 依赖漏洞扫描 + 许可证扫描 |
| 输入安全 | 请求体上限、SSRF/DNS 策略、路径穿越防护 |
| 数据保护 | PII 分类、脱敏、加密、最小化采集 |
| 审计 | 谁在何时做了什么；不可篡改；保留期符合合规 |

**产物**：认证/权限矩阵、`SBOM` 制品、`docs/security.md`、审计日志
**验收**：能回答"某个 CVE 我是否受影响"；能举证某次操作是谁做的

---

### 4.6 性能与容量

**目标**：知道瓶颈、知道扩容几台。

| 设计要点 | 具体做法 |
|---|---|
| 基线 | P50/P95/P99 + 吞吐 + 资源占用，每次发布对比 |
| 压测 | CI 冒烟（30 秒）+ 季度容量压测 |
| 容量模型 | `副本数 ≈ 到达率 × 平均处理时长 / (单实例并发 × 目标利用率)` |
| Profiling | CPU/内存/GC/连接池，热点有归属 |
| 缓存 | 命中率、失效策略、穿透/雪崩保护 |

**产物**：性能基线、压测脚本、容量公式、profile 记录
**验收**：回归 >10% 自动阻断；扩容决策有公式而非感觉

---

### 4.7 测试体系

**目标**：改动有安全网，失败路径被验证。

| 设计要点 | 具体做法 |
|---|---|
| 金字塔 | 单元为主（<10s 跑完）、集成为辅、E2E 极少 |
| 契约测试 | 端口/HTTP/事件：真实现与 fake 跑同一套断言 |
| 集成测试 | 真实依赖（compose / testcontainers），CI 可重复 |
| 属性测试 | 解析器、序列化、状态机用 hypothesis 覆盖边界 |
| 故障注入 | 超时、500、断连、部分失败 |
| 性能测试 | 冒烟纳入 CI，容量季度跑 |
| 数据管理 | 工厂 + 脱敏 fixture，不依赖生产数据 |

**产物**：测试目录规范、契约测试套件、覆盖率门禁（参考 85%，核心 95%）
**验收**：新功能 PR 必须同时含正向 + 失败路径用例

---

### 4.8 交付与发布

**目标**：随时能发；发坏 5 分钟能退。

| 设计要点 | 具体做法 |
|---|---|
| CI 六阶段 | lint → type → unit → integration → security → build |
| 制品 | 不可变镜像 + 语义化版本 + 签名 |
| 部署 | IaC（Helm/Kustomize）；环境差异仅配置 |
| 发布策略 | 灰度/金丝雀（1%→5%→50%→100%）+ 回滚触发条件 |
| 迁移解耦 | 先扩后缩（expand/contract），不要求同时发布 |
| 回滚演练 | 每季度一次，验证步骤而非纸面 |

**产物**：流水线配置、`Dockerfile`、`deploy/`、发布手册
**验收**：主干始终可发布；回滚演练有记录

---

### 4.9 配置与密钥

**目标**：一个镜像多环境运行，配置错误启动即暴露。

| 设计要点 | 具体做法 |
|---|---|
| 12-factor | 配置走环境变量；代码零硬编码 |
| 分组校验 | 按域分组；跨字段校验（如 TTL ≥ skew） |
| 敏感分离 | ConfigMap（非敏感）+ Secret（敏感），Secret 不入库不进镜像 |
| 变更审计 | 配置版本化、可回滚 |
| 默认值策略 | 新配置默认值 = 当前行为；危险默认值必须显式开启 |

**产物**：`.env.example`（逐项注释）、配置校验代码、配置变更记录
**验收**：同镜像可在 dev/staging/prod 运行；错误配置启动失败并给出可读原因

---

### 4.10 文档与知识

**目标**：文档不撒谎；新人 1 天能提 PR。

| 设计要点 | 具体做法 |
|---|---|
| 分层 | README（5 分钟上手）→ 架构 → ADR → Runbook → 参考手册 |
| **生成优先** | OpenAPI、事件表、指标表由代码生成，禁止手写副本 |
| ADR | 每个关键决策一页（背景/选项/结论/后果/复审条件） |
| 变更日志 | 用户可见变化；升级前能判断影响 |
| Onboarding | 一键起环境脚本 + 常见问题 |

**产物**：`README.md`、`docs/`、`adr/`、`CHANGELOG.md`、`docs/onboarding.md`
**验收**：文档中的命令可复制执行；事件/端点表与代码一致（CI 校验）

---

### 4.11 研发流程与治理

**目标**：质量靠制度，不靠个人。

| 设计要点 | 具体做法 |
|---|---|
| 分支与门禁 | 保护分支；必需 review + 必需 CI；禁止直推 |
| CODEOWNERS | 每个目录有 owner；评审 SLA（如 1 个工作日内） |
| 小 PR | <400 行、单一目的；模板强制填影响面 |
| 提交与版本 | 规范提交信息；语义化版本；自动 changelog |
| 技术债 | 预算约 20% 容量；登记在看板，可见可排期 |
| 依赖升级 | patch 周更、minor 双周；自动 PR + CI 验证 |

**产物**：`CODEOWNERS`、PR 模板、提交规范、Renovate 配置、技术债看板
**验收**：无 PR 能绕过 CI 合并；技术债条目有 owner 与优先级

---

### 4.12 成本与效率

**目标**：成本可归因、可优化、不突增。

| 设计要点 | 具体做法 |
|---|---|
| 单位成本 | 每千次请求/每 Run 成本；按租户归因 |
| 资源效率 | requests/limits 合理；长期低利用率有整改 |
| 外部调用成本 | 模型 token / 第三方 API 用量指标 + 突增告警 |
| 优化手段 | 缓存、批处理、预热、冷启动优化 |

**产物**：成本看板、用量指标、优化记录
**验收**：能回答"这个租户一个月花多少"；成本突增有告警

---

### 4.13 团队与事故

**目标**：任何时候有人负责；事故不重复。

| 设计要点 | 具体做法 |
|---|---|
| 值班 | on-call 轮值；5 分钟内响应；升级路径明确 |
| 事故分级 | P1（用户可见/数据风险）→ P4；分级决定响应速度 |
| 复盘 | blameless；根因 + 行动项 + owner + 期限 |
| 知识共享 | 设计评审、事故分享、值班交接清单 |

**产物**：值班表、事故手册、复盘文档、交接清单
**验收**：P1 事故有复盘且行动项闭环；新人能独立值班

## 5. 成熟度模型

| 级别 | 特征 | 典型缺口 |
|---|---|---|
| **L1 能跑** | 有 CI、有日志、手工部署 | 无 SLO、无告警、无回滚 |
| **L2 可运维** | 指标 + 告警 + Runbook + 镜像化 | 无灰度、无容量模型、无演练 |
| **L3 可信赖** | SLO/错误预算、灰度回滚、契约测试、供应链安全 | 自动恢复、成本归因、平台化 |
| **L4 卓越** | 混沌演练、自动扩缩、成本优化、自助平台 | —— |

**中大型项目的现实目标：L3。** 判据是四条：能承诺（SLO）、能证明（可观测+审计）、能安全地改（CI/灰度/回滚）、能恢复（备份/灾备/演练）。

---

## 6. 如果只能做五件事

| # | 事项 | 为什么优先 |
|---|---|---|
| 1 | **SLO + 告警 + Runbook** | 让"稳定"可度量、可响应 |
| 2 | **CI 门禁 + 不可变制品 + 回滚** | 把"能跑"变成"敢发" |
| 3 | **契约测试 + 版本化（含数据 schema）** | 防跨版本漂移，隐性成本最大 |
| 4 | **安全基线：认证/授权/密钥/供应链** | 一次事故抵多年投入 |
| 5 | **数据生命周期 + 备份恢复演练** | 删不掉、恢复不了最难补救 |

## 7. 常见误区

| 误区 | 后果 | 正解 |
|---|---|---|
| SLO 当 KPI 考核 | 隐瞒故障、数据造假 | SLO 是决策工具：预算耗尽冻结发布 |
| 只做 CI 不做 CD | 发布仍靠人 | 流水线 + 回滚演练 |
| 文档与代码两套 | 文档必然过期 | 由代码生成（OpenAPI/事件表/指标表） |
| 监控=告警 | 告警风暴 → 全部静音 | 分级 + burn-rate + 抑制 |
| 覆盖率当目标 | 测 getter 刷数字 | 关键路径清单 + 契约测试 |
| 一次大重构 | 无法回滚、周期失控 | 分阶段、每阶段可上线 |
| 安全最后补 | 架构级返工 | 认证/授权/密钥第一迭代定 |
| 没有 owner | 出问题无人认领 | CODEOWNERS + 值班表 |
| 灾备只有文档 | 真出事切不过去 | 每季度真实演练 |

## 8. 12 个月落地节奏

| 阶段 | 重点 | 产出 |
|---|---|---|

## 附录 A：评审清单（30 项）

**契约与数据**

- [ ] 对外接口有版本化方案（路径 + 数据 schema）
- [ ] 新字段为加性、默认关闭
- [ ] 每个数据有唯一权威写入方
- [ ] 迁移有回滚脚本，且与发布解耦
- [ ] 每类数据有 TTL/归档/删除策略
- [ ] 备份恢复有 RPO/RTO 且有演练记录

**可靠性与可观测**

- [ ] SLO + 错误预算已定义，且与发布流程挂钩
- [ ] 所有外部调用有超时；重试只针对可重试错误
- [ ] 有过载保护（限流或背压）
- [ ] 日志/指标/追踪共享关联 ID
- [ ] 告警分级 + burn-rate + 抑制规则
- [ ] 每个 P1/P2 告警有对应 Runbook

**安全与合规**

- [ ] 无匿名内部接口；资源有归属校验
- [ ] 密钥来自 Secret Manager 且可轮换
- [ ] SBOM + 镜像签名 + 依赖漏洞扫描
- [ ] 输入有大小上限；SSRF/路径穿越有防护
- [ ] 审计日志不可篡改、保留期符合合规
- [ ] 许可证扫描通过

**性能与测试**

- [ ] 性能基线存在且每次发布对比
- [ ] CI 内有冒烟压测，回归有阈值
- [ ] 容量公式可把负载换算成副本数
- [ ] 单元测试 <10s；契约测试覆盖关键端口
- [ ] 有故障注入用例（超时/500/断连）
- [ ] 覆盖率门禁（参考 85%，核心 95%）

**交付与治理**

- [ ] CI 六阶段全绿才能合并；主干可发布
- [ ] 镜像不可变、有版本号与签名
- [ ] 发布可灰度，回滚有演练记录
- [ ] 配置分组校验，错误配置启动即失败
- [ ] 每个目录有 CODEOWNERS；技术债有登记
- [ ] 值班表、事故分级、复盘机制存在

## 附录 B：参考数值（按业务调整）

| 项 | 参考值 | 说明 |
|---|---|---|
| 单文件行数 | ≤300 | 超过通常意味着职责过多 |
| 单元测试时长 | ≤10s | 超过会让人不愿跑 |
| 覆盖率 | 85% / 核心 95% | 是下限不是目标 |
| 提交接口 P95 | ≤500ms（本地受理） | 长任务必须异步 |
| 告警窗口 | 5m / 1h / 6h 多窗口 burn-rate | 减少误报 |
| 弃用通知 | ≥2 个发布周期或 90 天 | 取较长者 |
| 备份演练 | 每季度一次 | 真实恢复，不是纸面 |
| 技术债预算 | ~20% 容量 | 防止无限累积 |
| 依赖升级 | patch 周更、minor 双周 | 避免"三年不升" |

## 一句话总结

**内部结构决定"好不好改"，13 个外部能力决定"敢不敢用"。**

企业级的门槛不在写得多优雅，而在四件事：**能承诺（SLO）、能证明（可观测+审计）、能安全地改（CI/灰度/回滚）、能恢复（备份/灾备/演练）。**
