# 企业级高质量语料加工流水线

> 状态：⬜ 未开始
> 对应 roadmap 阶段：第 一 阶段
> 对应文档：`roadmap/大模型数据中心平台工程师.md`

## 目标

把**原始多源文本**变成**可训练、可入库、可追溯的高质量语料**：端到端输入是「原始文档集合（HTML/PDF/Markdown/JSONL/Wiki dump 等）+ 采集配置」，输出是「清洗去重后的语料分片 + 每片的 embedding 向量 + 一份可核对的加工报告（原始条数 → 清洗后条数 → 去重后条数 → 入库条数，各步剔除原因计数）」。

一句话可检验目标：**在 10GB 级原始文本上跑通「解析 → 清洗 → 去重 → 分片 → embedding → 落库」全链，并给出每步的计数与耗时，任何一步的产出可以被下游按 id 复现。**

（本项目是后续所有阶段的**数据入口**：02/03/05/07 消费的都是这里产出的语料与向量。）

## 技术栈

- 语言与运行时：Python 3.13（与 `pyproject.toml` 一致）、SQLite/PostgreSQL 之一作元数据表
- 数据处理：pandas（小批量校验）、PySpark（10GB 级分布式清洗；本机可用小样本模式验证逻辑，集群模式如实标注）
- 解析与清洗：BeautifulSoup/trafilatura（HTML）、PyMuPDF（PDF）、regex/unicodedata（规整）
- 去重：MinHash + LSH（手写实现，见「复用的算法实验」）、SimHash 作对照
- 分片与词元：tokenizer（tiktoken 或 HF tokenizers）、分片策略（按 token 数 + 重叠窗口）
- embedding：sentence-transformers / OpenAI 兼容 embedding 接口二选一（在线依赖标注「未在本环境验证」）
- 编排：Airflow 或 Makefile + 脚本（阶段一允许先脚本化，阶段七再接入统一编排）
- 观测：加工报告（Markdown + JSON）、结构化日志（每步计数与耗时）

## 系统架构

```text
        ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
原始源 → │ 采集/解析     │ → │ 清洗与规整    │ → │ 去重（MinHash）│
(多格式) └──────────────┘   └──────────────┘   └──────────────┘
                                                      │
                                                      ▼
┌──────────────┐   ┌──────────────┐   ┌──────────────────────┐
│ 加工报告      │ ← │ 元数据表      │ ← │ 分片 + embedding      │
│(计数/耗时/剔除)│   │(doc→chunk→vec)│   │(批量、可断点续跑)      │
└──────────────┘   └──────────────┘   └──────────────────────┘
                                                 │
                                                 ▼
                                        语料分片 + 向量（供 02/03/05/07 消费）
```

模块边界与关键决策：

| 模块 | 职责 | 关键设计点 |
|------|------|-----------|
| 采集/解析 | 按格式分发解析器，产出 `(doc_id, text, meta)` | 解析失败必须**计数 + 落死信**，不能静默丢 |
| 清洗与规整 | 去模板/去导航/去乱码/统一空白与编码 | 规则要**可配置且可回放**（同一输入同一输出） |
| 去重 | 文档级近重复 + 分片级重复 | MinHash 阈值可调；保留「保留哪一份」的规则与理由 |
| 分片 + embedding | 按 token 分片、批量向量化、可断点续跑 | 分片 id 稳定（`doc_id + 序号 + 内容哈希`），便于幂等重跑 |
| 元数据与报告 | 记录每步计数、耗时、剔除原因 | 报告数字必须与元数据表**逐项对账**（账要对得上） |

## 复用的算法实验

- [迷你 RAG 检索增强生成](../../../algorithms/05-generative/mini-rag/) —— 向量化与「检索口径」的源头；本项目的 embedding 产物必须能被它的检索链路直接消费（口径一致）
- [K-Means 聚类](../../../algorithms/02-statistical-ml/kmeans/) —— 语料主题分布抽样与去重后的覆盖度抽检（避免去重把某一类语料去没）
- [PCA 主成分分析](../../../algorithms/02-statistical-ml/pca/) —— embedding 降维可视化抽检（人眼确认向量空间没有塌缩）
- 去重算法（MinHash/LSH）本轮需**新增手写实验**：阶段一开工前应在 `algorithms/` 补一个 `05-generative/` 或新族下的 `minhash-dedup` 实验，或在实施笔记中记录「直接手写在项目内、后续回填为实验」——二者选一，不许留空

## 验收标准

- [ ] 能在 10GB 级原始文本（或等比例小样本 + 明确放大系数）上跑通全链，产出语料分片、向量与加工报告
- [ ] 加工报告的四个计数（原始/清洗后/去重后/入库）与元数据表逐项对账一致，且各步剔除原因有分类计数
- [ ] 去重可复现：同一输入两次运行得到相同的保留集合（幂等），并给出阈值与保留规则
- [ ] 分片 id 稳定：重复运行同一文档得到相同分片 id 与相同向量（可断点续跑、不重复入库）
- [ ] 存在质量抽检：随机抽 N 条入库语料，人工可核对「无残留模板/乱码/截断」，抽检结论写入报告
- [ ] 端到端耗时与吞吐有实测数字（条/秒、GB/小时），并标注硬件与本机/集群模式
- [ ] 依赖外部服务（embedding API / Spark 集群）的部分如实标注「未在本环境验证」并给出复现命令

## 实施笔记

- **2026-09（梳理阶段）**：本项目定位为「整条链路的**数据入口**」，因此验收标准里刻意加了两条「对账」与「幂等」——它们是后续 03（湖仓）与 07（整合）能否复算的前提。阶段一允许先用脚本编排（不引入 Airflow），到阶段七再统一。
- **2026-09（待验证假设）**：① 10GB 在本机是否可行——先用 1GB 小样本验证逻辑与内存曲线，再决定是否需要 Spark 或分块流式处理；② embedding 走本地 sentence-transformers 还是在线 API——前者可离线可复现、后者质量更高但引入外部依赖，实施时先本地跑通再对照。
- **已知边界**：本项目不做语料质量建模（那属算法侧），只做「可复现的加工 + 可核对的计数」；语料的法律与合规校验（版权/隐私）在阶段七的治理部分统一处理。
