## 1. 设计目标与原则

**目标**：对标腾讯云 WeData / 阿里云 DataWorks 的能力集，以"成熟开源集成 + 薄自研胶水"构建企业级 Data+AI 数据平台。

**核心判断**：不要自研平台，要集成平台。WeData / DataWorks 自研控制面是因为它们是商业产品；而它们底下的能力（集成、调度、元数据、质量、BI）在开源生态里已有同等成熟度的项目。我们的工作是把它们**装起来 + 打通 + 补齐契约**。

### 1.1 四条建设原则

| 原则 | 含义 |
|---|---|
| 底层核心引擎能用成熟开源就不自研 | 集成、调度、存储、计算、元数据等核心引擎，先找 Apache 顶级项目/行业事实标准 |
| 系统入口必须自建 | 统一 WebUI 门户 + 开放 API 是平台的脸面与用户契约，自己掌握；开源引擎自带的 UI 只作内部控制台，不对最终用户暴露 |
| 其余自研只做"胶水" | 只写开源之间缺失的粘合层，且必须薄（§4） |
| 每期可验证 | 每期都有具体命令/数据级的验收，不接受"基本可用" |

技术栈基调：**Java 为主**（平台与控制面）· **Python 为辅**（质量校验、AI、数据科学）。

### 1.2 企业级判据

**结构判据**（判断架构是否成立，超越功能清单）：

| 判据 | 不成立时的样子 |
|---|---|
| 统一目录是单一真相源 | 又一个元数据孤岛 |
| 治理内建在流水线里（不通过即阻断） | 事后外挂的补丁 |
| Data 与 AI 真正共栈（特征/权限/血缘打通） | 两套系统各玩各的 |
| 开放性（开放表格式 + 开放 API） | 被单一厂商锁定 |

**横切判据**（每个模块都要过线，否则不是企业级）：

| 判据 | 不过线的后果 |
|---|---|
| 多租户与配额 | 一个烂任务拖垮全平台 |
| 发布治理（dev/prod/版本/回滚） | 改错一个任务直接污染生产 |
| SLA 基线 | 产出迟到无人知、无人担责 |
| 审计合规 | 金融 / 政企场景不可上线 |
| 成本可算 | 平台变成无主的成本黑洞 |
| 开放 API | 平台变孤岛，无法嵌入企业流程 |

**模块建设顺序的设计哲学**：管理中心 → 集成 → 建模/标准 → 开发 → 运维 → 治理 → 消费——**底座先行、标准先行、治理贯穿**，而不是"先跑通再补治理"。因此发布、基线、标准、多租户这四件事不等晚期，最小版直接进 P1/P2。

## 2. 总体架构

### 2.1 架构图（结构视图）

```text
┌─ 系统入口（自研，见 §4）──────────────────────────────────────────────┐
│  【自研】统一门户 WebUI · 开放 API（由控制面的查询网关承载）           │
├─ 内部控制台（开源自带 UI，仅运维/管理员，不对最终用户暴露）───────────┤
│  DolphinScheduler UI · StreamPark UI · DataHub UI · Superset          │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 控制面（集成成熟开源 + 5 块自研胶水）─────────────────────────────────┐
│  编排/调度/补数  Apache DolphinScheduler（唯一编排器）                 │
│  实时作业托管    Apache StreamPark（被 DS 经 OpenAPI 启停）            │
│  元数据/血缘     DataHub                                               │
│  质量规则        SQL 规则（调度执行）+ Great Expectations（补强）      │
│  指标语义        【自研】metric_def + MQL→SQL（Apache Calcite）        │
│  查询网关        【自研】Spring Boot（鉴权/限流/审计）                 │
│  配置生成        【自研】YAML → SeaTunnel/Flink/Spark 作业配置         │
│  元数据上报      【自研】作业血缘 → DataHub                            │
│  契约           【自研】信封 / 命名 / DLQ 原因枚举                     │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 数据面（全部成熟开源）────────────────────────────────────────────────┐
│  集成    Apache SeaTunnel(Zeta)   ← 离线 + 实时 + CDC 统一入口         │
│  有界任务 DolphinScheduler Worker（SQL / Shell / Spark / SeaTunnel）   │
│  无界作业 StreamPark 托管的 Flink / Spark 长驻作业                     │
│  AI 计算  Ray（批量推理 / embedding / 多模态预处理，P5 启用）          │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 存储 ─────────────────────────────────────────────────────────────────┐
│  Kafka 总线 · Iceberg+MinIO 湖 · Apache Doris 仓 · PostgreSQL · Redis  │
│  Milvus 向量库（P5，AI 问数 / 检索）                                   │
└────────────────────────────────────────────────────────────────────────┘

横切：Prometheus + Grafana + OTel（可观测）· DataHub（元数据中枢）

注：图中箭头为管控下发方向；数据不经过控制面，数据的读写路径见 §2.2 数据流视图。
```

两条读图要点：

1. **入口与控制面分离**：最终用户只面对自研门户 WebUI 与开放 API；开源引擎自带 UI 全部降为内部控制台（原则 2 的落地）。
2. **关键结构差异（对照商业平台）**：控制面 = 成熟开源（调度/元数据/质量）+ 5 块自研胶水；而商业平台是整个控制面自研。

### 2.2 端到端数据流视图

上面的架构图是**结构视图**（系统分几层、每层装了什么）；本图是**行为视图**——一条数据从源到消费的完整旅程：

```text
数据源（业务库 CDC / 消息流 / 文件 / API）
    │  ① 统一信封（§5.1）：payload 保持源原貌 + event_time/ingest_time 双时间
    ▼
Kafka 总线（主题按 §5.2 命名族）───────────────────────────┐
    │                                                     │
    ├─ ②a 实时加工：Flink 长驻作业（窗口/状态/CEP）          │
    │      消费 Kafka → 实时清洗/聚合 → 写 Iceberg / Doris   │
    │                                                     │
    ▼ ②b 集成入湖：SeaTunnel（批/流/CDC 统一入口）          │（纯批量源可不过总线，直拉入湖）
Iceberg ODS ──► DWD ──► DWS     （湖内分层，底座与真相源）
    │    离线批加工走模板 A（Spark）；实时作业由模板 B/C 守护
    │    质量规则内建于两条链路，不过即阻断
    ▼ ③ 物化
Doris DWS/ADS（serving 加速层，任何一张表可从湖重建）
    │
    ▼ ④ 语义与服务（自研块 #4/#5）
指标语义层（MQL→SQL，口径唯一）──► 查询网关（鉴权/限流/审计）──► 业务系统 / Superset
    │
    ▼ ⑤ AI 工程化（P5）
NL→MQL（LLM 只产 MQL，不产 SQL）→ 语义层 → 与任何出口一致的答案

横切：每一跳的血缘 → DataHub；每一跳的质量 → SQL 规则阻断；每一跳的成本 → 归因
```

两条读图要点：

1. **湖是必经站**：实时（②a Flink）和离线（②b SeaTunnel + Spark）都在 Iceberg 分层里汇合（§5.5 任务归属规范），Doris 只是下游物化——这是"离线实时一个平台"在数据流上的样子。
2. **语义层是唯一出口**：报表、API、AI 问数都经 MQL→SQL 取数，没有第二条路——这是"同一指标任何出口答案一致"（⑦）在数据流上的样子。

### 2.3 控制面与数据面

```text
控制面负责"管控"：决定谁能用、怎么用、用多少、是否合规、是否稳定。
数据面负责"执行"：真正的数据接入、计算、存储、查询和 AI 服务执行。
```

这样架构才从"项目系统"升级为"平台系统"。控制面 12 个中心的职责细分：

| 中心 | 职责 |
|---|---|
| 权限中心 | 用户、角色、组织、租户、行列级权限、AI 工具调用权限 |
| 配置中心 | 服务配置、规则配置、灰度配置、告警阈值配置 |
| 元数据中心 | 表、字段、任务、接口、指标、模型、知识库元数据 |
| 指标中心 | 指标口径、指标版本、指标审批、实时/离线一致性 |
| 任务调度 | 离线任务、数据同步、质量检查、模型评测任务 |
| 数据质量 | 空值率、唯一性、完整性、时效性、波动检测、Schema Drift |
| 血缘中心 | 表血缘、字段血缘、任务血缘、指标血缘、AI 数据来源追踪 |
| 审计中心 | 数据访问审计、接口调用审计、AI 问答审计、权限变更审计 |
| 告警中心 | 任务失败、数据延迟、Kafka 积压、Flink 异常、模型异常 |
| 资源中心 | K8s 资源、队列资源、存储配额、计算资源、租户隔离 |
| 模型中心 | Prompt 版本、模型路由、RAG 评测、Embedding 管理、LLM Gateway |
| 成本中心 | 存储成本、计算成本、查询成本、模型调用成本、Token 成本 |

数据面各组件的执行职责细分：

| 组件 | 职责 |
|---|---|
| SeaTunnel（Zeta） | 数据集成的执行引擎：批/流/CDC 作业的实际读写、断点续传、脏数据输出 DLQ |
| DolphinScheduler Worker | 有界任务的实际执行：`sql` / `shell` / `python` / `spark` / `seatunnel` 任务 |
| Flink / Spark 长驻作业 | 无界流作业的实际运行：状态管理、窗口计算、checkpoint/savepoint（生命周期由 StreamPark 托管） |

两条要点：

1. **中心 ≠ 组件**：控制面按逻辑职责单元（中心）切分，与实现组件是多对多关系——如元数据中心与血缘中心都由 DataHub 承担，权限中心由 DS 权限、查询网关、Doris 行列权限共同分担；数据面按物理执行组件切分，组件即职责、一一对应。
2. **存储层不在数据面职责表内**：它是数据面读写结果的承载（职责与选型见 §3 ②），不是执行者；控制面的管控指令经各组件的管理接口下达（编排器 DS 经 OpenAPI 启停 StreamPark，见 §2.1 与 §5.5 模板 B/C）。

### 2.4 多租户模型（最小集，四层对齐）

平台会被多个团队/业务线共用。多租户模型回答一个问题：不同团队在同一个平台里，怎么互相看不见、互不干扰？**前期不做隔离功能，但隔离的"形状"必须在架构期定死**——下面四个隔离单位是建表、建项目时的物理边界：表一旦按 `order` 而不是 `biz.order` 建出来，日后再补隔离等于全量表迁移，改造成本极高。

| 层 | 隔离单位 | 含义 |
|---|---|---|
| DolphinScheduler | 租户 / 项目 | 一个团队 = 一个项目，任务与工作流互不可见 |
| DataHub | domain | 一个团队 = 一个域，元数据资产各看各的 |
| Iceberg | namespace | 一个团队的湖表放一个命名空间 |
| Doris | database | 一个团队一个库 |

两条边界说明：

1. **本模型只管"隔离"，不管"配额"**——计算/存储配额随 P3 资源中心一并设计（职责见 §2.3）。
2. **落地时点**：P3（§6），验收为 V30——建第二个租户，其任务、元数据、湖表、仓表对第一个租户不可见，四层各验一次。

### 2.5 可用性与容灾（组件能力口径）

**原则**：平台的可用性与容灾**建立在所选组件的原生能力之上，不自研容灾机制**。本节只确认一件事：每个组件都具备高可用与数据保护能力——将来部署形态从单机（P0 PoC）演进到多副本（生产 K8s）时，**不需要更换任何组件**。

| 组件 | 高可用（服务不死） | 容灾与数据保护（数据不丢、可恢复） |
|---|---|---|
| Kafka（KRaft） | 多 broker + 分区副本（ISR） | 副本同步、offset 重放 |
| Flink | JobManager HA（K8s 部署）+ checkpoint 恢复 | checkpoint / savepoint（状态精确一次） |
| SeaTunnel（Zeta） | Master/Worker 容错，作业自动 failover | checkpoint 恢复、断点续传 |
| Iceberg + MinIO | MinIO 分布式多节点（纠删码） | Iceberg 快照与时间旅行；MinIO 版本控制/对象锁/站点复制 |
| Doris | FE 多副本（Leader/Follower/Observer）+ BE 多副本 | 数据多副本；backup/restore 到对象存储 |
| PostgreSQL | 主备流复制 | PITR（WAL 归档） |
| Redis | 哨兵 / Cluster | AOF/RDB 持久化 |
| DolphinScheduler | 多 Master/Worker（注册中心选主） | 元数据存 PostgreSQL，随其备份 |
| StreamPark | 无状态应用层，可多实例（前置 LB） | 元数据存数据库；作业状态在 Flink 侧（savepoint） |
| DataHub | 多实例（前置 LB） | 元数据存 MySQL/PG + ES，随其备份 |
| Ray / Milvus（P5 引入） | Ray worker 故障自动重建；Milvus 多副本（K8s Operator） | Ray 任务级重试；Milvus Backup 备份至对象存储 |
| 自研组件（门户/网关/胶水） | 无状态化设计，K8s 多副本 | 状态只存 PG / Redis / 对象存储，继承上表能力 |

两条约定：

1. **自研组件一律无状态**——状态只存 PostgreSQL / Redis / 对象存储，可用性与容灾能力随之继承，自研件自身不需要任何容灾设计。
2. **统一备份策略后置，但原语已就位**——各组件的快照/复制/PITR 能力以本表为准（选型已确认）；统一的备份策略与恢复演练在生产化（K8s 多副本部署）阶段设计，不在 P0–P5 范围。

## 3. 能力域与选型

平台能力划分为八大能力域，自下而上：

```text
┌─────────────────────────────────────────────────────────────────┐
│ ⑧ AI 工程化    特征平台→训练→模型管理→推理服务→LLM 应用(RAG/Agent)│
├─────────────────────────────────────────────────────────────────┤
│ ⑦ 语义与服务   指标层 · 标签层 · API 服务 · BI                   │
├─────────────────────────────────────────────────────────────────┤
│ ⑥ 数据治理     质量 · 血缘 · 安全 · 成本          (控制面核心)    │
├─────────────────────────────────────────────────────────────────┤
│ ⑤ 开发工作台   SQL/管道 IDE · 调度 · 调试 · 版本管理              │
├─────────────────────────────────────────────────────────────────┤
│ ④ 统一目录     表/模型/特征/指标 —— Data+AI 一个 Catalog          │
├─────────────────────────────────────────────────────────────────┤
│ ③ 计算引擎     批流一体(Spark/Flink) · OLAP(Doris) · AI(Ray)     │
├─────────────────────────────────────────────────────────────────┤
│ ② 存储底座     湖仓一体(Iceberg + 对象存储)                       │
├─────────────────────────────────────────────────────────────────┤
│ ① 数据集成     批 / 流 / CDC / 文件 / API 全域接入                │
└─────────────────────────────────────────────────────────────────┘
        横切: 可观测性 · 多租户与权限 · 开放 API · 部署运维(K8s)
```

**选型标准**：① Apache 顶级项目或行业事实标准；② 有商业公司或大厂背书；③ 社区活跃（近半年有 release）；④ Java 生态优先。

### ① 数据集成

**职责**：把所有形态的数据接进来——这是平台的"进口"，决定了平台能吃多大的世界。

| 接入形态 | 说明 | 代表实现 |
|---|---|---|
| 流式 | 消息队列/设备上报，秒级 | Kafka、Pulsar；Flink CDC |
| 批量 T+1 | 业务库定时抽取 | SeaTunnel、DataX |
| CDC | 数据库变更捕获，分钟级 | Flink CDC、Debezium、Canal |
| 文件 | Excel/CSV/日志/报表 | 自研文件服务 + 对象存储 |
| 多模态 | 图片/音频/视频 | 对象存储 + 元数据管道 |
| API/SaaS | 第三方系统拉取 | Airbyte（300+ 连接器） |

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| **数据集成** | **Apache SeaTunnel 2.3.x（Zeta 引擎）** | DataX（仅离线）/ Flink CDC | Apache TLP；**~200 连接器**；批/流/CDC 一体；**逐 job 连接器依赖隔离** |
| CDC 采集 | **Flink CDC 3.x** | Debezium + Kafka Connect | Apache；全量+增量无缝一体（事实标准） |

**企业级要求**：接入任务可配置化（非硬编码）、断点续传、脏数据隔离（DLQ）、接入审计、Schema 契约管理。

### ② 存储底座

**职责**：一份数据、多处可用——湖仓一体是企业级的共识答案。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 湖表格式 | **Apache Iceberg 1.6+** | Hudi / Paimon / Delta | 开放表格式事实标准（Netflix/Apple/AWS）；ACID、Schema 演进、时间旅行、隐藏分区 |
| 对象存储 | **MinIO** | Ceph / 云 OSS / S3 | S3 兼容事实标准 |
| OLAP 仓 | **Apache Doris 2.x** | ClickHouse / StarRocks | Apache TLP；MySQL 协议；运维简单；Unique Key 支持 upsert |
| 交互查询（湖上） | **Trino** | Spark SQL | 联邦查询事实标准（可选） |
| 平台元数据库 | **PostgreSQL 16** | MySQL | —— |
| 缓存 / 状态 | **Redis 7** | —— | —— |

**数据分层**：ODS → DWD → DWS → ADS（+ DIM），行业通用数仓方法论。

**关键认知**：湖（Iceberg）是**底座与真相源**，OLAP 引擎（Doris）是 **serving 加速层**——两者不是竞品，是分工。明细入 Iceberg（湖保历史可重放），聚合作 Doris（仓保查询性能）。平台成熟度的标志之一是"任何一张服务层的表都能从湖仓重建"。

**企业级要求**：开放表格式（不锁定）、存储计算分离、分层生命周期（热温冷）、小文件治理、表级 owner/SLA 元数据。

### ③ 计算引擎

**职责**：三类负载，三类引擎，各司其职。

| AI 计算 | **Ray** | —— | Python 原生分布式（训练/批量推理/embedding/多模态） |
| ML 训练 | PyTorch | TensorFlow | GPU 框架事实标准 |

**关键认知**：Ray 与 Flink/Spark **不是并列的第三数据引擎**——Flink/Spark 算数据，Ray 算模型。Ray 服务 AI 层：批量推理、embedding 生成、超参搜索、多模态预处理。

**企业级要求**：批流一体（同一 SQL 语义）、资源隔离与弹性（K8s/Yarn）、作业全生命周期管理（提交/监控/savepoint/版本）、计算成本可归因。

**职责**：Data+AI 一个 Catalog——表、文件、模型、特征、指标，一处注册、处处可见。**这是平台的心脏，也是"项目"与"平台"的分水岭。**

## 5. 契约、规范与工作流模板（自研块 #1）

### 5.1 统一事件信封

所有源进总线前转成它（由配置模板固化，不靠人自觉）：

```json
{
  "envelope_version": "1",
  "source": "biz-mysql",
  "source_type": "cdc",
  "tenant": "biz",
  "entity_type": "order",
  "entity_id": "1001",
  "event_type": "updated",
  "event_time": "2026-09-24T10:15:30Z",
  "ingest_time": "2026-09-24T10:15:31Z",
  "idempotency_key": "cdc:biz-mysql:orders:1001:u:1727080530123",
  "payload": { "…源字段原样…" }
}
```

两条铁律：`payload` **保持源原貌**；`event_time` 与 `ingest_time` **必须都留**（否则分不清"数据延迟"和"源时钟不准"）。

### 5.2 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 主题 | `{env}.{source_type}.{source}.{entity}.v{major}` | `prod.cdc.biz-mysql.order.v1` |
| DLQ 主题 | `{env}.dlq.{source}.{reason}` | `prod.dlq.biz-mysql.schema_mismatch` |
| 湖表 | `{layer}_{entity}_{suffix}` | `ods_order_event` / `dwd_order_event` |
| 仓表 | `{layer}_{entity}_{grain}` | `dws_order_1m` / `ads_order_daily` |
| 工作流 | `ws_{产出表名}` | `ws_dwd_order_detail_di` |
| 任务（工作流内节点） | `{产出表名}` | `dwd_order_detail_di` |
| 作业 | `{env}-{source}-{entity}` | `prod-biz-mysql-order` |
| 指标 | `{domain}_{measure}_{grain}` | `order_amt_1d` |

### 5.3 DLQ 原因枚举

`parse_error` · `schema_mismatch` · `validation_error` · `auth_error` · `overflow`
（分原因是**为了排查路径不同**；不要只存 error 字符串）

### 5.4 参数规范（可重入 + 可补数的前提，必须写死）

| 规则 | 要求 |
|---|---|
| 分区字段 | **只能**来自 `${system.biz.date}` / `${system.biz.curdate}`，**禁止硬编码日期** |
| 湖表写入 | 用**动态分区覆盖**语义，**不用 append** |
| 任务可重入 | 同一天跑两次，结果必须完全相同 |

做到这三条，DS 的「补数」对 Iceberg 就自然成立——补数无非是拿另一个日期参数重跑一遍。

### 5.5 三种工作流模板（照抄，别每次从零拖）

模板是契约与规范在调度层的投影——信封、命名、幂等规则在这里落成可照抄的 DAG。

**任务归属规范（拖模板之前先过这张表）**：判断一个任务该由谁执行，只看一个问题——**这个任务跑完会退出吗？**

| 跑完会退出吗 | 任务在干什么 | 归属 |
|---|---|---|
| **会**（有界） | 搬数据 / SQL 计算 / 跑脚本 / 调外部 API（含启停实时作业） | DolphinScheduler |
| **不会**（无界） | Flink/Spark 长驻作业 | **StreamPark**（DS 侧只留一个 `http` 守护任务，即模板 C） |

三条推论：

1. **实时链路里也有"有界"任务**——CDC 首次全量初始化、每日维表刷新、实时产出后的质量校验。它们归 DolphinScheduler。
2. **离线链路里也可能有"无界"任务**——少见但存在，比如常驻的日志收集。它们归 StreamPark。
3. 所以**"离线/实时"不是归属依据，"有界/无界"才是**——实时和离线不分成两个平台，只分成两种"任务形态"。依据是湖表为两者共同的接口：实时写进 `dwd_order_detail_di`，离线要重跑修正它，这两件事必须落在同一个血缘图里才自洽。

**模板 A · 离线批链路**

```text
1. seatunnel   MySQL → Iceberg ods_order_di（按 ${system.biz.date} 分区）
2. spark       去重 / 清洗 → ods_order_di_clean
3. sql         质量规则 → 输出 OUT 参数 passed = true / false
4. conditions  passed ─┬─ true  → 结束（下游 dependent 任务自动触发）
                       └─ false → 告警 + 阻断下游
```

**模板 B · 实时链路首次启动**（一次性）

```text
1. seatunnel   建 Iceberg 表 / 首次全量初始化
2. http        POST StreamPark 启动 CDC 作业（幂等）
3. http        POST StreamPark 启动下游实时作业
4. http        健康检查，确认 RUNNING
```

**模板 C · 实时守护**（每 5 分钟）—— ⭐ **这个模板是"离线实时一个平台"成立的关键**

```text
1. sql     抢分布式锁（防止并发触发拉起两个实例）
2. http    GET StreamPark 查作业状态
3. switch  RUNNING ─┬─ 是 → 结束
                    └─ 否 → 下一步
4. http    POST StreamPark 拉起（幂等）
5. 告警
```

模板 C 把"实时作业还活着吗"变成了**一个有界任务**。这一招让实时和离线在 DolphinScheduler 里终于是同一个运维视图：同一个工作流列表、同一套告警、同一套权限、同一套审计。模板 C 在 P1 跑通的那一刻，就是"离线实时一个平台"成立的证据（V9，见 §7）。

**衔接三条规则**（模板 B/C 共同遵守，也是"DS → StreamPark OpenAPI"衔接接口的操作约束）：

1. **不要用 DS 的 `flink` 任务类型提交长驻作业。** 它的语义是"提交并等结果"，会占死一个 worker。
2. **启动编排进 DAG，运行守护也进 DAG，但重启决策归 StreamPark。** DS 只管"它该在跑"和"不在就拉起"，不管"为什么挂了"。
3. **所有启停必须幂等。** 前置一个 `sql` 任务抢分布式锁（模板 C 第 1 步），或依赖 StreamPark 的重复启动保护——否则补数/重跑会拉起第二个作业实例。

## 9. 风险与取舍

| # | 风险 | 对策 |
|---|---|---|
| 1 | **开源拼装的"最后一公里"比想象重**（各项目元数据不通） | 自研块 #3（元数据上报器）优先做；先打通 1 条血缘，再铺开 |
| 2 | **SeaTunnel 驱动/版本兼容** | P0 就验证（V7）；锁版本，建兼容矩阵 |
| 3 | **DataHub 部署重**（多组件） | P0 只验采集能力；完整部署放 P3；或用 OpenMetadata 替代 |
| 4 | **内存预算**（旧项目踩过） | V6 门禁卡住，先算后起 |
| 5 | **小文件**（流式入湖必踩） | compaction 作业在 P1 就要有 |
| 6 | **质量规则阻断误伤生产** | 规则分级 warn/error/**block**，只有核心用 block |
| 7 | **AI 问数不准就上线** | P5 强制评测集门槛（≥80%）才允许上线 |
| 8 | **过度自研**（不知不觉又造引擎） | 严守 §4 的自研边界（1 个入口 + 5 块胶水），新增自研需评审 |
| 9 | **Doris vs ClickHouse 选错** | P0 用 V3 实测同数据量下的写入与查询表现再定 |
| 10 | **契约漂移**（各源自己造信封） | 信封由**配置模板固化**，不靠人自觉 |
| 11 | **dev/prod 发布靠人工导出导入，可能错配数据源/参数** | 发布 SOP + 发布后自动校验脚本（对比两环境任务定义与数据源指向差异）；先人工后工具 |

### 三个关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 总线 | **Kafka**（若已有 RocketMQ 则复用） | offset 重放 + compacted topic + 生态最广；纯批量源可不过总线 |
| 湖 vs 仓 | 明细入 **Iceberg**，聚合入 **Doris** | 湖保历史可重放，仓保查询性能 |
| 自研 vs 开源 | **核心引擎开源优先；自研 = 1 个入口 + 5 块胶水** | 商业平台的"控制面全自研"是其产品属性，不是我们的必要成本；但系统入口（WebUI/开放 API）是用户契约，必须自建 |
