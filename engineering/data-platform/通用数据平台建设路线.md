## 1. 建设思路

### 核心判断

**不要自研平台，要集成平台。** WeData / DataWorks 之所以是自研控制面，因为它们是商业产品；而它们底下的能力（集成、调度、元数据、质量、BI）在开源生态里**已经有同等成熟度的项目**。我们的工作是把它们**装起来 + 打通 + 补齐契约**。

### 三条原则

| # | 原则 | 含义 |
|---|---|---|
| 1 | **能用成熟开源就不自研** | 每个能力先找 Apache 顶级项目/行业事实标准 |
| 2 | **自研只做"胶水"** | 只写开源之间缺失的粘合层，且必须薄 |
| 3 | **每期可验证** | 每期都有具体命令/数据级的验收，不接受"基本可用" |

### 与商业平台的对应关系

| WeData 模块 | 我们的实现 |
|---|---|
| 数据集成 | SeaTunnel（引擎）+ 自研配置生成 |
| 数据开发 | DolphinScheduler + StreamPark（可选） |
| 调度 | DolphinScheduler |
| 元数据中心 + 数据资产 | DataHub / OpenMetadata |
| 数据质量 | SQL 规则 + 调度器执行（+ Great Expectations 补强） |
| 数据安全 | Apache Ranger（后置）/ 平台内 RBAC |
| 数据服务 | Spring Boot 查询网关 + Superset |
| 语义建模 | **自研薄层 + Apache Calcite**（差异化核心） |
| 治理中心 | DataHub + Grafana 大盘 |

## 2. 开源选型总表

**选型标准**：① Apache 顶级项目 或 行业事实标准；② 有商业公司或大厂背书；③ 社区活跃（近半年有 release）；④ Java 生态优先。

### 2.1 存储与计算

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| 消息总线 | **Apache Kafka 3.x（KRaft）** | RocketMQ 5.x / Pulsar | Java/Scala | 流式事实标准；KRaft 后免 ZooKeeper |
| 湖表格式 | **Apache Iceberg 1.6+** | Hudi / Paimon / Delta | Java | 开放表格式事实标准（Netflix/Apple/AWS） |
| 对象存储 | **MinIO** | Ceph / 云 OSS / S3 | Go | S3 兼容事实标准 |
| OLAP 仓 | **Apache Doris 2.x** | ClickHouse / StarRocks | Java+C++ | Apache TLP；MySQL 协议；运维简单；Unique Key 支持 upsert |
| 交互查询（湖上） | **Trino** | Spark SQL | Java | 联邦查询事实标准（可选） |
| 流计算 | **Apache Flink 1.20** | Spark Structured Streaming | Java/Scala | 流计算事实标准 |
| 批计算 | **Apache Spark 3.5** | Flink 批模式 | Scala/Java | 批计算事实标准 |
| 平台元数据库 | **PostgreSQL 16** | MySQL | — | —— |
| 缓存 / 状态 | **Redis 7** | —— | C | —— |

### 2.2 集成 / 调度 / 开发

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| **数据集成** | **Apache SeaTunnel 2.3.x（Zeta 引擎）** | DataX（仅离线）/ Flink CDC | Java | Apache TLP；**~200 连接器**；批/流/CDC 一体；**逐 job 连接器依赖隔离** |
| CDC 采集 | **Flink CDC 3.x** | Debezium + Kafka Connect | Java | Apache；全量+增量无缝一体（事实标准） |
| 调度 / 工作流 | **Apache DolphinScheduler 3.x** | Apache Airflow（Python） | Java | Apache TLP；国内数据平台广泛使用；周期 + 依赖 + 补数 + 告警 |

| 对象存储/网关 | **Spring Cloud Gateway** | Apache APISIX | Java | Spring 事实标准 |

### 2.3 治理与语义

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| **元数据 / 血缘 / 资产目录** | **DataHub** | OpenMetadata / Apache Atlas | Java + Python | LinkedIn 开源；生态最广；血缘与影响分析成熟 |
| **数据质量** | **SQL 规则 + DolphinScheduler**（起步）→ 补 **Great Expectations** | Soda Core / Deequ | Java / **Python** | ⚠️ **Apache Griffin 已退役（进 Attic），不可选** |
| 权限 | Apache Ranger（后置） | 平台内 RBAC（起步） | Java | Hadoop 生态事实标准；但重，建议后置 |
| **指标语义层** | **自研薄层 + Apache Calcite** | Cube（Node，不符 Java 主） | Java | Calcite 是 Apache SQL 解析/优化事实标准 |
| BI / 看板 | **Apache Superset** | Grafana / Metabase | Python | BI 事实标准 |
| 数据科学 / AI | **Python（Jupyter / scikit-learn / LangChain）** | —— | Python | 辅助栈 |
| 向量库 | **Milvus** | Qdrant / pgvector | Go/C++ | 主流向量库（P5 用） |

### 2.4 可观测与工程

| 能力 | 首选 | 语言 | 成熟度依据 |
|---|---|---|---|
| 指标 / 看板 | **Prometheus + Grafana** | Go | 事实标准 |
| 链路追踪 | **OpenTelemetry + Jaeger/Tempo** | Go/Java | 事实标准 |
| 日志 | **Loki**（或 ELK） | Go/Java | 事实标准 |
| 容器化 | **Docker Compose → Kubernetes** | — | 事实标准 |
| CI/CD | GitLab CI 或 GitHub Actions | — | 事实标准 |

### 2.5 **明确不选**的（避坑）

| 不选 | 原因 |
|---|---|
| **Apache Griffin**（数据质量） | **已退役进 Attic** |
| Apache Sqoop | 已退役 |
| Apache Flume | 生态衰退，被 Kafka/SeaTunnel 取代 |
| Apache NiFi | 过重，流式场景不如 SeaTunnel |
| 自研调度引擎 | DolphinScheduler 已足够，自研纯投入无差异 |
| 自研集成引擎 | SeaTunnel 已有 ~200 连接器 |
| Cube.js 做语义层 | Node 生态，与 Java 主栈不符 |

## 3. 目标架构

```text
┌─ 用户与接入 ───────────────────────────────────────────────────────┐
│  DolphinScheduler UI · DataHub UI · Superset · 自研门户/API（可选）  │
└────────────────────────────┬──────────────────────────────────────┘
                             │
┌─ 控制面（集成成熟开源 + 5 块自研胶水）──────────────────────────────┐
│  调度与依赖      Apache DolphinScheduler                             │
│  元数据/血缘     DataHub                                             │
│  质量规则        SQL 规则（调度执行）+ Great Expectations（补强）      │
│  指标语义        【自研】metric_def + MQL→SQL（Apache Calcite）       │
│  查询网关        【自研】Spring Boot（鉴权/限流/审计）                 │
│  配置生成        【自研】YAML → SeaTunnel/Flink/Spark 作业配置        │
│  元数据上报      【自研】作业血缘 → DataHub                          │
│  契约           【自研】信封 / 命名 / DLQ 原因枚举                    │
└────────────────────────────┬──────────────────────────────────────┘
                             │
┌─ 数据面（全部成熟开源）────────────────────────────────────────────┐
│  集成    Apache SeaTunnel(Zeta)   ← 离线 + 实时 + CDC 统一入口        │
│  流计算  Apache Flink                                                │
│  批计算  Apache Spark                                                │
│  调度执行 DolphinScheduler Worker（跑 SQL / Shell / Spark 任务）      │
└────────────────────────────┬──────────────────────────────────────┘
                             │
┌─ 存储 ─────────────────────────────────────────────────────────────┐
│  Kafka 总线 · Iceberg+MinIO 湖 · Apache Doris 仓 · PostgreSQL · Redis │
└────────────────────────────────────────────────────────────────────┘

横切：Prometheus + Grafana + OTel（可观测）· DataHub（元数据中枢）
```

**关键结构差异（对照商业平台）**：我们把"控制面"拆成 **成熟开源（调度/元数据/质量）+ 5 块自研胶水**；而商业平台是整个控制面自研。

## 4. 自研边界（**只有 5 块，且都要薄**）

| # | 自研块 | 为什么必须自研 | 复杂度 |
|---|---|---|---|
| 1 | **契约**（事件信封 / 命名规范 / DLQ 原因枚举） | 开源项目之间没有统一契约，这是"拼装平台"的粘合剂 | 低（文档 + 一份 JSON Schema） |
| 2 | **配置生成器**（YAML → SeaTunnel/Flink/Spark 配置） | 把"加一个源"从写配置变成填 YAML；这是平台化的核心动作 | 中 |
| 3 | **元数据上报器**（作业血缘 → DataHub） | 开源项目各自不知道对方的存在，需把 SeaTunnel/DS 的作业关系推给 DataHub | 中 |
| 4 | **指标语义层**（metric_def + MQL→SQL，基于 Calcite） | 开源里没有贴合我们口径模型的语义层；**也是 AI 问数的前提** | 高（差异化核心） |
| 5 | **查询网关**（Spring Boot：鉴权/限流/审计） | 统一对外出口；权限与审计必须自己掌握 | 中 |
| （可选） | 推式接入网关 | 若需接收 webhook 推送（SeaTunnel 的 Http 是拉式） | 低 |

**其余一律不自研。**

## 5. 契约与规范（自研块 #1）

### 5.1 统一事件信封

所有源进总线前转成它（由配置模板固化，不靠人自觉）：

```json
{
  "envelope_version": "1",
  "source": "biz-mysql",
  "source_type": "cdc",
  "tenant": "biz",
  "entity_type": "order",
  "entity_id": "1001",
  "event_type": "updated",
  "event_time": "2026-09-24T10:15:30Z",
  "ingest_time": "2026-09-24T10:15:31Z",
  "idempotency_key": "cdc:biz-mysql:orders:1001:u:1727080530123",
  "payload": { "…源字段原样…" }
}
```

两条铁律：`payload` **保持源原貌**；`event_time` 与 `ingest_time` **必须都留**（否则分不清"数据延迟"和"源时钟不准"）。

### 5.2 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 主题 | `{env}.{source_type}.{source}.{entity}.v{major}` | `prod.cdc.biz-mysql.order.v1` |
| DLQ 主题 | `{env}.dlq.{source}.{reason}` | `prod.dlq.biz-mysql.schema_mismatch` |
| 湖表 | `{layer}_{entity}_{suffix}` | `ods_order_event` / `dwd_order_event` |
| 仓表 | `{layer}_{entity}_{grain}` | `dws_order_1m` / `ads_order_daily` |
| 作业 | `{env}-{source}-{entity}` | `prod-biz-mysql-order` |
| 指标 | `{domain}_{measure}_{grain}` | `order_amt_1d` |

### 5.3 DLQ 原因枚举

`parse_error` · `schema_mismatch` · `validation_error` · `auth_error` · `overflow`
（分原因是**为了排查路径不同**；不要只存 error 字符串）

## 6. 实施路线

> 每期给出：**装什么 → 写什么胶水 → 交付物 → 验收（可测） → 风险**

### P0 · 选型验证 PoC（2–3 周）

**目标**：证明这些开源能拼起来，且关键连接器可用。**不做业务**。

**装什么**（一台 8C16G 起步，Docker Compose）

| 组件 | 版本 | 用途 |
|---|---|---|
| Kafka（KRaft） | 3.7+ | 总线 |
| MinIO | latest | 对象存储 |
| SeaTunnel（Zeta） | 2.3.x | 集成引擎 |
| Apache Doris | 2.1.x | OLAP 仓 |
| DolphinScheduler | 3.2.x | 调度 |
| DataHub | 最新稳定 | 元数据 |
| PostgreSQL / Redis | 16 / 7 | 平台元数据 / 缓存 |

**要做的验证（V 编号，后续复用）**

| 编号 | 验证内容 | 通过标准 |
|---|---|---|
| **V1** | SeaTunnel 跑通 `MySQL-CDC → Kafka` | 源库改一行，Kafka 里 5 秒内可见，信封字段完整 |
| **V2** | SeaTunnel 跑通 `Kafka → Iceberg ODS` | 湖表可查；重放两次行数不变 |
| **V3** | SeaTunnel 跑通 `JDBC（分片）→ Doris` | 大表分片并行；`SHOW LOAD` 无错误 |
| **V4** | DolphinScheduler 调度一个 SeaTunnel 批作业 | 定时触发成功，失败可重跑 |
| **V5** | DataHub 采集 Doris/Iceberg 元数据 | 表与字段在 DataHub 可见 |
| **V6** | 资源预算 | 所有容器 `mem_limit` 加总 < 宿主机内存 × 0.8（脚本校验） |
| **V7** | Iceberg 与 SeaTunnel 版本兼容 | Iceberg sink 写入成功（官方支持 1.6.1，需对齐） |

**交付物**：`选型验证报告.md` + 可复跑的 `docker-compose.yml` + 7 条 V 的实测记录

**风险与对策**

| 风险 | 对策 |
|---|---|
| 驱动 jar 目录官方文档三处不一致 | 实测确认，写进部署规范 |
| Iceberg 与 SeaTunnel 版本不兼容 | 锁 SeaTunnel 支持的 Iceberg 版本（1.6.1） |
| 内存打穿（旧项目踩过：6 容器 + 1 万长连接打穿 6GB） | V6 门禁卡住，先算预算再起容器 |
| DataHub 组件多（GMS + 前端 + ES/MySQL） | PoC 阶段可先只用其采集能力，部署可后置 |

### P1 · 最小闭环（4–6 周）

**目标**：**新增一个源 = 加一份 YAML**，别的什么都不用改。

**装什么**：P0 的栈 + SeaTunnel 集群模式 + 主题族规范落地

**写什么胶水**

| # | 胶水 | 内容 |
|---|---|---|
| 1 | **契约** | 信封 JSON Schema + 命名规范 + DLQ 枚举（文档 + 代码常量） |
| 2 | **配置生成器** | 读 `sources/*.yaml` + 模板 → 生成 SeaTunnel `.conf`（凭证用 `${}` 注入） |
| 3 | **作业提交与状态** | 调 Zeta 提交/停止/查状态；采集 lag、吞吐、错误率 |
| 4 | **健康四态** | 健康 / 降级 / 失败 / **静默**（按日增量基线判定） |
| 5 | **DLQ 与重放** | 按原因分类；按时间窗重放 |

**交付物**：控制面 v0（源注册 / 配置生成 / 提交 / 状态 / 健康）+ 实时链路 + 离线链路 + 门禁脚本

**验收（全可测）**

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **新增一个源只加 YAML** | 演练加一张新表；计时；**不改代码、不登服务器** |
| 2 | 端到端入湖 | 源库改一行 → 湖表可见，记录延迟 |
| 3 | 幂等 | 重放同一时间窗两次 → 行数与内容不变 |
| 4 | 失败隔离 | 停一个源 → 其它源与数据流不受影响 |
| 5 | 静默检测 | 人为停写入 → 配置窗口内收到静默告警 |
| 6 | DLQ 可重放 | 注入坏数据 → 进 DLQ（原因正确）→ 修规则 → 重放成功 |
| 7 | 水位正确 | 批任务中途失败 → 重跑 → 不丢不重 |
| 8 | 门禁全绿 | V6 资源预算 + 链路健康 + 端到端 e2e + 重启恢复 |

**不做**：指标层、血缘、权限、数据服务、AI、文件接入、K8s

### P2 · 建模与指标（6–8 周）

**目标**：数据可用（分层建模）+ **口径唯一**（语义层）+ 质量可拦。

**装什么**：Spark（批加工）+ Doris（DWS/ADS）+ Calcite（语义层）

**做什么**

| # | 内容 |
|---|---|
| 1 | **数仓分层落地**：ODS → DWD → DWS → ADS（+ DIM），含分区与幂等规范 |
| 2 | **指标语义层**：`metric_def` 唯一来源 + 派生关系 + **MQL → SQL 翻译器（Calcite）** |
| 3 | **质量规则**：SQL 规则集（非空/唯一/范围/枚举/引用/自定义）+ 调度执行 + **阻断下游** |
| 4 | **加工模板**：DWD 清洗、DWS 聚合可复用模板 |
| 5 | **物化**：Doris 建表 + 降采样（1m/1h/1d） |

**验收**

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **指标一次定义、多处复用** | 同一指标两处取数数值一致；改定义 → 两处同时生效 |
| 2 | 口径可追溯 | 任一指标可查定义/来源/表达式/负责人/版本 |
| 3 | **脏数据被阻断** | 注入越界数据 → 规则命中 → **下游任务未产出**（不是仅告警） |
| 4 | DWD 幂等正确 | update/delete 正确反映到 DWD |
| 5 | 分层可追溯 | 任一 ADS 指标可沿 DWD→ODS 追到源表 |
| 6 | 物化延迟 | DWS 1 分钟粒度可查延迟 ≤ 3 分钟 |

**不做**：字段级血缘、权限脱敏、数据服务、AI 问数

### P3 · 元数据与治理（6–8 周）

**目标**：可信（血缘/质量）、可控（权限/脱敏）、可算账（成本）。

**装什么**：DataHub（完整部署）+ 权限方案（起步用平台内 RBAC）

**做什么**

| # | 内容 |
|---|---|
| 1 | **元数据采集**：Doris/Iceberg/Kafka 的库表字段进 DataHub，周期更新 |
| 2 | **血缘上报器**：SeaTunnel/DolphinScheduler/Spark 作业血缘 → DataHub（含字段级，标注置信度） |
| 3 | **影响分析**：基于血缘给出下游影响面 |
| 4 | **权限与脱敏**：表级 + 字段级；PII 打标与掩码；审批流 |
| 5 | **成本归因**：存储 + 计算按项目/数据集分摊 |
| 6 | **治理看板**：Grafana 资产/质量/成本大盘 |

**验收**

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **影响分析可用** | 改一个字段 → 列出受影响下游表/指标/API，与人工核对一致 |
| 2 | 越权不可见 | 无权限查询被拒或返回空，**有审计记录** |
| 3 | 脱敏生效 | 无权限用户查 PII 只看到掩码值 |
| 4 | 血缘覆盖率 | 核心表 ≥ 90%，随任务变更**自动更新** |
| 5 | 成本可分摊 | 报表按项目/数据集出数，误差可解释 |
| 6 | 审计可查 | 授权/查询/导出可追溯到人、时间、对象 |

**不做**：对外 API、完整 Ranger 集成、计费

### P4 · 服务化（4–6 周）

**目标**：业务系统能安全、可控地直接消费数据。

**装什么**：Superset + Spring Cloud Gateway

**做什么**

| # | 内容 |
|---|---|
| 1 | **查询网关**：鉴权 / 限流 / 审计 / 三种查询模式（`metric_mql` / `sql_template` / `dataset_query`） |
| 2 | **API 管理**：定义、版本、发布、下线 |
| 3 | **调用统计**：QPS、延迟、错误率、调用方排行 |
| 4 | **BI 接入**：Superset 接 Doris，指标走语义口径 |

**验收**

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | 业务可调 | 业务系统调 API 取到预期数据 |
| 2 | 鉴权生效 | 无 token / 过期 / 越权 token 都被拒 |
| 3 | 限流生效 | 超配额返回**明确错误码**（不是超时） |
| 4 | 口径一致 | 同一指标 API 与看板数值一致 |
| 5 | 可观测 | 每 API 的 QPS/延迟/错误率可查 |
| 6 | 变更安全 | 破坏性变更升版本，旧版仍可用 |

**不做**：API 市场、计费、拖拽编排

### P5 · AI 增强（6–8 周）

**目标**：数据"能问"，而且**问得准**。

**装什么**：向量库（Milvus）+ Python 栈（LangChain/LangGraph + Jupyter）

**做什么**

| # | 内容 |
|---|---|
| 1 | **NL → MQL 解析**（LLM 只产 MQL，**不产 SQL**） |
| 2 | **MQL → SQL**（复用 P2 的语义层，保证口径唯一） |
| 3 | **评测集**：问数问题集 + 标准答案，可持续回归 |
| 4 | **诊断助手**：RAG + 工具调用，结论必带引用 |
| 5 | **兜底**：低置信度转人工、越权返回空、幻觉检测 |

**验收**

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | 问数准确率可量化 | 评测集（如 100 题）与人工核对一致率 ≥ 80% |
| 2 | 口径可信 | 同问题多次提问结果一致；与人工 SQL 结果一致 |
| 3 | **不直生成 SQL** | 日志可证：Agent 产 MQL，SQL 由语义层生成 |
| 4 | 必带来源 | 诊断结论每条带引用，无出处不生成 |
| 5 | 低置信度转人工 | 低于阈值时明确说"需人工确认" |
| 6 | 越权返回空 | 无权限检索返回空，不报错、不泄露存在性 |

**不做**：写操作自动化（写库/发货/退款）、无评测集上线

## 9. 风险与取舍

| # | 风险 | 对策 |
|---|---|---|
| 1 | **开源拼装的"最后一公里"比想象重**（各项目元数据不通） | 自研块 #3（元数据上报器）优先做；先打通 1 条血缘，再铺开 |
| 2 | **SeaTunnel 驱动/版本兼容** | P0 就验证（V7）；锁版本，建兼容矩阵 |
| 3 | **DataHub 部署重**（多组件） | P0 只验采集能力；完整部署放 P3；或用 OpenMetadata 替代 |
| 4 | **内存预算**（旧项目踩过） | V6 门禁卡住，先算后起 |
| 5 | **小文件**（流式入湖必踩） | compaction 作业在 P1 就要有 |
| 6 | **质量规则阻断误伤生产** | 规则分级 warn/error/**block**，只有核心用 block |
| 7 | **AI 问数不准就上线** | P5 强制评测集门槛（≥80%）才允许上线 |
| 8 | **过度自研**（不知不觉又造引擎） | 严守 §4 的 5 块边界，新增自研需评审 |
| 9 | **Doris vs ClickHouse 选错** | P0 用 V3 实测同数据量下的写入与查询表现再定 |
| 10 | **契约漂移**（各源自己造信封） | 信封由**配置模板固化**，不靠人自觉 |

### 三个关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 总线 | **Kafka**（若已有 RocketMQ 则复用） | offset 重放 + compacted topic + 生态最广；纯批量源可不过总线 |
| 湖 vs 仓 | 明细入 **Iceberg**，聚合入 **Doris** | 湖保历史可重放，仓保查询性能 |
| 自研 vs 开源 | **开源优先，自研只 5 块** | 商业平台的"控制面全自研"是其产品属性，不是我们的必要成本 |
