## 1. 设计目标与原则

**目标**：对标腾讯云 WeData / 阿里云 DataWorks 的能力集，以"成熟开源集成 + 薄自研胶水"构建企业级 Data+AI 数据平台。

**核心判断**：不要自研平台，要集成平台。WeData / DataWorks 自研控制面是因为它们是商业产品；而它们底下的能力（集成、调度、元数据、质量、BI）在开源生态里已有同等成熟度的项目。我们的工作是把它们**装起来 + 打通 + 补齐契约**。

### 1.1 四条建设原则

| 原则 | 含义 |
|---|---|
| 底层核心引擎能用成熟开源就不自研 | 集成、调度、存储、计算、元数据等核心引擎，先找 Apache 顶级项目/行业事实标准 |
| 系统入口必须自建 | 统一 WebUI 门户 + 开放 API 是平台的脸面与用户契约，自己掌握；开源引擎自带的 UI 只作内部控制台，不对最终用户暴露（唯一例外：BI 通道 Superset 面向分析师，消费通道与权限链路见 §3⑦） |
| 其余自研只做"胶水" | 只写开源之间缺失的粘合层，且必须薄（§4） |
| 每期可验证 | 每期都有具体命令/数据级的验收，不接受"基本可用" |

技术栈基调：**Java 为主**（平台与控制面）· **Python 为辅**（质量校验、AI、数据科学）。

### 1.2 企业级判据

**结构判据**（判断架构是否成立，超越功能清单）：

| 判据 | 不成立时的样子 |
|---|---|
| 统一目录是单一真相源 | 又一个元数据孤岛 |
| 治理内建在流水线里（不通过即阻断） | 事后外挂的补丁 |
| Data 与 AI 真正共栈（特征/权限/血缘打通） | 两套系统各玩各的 |
| 开放性（开放表格式 + 开放 API） | 被单一厂商锁定 |

**横切判据**（每个模块都要过线，否则不是企业级）：

| 判据 | 不过线的后果 |
|---|---|
| 多租户与配额 | 一个烂任务拖垮全平台 |
| 发布治理（dev/prod/版本/回滚） | 改错一个任务直接污染生产 |
| SLA 基线 | 产出迟到无人知、无人担责 |
| 审计合规 | 金融 / 政企场景不可上线 |
| 成本可算 | 平台变成无主的成本黑洞 |
| 开放 API | 平台变孤岛，无法嵌入企业流程 |

**模块建设顺序的设计哲学**：管理中心 → 集成 → 建模/标准 → 开发 → 运维 → 治理 → 消费——**底座先行、标准先行、治理贯穿**，而不是"先跑通再补治理"。因此发布、基线、标准、多租户这四件事不等晚期，最小版直接进 P1/P2。

## 2. 总体架构

### 2.1 架构图（结构视图）

```text
┌─ 系统入口（自研，见 §4）───────────────────────────────────────────────┐
│  【自研】统一门户 WebUI · 开放 API（由控制面的查询网关承载）           │
├─ 内部控制台（开源自带 UI，仅运维/管理员，不对最终用户暴露）────────────┤
│  DolphinScheduler UI · StreamPark UI · DataHub UI· Superset            │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 控制面（集成成熟开源 + 5 块自研胶水）─────────────────────────────────┐
│  编排/调度/补数  Apache DolphinScheduler（唯一编排器）                 │
│  实时作业托管    Apache StreamPark（被 DS 经 OpenAPI 启停）            │
│  元数据/血缘     DataHub                                               │
│  质量规则        SQL 规则（调度执行）+ Great Expectations（补强）      │
│  指标语义        【自研】metric_def + MQL→SQL（Apache Calcite）        │
│  查询网关        【自研】Spring Boot（鉴权/限流/审计）                 │
│  配置生成/管控   【自研】表单→作业配置；Zeta 提交/状态/健康/DLQ 重放   │
│  元数据上报      【自研】作业血缘 → DataHub                            │
│  契约           【自研】信封 / 命名 / DLQ 原因枚举                     │
│  模型出口        调用 AI 平台的模型网关（P5 接入）                     │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 数据面（全部成熟开源）────────────────────────────────────────────────┐
│  集成    Apache SeaTunnel(Zeta)   ← 离线 + 实时 + CDC 统一入口         │
│  有界任务 DolphinScheduler Worker（SQL / Shell / Spark / SeaTunnel）   │
│  无界作业 StreamPark 托管的 Flink / Spark 长驻作业                     │
│  AI 计算  Ray（批量推理 / embedding / 多模态预处理，P5 启用）          │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 存储 ─────────────────────────────────────────────────────────────────┐
│  Kafka 总线 · Iceberg+MinIO 湖 · Apache Doris 仓 · PostgreSQL · Redis  │
│  Milvus 向量库（P5，AI 问数 / 检索）                                   │
└────────────────────────────────────────────────────────────────────────┘

横切：Prometheus + Grafana + OTel（可观测）· DataHub（元数据中枢）

注：图中箭头为管控下发方向；数据不经过控制面，数据的读写路径见 §2.2 数据流视图。Superset 是唯一面向最终用户的开源 UI（BI 通道，仅查 Doris serving 层与指标视图），故不归入内部控制台，其权限链路见 §3⑦。
```

两条读图要点：

1. **入口与控制面分离**：最终用户只面对自研门户 WebUI 与开放 API；开源引擎自带 UI 降为内部控制台（原则 2 的落地）——唯一例外是 Superset（BI 通道面向分析师，权限链路见 §3⑦）。
2. **关键结构差异（对照商业平台）**：控制面 = 成熟开源（调度/元数据/质量）+ 5 块自研胶水；而商业平台是整个控制面自研。

### 2.2 端到端数据流视图

上面的架构图是**结构视图**（系统分几层、每层装了什么）；本图是**行为视图**——一条数据从源到消费的完整旅程：

```text
数据源（业务库 CDC / 消息流 / 文件 / API）
    │  ① 统一信封（§5.1）：payload 保持源原貌 + event_time/ingest_time 双时间
    ▼
Kafka 总线（主题按 §5.2 命名族）───────────────────────────┐
    │                                                     │
    ├─ ②a 实时加工：Flink 长驻作业（窗口/状态/CEP）          │
    │      消费 Kafka → 实时清洗/聚合 → 写 Iceberg / Doris   │
    │                                                     │
    ▼ ②b 集成入湖：SeaTunnel（批/流/CDC 统一入口）          │（纯批量源可不过总线，直拉入湖）
Iceberg ODS ──► DWD ──► DWS     （湖内分层，底座与真相源）
    │    离线批加工走模板 A（Spark）；实时作业由模板 B/C 守护
    │    质量规则内建于两条链路，不过即阻断
    ▼ ③ 物化
Doris DWS/ADS（serving 加速层，任何一张表可从湖重建）
    │
    ▼ ④ 语义与服务（自研：指标语义层 + 查询网关）
指标语义层（MQL→SQL，口径唯一）─┬─► 查询网关（鉴权/限流/审计）──► 业务系统（API 通道）
    └─► 生成 Doris 指标视图（同源产物）──► Superset 直查（BI 通道，权限链路见 §3⑦）
    │
    ▼ ⑤ AI 工程化（P5）
NL→MQL（LLM 只产 MQL，不产 SQL；LLM 调用经 AI 平台的模型网关统一出口，§3⑧）→ 语义层 → 与任何出口一致的答案

横切：每一跳的血缘 → DataHub；每一跳的质量 → SQL 规则阻断；每一跳的成本 → 归因
```

两条读图要点：

1. **湖是必经站**：实时（②a Flink）和离线（②b SeaTunnel + Spark）都在 Iceberg 分层里汇合（§5.5 任务归属规范），Doris 只是下游物化——这是"离线实时一个平台"在数据流上的样子。
2. **语义层是口径的唯一来源**：报表、API、AI 问数同出一处口径——API 与 AI 问数经查询网关物理过语义层，BI 查的是语义层生成的 Doris 指标视图（同一份 MQL→SQL 产物，两种承载）。消费方到 Doris 只有 API / BI 两条通道，权限与审计各自闭合，完整约定见 §3⑦（探索式取数通道后置、启用前评审，§3⑦ 约定 3）。

### 2.3 控制面与数据面

```text
控制面负责"管控"：决定谁能用、怎么用、用多少、是否合规、是否稳定。
数据面负责"执行"：真正的数据接入、计算、存储、查询和 AI 服务执行。
```

这样架构才从"项目系统"升级为"平台系统"。控制面 12 个中心的职责细分：

| 中心 | 职责 |
|---|---|
| 权限中心 | 用户、角色、组织、租户、行列级权限、AI 工具调用权限；身份来源统一走 OIDC（企业 IdP / Keycloak），平台不自建账号体系 |
| 配置中心 | 服务配置、规则配置、源注册配置、灰度配置、告警阈值配置 |
| 元数据中心 | 表、字段、任务、接口、指标、模型、知识库元数据 |
| 指标中心 | 指标口径、指标版本、指标审批、实时/离线一致性 |
| 任务调度 | 离线任务、数据同步、质量检查、模型评测任务 |
| 数据质量 | 空值率、唯一性、完整性、时效性、波动检测、Schema Drift |
| 血缘中心 | 表血缘、字段血缘、任务血缘、指标血缘、AI 数据来源追踪 |
| 审计中心 | 数据访问审计、接口调用审计、AI 问答审计、权限变更审计 |
| 告警中心 | 任务失败、数据延迟、Kafka 积压、Flink 异常、模型异常 |
| 资源中心 | K8s 资源、队列资源、存储配额、计算资源、租户隔离 |
| 模型中心 | Prompt 版本、模型路由、RAG 评测、Embedding 管理、LLM Gateway（**复用 AI 平台的模型网关**，不自研） |
| 成本中心 | 存储成本、计算成本、查询成本、模型调用成本、Token 成本 |

数据面各组件的执行职责细分：

| 组件 | 职责 |
|---|---|
| SeaTunnel（Zeta） | 数据集成的执行引擎：批/流/CDC 作业的实际读写、断点续传、脏数据输出 DLQ |
| DolphinScheduler Worker | 有界任务的实际执行：`sql` / `shell` / `python` / `spark` / `seatunnel` 任务 |
| Flink / Spark 长驻作业 | 无界流作业的实际运行：状态管理、窗口计算、checkpoint/savepoint（生命周期由 StreamPark 托管） |

两条要点：

1. **中心 ≠ 组件**：控制面按逻辑职责单元（中心）切分，与实现组件是多对多关系——如元数据中心与血缘中心都由 DataHub 承担，权限中心由 DS 权限、查询网关、Doris 行列权限共同分担；数据面按物理执行组件切分，组件即职责、一一对应。
2. **存储层不在数据面职责表内**：它是数据面读写结果的承载（职责与选型见 §3 ②），不是执行者；控制面的管控指令经各组件的管理接口下达（编排器 DS 经 OpenAPI 启停 StreamPark，见 §2.1 与 §5.5 模板 B/C）。

### 2.4 多租户模型（最小集，四层对齐）

平台会被多个团队/业务线共用。多租户模型回答一个问题：不同团队在同一个平台里，怎么互相看不见、互不干扰？**前期不做隔离功能，但隔离的"形状"必须在架构期定死**——下面四个隔离单位是建表、建项目时的物理边界：表一旦按 `order` 而不是 `biz.order` 建出来，日后再补隔离等于全量表迁移，改造成本极高。

| 层 | 隔离单位 | 含义 |
|---|---|---|
| DolphinScheduler | 租户 / 项目 | 一个团队 = 一个项目，任务与工作流互不可见 |
| DataHub | domain | 一个团队 = 一个域，元数据资产各看各的 |
| Iceberg | namespace | 一个团队的湖表放一个命名空间 |
| Doris | database | 一个团队一个库 |

四条边界说明：

1. **本模型只管"隔离"，不管"配额"**——计算/存储配额随 P3 资源中心一并设计（职责见 §2.3）。
2. **落地时点**：P3（§6），验收为 V32——建第二个租户，其任务、元数据、湖表、仓表对第一个租户不可见，四层各验一次。
3. **租户与 env 的叠加规则**（P1 双环境落地时按此建，各组件不得自造写法）——Doris：`{tenant}_{env}`（如 `biz_prod` / `biz_dev`）；Iceberg：租户 = namespace、env = catalog 别名（dev/prod 各一套 warehouse 根路径与元数据 schema）；DS：租户 = 项目（dev/prod 两套实例，项目名即租户名）；DataHub：domain = 租户、env 走其 URN 的 env 段。
4. **多租户源的路由**——一个源库服务多租户时，由配置生成器按 `envelope.tenant` 展开成每租户一个 sink 作业，禁止多租户混写同一 namespace / database。

### 2.5 可用性与容灾（组件能力口径）

**原则**：平台的可用性与容灾**建立在所选组件的原生能力之上，不自研容灾机制**。本节只确认一件事：每个组件都具备高可用与数据保护能力——将来部署形态从单机（P0 PoC）演进到多副本（生产 K8s）时，**不需要更换任何组件**。

| 组件 | 高可用（服务不死） | 容灾与数据保护（数据不丢、可恢复） |
|---|---|---|
| Kafka（KRaft） | 多 broker + 分区副本（ISR） | 副本同步、offset 重放 |
| Flink | JobManager HA（K8s 部署）+ checkpoint 恢复 | checkpoint / savepoint（状态精确一次） |
| SeaTunnel（Zeta） | Master/Worker 容错，作业自动 failover | checkpoint 恢复、断点续传 |
| Iceberg + MinIO | MinIO 分布式多节点（纠删码） | Iceberg 快照与时间旅行；MinIO 版本控制/对象锁/站点复制 |
| Doris | FE 多副本（Leader/Follower/Observer）+ BE 多副本 | 数据多副本；backup/restore 到对象存储 |
| PostgreSQL | 主备流复制 | PITR（WAL 归档） |
| Redis | 哨兵 / Cluster | AOF/RDB 持久化 |
| DolphinScheduler | 多 Master/Worker（注册中心选主） | 元数据存 PostgreSQL，随其备份 |
| StreamPark | 无状态应用层，可多实例（前置 LB） | 元数据存数据库；作业状态在 Flink 侧（savepoint） |
| DataHub | 多实例（前置 LB） | 元数据存平台 PostgreSQL，随其备份 |
| Elasticsearch（DataHub 依赖） | 多分片副本（多节点） | snapshot 至对象存储；索引可从元数据库重建 |
| Ray / Milvus（P5 引入） | Ray worker 故障自动重建；Milvus 多副本（K8s Operator） | Ray 任务级重试；Milvus Backup 备份至对象存储 |
| 自研组件（门户/网关/胶水） | 无状态化设计，K8s 多副本 | 状态只存 PG / Redis / 对象存储，继承上表能力 |

三条约定：

1. **自研组件一律无状态**——状态只存 PostgreSQL / Redis / 对象存储，可用性与容灾能力随之继承，自研件自身不需要任何容灾设计。
2. **统一备份策略后置，但原语已就位**——各组件的快照/复制/PITR 能力以本表为准（选型已确认）；统一的备份策略与恢复演练在 P6 设计（§6），不在 P0–P5 范围。
3. **平台 PostgreSQL 的复用边界**——一个 PG 实例承载 DataHub 元数据库、Iceberg JdbcCatalog、DS 元数据库、平台配置库与审计日志：**按组件分 schema（或独立 database）+ 独立账号 + 连接数上限**，P0 由 V5 确认并写入部署规范；备份对象清单随 P6 统一备份策略（§6 P6 做什么 2）一并登记，连接数上限按 §2.6 规模档位设定，禁止各组件共用默认池。

### 2.6 规模假设（三档口径）

架构里的每个数字（容器内存、分区数、副本数、物化粒度、成本单价）都挂在规模上。本节给出**假设值**，P0 用业务访谈 + 实测回填；未回填前，任何容量 / SLA / 成本结论都按本节口径读。

| 维度 | PoC（P0） | 试点（P1–P3） | 生产（P4–P6） |
|---|---|---|---|
| 源 / 表 | 1 源 · 1 表 | 10 源 · 200 表（含 20 张 CDC 表） | 50 源 · 2000 表（含 200 张 CDC 表） |
| 日增量 / 峰值写入 | ≤ 10 MB/s | 500 GB/日 · 50 MB/s | 5 TB/日 · 300 MB/s |
| 实时作业 / 离线任务 | 1 个 / 5 个每日 | 10 个 / 300 个每日 | 50 个 / 3000 个每日 |
| 指标 / API | —— | 30 指标 · 50 QPS 峰值 | 300 指标 · 500 QPS 峰值 |

## 3. 能力域与选型

平台能力划分为八大能力域，自下而上：

```text
┌─────────────────────────────────────────────────────────────────┐
│ ⑧ AI 工程化    特征平台→训练→模型管理→推理服务→LLM 应用(RAG/Agent)│
├─────────────────────────────────────────────────────────────────┤
│ ⑦ 语义与服务   指标层 · 标签层 · API 服务 · BI                   │
├─────────────────────────────────────────────────────────────────┤
│ ⑥ 数据治理     质量 · 血缘 · 安全 · 成本          (控制面核心)    │
├─────────────────────────────────────────────────────────────────┤
│ ⑤ 开发工作台   SQL/管道 IDE · 调度 · 调试 · 版本管理              │
├─────────────────────────────────────────────────────────────────┤
│ ④ 统一目录     表/模型/特征/指标 —— Data+AI 一个 Catalog          │
├─────────────────────────────────────────────────────────────────┤
│ ③ 计算引擎     批流一体(Spark/Flink) · OLAP(Doris) · AI(Ray)     │
├─────────────────────────────────────────────────────────────────┤
│ ② 存储底座     湖仓一体(Iceberg + 对象存储)                       │
├─────────────────────────────────────────────────────────────────┤
│ ① 数据集成     批 / 流 / CDC / 文件 / API 全域接入                │
└─────────────────────────────────────────────────────────────────┘
        横切: 可观测性 · 多租户与权限 · 开放 API · 部署运维(K8s)
```

**选型标准**：① Apache 顶级项目或行业事实标准；② 有商业公司或大厂背书；③ 社区活跃（近半年有 release）；④ Java 生态优先。

**选型时效**：本章的版本号与社区活跃度判断每半年复查一次，随最近一次 §7 验证清单的执行同步更新。

### ① 数据集成

**职责**：把所有形态的数据接进来——这是平台的"进口"，决定了平台能吃多大的世界。

| 接入形态 | 说明 | 代表实现 |
|---|---|---|
| 流式 | 消息队列/设备上报，秒级 | Kafka、Pulsar；Flink CDC |
| 批量 T+1 | 业务库定时抽取 | SeaTunnel、DataX |
| CDC | 数据库变更捕获，分钟级 | Flink CDC、Debezium、Canal |
| 文件 | Excel/CSV/日志/报表 | 文件接收服务（自研后置件）+ 对象存储 |
| 多模态 | 图片/音频/视频 | 对象存储 + 元数据管道 |
| API/SaaS | 第三方系统拉取 | Airbyte（300+ 连接器） |

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 数据集成 | **Apache SeaTunnel 2.3.x（Zeta 引擎）** | DataX（仅离线）/ Flink CDC | Apache TLP；**~200 连接器**；批/流/CDC 一体；**逐 job 连接器依赖隔离** |
| CDC 采集 | **SeaTunnel CDC 连接器（统一入口）** | Flink CDC 3.x / Debezium + Kafka Connect | 与 §2.1「SeaTunnel = 批/流/CDC 统一入口」一致（V1 验证）；Flink CDC 为备选（需 Flink 原生 CDC 管道时启用，Flink 已在 P0 栈内） |

**企业级要求**：接入任务可配置化（非硬编码）、断点续传、脏数据隔离（DLQ）、接入审计、Schema 契约管理。

### ② 存储底座

**职责**：一份数据、多处可用——湖仓一体是企业级的共识答案。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 湖表格式 | **Apache Iceberg 1.6+** | Hudi / Paimon / Delta | 开放表格式事实标准（Netflix/Apple/AWS）；ACID、Schema 演进、时间旅行、隐藏分区 |
| Iceberg Catalog | **JdbcCatalog（复用平台 PostgreSQL）** | Iceberg REST Catalog（Gravitino / Lakekeeper 承载）/ Hive Metastore | 多引擎共表的元数据枢纽；起步选最轻、零新增组件，HA 随 PG 继承（§2.5）；REST 是官方标准接口，为升级方向 |
| 对象存储 | **MinIO** | Ceph / 云 OSS / S3 | S3 兼容事实标准 |
| OLAP 仓 | **Apache Doris 2.x** | ClickHouse / StarRocks | Apache TLP；MySQL 协议；运维简单；Unique Key 支持 upsert |
| 交互查询（湖上） | **Trino** | Spark SQL | 联邦查询事实标准（可选） |
| 平台元数据库 | **PostgreSQL 16** | MySQL | —— |
| 缓存 / 状态 | **Redis 7** | —— | —— |

**Catalog 两条约定**：

1. **Catalog 唯一**——它是多引擎共表的元数据枢纽：Spark / Flink / SeaTunnel / Doris 外部目录 / Trino（可选）全部指向同一个 Iceberg Catalog；任何引擎不得自建私有 catalog，否则"湖是底座与真相源"不成立。
2. **起步 JdbcCatalog，升级 REST 是迁移而非重建**——表数据在 warehouse 不动，仅元数据登记迁移；升级触发条件：多引擎并发写冲突显现、需要对外 REST 开放、或并入 Gravitino 统一目录（§3④ 跟踪项）。并发提交正确性在 P2 引入 Spark 时验证（§6 P2 做什么 1）。

**数据分层**：ODS → DWD → DWS → ADS（+ DIM），行业通用数仓方法论。

**关键认知**：湖（Iceberg）是**底座与真相源**，OLAP 引擎（Doris）是 **serving 加速层**——两者不是竞品，是分工。明细入 Iceberg（湖保历史可重放），聚合作 Doris（仓保查询性能）。平台成熟度的标志之一是"任何一张服务层的表都能从湖仓重建"。

**企业级要求**：开放表格式（不锁定）、存储计算分离、分层生命周期（热温冷）、小文件治理、表级 owner/SLA 元数据。

### ③ 计算引擎

**职责**：三类负载，三类引擎，各司其职。

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 流处理 | **Apache Flink 1.20** | Spark Structured Streaming | 流计算事实标准 |
| 批处理 | **Apache Spark 3.5** | Flink 批模式 | 批计算事实标准 |
| 交互式分析 | **Doris**（见②） | ClickHouse / StarRocks / Trino（联邦） | —— |
| AI 计算 | **Ray** | —— | Python 原生分布式（训练/批量推理/embedding/多模态） |
| ML 训练 | PyTorch | TensorFlow | GPU 框架事实标准 |

**关键认知**：Ray 与 Flink/Spark **不是并列的第三数据引擎**——Flink/Spark 算数据，Ray 算模型。Ray 服务 AI 层：批量推理、embedding 生成、超参搜索、多模态预处理。

**企业级要求**：批流一体（同一 SQL 语义）、资源隔离与弹性（K8s/Yarn）、作业全生命周期管理（提交/监控/savepoint/版本）、计算成本可归因。

### ④ 统一目录

**职责**：Data+AI 一个 Catalog——表、文件、模型、特征、指标，一处注册、处处可见。**这是平台的心脏，也是"项目"与"平台"的分水岭。**

| 构成 | 说明 |
|---|---|
| 技术元数据 | 表/字段/分区/文件/模型/特征的定义与统计 |
| 业务元数据 | 口径、负责人、标签、密级 |
| 运行时元数据 | 任务、血缘、质量结果、用量 |
| 统一授权 | 基于 Catalog 的行列级权限，一处授权处处生效 |
| 开放接口 | REST/JDBC/HCatalog 兼容，引擎与工具自由接入 |

| 能力 | 首选 | 备选 | 成熟度依据 |
|---|---|---|---|
| 元数据 / 血缘 / 资产目录 | **DataHub** | OpenMetadata / Apache Atlas / Apache Gravitino | LinkedIn 开源；生态最广；血缘与影响分析成熟。Gravitino 面向 Data+AI 统一目录（含模型/文件），最年轻也最有方向感，持续跟踪（亦可作为 Iceberg REST Catalog 的承载实现，见 §3② Catalog 约定 2） |

**业界参照**：Unity Catalog（Databricks）、Hive Metastore（上一代事实标准）。

**企业级要求**：元数据自动采集（非人工登记）；一处注册、处处可见（技术/业务/运行时元数据同目录）；统一授权基于 Catalog 一点配置、全栈生效。

### ⑤ 开发工作台

**职责**：数据开发与 AI 开发的"IDE"——让生产者自助，是平台被用起来的关键。**专业工作台能力不自研**（复用开源 IDE/控制台），统一入口门户见 §4「入口」。

| 能力 | 首选 | 备选 | 成熟度依据 |

| 编排 / 调度 / 补数 | **Apache DolphinScheduler 3.x** | Apache Airflow | Apache TLP；官方文档任务类型 **36 种**；`dependent` 任务做跨周期依赖；**同一套工作流既能编排有界任务，也能编排实时作业的启停守护** |
| 离线任务编写 | DolphinScheduler 自带编辑器（`sql` / `python` / `shell` / `spark` / `stored-procedure` / `http` 任务） | —— | 不需要额外组件 |
| 分布式任务编排插件 | **不自研**，只用 DS 现有任务类型 | —— | 少一个自研物就少一处长期维护 |
| 实时作业托管（启停 / Savepoint / 监控 / 告警） | **Apache StreamPark** | Dinky | **2025-01 毕业的 Apache TLP**；应用全生命周期管控 |
| 实时 SQL 开发体验（多语句 IDE / 血缘 / 版本对比） | Dinky | —— | **非 ASF 项目**（DataLinkDC 社区项目）。功能明显强于 StreamPark，但治理与发版节奏需在 P0 评估 |

**企业级要求**：工作流与发布版本化（资产可评审、可回滚；发布快照入控制面版本库，见 §6 P1 发布 SOP）；dev/prod 发布必经 SOP（V17）；调试信息（日志/执行计划/数据探查）对开发者自助可见。

### ⑥ 数据治理

**职责**：让数据可信、可控、可追责——管控不出活，但让出活的东西值得信任。

| 能力 | 说明 | 选型 |
|---|---|---|
| 数据质量 | 空值/唯一/完整/时效/波动检测，质量分 | **SQL 规则 + DolphinScheduler**（起步）→ 补 **Great Expectations**（备选 Soda Core / Deequ） |
| 血缘 | 表/字段/任务/指标血缘，影响分析 | **DataHub + OpenLineage**：DS / Spark / Flink 发 OpenLineage 事件由 DataHub 原生摄入，SeaTunnel 与自研件由上报器补事件（§4） |
| 安全合规 | 行列级权限、脱敏、审计、密级、身份认证、传输/静态加密 | 平台内 RBAC（起步）；**身份认证 OIDC（P1 随门户接入，P4 网关复用同一身份源）**；**传输加密 TLS + 静态加密（P6 随 K8s 落地，见下约定 3）**；Apache Ranger（后置，Hadoop 生态事实标准但重） |
| 成本治理 | 存储/计算/查询/Token 成本归因与优化 | 自研 + 账单分析 |

**企业级要求**：质量规则**内建于流水线**（不通过即阻断/告警），而非事后扫描；血缘自动采集（非人工登记）；权限一点配置全栈生效。

四条约定：

1. **审计空窗兜底**——审计中心 P3 才建成（V28）；空窗期 DS 操作日志与平台操作日志统一落 PG 保留，P3 由审计中心回溯采集。空窗期不可接受的是"未落库"，不是"未汇总"。
2. **服务账号收口**——Superset / 网关 / DS 连 Doris 的账号由 **Vault** 统一托管（§3 横切；按平台分 path/policy），禁止个人持有；这是 §3⑦「直连入口封禁」的执行前提。
3. **加密口径**——传输加密（TLS）与静态加密随 P6 生产化一并落地（§6 P6 做什么 1）；P0–P5 内网环境不强制，金融/政企等合规场景上线前必须落地。
4. **两套校验的边界**——入口逐条校验（§5.1）只做**行级 / 结构级**（parse / schema / validation）并进 DLQ；本节 SQL 规则只做**表级 / 跨表 / 时序**（非空率 / 唯一性 / 波动 / 引用完整性）并阻断下游。同一规则只在一个落点实现，禁止双写；分级 warn / error / **block** 由数据 owner 定，block 名单需平台评审后生效。

### ⑦ 语义与服务

**职责**：把数据翻译成业务语言，并以服务的形式交付——消费方不碰表，只碰语义。

| 能力 | 说明 | 选型 |
|---|---|---|
| 指标层 | 口径一处定义，BI/API/AI 处处复用 | **自研薄层 + Apache Calcite**（差异化核心；Cube 是 Node 生态，与 Java 主栈不符，不选） |
| API 服务 | 指标/数据 REST 化 | **自研 Spring Boot 查询网关**、Kyuubi（可选） |
| BI 可视化 | 看板、自助分析 | **Apache Superset**（备选 Grafana / Metabase） |
| 标签层 | 实体画像 | 自研 + Doris（后置） |

**消费通道与权限链路**：消费方到 Doris 只有两条通道，权限与审计在两条上各自闭合——

| 通道 | 链路 | 鉴权 / 审计落点 |
|---|---|---|
| API 通道 | 业务系统 → 查询网关（鉴权/限流/审计）→ 语义层 MQL→SQL → Doris | 网关是强制点；审计在网关 |
| BI 通道 | Superset → Doris（仅 serving 层 DWS/ADS + 语义层生成的指标视图） | Doris 原生行列权限（行策略 + 列级授权），PII 走掩码视图；审计由 Doris audit log 采集回审计中心 |

四条约定：

1. **口径唯一靠"同源产物"，不靠物理链路唯一**——BI 通道的指标视图定义与 API 通道的执行 SQL 出自同一个 MQL→SQL 翻译器、同一版本 `metric_def`；V35（API 与看板口径一致）验的就是这一点。
2. **权限一点配置、两处下发；直连入口封禁**——权限中心（§2.3）是 RBAC 唯一配置入口，规则同步下发到网关与 Doris 账号/角色；Doris 查询端口仅服务账号（Superset / 网关 / DS）可用，终端用户无直连账号。Ranger 后置选项（§3⑥）不变——届时替换的是下发机制，不是这套模型。
3. **探索式取数通道后置**——数据科学/探索式查询（湖上明细）不开放 Doris 直连，也不走网关；需求随 P5 Jupyter 一并设计（§6 P5 做什么 7），候选承载 Kyuubi / Trino（§3②⑦），规模触发、启用前评审。
4. **语义层的版本与再生成**——MQL 语法与生成器随平台资产 Git 版本化（与信封同纪律）；`metric_def` 变更触发**指标视图再生成作业**（Doris 视图 DDL 与网关执行 SQL 由同一翻译器、同一版本生成，附生成器版本哈希）；每次发布的指标定义版本可回溯（P3 元数据中心承接）。"口径一致"（V35）由同源 + 同版本哈希证明，不靠人工比对。

**企业级要求**：指标口径字典是强约束（新指标先登记后开发）；所有出口（报表/API/AI）引用同一口径——**同一个指标在任何出口答案一致**。

### ⑧ AI 工程化

**职责**：AI 从 Demo 到生产的全生命周期——与数据共栈是新一代平台的分水岭。

```text
数据资产(①–④) → 特征平台 → 训练(Ray/PyTorch) → 模型管理(MLflow)
→ 推理服务(vLLM/Triton) → AI 应用(RAG/Agent/Copilot) → 评测与反馈
```

| 能力 | 选型 |
|---|---|
| LLM 应用框架 | **LangChain / LangGraph**（Python 辅助栈） |
| 向量库 | **Milvus**（备选 Qdrant / pgvector） |
| 问数链路 | **NL → MQL（LLM 只产 MQL，不产 SQL）→ 语义层 MQL→SQL**（复用⑦，保证口径唯一） |
| 评测体系 | 问数评测集 + 标准答案，可持续回归（RAGAS 可参考） |
| LLM Gateway / Prompt 管理 | **复用 AI 平台的模型网关**（[`engineering/ai-platform/`](../ai-platform/) 的 06 底座；与 MCP 网关 / 沙箱一起“只建一次”），P5 接入；本域只维护 Prompt 内容与问数语义（§6 P5 做什么 6） |
| 特征平台 / 模型管理 / 推理服务 | Feast / MLflow / vLLM（均后置，规模触发） |

**企业级要求**（铁律）：AI 的权限边界 = 数据权限边界（AI 经 API 取数，不直连库）；AI 输出可追溯（血缘到源数据）；AI 成本可计价；无评测集不上线。

**与仓库内 AI 平台的关系**：本域 P5 是数据平台自身的 AI 工程化能力（问数 / 诊断）；[`engineering/ai-platform/`](../ai-platform/) 是并列的 AI 平台（七个纵切单元，见其平台路线文档）。**两平台的分工已定稿**：模型出口 / 模型网关、MCP 网关、沙箱等 AI 基础设施**由 AI 平台拥有**（只建一次），本域 P5 作为**调用方**接入；湖仓表格式（Iceberg）与对象存储**由本域拥有**，AI 平台消费（v36 定稿）。**编排按“数据任务 vs 模型任务”划界**：数据任务（含实时守护）归本域的 DolphinScheduler，模型与集成任务归 AI 平台的 Airflow，两者通过 API 互相触发、不互相替代（v37 补）。除此之外不共用代码与部署，选型相互参照，避免同一选型出现两套结论。

## 4. 自研边界

自研边界 = **1 个入口 + 5 块胶水**；模型出口 / LLM Gateway 不自研（由 AI 平台承载，见下），后置自研件按触发条件启用。

**入口（系统的脸面与用户契约，必须自建）**

| 自研块 | 为什么必须自研 | 复杂度 |
|---|---|---|
| **统一门户 WebUI + 开放 API** | 系统入口是平台的统一脸面：开源引擎各自的 UI 口径不一、体验割裂，最终用户只应面对一个门户、一套 API。开放 API 的鉴权/审计/版本契约必须自己掌握 | 高（前端 + BFF；分期建设：P1 先出最小控制台——源注册/状态/健康，随 P2–P5 逐步纳入指标、血缘、服务、问数入口） |

**胶水（开源之间缺失的粘合层，必须薄）**

| 自研块 | 为什么必须自研 | 复杂度 |
|---|---|---|
| **契约**（事件信封 / 命名规范 / DLQ 原因枚举） | 开源项目之间没有统一契约，这是"拼装平台"的粘合剂 | 低（文档 + 一份 JSON Schema） |
| **配置生成与接入作业管控**（源注册表单 / 配置库 → SeaTunnel/Flink/Spark 配置；Zeta 提交/状态/健康四态；DLQ 重放） | 把"加一个源"从写配置变成**门户填表单**（平台化的核心动作）；源注册配置存平台 PG（含版本 / 回滚），配置生成器读库生成引擎配置。作业接进来还要盯得住——提交/停止/查状态、lag/吞吐/错误率采集、健康四态（健康/降级/失败/静默）、DLQ 按原因重放，是同一条接入生命周期的两半 | 中高 |
| **元数据上报器**（作业血缘 → DataHub） | 开源项目各自不知道对方的存在。它拉取 DS 工作流定义 + SeaTunnel 配置，解析出输入/输出表后推给 DataHub（SQL 解析复用 DataHub 生态自带能力，不自己写） | 中 |
| **指标语义层**（metric_def + MQL→SQL，基于 Calcite） | 开源里没有贴合我们口径模型的语义层；也是 AI 问数的前提 | 高（差异化核心；预估 3–6 人月，全平台最大单项自研，量级由 P0 语义层 spike 校准） |
| **查询网关**（Spring Boot：鉴权/限流/审计） | 统一对外出口（开放 API 的承载者）；权限与审计必须自己掌握 | 中 |


**不自研：模型出口 / LLM Gateway**——由 AI 平台的 06 底座承载（模型网关与 MCP 网关 / 沙箱 / 可观测一起“只建一次”），本域 P5 作为**调用方**接入（§3⑧）。v31–v35 曾把它算作第 6 块胶水，v36 撤销：自研边界回到 **1 个入口 + 5 块胶水**。

**后置自研件**（规模触发才启用，不计入常态边界；启用前需评审）：

| 自研块 | 触发条件 | 复杂度 |
|---|---|---|
| 推式接入网关 | 需接收 webhook 推送时（SeaTunnel 的 Http 是拉式） | 低 |
| 文件接收服务 | 文件/多模态源成规模接入时（①） | 低 |
| 成本归因 | P3 治理期，账单分析不够用时（⑥） | 中 |
| 标签层 | 实体画像需求出现时（⑦） | 中 |

**其余一律不自研。**

## 5. 契约与规范

### 5.1 统一事件信封

所有源进总线前转成它（由配置模板固化，不靠人自觉）：

```json
{
  "envelope_version": "1",
  "source": "biz-mysql",
  "source_type": "cdc",
  "tenant": "biz",
  "entity_type": "order",
  "entity_id": "1001",
  "event_type": "updated",
  "event_time": "2026-09-24T10:15:30Z",
  "ingest_time": "2026-09-24T10:15:31Z",
  "idempotency_key": "cdc:biz-mysql:orders:1001:u:mysql-bin.000042:158237",
  "payload": { "…源字段原样…" }
}
```

两条铁律：`payload` **保持源原貌**；`event_time` 与 `ingest_time` **必须都留**（否则分不清"数据延迟"和"源时钟不准"）。

两条构造约定：

1. `idempotency_key` 统一按 `{source_type}:{source}:{表}:{主键}:{操作}:{位点}` 构造。**位点必须是源端可重放的坐标**：CDC 用 binlog 坐标（GTID 或 `{file}:{pos}` / LSN），批量源用批次号，API 拉取用游标或批次——**禁止用挂钟时间戳**（源时钟漂移或重放会让同一次变更产生不同的键，幂等当场失效）。无表/主键的源（批文件、API 拉取）用 `{source_type}:{source}:{对象标识}:{批次}`。**键的格式即幂等的边界**——各源不得自造格式。
2. `envelope_version` 与主题的 `v{major}`（§5.2）**联动**：信封发生不兼容变更时主题升 major 版本，新旧版本并行一个迁移期，不得原位改语义。

两条 Schema 演进约定：

1. **兼容演进自动通过，不兼容变更进 DLQ、走契约升版**——加可选字段等兼容变更自动通过并登记；删字段 / 改类型等不兼容变更触发 `schema_mismatch` DLQ + 告警，恢复路径只有两条：源端回退，或按上文构造约定 2 升 `envelope_version` 与主题 major、新旧并行一个迁移期。不得原位改语义。
2. **不引入 Schema Registry**——信封 JSON Schema 以 Git 版本化管理（随 `envelope_version` 演进，变更即 code review）；漂移检测的两个落点：接入作业**启动前**比对源 schema 与契约（warn）、**运行时**逐条校验（block → DLQ）。§2.3 质量中心的 Schema Drift 职责即由这两个落点承载。

### 5.2 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 主题 | `{env}.{source_type}.{source}.{entity}.v{major}` | `prod.cdc.biz-mysql.order.v1` |
| DLQ 主题 | `{env}.dlq.{source}.{reason}` | `prod.dlq.biz-mysql.schema_mismatch` |
| 湖表 | `{layer}_{entity}_{suffix}` | `ods_order_event` / `dwd_order_event` |
| 仓表 | `{layer}_{entity}_{grain}` | `dws_order_1m` / `ads_order_daily` |
| 工作流 | `ws_{产出表名}` | `ws_dwd_order_detail_di` |
| 任务（工作流内节点） | `{产出表名}` | `dwd_order_detail_di` |
| 作业 | `{env}-{source}-{entity}` | `prod-biz-mysql-order` |
| 指标 | `{domain}_{measure}_{grain}` | `order_amt_1d` |

两条边界说明：

1. **租户维度不在命名段内**——湖表的租户落在 Iceberg namespace（§2.4，即 `biz.ods_order_event` 中的 `biz` 段）；Kafka 无租户概念，主题级隔离靠 ACL 与配额。
2. **DLQ 主题的 `{reason}` 段取值即 §5.3 的枚举**——新增原因需先扩枚举再使用。

### 5.3 DLQ 原因枚举

`parse_error` · `schema_mismatch` · `validation_error` · `auth_error` · `overflow`

两条约定：

1. **分原因是分拣，不是记录**——`parse_error` 修解析、`schema_mismatch` 查上游变更、`auth_error` 查凭证……原因不同排查路径不同，不要只存 error 字符串。
2. **枚举封闭**——命名规范中 DLQ 主题的 `{reason}` 段（§5.2）取值即本枚举；新增原因先扩本枚举，再在主题中使用。

### 5.4 参数规范（可重入 + 可补数的前提，必须写死）

| 规则 | 要求 |
|---|---|
| 分区字段 | **只能**来自 `${system.biz.date}` / `${system.biz.curdate}`，**禁止硬编码日期** |
| 湖表写入 | 用**动态分区覆盖**语义，**不用 append** |
| 任务可重入 | 同一天跑两次，结果必须完全相同 |

**收益**：做到这三条，DS 的「补数」对 Iceberg 就自然成立——补数无非是拿另一个日期参数重跑一遍。

### 5.5 三种工作流模板（照抄，别每次从零拖）

模板是契约与规范在调度层的投影——信封、命名、幂等规则在这里落成可照抄的 DAG。

**任务归属规范（拖模板之前先过这张表）**：判断一个任务该由谁执行，只看一个问题——**这个任务跑完会退出吗？**

| 跑完会退出吗 | 任务在干什么 | 归属 |
|---|---|---|
| **会**（有界） | 搬数据 / SQL 计算 / 跑脚本 / 调外部 API（含启停实时作业） | DolphinScheduler |
| **不会**（无界） | Flink/Spark 长驻作业 | **StreamPark**（DS 侧只留一个 `http` 守护任务，即模板 C） |

三条推论：

1. **实时链路里也有"有界"任务**——CDC 首次全量初始化、每日维表刷新、实时产出后的质量校验。它们归 DolphinScheduler。
2. **离线链路里也可能有"无界"任务**——少见但存在，比如常驻的日志收集。它们归 StreamPark。
3. 所以**"离线/实时"不是归属依据，"有界/无界"才是**——实时和离线不分成两个平台，只分成两种"任务形态"。依据是湖表为两者共同的接口：实时写进 `dwd_order_detail_di`，离线要重跑修正它，这两件事必须落在同一个血缘图里才自洽。

**模板 A · 离线批链路**

```text
1. seatunnel   MySQL → Iceberg ods_order_di（按 ${system.biz.date} 分区）
2. spark       去重 / 清洗 → ods_order_di_clean
3. sql         质量规则 → 输出 OUT 参数 passed = true / false
4. conditions  passed ─┬─ true  → 结束（下游 dependent 任务自动触发）
                       └─ false → 告警 + 阻断下游
```

**模板 B · 实时链路首次启动**（一次性）

```text
1. seatunnel   建 Iceberg 表 / 首次全量初始化
2. http        POST StreamPark 启动 CDC 作业（幂等）
3. http        POST StreamPark 启动下游实时作业
4. http        健康检查，确认 RUNNING
```

**模板 C · 实时守护**（每 5 分钟）—— ⭐ **这个模板是"离线实时一个平台"成立的关键**

```text
1. sql     抢分布式锁（防止并发触发拉起两个实例）
2. http    GET StreamPark 查作业状态
3. switch  RUNNING ─┬─ 是 → 结束
                    └─ 否 → 下一步
4. http    POST StreamPark 拉起（幂等）
5. 告警
```

模板 C 把"实时作业还活着吗"变成了**一个有界任务**。这一招让实时和离线在 DolphinScheduler 里终于是同一个运维视图：同一个工作流列表、同一套告警、同一套权限、同一套审计。模板 C 在 P1 跑通的那一刻，就是"离线实时一个平台"成立的证据（V9，见 §7）。

**衔接三条规则**（模板 B/C 共同遵守，也是"DS → StreamPark OpenAPI"衔接接口的操作约束）：

1. **不要用 DS 的 `flink` 任务类型提交长驻作业。** 它的语义是"提交并等结果"，会占死一个 worker。
2. **启动编排进 DAG，运行守护也进 DAG；拉起动作的唯一出口是模板 C。** 瞬态故障由 Flink 作业自身的 restart strategy 消化（作业不退出）；作业一旦退出（FAILED / CANCELED / 丢失），StreamPark 侧**不配置自动拉起**——只由守护工作流幂等拉起。任何时候全网只有一个控制环，不存在双脑；DS 不管"为什么挂了"（那是诊断，不是守护的职责）。
3. **所有启停必须幂等。** 前置一个 `sql` 任务抢分布式锁（模板 C 第 1 步），或依赖 StreamPark 的重复启动保护——否则补数/重跑会拉起第二个作业实例。

**装什么**：P0 的栈 + SeaTunnel 集群模式 + 主题族规范落地 + **DS 的模板 A / 模板 C 两个工作流（§5.5）** + **dev/prod 两套 DS 环境**（环境拓扑见下） + **Iceberg compaction 作业**（流式入湖必配，见 §9 风险 5） + **Prometheus + Grafana + Alertmanager**（横切栈首期落地：健康四态指标的存储 / 看板与告警中心统一出口，见 §3 横切） + **身份与密钥最小方案**（门户 OIDC 登录；连接器凭证经 K8s Secret 注入作过渡（唯一终点是 Vault，见 §3 横切），禁止入库明文与 Git 明文，见 §3 横切）

**环境拓扑两条约定**（dev/prod 的物理形态，随本期双环境一并落地）：

1. **控制面双环境，数据面单集群**——DS 与门户分 dev/prod；Kafka / 湖 / 仓不拆集群，以 env 维度隔离：主题 `{env}.` 前缀（§5.2 已有）；Iceberg 用 catalog 别名（dev/prod 各一套 warehouse 根路径与元数据 schema，同一个 JdbcCatalog，选型见 §3②）；Doris 用 database 加 `_{env}` 后缀（§2.4 隔离单位在 env 维度的展开，如 `biz` / `biz_dev`）。
2. **prod 写权限仅发布账号持有**——发布 SOP 的"参数/数据源切换"即把作业指向从 dev 别名切到 prod 别名；开发者对 prod 段只读。这是风险 11（发布错配）的结构性缓解，SOP 与发布后校验脚本是其流程兜底。

### 各期完成后的能力台阶（累积视图）

上面七期是**建设视角**（每期装什么、做什么）；本节是**能力视角**——每期验收通过后，平台"长什么样"、谁得到什么。能力是累积的，每期含之前所有期：

```text
P0 能拼起来 ──► P1 进得来 ──► P2 用得上 ──► P3 管得住 ──► P4 取得出 ──► P5 问得准 ──► P6 扛得住
 (内部验证)     (数据入湖)      (口径唯一)     (治理合规)      (服务化)       (AI 问数)      (生产 SLA)
```

| 期 | 一句话效果 | 完成后的能力 | 还没有 |
|---|---|---|---|
| P0 | 能拼起来（内部验证，对业务零价值） | 全组件连通实测：CDC→Kafka→Iceberg→Doris 三条链路通；StreamPark 外部幂等启停；DataHub 采集（复用平台 PG）；《选型验证报告》（兼容矩阵 / 资源预算 / 语义层 spike 与 Dinky 评估结论） | 一切业务能力——无胶水、无门户、无真实数据流 |
| P1 | 进得来（接入自助化） | 新增源 = 门户填一份表单（全程 UI）；离线 + 实时入湖；健康四态与静默告警；DLQ 分类重放；幂等 / 水位正确；模板 C 实时守护（离线实时同一运维视图）；dev/prod 双环境 + 发布 SOP；监控看板；门户最小控制台（OIDC） | 分层数仓、指标、血缘、权限、对外服务 |
| P2 | 用得上（口径唯一） | ODS→DWD→DWS→ADS 分层（DWD 幂等正确）；metric_def + MQL→SQL（一处定义多处复用）；质量阻断（脏数据下游不产出）；数据标准落标拦截；基线 SLA 破线前预警；Doris 物化（1m 粒度 ≤ 3 分钟）；表级血缘最小闭环（DataHub）；集中日志（Loki） | 字段级血缘影响分析、权限脱敏、对外 API |
| P3 | 管得住（可信 / 可控 / 可算账） | 元数据自动采集 + 字段级血缘 + 影响分析；权限 / 脱敏 / 审批 + 审计到人；多租户四层隔离（第二团队入驻互不可见）；成本分摊报表；治理大盘 | 对外 API |
| P4 | 取得出（服务化） | 查询网关三种查询模式（鉴权 / 限流 / 审计）；API 生命周期与版本（破坏性变更升版、旧版可用）；Superset 看板走语义口径（API 与看板数值一致）；调用统计大盘；OTel 链路追踪 | AI 能力 |
| P5 | 问得准（AI 上线） | NL→MQL 问数（与各出口同口径，日志可证不产 SQL）；评测集 ≥80% 门槛可持续回归；诊断助手（结论必带引用）；经 AI 平台模型网关统一模型出口（路由 / 审计 / Token 计量）；Jupyter 探索取数通道 | 生产级 HA / 容灾 |
| P6 | 扛得住（生产可用） | K8s 多副本 HA（杀节点服务不中断、数据不丢）；TLS + 静态加密（合规门槛）；备份恢复经演练（PG PITR / Doris 对象存储）；按 §2.6 生产档 2 倍峰值压测 24h；滚动升级业务无感可回滚 | 多机房容灾、弹性伸缩（规模触发） |

两条要点：

1. **台阶设计的意图**——P1 就有发布治理与监控（不是先跑通再补）；P2 锁住口径与 SLA（治理内建）；P3 权限审计先于 P4 对外开放（先能管才能放）；P5 的 AI 复用 P2 语义层与 P4 网关（不另起炉灶）；P6 之前不对外承诺生产可用（§8 说明 5）。
2. **"还没有"列是刻意的范围切割，不是遗漏**——它是各期"不做"清单的能力视角；补齐时点见各期"装什么 / 做什么"与 §4 后置自研件。

## 8. 工作量与周期

**按 1 名后端 + 1 名数据开发 + 0.5 名前端 + 0.5 名运维**（可并行）：

| 期 | 周期 | 主要工作量 |
|---|---|---|
| P0 选型验证 | 2–3 周 | 装环境、跑通 8 条验证 |
| P1 最小闭环 | 6–8 周 | P1a 接入闭环（配置生成与接入作业管控 + 监控与告警栈 + 门户源注册/状态/健康）+ P1b 链路与发布（模板 A/C + dev/prod 双环境与发布 SOP + compaction + 告警出口） |
| P2 建模与指标 | 8–12 周 | 分层建模 + **语义层（Calcite，单项最大自研）** + 质量规则 + 数据标准落标 + 基线 SLA + 表级血缘 + Loki 集中日志 |
| P3 元数据与治理 | 6–8 周 | DataHub 部署 + 血缘上报器（字段级）+ 权限 + 多租户四层对齐 + 资源配额 |
| P4 服务化 | 4–6 周 | 查询网关 + API 管理 |
| P5 AI 增强 | 6–8 周 | NL→MQL + 评测集 + 助手 + 模型网关接入 |
| P6 生产化 | 8–12 周 | K8s 多副本部署（含 TLS/静态加密落地）+ 备份恢复演练 + 容量规划与压测 + 滚动升级回滚 SOP |
| **合计（P0–P6）** | **40–57 周（约 10–13 个月）** | |

五点说明：

1. **统一门户**（§4 入口）从 P1 最小控制台起步，随 P2–P5 逐期扩展（指标 → 血缘 → 服务 → 问数入口），工作量已含在各期内。
2. **门户降级预案**——若 0.5 前端人力不到位，P1 最小控制台降级为服务端渲染表单页（复用同一套控制面 API 与配置库），门户完整版顺延至前端到位；V10（新增源全程 UI）不受影响——降级的是前端形态，不是入口：**入口始终是 UI 表单，配置始终落平台 PG**。
3. **可并行项**：P3 的 DataHub 部署可与 P2 并行（人够的话）。
4. **单人串行口径**：若为一人执行，按 3 人折算约 **28–39 个月**，且并行项不成立——建议严格按期推进，不跳期。
5. **P6 是对外承诺的分界线**——P0–P5 交付架构正确、功能完整的平台；生产可用（HA / 备份 / 容量）以 P6 完成为准。对外汇报上线时间必须指明口径，避免拿 P5 完成时间当生产承诺。

## 9. 风险与取舍

| # | 风险 | 对策 |
|---|---|---|
| 1 | **开源拼装的"最后一公里"比想象重**（各项目元数据不通） | 自研胶水「元数据上报器」以 **OpenLineage 事件**为契约（§4）；表级血缘随 P2 加工模板落地（先打通 1 条），字段级随 P3 铺开 |
| 2 | **SeaTunnel 驱动/版本兼容** | P0 就验证（V7）；锁版本，建兼容矩阵 |
| 3 | **DataHub 部署重**（多组件） | P0 只验采集能力；完整部署放 P3；或用 OpenMetadata 替代 |
| 4 | **内存预算**（旧项目踩过） | V6 门禁卡住，先算后起；宿主按 §2.6 PoC 档 32G 起（16G 不足以同启 Doris / DS / DataHub + ES） |
| 5 | **小文件**（流式入湖必踩） | compaction 作业在 P1 就要有 |
| 6 | **质量规则阻断误伤生产** | 规则分级 warn/error/**block**，只有核心用 block |
| 7 | **AI 问数不准就上线** | P5 强制评测集门槛（≥80%）才允许上线 |
| 8 | **过度自研**（不知不觉又造引擎） | 严守 §4 的自研边界（1 个入口 + 5 块胶水），新增自研需评审 |
| 9 | **Doris vs ClickHouse 选错** | P0 同时装 ClickHouse 与 Doris，按 V3 同数据量的写入 / 查询实测再定（对照口径按 §2.6 PoC 档） |
| 10 | **契约漂移**（各源自己造信封） | 信封由**配置模板固化**，不靠人自觉 |
| 11 | **dev/prod 发布靠人工导出导入，可能错配数据源/参数** | 结构性缓解：prod 写权限仅发布账号持有（§6 P1 环境拓扑约定 2）；流程兜底：发布 SOP（发布快照入版本库留痕）+ 发布后自动校验脚本（对比两环境任务定义与数据源指向差异）；先人工后工具 |
| 12 | **版本僵化与安全补丁积压**（12+ 开源组件的长期 OPEX，无人管就烂尾） | 版本治理两条约定（§3 横切）：期内冻结 + 半年升级窗口（与选型复查合并）+ 升级即回归 V 清单；兼容矩阵随 P0 建立并持续维护 |

### 三个关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 总线 | **Kafka**（若已有 RocketMQ 则复用） | offset 重放 + compacted topic + 生态最广；纯批量源可不过总线 |
| 湖 vs 仓 | 明细入 **Iceberg**，聚合入 **Doris** | 湖保历史可重放，仓保查询性能 |
| 自研 vs 开源 | **核心引擎开源优先；自研 = 1 个入口 + 5 块胶水** | 商业平台的"控制面全自研"是其产品属性，不是我们的必要成本；但系统入口（WebUI/开放 API）是用户契约，必须自建 |
