# 生产化（p6）

> 状态：⬜ 未开始
> 所属平台与单元：data-platform · p6 生产化（类别：期）
> 对应文档：../通用数据平台建设路线.md（工程路线：§6 p6 排期、§7 V45–V48 通过标准）；../../roadmap/智能通用大数据平台工程师.md（职业路线）

## 目标

从"架构正确"到"**生产可用**"——多副本 HA 落地、备份恢复经过演练、容量有据、升级可回滚。

本单元是**收口型**（形态：收口）：它不新建业务链路，而是把前面各期已建成的链路**抬到生产形态**；**p6 是对外承诺"生产可用"的分界线**——p0–p5 的产出都可以说是"跑得起来"，只有过了 p6 才敢说"敢让它跑"。

## 范围与不做

- **范围**：K8s 多副本部署（含组件间 TLS 与静态加密）；统一备份策略与**恢复演练**；容量规划与压测（按 §2.6 生产档并回填假设）；滚动升级与回滚 SOP。
- **不做**：多机房容灾、自动弹性伸缩（规模触发后再议）。

## 技术栈

- **Kubernetes**（各组件 Helm Chart / Operator；与 AI 平台**共用同一集群、不同队列**）
- **统一备份体系**：Iceberg 快照 · Doris backup · PostgreSQL PITR · MinIO 版本控制（§2.5 约定 2 的落点）
- **TLS / 静态加密**（§3⑥ 约定 3 的落地锚点；密钥托管与 Vault 的分工见实施笔记）
- 自研件一律**无状态、多副本**（§2.5 约定 1），无需专门的高可用改造

## 系统架构

```text
【部署形态跃迁】
p0–p5：单机 Compose / 单集群 ──────────────▶ p6：K8s 多副本（Helm / Operator）
  Kafka 多 broker · Doris 多 FE/BE · PostgreSQL 主备 · Redis · 自研组件多副本（无状态）
  ── 组件间 TLS + 静态加密一并落地 ──

【可靠性四件事】
  ① 故障自愈      ：broker / BE 挂掉 → 服务不中断、数据不丢（随机关节点演练）
  ② 备份与恢复    ：Iceberg 快照 · Doris backup · PG PITR · MinIO 版本控制
                     → **恢复演练**（PG 误删表 PITR 回时间点；Doris 表从对象存储恢复）
  ③ 容量与压测    ：按 §2.6 生产档定初始规格 → 2 倍峰值跑 24h → 延迟与错误率进登记基线
                     → 回填 §2.6 的假设值（未回填前，容量 / SLA / 成本结论按假设口径读）
  ④ 滚动升级与回滚：升级附回滚方案；一个组件滚动升级业务无感；回滚成功
```

## 前置与复用

- **前置单元**：**p1**（dev/prod 双环境与发布 SOP）、**p4**（对外 API——容量的主要消费者）、**p5**（问数链路与 Token 成本口径）；p2 / p3 的 SLA 与配额口径是压测的判据。
- **前置条件**：生产硬件与集群规模确定（§2.6 生产档：6+ 节点 × 32C128G 起）；备份存储容量与保留期确定（湖 3 年 / 仓 1 年）；演练窗口与回滚脚本就绪。
- **复用**：不复用 `algorithms/` 的实验；复用 p0–p5 的部署清单（Compose → Helm 的迁移面在此收口）。
- **产出被谁引用**：本单元即平台对外承诺的生产形态；后续演进（多机房、弹性伸缩、计费）以它为基线。

## 验收标准

- [ ] **V45** 节点故障自愈 —— 随机关一个 Kafka broker / Doris BE → 服务不中断、数据不丢
- [ ] **V46** 备份恢复演练 —— PG 误删表 → PITR 恢复到时间点；Doris 表 → 从对象存储备份恢复成功
- [ ] **V47** 容量压测（§2.6 生产档）—— 2 倍峰值跑 24h，延迟与错误率在登记基线内
- [ ] **V48** 滚动升级可回滚 —— 一个组件 K8s 滚动升级业务无感；回滚成功

**交付物**：K8s 部署清单（Helm / Operator）+ 备份恢复 SOP 与演练记录 + 容量规划文档（含 §2.6 假设回填）+ 压测报告。

## 实施笔记

- **开工前置条件**（2026-09 拟定）：① 生产集群与硬件到位（§2.6 生产档规格）；② 备份存储容量与保留策略批准（湖 3 年 / 仓 1 年，成本按 p3 的单价口径估算）；③ 演练窗口与业务侧告知（故障演练会真的杀节点）；④ 压测数据生成方案（不得用生产 PII 造数）。
- **待决策项**：① K8s 发行版与 Operator 选型收口（Doris / Kafka / DataHub 各自的 Operator 成熟度不一）；② 加密密钥的托管方式与 Vault 的分工（密钥是否统一走 Vault，还是 K8s Secret + 外部 KMS）；③ 容量假设的更新节奏（§2.6 回填频次与责任人）。
