## 1. 分期总览

| 期 | 主题 | 一句话目标 | 验收判据（摘要） |
|---|---|---|---|
| **P0** | 设计 | 把平台设计清楚 | 5 份文档评审通过 |
| **P1** | **最小闭环** | 验证"控制面 + 引擎"抽象是否成立 | **新增一个源只加一份 YAML** |
| **P2** | 建模与指标 | 数据可用 + 口径唯一 | 指标**一次定义、多处复用** |
| **P3** | 治理 | 数据可信、可控、可算账 | 改字段能查出**下游影响面** |
| **P4** | 服务化 | 业务能直接用 | 业务系统调 API 取数成功 |
| **P5** | AI 增强 | 问数与诊断 | 问数准确率**可量化** |

**排序理由**（不是随意排的）：

1. **P1 必须最先**：它验证的是抽象。抽象不成立，后面全是补丁
2. **⑧ 语义层（P2）必须早于 P5 的 AI 应用**：没有统一口径，问数不可能可靠
3. **⑤ 质量（P2）必须早于 P3 治理**：质量结果是治理的输入
4. **④ 血缘（P3）必须早于 P4 服务化**：对外开放数据前要知道影响面

## 3. P1 · 最小闭环（**最重要的一期**）

**目标**：用一条完整链路证明"控制面自研 + 引擎外购"这套抽象成立。

### 3.1 交付物

| # | 交付物 | 说明 |
|---|---|---|
| 1 | **引擎就绪** | SeaTunnel Zeta 单机可跑（compose）；驱动与插件目录规范确定 |
| 2 | **控制面 v0** | 源注册 · 凭证引用 · 配置生成器 · 作业提交 · 状态采集 · 健康四态 |
| 3 | **实时链路** | `MySQL CDC → Kafka → Iceberg ODS` + **compaction 作业** |
| 4 | **离线链路** | `JDBC（分片并行 + 水位）→ Iceberg` |
| 5 | **统一信封** | 固化进配置模板（所有生成作业自动满足） |
| 6 | **DLQ 与重放** | 按原因分类 + 按时间窗重放 |
| 7 | **最小元数据采集** | 源表字段写入 `dataset` / `dataset_field` |
| 8 | **调度接批** | DolphinScheduler 触发一个批作业（含依赖） |
| 9 | **门禁脚本** | 资源预算 · 链路健康 · 端到端 e2e · 重启恢复 |

### 3.2 验收标准（**全部可测**）

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **新增一个源只加一份 YAML** | 演练：加一张新表的同步；计时；全程**不改代码、不登服务器** |
| 2 | **端到端入湖** | 在源库改一行 → 湖表可见（记录延迟） |
| 3 | **幂等** | 重放同一时间窗两次 → 湖表行数与内容不变 |
| 4 | **失败隔离** | 停掉一个源的作业 → 其它源作业与数据流不受影响 |
| 5 | **静默检测** | 人为停 CDC 写入 → 在配置窗口内（如 2 小时）收到静默告警 |
| 6 | **DLQ 可重放** | 注入坏数据 → 进 DLQ（原因正确）→ 修规则 → 按原因重放成功 |
| 7 | **水位正确** | 批任务中途失败 → 重跑 → 不丢不重 |
| 8 | **资源预算** | 所有容器 `mem_limit` 加总 < 宿主机内存 × 0.8（脚本校验） |
| 9 | **门禁全绿** | 4 个门禁脚本全部通过 |

### 3.3 P1 **不做**（范围控制）

- ❌ 指标语义层、数据服务、血缘、权限、AI 应用
- ❌ 文件/对象存储接入（P1.5 或 P2）
- ❌ 推式接入（取决于待定项 #1）
- ❌ 文档/多模态（取决于待定项 #2）
- ❌ K8s（P1 用 compose）

### 3.4 P1 风险

| 风险 | 应对 |
|---|---|
| **驱动 jar 目录官方文档三处不一致** | 落地前实测确认，写进部署规范（见 `数据集成设计.md` §8 附注） |
| 验证环境内存不足（旧实现曾打穿 6GB VM） | 先算资源预算再起容器；门禁脚本卡住 |
| 小文件爆炸 | compaction 作业在 P1 就要有，不留到后面 |
| `checkpoint.interval` 调参无依据 | 压测取数，记录在配置模板注释里 |
| 抽象不成立（发现还是要改代码） | **这正是 P1 要暴露的**——若发生，回头改设计而不是硬扛 |

## 4. P2 · 建模与指标

**目标**：数据可用（分层建模）+ 口径唯一（语义层）+ 质量可拦（前置校验）。

### 4.1 交付物

| # | 交付物 |
|---|---|
| 1 | **数仓分层落地**：ODS → DWD → DWS → ADS（含 DIM） |
| 2 | **建模规范**：命名、分区、幂等、拉链表/快照的选型指南 |
| 3 | **指标语义层**：`metric_def` 唯一来源 + 派生关系 + MQL→SQL 翻译器 |
| 4 | **质量规则引擎**：模板（非空/唯一/范围/枚举/引用/自定义 SQL）+ 事前/事中/事后 + **阻断** |
| 5 | **DWS/ADS 物化**：到 ClickHouse（含降采样 1m/1h/1d） |
| 6 | **加工作业模板**：DWD 清洗、DWS 聚合的可复用模板 |

### 4.2 验收标准

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **指标一次定义、多处复用** | 同一指标在两个不同消费处取数 → 数值一致；改定义 → 两处同时生效 |
| 2 | **口径可追溯** | 任一指标能查到：定义、来源数据集、计算表达式、负责人、版本历史 |
| 3 | **脏数据被阻断** | 注入越界/空值数据 → 质量规则命中 → **下游任务未产出**（不是仅告警） |
| 4 | **DWD 幂等正确** | update/delete 都能正确反映到 DWD（upsert 生效） |
| 5 | **分层可追溯** | 任一 ADS 指标能沿 DWD→ODS 追到源表 |
| 6 | **物化延迟达标** | DWS 1 分钟粒度：可查延迟 ≤ 3 分钟 |

### 4.3 P2 **不做**

- ❌ 字段级血缘、影响分析（P3）
- ❌ 权限与脱敏（P3）
- ❌ 数据服务 API（P4）
- ❌ AI 问数（P5，虽然语义层已就绪）

### 4.4 P2 风险

| 风险 | 应对 |
|---|---|
| 建模规范与实际不符（先写了规范才发现表设计不支持） | 先用 1 个主题域试点，再定规范 |
| 指标口径反复变更 | 口径变更必须升版本 + 记原因；变更影响面用指标血缘看 |
| 质量规则过多导致管道被频繁阻断 | 规则分级（warn / error / **block**），只有核心规则用 block |

## 5. P3 · 治理

**目标**：数据可信（血缘/质量）、可控（权限/脱敏）、可算账（成本）。

### 5.1 交付物

| # | 交付物 |
|---|---|
| 1 | **血缘**：表级 + **字段级**（作业定义 + SQL 解析 + 运行时上报三路合成） |
| 2 | **影响分析**：给定字段/表 → 列出所有下游（表/指标/API） |
| 3 | **权限**：表级 + 字段级；审批流；与查询链路打通（越权返回空而非报错） |
| 4 | **脱敏**：PII 字段按策略掩码，权限不足者只见脱敏值 |
| 5 | **成本归因**：按项目/数据集分摊存储与计算成本 |
| 6 | **治理看板**：资产大盘 · 质量大盘 · 成本大盘 |

### 5.2 验收标准

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **影响分析可用** | 改一个字段 → 系统列出受影响的下游表/指标/API，且与人工核对一致 |
| 2 | **越权不可见** | 无权限用户查询 → 被拒或返回空，且**有审计记录** |
| 3 | **脱敏生效** | 无权限用户查 PII 字段 → 只看到掩码值 |
| 4 | **血缘覆盖率** | 核心表血缘覆盖率 ≥ 90%，且随任务变更**自动更新** |
| 5 | **成本可分摊** | 成本报表能按项目/数据集出数，误差可解释 |
| 6 | **审计可查** | 任一敏感操作（授权/查询/导出）可追溯到人、时间、对象 |

### 5.3 P3 **不做**

- ❌ 对外 API（P4）
- ❌ 完整 Ranger 集成（先用平台内权限，Ranger 留作对接选项）
- ❌ 多租户计费

### 5.4 P3 风险

| 风险 | 应对 |
|---|---|
| 字段级血缘解析准确率低（复杂 SQL） | 三路合成：配置能推的就推，SQL 能解析的就解析，剩下的运行时上报兜底；**标注置信度** |
| 权限改造影响既有查询 | 权限校验放在查询网关统一层，不散落到各服务 |
| 成本数据拿不到（引擎/存储不暴露用量） | 优先用可得的粗粒度指标（存储量、CU 时长），不追求精确 |

## 6. P4 · 服务化

**目标**：业务系统能安全、可控地直接消费数据。

### 6.1 交付物

| # | 交付物 |
|---|---|
| 1 | **数据服务网关**：API 生产 / 管理 / 鉴权 / 限流 / 审计 |
| 2 | **三种查询模式**：`metric_mql`（走语义层）/ `sql_template` / `dataset_query` |
| 3 | **调用统计**：QPS、延迟、错误率、调用方排行 |
| 4 | **API 版本管理**：新增字段兼容、破坏性变更升版本 |

### 6.2 验收标准

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **业务可调** | 业务系统通过 API 取到数据，字段与口径符合预期 |
| 2 | **鉴权生效** | 无 token / 过期 token / 越权 token 均被正确拒绝 |
| 3 | **限流生效** | 超配额调用被限流（返回明确错误，不是超时） |
| 4 | **口径一致** | 同一个指标通过 API 与通过看板取到的数值一致 |
| 5 | **可观测** | 每个 API 的 QPS/延迟/错误率可查 |
| 6 | **变更安全** | 破坏性变更需升版本，旧版本仍可用（灰度下线） |

### 6.3 P4 **不做**

- ❌ API 市场（商业化功能）
- ❌ 计费
- ❌ 拖拽式 API 编排

## 7. P5 · AI 增强

**目标**：让数据"能问"，并且**问得准**。

### 7.1 交付物

| # | 交付物 |
|---|---|
| 1 | **数据分析 Copilot**：自然语言 → **MQL** → 语义层翻译 SQL → 结果 + 口径说明 |
| 2 | **智能诊断助手**：基于 RAG + 工具调用，输出结论必带引用 |
| 3 | **评测集**：问数问题集 + 标准答案，可持续回归 |
| 4 | **兜底策略**：低置信度转人工、越权返回空、幻觉检测 |

### 7.2 验收标准

| # | 验收 | 怎么测 |
|---|---|---|
| 1 | **问数准确率可量化** | 评测集上（如 100 题）与人工核对一致率 ≥ 阈值（如 80%） |
| 2 | **口径可信** | 同一问题多次提问结果一致；数值与人工用 SQL 查的一致 |
| 3 | **不直生成 SQL** | 链路可验证：Agent 产出 MQL，SQL 由语义层生成（日志可查） |
| 4 | **必带来源** | 诊断结论每条都带引用来源，无出处不生成结论 |
| 5 | **低置信度转人工** | 低于阈值时给出"需要人工确认"，不硬答 |
| 6 | **越权返回空** | 无权限数据检索返回空，不报错、不泄露存在性 |

### 7.3 P5 **不做**

- ❌ 自动执行写操作（写库/发货/退款）——只读问数与诊断
- ❌ 无评测集的"能跑就行"

## 8. 验收方法论

**所有验收必须满足三条**：

1. **可测**：有具体的操作步骤与可观测的结果（不接受"体验好""基本可用"）
2. **可复现**：别人按步骤能得出同样结论
3. **尽量自动化**：能写成脚本的写成门禁脚本，进 CI

**验收记录**：每条验收留下**证据**（命令、输出、截图、数据对账结果），归档在 `design/验收记录/`。

## 9. 门禁（每期都要绿）

| # | 门禁 | 内容 |
|---|---|---|
| 1 | **资源预算** | 容器 `mem_limit` 加总 vs 宿主机内存（防打穿） |
| 2 | **配置契约** | 生成的作业配置带统一信封；命名规范校验 |
| 3 | **链路健康** | 各源 lag、DLQ 速率、端到端延迟在阈值内 |
| 4 | **端到端 e2e** | 一条数据从源到湖/仓可见 |
| 5 | **重启恢复** | 引擎重启后作业自动恢复、不丢不重 |
| 6 | **文档一致性** | 设计文档与实现不漂移（配置项/命名/口径） |

> 门禁脚本要**自定位根目录**（`ROOT="$(cd "$(dirname "$0")/.." && pwd)"`），不依赖调用时的 cwd。
