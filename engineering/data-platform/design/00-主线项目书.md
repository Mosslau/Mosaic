## 1. 项目定位

**一句话**：建设一套**通用数据平台**——把多源异构数据可靠地采集、加工、治理、服务化，并以统一的指标语义支撑分析与 AI 应用。

**它服务于谁**：

| 角色 | 用平台做什么 |
|---|---|
| 数据开发 | 配源、配同步、写加工逻辑、看血缘与质量 |
| 数据分析 | 取数、问数（走语义层）、看指标口径 |
| AI 应用开发 | 拿干净的语料与特征、接语义层做问数 |
| 平台负责人 | 看资产、看成本、定 SLA、做容量规划 |
| 业务方 | 通过数据服务 API 消费数据 |

**它不是什么**：不是 BI 工具、不是报表系统、不是单个同步脚本的集合。

---

## 2. 范围

### 做

1. **数据集成**：多源接入（离线 + 实时）、统一事件契约、脏数据与重放
2. **数据开发**：作业定义与版本、加工逻辑（SQL/流作业/Python）
3. **调度**：周期与事件触发、依赖（含跨周期）、回补与重跑
4. **元数据与资产**：元数据采集、目录、血缘、影响分析
5. **数据质量**：规则模板、事前/事中/事后校验、**阻断**
6. **数据安全**：表/字段级权限、脱敏、审批、审计
7. **数据服务**：查询 API、服务管理
8. **语义与指标**：指标一次定义多处复用、指标血缘、NL2MQL2SQL
9. **可观测与成本**：健康、SLA、成本归因、治理看板

### 不做（明确边界，避免职责蔓延）

| 不做 | 原因 |
|---|---|
| 可视化拖拽 IDE | 我们有 Git + YAML + SQL；拖拽带来前端工作量而非平台价值 |
| API 商业化市场 | 先做"数据服务"，市场是商业化功能 |
| 多租户计费 | 除非要对外售卖 |
| 自研调度引擎 | 用 DolphinScheduler；这是纯投入无差异的地方 |
| 自研集成引擎/连接器框架 | 用 SeaTunnel；只在缺口处按 SPI 二开 |
| BI 报表与可视化大屏 | 交给 Grafana / BI 工具 |
| 重造监控体系 | 用 Prometheus + Grafana + OTel |

## 5. 设计原则

| # | 原则 | 含义 |
|---|---|---|
| 1 | **控制面自研、数据面外购** | 引擎不自己写；治理与运营必须自己掌握 |
| 2 | **元数据是中枢** | 血缘、影响分析、成本、权限、质量都挂在数据集这一层 |
| 3 | **一切皆配置 + GitOps** | 源、作业、质量规则、权限策略都可声明式、可 review、可回滚 |
| 4 | **契约先行** | 事件信封、schema、指标口径先定，工具去适配契约（不是反过来） |
| 5 | **失败隔离 + 可重放** | 一源一作业；重放是常规操作，不是应急预案 |
| 6 | **分层交付** | 一次只推进一期，每期有可验证的验收标准 |

补充两条**运行时**原则（借商业平台）：
- **脏数据/质量问题必须能"阻断"**，不只是出报告（WeData 明确强调"防止脏数据向下游蔓延"）
- **AI 不直生成 SQL**：自然语言 → MQL → 语义层确定性翻译成 SQL（WeData 的 NL2MQL2SQL 范式）

## 6. 交付分期

| 期 | 主题 | 核心交付 | 验收判据 |
|---|---|---|---|
| **P0** | 设计 | 本套 5 份设计文档 | 评审通过 |
| **P1** | **最小闭环** | SeaTunnel 跑通 CDC/离线入湖 + 控制面（源/配置生成/提交/健康四态）+ 最小元数据采集 + 调度接批 | **新增一个源只加一份 YAML，不改代码** |
| **P2** | 建模与指标 | 数仓分层（ODS/DWD/DWS/ADS）+ 指标语义层 + 质量校验前置 | 指标**一次定义、多处复用** |
| **P3** | 治理 | 血缘 + 影响分析 + 权限/脱敏 + 成本归因 | 改一个字段能查出**影响哪些下游** |
| **P4** | 服务化 | 数据服务 API + 服务管理 + 语义出口 | 业务系统可直接调 API |
| **P5** | AI 增强 | 数据分析 Copilot · 诊断助手（走语义层） | 问数结果与人工一致率可量化 |

**分期理由**：
- P1 先验证"控制面 + 引擎"这套抽象是否成立——**它成立则后面全是加模块**
- ⑧ 语义层（P2）**必须早于** P5 的 AI 应用：没有统一指标口径，问数不可能可靠
- ⑤ 质量（P2 前置校验）**必须早于** P3 治理：质量是治理的输入

## 7. 平台级成功判据

| # | 判据 | 怎么验证 |
|---|---|---|
| 1 | 新增一个源 = 加配置，不改主链路 | 演练一次并计时 |
| 2 | 任一源故障不阻塞其它源 | 故障注入 |
| 3 | 重放两次，湖/仓结果不变 | 幂等验证 |
| 4 | 端到端延迟有分位指标 | `event_time → 可见` 的 P50/P95/P99 |
| 5 | 静默（无数据）能被告警发现 | 人为停一个源 |
| 6 | 指标口径唯一 | 同名指标跨报表数值一致 |
| 7 | 改字段能查出下游影响面 | 血缘查询 |
| 8 | 脏数据能被阻断且可追溯 | 注入脏数据看下游是否被拦 |

## 8. 关键决策与待定项

### 已定

| 决策 | 结论 |
|---|---|
| 集成引擎 | **SeaTunnel（Zeta）** |
| 总线 | Kafka（**待确认是否复用已有 MQ 中间件**） |
| 湖 / 仓 | Iceberg + MinIO / ClickHouse |
| 平台元数据库 | PostgreSQL |
| 调度 | DolphinScheduler（只管批） |
| 连接器缺口 | 按 **SPI 二开**（加 module，不改内核） |
| MQTT / gRPC | **不做** |
| 消息中间件选型理由 | 见 `数据集成设计.md` §3 |

### 待定（影响 P1 边界）

| # | 问题 | 选项 | 影响 |
|---|---|---|---|
| 1 | **HTTP 推式源收不收** | 收 → 保留薄网关（鉴权+幂等+写 Kafka） / 不收 → 全链路都是 SeaTunnel 去拉 | P1 是否含网关 |
| 2 | **文档/多模态本期是否纳入** | 纳入 → Python 管道单独立项 / 不纳入 → 本期仅结构化与半结构化 | P1 范围与人力 |
| 3 | **roadmap 里的 Go 如何处置** | 保留为学习线 + 本设计标注差异 / 改 roadmap 指派 / 折中 | 影响 930 个 Go 教学文件 |
| 4 | **是否复用已有消息中间件** | 已有 Kafka → 直接用 / 已有 RocketMQ → 复用（状态流另做） / 都没有 → 从零建 Kafka | 总线选型与运维面 |
| 5 | **元数据自研还是用开源** | 自研贴合自己的模型 / 用 OpenMetadata、DataHub 兜底 | P1 元数据采集的实现量 |

## 9. 术语表

| 术语 | 含义 |
|---|---|
| **数据集 dataset** | 源里的一个可采集对象（表/主题/文件前缀）；平台元数据的中枢实体 |
| **事件信封 envelope** | 所有源归一后的统一数据结构（见 `02-数据模型.md` §5.1） |
| **水位 watermark** | 批任务的"上次成功窗口"，用于增量抽取 |
| **游标 cursor** | 流/批任务"读到哪"的位点，与 sink 的 checkpoint 分离 |
| **脏数据 DLQ** | 解析/schema/校验失败的数据，按原因分类，可重放 |
| **健康四态** | 健康 / 降级 / 失败 / **静默** |
| **MQL** | 指标查询语言（指标 + 维度 + 过滤），NL2MQL2SQL 的中间层 |
| **契约 contract** | 信封、schema 版本、指标口径等跨模块的稳定约定 |
