# 最小闭环（p1）

> 状态：⬜ 未开始
> 所属平台与单元：data-platform · p1 最小闭环（类别：期）
> 对应文档：../通用数据平台建设路线.md（工程路线：§6 p1 排期、§7 V9–V17 通过标准）；../../roadmap/智能通用大数据平台工程师.md（职业路线）

## 目标

**新增一个源 = 门户填一份表单**——全程 UI，不改代码、不登服务器、不碰 Git。

本单元是**纵切型**（形态：纵切）：交付一条能独立演示的接入闭环（源 → 信封 → 总线 → 湖），外加把它管起来的最小控制面与发布流程。

**内部里程碑**（两个里程碑各自可演示）：

| 里程碑 | 内容 | 参考工期 |
|---|---|---|
| p1a 接入闭环 | 契约 + 配置生成器 + 作业提交与状态 + 健康四态 + DLQ 重放 + 门户源注册 / 状态 / 健康页 + 监控与告警栈 | 3–4 周 |
| p1b 链路与发布 | 模板 A / 模板 C 工作流 + 实时守护 + Iceberg compaction + dev/prod 双环境与发布 SOP + 门户发布页 | 3–4 周 |

## 范围与不做

- **范围**：实时链路（CDC → Kafka → Iceberg）与离线链路（批入湖）；6 块自研胶水（见「系统架构」）；dev/prod 双环境与发布 SOP；监控与告警栈；门户最小控制台（源注册 / 状态 / 健康 / 发布页）。
- **不做**：指标层（p2）、血缘（p2 / p3）、权限与脱敏（p3）、数据服务（p4）、AI（p5）、文件接入（后置自研件）、K8s（p6）。
- **两类资产的边界**：**平台用户的操作**（源注册、发布）全程 UI + 平台 PG，不碰代码与 Git；**平台团队的资产**（信封 JSON Schema、生成模板、胶水代码、部署清单）保持 Git 版本化——那是平台自身的代码开发，不是平台使用流程。

## 技术栈

- **p0 的栈**（组件版本与兼容矩阵以 [`../p0-selection-validation/README.md`](../p0-selection-validation/README.md) 为准）+ SeaTunnel 集群模式 + 主题族规范落地
- **DS 的模板 A / 模板 C 两个工作流**（§5.5）+ **dev/prod 两套 DS 环境**
- **Iceberg compaction 作业**（流式入湖必配，见 §9 风险 5）
- **Prometheus + Grafana + Alertmanager**（横切栈首期落地：健康四态指标的存储 / 看板 + 告警中心统一出口）
- **身份与密钥最小方案**：门户 OIDC 登录；连接器凭证经 K8s Secret 注入作过渡（**唯一终点是 Vault**），禁止入库明文与 Git 明文

**环境拓扑两条约定**（dev/prod 的物理形态，随本期双环境一并落地）：

1. **控制面双环境，数据面单集群**——DS 与门户分 dev/prod；Kafka / 湖 / 仓不拆集群，以 env 维度隔离：主题 `{env}.` 前缀（§5.2 已有）；Iceberg 用 catalog 别名（dev/prod 各一套 warehouse 根路径与元数据 schema，同一个 JdbcCatalog，见 §3②）；Doris 用 database 加 `_{env}` 后缀（§2.4 隔离单位在 env 维度的展开，如 `biz` / `biz_dev`）。
2. **prod 写权限仅发布账号持有**——发布 SOP 的"参数 / 数据源切换"即把作业指向从 dev 别名切到 prod 别名；开发者对 prod 段只读。这是风险 11（发布错配）的结构性缓解，SOP 与发布后校验脚本是其流程兜底。

## 系统架构

**两条链路 + 一个控制面**（全部落在"双控制面 / 单数据面集群"的环境拓扑上）：

```text
【数据链路】
业务库(CDC) ──▶ ① 统一信封（envelope_version · 双时间 · 幂等键）
                    │
                    ▼
              Kafka 主题族 {env}.{source_type}.{source}.{entity}.{major}
                    │
        ┌───────────┴────────────┐
        ▼ 实时（模板 B/C 守护）    ▼ 离线（模板 A）
   Flink 长驻作业             SeaTunnel / Spark 批作业
        │                         │
        └────────────┬────────────┘
                     ▼
              Iceberg ODS → DWD（湖 = 真相源）
                     │
        坏数据 ──▶ DLQ 主题 {env}.dlq.{source}.{reason}（按原因重放）

【控制链路】
门户（源注册表单 / 状态 / 健康 / 发布页）──▶ 平台 PG（配置库，含版本 / 回滚）
                     │  配置生成器
                     ▼
        SeaTunnel .conf / Flink 配置 / DS 工作流参数
                     │  作业提交与状态（Zeta OpenAPI）
                     ▼
   Zeta 提交 / 停止 / 查状态 ──▶ 健康四态（健康 / 降级 / 失败 / 静默）──▶ 告警出口（Alertmanager）
                     │
   DS 模板 A（离线 DAG）· 模板 C（实时守护：`http` 启停 StreamPark 作业）
```

**本期的 6 块胶水**（§4 自研边界在本期的落地；2–5 同属「配置生成与接入作业管控」，6 是流程而非代码）：

| # | 胶水 | 内容 |
|---|---|---|
| 1 | **契约** | 信封 JSON Schema（Git 版本化管理，随 `envelope_version` 演进，见 §5.1 Schema 演进约定）+ 命名规范 + DLQ 枚举 |
| 2 | **配置生成器** | 读控制面配置库（平台 PG，门户表单维护，含版本 / 回滚）+ 模板 → 生成 SeaTunnel `.conf`（凭证由 K8s Secret 注入，唯一终点 Vault） |
| 3 | **作业提交与状态** | 调 Zeta 提交 / 停止 / 查状态；采集 lag、吞吐、错误率 |
| 4 | **健康四态** | 健康 / 降级 / 失败 / **静默**（按日增量基线判定） |
| 5 | **DLQ 与重放** | 按原因分类；按时间窗重放 |
| 6 | **发布 SOP** | dev 工作流导出 → 参数 / 数据源切换（dev 别名 → prod 别名）→ 导入 prod → **发布快照入控制面版本库**（评审 / 留痕 / 可回滚，§3⑤ 版本化要求的起步落点）→ 上线；附发布后校验脚本 |

## 前置与复用

- **前置单元**：**p0**（兼容矩阵 / 版本锁定 / 资源预算）——p0 未过则本期不启动；本期门禁含 p0 的 **V6（资源预算）**。
- **前置条件**：前端 0.5 人（门户是本期关键路径）；OIDC 身份源可用；DS ↔ StreamPark 的 `http` 任务接口（由 p0 的 V8 验证）。
- **复用**：不复用 `algorithms/` 的实验；复用 p0 锁定的版本与 compose 骨架。
- **产出被谁引用**：p2 以本期的湖表与命名族为输入；p3 以本期的配置库 / DLQ / 审计日志为输入；p6 在本期的 dev/prod 拓扑上演进为生产形态。

## 验收标准

- [ ] **V6（p0 承载，门禁复合项）** 资源预算 —— 资源预算成立 + 链路健康 + 端到端 e2e + 重启恢复四项全绿
- [ ] **V9** DS `http` 任务启停 StreamPark 作业（模板 C 跑通）—— 守护工作流能发现已停止的作业并拉起，且不重复拉起
- [ ] **V10** 新增源全程 UI 表单 —— 不改代码、不登服务器、不碰 Git
- [ ] **V11** 端到端入湖延迟 —— 记录实测值
- [ ] **V12** 幂等重放 —— 两次结果一致
- [ ] **V13** 失败隔离 —— 单源故障不影响他人
- [ ] **V14** 静默检测 —— 窗口内告警
- [ ] **V15** DLQ 按原因重放 —— 重放成功
- [ ] **V16** 水位正确 —— 失败重跑不漏不重
- [ ] **V17** DS 工作流 dev→prod 发布 —— dev 改完经导出导入发布到 prod；发布快照入版本库留痕；prod 产出正确，dev 改动不影响 prod

**交付物**：控制面 v0（源注册 / 配置生成 / 提交 / 状态 / 健康）+ 实时链路 + 离线链路 + 门禁脚本 + **dev/prod 双环境与发布 SOP**（含环境拓扑落地）+ **监控栈**（Prometheus + Grafana 健康看板 + Alertmanager 告警出口）+ **门户最小控制台**（源注册表单 / 状态 / 健康页，OIDC 登录）。

## 实施笔记

- **里程碑与验收的对应**：p1a 覆盖验收 V6 / V10–V16，p1b 覆盖 V9 与 V17（发布与守护属 p1b；验收 8"门禁全绿"是跨里程碑的复合项）。
- **开工前置条件**（2026-09 拟定）：① p0 通过（含 V6 / V8）；② 前端 0.5 人到位（门户是本期关键路径，§8 说明 2 的降级预案是兜底）；③ OIDC 身份源与门户登录打通；④ 主题族与命名规范（§5.2）在配置生成器里固化，不靠人自觉。
- **待决策项**：① 门户前端形态（React SPA vs 服务端渲染表单）——影响 p1a 工期；② 发布快照的存储位置与格式（控制面 PG 版本库，需与 §3⑤ 版本化要求对齐）；③ DLQ 按原因重放的并发与限速策略（避免重放打穿下游）。
