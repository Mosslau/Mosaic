## 1. 三条通道：端到端完整示例

### 1.1 通道① HTTP（设备直连）

```bash
curl -i -X POST http://localhost:18080/api/v1/vehicle/report \
  -H "Content-Type: application/json" \
  -H "X-Device-Token: dev-OV90000001" \
  -d '{"vin":"OV90000001","ts":'"$(date +%s)"',"type":"vehicle_status","data":{"speed":32.5,"soc":78}}'
```

**期望输出**（实测）：

```text
HTTP/1.1 202 Accepted
{"code":0,"message":"accepted"}
```

**Kafka 侧应消费到**（实测，注意 `schema_version` 已自动回填）：

```json
{"vin":"OV90000001","ts":1789700375,"type":"vehicle_status","data":{"speed":32.5,"soc":78},"schema_version":"v1"}
```

```bash
docker exec mosaic-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic vehicle-report-raw --from-beginning --timeout-ms 5000
```

**判定**：HTTP 202 + Kafka 出现同 VIN 消息（`schema_version=v1`）。

### 1.2 通道② MQTT JSON（EMQX 规则 → webhook）

```bash
# ① 确认规则已加载（应有两条）
docker exec mosaic-emqx emqx ctl rules list

# ② 发数据（dev 形态：clientid=dev-{VIN}，匿名，明文 11883）
cd ingest/device-simulator
go run ./cmd/mqtt-simulator -broker tcp://localhost:11883 -devices 10 -interval 2s -duration 10s
```

**期望输出**（实测）：

```text
[     5s] 连接 ok=10 fail=0 | 发布 ok=24 fail=0 | 近5s qps=4.8
===== 压测结束 =====
时长: 10s, 连接成功: 10/10, 发布成功: 47, 失败: 0, 平均 QPS: 4.7
```

**判定**：网关指标出现该通道路径（实测）：

```bash
curl -s localhost:18081/metrics | grep 'gateway_requests_total{path="/api/v1/mqtt/ingest"'
# gateway_requests_total{path="/api/v1/mqtt/ingest",result="ok"} 47
```

### 1.3 通道③ MQTT 二进制（透传 → codec 解码）

**方式 A：模拟器（推荐，最接近真实）**

```bash
cd ingest/device-simulator
go run ./cmd/bin-simulator -broker tcp://localhost:11883 -devices 20 -interval 2s -duration 12s
```

**期望输出**（实测）：

```text
[    12s] 连接 ok=20 fail=0 | 帧 111 | 发布 ok=111 fail=0 | 近5s qps=9.2
```

**方式 B：手工发一帧（用于定位问题，可精确控制字节）**

```bash
FRAME=$(python3 -c "
import base64
f=bytes.fromhex('232302fe'+'4f56323032363030303100000000000000'+'01'+'0021'
  +'1a09110c1e00'+'080101025a26dd00040001040ccc0cd00cc10cc7'+'0901010002474b'+'65')
print(base64.b64encode(f).decode())")
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:18080/api/v1/bin/ingest \
  -H "Content-Type: application/json" -H "X-Webhook-Token: dev-webhook-secret" \
  -d "{\"clientid\":\"dev-OV20260001\",\"topic\":\"ov/OV20260001/bin\",\"ts\":$(date +%s)000,\"payload_b64\":\"$FRAME\"}"
# 期望: 204（受理, 无响应体 —— webhook 惯例; 注意 204 只代表受理不代表已解码）
```

**`ov.raw.binary.v1` 里的信封**（实测）：

```json
{"vin":"OV20260001","ts":1789619400,"proto_ver":"v1","cmd":2,"payload":"IyMC/k9WMjAyNjAwMDEAAAAAAAAAAQAhGgkRDB4ACAEBAlom3QAEAAEEDMwM0AzBDMcJAQEAAkdLZQ=="}
```

**codec 解码产物**（实测，落在 `vehicle-report-raw`）：

```json
{"vin":"OV20260001","ts":1789619400,"type":"battery_status","data":{"voltage":60.2,"current":-5.1,"cell_voltages":[3.276,3.28,3.265,3.271],"probe_temps":[31,35]},"schema_version":"v1"}
```

**判定**：`ov.raw.binary.v1` offset 增加数 == 网关 `bin/ingest ok` 计数；codec 侧 `codec_consumed_total` 同步增长、`codec_consumer_lag` 归零。

## 2. 五环逐环示例（同一请求走完治理链）

**触发方式总表**（实测输出见后）：

| 环节 | 触发方式 | 期望响应 | 指标 result 标签 |
|---|---|---|---|
| 鉴权 | 不带/错 token | `401 UNAUTHORIZED` | `unauthorized` |
| 身份 | token 合法但载荷 `vin` 是**别人的车** | `400 INVALID_DATA`（消息含两个 VIN） | `vin_mismatch` |
| 限流 | 超单设备速率 | `429 RATE_LIMITED` + `Retry-After: 1` | `rate_limited` |
| 校验(解析) | body 非 JSON | `400 INVALID_BODY` | `invalid_body` |
| 校验(契约) | 字段越界 | `400 INVALID_DATA` + 具体原因 | `invalid_data` |
| 投递 | Kafka 不可用 | `500 INTERNAL` | `kafka_error` |
| 正常 | —— | `202` + `{"code":0,"message":"accepted"}` | `ok` |

**① 鉴权拦截**

```bash
curl -i -X POST http://localhost:18080/api/v1/vehicle/report -d '{}'
```
```text
HTTP/1.1 401 Unauthorized
{"code":"UNAUTHORIZED","message":"设备令牌缺失或非法"}
```

**② 限流拦截**（用低阈值实例复现：`RATE_PER_DEVICE=1 RATE_GLOBAL=2 GATEWAY_PORT=18082`）

```bash
for i in 1 2 3; do curl -s -D - -o /dev/null -X POST http://localhost:18082/api/v1/vehicle/report \
  -H "X-Device-Token: dev-OV90000004" \
  -d '{"vin":"OV90000004","ts":'"$(date +%s)"',"type":"vehicle_status","data":{"soc":50}}' \
  | grep -E "^HTTP|^Retry-After"; done
```
```text
HTTP/1.1 202 Accepted
HTTP/1.1 429 Too Many Requests
Retry-After: 1
HTTP/1.1 429 Too Many Requests
Retry-After: 1
```
响应体：`{"code":"RATE_LIMITED","message":"触发限流, 请降速重试"}`；指标：
`gateway_requests_total{...,result="rate_limited"} 3`、`{result="ok"} 1`（**实测**）

**③ 契约校验拦截**

```bash
curl -i -X POST http://localhost:18080/api/v1/vehicle/report \
  -H "X-Device-Token: dev-OV90000001" \
  -d '{"vin":"OV90000001","ts":'"$(date +%s)"',"type":"vehicle_status","data":{"soc":300}}'
```
```text
HTTP/1.1 400 Bad Request
{"code":"INVALID_DATA","message":"soc 超出 [0,100]: 300"}
```

**④ 投递失败（Kafka 不可用）**：`docker pause mosaic-kafka` 后上报 → `500 {"code":"INTERNAL","message":"消息投递失败"}`，指标 `kafka_error`；
恢复 `docker unpause mosaic-kafka` 后由 kafka-go 内部缓冲自动补投（实测 45s 窗口零失败，见《接入层设计》§6）。

## 3. codec 字节级 worked example

### 3.1 一帧 58 字节的完整解剖（与上文 1.3 同一帧）

```text
23 23                       起始符 ##
02 fe                       命令 0x02 实时上报 + 应答 0xFE 无应答
4f 56 32 30 32 36 30 30 30 31   "OV20260001"
00 00 00 00 00 00 00        VIN 右补 0x00 至 17B（《GB32960 映射》§8-①）
01                          不加密
00 21                       数据单元长度 33B（大端）
1a 09 11 0c 1e 00           时间 26-09-17 12:30:00（GMT+8, 《GB32960 映射》§8-③）
08 01 01 02 5a 26 dd        0x08: 1 子系统 / 电压 0x025a×0.1=60.2V / 电流 0x26dd×0.1-1000=-5.1A
00 04 00 01 04              单体总数 4 / 起始序号 1 / 本帧 4 个
0c cc 0c d0 0c c1 0c c7     单体电压 ×0.001 → 3.276 / 3.280 / 3.265 / 3.271 V
09 01 01 00 02 47 4b        0x09: 1 子系统 / 2 探针 → (0x47-40)=31℃ / (0x4b-40)=35℃
65                          BCC（命令单元首字节起逐字节异或）
```

→ 输出一条 `battery_status`（见 1.3 的 JSON）。**判定**：单体电压/V 与帧内十六进制按 ×0.001 换算一致。

### 3.2 全信息体帧（142B → 5 条 L2 消息）

含 0x01 整车 + 0x05 位置 + 0x06 极值 + 0x07 报警 + 0x08 电压 + 0x09 温度 + 0x80 charging + 0x81 work，
按《接入层设计》《GB32960 映射》§8-④ 拆成 **5 条**：

| L2 type | 来源信息体 | 本帧实测值 |
|---|---|---|
| `vehicle_status` | 0x01+0x05+0x06 合并 | speed 32.5 / odometer 12345.6 / soc 78 / lng 113.94 / lat 22.54 / temp_max 35 / temp_min 28 |
| `fault` | 0x07 独立 | `fault_codes: ["E1001"]`（4B hex 大写无前缀，《GB32960 映射》§8-⑤） |
| `battery_status` | 0x08+0x09 合并 | voltage 60.2 / cell_voltages[3.276,3.28] / probe_temps[31,35] |
| `charging` | 0x80 | remain 45min / power 1.5kW / kwh 0.8 / pile 1024 / station 88 / slot 3 |
| `work` | 0x81 | riding / sport / 1200rpm / 12.5N·m / 800W / throttle 60 |

**判定**：`codec_decoded_total` 按 type 分类的增量与上表一致（可用 `curl -s localhost:18090/metrics | grep codec_decoded_total` 核对）。

### 3.3 失败与边界示例

| 场景 | 触发 | 期望 |
|---|---|---|
| 帧同步失败 | 载荷非 `##` 开头 | 帧级 DLQ `stage=parse`，reason 含"帧同步失败" |
| 长度不符 | 改坏长度字段 | 帧级 DLQ `reason=数据单元长度与实际不符` |
| BCC 错 | 翻转校验字节 | 帧级 DLQ `reason=BCC 校验失败` |
| 未知协议版本 | `proto_ver != v1` | 帧级 DLQ（版本纪律：不猜） |
| 自定义单元未知版本 | 0x80 单元版本字节改 0x02 | **单元级** DLQ；同帧其他信息体照常解析 |
| 无效值字段 | 车速填 `0xFFFF` | 该字段丢弃，**不进 DLQ**（不会解出 6553.5km/h） |
| 整帧过短 | 载荷 `##BAD`（5B） | 帧级 DLQ `reason=帧长度不足: 5`（实测见 §4） |

## 4. DLQ 真实样例

**实测记录**（发 `##BAD` 后从 `ov.dlq.codec.v1` 读出，`raw_b64` 截断显示）：

```json
{
  "vin": "OV20260001",
  "stage": "parse",
  "reason": "帧长度不足: 7",
  "raw_b64": "IyNCQkJBRA==…",
  "at": 1789700350
}
```

字段含义：`vin` 来自透传信封主题；`stage ∈ {envelope, parse, vin_invalid, vin_mismatch, decode, validate, encode}`（与 `codec_dlq_total` 的取值一致，见《接入层设计》§9）；`reason` 具体原因；
`raw_b64` **原始帧字节**（排障可完整还原）；`at` 写入时间(Unix 秒)。

```bash
docker exec mosaic-kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic ov.dlq.codec.v1 --from-beginning --timeout-ms 5000
```

**判定**：DLQ 为空即链路健康；有记录先看 `stage`：`parse/decode` 多为对端字节问题，`validate` 多为契约演进不同步，`encode` 为平台侧序列化异常（需查代码），`vin_invalid` 是 **VIN 本身不合契约**（5~32，多因 topic/ACL 配错，查配置而非查设备），**`vin_mismatch` 是安全事件**——设备用自己凭证发自己的 topic，却在帧内填了他人 VIN，已被拦下（未产出任何 L2 数据），按凭证滥用处理。

## 7. 一页判定清单（现象 → 结论 → 下一步）

| 现象 | 结论 | 下一步 |
|---|---|---|
| 模拟器"连接成功"但 EMQX 无客户端/无消息 | 连错 broker（宿主 1883 被别的 MQTT 占用） | 改用 11883（`deploy/.env` 的 `EMQX_MQTT_PORT`） |
| 网关 202 但 topic offset 不涨 | Kafka 写入失败 | 看 `kafka_write_total{result="error"}`；容器内需用 `kafka:9092`（不是 localhost:19092） |
| codec 起不来/不消费，`consumed` 恒 0 | 消费组僵尸成员占分区 | `pkill -f exe/server` + 等 60s |
| `codec_consumer_lag` 持续 >0 | codec 跟不上或下游写慢 | 看 `codec_flush_duration_seconds`/分区数；横扩 codec 副本 |
| `codec_dlq_total{stage="parse"}` 增长 | 对端帧字节有问题 | 取 DLQ 的 `raw_b64` 还原字节，比对《GB32960 映射》§2/§3 |
| `codec_dlq_total{stage="vin_mismatch"}` 增长 | **安全事件**：设备用自己凭证发自己的 topic，却在帧内填他人 VIN | 在 DLQ 的 `reason` 里看两个 VIN（envelope=发送者 / frame=被冒充者），按凭证滥用处理（告警 ⑨） |
| 8883 连不上、日志 `cert_file_not_found` | 未生成证书 | `bash deploy/emqx/gen-certs.sh`（deploy/README §4） |
| 安全自检 ② / ③ 失败 | 一车一密未生效 | 检查 8883 监听器认证配置与 `seed-users.sh` 是否跑过 |
| 安全自检 ④ 失败 | ACL 未生效 | 检查 `deploy/emqx/acl.conf` 与 `authorization` 段 |

## 8. 上报路径、频率与补发（口径速查）

### 2.1 三条上报路径

| 通道 | 链路 | 适用设备 | 治理位置 |
|---|---|---|---|
| ① HTTP | `POST /api/v1/vehicle/report` | App、充电桩、轻量设备 | 网关全权（鉴权+限流+校验） |
| ② MQTT JSON | `ov/{vin}/{status,battery,fault}` → EMQX 规则 → `/api/v1/mqtt/ingest` | 车端 T-BOX（长连接/弱网/省电） | EMQX 管连接/QoS，网关管契约 |
| ③ MQTT 二进制 | `ov/{vin}/bin`（GB/T 32960 帧）→ EMQX 规则(base64) → `/api/v1/bin/ingest` | 真实固件（省流量、标准帧） | 同上；解析归 codec |

### 2.2 topic 契约与 QoS 策略

> 表见《01-接入层设计-v1.md》**§4.2（唯一源）**。记忆要点：周期类（`status`/`bin`）QoS0 可丢；事件类（`fault`）QoS1 必达，重复由下游 `(vin, ts)` 幂等吸收。

### 2.3 频率与补发策略（国标口径，《GB32960 映射》§3.1）

| 场景 | 策略 |
|---|---|
| 正常上送 | 周期 ≤30s，**建议 10s**（模拟器默认 10s） |
| 故障 | 1s 频率补报故障点**前后各 30s** |
| 弱网补发（0x03） | 本地缓存 → 链路恢复补传，窗口 ≤24h；时间=数据发生时间；**热事件优先于普通数据** |
| 去重 | 下游按 `(vin, ts)`（fault 再加 `fault_codes`）幂等 |

### 2.4 身份与安全策略

- 内网路径：1883 明文 + 匿名（dev- 前缀 clientid）；应用层 token 白名单
- 公网路径：**8883 TLS + 一车一密**（username=clientid=VIN，EMQX 内置库）+ **ACL**（只能 pub `ov/${clientid}/#`，越权即断）
- 红线：TLS/一车一密/ACL 未就绪不得开放 8883

## 9. 端到端对账与验证结论（2026-09-17）

| 链路 | 对账结果 |
|---|---|
| 二进制：模拟器 → EMQX → 网关 → Kafka → codec | 发布 191 帧 = 网关受理 191 = codec offset 追平（lag 0），DLQ 0 |

| 黄金样本对拍 | 58B/142B 两份样本双端一致；对拍机制实抓 1 处 0x08 字节错位 |
