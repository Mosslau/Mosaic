## 1. 建设思路

### 核心判断

**不要自研平台，要集成平台。** WeData / DataWorks 之所以是自研控制面，因为它们是商业产品；而它们底下的能力（集成、调度、元数据、质量、BI）在开源生态里**已经有同等成熟度的项目**。我们的工作是把它们**装起来 + 打通 + 补齐契约**。

### 三条原则

| # | 原则 | 含义 |
|---|---|---|
| 1 | **能用成熟开源就不自研** | 每个能力先找 Apache 顶级项目/行业事实标准 |
| 2 | **自研只做"胶水"** | 只写开源之间缺失的粘合层，且必须薄 |
| 3 | **每期可验证** | 每期都有具体命令/数据级的验收，不接受"基本可用" |

### 与商业平台的对应关系

| WeData 模块 | 我们的实现 |
|---|---|
| 数据集成 | SeaTunnel（引擎）+ 自研配置生成 |
| 数据开发 · 编排与调度 | **DolphinScheduler**（唯一编排器） |
| 数据开发 · 离线任务 | DolphinScheduler 自带编辑器（`sql` / `python` / `shell` / `spark` 任务） |
| 数据开发 · 实时作业 | StreamPark（运行时托管）+ Dinky（SQL IDE，可选）—— **不承担编排** |
| 调度 | DolphinScheduler |
| 元数据中心 + 数据资产 | DataHub / OpenMetadata |
| 数据质量 | SQL 规则 + 调度器执行（+ Great Expectations 补强） |
| 数据安全 | Apache Ranger（后置）/ 平台内 RBAC |
| 数据服务 | Spring Boot 查询网关 + Superset |
| 语义建模 | **自研薄层 + Apache Calcite**（差异化核心） |
| 治理中心 | DataHub + Grafana 大盘 |

> **两个 IDE 可以，两个平台不行。** 实时开发者活在 StreamPark/Dinky，离线开发者活在 DolphinScheduler——但**编排、调度、血缘、质量、权限、发布只有一套**。依据是**湖表是两者共同的接口**：实时写进 `dwd_order_detail_di`，离线要重跑修正它，这两件事必须落在同一个血缘图里才自洽。判定规则见 §5.4。

### 企业级能力全景与本文档的覆盖度

商业平台（DataWorks / WeData / DataLeap）的官方模块清单可抽象为 **5 个面 × 15 个能力域**：

| 面 | 能力域 | 本文档的实现 |
|---|---|---|
| 数据面 | 接入 / 存储 / 计算 | SeaTunnel + Flink CDC / Iceberg + MinIO + Doris / Spark + Flink + Trino |
| 开发面 | 任务开发 / 编排调度 / **版本与发布** / 运维中心（**基线 SLA**） | DS + StreamPark / DS / **见下方"本次补入"** / DS 告警 + 基线 |
| 治理面 | 建模与标准 / 元数据资产 / 质量 / 安全 | 分层规范 + 语义层 / DataHub / SQL 规则 + 阻断 / 平台内 RBAC（Ranger 后置） |
| 消费面 | 数据服务 / 分析 BI / AI | 自研网关 + Superset / Superset / 自研 MQL（P5） |
| 平台面 | 平台工程（**多租户** / 配额 / 审计 / 备份灾备） | 见下方"本次补入"与"后置" |

**"成熟企业级"与"能跑"的分水岭，不是模块数量，而是 6 条横切判据**——每个模块都得满足：

| 判据 | 不过线的后果 |
|---|---|
| 多租户与配额 | 一个烂任务拖垮全平台 |
| 发布治理（dev/prod/版本/回滚） | 改错一个任务直接污染生产 |
| SLA 基线 | 产出迟到无人知、无人担责 |
| 审计合规 | 金融 / 政企场景不可上线 |
| 成本可算 | 平台变成无主的成本黑洞 |
| 开放 API | 平台变孤岛，无法嵌入企业流程 |

**覆盖度盘点**（拿全景对照本文档）：

| 档位 | 能力域 |
|---|---|
| ✅ 已覆盖且可验证 | 接入、存储、计算、开发编排、调度补数、血缘、质量阻断、语义层、数据服务、BI、AI 问数 |
| 🟡 半覆盖 | 成本（有验收无设计）、安全（后置）、建模（有分层无落标机制） |
| 🆕 本次补入路线 | **发布流程（P1）、基线 SLA（P2）、数据标准落标（P2）、多租户最小集（P3）** |
| ⏸️ 明确后置（规模触发） | 备份灾备、成本精细治理、数据推送/订阅、资产健康度、特征平台 |
| 🚫 明确不做 | 统一门户、计量计费、自建 Web IDE（触碰 §4 自研边界） |

**多租户最小集约定**（四层对齐；前期不做，后期改造成本极高）：

| 层 | 隔离单位 |
|---|---|
| DolphinScheduler | 租户 / 项目 |
| DataHub | domain |
| Iceberg | namespace |
| Doris | database |

**从商业平台学到的一个设计哲学**：模块顺序是"管理中心 → 集成 → 建模/标准 → 开发 → 运维 → 治理 → 消费"——**底座先行、标准先行、治理贯穿**，而不是"先跑通再补治理"。因此发布、基线、标准、多租户这四件事不等 P3，最小版直接进 P1/P2。

## 2. 开源选型总表

**选型标准**：① Apache 顶级项目 或 行业事实标准；② 有商业公司或大厂背书；③ 社区活跃（近半年有 release）；④ Java 生态优先。

### 2.1 存储与计算

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| 消息总线 | **Apache Kafka 3.x（KRaft）** | RocketMQ 5.x / Pulsar | Java/Scala | 流式事实标准；KRaft 后免 ZooKeeper |
| 湖表格式 | **Apache Iceberg 1.6+** | Hudi / Paimon / Delta | Java | 开放表格式事实标准（Netflix/Apple/AWS） |
| 对象存储 | **MinIO** | Ceph / 云 OSS / S3 | Go | S3 兼容事实标准 |
| OLAP 仓 | **Apache Doris 2.x** | ClickHouse / StarRocks | Java+C++ | Apache TLP；MySQL 协议；运维简单；Unique Key 支持 upsert |
| 交互查询（湖上） | **Trino** | Spark SQL | Java | 联邦查询事实标准（可选） |
| 流计算 | **Apache Flink 1.20** | Spark Structured Streaming | Java/Scala | 流计算事实标准 |
| 批计算 | **Apache Spark 3.5** | Flink 批模式 | Scala/Java | 批计算事实标准 |
| 平台元数据库 | **PostgreSQL 16** | MySQL | — | —— |
| 缓存 / 状态 | **Redis 7** | —— | C | —— |

### 2.2 集成 / 编排 / 运行时（**分层看，不要混在一张表里比**）

选型最容易犯的错，是把"集成""开发""调度"当成同一层的三个能力去比较。它们分属三层，**判断自己该放哪一层，只看一个问题：这个任务跑完会退出吗？**（判定规则见 §5.4）

#### 集成层 —— 数据怎么进湖

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| **数据集成** | **Apache SeaTunnel 2.3.x（Zeta 引擎）** | DataX（仅离线）/ Flink CDC | Java | Apache TLP；**~200 连接器**；批/流/CDC 一体；**逐 job 连接器依赖隔离** |
| CDC 采集 | **Flink CDC 3.x** | Debezium + Kafka Connect | Java | Apache；全量+增量无缝一体（事实标准） |

#### 编排层 —— 谁决定"什么时候跑、按什么顺序跑"（**只有一个**）

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| **编排 / 调度 / 补数** | **Apache DolphinScheduler 3.x** | Apache Airflow（Python，与 Java 主栈不符） | Java | Apache TLP；官方文档任务类型 **36 种**；`dependent` 任务做跨周期依赖；**同一套工作流既能编排有界任务，也能编排实时作业的启停守护** |
| 离线任务编写 | DolphinScheduler 自带编辑器（`sql` / `python` / `shell` / `spark` / `stored-procedure` / `http` 任务） | —— | Java | 不需要额外组件 |
| 分布式任务编排插件 | **不自研**，只用 DS 现有任务类型 | —— | —— | 少一个自研物就少一处长期维护 |

#### 运行时层 —— 长驻作业谁托管

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| **实时作业托管**（Flink/Spark 长驻作业的生命周期：启停 / Savepoint / 监控 / 告警） | **Apache StreamPark** | Dinky | Java | **2025-01 毕业的 Apache TLP**；应用全生命周期管控 |
| 实时 SQL 开发体验（多语句 IDE / 血缘 / 版本对比 / 逻辑计划） | Dinky | —— | Java | ⚠️ **非 ASF 项目**（DataLinkDC 社区项目）。功能明显强于 StreamPark，但治理与发版节奏需在 P0 评估 |

#### 平台服务

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| 平台服务框架 | **Spring Boot 3** | Quarkus / Micronaut | Java | Java 事实标准 |
| 配置中心 | **Nacos** | Apollo | Java | 国内成熟（可选） |
| 对象存储/网关 | **Spring Cloud Gateway** | Apache APISIX | Java | Spring 事实标准 |

> **分层铁律**：编排层一个（DolphinScheduler）；运行时层可以两个（DS 管有界任务、StreamPark 管无界作业）。**实时和离线不分成两个平台，只分成两种"任务形态"。**

### 2.3 治理与语义

| 能力 | 首选 | 备选 | 语言 | 成熟度依据 |
|---|---|---|---|---|
| **元数据 / 血缘 / 资产目录** | **DataHub** | OpenMetadata / Apache Atlas | Java + Python | LinkedIn 开源；生态最广；血缘与影响分析成熟 |

### 2.5 **明确不选**的（避坑）

| 不选 | 原因 |
|---|---|
| **Apache Griffin**（数据质量） | **已退役进 Attic** |
| Apache Sqoop | 已退役 |

## 3. 目标架构

```text
┌─ 用户与接入 ───────────────────────────────────────────────────────────┐
│  DolphinScheduler UI · DataHub UI · Superset · 自研门户/API（可选）    │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 控制面（集成成熟开源 + 5 块自研胶水）─────────────────────────────────┐
│  编排/调度/补数  Apache DolphinScheduler（唯一编排器）                 │
│  实时作业托管    Apache StreamPark（被 DS 经 OpenAPI 启停）            │
│  元数据/血缘     DataHub                                               │
│  质量规则        SQL 规则（调度执行）+ Great Expectations（补强）      │
│  指标语义        【自研】metric_def + MQL→SQL（Apache Calcite）        │
│  查询网关        【自研】Spring Boot（鉴权/限流/审计）                 │
│  配置生成        【自研】YAML → SeaTunnel/Flink/Spark 作业配置         │
│  元数据上报      【自研】作业血缘 → DataHub                            │
│  契约           【自研】信封 / 命名 / DLQ 原因枚举                     │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 数据面（全部成熟开源）────────────────────────────────────────────────┐
│  集成    Apache SeaTunnel(Zeta)   ← 离线 + 实时 + CDC 统一入口         │
│  有界任务 DolphinScheduler Worker（SQL / Shell / Spark / SeaTunnel）   │
│  无界作业 StreamPark 托管的 Flink / Spark 长驻作业                     │
└────────────────────────────┬───────────────────────────────────────────┘
                             │
┌─ 存储 ─────────────────────────────────────────────────────────────────┐
│  Kafka 总线 · Iceberg+MinIO 湖 · Apache Doris 仓 · PostgreSQL · Redis  │
└────────────────────────────────────────────────────────────────────────┘

横切：Prometheus + Grafana + OTel（可观测）· DataHub（元数据中枢）
```

**关键结构差异（对照商业平台）**：我们把"控制面"拆成 **成熟开源（调度/元数据/质量）+ 5 块自研胶水**；而商业平台是整个控制面自研。

### 3.1 编排层 ↔ 运行时层的衔接（**全平台唯一的跨层接口**）

DolphinScheduler **不直接提交长驻作业**，而是用 `http` 任务调 StreamPark OpenAPI：

```text
DS `http` 任务 ──POST（启动/停止/查状态）──> StreamPark OpenAPI ──> Flink/Spark 长驻作业
              <───────── 状态回读 ─────────
```

三条规则：

1. **不要用 DS 的 `flink` 任务类型提交长驻作业。** 它的语义是"提交并等结果"，会占死一个 worker。
2. **启动编排进 DAG，运行守护也进 DAG，但重启决策归 StreamPark。** DS 只管"它该在跑"和"不在就拉起"，不管"为什么挂了"。
3. **所有启停必须幂等。** 前置一个 `sql` 任务抢分布式锁，或依赖 StreamPark 的重复启动保护——否则补数/重跑会拉起第二个作业实例。

> ⚠️ StreamPark OpenAPI 的**鉴权方式（access token）与重复启动的幂等行为**属于外部假设，**必须在 P0 实测**（见 §6 P0 的 V8）。这条不成立，整个衔接方式就要换。

## 4. 自研边界（**只有 5 块，且都要薄**）

| # | 自研块 | 为什么必须自研 | 复杂度 |
|---|---|---|---|
| 1 | **契约**（事件信封 / 命名规范 / DLQ 原因枚举） | 开源项目之间没有统一契约，这是"拼装平台"的粘合剂 | 低（文档 + 一份 JSON Schema） |
| 2 | **配置生成器**（YAML → SeaTunnel/Flink/Spark 配置） | 把"加一个源"从写配置变成填 YAML；这是平台化的核心动作 | 中 |
| 3 | **元数据上报器**（作业血缘 → DataHub） | 开源项目各自不知道对方的存在。它**拉取 DS 工作流定义 + SeaTunnel 配置**，解析出输入/输出表后推给 DataHub（SQL 解析复用 DataHub 生态自带能力，不自己写） | 中 |
| 4 | **指标语义层**（metric_def + MQL→SQL，基于 Calcite） | 开源里没有贴合我们口径模型的语义层；**也是 AI 问数的前提** | 高（差异化核心） |
| 5 | **查询网关**（Spring Boot：鉴权/限流/审计） | 统一对外出口；权限与审计必须自己掌握 | 中 |
| （可选） | 推式接入网关 | 若需接收 webhook 推送（SeaTunnel 的 Http 是拉式） | 低 |

**其余一律不自研。**

## 5. 契约与规范（自研块 #1）

### 5.1 统一事件信封

所有源进总线前转成它（由配置模板固化，不靠人自觉）：

```json
{
  "envelope_version": "1",
  "source": "biz-mysql",
  "source_type": "cdc",
  "tenant": "biz",
  "entity_type": "order",
  "entity_id": "1001",
  "event_type": "updated",
  "event_time": "2026-09-24T10:15:30Z",
  "ingest_time": "2026-09-24T10:15:31Z",
  "idempotency_key": "cdc:biz-mysql:orders:1001:u:1727080530123",
  "payload": { "…源字段原样…" }
}
```

两条铁律：`payload` **保持源原貌**；`event_time` 与 `ingest_time` **必须都留**（否则分不清"数据延迟"和"源时钟不准"）。

### 5.2 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| 主题 | `{env}.{source_type}.{source}.{entity}.v{major}` | `prod.cdc.biz-mysql.order.v1` |
| DLQ 主题 | `{env}.dlq.{source}.{reason}` | `prod.dlq.biz-mysql.schema_mismatch` |
| 湖表 | `{layer}_{entity}_{suffix}` | `ods_order_event` / `dwd_order_event` |
| 仓表 | `{layer}_{entity}_{grain}` | `dws_order_1m` / `ads_order_daily` |
| 工作流 | `ws_{产出表名}` | `ws_dwd_order_detail_di` |
| 任务（工作流内节点） | `{产出表名}` | `dwd_order_detail_di` |
| 作业 | `{env}-{source}-{entity}` | `prod-biz-mysql-order` |
| 指标 | `{domain}_{measure}_{grain}` | `order_amt_1d` |

### 5.3 DLQ 原因枚举

`parse_error` · `schema_mismatch` · `validation_error` · `auth_error` · `overflow`
（分原因是**为了排查路径不同**；不要只存 error 字符串）

### 5.4 数据开发的任务归属（**有界 / 无界判定**）

每个任务上线前必须过这张判定。**归错层就是运维事故**（最典型：拿 DS 的 `flink` 任务交一个永不退出的作业，占死 worker）。

**只问一个问题：这个任务跑完会退出吗？**

| 跑完会退出吗 | 任务在干什么 | 归属 | DS 侧用什么任务类型 |
|---|---|---|---|
| **会**（有界） | 搬数据 | DolphinScheduler | `seatunnel` |
| **会**（有界） | SQL 计算 | DolphinScheduler | `sql`（库内）/ `spark`（大数据量） |
| **会**（有界） | 写代码 | DolphinScheduler | `python` / `shell` / `java` |
| **会**（有界） | 调外部 API、启停实时作业 | DolphinScheduler | `http` |
| **不会**（无界） | Flink/Spark 长驻作业 | **StreamPark** | DS 侧只留一个 `http` 守护任务（模板 C） |

三条推论：

1. **实时链路里也有"有界"任务**——CDC 首次全量初始化、每日维表刷新、实时产出后的质量校验。它们归 DolphinScheduler。
2. **离线链路里也可能有"无界"任务**——少见但存在，比如常驻的日志收集。它们归 StreamPark。
3. 所以**"离线/实时"不是归属依据，"有界/无界"才是**。这就是为什么不需要两套数据开发平台。

**参数规范（可重入 + 可补数的前提，必须写死）**

| 规则 | 要求 |
|---|---|
| 分区字段 | **只能**来自 `${system.biz.date}` / `${system.biz.curdate}`，**禁止硬编码日期** |
| 湖表写入 | 用**动态分区覆盖**语义，**不用 append** |
| 任务可重入 | 同一天跑两次，结果必须完全相同 |

做到这三条，DS 的「补数」对 Iceberg 就自然成立——补数无非是拿另一个日期参数重跑一遍。

### 5.5 三种工作流模板（**照抄，别每次从零拖**）

**模板 A · 离线批链路**

```text
1. seatunnel   MySQL → Iceberg ods_order_di（按 ${system.biz.date} 分区）
2. spark       去重 / 清洗 → ods_order_di_clean
3. sql         质量规则 → 输出 OUT 参数 passed = true / false
4. conditions  passed ─┬─ true  → 结束（下游 dependent 任务自动触发）
                       └─ false → 告警 + 阻断下游
```

**模板 B · 实时链路首次启动**（一次性）

```text
1. seatunnel   建 Iceberg 表 / 首次全量初始化
2. http        POST StreamPark 启动 CDC 作业（幂等）
3. http        POST StreamPark 启动下游实时作业
4. http        健康检查，确认 RUNNING
```

**模板 C · 实时守护**（每 5 分钟）—— ⭐ **这个模板是"离线实时一个平台"成立的关键**

```text
1. sql     抢分布式锁（防止并发触发拉起两个实例）
2. http    GET StreamPark 查作业状态
3. switch  RUNNING ─┬─ 是 → 结束
                    └─ 否 → 下一步
4. http    POST StreamPark 拉起（幂等）
5. 告警
```

模板 C 把"实时作业还活着吗"变成了**一个有界任务**。这一招让实时和离线在 DolphinScheduler 里终于是同一个运维视图：同一个工作流列表、同一套告警、同一套权限、同一套审计。

> **验收点**：模板 C 在 P1 跑通——那一刻就是"离线实时一个平台"成立的证据（见 §7 的 V9）。

| P2 建模与指标 | 6–8 周 | 分层建模 + 语义层（Calcite）+ 质量规则 + 数据标准落标 + 基线 SLA |
| P3 元数据与治理 | 6–8 周 | DataHub 部署 + 血缘上报器 + 权限 + 多租户四层对齐 |
| P4 服务化 | 4–6 周 | 查询网关 + API 管理 |
| P5 AI 增强 | 6–8 周 | NL→MQL + 评测集 + 助手 |
| **合计** | **28–39 周（约 7–10 个月）** | |

**可并行的**：P3 的 DataHub 部署可与 P2 并行（人够的话）。

## 9. 风险与取舍

| # | 风险 | 对策 |
|---|---|---|
| 1 | **开源拼装的"最后一公里"比想象重**（各项目元数据不通） | 自研块 #3（元数据上报器）优先做；先打通 1 条血缘，再铺开 |
| 2 | **SeaTunnel 驱动/版本兼容** | P0 就验证（V7）；锁版本，建兼容矩阵 |
| 3 | **DataHub 部署重**（多组件） | P0 只验采集能力；完整部署放 P3；或用 OpenMetadata 替代 |
| 4 | **内存预算**（旧项目踩过） | V6 门禁卡住，先算后起 |
| 5 | **小文件**（流式入湖必踩） | compaction 作业在 P1 就要有 |
| 6 | **质量规则阻断误伤生产** | 规则分级 warn/error/**block**，只有核心用 block |
| 7 | **AI 问数不准就上线** | P5 强制评测集门槛（≥80%）才允许上线 |
| 8 | **过度自研**（不知不觉又造引擎） | 严守 §4 的 5 块边界，新增自研需评审 |
| 9 | **Doris vs ClickHouse 选错** | P0 用 V3 实测同数据量下的写入与查询表现再定 |
| 10 | **契约漂移**（各源自己造信封） | 信封由**配置模板固化**，不靠人自觉 |
| 11 | **dev/prod 发布靠人工导出导入，可能错配数据源/参数** | 发布 SOP + 发布后自动校验脚本（对比两环境任务定义与数据源指向差异）；先人工后工具 |

### 三个关键取舍

| 取舍 | 选择 | 理由 |
|---|---|---|
| 总线 | **Kafka**（若已有 RocketMQ 则复用） | offset 重放 + compacted topic + 生态最广；纯批量源可不过总线 |
| 湖 vs 仓 | 明细入 **Iceberg**，聚合入 **Doris** | 湖保历史可重放，仓保查询性能 |
| 自研 vs 开源 | **开源优先，自研只 5 块** | 商业平台的"控制面全自研"是其产品属性，不是我们的必要成本 |
