## 1. 物种定位与演进站位

| 产品 | 演进站位 |
|:--|:--|
| **Claude Code** | **完整现代范式**（14 维全经历，闭源打磨） |
| **Codex** | **完整现代范式**（14 维全经历，闭源打磨） |
| **DeepSeek Harness (dsh)** | **完整现代范式**（14 维全经历，且可替换） |

## 2. 统一坐标系：感知 → 推理 → 行动 → 观察

| 阶段 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **感知 Perceive**（看到什么） | 读文件/grep + CLAUDE.md + Skills 渐进加载 | 读文件/rg + AGENTS.md | **claim 输入 + 从事件日志派生历史** | 输入节点 + 知识检索节点（RAG） |
| **推理 Reason**（怎么想） | Claude 模型推理 | 模型推理 + update_plan 计划 | agent/request → llm/stream | Agent 节点内 FC / ReAct 策略 |
| **行动 Act**（干什么） | 工具调用（PreToolUse hooks 拦截） | 工具调用（沙箱权限判定 + 审批） | tool/call → pre-execute → execute → post-execute | 工具节点（插件市场） |
| **观察 Observe**（看到结果） | 工具结果回填 | 结果回填 + checkpoint 落盘 | **tool/result 写入事件日志** | 结果沿 DAG 流转到下一节点 |

**关键发现**：四款的循环内核没有本质差别，**差异全在循环外的工程**——拦截点位置、记忆管理、停止判定、可回放性。这印证了"Agent = Model + Harness"：模型都差不多，Harness 决定上限。

## 3. 四款 Loop 流程

> 四款流程为缩略图，事件/工具名等细节以 [../Agent产品对比/](../Agent产品对比/README.md) 01-04 单篇为单一事实源。

**① Claude Code：单会话自由循环 + Hooks 硬控制**

```text
用户指令
  → 上下文组装（CLAUDE.md + Skills 渐进加载 + 历史记忆）
  → [UserPromptSubmit hook]
  → 模型推理（Claude）
  → 工具调用 ──[PreToolUse hook: 可阻止]──> 执行 ──[PostToolUse/PostToolUseFailure hook]──> 结果回填
  → 模型继续推理（循环）……直到任务完成 / /compact 压缩上下文 / 权限拦截 / 预算耗尽
  → [Stop hook] → [SessionEnd hook]
```

设计要点：**循环归属模型（自由），控制点归属 hooks（确定性）**——17 个事件覆盖工具调用前后、权限请求、压缩前、子代理启停、任务完成、worktree 生命周期；子代理循环可被 SubagentStart/Stop 拦截；/loop（会话级定时）、/schedule（持久化）、CronCreate 把循环延伸到"自驱动"；停止条件 = 任务完成判定 + 权限拦截 + /compact 兜底 + 会话级超时。

**② Codex：沙箱内循环 + Goal 跨会话 + 可重放**

```text
（沙箱内）
用户目标 → update_plan 建计划 → 模型推理 → 工具调用（沙箱权限判定：writable_roots / require_escalated / 审批）
  → 结果回填 → 更新 plan → 继续（并行 agent 可同时跑多个子循环）
  → 会话结束 → checkpoint 落盘（state_5.sqlite / history.jsonl）
（跨会话）
create_goal（带 token 预算）→ 新会话 get_goal 恢复目标 → 继续迭代 → 预算耗尽或完成
```

设计要点：循环边界靠**沙箱**（安全）而非模型自觉；**plan 工具**让循环"有计划"；**goal 工具**让循环"跨会话"（目标 + token 预算 + 完成状态持久化）；**checkpoint/replay** 任意一步可回滚重放；并行子代理多循环同时跑。

**③ DeepSeek Harness：turn/step 两段式 + 事件日志单一事实源**

```text
turn/start
  claim 输入（next-step 输入 + 一条排队消息）
  组装 prompt 分区 + 工具 schema
  → agent/pre-step（waterfall：拒绝(reject) 或 进入(enter)；拒绝或首个 enter 为空 → 零 step 关 turn，日志记录尝试）
  step/start
    输入以 user/message 追加
    从日志派生模型历史（deriveMessages）
    agent/request → llm/stream → assistant/chunk* → assistant/message
    tool/call* → tools/pre-execute → tools/execute → tools/post-execute → tool/result*
  step/end
  · 工具还欠请求或有新输入 → 下一 step
  → agent/turn-stopping（串行终检点）
turn/end
```

设计要点（企业级 loop 的范本）：turn/step 两段式（step = 一次模型请求 + 工具调用，最小可审计单元）；三层事件域（Session 持久事实 / Agent 活体协调 / Capability 接缝策略）；单一事实源不变式 `model-visible means logged`；四位置瀑布拦截（pre-step / request / llm-stream / tools）+ turn-stopping 串行终检；失败恢复（request-error 瀑布 + compaction 代际推进）；**循环可替换**（Agent 接口零循环依赖，driver 是插件）。

**④ Dify：显式工作流 DAG + 节点内隐式循环**

```text
（应用层：显式图）
用户输入 → Chatflow DAG 开始
  → 知识检索节点（RAG）→ 条件节点（分支）→ Agent 节点 ═══> Answer 节点 → 返回
                                    ↓（Agent 节点内部：隐式循环）
                              function-calling / ReAct 策略
                              模型推理 → 工具调用 → 结果回填 → 迭代（≤ 最大轮数）
                              → 节点结束，输出沿 DAG 继续流转
```

设计要点：**循环归属"图"**——收敛路径显式定义，分支/回退/循环边可见可控（Graph Engineering 产品化）；**隐式循环被关进节点**（自由度只在 Agent 节点内，受"最大迭代轮数"硬约束）；Chatflow 中间可插人工确认节点；可观测是平台级（每次运行有日志与成本记录）。

**⑤ Loop 设计对比表**

| 设计维度 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **循环粒度** | 会话级（一次对话） | 会话级 + Goal 跨会话 | **turn/step 两段式** | 工作流级（节点内 step） |
| **循环归属** | 模型（自由） | 模型 + 沙箱约束 | 可替换的 driver 插件 | **图（显式）** + 节点内模型 |
| **停止条件** | 任务完成/预算/权限 | 任务完成/goal 预算/沙箱 | 无欠账 + turn-stopping + 硬边界 | DAG 走完/节点最大轮数 |
| **拦截点** | 17 个 hooks | approval 策略 | **pre-step/request/tools 瀑布** | 节点边界（图级） |
| **可回放** | 会话恢复（/resume） | **checkpoint 回滚重放** | **事件日志完整重建** | 对话日志 |
| **记忆** | CLAUDE.md + 会话 | AGENTS.md + goal | 事件日志（事实）+ 插件记忆 | 知识库 + 会话变量 |
| **安全边界** | 权限匹配 + hooks | 沙箱（最严） | sandbox/guard 插件 | 多租户 + RBAC |
| **跨会话** | /resume + /schedule | **Goal（token 预算）** | 会话持久化 + resume | 应用级持久对话 |
| **自主循环** | /loop、/schedule、cron | goal + sandbox + parallel | schedule + goal + workflow 插件 | 定时触发 + 工作流 |

## 4. 机制深对比（五张表）

**① 上下文管理机制对比**

| 机制 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **会话上下文** | 上下文窗口 + `/compact` 手动/自动压缩 | 上下文窗口 + checkpoint 分段 | **事件日志投影**（`deriveMessages()`，不信任内存状态） | 会话变量 + 知识库检索回填 |
| **压缩策略** | `/compact` 摘要 + `PreCompact` hook 可干预 | 隐式（靠会话分段/checkpoint 控制窗口） | **compaction 插件**：压力检测 → 工具结果剪枝 → 选摘要 → **"代际推进"后才允许开重试 turn** | 对话轮次截断 + 变量引用 |
| **项目记忆** | CLAUDE.md（每会话注入） | AGENTS.md | context/workspace 插件 | 知识库 + 系统提示词配置 |
| **核心差异** | 压缩靠 hook 编程干预 | 压缩靠分段隔离 | **压缩有可验证语义**（不推进代际就不重试，杜绝"压缩失败还硬重试"） | 压缩靠平台配置 |

> 要点：上下文管理不是"塞更多"，而是**何时压缩、压缩后能否安全重试**——dsh 把这件事做成了有严格语义的机制，其余三者靠人工/经验兜底。

**② 失败恢复机制对比**

| 失败类型 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **工具执行失败** | `PostToolUseFailure` hook（可编程补救） | 沙箱内重试 / 升级审批 | `tools/post-execute` + `agent/request-error` 瀑布 | 节点错误分支（图级容错） |
| **模型请求失败** | 内置重试 | 内置重试 | **request-error 瀑布**：返回 `{kind:'retry'}` 或保留原始错误（权威性明确） | 节点重试配置 |
| **上下文溢出** | `PreCompact` hook 兜底 | checkpoint 回退到分段 | **compaction 代际替换**：剪枝/摘要推进代际后才开新重试 turn | —（靠截断） |
| **崩溃恢复** | `/resume` 恢复对话 | **checkpoint 回滚重放** | **事件日志重建**（fork/resume/transcript 同源） | 平台对话日志 |

> 要点：失败恢复的核心问题是**"重试的前提是什么"**——dsh 的回答最严谨（推进了代际才允许重试），Codex 的回答最实用（任意步可回滚），CC 靠 hook 编程，Dify 靠图级容错。

**③ 停止判定机制对比**

| 停止机制 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **完成判定** | 模型自评 + 人工确认 | 模型自评 + goal 完成状态 | **turn-stopping 终检**（可挂代码验证） | 图走完（Answer 节点输出） |
| **硬边界** | 会话超时 / 权限拦截 | **goal token 预算**（最量化） | 无进展检测 / 最大迭代 / 预算（插件） | **节点最大迭代轮数** |
| **交人（HITL）** | 权限 ask 弹窗 | request_user_input / 审批 | turn-stopping 交人通道 | 人工确认节点（Chatflow） |
| **核心差异** | 偏人工兜底 | 预算最可量化 | **最形式化**（"无欠账" + 终检 + 三硬边界） | 图结构天然保证终止 |

> 要点：停止条件是 loop 最容易被忽略的设计点——"模型说做完了"不可信，**必须用代码验证 + 硬边界**；dsh 的 turn-stopping 终检和 Codex 的 goal 预算是两个可借鉴的成熟实现。

**④ 嵌套与并行机制对比**

| 机制 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **子代理** | Subagent（SubagentStart/Stop hooks 可拦截） | Agents 子代理系统 | **subagent 插件**（作用域 + 属主 + 血缘） | —（图节点即编排单位） |
| **并行** | 多会话 / 多 worktree | **多 agent 并行** | driver 隔离（**initiator 作用域**，父子不串扰） | 工作流并行分支节点 |
| **嵌套语义** | 主-子上下文隔离 | 主-子会话隔离 | **作用域注册 + 运行时属主 + 持久血缘三者分离**（最严谨） | 节点内无嵌套 |
| **资源/预算传递** | 无显式机制 | goal 预算 | initiator 边界内传递 + drain 跟踪 | 平台级配额 |

> 要点：子代理嵌套最容易出"上下文串扰、资源泄漏"问题——dsh 用作用域（scope）把"谁能注册什么"和"谁继承谁的发起者"都显式化了。

**⑤ 状态与记忆机制对比**

| 状态 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **会话状态** | 内存 + /resume | SQLite checkpoint（state_5.sqlite） | **append-only 事件日志**（重载不丢事实） | 应用级会话 |
| **跨会话** | /schedule（定时） | **goal 系统**（预算 + 完成状态） | 会话持久化 + resume | 定时触发 + 应用续聊 |
| **事实一致性** | 无强保证 | history.jsonl 可查 | **"model-visible means logged" 运行时不变式** | 平台日志 |
| **成本核算** | 无内建 | goal 预算统计 | step 级 token 记录（来源事件序列） | LLMOps 成本追踪 |

> 要点：状态管理的分水岭是**"模型看到的东西能否从日志重建"**——dsh 用不变式保证，Codex 用 history.jsonl 尽力记录，CC/Dify 靠平台日志。

## 5. 关键设计差异与强度评级

**① 自由 vs 确定性的光谱**：Dify（图）最确定 → CC/Codex（自由循环 + 硬约束）居中 → dsh（可替换，两者都能做）。选型取决于任务形态：流程型要确定性，探索型要自由度。

**② 循环粒度的工程意义**：dsh 的 turn/step 两段式把"一次模型请求 + 工具调用"变成可审计的最小单元——这是"循环可治理"的前提；CC/Codex 的粒度是会话，Dify 的粒度是节点。

**③ 可回放是调试的分水岭**：Codex checkpoint 与 dsh 事件日志解决了"循环是黑盒"的痛点；不可回放的循环，出问题只能从头再跑。

**④ 停止条件的严谨度**：dsh 的"无欠账 + turn-stopping 终检 + 硬边界"最形式化；Codex 的 goal 预算最可量化；CC 靠权限/超时兜底；Dify 靠节点轮数 + 图走完。

**⑤ 谁在拦截**：CC 靠 hooks（17 个确定性事件）、Codex 靠 approval 策略、dsh 靠瀑布监听者（可编程策略）、Dify 靠节点边界——拦截点的位置决定了你能在循环的哪个环节施加策略。

**⑥ 强度评级（主观评分）**：安全 / 可观测 / 开源定制的 ★ 评级与理由见 [../Agent产品对比/05-横向解读与选型.md](../Agent产品对比/05-横向解读与选型.md) §1.6–1.8（单一事实源，本文不重复）。

## 6. 同一任务的三种运行轨迹

**任务 A：修复挂掉的测试**（harness 主场）
- **Dify**：5 轮撞迭代上限草草收场，无"重试-验证"韧性（且其工具生态本不含 shell）；
- **DSH / CC / CX**：turn 里跑几十个 step——跑测试→读文件→定位根因（浮点精度）→改 Decimal→重跑→全量回归→发现关联测试变化→继续修→全绿→汇报；上下文快满自动压缩，崩溃可 resume，用户随时可打断纠偏。

**任务 B：业务查询问答**（Dify 主场）
- **Dify**："查订单 SF20260801 什么时候发货" → 调 `query_order` → 拿到状态 → 输出，3 轮结束，画布每步可审；
- **harness**：杀鸡用牛刀——会探索环境、读配置、写脚本验证，反而慢。

**任务 C：跨域数据分析**（多 agent 协作）
- **DSH**：主 agent 判断跨域 → 并行 spawn 车辆域/用户域 subagent → 回收 → 交叉分析 → 综合报告；subagent 隔离上下文，可 continuation 纠偏；
- **Dify**：需画布 DAG 手动拆两个 Agent 节点并行分支，适合固定流程；
- **CC**：subagent 并行委派 + `SubagentStart/Stop` hooks 聚合。

### 6.1 同一任务在四款产品里的 loop 表现

| 环节 | Claude Code | Codex | dsh | Dify |
|:--|:--|:--|:--|:--|
| **触发** | `/loop 15m babysit PRs` | `create_goal`（预算 $2） | schedule 插件 + goal | 定时触发器 + 工作流 |
| **项目记忆** | CLAUDE.md 注入 | AGENTS.md + goal 上下文 | 事件日志 + context 插件 | 知识库检索项目规范 |
| **拦截示例** | PreToolUse hook：只允许改 `orders.py`，其他文件拦截 | 沙箱：只能写 `writable_roots`，pytest 在沙箱内跑 | pre-step 注入 skill；tools/pre-execute 校验参数与权限 | 图节点：`修文件`节点 → `跑测试`节点，边是固定流转 |
| **失败处理** | PostToolUseFailure hook：测试失败自动 `git checkout` 回滚 | checkpoint 回滚到上一分段 | request-error retry（**推进代际才重试**，否则保留错误） | 测试节点错误分支 → 回到修文件节点（图级回退） |
| **停止判定** | 模型自评 + 人工确认 | goal 完成状态（pytest 绿 = 完成） | turn-stopping 代码验证 + 三硬边界 | 图走完（Answer 节点输出） |
| **跨会话续跑** | /resume 恢复 | **新会话 get_goal 继续**（预算未花完） | 事件日志 resume | 定时任务下轮再跑 |

> 结论：同一任务四款都能完成，**差别在边界与可追溯性**——CC 靠 hook 防越界、Codex 靠沙箱+预算、dsh 靠日志+代际、Dify 靠图结构。

## 7. 机制层核心结论

1. **四款都是 ReAct 循环，差距全在循环外的工程**（详见 §2 关键发现）——拦截点、记忆、停止、回放、嵌套
2. **dsh 把循环做成了可治理的最小单元**（turn/step + 事件日志 + 代际压缩 + 作用域）——最接近"企业标准"的骨架
3. **Codex 贡献了预算与回放**（goal token 预算 + checkpoint）、**CC 贡献了 hooks 拦截**（17 事件确定性控制）、**Dify 贡献了显式图**（收敛路径画死 + 节点轮数）
4. **标准企业设计 = dsh 的骨架 + Codex 的安全预算 + CC 的 hooks 拦截 + Dify 的显式图**（详见 [03-标准设计.md](03-标准设计.md)）
