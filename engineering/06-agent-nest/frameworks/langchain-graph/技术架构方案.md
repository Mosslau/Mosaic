## 1. 概述

### 1.1 背景与目标

建设一套企业级 Agent 编排平台，以 **LangGraph 图状态机编排**为技术基座，满足四类核心诉求：

1. **复杂工作流编排**：把"收敛路径可预画"的业务流程（合规审批、多步数据加工、固定业务流）画成显式图——节点 + 边 + 状态，收敛由拓扑保证，走完即结束。
2. **人机协同（HITL）**：基于 Checkpointer 状态快照实现"中断 → 人工改 State → 恢复"，高风险节点必须人工确认后才能继续。
3. **多 Agent 团队**：以 DeepAgents（LangChain 官方多 Agent harness）作为上层，Workflow / Handoff 双模式编排多 Agent 协作。
4. **可中断 / 可恢复 / 可重放**：图执行的任意执行点固化为 Checkpointer 快照——会话可中断恢复、故障可重放定位、审计可追溯。

### 1.2 技术基座

| 组件 | 定位 | 事实依据（来自 research 素材） |
|---|---|---|
| **LangGraph** | 图状态机编排引擎，生产级事实标准 | LangChain / LangGraph 为 LangChain Inc. 出品；LangChain 月下载 **3,900 万**，远超其他框架；"图状态机编排，生产级事实标准" |
| **LangChain** | 链/组件抽象，模型接入、工具、消息协议 | "LangChain 提供链/组件抽象，LangGraph 提供图状态机编排" |
| **DeepAgents**（可选上层） | 官方多 Agent harness，batteries-included | "构建在 LangGraph 之上的开箱即用层（不是新的图引擎，而是图状态机的产品化上层）"；双模式 Workflow / Handoff |

平台化方向与选型边界（判断准则来自素材）：

> **何时用图、何时用循环**：问"收敛路径是否可预画"——能画死 → Graph；画不死、靠探索 → Loop。本平台承载**路径明确、要稳定复现**（合规/审批/固定业务流）的工作流；开放探索型任务（修 bug / 研究）不在本平台默认编排模型范围内，可走"Loop 内核 + 图编排外层"的折中方案（见 §4.5）。

### 1.3 设计原则

| 原则 | 说明 |
|---|---|
| 图是唯一编排模型 | 所有业务工作流统一以 LangGraph 图状态机表达；State / Node / Edge 是唯一定义原语，不引入第二套编排语法 |
| 状态持久化是一等需求 | 所有生产图执行启用 Checkpointer；中断/恢复/重放基于状态快照，不是靠重跑 |
| 控制面 / 数据面分离 | 工作流定义与版本治理在控制面；图执行引擎（LangGraph Runtime）在数据面，二者通过"发布物化"单向同步 |
| 复用框架、扩展点注入 | 平台不自研图引擎；多租户/审批/密钥通过节点工厂、工具层、网关等扩展点注入 |
| 平台化扩展显式标注 | 本文凡属平台自建能力（多租户、API、审批、密钥、版本治理），均标注【平台化扩展】 |
| 安全默认 | 高风险节点默认人工审批；密钥密文存储、凭证不出网关；可观测数据按租户脱敏 |

### 1.4 术语表

| 术语 | 含义 |
|---|---|
| State | LangGraph 共享状态 schema——一等公民；节点读它写它，状态沿边流转 |
| Node | 图节点：LLM 调用 / 工具执行 / 条件函数（纯函数：读 State 写 State） |
| Edge | 图边：流转 / 条件边 / 回退 / 循环，收敛路径画在图上 |
| Checkpointer | 状态持久化器：把任意执行点固化为可恢复快照，支撑中断/恢复/重放 |
| compile() | 图定义编译为可执行图的入口；执行时状态沿边流转，每步写入 State |
| HITL | Human-in-the-Loop：中断 → 人工改 State → 恢复 |
| DeepAgents | LangChain 官方多 Agent harness，Workflow / Handoff 双模式 |
| 物化（Materialize） | 发布时把控制面的图定义/配置转换为运行时实体 |

### 2.2 两进程模型

| 进程 | 职责 | 状态 | 存储 |
|---|---|---|---|
| **control-plane**（控制面） | 工作流定义 CRUD、图编译校验、发布版本快照、租户/RBAC、密钥、审批票据、审计计量 | 有状态（业务数据） | PostgreSQL + 对象存储 |
| **runtime**（数据面） | 图执行（LangGraph）、Checkpointer 快照读写、会话管理、SSE 流式、HITL 挂起/恢复 | 无状态（快照在共享存储） | Redis / PostgreSQL（Checkpointer 后端）+ 快照存储 |

边界：**控制面永远不参与单条执行链路**；运行时永远不查询业务库。唯一同步通道是"发布物化"（控制面 → 运行时的单向写入），与 agentscope 路线的控制面/数据面模型一致。

### 2.3 关键交互流程

**流程一：Admin 发布工作流（物化流）**

```
Admin → 控制面: 保存图定义（State Schema + Node + Edge + 模型/工具引用）
控制面: 图编译校验（拓扑合法性、节点 schema 一致性、条件边可达性）
      → 生成 workflow_release 不可变快照（版本号 + 图定义 JSON + 资源锁定版本）
      → 物化到运行时: Checkpointer 后端就绪 + 工具/MCP 配置 + 密钥引用（不含明文）
      → 写入 tenant_workflow_bindings（可见范围）
```

**流程二：用户触发执行（执行流）**

```
用户 → API 层: POST /v1/runs（workflow_id + 初始 State + session_id）
runtime: 按 release 快照装配图（compile() 产物）+ 工具层 + 模型
      → 图执行：状态沿边流转，每步写入 State
      → 每步 Checkpointer 快照（可中断/恢复/重放）
      → 遇 HITL 节点 → 挂起并推送审批/确认事件 → 等待人工
      → 人工确认 → 恢复执行（从快照续跑）→ 完成
      → SSE 事件流推送给调用方（message / node_start / hitl / done）
```

**流程三：故障恢复 / 重放（运维流）**

```
某 run 失败/中断 → 控制面/运维按 run_id 查 Checkpointer 快照
      → 从指定执行点恢复（resume）或完整重放（replay）定位问题
      → 审计：每个执行点有快照与 trace（LangSmith），可核对"模型当时看到了什么"
```

## 3. 核心架构决策（ADR）

### ADR-001：图状态机（LangGraph）为编排唯一模型

- **背景**：复杂工作流需要确定性编排；自由循环（Loop）难以约束、调试极难、token 成本失控（素材《Agent 工程范式演进》第四层局限）。
- **决策**：平台所有业务工作流统一以 LangGraph 图状态机表达；收敛路径画在图上，分支/循环/回退显式声明，收敛由图的拓扑保证（走完 = 结束）。
- **理由**：LangGraph 是生产级事实标准（LangChain 月下载 3,900 万）；Graph Engineering 层换取"确定性、可追踪、可验证"（素材《Agent 工程范式演进》第五层）。
- **影响**：开放探索型任务不适用本平台默认编排模型（见 §4.5 边界）；团队需具备图建模能力。
- **代价**：图维护成本（每张图需设计 State Schema 与节点拆分）；节点须为纯函数约束。

### ADR-002：Checkpointer 状态持久化为中断/恢复/重放的基础

- **决策**：所有生产图执行启用 Checkpointer；任意执行点固化为可恢复快照。
- **理由**：素材《03-海外通用编排框架》机制速览——图状态机路线机制核心即"节点 + 边 + 可持久化状态（checkpointer），中断/恢复/重放基于状态快照"。
- **影响**：会话可中断恢复、故障可重放、可审计；快照存储需承载容量与 TTL 治理。
- **平台化扩展**：快照按租户隔离存储、绑定 release 版本，并提供恢复/重放的平台 API。

### ADR-003：State 是一等公民（与普通 DAG 的本质区别）

- **决策**：尊重并利用 LangGraph "State 是一等公民"的机制设计全部编排：节点是纯函数（读 State 写 State），边是"转移"，人工干预 = 修改 State 后恢复。
- **理由**：素材《01-演进机理》§5——"LangGraph 与普通 DAG 的本质区别是 **State 是一等公民**——节点是'纯函数'（读 State 写 State），边是'转移'，Checkpointer 把任意执行点固化为可恢复快照"。
- **影响**：工作流定义、调试、审批全部围绕 State 展开；HITL 的"人工确认"在实现上即"中断 → 人工改 State → 恢复"（素材 §5 原话：这使"人机协同"天然成立）。

### ADR-004：DeepAgents 作为多 Agent 上层（Workflow / Handoff 双模式）

- **背景**：单图编排能覆盖"收敛路径可预画"的工作流；但多 Agent 团队协作（分工、对话控制权交接）若用 LangGraph 原语手动拼装，工作量大。
- **决策**：多 Agent 场景优先使用 DeepAgents——官方 batteries-included harness，**Workflow**（显式图流程）与 **Handoff**（对话控制权交接）双模式；需要底层控制时直接落到 LangGraph 自定义节点/边（与 LangGraph 同源）。
- **理由**：素材《03-海外通用编排框架》DeepAgents 节——"记忆、工具调用、human-in-the-loop（HITL）开箱即用，无需从 LangGraph 原语手动拼装"；"不是新的图引擎，而是图状态机的产品化上层"。
- **影响**：M0 需验证双模式在生产约束（多租户、审批、可观测）下的可行性；若验证不通过，回退为纯 LangGraph 自定义节点实现（见实施计划 R-1）。

### ADR-005：LangSmith 可观测统一接入

- **决策**：所有图执行与模型调用的 tracing 统一接入 LangSmith；prompt 与评估资产经 LangSmith hub 管理。
- **理由**：素材《03-海外通用编排框架》——LangGraph/LangChain"人机协同与可观测性生态最强（LangSmith tracing、hub）"。
- **影响**：tracing 数据含业务内容，需按租户脱敏与访问控制（见 §6）；平台自身的业务指标（租户/成本/审批）在 LangSmith 之外自建。
- **平台化扩展**：tracing 网关代理（统一 API Key 注入、数据脱敏）、评估集沉淀、trace 与 Checkpointer 快照关联检索。

## 4. 基于 LangGraph 真实机制的设计

### 4.1 机制链：State → Node → Edge → compile() → 执行 → Checkpointer

素材《03-海外通用编排框架》机制深挖给出的 LangGraph 图状态机数据流，即为本平台执行引擎的**唯一事实机制**：

```
定义 State(共享状态 schema) → 定义 Node(LLM/工具/条件函数) → 定义 Edge(流转/条件边)
  → compile() → 执行: 状态沿边流转，每步写入 State → Checkpointer 快照(可中断/恢复/重放)
```

平台按此机制落地运行时：

| 机制环节 | 平台落地 |
|---|---|
| State | 工作流定义的共享状态 schema（控制面建模，JSON Schema / Pydantic 表达）；运行时的唯一数据载体 |
| Node | 三类节点：LLM 节点（模型调用 + 结构化输出）、工具节点（函数工具 / MCP）、条件节点（路由/校验，决定条件边走向） |
| Edge | 普通流转边 + 条件边（分支 / 回退 / 循环在图上一一显式声明）；收敛路径画死 |
| compile() | 发布物化时编译图定义，产物（编译后的图）缓存于运行时，按 release 版本隔离 |
| 执行 | 状态沿边流转，每步写入 State；每步落 Checkpointer 快照 |
| Checkpointer | 任意执行点可中断 / 恢复 / 重放；HITL 与故障恢复都基于快照 |

### 4.2 State 一等公民：与普通 DAG 的本质区别

- 普通 DAG 只管"数据依赖 + 任务顺序"；LangGraph 的 **State 是一等公民**——节点是"纯函数"（读 State 写 State），边是"转移"。
- 工程含义：① 调试时任意执行点可固化为快照（素材 §5：可追踪可验证）；② 人工干预不是"打断重跑"，而是"改 State 再恢复"；③ 审计粒度是"State 快照 + trace"，可核对模型每一步看到的状态。
- 平台约束：节点必须保持纯函数性（不在节点外隐式修改状态），这是图可重放的前提，写入开发规范。

### 4.3 人机协同（HITL）设计

素材 §5 原话："Checkpointer 把任意执行点固化为可恢复快照；这使'人机协同'天然成立（中断 → 人工改 State → 恢复）"。平台落地：

```
图执行 → 到达 HITL 节点（如"生成发布单，待确认"）
  → 中断执行，Checkpointer 固化当前执行点
  → 平台推送审批/确认事件（API 层 SSE + 渠道卡片）
  → 人工确认/修改参数（等价于修改 State 的指定字段）
  → 恢复执行：从快照续跑，按修改后的 State 继续沿边流转
```

- HITL 节点在工作流定义中显式声明（节点属性 `hitl: true` + 可修改字段白名单）【平台化扩展】。
- 审批动作全程落审计（审批人、时间、State 修改 diff）【平台化扩展】。

### 4.4 多 Agent 团队：DeepAgents 双模式

- **Workflow 模式**：显式图流程——多 Agent 的分工步骤画成图，适合步骤明确的团队流程（如"检索 Agent → 写作 Agent → 审校 Agent"流水线）。
- **Handoff 模式**：对话控制权交接——主 Agent 在对话中把控制权移交给合适的子 Agent，适合面向用户的对话型多 Agent。
- 与 LangGraph 同源：DeepAgents 内部即图状态机；平台在"需要底层控制时直接落到 LangGraph 自定义节点/边"（素材原话）。
- 平台化定位：DeepAgents 是"图状态机的产品化上层"，不是第二套引擎——平台编排模型唯一性（ADR-001）不因此破坏。

### 4.5 编排边界：何时用图、何时用循环（选型准则落地）

| 任务形态 | 平台处置 | 依据（素材《01-演进机理》§5 对照表） |
|---|---|---|
| 路径明确、要稳定复现（合规/审批/固定业务流） | **默认：LangGraph 图** | 收敛由拓扑保证，分支回退显式，可审计可审批 |
| 任务开放、要自主探索（修 bug/研究/长任务） | **不在平台默认编排范围内**；如确需，走"Loop 内核 + 图编排外层"折中 | 自由度换深度，探索型任务需要模型自主决策 |
| 折中 | Loop 内核 + 图编排外层（把固定段落画成图，探索段落留给循环） | 引擎保持自由循环，把固定段落画成图 |

## 5. 多租户与安全模型

> 本节为【平台化扩展】——LangGraph/LangChain 内核不感知租户，多租户、版本治理、审批、密钥由平台自建并收敛注入。

### 5.1 租户隔离设计

| 隔离面 | 机制 | 强制点 |
|---|---|---|
| 工作流定义与版本 | 控制面行级 `tenant_id` 过滤 + 发布快照按租户绑定 | 控制面 Repository 基类 |
| 图执行与会话 | 运行时按 `tenant_id + user_id` 命名 run/session；Checkpointer 快照键带租户前缀 | 运行时会话服务 |
| Checkpointer 快照 | 快照存储键 `tenant_{id}/{run_id}/...`，读写统一入口校验 | 快照服务封装 |
| 工具/MCP | 工具层按租户注入凭证（真实密钥不出网关）；高风险写操作经网关审批 | MCP 网关 |
| 可观测数据 | LangSmith trace 按租户脱敏 + 访问控制（见 §6） | tracing 网关代理 |

### 5.2 工作流版本治理（发布物化）

```
① 校验 → ② 快照 → ③ 物化 → ④ 绑定
图引用完整性/权限 → workflow_release 不可变快照 → 编译产物+工具/密钥引用写入运行时 → 租户可见性绑定
```

不变量（对齐 agentscope 路线做法）：

1. `workflow_releases` 创建后不可修改（仅状态流转 published → deprecated）；
2. run 创建时绑定 release_id，存续期间永远用该版本图定义执行；
3. 再次发布产生新版本；租户升级策略 `auto` / `pin`。

### 5.3 审批模型（HITL 与工具审批）

| 审批类型 | 触发 | 实现 |
|---|---|---|
| 节点级 HITL | 工作流定义声明 `hitl: true` 的节点 | 中断 → 快照 → 人工确认/改 State → 恢复（§4.3） |
| 工具级审批 | 高风险写工具（MCP risk_level=write） | MCP 网关挂起 → 审批票据 → 回调放行/拒绝 → 审计 |
| 票据治理 | 挂起票据超时、凭证吊销联动 | 票据 TTL（如 10 分钟过期）+ 吊销时强制过期相关 pending 票据 |

### 5.4 密钥管理

- 模型 / MCP / 工具凭证统一存控制面密钥库（KMS 加密存储）；
- 发布物化时仅写入**密钥引用**（`${{secrets.xxx}}`），明文凭证只在网关/模型层解析、用后即弃；
- 运行时、图节点、LLM 上下文任何环节接触不到明文密钥。

## 6. 可观测性与运维

### 6.1 双轨可观测

| 轨道 | 覆盖 | 工具 |
|---|---|---|
| **执行轨（LangSmith）** | 图执行 tracing（节点级调用链）、模型调用（token/延迟/成本）、prompt 版本、评估集 | LangSmith tracing + hub（素材：人机协同与可观测生态最强） |
| **平台轨（自建）** | 租户用量、审批指标、快照存储水位、并发/延迟、SSE 断连率 | Prometheus + Grafana + Loki（自建） |

### 6.2 LangSmith 接入策略

- tracing 经**网关代理**统一接入：平台统一管理 API Key、按租户注入、对 trace 内容做脱敏（过滤凭证、隐私字段）；
- prompt 模板与评估集经 hub 管理，随工作流 release 版本沉淀；
- trace 与 Checkpointer 快照关联：以 run_id 为纽带，支持"从 trace 定位到执行点 → 用快照重放"的运维闭环。

### 6.3 运维要点

- **恢复与重放**：run 中断后可从任意快照点 resume；复盘用 replay（核对"模型当时看到了什么"）。
- **快照治理**：Checkpointer 快照按 TTL 归档/清理；孤儿快照定期对账。
- **告警分级**：P1（全平台不可用/数据泄露嫌疑）15 分钟响应；P2（单租户/单工作流故障）2 小时；P3（性能退化）次日。
