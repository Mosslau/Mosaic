# 算法评估与生产化路线（42 个算法）

> 版本：v2 · 2026-11-02
> 定位：**当前唯一总视图**——把「交付完整性 + 验证深度」与「生产应用差距 + 最小落地路径」放在同一份文档里。
> 覆盖：42 个算法的交付/深度逐项评估；生产系统分层、选型、四步、最小栈、术语、误区；每个算法的 P0 → P1 最小路径。
> 口径：42 个单元统一称为**算法**；“验证/运行”只指单个算法内部的运行形态，不作为总称。

## 0. 结论

- **交付完整性：42/42。** 42 个算法都有 README、`impl.py`、`demo.py`、测试、`exercises/`、`project/`、独立对照（`framework.py` 或 `baseline.py`）和 ✅ 完成日期；全仓 **575 passed**。
- **验证深度：3 个 L4 + 39 个 L3 + 0 个 L2/L1，平均 3.07/4。** L2/L1 已清零，但 L4 仍只有 CFR、线性回归、逻辑回归三个。
- **生产就绪：0/5。** 42 个当前全部是 **P0 教学实现**，没有一个到 P1 可服务原型；本文的“最小路径”是到 P1，不是到 P2 生产。
- **一句话：交付已齐，深度已抬到教学级；下一步的瓶颈是 L4 与生产化，不是继续加第 43 个算法。**

## 1. 评估口径

### 1.1 第一维：交付完整性

| 检查项 | 含义 |
|---|---|
| 六件套 | README + `impl.py` + `demo.py` + 测试 + `exercises/` + `project/` |
| 独立对照 | `framework.py`（框架对照）或 `baseline.py`（基线/独立参考）至少一个 |
| 状态/日期 | README 首行 ✅ + 完成日期，且与索引表一致 |
| 测试 | `pytest` 可收集、可运行；本文记录当前用例数 |

**判定**：六件套 + 独立对照 + 状态/日期齐全 = ✅；缺任一项 = ⚠️。当前 **42/42 全 ✅**。

### 1.2 第二维：验证深度

| 等级 | 含义 |
|---|---|
| **L4 深** | 真实/半真实数据或标准基准 + 外部真值 + 强数值/边界测试 + 量化失败分析 + 多基线 |
| **L3 较深** | toy/合成但严谨；核心性质与边界有测试；公平基线；heldout / 种子方差 / 局限量化 |
| **L2 中** | 测试以 shape/smoke 为主；核心反传或生成路径未验证；基线薄 |
| **L1 浅** | 测试仅契约；基线是稻草人；无 heldout |

**判定**：不是“测试越多越深”，而是看**断言是否锁住核心性质**（FD、最优性、heldout、基线公平性、失败模式）。当前：L4 3 个、L3 39 个、L2/L1 0 个。

### 1.3 生产就绪等级

| 等级 | 含义 | 当前 |
|---|---|---|
| **P0 教学实现** | 单机、toy 数据、无服务/监控/权限；用于讲原理和回归 | **42/42** |
| **P1 可服务原型** | 真实/半真实数据 + 服务接口 + 评测集 + 基础监控；单租户可接受 | **0/42** |
| **P2 生产系统** | HA、备份、限流/配额、权限/审计、成本、SLO、压测、灰度 | **0/42** |

> 本文第二部分给的是 **P0 → P1** 的最小路径；P1 → P2 的通用要求见 §5.1。

# 第二部分：从算法到生产

> 核心：**算法决定“能做什么”，工程决定“能不能稳定交付”。** 生产系统 = 算法核心 + 一组工程层（数据、训练、推理、评测、观测、部署、安全）；接入、应用、跟踪是横切层。`algorithms/` 提供原理与 oracle（回归基准），不提供运行时。
> 当前 42 个全部是 **P0 教学实现**；本文先给每个算法的 P0 → P1 最小路径（§4.1），再讲通用框架（§4.2–§4.9）与边界/误区（§4.10）；P1 → P2 的通用要求见 §4.3.4。

## 4.1 每个阶段、每个算法的生产路径

> 当前全部 **P0**。下表给的是 **P0 → P1** 的最小路径：换真实数据/成熟库、补评测与服务、加基础监控；P1 → P2 的通用要求见 §4.3.4。
> 原则：**教学实现是 oracle，不是 runtime。** 不直接 import `algorithms/`；用成熟库重写服务，把教学实现当固定输入/输出回归基准。

## 4.2 三个词先分清

| 词 | 是什么 | 例子 | 不是什么 |
|---|---|---|---|
| **算法** | 讲原理、手写实现、双跑对照 | `p04-transformer/attention` | 不是服务 |

### 4.3.3 三条原则

1. **算法核心薄，工程层厚。** 真正可复用的算法实现约 **9.0k 行**；生产需要的数据、训练、推理、评测、观测、安全是另外几层。
2. **教学实现是 oracle，不是 runtime。** 用它产出固定输出、做回归测试，而不是让生产服务直接 import。
3. **先纵切，后平台。** 先让一条“数据 → 模型 → API → 评测 → 观测”的链路跑通，再考虑多模型、多租户、K8s。

### 4.3.4 六层通用要求（P0 → P1 → P2）

| 层 | P0 教学实现 | P1 可服务原型 | P2 生产 |
|---|---|---|---|
| 数据 | digits/合成/小语料 | 真实/半真实数据、固定切分、版本化 | 质量、漂移、PII、保留策略 |
| 训练 | 单机 numpy/小 torch | 可重跑训练脚本 + 超参/种子入档 | 分布式、训练追踪、模型注册 |
| 推理 | `demo.py` 单次调用 | API/批处理 + 延迟/吞吐基线 | 自动扩缩、灰度、回滚、GPU 池 |
| 评测 | README 指标 + pytest | 固定评测集 + 指标门槛 + 回归 | 线上评测、人工反馈、A/B |
| 观测 | 基本日志/无 | 请求日志、延迟、错误率、模型指标 | Trace、告警、SLO、成本看板 |
| 安全/成本 | 无 | 鉴权、输入校验、依赖锁定 | 多租户、审计、配额、密钥轮换 |

### 4.4.3 13 个系统题：不在 algorithms 做

判断标准：**产物是「一个算法 + 一个 demo」，还是「数据 + 训练 + 服务 + 评测 + 治理」？** 后者是系统题，验收在工程域；不在 `algorithms/` 里做 toy 版。

| 路线小节 | 为什么不是算法 | 工程落点（当前 D 阶段） |
|---|---|---|
| 6.2 LLM 技术组成 | 需要预训练与大规模推理，toy 覆盖不了 | AI D5 推理与服务 + D6 算力与调度 |
| 6.4 多模态大模型 | 需要大模型与多模态数据 | AI D5 的 OpenAI 兼容接口可接多模态模型（选型阅读） |
| 6.5 视频生成 / 世界模型 | 算力与数据差 3–6 个数量级 | 不做；读 p05 DDPM + 视频生成综述 |
| 7.1 预训练 | 成本 10²–10⁴ GPU·天，不是学习项目 | 不做；AI D7 只做微调 |
| 7.2 指令微调 | 需要数据 / GPU / 评测集 | AI D7（LoRA/QLoRA）+ D6 计量 |
| 7.3 对齐（RLHF/DPO） | 需要偏好数据 + 训练基础设施 | AI D7 扩展；当前 D7 只覆盖 SFT/LoRA，不含 RLHF |
| 7.4 PEFT | 可做，但归 AI D7 的微调验收 | AI D7 |
| 7.5 压缩 / 推理优化 | 需要真实模型与服务 | AI D5（量化/压测） |

| 9.3 风险 / 安全 | 需要治理 / 审计 / 权限 | AI D9/D10 + 数据 D8/D12 |

|---|---|---|
| AI D2 数据与语料 / D4 存储与版本 | 数据 / 存储 | p02 去重聚类/PCA、p05 embedding/RAG |
| AI D3 检索与知识 | 应用 / RAG | p05 RAG、p04 embedding/attention |

## 4.5 从开发到生产：四步

```text
业务问题 → 任务定义 → 基线 → 数据/评测 → 服务 → 观测 → 迭代
```

| 步骤 | 要回答的问题 | 产出 |
|---|---|---|
| ① 任务定义 | 输入/输出是什么、成功指标是什么 | 一页任务说明 + 指标 |
| ② 基线 | 最简单的可用方法是什么 | 规则 / 逻辑回归 / 预训练模型 |
| ③ 数据 + 评测 | 数据从哪来、怎么切、怎么算好 | 数据快照 + golden set + 阈值 |
| ④ 服务 + 观测 | 怎么部署、怎么发现变坏 | API + 指标 + 告警 + runbook |

**算法主要出现在 ②；① 定义问题与指标，③④ 是工程。** 很多项目失败不是算法不行，而是 ③④ 没做。

## 4.6 教学实现 vs 生产实现

| 资产 | 生产用途 | 处理方式 |
|---|---|---|
| **9.0k 行 `impl.py`** | 公式、边界、反传的参考 | 不 import；用固定输入/输出做 oracle |
| **6.3k 行 `test_impl.py`** | 梯度检查、形状契约、边界条件 | 移植为生产回归测试 |
| `demo.py` / 素材脚本 | 教学演示 | 不进生产 |
| `framework.py` / `baseline.py` | 选型对照 | 参考，不直接依赖 |
| `project/` | 迁移场景 | 可演化成 demo，不作为服务 |
| RAG 链路 / 评测口径 | 应用蓝图 | 用真 embedding/向量库/LLM 重写 |

**必须替换的六层**：数据管道、训练工程、推理服务、评测体系、观测体系、安全/成本。生产不是把 **44.4k 行**“改一改”，而是围绕核心另建一层。

## 4.9 学习 / 落地顺序

1. **PyTorch 基础**：Tensor、autograd、`nn.Module`、optimizer、DataLoader、device；
2. **HF Transformers**：模型、tokenizer、训练/推理；
3. **PEFT/LoRA**：拿一个小模型做一次微调；
4. **FastAPI + Ollama/vLLM**：包一个 OpenAI 兼容接口；
5. **MLflow**：记录参数、指标、模型版本；
6. **Docker Compose + Prometheus/Grafana**：部署与观测；
7. 可选：Ray、Airflow、K8s、Iceberg、Milvus。

**每层选一个，不要混着学。** 先从“算 → 服务 → 看”这条最短路径走通，再补数据和调度。

## 4.10 边界与常见误区

- ❌ 生产不是“把 demo 放大”。
- ❌ 不是 GPU 越大越好；先看任务和评测。
- ❌ 不是算法越新越好；基线和数据往往更决定结果。
- ❌ 不是先建平台再找应用；先有一条真实链路。
- ❌ 教学实现不能直接当生产参考（公式对，边界/规模/失败模式不对）。
- ❌ 不要把 **42 个算法**都服务化；选一个应用场景。
- ❌ 没有 golden set 不要调模型。
- ❌ 一开始就上 K8s / Volcano / Iceberg / Milvus，通常是在给未来的人写维护负担。
