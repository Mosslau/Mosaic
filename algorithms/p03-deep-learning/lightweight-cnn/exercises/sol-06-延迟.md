# 参考解 6：延迟为什么不能按参数估

**测量**（batch=128，15 次中位数，随机初始化的网络即可）：

| 实现 | 参数量 | 延迟 |
|---|---|---|
| 手写 DS | 2858 | 17.5 ms |
| 手写标准 Conv | 15554 | 28.1 ms |
| torch DS（1 线程） | 2858 | 6.3 ms |
| torch DS（4/8 线程） | 2858 | 3.9 / 3.7 ms |

**三个原因**：

1. **算术强度**：depthwise 每个输出只做 9 次乘加，数据复用低，访存/调度占比高；
   标准卷积一次矩阵乘把通道维也用满，单位时间做的有用功更多。
2. **算子融合**：torch 的 depthwise/1×1 是融合 C++ kernel；手写版每次前向要建
   im2col 大矩阵、逐层 Python 调用，固定开销摊不掉。
3. **线程与负载**：这次推理 batch=128 时多线程有效（6.3→3.7 ms）；但训练时
   小 batch 的逐步同步开销更大，`algorithms/…/framework.py` 反而固定 1 线程。
   线程收益取决于算子、batch 与并行粒度，不能一概而论。

**结论**：参数量是"模型占多少内存"的指标，不是"跑多快"的指标。评估端侧要同时看
FLOPs、访存、算子支持、batch 与硬件；本实验的 DS 参数少 5.4×，手写 wall-clock
只快 1.6×，torch 通过融合与多线程才追到 3.7 ms。
