# 参考解：第 3 题（判断）

## 1. 错在哪

`value` 的口径必须固定为：**"走出这一步的那一方"从这一步出发的收益**（赢 +1 / 输 −1 / 平 0）。

不翻转符号的话，父节点累计到的就不是"父方视角"的收益，而是**子方（对手）视角**的收益。
于是 `win_rate = value / visits` 在两层表示的是**同一个人的胜率**——Selection 拿它比大小时，
等于把"对手的胜率"当成"我方选这步的收益"，整棵树按反方向选择。

一句话：**符号翻转是"每一步的收益只对某一方成立"这个事实的编码**，不翻就等于篡改了视角。

## 2. 实测后果（40 局对精确搜索，每步 50 次模拟）

| 实现 | 胜 | 平 | 负 |
|---|---|---|---|
| 正确 | 0 | **39** | 1 |
| 符号不翻转（bug） | 0 | 4 | **36** |

**这个 bug 不报错、不崩溃、也不抛异常**——它只是让棋力从"能和精确搜索打平"掉到"几乎必输"。
如果只用一个弱对手（比如纯随机）来测，甚至可能看不出明显异常（随机对手太弱，
反着选也能赢），这正是它危险的地方。

**暴露它的两种办法**（本参考解都实现了）：

1. **不变式测试**（不需要对局，最可靠）：构造一个只有一步的对局，直接检查
   根与子节点的 `value` 符号——正确实现必然**相反**，bug 实现**同号**。
   ```
   正确实现: 子节点 value = +1.0，根 value = -1.0
   bug 实现 : 子节点 value = +1.0，根 value = +1.0
   ```
2. **固定种子的战绩回归**：对足够强的对手（精确搜索）跑固定局数，
   把"和棋 / 负"的数字写进测试当门槛。

## 3. 更小的验证方法（不变式版）

不用整局对局，只要一棵"一步定胜负"的小局面：

```text
构造 OneMove：根（轮到对手）→ 唯一招法 → 终局（我方赢）
展开一步 + 模拟 + 回传，然后断言：
    child.value == +1.0     # 走出该步的是我方，我方赢了
    root.value  == -1.0     # 根的"走出那一步的一方"是对手，对手输了
```

这个不变式**与棋类无关**，任何对弈接口都能跑；写进测试后，
以后任何一次重构（比如改 `_simulate` 的收益口径）都会被它拦住。
