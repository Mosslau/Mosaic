# 生产系统栈与算法应用

> 定位：`algorithms/` 的配套参考，回答三个问题——生产系统由哪些层组成？每个算法族在生产系统里对应什么位置？从教学实现到生产应用，哪些复用、哪些替换？
> 基线：2026-10-23 工作区（`main @ 83aedfc2`，写作前基线）。
> 关联：[阶段成熟度评估](阶段成熟度评估-2026-10-22.md)（差距量化）· [engineering/ai-platform](../engineering/ai-platform/README.md)（平台设计）· [algorithms/README.md](README.md)（实验索引）。
> 边界：本文不替代实验 README，也不替代 `engineering/` 的平台设计；它只给“算法 ↔ 生产”的映射与选型地图。

## 0. 一句话

**算法决定“能做什么”，工程决定“能不能稳定交付”。**

生产系统 = **算法核心 + 一组工程层**（数据、训练、推理、评测、观测、部署、安全）；接入、应用、跟踪是横切层。`algorithms/` 提供原理与 oracle（回归基准），不提供运行时。

---

## 1. 三个词先分清

| 词 | 是什么 | 例子 | 不是什么 |
|---|---|---|---|
| **算法实验** | 讲原理、手写实现、双跑对照 | `p04-transformer/attention` | 不是服务 |
| **生产系统** | 可部署、可评测、可观测的服务或流水线 | 一个 RAG `/ask` 服务 | 不是 notebook |
| **平台** | 多系统共用的底座 | K8s + 网关 + 注册 + 观测 | 不是第一个项目 |

先有生产系统，再谈平台。反过来做，通常会把时间花在 K8s 和网关上，却没有一个真实请求。

## 2. 生产系统的分层框架

### 2.1 分层图

```text
接入层       API 网关 / 鉴权 / 限流 / 路由
应用层       RAG / Agent / 业务编排
推理层       模型服务 / 批处理 / 流式
训练层       训练 / 微调 / 量化
跟踪层       实验跟踪 / 模型注册 / 数据版本
数据层       对象存储 / 湖表 / 向量库 / 元数据
评测层       golden set / 回归 / 漂移
观测层       指标 / 日志 / 追踪 / 告警
部署层       容器 / 编排 / GPU 调度
安全/成本    密钥 / 权限 / 计量
```

### 2.2 每层职责与工具

| 层 | 职责 | 典型工具 | 产出 |
|---|---|---|---|
| 接入 | 统一 API、鉴权、限流、路由 | FastAPI、Kong、LiteLLM | 稳定接口 |
| 应用 | RAG / Agent / 业务编排 | LangChain、LlamaIndex、LangGraph | 业务闭环 |
| 推理 | 模型加载、批处理、流式 | vLLM、TGI、SGLang、Triton、Ollama | 低延迟响应 |
| 训练 | 训练、微调、量化 | PyTorch、HF Transformers、PEFT、DeepSpeed | 模型产物 |
| 跟踪 | 实验、版本、注册 | MLflow、W&B、HF Hub | 可复现产物 |
| 数据 | 存储、湖表、向量、元数据 | S3/MinIO、Iceberg、pgvector、Milvus | 数据与索引 |
| 评测 | 质量、回归、漂移 | pytest、Ragas、DeepEval、promptfoo | 质量门槛 |
| 观测 | 指标、日志、追踪 | Prometheus、Grafana、OTel、Langfuse | 可诊断 |
| 部署 | 容器、编排、GPU 调度 | Docker、Compose、K8s、Volcano | 可部署 |
| 安全/成本 | 密钥、权限、计量 | Vault、Keycloak、OpenCost | 可运营 |

### 2.3 三条原则

1. **算法核心薄，工程层厚。** 真正可复用的算法实现约 7.9k 行；生产需要的数据、训练、推理、评测、观测、安全是另外几层。
2. **教学实现是 oracle，不是 runtime。** 用它产出固定输出、做回归测试，而不是让生产服务直接 import。
3. **先纵切，后平台。** 先让一条“数据 → 模型 → API → 评测 → 观测”的链路跑通，再考虑多模型、多租户、K8s。

## 3. 算法族 → 生产位置

### 3.1 五个族分别在哪里

| 族 | 代表算法 | 生产中的位置 | 典型应用 | 可复用 | 需替换 |
|---|---|---|---|---|---|
| **p01 搜索** | DFS/BFS/UCS、A*、Minimax、MCTS、CFR、CSP | 求解 / 规划层 | 路径规划、资源调度、游戏 AI、Agent planning | 状态表示、搜索/剪枝/约束逻辑、测试用例 | 大图索引、并行/内存受限搜索、服务化 |
| **p02 统计 ML** | 线性/逻辑回归、正则化、SVM、树、森林、Boosting、K-Means、PCA、NB、关联规则、主题、推荐、异常 | 预测 / 排序 / 聚类层 | 风控、推荐、用户分群、异常检测、质量抽检 | 公式、指标口径、边界条件、性质测试 | sklearn / LightGBM / XGBoost / Spark ML |
| **p03 深度学习** | 感知机、MLP、CNN、RNN/LSTM、AE、GAN、GCN、DQN | 表示学习 / 视觉 / 序列 / 图 / RL | 图像分类、序列预测、图分析、控制 | 训练循环、梯度检查、数据管线设计 | PyTorch + 预训练模型 + AMP/DDP |
| **p04 Transformer** | Attention、Block、BERT、GPT、T5、ViT、CLIP | LLM / Embedding / 多模态 | 问答、摘要、翻译、检索、分类、跨模态 | mask、注意力、目标函数、反传推导 | HF Transformers + vLLM + 预训练权重 |
| **p05 生成/RAG** | VAE、DDPM、RAG | 生成 / 检索增强层 | 图像生成、RAG 问答、推荐解释 | RAG 链路、引用与评测口径 | diffusers / vLLM / 向量库 / 真 embedding |

### 3.2 应用 → 算法 → 生产栈

| 应用 | 算法供给 | 生产栈 | 关键指标 |
|---|---|---|---|
| 企业知识库问答 | p05 RAG + p04 embedding/attention | FastAPI + embedding + pgvector + LLM + reranker | Recall@k、引用准确率、答案要点覆盖率 |
| 文档分类 / 信息抽取 | p04 BERT + p02 逻辑回归 | HF Transformers + FastAPI | F1、P95 延迟 |
| 推荐 / 排序 | p02 GBDT/MF + p04 embedding | LightGBM/Spark + 特征管道 + 召回/排序服务 | AUC、NDCG、覆盖率 |
| 异常检测 | p02 树/密度 + p03 AE | sklearn/PyTorch + 流式管道 | Precision/Recall、误报率 |
| 路径规划 / 调度 | p01 A*/CSP | OR-Tools/NetworkX + 求解服务 | 成本、时延、成功率 |
| 游戏 / 决策 | p01 MCTS/CFR + p03 DQN | 自研 solver + 模拟环境 | 胜率、ELO、样本效率 |
| 图像分类 / 检测 | p03 CNN + p04 ViT | PyTorch + Triton/TorchServe | Acc/F1、P95 延迟 |
| 图像 / 内容生成 | p05 VAE/DDPM | diffusers + GPU 推理 | FID/CLIP score、延迟 |

### 3.3 与 engineering 的 p0–p6 对应

| 单元 | 生产层 | 算法供给 |
|---|---|---|
| p0 AI 数据基础 | 数据 / 存储 | p02 去重聚类/PCA、p05 embedding/RAG |
| p1 RAG 数据平台 | 应用 / RAG | p05 RAG、p04 attention/embedding |
| p2 向量化数据湖 | 数据 / 存储 | p02/p05 向量与索引口径 |
| p3 K8s + GPU 调度 | 部署 / 调度 | 无直接算法 |
| p4 训练与推理平台 | 训练 / 推理 | p03/p04 |
| p5 Agent 平台 | 应用 / Agent | p01 规划、p04/p05 工具与知识 |
| p6 数据中心整合 | 接入 / 控制面 | 无直接算法 |

**算法是原理供给，不是平台组件。** 平台用成熟库，不直接 import `algorithms/`；算法实验负责“讲清原理 + 提供回归基准”。

## 4. 从算法到生产：四步

```text
业务问题 → 任务定义 → 基线 → 数据/评测 → 服务 → 观测 → 迭代
```

| 步骤 | 要回答的问题 | 产出 |
|---|---|---|
| ① 任务定义 | 输入/输出是什么、成功指标是什么 | 一页任务说明 + 指标 |
| ② 基线 | 最简单的可用方法是什么 | 规则 / 逻辑回归 / 预训练模型 |
| ③ 数据 + 评测 | 数据从哪来、怎么切、怎么算好 | 数据快照 + golden set + 阈值 |
| ④ 服务 + 观测 | 怎么部署、怎么发现变坏 | API + 指标 + 告警 + runbook |

**算法主要出现在 ②；① 定义问题与指标，③④ 是工程。** 很多项目失败不是算法不行，而是 ③④ 没做。

## 5. 教学实现 vs 生产实现

| 资产 | 生产用途 | 处理方式 |
|---|---|---|
| **7.9k 行 `impl.py`** | 公式、边界、反传的参考 | 不 import；用固定输入/输出做 oracle |
| **5.0k 行 `test_impl.py`** | 梯度检查、形状契约、边界条件 | 移植为生产回归测试 |
| `demo.py` / 素材脚本 | 教学演示 | 不进生产 |
| `framework.py` | 选型对照 | 参考，不直接依赖 |
| `project/` | 迁移场景 | 可演化成 demo，不作为服务 |
| RAG 链路 / 评测口径 | 应用蓝图 | 用真 embedding/向量库/LLM 重写 |

**必须替换的六层**：数据管道、训练工程、推理服务、评测体系、观测体系、安全/成本。生产不是把 38k 行“改一改”，而是围绕核心另建一层。

## 6. 最小生产栈

| 层 | 选型 | 备注 |
|---|---|---|
| API | FastAPI + Pydantic | 轻、够快、易测 |
| 模型 | PyTorch（DL）/ sklearn（表格） | 先用预训练/简单模型 |
| 推理 | vLLM（GPU）/ Ollama（Mac） | OpenAI 兼容；Mac 上 vLLM 不实用 |
| 跟踪 | MLflow | 本地可起；记录参数、指标、产物 |
| 数据 | PostgreSQL + S3/MinIO + pgvector | 先不上 Iceberg/Milvus |
| 评测 | pytest + Ragas/promptfoo | golden set + 阈值 |
| 观测 | Prometheus + Grafana | 指标 + 仪表盘；日志用结构化 JSON |
| 部署 | Docker Compose | 先不上 K8s |
| CI | GitHub Actions | lint + test + build + eval |

这 9 个够跑通一条纵切。Ray / Airflow / K8s / Iceberg / Milvus / Volcano 等**有第二个服务、第二个人、真实规模**再上。

## 7. 术语表

| 名字 | 层 | 一句话 |
|---|---|---|
| **PyTorch** | 训练/计算 | 张量 + 自动求导 + GPU，负责“算” |
| **HF Transformers** | 训练/模型 | 加载预训练模型与 tokenizer |
| **PEFT** | 微调 | LoRA/QLoRA 等参数高效微调 |
| **TRL** | 微调 | SFT/DPO/RLHF 训练 |
| **DeepSpeed / FSDP** | 训练 | 分布式训练、显存优化 |
| **vLLM** | 推理 | GPU 上的高吞吐 LLM 服务，OpenAI 兼容 |
| **TGI** | 推理 | Hugging Face 的 LLM 推理服务 |
| **SGLang** | 推理 | 高吞吐 + 结构化生成 |
| **TensorRT-LLM** | 推理 | NVIDIA 深度优化，性能高、复杂度高 |
| **Triton** | 推理 | 注意：NVIDIA Triton Inference Server ≠ OpenAI Triton（kernel 语言） |
| **Ollama / llama.cpp** | 本地推理 | Mac/CPU 跑量化模型；vLLM 的本地/低并发替代 |
| **MLflow** | 跟踪/注册 | 实验记录 + 模型版本；不是高性能推理 |
| **W&B / TensorBoard** | 跟踪 | 实验可视化；W&B 托管，TensorBoard 本地 |
| **FastAPI** | 接入 | Python API 框架 |
| **Docker / Compose** | 部署 | 打包与单机编排 |
| **K8s** | 部署 | 集群编排；多服务/多机器再上 |
| **Prometheus / Grafana** | 观测 | 指标采集 + 仪表盘 |
| **OpenTelemetry** | 观测 | 统一日志/指标/追踪的埋点标准 |
| **pgvector / Milvus / FAISS** | 检索 | 向量检索；pgvector 起步，FAISS 是库，Milvus 是向量数据库 |
| **LangChain / LlamaIndex** | 应用 | RAG/文档编排；不等于生产运行时 |
| **Ragas / DeepEval** | 评测 | RAG/LLM 质量评测 |
| **Airflow / Dagster** | 数据 | 批处理编排 |
| **Ray** | 分布式 | Train/Serve/Tune/Data 一套分布式能力 |
| **Iceberg** | 存储 | 湖表格式；数据平台阶段再上 |

## 8. 学习 / 落地顺序

1. **PyTorch 基础**：Tensor、autograd、`nn.Module`、optimizer、DataLoader、device；
2. **HF Transformers**：模型、tokenizer、训练/推理；
3. **PEFT/LoRA**：拿一个小模型做一次微调；
4. **FastAPI + Ollama/vLLM**：包一个 OpenAI 兼容接口；
5. **MLflow**：记录参数、指标、模型版本；
6. **Docker Compose + Prometheus/Grafana**：部署与观测；
7. 可选：Ray、Airflow、K8s、Iceberg、Milvus。

**每层选一个，不要混着学。** 先从“算 → 服务 → 看”这条最短路径走通，再补数据和调度。

---

## 9. 边界与常见误区

- ❌ 生产不是“把 demo 放大”。
- ❌ 不是 GPU 越大越好；先看任务和评测。
- ❌ 不是算法越新越好；基线和数据往往更决定结果。
- ❌ 不是先建平台再找应用；先有一条真实链路。
- ❌ 教学实现不能直接当生产参考（公式对，边界/规模/失败模式不对）。
- ❌ 不要把 38 个实验都服务化；选一个应用场景。
- ❌ 没有 golden set 不要调模型。
- ❌ 一开始就上 K8s / Volcano / Iceberg / Milvus，通常是在给未来的人写维护负担。
