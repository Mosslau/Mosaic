# 05 · constexpr 与编译期计算

> demo: `make && ./demos/05_constexpr`

## 1. 设计动机

"运行时能算的，编译期能不能先算掉？" 常量表、查找表、配置计算如果能在
编译期完成，运行时就是零成本。C++ 的命题：**用 constexpr 把任意函数提升为
编译期可执行**——这是 C++ 模板元编程（TMP）的现代替代品。

## 2. 机制拆解

```cpp
// constexpr 函数：既能在编译期算（用于常量），也能在运行时算
constexpr int fib(int n) {
    return n < 2 ? n : fib(n - 1) + fib(n - 2);
}

constexpr int FIB_10 = fib(10);   // 编译期求值，FIB_10 是编译期常量
int runtime = fib(20);            // 运行时求值，同一个函数
```

**constexpr 的约束**（这是它和普通函数的差别）：
- 函数体必须是"可常量求值"的（早期版本限制严格，C++14 后放宽到普通循环/分支）
- 输入是编译期常量时，结果强制在编译期算出
- `static_assert` 配合编译期断言：`static_assert(fib(10) == 55)` 编译不过就报错

**历史**：C++11 之前，编译期计算靠模板元编程（TMP）——用类型递归"算"，
可读性极差；constexpr 让编译期计算用**普通函数语法**写出来。

## 4. 代价与取舍

| 代价 | 说明 |
|------|------|
| 规则复杂 | 什么能 constexpr、什么不能，规则一直在演进 |
| 编译变慢 | 编译期计算 = 编译器替你跑程序 |
| 滥用风险 | 巨型编译期计算拖垮构建 |

**换来的**：运行时零成本常量、编译期断言（静态错误在编译期暴露）。

## 5. 对 Tenet 的启示

- ✅ **吸收"能提前做的检查提前做"**：Tenet 的错误在词法→语法→语义尽可能早的阶段
  暴露，与 constexpr"把检查提前到编译期"是同一个哲学
- ✅ **吸收"编译期常量"思想**：Tenet 有 `let` 无 `const`——
  演进时值得参照 C++ 加 `const`（编译期常量 + 不可变保证）
- ❌ **拒绝编译期计算/宏元编程**：对教学解释器，编译期求值是性能优化，
  不是语言设计的核心
- 💡 `static_assert` 式的"编译期验证"对应 Tenet 的单元测试文化

**一句话**：C++ 把计算提到编译期换取运行时零成本；Tenet 把错误检查提前
到最早期阶段，哲学相同，实现是"测试 + 静态类型"。
