# TenetLang 学习笔记写作规范

## Overview

TenetLang 仓库的 `languages/studies/` 目录是多门主流语言的系统化学习笔记库，最终服务于「学习 → 分析 → 合成 Tenet 语言」的闭环。本 skill 定义每个阶段的四层交付物标准——**知识文档 + 示例代码（examples/）+ 代码练习（exercises/）+ 综合项目（project/）**——并规范 Roadmap 与阶段目录的重构流程，保证任何一门语言、任何一个阶段写出来都长一个样。本 skill 只含规范与模板，不维护任何语言的现状快照（哪门语言有几个阶段、完成到哪，以各 roadmap 文件与磁盘目录为准）。

**适用范围**：本 skill 只管 `languages/studies/` 目录（roadmap、阶段笔记、代码层 README）。`analysis/`（设计解剖）与 `tenet/`（语言合成与实现）的写作、仓库根 README 等非 languages/studies/ 文档不受本规范约束——不要用本 skill 的章节模板去约束它们。

**管辖边界（不纳入本规范的文件）**：即使物理位置落在 `languages/studies/` 下，以下内容也不受本规范约束，**写作与检查都跳过，不要按模板整改**：

- 自动生成或工具产物：`CHANGELOG.md`、`LICENSE`、lock 文件、`target/`、`build/`、`.pytest_cache/`、`.ruff_cache/`、`.mypy_cache/`、`node_modules/` 等
- 第三方代码与示例数据：vendored 依赖、样例日志/二进制数据文件

判据：**该文件能否由某条命令重新生成，或是否由工具维护**——能，就不归本规范；只有人手写的笔记与代码层文档才归本规范。完成度矩阵与格式检查都不统计这些文件。

## 目录结构

```
languages/studies/<语言缩写>/                  # c, cpp, go, java, py, rs
├── <语言名>.md                        # Roadmap 总览（如 c.md, python.md）
└── ph01-<主题>/ ~ phNN-<主题>/        # N 个阶段目录（N 按语言复杂度定）
    ├── 01-<主题>.md                   # 知识文档（主文档，必含，编号与目录一致）
    ├── examples/                      # 文档示例的完整可运行版本（推荐）
    ├── exercises/                     # 代码练习：题目 + 参考实现（推荐）
    └── project/                       # 阶段综合项目（推荐）
```

规则：
- 阶段数不固定：由每门语言的 Roadmap 自行规划（可为任意 N）。唯一硬约束是 **Roadmap 中每个阶段必须对应一个 ph 目录**（承诺必须可兑现）；反向允许目录先行——先建 phXX 目录再回头在 roadmap 中补该阶段小节，但完成后两边必须对齐。skill 不断言任何具体语言当前有多少阶段，以各语言 roadmap 文件为准
- 阶段目录命名：`ph<两位数>-<kebab-case 主题>`，如 `ph04-memory-mgmt`；编号必须连续，重构删并阶段后重排编号
- 主文档文件名：`<两位数>-<主题>.md`，与目录主题一致，如 `ph04-memory-mgmt/04-memory-mgmt.md`
- 四层交付物：`.md` 知识文档是骨架必含；`examples/` `exercises/` `project/` 是肉身，重构/完善阶段时逐步补齐（完成度检查时按四层统计）
- 每个代码文件必须附带**可复现的编译/运行/测试方式**：文档（README 或文件头注释）写明验证环境（编译器/解释器版本、依赖库）、编译命令、运行命令、测试命令。**不强制在本环境实际编译/运行通过**（依赖库环境可能不同）；验证状态的三个位与书写格式见下节「验证状态声明规范」——禁止虚构验证结果

## 验证状态声明规范

**「已验证」必须可被第三方重跑复现，而不是一句声明。** 三个状态位与书写格式：

| 状态 | 何时使用 | 必须写出的内容 |
|------|---------|--------------|
| `已验证` | 在本环境按所给命令实际跑过并观察到结果 | ① **命令**（含编译器/解释器版本与关键 flag）② **输入**（具体测试数据 / 环境前提）③ **观察到的结果**（输出要点或退出码，不做概括） |
| `未在本环境验证` | 依赖缺失、平台不支持、沙箱限制等未能实跑 | ① 缺什么 ② 为什么缺 ③ 读者该在本机怎么验证 |
| `无法验证` | 该行为在本环境原理上不可复现（如已被修复的历史版本行为） | 明确写出"不可复现"的原因 |

正例（照此写）：

```text
已验证：Apple clang 21.0.0，cc -Wall -Wextra -Werror -std=c99 ex01.c -o ex01；
        输入 3 + 4 → 输出 7.00；输入 1 / 0 → 输出 "错误: 除数为零"
未在本环境验证：需 Redis 服务器（本机未安装）；读者可 docker run redis 后按同一命令验证
```

反例（一律不通过）：

```text
已验证
已在本环境验证，输出正确
```

**禁止的行为**：① 裸写「已验证」而不给命令/输入/结果；② 声称跑过依赖缺失的服务（真 Kafka/Redis/Docker/K8s）——必须标注「未在本环境验证」；③ 把「编译通过」说成「功能验证通过」——编译通过只写「编译通过（零警告）」。

**时效性**：`已验证` 是**某次运行**的快照，不是永久属性。工具链升级、源码被编辑、依赖版本变动后，旧的证据可能失效；场景 D 应把这类声明当作**易过期元信息**回访（见场景 D 第 4 步）。

**禁止用行号引用其他文件的实测输出**：写「见 `ex05.c:92`」这类精确行号，源码一编辑（哪怕只是上方插入一个注释）就漂移失效。改为引用**符号或片段内容**（如「见 `ex05-combo.c` 中 `demo_oob` 的溢出那一行」），或让输出由脚本文本比对生成。

## 外部规范层（本仓库已安装的兄弟 skill）

本 skill 不是孤立的。`.dsh/skills/` 下安装了一组外部规范 skill，与本 skill 构成**三层优先级**：

| 层 | 规范 | 管什么 | 冲突时 |
|----|------|--------|--------|
| L1 项目约定层 | **本 skill（tenetlang-notes）** | 笔记结构、章节模板、仓库特有规则（phXX 引用、blockquote 四用途、边界声明等） | **最高优先级，赢** |
| L2 通用基础层 | `markdown-style` | Markdown 语法正确性 + 通用风格（Google 文档风格指南） | 被 L1 覆盖时服从 L1 |
| L3 语言规范层 | `cpp-coding-standards` / `rust-patterns` / `golang-patterns` / `python-patterns` / `java-coding-standards` | 各语言代码片段的编码规范 | 被 L1 的教学性覆盖时服从 L1（见下） |

**调用时机**：

- 写/改任何 `.md` 笔记 → 先读本 skill 的「Markdown 排版规范」（L1），拿不准的通用语法/风格问题再参考 `markdown-style`（L2）的 `references/syntax-canon.md` 与 `references/style-overlay.md`
- 在笔记中写某语言的代码片段（examples/、exercises/sol-*、project/ 源码、文档内嵌代码块）→ 参考对应语言的 L3 skill：
  - C++ → `cpp-coding-standards`（锚定 C++ Core Guidelines 编号，可引用规则号如 R.11）
  - Rust → `rust-patterns`
  - Go → `golang-patterns`
  - Python → `python-patterns`
  - Java → `java-coding-standards`
  - C → 无外部规范（市场空白），沿用本 skill 要求：`-Wall -Wextra` 零警告 + 语言社区主流惯例

**教学性覆盖条款（L1 对 L3 的合法覆盖）**：笔记中的代码为教学服务，允许两种有意偏离 L3 的情形——(a) 「故意出错」示例（如演示 ASan 抓越界），必须在代码首行注释写明运行前提；(b) 为聚焦当前主题而简化无关部分（如跳过错误处理以突出语法点），需在正文或注释中说明"为聚焦 X 省略了 Y"。除此之外的代码应符合 L3 规范。

**完成度检查（场景 D）**：深检代码质量时，以对应 L3 skill 为判据之一；发现代码违规但属于教学性覆盖的，不记为缺口。

存量兼容原则：仓库早期笔记可能与本规范有出入（章节命名、子结构、是否有代码层）。执行任何任务时**以本 skill 为准**，不通过模仿旧笔记来推断规范；旧笔记的偏差在完成度检查（场景 D）中记录为待升级项，而非视为另一种合法格式。

## Git 变更与远程分支规范

规范管到「检查通过」，本节的落点是**检查通过之后如何与远程分支对齐**。以下取本仓库实际提交史（122 次提交，全在 `main`，跟踪 `origin/main`），不是通用最佳实践。

**① 工作分支与远程对齐**

- 本仓库在 `main` 上直接推进（无 feature 分支惯例），远程为 `origin`。**不要为本 skill 的改名/重构另开长期分支**——阶段目录改名已在历史上一次性完成并同步全库引用，再开分支只会让相对链接的核对对象分裂
- 跑场景 D 之前先确认本地与远程的关系：`git fetch` → `git status -sb` 看 `ahead/behind`。**在落后于远程的分支上跑完成度检查没有意义**（基线可能已经被别人改动），先同步再检查
- 不要把「提交前跑一遍完成度检查」（场景 A/B/C 的第 5~7 步）理解成"只要提交就自动合规"——该检查默认只看**工作区文件**，不看你将要提交的**变更集**；变更集层的问题见下面第 ③ 条

**② 提交信息体例**（与存量 122 次提交保持一致）

- 中文书写，可带类型前缀：`docs:` / `chore:` / `refactor:` / `fix:` / `analysis:`
- 体例：`<动作> + <范围> + <内容>`，动作常用「新建 / 补齐 / 修复」；范围带 `phNN` 与语言缩写；内容用「——」引出要点，多个要点用「，」分隔
- 本类工作固定句式：新建阶段 → `新建 <语言> phNN 四层交付物并升级存量链接——主文档 <行数>行，roadmap 推进至第 NN 节`；修深检问题 → `修复 phNN <语言> 场景 D 深检问题（P1→P2→P3）`
- 以"补齐/修复 + 结论"为主，不写"更新文档""改了一些东西"这类无信息量的描述

**③ 提交前核对变更集（本仓库的反复踩坑点）**

`git status --short --untracked-files=all` 必须逐行看过再提交。历史上**至少 7 次**提交把构建产物（`kvlog`、`wal_tool`、`test_buffer`、`logdemo`、`app.log*`、`*.dSYM`、`build/`）带了进去，随后只能追加 `chore: 移除 … 误提交的构建产物并加 gitignore` 补救。**一次提交前 10 秒的核对，能省掉一次补救提交**：

- 未跟踪（`??`）项里出现的可执行文件、`*.o` / `*.dSYM/` / `*.log` / `build/` / `target/` / `__pycache__/` → 不进提交，先确认 `.gitignore` 覆盖，再决定是否补规则
- 被修改（`M`）项里出现二进制或日志 → 说明它本就不该被跟踪，走"移除 + 补 gitignore"两步
- 自动生成物（`CHANGELOG.md` 等）按开头「管辖边界」处理：它们不归本 skill 的格式管辖，但**是否该提交由生成它的流程决定**，不要夹带在笔记类提交里
- 推荐固化为门禁：`python3 .dsh/skills/tenetlang-notes/scripts/validate.py --git` 会把上述检查跑一遍并给出候选清单

**④ 检查结论与远程提交绑定**

场景 D 的落盘记录（`.workbuddy/memory/YYYY-MM-DD.md`）**必须写明本次结论对应的分支与提交**，否则事后无法判断某个结论是在哪份代码上得出的：

- 已提交后记录：`基线：main @ <短 SHA>（origin/main 已同步）`
- 检查时工作区有未提交改动：`基线：工作区（未提交，基于 <短 SHA>）` 并列出涉及的路径——这正是 7 次误提交暴露的口径问题：**检查结论锚在哪个 revision 上必须写死**
- **不要事后补记当时的 SHA**——只能用检查那一刻真实存在的 revision，否则就是新一种"锚点漂移"
- `已验证` 的证据同样受此约束：**写入笔记的实测数字应与记录里的基线一致**；若后续源码或工具链变化导致重跑结果不同，按「验证状态声明规范」的时效性条款回访

## 工作流

### 场景 A：重构 Roadmap

对已有语言的 roadmap 做结构调整（改阶段切分、重排顺序、补全未展开阶段）：

1. 先读现有 `<语言名>.md` 与全部已有 ph 目录，列出「roadmap 承诺的阶段」与「磁盘实际存在的阶段」的差异清单
2. 确定新的阶段划分（数量、主题、顺序），与用户确认后再动手——重构 roadmap 是破坏性操作
3. 按新划分增删并改 ph 目录，重排编号保持连续
4. 更新 `<语言名>.md` 中全部阶段小节与 `📖 详细展开版见` 链接，保证链接与目录一一对应
5. 目录改名/迁移时，同步修正其他阶段笔记中的交叉引用。用以下命令找出全部引用点后逐个更新：
   ```bash
   # 找出引用了旧编号的全部笔记（以 ph04 为例，逐个旧编号执行）
   grep -rn "ph04" languages/studies/ --include="*.md"
   # 复核：解析全部相对链接并检查目标存在（覆盖 ./ 与 ../ 两种写法）
   python3 .dsh/skills/tenetlang-notes/scripts/validate.py --links
   ```
6. 提交前跑一遍完成度检查（场景 D）确认无悬挂链接

### 场景 B：重构/补全某个阶段

把已有阶段升级为四层完整交付物（知识文档 + 示例代码 + 代码练习 + 综合项目）：

1. 读对应语言的 Roadmap 总览，确认该阶段定位（前置阶段、为后续铺垫什么）
2. 评估现状：主文档章节是否齐全（对照 `references/phase-template.md`）、有无 examples/exercises/project
3. 补写或重写主文档，按模板章节结构执行。除七章结构外，两个内容项是**每次必写、不可省略**的（历史上反复漏）：
   - **第 1 节末尾的边界声明**：固定句式"这个阶段只涉及 X，**不涉及 Y、Z — 那些是 phYY/phZZ 阶段的内容**"，必须带具体 ph 编号
   - **第 2 章末尾的基线说明**："本文示例以 **<版本>** 为基线（<选择理由>），验证工具链 <版本>"，写法见 `references/phase-template.md` 的「## 2. 来源与演变」一节
4. 补代码层（结构见下节「阶段代码层结构」）：
   - `examples/`：把文档中的代码片段提取为完整可运行文件
   - `exercises/`：题量按 `references/roadmap-template.md`「写作要点」的题量带宽执行，题目描述 + 参考实现分离（`exercises/README.md` 出题，`exercises/sol-*.ext` 给参考解）
   - `project/`：Roadmap「推荐项目」小节的落地，含 `project/README.md`（需求说明 + 验收标准）+ 完整源码
5. 为全部代码补上可复现的编译/运行/测试说明（命令 + 验证环境，见「目录结构」规则），并按「验证状态声明规范」写足「已验证」的证据三要素；无法验证的标注「未在本环境验证」并说明缺什么，不虚构验证结果
6. 保持与同语言其他阶段的交叉引用（「属于 phXX 的内容，这里不展开」），编号变更后同步更新
7. 提交前跑一遍完成度检查（场景 D），确认本阶段四层交付物无缺口、无悬挂链接——编号变更后此步不可省略

### 场景 C：新增一门语言

1. 创建 Roadmap 总览 `languages/studies/<缩写>/<语言名>.md`，模板见 `references/roadmap-template.md`
2. 规划阶段切分（按 `references/roadmap-template.md`「阶段切分节奏」：基础 → 核心机制 → 生态/工程化 → 进阶专题），阶段数按语言复杂度定
3. 创建全部阶段目录骨架（至少含主文档占位）
4. 逐个阶段按场景 B 的标准填充四层交付物
5. 提交前跑一遍完成度检查（场景 D），重点做 roadmap ↔ 目录双向核对——批量新建时链接与目录名失配最常见

### 场景 D：完成度检查

分两层执行：**第 1~3 步是存在性检查**（全量、快速，只判"在不在"），**第 4 步是内容质量检查**（深检，判"对不对、全不全、齐不齐"）。被场景 A/B/C 作为提交前验收调用时，可只对本批涉及的目录跑深检。

1. 遍历 `languages/studies/*/`，按四层标准逐项检查：
   - Roadmap 是否存在、其列出的每个阶段是否都有对应 ph 目录与有效链接（双向核对：roadmap → 目录、目录 → roadmap 小节）
   - 每阶段：主文档是否存在且章节齐全 / examples 是否存在 / exercises 是否存在 / project 是否存在
2. 输出完成度矩阵（语言 × 阶段 × 四层交付物），标注缺口。矩阵统一用以下格式：
   ```markdown
   ## 完成度矩阵（YYYY-MM-DD）

   图例：✅ 完整 | 🟡 存在但不完整 | ❌ 缺失

   | 语言 | 阶段 | 主文档 | examples | exercises | project | 备注 |

## Roadmap 总览规范（`<语言名>.md`）

必须包含的元素，按顺序：

1. **标题**：`# <语言> 语言学习 Roadmap`
2. **导语**（blockquote）：一句话说明这门语言的学习定位/应用方向（如 C 面向系统底层、KV 存储引擎）
3. **N 个阶段**（数量按语言复杂度定，与磁盘 ph 目录一一对应），每阶段固定小节：
   - `### 目标` — 一句话，可检验
   - `### 学习内容` — 知识点列表
   - `### 必会概念` — 核心心智模型列表（区别于"学习内容"，这里是必须内化的认知）
   - `### 示例` — 一段可运行代码或目录结构示意
   - `### 练习` — 动手题（题量带宽见 `references/roadmap-template.md`「写作要点」）
   - `### 阶段验收` — 自检标准（"能……"句式）
   - `### 推荐项目` — 1~2 个综合小项目
4. 每个阶段标题下方加链接行：`> 📖 详细展开版见 [phXX-主题/XX-主题.md](./phXX-主题/XX-主题.md)`

## 阶段详细笔记规范（`phXX-主题/XX-主题.md`）

必须包含的章节，按顺序：

1. `# <语言> <阶段主题>阶段` + 一句 blockquote 导语
2. `## 1. 概述` — 阶段定位 + 覆盖维度表格 + 边界声明（明确"不涉及 X，属于 phYY"）
3. `## 2. 来源与演变` — 该主题的历史背景、标准/版本演进表格、本文的基线说明
4. `## 3. 语法与参数` — 主体内容，3.1/3.2/... 小节展开，代码示例 + 表格为主
5. `## 4. 底层原理`（可选但推荐）— 该主题的实现机制/内存模型/编译器视角
6. `## 5. 使用场景`（推荐，存量笔记普遍有）— 该知识在真实工程中的用途、什么场景选它/不选它
7. `## 6. 代码示例` — 完整可运行示例（指向 `examples/` 目录中的文件，文档内嵌关键片段）
8. `## 7. 总结` — 关键要点回顾 + 阶段验收清单 + 指向 `exercises/`、`project/` 的入口 + `### 下一阶段` 导航链接（串联学习路径）

**内容深度要求**：在阶段主题范围内鼓励写透"为什么这样设计、常见陷阱、底层原理"等教学增量（详见 `references/phase-template.md` 写作要点第 8 条）——这是优点不是冗余。判断标准：增量始终围绕当前阶段主题，不引入后续阶段才讲的概念；超纲（讲了别的阶段的内容）才是问题。

## 阶段代码层结构

每个阶段的代码交付物按此组织：

```
ph<NN>-<主题>/
├── <NN>-<主题>.md            # 知识文档，编号与目录一致（如 ph04-memory-mgmt/04-memory-mgmt.md）
├── examples/                 # 文档示例的完整版
│   ├── README.md             # 每个示例一句话说明 + 运行命令
│   └── ex01-*.ext ...        # 可独立编译/运行
├── exercises/                # 代码练习
│   ├── README.md             # 题目列表：每题含目标、提示、验收标准（不附答案）
│   └── sol-01-*.ext ...      # 参考实现（与题目一一对应）
└── project/                  # 阶段综合项目
    ├── README.md             # 需求说明、功能清单、验收标准、扩展方向
    └── <项目源码>            # 完整可构建
```

规则：
- `exercises/` 的题量带宽与题解分离要求以 `references/roadmap-template.md`「写作要点」为唯一权威来源，本节不重复维护；`README.md` 出题（每题含目标/要求/验收标准，不附答案），`sol-01-*.ext` 给参考解（与题目一一对应），方便学习者先自己做
- `project/` 对应 Roadmap 该阶段「推荐项目」小节，选 1 个落地即可，不求全
- 代码风格与该语言社区主流规范对齐（如 C 用 `-Wall -Wextra` 零警告、Rust 过 `clippy`、Python 过 `ruff`），具体规则以对应的外部语言规范 skill（L3，见上节）为准；C 无外部 L3 skill，其 L3 规范即本 skill「外部规范层」一节中对 C 的要求（`-Wall -Wextra` 零警告 + 语言社区主流惯例）
- examples/project 附可复现的构建/运行/测试说明：编译型语言给构建命令（Makefile/CMakeLists.txt/Cargo.toml 或 README 单行命令）+ 运行/测试命令，解释型语言给运行/测试命令 + 依赖安装方式

## Markdown 排版规范

### 仓库特有规则（L1，L2 没有）

**标题结构与模板绑定**
- `#` 主标题句式固定：roadmap 是 `# <语言> 语言学习 Roadmap`，阶段笔记是 `# <语言> <阶段主题>阶段`；**全文只允许这一个 H1**
- roadmap 编号阶段标题句式固定 `## N. <主题>阶段`（统一带"阶段"后缀）；编号阶段之后允许追加**非编号**的 `##` 附加章节（推荐学习顺序 / 语言对比 / 项目路线 / 推荐路线 / 附录），规则见 `references/roadmap-template.md`「尾部附加章节」
- "阶段性项目验收标准"是元规则、不含语言知识点，**不占编号阶段**，统一放尾部 `## 附录：阶段性项目验收标准`
- 阶段笔记章节固定 `## 1.` ~ `## 7.`（**这是 Markdown 的一级子标题 `##`，不是正文序号**——「1. 概述」是文档章节编号，不是 Markdown 的 `#`），小节 `###` 并以 `3.1`/`3.2` 形式编号，与 `## 3.` 一一对应；标题编号一律用「数字 + 点 + 空格」（`## 1. 概述`），不得混用「第一章」「1、」「(1)」等异体编号

  ```

  退出码：0 = 无问题，1 = 存在问题（可用于提交前门禁）。

  覆盖：roadmap ↔ ph 目录双向核对、四层交付物存在性、7 章齐全、单一 H1、标题前后空行、章节空壳、相对链接可解析（含 `../` 跨阶段链接）、题解数量对应、必查小节名、**建设状态断言与磁盘核对**（断言「待建」的阶段必须真的不存在，引用的节号优先于 `phNN` 解析）；`--git` 另覆盖分支/远程同步状态与变更集里的构建产物。**不管**内容质量判断（知识点覆盖、教学增量、代码是否正确）、「待建」之外的契约定性描述与「已验证」证据是否属实——那些仍需按场景 D 第 4 步人工深检，并可用 `--deep` 列出需人工核对的漂移项（裸「已验证」、行号引用、版本号）。
