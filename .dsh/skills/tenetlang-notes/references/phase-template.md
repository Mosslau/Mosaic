### 3.1 变量与赋值

```rust
let x = 5;      // 类型由初始化值推断，绑定后不可变
let mut y = 2;  // mut 声明可变绑定
y = x + 1;      // 允许重新赋值
```

Rust 默认变量不可变，**可变性需显式声明**。

**可变绑定（mut）**

- 写 `mut`：绑定可变，可重新赋值
- 不写 `mut`：重新赋值是编译错误——默认不可变是语言的安全设计

> 本阶段只用基础绑定，**借用与所有权规则属于 ph02 所有权阶段**，这里只需理解「默认不可变」这一条。

**③ 第 7 章小节名（模板小节保持原样；「跨语言对比」作为追加小节，插在模板小节之间逻辑顺的位置）**

### 关键要点

## 写作要点

1. **边界声明是灵魂**：第 1 节末尾必须明确"不涉及什么、属于哪个后续阶段"。这是防止笔记之间内容重叠的关键机制。
2. **来源与演变**：不是凑字数的历史课——它回答"为什么这个语法长这样"，为后续 `analysis/` 目录的设计解剖埋下伏笔。
3. **基线说明**：涉及标准/版本时明确基线（如 C99、C++17、Go 1.21），避免读者困惑"为什么我的编译器报这个错"。
4. **代码即文档**：示例代码的行内注释承担 50% 的解释工作，注释直接写在关键行尾部。
5. **表格优先**：凡是"多维度对比"（类型大小、运算符类别、版本差异）一律用表格，不用散文罗列。
6. **交叉引用格式**：提及其他阶段一律用 `phYY <阶段名>阶段` 格式，保持全库一致；阶段编号变更后必须 grep 全库更新引用。**不得用行号引用其他文件的实测输出**（如「见 `ex05.c:92`」）——源码一编辑即漂移失效，改为引用符号名/片段内容，或让输出由脚本比对生成。
7. **练习题目与答案分离**：exercises/README.md 只出题，参考实现放 sol-* 文件；文档正文不附答案。
8. **教学增量要写透**：在阶段主题范围内，鼓励写"为什么这样设计、常见陷阱、底层原理"这类超出最小必要的内容——例如 C 的 `scanf` 为何要 `&`、Java 的 Scanner 换行坑、Go 的 nil map panic、Rust 的 `println!` 宏与格式符、Python 的 `__name__ == "__main__"`、C++ 的 auto 推导规则。这些是**教学增量**（在同一主题内讲透），不是**超纲**（讲了别的阶段的内容）。判断标准：增量始终围绕当前阶段主题，不引入后续阶段才讲的概念。写透是优点，不是冗余。
9. **代码必须有可复现的编译/运行/测试方式**：写入 examples/exercises/project 的每个文件，都在文档（README 或文件头注释）给出验证环境（编译器/解释器版本、依赖）、编译命令、运行命令、测试命令。不强制在本环境实际跑通（依赖库环境可能不同）；实际验证过的写「已验证」并**必须带证据三要素：命令 + 输入 + 观察到的结果**（裸写「已验证」四个字不算），未验证的必须如实标注「未在本环境验证」并说明缺什么，禁止虚构验证结果；也不得把「编译通过」说成「功能验证通过」。格式见 SKILL.md「验证状态声明规范」。
