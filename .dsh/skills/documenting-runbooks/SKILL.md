# Documenting Runbooks

## 使用边界

此 skill 用于以下任务：

- 编写故障诊断和恢复流程
- 记录发布、回滚、扩缩容或数据恢复步骤
- 说明某类告警或错误对应的处置路径
- 把散落在聊天、笔记中的运维步骤整理成可执行 runbook

此 skill 不用于：

- 解释系统整体架构
- 写功能使用教程
- 写 API 参考或算法说明
- 虚构从未执行过、也无法从源码或配置推导的处置流程

## 写作前确认

开始前确认：

- 读者：值班工程师、开发工程师还是运维负责人
- 操作类型：诊断、修复、回滚、备份还是发布；它决定回滚章节是否适用
- 适用服务与环境：服务名、环境名（生产/预发/测试）、覆盖的操作时间范围（该流程保持有效的时段或版本区间）
- 触发条件：告警、错误、用户反馈还是已知事件
- 可执行来源：真实命令、日志位置、配置、脚本和验证方式
- 风险边界：哪些步骤需要权限、哪些情况下必须停止并升级
- 是否具备可运行的测试环境；不具备时按「输出契约」走源码模式

## 写作流程

1. 找到真实服务和环境入口，不凭记忆写目录或命令。
2. 已有 runbook 和运维笔记可作为事实线索，但不能替代真实命令、日志格式和恢复验证，也不能因为仓库风格而省略风险边界。
3. 先写触发条件和停止条件，再写诊断与处置。
4. 用日志、指标、配置或命令确认每个判断点；每个判断点写出具体命令与判读规则。
5. 对破坏性操作明确前置检查、备份、回滚和执行权限。
6. 用真实或接近真实的测试环境执行步骤，再标记验证方式；无法实测的步骤按「输出契约」的源码模式单独成节。
7. 把新 runbook 登记到所在环境的索引或 README，使其他 runbook 的「转向其它 runbook」可被找到；无索引时在文档开头列出相邻 runbook。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；命令、日志片段、告警名保留原文。
- **位置与命名**：按 `<服务或场景>-runbook.md` 命名；已有运维文档目录时放入其中。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**源码模式（降级）**：没有可运行环境时，不因此停止写作，也不得虚构流程。改为：只写能从源码、配置、脚本或部署文件推导出的步骤，全部标注「来源确认（未实测）」；禁止任何破坏性命令（重启、删数据、改配置、切流量）；把所有此类步骤集中放在「未验证步骤」一节，明确标注“本 runbook 尚未在真实环境验证，执行前必须先在测试环境走一遍”。

**回滚章节适用范围**：仅发布、迁移、配置变更类操作必须写回滚。纯诊断型 runbook 写「不适用（本 runbook 不改变系统状态）」并说明理由。

本 skill 的说法若与 `references/runbook-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 开头一行之内给出适用服务/环境、操作类型（诊断/发布/回滚/备份）、操作时间范围，以及执行人或审批角色
- 读者能根据列出的症状（告警名、错误文本、指标异常）判断本 runbook 是否适用
- 诊断步骤给出具体命令、日志位置或查询入口；出现“检查服务状态”这类无入口的步骤即不合格
- 每个判断点写成「命令 → 判读规则」，读者知道看到什么就进入哪个分支
- 停止条件写成可判定的阈值形式：`当 <指标> <比较符> <阈值> 持续 <时长> 时停止`；无适用阈值时写明停止依赖的具体信号
- 升级对象写成角色或负责人入口；没有值班联系人时给出 owner 与 issue 链接，不写“联系运维”
- 破坏性操作逐条列出前置检查、备份、权限与回滚动作；缺少任一项即不合格
- 回滚章节存在：适用则给出回滚目标版本、回滚前备份、回滚期写入处理与失败升级路径；不适用则写明不适用及理由
- 恢复验证写成「命令 → 期望输出/断言」形式，读者据此能判断故障已结束
- 步骤顺序可连续执行，且每步写明执行环境；不要求读者自行推断环境差异
- 命令、脚本、路径和版本与当前系统一致，且能追到来源
- 未验证步骤与已验证步骤分区呈现，未实测部分集中在独立小节并标注
- 每个被声称的行为或阈值都能追溯到源码、配置、日志或真实运行记录；无法追溯的不得写入

## 与其他 skill 的边界

- 若内容是让读者学习完成一个任务，改用 `documenting-tutorials`。
- 若内容是系统架构解释，改用 `explaining-systems`。
- 若内容是接口或数据现状，分别改用 `documenting-api-contracts` / `documenting-data-models`。
- 若用户只是提问、不要求产出文档，直接用对话回答。
