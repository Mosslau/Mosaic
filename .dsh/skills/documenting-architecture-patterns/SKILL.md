# Documenting Architecture Patterns

## 使用边界

此 skill 用于以下任务：

- 解释一个架构模式解决什么问题
- 说明模式中的参与者、职责和协作方式
- 分析模式在当前系统中的落地位置
- 比较相近模式并解释适用边界
- 判断某个模式是否适合当前问题
- 记录模式引入后的演进、版本兼容与替换代价

此 skill 不用于：

- 描述某个系统实例的完整架构
- 解释一个具体算法
- 讲解语言特性
- 输出只含优点、没有代价的模式介绍

## 写作前确认

开始前确认：

- 读者：架构师、开发者、技术负责人还是系统维护者
- 文档目的：理解模式、评估是否采用、指导实现，还是审查现有设计
- 模式是理论模式还是项目中的具体实现
- 资料来自哪些权威来源
- 是否有真实系统代码、类、文件或调用链可以引用
- 该模式在当前对象中是否已经历过版本演进或替换；有则一并记录，无则明确写“无落地演进记录”

## 写作流程

1. 先说明上下文和问题，不直接跳到结构图。
2. 列出冲突力量，解释模式为什么是权衡后的答案。
3. 说明参与者、结构、协作和运行流程。
4. 写出可观察的代价和失效方式，不能只讲好处。
5. 给出适用条件和不适用条件。
6. 如果文档涉及真实系统落地，把参与者映射到实际文件、类、模块或进程；纯理论模式则明确标注“理论说明”。
7. 若有真实落地，补写演进与兼容：模式引入前后发生了什么变化、涉及哪些版本或迁移、替换该模式的代价与触发条件；纯理论模式则显式写明“无落地演进记录”。
8. 最后用权威资料和现有源码或架构文档验证结论；不能把个人理解和推测写成已验证事实。

## 输出契约

交付前确认以下四项，缺一项即视为未完成：

- **语言**：正文跟随当前仓库主要文档语言（本仓库为中文）；模式名保留通行英文名。
- **位置与命名**：按 `<模式名>.md` 命名；已有架构文档目录时放入其中。
- **位置与命名优先级**：调用方显式指定的路径或文件名优先；未指定时按本 skill 的命名规则。
- **完整性**：不得残留任何未填充的占位段落（例如以括号包裹的提示句）。
- **事实标注**：未验证内容必须显式写「未验证」或「来源确认」，不得以留空或省略代替；结论来自来源材料而非本人核对时，用「来源确认」。

**两种降级模式，按可得证据选择并在开头声明**：

- **理论模式**：没有真实系统落地。全文开头声明「理论说明」；参与者映射一节写「本对象暂无落地实例」；不得出现任何未确认的文件名、类名或模块名。
- **来源材料模式**：模式有落地，但无源码或集群可查（只见于设计文档、会议记录或他人转述）。全文标注「来源确认」；参与者映射写到「服务/进程/端口/制品」粒度并注明“文件级位置未核对”；演进与兼容只写材料确实记录的内容，其余写「未验证」并给验证动作；开头声明“本文基于来源材料，未核对源码与运行环境”。

本 skill 的说法若与 `references/architecture-pattern-standard.md` 冲突，以该 reference 为准。

## 写作质量门

最终交付前必须满足：

- 文档开头一段写明模式名称、类别、写的是理论模式还是具体落地，以及依据的权威来源
- 模式解决的问题用现实约束说清，不出现“需要灵活性和可扩展性”这类无法验证的表述
- 参与者职责各自可区分；出现“核心组件”这类统称即不合格
- 协作流程给出方向与顺序，读者能据此画出调用链
- 优点和代价都给出可观察结果，例如接口数量、间接层数量、一致性保证、故障范围、扩展路径
- 适用与不适用条件各写成可判定的信号：每条条件能对应到一个可观察现象或一个真实位置
- 有真实落地时，参与者映射到具体文件/类/模块，并写明当前实现是否严格遵循模式、哪些属于变体或例外
- 演进与兼容一节存在：有落地则给出变更范围、兼容影响与替换代价；无落地则显式写明无记录
- 没有把模式名称当成架构事实；理论模式与系统实例的边界在开头已声明

## 与其他 skill 的边界

- 若目标是解剖某个具体系统/框架/代码库的现状，改用 `explaining-systems`。
- 若目标是记录一次具体的设计取舍决策（ADR），改用 `documenting-design-decisions`。
- 若目标是算法或数据结构，改用 `explaining-algorithms`。
- 若用户只是提问、不要求产出文档，直接用对话回答。
