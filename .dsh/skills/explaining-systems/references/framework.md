# 框架解剖写作标准

这个标准用于解剖一个可复用框架或库。它不能只写“怎么调用 API”，还要回答：框架的设计思想是什么，调用后内部发生了什么，扩展点在哪里，哪些能力由框架承担，哪些能力必须由使用方承担。

它也不是仓库模板。已有教程和项目文档可以提供入口，但“框架内部如何运行”的结论必须能追溯到源码、测试或可观察行为。

## 事实标注与证据规范

以下规范在整个 skill 家族中统一使用。SKILL.md 与本 reference 冲突时，以本 reference 为准。

### 事实标签词表

每条关键结论必须带且只带下列标签之一：

| 标签 | 含义 | 可用于 |
| --- | --- | --- |
| `源码确认` | 我本人直接读到源码、配置或 schema | 结构、签名、默认值、常量 |
| `运行确认` | 我本人执行命令并观察到输出 | 耗时、计数、退出码、实际报错 |
| `规范确认` | 来自规范、RFC、官方文档或论文 | 语义、协议约定、算法性质 |
| `来源确认` | 我本人没有读到源码，但来源材料陈述了该事实；来源可能是引述源码的文档、他人整理的笔记或任务给定材料 | 命令、配置项、路径、指标名、阈值；**仅当该材料的原始出处指向源码或配置时使用** |
| `文档确认` | 只来自二手文档或口头说明 | 背景、意图，不得作为行为依据；材料的原始出处是发布说明、会议记录、内部 wiki 等非源码文档时用此档 |
| `设计意图` | 作者目标，未验证是否达成 | 动机、规划，不得写成现状 |
| `未验证` | 尚无法确认 | 一切推测与待办 |

### 标签用法

- **选档顺序**：先问「我本人读到源码了吗」→ 是则用 `源码确认`；否则问「我本人执行并看到输出了吗」→ 是则用 `运行确认`。两者都否、但来源材料有明确陈述 → 用 `来源确认`。
- **不要用 `源码确认` 标注你只是转述的内容**。这正是 `来源确认` 要解决的问题：区分「作者亲自核对了源码」与「作者转述了一份声称来自源码的材料」。
- `来源确认` 的结论来自材料，作者不对其真实性负责，但必须负责标注它未经本人核对；需要读者据此行动时，配一个可自行复核的命令。
- 每条关键结论在句末标注，例如：“`solve` 的默认启发式为 `manhattan`（源码确认，`<文件>:<行号>`）。”“服务监听 `:9100`（来源确认，材料「Metrics endpoint」）。”
- 能被源码直接读到的结论不要标 `运行确认`；能运行的结论不要标 `规范确认`。
- 全局标签可写在文档开头的状态行，但局部结论必须单独标注。
- 无法给出标签的结论不得写入正文。
- **同一个结论只给一个标签；不要用「标签 + 限定词」表达单标签装不下的意思**。当一条结论里有一部分已确认、另一部分未确认时，拆成两句分别标注，而不是叠在一句上。例：

  ```text
  不合格：清单里含 011_add_capture_mode.sql，属新增（来源确认，未验证）
  合  格：清单里含 011_add_capture_mode.sql（来源确认，材料「migrations 目录」）。其变更类别无法判定，因为看不到 DDL（未验证）。
  ```

### 证据书写

- **数字**：每个被报告的数字必须能追溯到命名的脚本、命令或来源；无法追溯的数字不得写入。禁止把未运行过的实验写成运行结果。
- **命令与输出**：每条命令与它的实际输出成对给出；只给命令不给输出，必须标注 `未验证` 并说明未实测的原因。
- **未运行的命令**：在文档没有对应环境、或作者没有执行过命令时，命令照给，但必须紧跟 `未验证` 并注明「作者未运行」，必要时补一句为什么要给一条没跑过的命令（读者照做即可验证）。**不得让读者以为那是实测输出。**
- **预期输出标记**：每个预期输出标注 `[固定]`（与版本/环境无关，如文件存在、断言通过）或 `[随环境/版本变化]`（如耗时、内存、时间戳）；无法判断时标 `[随环境/版本变化]`。
- **第三方实测值不算 `运行确认`**：材料中出现的 `[measured: …]`、截图数字或他人记录的性能数据，一律标 `来源确认`，并在紧邻处写明「非本机运行结果」。这是最容易误标的一类。
- **引用格式**：有行号时写 `<文件>:<行号>`；只有文件名时写 `<文件名>`；只有材料时写「材料「<小节标题>」」。三者都没有时写 `未验证`。**不得编造行号。**
- **不适用**：某章节在本对象上不适用时，写“不适用”并给一句理由，不留空、不省略。
- **禁止占位**：交付文档不得残留任何未填充的占位段落（例如以括号包裹的提示句）。正文中的说明性括号不属于占位，但不得以括号代替应写的内容。
- **待验证清单格式**：集中收纳未验证项时使用固定列名，使不同文档可比较：

  | 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
  | --- | --- | --- | --- |
  | V1 | <待确认的结论> | <缺什么证据：无源码 / 无环境 / 材料未给> | <可执行的命令或动作> → <看到什么算确认、看到什么算否定> |

- **完整性检查**：正文中每个“待验证”“不适用”“无此项”都必须指向具体原因或后续动作。

## 对象与版本

开始前记录解剖对象：

- 框架名称、版本/提交、语言和包管理器来源
- 文档覆盖的 API 版本和运行环境
- 文档描述的是官方语义、源码实现，还是某个项目中的使用方式
- 与普通库、平台、插件和框架内层模块的边界

## 定位与设计哲学

先写清楚：

- 框架解决什么问题
- 它和普通函数库、平台或业务系统的区别
- 框架主张的设计哲学，例如约定优于配置、显式优于隐式、单向数据流
- 面向的典型使用者和使用场景
- 框架边界，什么场景不应使用它

## 核心抽象

框架通常由少量核心抽象构成。对每个抽象说明：

- 抽象名称和概念含义
- 使用方提供什么，框架提供什么
- 生命周期何时创建、运行、销毁
- 在框架内部的职责
- 对应代码位置

例如：训练框架中的模型、数据集、优化器、调度器、回调；Web 框架中的应用、路由、中间件、请求上下文。

## 主流程解剖

选择一条最典型的流程，例如一次请求、一次训练、一次渲染或一次任务执行，追踪框架如何把它调度完成：

1. 使用方从哪里调用入口
2. 框架如何创建上下文和核心对象
3. 核心对象如何协作
4. 钩子、回调或扩展点何时触发
5. 框架在哪个阶段替使用方完成默认行为
6. 流程结束时如何清理资源或返回结果

主流程应给出源码入口和关键调用位置。

## API 与扩展点

说明使用方真正需要知道的最小 API：

- 必用 API 和生命周期顺序
- 可选 API 和高级能力
- 配置或声明式选项
- 扩展机制，例如继承、组合、回调、插件、中间件、装饰器
- 官方扩展和社区扩展的区别
- 版本更新时哪些 API 容易变化

不要复制框架的完整 API 文档，只保留本框架文档场景所需部分，并链接权威参考。

## 内部模块与依赖

解剖内部结构：

- 核心模块有哪些
- 模块之间如何依赖，是否允许循环依赖
- 公共抽象、内部实现和平台适配分别在哪里
- 框架如何隔离内核与插件
- 内部数据结构和状态由谁拥有

## 框架做了和没做的事

用明确清单区分职责：

- 框架负责的生命周期、调度、资源管理或默认策略
- 使用方必须提供的业务逻辑、数据格式或生命周期钩子
- 框架不负责的错误处理、安全、持久化或并发策略
- 框架默认行为在什么情况下会带来意外

## 运行机制与限制

解释关键运行机制：

- 初始化、执行、清理各阶段
- 线程、进程、异步任务或设备资源的组织方式
- 错误传播方式
- 性能开销主要来自哪里
- 哪些能力有明确边界，例如不支持的热更新、不保证的实时性

## 常见误用与调试路径

对使用者最有价值的部分：

- 调用顺序错误导致的典型问题
- 扩展点写错位置导致的典型问题
- 状态或生命周期误解导致的资源泄漏
- 如何定位“框架自动执行了没想到的行为”
- 调试时读取日志、状态或断点的位置

## 源码导航

列出：

- 框架仓库顶层目录结构
- 核心抽象的定义位置
- 主流程入口
- 扩展点接口
- 测试或示例目录

## 无运行环境时的写法

无法实际调用框架时，不因此停止写作，也不得虚构运行结论：

- 全文只使用 `源码确认`、`规范确认`、`文档确认`、`设计意图`、`未验证` 五种标签；不使用 `运行确认`。
- 不写“实测耗时”“实际行为为”这类结论；主流程解剖改为标注源码中的调用顺序与位置。
- 文档开头声明“本文基于源码阅读，未实际调用该框架”。
- 把需要运行才能确认的点集中列入「待验证入口」，每条给出可执行的验证动作。

## 待验证入口

本节集中列出本文未验证、但读者可以自行验证的结论。每条写成「待验证结论 → 验证动作 → 期望观察」，例如：

- 「框架在 `X` 阶段自动注入默认配置」→ 运行 `<最小调用示例>` → 观察框架是否在该阶段产生预期副作用
- 「扩展点 `Y` 在初始化后不可更改」→ 在初始化后调用 `<命令>` → 观察是否报错及错误类型

无法实际调用框架时，本节不可省略：它是读者接手验证的入口，也是本文与已验证文档的边界。

## 示例

以下用同一结论演示两种证据条件下的写法差异。结论：框架在初始化阶段触发 `on_start` 钩子。

### 证据充分：可指向真实代码与运行

```markdown
框架在一次生命周期开始时触发 `on_start` 一次，且发生在加载配置之后、进入主循环之前（源码确认，`<框架源码目录>/<初始化文件>:<行号>`、`<钩子注册表文件>:<行号>`）。

- 初始化入口 `<初始化文件>:<行号>` 依次调用 `load_config()`、`emit("on_start")`、`run_loop()`（源码确认，`<初始化文件>:<行号>`–`<行号>`）。
- `emit` 在 `<钩子注册表文件>:<行号>` 遍历已注册回调；回调签名与注册 API 见 `<扩展点文件>:<行号>`（源码确认）。
- 运行最小调用示例 `<调用示例文件>:<行号>`，实际输出（运行确认）：
  # 输出：[固定]
  load_config
  on_start
  run_loop
```

### 证据受限：只有二手材料

```markdown
官方文档称框架在初始化阶段触发 `on_start`（来源确认，材料「<小节标题>」），教程示例把它写在配置加载之前（来源确认，材料「<小节标题>」）。

- 触发次数、与配置加载的先后顺序、主循环前是否还有其他钩子，均无法由材料确定（未验证）。
- 「初始化后不能再注册钩子」只有教程暗示，未经源码或运行核对（未验证）。

| 编号 | 待验证项 | 为什么现在无法确认 | 验证动作 → 期望观察 |
| --- | --- | --- | --- |
| V1 | `on_start` 每次生命周期只触发一次 | 无源码、无运行环境 | 在钩子内计数后运行 `<运行命令>` → 计数为 1 算确认，大于 1 算否定 |
| V2 | `on_start` 在配置加载之后触发 | 两份材料对顺序说法不一致 | 读 `<初始化文件>:<行号>` 的调用顺序，并在回调内读配置 → 两种方式结论一致算确认 |
```

对照：证据受限版把「初始化阶段触发」写成材料转述，触发次数与顺序一律降为 `未验证`，不得替材料补出确定顺序。
