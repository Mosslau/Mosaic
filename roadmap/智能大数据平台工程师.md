# 四、通用数据平台的业务知识体系

你要重点理解的不是某个具体行业，而是数据如何驱动业务：任何业务都能被抽象成一组相对稳定的对象，以及它们随时间产生的事实。

## 1. 核心业务对象

一套通用的数据平台，建模时最终都会落到四类对象上：实体（Entity）、事件（Event）、指标（Metric）、维度（Dimension）。它们分别回答“谁/什么”“发生了什么”“怎么衡量”“从什么角度看”，是平台建模的骨架。

|对象|定义|平台为什么关心|建模方式|中性示例|
|---|---|---|---|---|
|实体 Entity|业务中相对稳定、有唯一标识和生命周期的对象|实体档案是所有明细数据挂载的锚点，实体打通决定后续分析能不能关联|实体档案表 + 拉链表 / 快照表，保留标识映射与状态变迁|用户 User（user_id、注册渠道、生命周期状态）；订单 Order（order_id、订单状态、金额、创建时间）|
|事件 Event|在某个时间点发生的、不可变的事实记录|事件表通常是平台数据量最大、接入最频繁的部分，决定接入与计算成本|事实表 + 时间分区；以 event_id 保证幂等，以事件时间支持乱序|业务动作事件（user_id、action、ts）；状态变更事件（order_id、status、ts）|
|指标 Metric|对事件与实体状态的数值化聚合|指标是业务和数据之间的契约，口径、血缘、SLA 都要被治理|原子指标 → 派生指标 → 复合指标；指标层 + 语义层统一口径|日活跃实体数（DAU）、P95 处理延迟、失败率、转化率|
|维度 Dimension|观察事实的角度与分组方式|维度决定同一份事实能否被一致地切片对比|星型模型的维度表；缓慢变化维用拉链表或快照|时间（日 / 周 / 小时）、地域、渠道、产品线、实体类型|

至少要建立起这几张骨架表的心智模型：

- dim_entity / dim_user：实体维表，统一标识与属性
- dwd_*_event：明细事实表，按事件时间分区
- dws_*_day：轻度聚合的实体 / 维度日粒度汇总
- metric_def：指标定义与口径元数据

判断一个平台是否成熟，往往就看这四类对象是否清晰：实体有没有打通、事件有没有统一、指标有没有口径、维度有没有一致性。很多“数据对不上”的问题，根因都不是计算错误，而是这四类对象没有被定义清楚。

你应该用一个主项目统领所有技术：

> **通用数据平台**

然后每门技术都服务于这个平台：

|技术|服务的目标|
|---|---|
|Java|业务服务、指标服务、规则服务|
|Go|多源接入、高并发网关|
|Python|数据分析、AI 应用、模型服务|
|Kafka|数据总线|
|Flink|实时计算|
|Iceberg|湖仓底座|
|ClickHouse / Doris|实时分析|
|K8s|部署与治理|
|OTel|可观测性|
|LLM|智能诊断与问数|
|Rust / C++|底层理解与基础设施能力|

---

# 十二、最终路线一句话

你现在最好的路线是：

> **以通用数据平台为主线，用 Java / Go / Python 打通多源数据接入、实时计算、湖仓建模、微服务和 AI 大模型应用；  
> 以 Rust / C++、数据库内核和分布式系统作为长期技术深度，最终成长为既懂业务价值、又懂平台工程、还懂底层基础设施的数据智能负责人。**

这条路线是成立的，而且比单纯“Java 后端”“大数据开发”“AI 应用开发”“Rust 系统工程师”都更贴合“通用数据平台 + AI 平台数据中心”这个定位。
