## 第一章 个人：AI 能力 Level 1→10

> 来源：`roadmap/image/AI流程FDE/20261030-223614.jpg`

图的判断口径放在标题下：**差距不在会不会问，而在能不能把 AI 变成结果。** 五个判断维度是「提问质量 / 迭代能力 / 工作流整合 / 结果落地 / 复利能力」。

### 1.1 十级阶梯

| Level | 名称 | 表现 | 理由（这一级的本质变化） |
|---|---|---|---|
| 1 | 围观者 | 听说 AI 很厉害，但几乎不用。 | 停留在认知层，还没有形成行动。 |
| 2 | 体验者 | 偶尔用来翻译、润色、查资料。 | 把 AI 当玩具或搜索补充，使用很浅。 |
| 3 | 提问者 | 会写基础 Prompt，能得到像样回答。 | 开始理解「输入决定输出」，但还不稳定。 |
| 4 | 使用者 | 会把 AI 用在写作、总结、表格、邮件等任务里。 | AI 开始替代零散体力活，效率明显提升。 |
| 5 | 协作者 | 会多轮追问、纠错、补充上下文，让 AI 越做越准。 | 不再是一问一答，而是把 AI 当协作对象。 |
| 6 | 工作流玩家 | 把 AI 接进固定流程：调研 → 分析 → 输出 → 复盘。 | 能力从「单点使用」升级成「流程提效」。 |
| 7 | 系统搭建者 | 会组合多工具、多模型、模板、知识库或自动化。 | AI 不只是工具，而是被你做成了系统。 |
| 8 | 业务重构者 | 用 AI 重做服务、营销、交付、管理方式。 | 你开始改变业务结构，而不只是提升个人效率。 |
| 9 | 杠杆放大者 | 1 个人能做过去一个小团队的产出，还能持续复用。 | AI 开始产生复利，速度、质量、规模一起放大。 |
| 10 | AI 原生指挥官 | 把 AI 当「第二大脑 + 操作系统」，持续设计人机协作。 | 核心已经不是「会用工具」，而是「会定义问题、搭系统、拿结果」。 |

### 1.2 三条成长规则（原图「你的成长路线图」）

- 每升一级，视野更高，影响更大。
- 从使用 AI，到驾驭 AI。
- 最终：用 AI 创造持续价值。

### 1.3 顶部结论与底部判据

- 顶部：**差距不在会不会问，而在能不能把 AI 变成结果。**
- 底部（原图下边缘被裁切，仅存一行）：**Level 越高，不是 Prompt 越花，而是：只更会定义任务 / 更会校验结果 / 更会沉淀流程 / 更会放大价值。** ［截断］

> 落地提示（本仓库补充）：L1–L4 是「会用」，L5–L6 是「用顺」，L7–L8 是「用成系统」，L9–L10 是「用出组织杠杆」。第二章的 FDE 岗位，对应的正是 L6–L8 之间的能力带。

### 1.4 个人日常作业流：AI 高手的一天（8 步环形）

> 来源：`roadmap/image/AI流程FDE/20261030-223639.png`

标题副句：「从想法到结果的完整工作流」。四项目标：更清晰的思考（把复杂问题简单化）、更高效的执行（用 AI 提升生产力）、更优质的输出（创造更大价值）、持续的成长（不断迭代与进化）。

八步构成闭环，中心是「思考增强 × 效率提升，创造更大价值」，箭头单向成环：

| 步 | 环节 | 动作要点 |
|---|---|---|
| 1 | 定义问题 | 明确目标，拆解问题，找准核心需求 |
| 2 | 信息收集 | AI 搜索、查资料，获取全面信息 |
| 3 | 分析理解 | 总结要点，提炼逻辑，建立结构化认知 |
| 4 | 生成内容 | AI 生成初稿、方案、代码、文案、图表等 |
| 5 | 验证与优化 | 检查事实、逻辑与质量，优化改进内容 |
| 6 | 执行落地 | 将结果应用到具体工作或项目中 |
| 7 | 自动化 / 提效 | 使用 AI 与自动化工具，批量处理、节省时间 |
| 8 | 复盘与沉淀 | 总结经验，沉淀模板，形成知识资产 |

图底原话：**这是一个持续迭代的闭环，每一次循环都让你更专业，更高效。**

#### 输入：你的起点（左侧栏）

- 问题 / 目标：明确你想解决的问题。
- 背景知识：相关资料与已有信息。
- 数据 / 资料：文档、表格、图片等。
- 灵感 / 想法：闪现的点子与思考。

#### 写出好问题（Prompt）五要素

- 明确具体：清晰描述目标与需求。
- 提供背景：给出必要的上下文信息。
- 设定约束：说明条件、范围与限制。
- 期望输出：指定格式、长度与风格。
- 迭代优化：根据结果持续调整提问。

公式：**角色 + 任务 + 背景 + 约束 + 输出格式 + 示例**。横幅原话：好问题 = 好答案。

#### 高质量 Prompt 框架（示例）

| 要素 | 示例 |
|---|---|
| 角色（Role） | 你是一位资深产品经理 |
| 任务（Task） | 请帮我分析这款产品的核心用户需求 |
| 背景（Context） | 这是一款面向大学生的学生 App |
| 约束（Constraints） | 分析维度：用户画像、核心需求、痛点、解决方案 |
| 输出格式（Format） | 请用表格输出，并给出结论与建议 |
| 示例（Example） | 参考格式：\| 维度 \| 描述 \| 结论 \| 建议 \| |

结论句：**越清晰的 Prompt，越高质量的输出。**

#### 常用 AI 工具箱（右侧栏）

ChatGPT / GPT-4o（对话、创作、分析、编程）、Claude（长文本、深度分析、写作）、Perplexity（AI 搜索、信息整合）、Notion AI（笔记、知识管理、写作）、Cursor / Copilot（AI 编程、代码生成）、DALL·E / Midjourney（AI 绘图、创意视觉）、Whisper / TTS（语音转文字 / 文字转语音）、Zapier / Make（自动化工作流）。

#### 自动化的力量

- 信息自动收集：定时抓取新闻、数据。
- 内容自动生成：报告、文案、摘要。
- 流程自动执行：发送、归档、提醒等。
- 结果自动同步：多平台整合与通知。

原话：**把重复的工作交给 AI 和自动化，你专注于创造！**

#### 适用场景

学习研究（资料总结、文献分析、概念理解、考试辅导）、工作提效（报告撰写、数据分析、会议纪要）、编程开发（代码生成、调试优化、文档编写、技术问答）、内容创作（文章写作、文案创意、脚本创作、翻译润色）、设计创意（灵感发散、图片生成、PPT 设计、视觉优化）、生活助手（旅行规划、健康建议、理财分析、日常决策）。

#### 使用 AI 的最佳实践

明确目标，带着问题使用 AI；提供充足上下文，减少误解；分步骤提问，逐步深入；验证重要信息，避免 AI 幻觉；结合自己的思考与判断；保护隐私，不输入敏感信息；尊重版权与道德，合理使用；持续学习，掌握 AI 新能力。

#### 黄金法则（六条）

| 法则 | 释义 |
|---|---|
| 以人为本 | AI 增强能力，而不是替代思考 |
| 批判思维 | 不盲从 AI 答案，保持独立判断 |
| 隐私安全 | 保护数据安全，不泄露敏感信息 |
| 持续迭代 | 不断优化提问，持续提升效果 |
| 学以致用 | 将 AI 输出用于真正的价值创造 |
| 长期主义 | 把 AI 能力变成可复用的系统 |

页脚记忆点：**工具决定效率，思维决定高度，习惯决定未来。** 「AI 是副驾驶，方向盘在你手中。」

## 第二章 FDE：角色与方法论

> 来源：`roadmap/image/AI流程FDE/20261030-223633.png`（岗位底层逻辑）、`20261030-223627.jpg`（进入企业技术过程）

### 2.1 岗位定义

**把客户现场的真实问题，转化为可运行、可验证、可复用的系统。**

定义公式：

> 现场理解 × 工程实现 × 业务闭环 × 产品沉淀

四个因子是乘号，不是加号 —— 任何一项为零，整条链路归零。

### 2.2 五步工作流（含交付证据）

| 步 | 动作 | 关键动作 | 交付证据 |
|---|---|---|---|
| 01 | 进入现场 | 观察真实用户、流程与目标 | 场景图 |
| 02 | 拆清约束 | 厘清数据、权限、成本与卡点 | 约束清单 |
| 03 | 原型验证 | 用最短路径验证关键假设 | 可试用原型 |
| 04 | 系统接入 | 接入业务流程，验证真实使用 | 上线工作流 |
| 05 | 结果复盘 | 评估效果，把反馈变成产品能力 | 指标与产品建议 |

闭环：05 之后有一条**「反馈进入下一轮」**的回流箭头指回 01，形成螺旋，而不是一次性交付。

### 2.3 能力、适用场景与验收

**岗位需要的能力**

- 业务理解与问题拆解
- 快速开发与系统集成
- 跨团队协作与结果复盘

**哪些场景需要 FDE**

- 需求仍有较高不确定性
- 数据、权限与系统需整合
- 现场反馈能持续改进产品

**如何判断闭环成立**（三条同时成立才算）

- 真实用户在用
- 业务指标可验证
- 经验能复用

**交付标准**

> 可用工作流 + 使用证据 + 业务结果 + 产品洞察

### 2.4 FDE 进入企业技术过程（8 阶段工程闭环）

副标题：**从环境接入到持续迭代，构建企业 AI 能力的工程闭环。** 左侧是 Visio 逻辑流程图，右侧是各阶段的关键活动与技术要点。

阶段之间存在三个判断点：阶段 2 的「是否确定首个场景」（否 → 回到业务梳理）、阶段 6 的「效果是否达标」（否 → 回到真实环境试运行）、阶段 8 的「是否有新场景」（是 → 新场景 / 否 → 结束）。

#### 阶段 1 · 企业技术环境接入

流程：`开始` → 对接企业 CIO / IT / 业务负责人 → 梳理企业 IT 架构与现状 → 确认网络、权限、安全与部署环境。

关键活动与技术要点：

- 网络拓扑（内网 / DMZ / VPN）
- 身份认证（AD / LDAP / SSO）
- 现有系统（ERP / MES / CRM / PLM / OA 等）
- 服务器与容器环境（VM / K8s）
- 安全与合规要求

#### 阶段 2 · 业务与技术诊断

流程：梳理业务流程与痛点 → 分析数据、系统、人工流程 → 评估技术可行性与 ROI → **是否确定首个场景？**（否 → 回到流程梳理；是 → 进入阶段 3）。

关键活动与技术要点：

- 业务流程梳理
- 痛点与机会识别
- 数据与系统现状分析
- 选择高价值 AI 应用场景

#### 阶段 3 · 数据与知识接入

流程：连接企业数据源（DB / API / 文件）→ 数据清洗与标准化 → 构建企业知识库与数据中台 → 建立业务对象与数据映射（企业本体 Ontology）。

关键活动与技术要点：

- 数据库连接（MySQL / Oracle 等）
- API / MCP / 文件接入
- 数据清洗与标准化
- 字段语义与业务映射
- 企业知识库 / 向量库
- 构建业务对象与关系（Ontology）

#### 阶段 4 · AI 技术架构搭建

流程：选择大模型与部署方案 → 搭建模型服务层（Model Service）→ 构建 RAG 与知识服务 → 设计 Agent 架构与工具体系（Tools / MCP）。

关键活动与技术要点：

- 模型选型与路由（云 / 本地 / 混合）
- Embedding / Rerank / Model Routing
- RAG 与知识检索
- Agent 架构设计（Planner / Reasoning）
- Tool 集成（MCP / API / SDK）

#### 阶段 5 · 业务场景开发

流程：设计业务流程与解决方案 → 开发 Agent / Copilot 与工作流 → 对接企业系统（ERP / MES / CRM 等）→ 完成功能开发与内部测试。

关键活动与技术要点：

- 基于真实业务流程开发
- Agent / Workflow 实现
- 系统集成（API / MCP / RPA）
- 功能开发与单元测试
- 业务规则与权限控制

#### 阶段 6 · 现场验证

流程：在真实环境中试运行（真实数据 / 真实用户）→ 收集使用反馈与业务数据 → **效果是否达标？**（否 → 优化调整后再试；是 → 进入阶段 7）。

关键活动与技术要点：

- 真实业务场景验证
- 准确率 / 响应速度 / 使用率
- 业务效果评估（效率 / 成本 / ROI）
- 问题收集与优化调整

#### 阶段 7 · 生产环境上线

流程：部署到生产环境（灰度发布）→ 配置权限与安全策略 → 建立监控与告警（日志 / 审计）→ 正式上线与用户推广。

关键活动与技术要点：

- 灰度发布与全量上线
- 权限控制与数据安全
- 模型监控与日志审计
- 稳定性保障与应急预案
- 用户培训与推广

#### 阶段 8 · 持续迭代与优化

流程：持续收集使用数据与业务反馈 → 分析问题与优化点 → 迭代优化（模型 / Agent / 场景）→ **是否有新场景？**（是 → 新场景；否 → 结束）。

关键活动与技术要点：

- 使用数据分析与效果评估
- 模型与流程持续优化
- 扩展应用场景
- 建立长期运营与支持机制
- 推动企业 AI 能力不断进化

> 落地提示（本仓库补充）：这 8 个阶段与第三章的「企业五阶段」是同一件事的两种切法 —— 8 阶段是**单个项目的交付视角**，五阶段是**企业整体建设的视角**。阶段 1–2 对应五阶段的一、二，阶段 3–5 对应三，阶段 6–8 横跨四、五。

## 第三章 企业：五阶段、研发主流程与 Agent 平台架构

### 3.1 大中型企业 AI 落地五大阶段

> 来源：`roadmap/image/AI流程FDE/20261030-223621.jpg`

副标题：**从战略规划到企业级智能化运营，分阶段投入，逐步构建企业 AI 能力体系。**

| 阶段 | 名称 | 目标标语 | 核心投入（三组） |
|---|---|---|---|
| 01 | AI 战略规划与顶层设计 | 明确方向，规划路径，让 AI 建设更可落地 | ① **AI 建设规划**：应用场景分析、业务需求梳理 ② **技术架构规划**：模型与数据规划、系统连接规划 ③ **项目实施规划**：试点场景选择、落地路线设计 |
| 02 | AI 基础能力建设 | 搭建企业 AI 底座，让 AI 理解企业 | ① **AI 智能体开发平台**：智能体搭建、工作流编排 ② **企业知识库**：知识沉淀管理、智能检索问答 ③ **AI 安全体系**：权限管理、私有化部署 |
| 03 | AI 业务场景落地 | 让 AI 进入具体岗位，提升业务效率 | ① **部门 AI 助手**：销售 / 客服 / 财务 / 采购 / 人事 / 运营助手 ② **核心业务应用**：智能审批、智能填单、智能报告、合同审核、智能问数、企业知识问答 ③ **流程自动化**：AI 执行任务、自动流转业务 |

### 3.3 企业级 Agent 平台架构（五层）

> 来源：`roadmap/image/AI系统平台/20261030-223730.png`，副标题「多模型 · 多工具 · 安全隔离 · 可扩展 · 企业级落地」

#### 分层结构

| 层 | 组成 |
|---|---|
| **用户层** | Web / H5、移动端、企业应用、API 接入 |
| **应用层（Agent Core）** | 上为 **Agent Core**：意图理解、任务规划、工具调用、结果生成、记忆管理；右上为 **Memory / State**：会话记忆、长期记忆、向量记忆。下为双网关 —— **模型网关（Model Gateway）**：多模型接入（OpenAI / Claude / 通义等）、模型路由 / 限流 / 计费 / 灰度、Fallback / 重试 / 负载均衡、模型日志 / 审计；**工具网关（Tool Gateway）**：工具注册 / 管理 / 鉴权、参数校验 / 限流 / 熔断、Pre Hook / Post Hook、调用日志 / 审计 / 脱敏 |
| **工具层（Tools）** | 内部工具（企业内部 API、业务系统、数据库查询、内部服务）、MCP 工具（MCP Server A / B / …）、Skill / 工作流（已封装技能、Prompt 模板、工作流编排、行业场景包）、外部工具（第三方 SaaS、外部 API、插件工具、Webhook）、Sandbox 工具（代码执行、文件处理、命令行执行、浏览器操作） |
| **执行层（Runtime）** | **Serverless Runtime（无状态执行）**：函数计算 FC / Serverless、短任务 / 工具调用 / API 执行、弹性伸缩 / 按需付费；**Sandbox Runtime（有状态隔离环境）**：容器化隔离环境（Docker / K8s）、代码运行 / 文件读写 / 长任务、资源限制 / 网络隔离 / 日志采集 |
| **存储层（Storage）** | 对象存储 OSS / S3 / Agentic Bucket（文件 / 日志 / 中间产物）、文件存储 NAS / 分布式文件系统（大文件 / 挂载 / 共享）、数据库 PostgreSQL / MongoDB（会话 / 业务数据）、向量数据库 Milvus / Pinecone（向量检索 / 知识库）、缓存 Redis / Memcached（会话缓存 / 限流 / 缓存） |

#### 架构设计思路

通过**分层解耦 + 网关统一 + 运行时隔离**的设计，构建一个安全、可扩展、易维护的企业级 Agent 平台，支持多模型、多工具、多场景的智能化应用落地。

- Agent Core：负责推理、规划、记忆、结果生成
- 双网关设计：模型网关 + 工具网关，统一管理与治理
- 多工具生态：支持内部工具、MCP、Skill、外部工具、Sandbox
- 双运行时：Serverless 处理无状态任务，Sandbox 处理有状态任务
- 多存储策略：对象存储 + 文件存储 + 数据库 + 向量库 + 缓存

#### 核心优势

- 安全隔离：Sandbox 环境隔离，保障系统安全
- 灵活扩展：模块化设计，支持快速接入新能力
- 高可用性：网关治理 + 负载均衡 + 容灾设计
- 成本可控：Serverless 按需付费，资源弹性伸缩
- 企业级能力：权限控制 / 审计日志 / 数据脱敏

#### 适用场景

企业智能助理、代码生成与执行、数据分析与报表、文档处理与知识库、自动化运维、行业解决方案。

图末原话：**架构是骨架，数据是血液，场景是灵魂。**

### 3.5 企业 Agent 员工系统架构

> 来源：`roadmap/image/AI系统平台/20261030-223753.png`，副标题「从业务目标到可验收结果的协作闭环」

定义：**Agent 员工 = 在明确职责与授权范围内，调用知识和工具完成任务的软件执行单元。**［原图该句末尾有重复字，按语义读作「完成任务」］

#### 左栏：运行基础

身份与角色（管理成员身份与角色权限）、任务识别（任务的排队与调度管理）、状态存储（记录任务状态与中间结果）、文件与版本（管理文件与版本历史）。

#### 主干五段

| 段 | 名称 | 组成 |
|---|---|---|
| 1 | **业务与人类负责人** | 业务目标（明确要达成的业务结果）、任务入口（员工提交 / 定时任务 / 业务事件）、验收标准（定义可量化的验收条件）、人类负责人（设定目标 · 审批关键动作 · 验收结果） |
| 2 | **任务编排与运行控制**（协调与调度中心） | 任务拆解 → 角色分析 → 依赖调度 → 状态调度；三个兜底：超时重试、异常转人工、预算控制。另有一条「不通过 → 退工裁转人工」的红色回流 |
| 3 | **专业 Agent 员工**（按需启用单个角色或多个角色协作） | 研究 Agent（检索与分析）、内容 Agent（撰写与排版）、运营 Agent（线索与跟进）、运营 Agent（执行与复盘）［原图三、四号框同名，疑后者应为「投放 / 复盘 Agent」，原文如此］。每个框下统一标注「职责 · 工具 · 交付物」，相邻 Agent 之间的双向箭头注明「调用 / 返回」，内容 Agent 与运营 Agent 之间另有「结构化文档」传递 |
| 4 | **共享能力与企业连接** | 模型服务（推理与生成）、知识与记忆（企业知识库、经审核的经验；标注「检索遵循访问权限」）、工具与接口（CRM · 邮件 · 文档 · 业务系统；标注「经授权获得真实操作」） |
| 5 | **交付与验收** | 结果产物（文档 / 报告等）→ 规则校验（检查完整性与合规性）→ 业务校验（是否达成业务目标）→ 通过则交付，不通过则退回人工；末端为知情记录（保留结果与过程） |

#### 右栏：治理与可观测

最小权限（按需授权，降低风险）、关键操作审批（重要操作必经审批）、日志与审计（记录所有关键活动，支持审计）、质量与成本评估（评估任务效果与资源消耗）。

#### 一项真实任务如何流动（图内实例）

1. **任务提交**：明确活动主题、受众与预期效果。
2. **研究 Agent**：整理资料、专家信息、竞品要点。
3. **内容 Agent**：生成图文 / 撰写文案、设计海报。
4. **人工审核**：检查内容是否合规、准确。
5. **运营 Agent**：写入公众号草稿箱、按模式与人群做投放。
6. **发布后**：经授权获取数据并复盘（发送效果、数据回收）→ 优化任务模板与工作流 → 反哺用于任务前设计，经验沉淀后入库。

#### 一个 Agent 员工内部有什么

`角色指令 + 模型 + 授权工具 + 任务状态`

运行循环：**理解 → 行动 → 检查 → 继续或停止**（达到验收条件、预算上限或异常边界时停止）。

#### 读懂这张图的三个关键

- **角色层 · 谁负责什么**：明确每个 Agent 的职责、工具与交付物。
- **编排层 · 任务如何协作**：通过任务拆解、角色分配和依赖调度，完成任务的闭环。
- **治理层 · 动作是否可控**：依靠权限、审计、回滚与预算，确保安全可控。

底部结论：**企业 Agent 系统的价值：让任务有负责人、执行有边界、结果可验收。**

| LLM 基础加速 | Tokenizer（HF Rust）；KV Cache；量化算子 |
| 高并发基础服务 | Axum / Actix 高并发网关；gRPC 服务；零拷贝传输 |
| 分布式协调 | Raft 共识 / 分布式锁；任务分片调度；数据一致性校验；心跳 / 故障检测 |

**部署方式**（三选一）：① PyO3 → Python 扩展包；② gRPC / REST → 独立常驻服务；③ JNI → Java 调用。

#### 基础设施层（IaaS / PaaS）

**运维底座**：CI/CD（Jenkins / GitLab）· 镜像仓库 · 监控告警 · 链路追踪 · 日志平台。

## 第四章 数据底座：中台关系与 15 个核心概念

### 4.1 数据中台、AI 中台与 AI 智能体

> 来源：`roadmap/image/数据AI/20261030-223722.png`

副标题：**三者协同，构建从数据到智能到业务价值的完整闭环。**

顶部一句链：**数据中台**（提供高质量数据基础）→ **AI 中台**（提供智能能力与工具）→ **AI 智能体**（面向业务场景创造价值）。

#### 三层结构（自下而上）

| 层 | 定位 | 组成 | 核心能力 / 价值 |
|---|---|---|---|
| **数据中台层**（Data Platform）· 数据基础层 | 提供高质量、可信赖、标准化的数据基础 | 数据采集（多源采集、实时 / 离线）、数据存储（数据湖 / 数仓、高可用存储）、数据治理（数据标准、质量管理）、数据开发（ETL 开发、任务调度）、数据服务（API 服务、数据接口）、数据安全（权限控制、脱敏审计） | 核心能力：高质量、一致性、安全合规、可追溯、可共享。核心价值：统一数据资产、保障数据质量、降低数据成本、支撑业务决策 |
| **AI 中台层**（AI Platform）· 能力中台层 | 将 AI 能力产品化、组件化、服务化 | 模型管理（模型接入、管理版本、评测）、训练平台（数据标注、训练微调、评估）、推理服务（高性能推理、弹性扩缩容）、能力组件（NLP、CV、预测推荐等组件）、AI 工具库（通用工具集、可复用工具）、评估监控（效果评估、监控告警、追踪） | 核心能力：标准化、可复用、可拔插、可扩展、可运营。关键作用：降低 AI 门槛、提升复用性、加速创新、保障效果一致性 |
| **AI 智能体层**（AI Agents）· 业务应用层 | 面向具体业务场景，自主感知、决策、执行 | 智能客服、营销助手、数据分析师、研发助手、知识助手、更多场景… | 智能体具备：记忆、规划、工具使用、反思与学习等能力。创造价值：提升效率、优化体验、驱动增长、创新业务模式 |

中间两条向上箭头：数据中台「提供高质量数据支撑」→ AI 中台；AI 中台「提供能力与工具支撑」→ AI 智能体。

#### 协同关系（右下）

1. 数据中台是**基础** → 提供燃料（数据）
2. AI 中台是**引擎** → 提供能力（算法与工具）
3. AI 智能体是**应用** → 输出价值（解决业务问题）

#### 价值传递链路

`数据资产 → 智能能力 → 业务应用 → 业务价值`

环形注解：**数据驱动智能，智能创造价值，价值反哺数据。**

#### 总结

- 数据中台解决「数据从哪里来、是否可信」；
- AI 中台解决「智能能力如何高效构建与复用」；
- AI 智能体解决「如何在实际业务中用好的智能、创造价值」。

### 4.2 数据开发必懂的 15 个核心概念

> 来源：`roadmap/image/数据AI/20261030-223713.png`（8 页拼图，右上角标注 01/08–08/08）

导读原话：**搞懂这 15 个概念，基本能看懂 90% 的数据开发工作。** 底部提醒：**不是记住概念，而是理解它们在实际工作中的关系和价值。**

十五个概念总览（图首的编号网格）：

| 编号 | 概念 | 编号 | 概念 | 编号 | 概念 |
|---|---|---|---|---|---|
| 01 | ETL | 06 | 数据集市 | 11 | 数据质量 |
| 02 | ELT | 07 | 数据建模 | 12 | 数据治理 |
| 03 | 数据源 | 08 | 调度 | 13 | 数据标准 |
| 04 | 数据仓库 | 09 | 数据血缘 | 14 | 数据安全 |
| 05 | 数据湖 | 10 | 元数据 | 15 | 数据服务 |

#### 01 ETL：传统的数据处理范式

定义：ETL（Extract-Transform-Load）。

流程：`抽取 Extract`（从业务系统抽取数据）→ `转换 Transform`（清洗、加工、转换，成统一的数据格式）→ `加载 Load`（写入数据仓库或目标系统）。

特点：数据在目标端之前完成转换；适合结构化数据和传统数仓；对源系统压力较小。

典型工具：Informatica、DataStage、Kettle（开源）、Talend、国产工具（如 DataX）。

结论：**ETL 是数据开发的经典范式，至今仍广泛应用于企业数仓建设。**

#### 02 ELT：面向大数据时代的新范式

定义：ELT（Extract-Load-Transform）。

流程：`抽取 Extract`（从多源抽取数据）→ `加载 Load`（直接写入目标存储，如数据湖 / 数仓）→ `转换 Transform`（在目标端进行大规模计算与转换）。

特点：充分利用目标端的计算能力；适合海量数据和云数据平台；加载速度快，灵活性高。

典型场景：云数仓（如 Snowflake、BigQuery）、大数据平台（如 Hive、Spark）、数据湖（如 Hudi、Iceberg）。

结论：**ELT 更适合大数据和云原生时代，是当前的主流趋势。**

ETL 与 ELT 对照：

| 维度 | ETL | ELT |
|---|---|---|
| 转换位置 | 加载前，在独立转换引擎里 | 加载后，在目标存储里 |
| 典型承载 | 传统数仓、结构化数据 | 云数仓、数据湖、大数据平台 |
| 优势 | 对源系统压力小，结果先净化后入库 | 复用目标端算力，加载快、灵活性高 |
| 代表工具 / 平台 | Informatica、DataStage、Kettle、Talend、DataX | Snowflake、BigQuery、Hive、Spark、Hudi、Iceberg |

#### 03 数据源：数据的起点

定义：数据源 = 数据产生的地方，是数据开发的起点。

常见数据源类型：业务数据库（如 MySQL、Oracle）、业务系统（如 ERP、CRM、OA）、文件数据（如 Excel、CSV、日志）、第三方接口（如 API、SDK）、实时数据（如 Kafka、MQ）、其他（如传感器、IoT 设备）。

关注点：数据的可用性与稳定性、数据的更新频率、数据的结构与质量、数据的接入方式（全量 / 增量）、对源系统的影响（性能、安全）。

结论：**数据源决定了数据的边界，理解数据源是数据开发的第一步。**

#### 04 数据仓库 vs 05 数据湖

| 维度 | 数据仓库（Data Warehouse） | 数据湖（Data Lake） |
|---|---|---|
| 数据形态 | 面向结构化数据 | 支持多种类型数据（结构化 / 半结构化 / 非结构化） |
| Schema | Schema 预定义 | Schema 灵活（读时定义） |
| 适用 | 适合分析和报表 | 适合海量原始数据存储 |
| 特性 | 数据质量高，稳定性强 | 成本低，扩展性强 |
| 典型产品 | Hive、ClickHouse、Snowflake、Redshift | HDFS、MinIO、S3、Delta Lake、Iceberg |

一句话：**数据仓库是「精装房」，数据湖是「毛坯房」。**

#### 06 数据集市 vs 07 数据建模

| 维度 | 数据集市（Data Mart） | 数据建模（Data Modeling） |
|---|---|---|
| 定位 | 面向特定业务领域的数据仓库 | 数据组织的核心方法 |
| 要点 | 面向特定业务领域（如财务、销售、营销）；数据范围小，主题明确；建设周期短，使用灵活；常从企业级数仓中抽取；支持自助分析和报表 | 对业务进行抽象，设计数据结构；常见模型：星型、雪花、Data Vault；明确数据的粒度、维度与指标；提高数据的一致性和可维护性；是数仓建设的核心环节 |

一句话：**没有好的数据建模，就没有高质量的数据仓库。**

#### 08 调度、09 数据血缘、10 元数据：数据开发的「管理三剑客」

| 概念 | 作用 | 要点 |
|---|---|---|
| **08 调度**（Task Scheduling） | 保障任务有序、数据可追溯、资产可管理 | 按时间或事件触发任务；支持依赖关系和重试机制；常见工具：Azkaban、Airflow、DolphinScheduler；保障数据任务稳定运行 |
| **09 数据血缘**（Data Lineage） | 记录数据的来龙去脉，支持影响分析和问题定位 | 记录数据的来龙去脉；支持影响分析和问题定位；分为表血缘、字段血缘；常见工具：Atlas、DataHub、Amundsen |
| **10 元数据**（Metadata） | 描述数据的数据，是数据治理的基础 | 描述数据的数据；包括表结构、字段、口径、来源、负责人等；支持数据资产管理和检索；是数据治理的基础 |

一句话：**调度管「时间」，血缘管「关系」，元数据管「身份」。**

#### 11–15：从「能用」到「好用」，再到「安全可持续」

原图导读：构建完整的数据体系，五个概念构成一条价值链。

| 概念 | 要点 |
|---|---|
| **11 数据质量** | 完整性、准确性、一致性、及时性、可用性 |
| **12 数据治理** | 组织机制、制度流程、数据资产、生命周期、考核与改进 |
| **13 数据标准** | 统一口径、命名规范、指标标准、编码规范、数据字典 |
| **14 数据安全** | 权限管理、数据脱敏、访问控制、安全审计、合规要求 |
| **15 数据服务** | 数据 API、数据中台、数据产品、自助分析、对外数据服务 |

页脚结论（原图有文字压印，语义清晰）：**数据开发的终点不是写完任务，而是让数据持续产生业务价值。**

```
数据源(03)

```
