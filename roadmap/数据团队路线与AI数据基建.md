# 数据团队路线与 AI 数据基建：从“人消费数据”到“Agent 理解业务”

> 一句话：过去十多年，数据基建解决的是“人怎么看数”；AI 时代要解决的是“Agent 怎么理解业务”。

## 1. 过去十多年，数据团队的主线

数据团队的主线并不神秘，大致可以分成三段。

### 1.1 离线数仓：让企业有统一的经营数据

第一段是离线数仓。

把业务系统里的数据抽出来，做清洗、建模、分层、汇总：

```text
业务库 → ODS → DWD → DWS → ADS → 报表/取数
```

这段解决的是“企业有没有统一的经营数据”：

- 口径统一，不再各查各的；
- 分层建模，明细和汇总各归其位；
- 报表、取数、经营分析有稳定的数据底座。

### 1.2 实时数仓：让业务更快看到变化

第二段是实时数仓。

用户行为、交易事件、风控事件、运营事件通过 CDC、消息队列、流计算更快进入数仓：

```text
业务事件 → CDC/Kafka → Flink → 实时明细/实时指标 → 看板/告警
```

这段解决的是“业务能不能在分钟级甚至秒级看到变化”：

- 实时大盘、实时告警；
- 活动效果、风控拦截、运营动作更快反馈；
- 离线与实时开始共用一套口径。

### 1.3 平台化补齐：从数仓到数据平台

第三段是平台化。

湖仓一体、统一指标平台、OLAP 引擎、数据服务、标签体系、数据治理、数据目录、血缘、质量监控逐步补齐。

这段解决的是“数据能不能被加工、被查询、被复用、被展示”：

- 湖仓做统一存储与开放计算；
- 指标平台做口径复用；
- OLAP 做交互式分析；
- 数据服务把数据变成 API；
- 标签体系做用户/对象画像；
- 治理、目录、血缘、质量让数据“可用且可控”。

### 1.4 这三段的共同点

| 阶段 | 核心问题 | 主要产出 | 主要使用者 |
|---|---|---|---|
| 离线数仓 | 有没有统一经营数据 | 分层模型、报表、指标 | 人 |
| 实时数仓 | 能不能更快看到变化 | 实时明细、实时指标、告警 | 人 |
| 平台化 | 能不能复用、服务化、治理 | 湖仓、指标、OLAP、API、目录、血缘 | 人 |

共同点是：**数据基建的表达对象，主要是“表、字段、指标、维度、报表”**。

它服务的是人：

- 人通过报表看数；
- 人通过取数分析问题；
- 人通过 BI 做下钻；
- 人通过 SQL 查明细；
- 人通过数仓模型复用口径。

这套体系非常成功，但它有一个隐含前提：**最后理解业务、做判断的是人，不是机器。**

## 2. AI 带来的变化：使用者从“人”变成“Agent”

AI 进入企业经营管理以后，数据基建多了一个新的使用者：Agent。

Agent 不只是在查一张表，也不只是在生成一段 SQL。它要：

- 理解业务问题；
- 识别对象和事件；
- 判断指标变化的含义；
- 沿着业务关系做归因；
- 知道哪些数据能看；
- 知道哪些动作可以建议；
- 知道哪些结论必须附带证据。

| 人消费数据 | Agent 消费数据 |
|---|---|
| 看报表 | 理解业务问题 |
| 取数分析 | 识别对象和事件 |
| BI 下钻 | 沿业务关系归因 |
| SQL 查明细 | 判断指标含义、权限、证据、动作 |
| 人做最终判断 | Agent 给建议，人审批 |

这意味着：**Text-to-SQL 不是 AI 数据基建的全部。**

Text-to-SQL 能解决“这句话对应哪张表、怎么写 SQL”，但它解决不了：

- 这个业务词到底指哪个对象？
- 这两个对象之间应该怎么 Join？
- 这个指标的口径是什么，和另一个指标是不是同名不同义？
- 这个异常应该沿哪条业务关系拆解？
- 这个结论来自哪个快照、哪条规则、哪份文档？
- 当前用户/Agent 有没有权限看这些数据、能不能建议这个动作？

所以，AI 对数据部门的冲击，表层发生在岗位，深层发生在**数据基建的表达能力**上。

## 3. 尴尬：数仓很完整，但业务世界没有被建模

很多企业会走到这样一个状态：

- 数仓很完整；
- 指标很多；
- 目录、血缘、治理也都有；
- 但企业业务世界并没有被建模成 AI 能理解、能验证、能治理的形式。

问题不在于“数据不够”，而在于“表达不够”。

| 层 | 回答什么 | 典型产物 |
|---|---|---|
| 物理模型 | 有哪些表、字段 | 表结构、分区 |
| 维度模型 | 事实、维表怎么分 | ODS/DWD/DWS/ADS |
| 指标语义 | 指标怎么算、怎么查 | `metric_def`、MQL |
| 数据目录 | 数据在哪、谁负责 | 表/字段元数据、血缘 |
| 治理 | 谁能看、质量如何 | 权限、质量规则、审计 |
| **业务本体** | **业务对象、关系、规则、术语是什么** | **实体/关系/规则/术语模型** |

前五层解决的是“数据怎么加工、怎么查、怎么管”。

业务本体解决的是“业务世界是什么”。

如果缺少这一层，Agent 看到的仍然是一堆表，而不是一个可理解的业务世界。

## 4. AI 数据基建的两条大线

未来企业 AI 数据基建，大概会有两条大线。

```text
                         ┌──────────────────────────────┐
                         │            Agent             │
                         │  理解问题 / 归因 / 建议 / 证据  │
                         └──────────────┬───────────────┘
                                        │
              ┌─────────────────────────┴─────────────────────────┐
              │                                                   │
    ┌─────────▼─────────┐                               ┌─────────▼─────────┐
    │ 结构化数据主线      │                               │ 非结构化/多模态主线 │
    │ 数仓/湖仓/OLAP      │                               │ 文档/图片/语音/视频 │
    │ + 本体化语义层      │                               │ + 企业知识引擎      │
    └───────────────────┘                               └───────────────────┘
```

### 4.1 第一条线：结构化数据 + 本体化语义层

企业的经营事实、交易事实、财务事实、用户事实、供应链事实，大量仍然落在数据库、数仓、湖仓和 OLAP 系统里。

这条线继续往前走，关键补位是**本体化语义层**。

它不只回答“指标怎么算”，还回答：

- 业务对象有哪些：客户、订单、商品、设备、合同、工单、区域、渠道；
- 对象之间什么关系：客户下单、订单包含商品、设备归属客户、工单关联设备；
- 业务规则是什么：一个订单只能属于一个客户；合同到期不能下单；
- 业务术语是什么：GMV、活跃设备、客户、门店；
- 实体/属性映射到哪张表、哪个字段；
- 指标映射到哪个 `metric_def`；
- 权限、版本、证据从哪里来。

可以把它理解成：

```text
物理表/字段
   ↓
维度模型（事实/维表/分层）
   ↓
指标语义（metric_def / MQL）
   ↓
业务本体（实体/关系/规则/术语/映射/权限/证据）
   ↓
Agent
```

**它不是替代数仓，也不是替代指标平台。** 它是在两者之上，补一层“业务世界模型”。

它也不一定是学术意义上的 OWL/RDF。更现实的起点是轻量本体：

- 实体/事件表；
- 关系表；
- 规则表；
- 术语/同义词表；
- 实体属性到物理表的映射；
- 指标到实体的绑定；
- 权限与证据字段。

### 4.2 第二条线：非结构化/多模态数据 + 企业知识引擎

企业文档、会议纪要、合同、图片、语音、视频、页面截图、流程记录，都会进入 AI 引擎。

这条线需要的不只是“文档切块 + 向量检索”，而是一套企业知识引擎：

- 文档理解：PDF、扫描件、表格、合同条款；
- 多模态检索：文本、图片、表格、语音、视频；
- 多模态推理：图文对齐、跨模态引用、时间线；
- 引用与证据：答案能回到原文/原图/原视频片段；
- 权限与审计：哪些文档谁能看、Agent 能引用到什么程度；
- 评测：召回、引用准确率、答案覆盖率、幻觉率。

这条线和结构化主线不是二选一，而是互补：

- 结构化线管“业务事实”；
- 非结构化线管“业务知识”；
- Agent 需要两者一起，才能既查得到数，又讲得清原因。

## 5. 一个例子：Agent 怎么用两条线

问题：

> 为什么华东区最近一周设备故障率上升？

Agent 的理想路径：

1. **识别对象/事件**：区域=华东；对象=设备；事件=故障；指标=故障率。
2. **走本体关系**：设备属于客户/区域；故障事件关联设备；工单关联故障。
3. **确认指标口径**：故障率 = 故障设备数 / 在线设备数；时间窗口=最近 7 天。
4. **查结构化数据**：按区域、设备型号、固件版本、客户分组，找异常贡献。
5. **查非结构化知识**：最近的维修记录、固件发布公告、客服工单、现场照片。
6. **做归因**：是某型号固件问题，还是某区域网络问题，还是数据口径变化。
7. **给证据**：SQL 结果、数据快照、文档引用、工单编号、权限校验。
8. **给建议**：建议排查/升级/回滚，高风险动作转人工审批。

没有本体，Agent 可能只能写 SQL；没有知识引擎，Agent 只能看到数，讲不清“为什么”。

## 6. 对数据团队和平台的启示

### 6.1 角色会变，但不会消失

数据团队不会因为 AI 消失，但工作重心会从“建表、取数、做报表”转向：

- 建业务对象/关系/规则模型；
- 建指标口径与语义映射；
- 建证据链、权限与治理；
- 建评测集与质量门禁；
- 建 Agent 可用的数据产品/API。

### 6.2 平台优先级

1. **先把指标语义层做扎实**：没有稳定口径，本体只是空壳。
2. **再做轻量业务本体 MVP**：10 个核心实体、20 条关系、50 个术语、10 条规则。
3. **再做 Agent 语义 API**：实体识别、指标解析、Join 路径、权限、证据。
4. **同步做非结构化 RAG/知识引擎**：引用、权限、评测先于规模。
5. **最后做跨模态实体链接**：文档中的设备/合同/工单，能连到结构化对象。

### 6.3 常见误区

- 把 ER 图当成本体：ER 图只描述数据结构，不描述业务规则和术语。
- 把 Text-to-SQL 当成 AI 数据基建：它只是查询生成，不是业务理解。
- 把知识图谱当成万能药：没有稳定指标和治理，图谱也会变成新的孤岛。
- 买了数据目录就以为有了本体：目录管元数据，不管业务对象/关系/规则。
- 只做文档 RAG，不做权限和证据：企业场景不可用。

## 7. 映射到当前 Mosaic 数据平台

| 能力 | 当前落点 | 与两条线的关系 |
|---|---|---|
| 指标语义 | 数据 D6：`metric_def` + MQL→SQL | 结构化线的底座 |
| 目录/血缘 | 数据 D7：DataHub + 字段级血缘 | 本体的元数据来源 |
| 治理 | 数据 D8：质量/权限/PII/成本 | 本体的权限与证据基础 |
| NL→MQL | 数据 D10：问数 | 结构化线的 Agent 入口 |
| 业务本体 | 数据 D6：`V6-5` 轻量本体（平台支持） | 第一条线的关键层 |
| RAG/知识 | AI D3：RAG + 知识引擎（`A3-5`–`A3-7`） | 第二条线的起点 |
| 多模态数据 | AI D2：多模态/文档加工（`A2-8`/`A2-9`） | 第二条线的数据底座 |
| 跨平台契约 | 工程域 README §9：`EntityRef`/`MetricRef`/`EvidenceRef`/`Policy` | 两条线共用同一套语义、权限、证据 |
| 训练数据/通路 | T2-B/T2-C | 两条线共用的数据工程能力 |

结论：

- **结构化线**：数据平台从“指标语义层”扩到“轻量业务本体 + 指标语义层”（D6 `V6-5`）。
- **非结构化线**：AI 平台从“文档 RAG”扩到“企业知识引擎”（D3 `A3-5`–`A3-7`）。
- 两条线通过 `EntityRef`/`MetricRef`/`EvidenceRef`/`Policy` 共用语义、权限、证据和评测，不是两个孤岛。

## 8. 结论

过去十多年，数据团队把“人怎么看数”这件事做到了极致：离线数仓、实时数仓、湖仓、指标、OLAP、服务、治理、目录、血缘、质量。

AI 时代，数据基建要再往前一步：

> **让 Agent 不仅查得到数，还能理解业务对象、关系、规则和指标，能沿业务关系归因，能给结论附证据，能在权限内建议动作。**

结构化侧的答案是**本体化语义层**；非结构化侧的答案是**企业知识引擎**。

两条线不是二选一，而是企业 AI 数据基建的两翼。
