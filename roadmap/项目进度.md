**运维纪律沉淀**（本轮踩坑的直接产物）：

- 服务一律用 `go build` 出的二进制起，**不要用 `go run`** —— 包装进程被杀会留下编译产物孤儿，占住消费组与端口（Q11 根因，已两次现场复现）。
- 告警能力边界如实记录：本机**无 Alertmanager**，告警只在 Prometheus UI/API 里，**需主动看**；接 Alertmanager 是第 2 阶段（清零清单⑥）。
- **改 provisioning 后必须确认容器 `healthy`，不能只看"容器起来了"**：本轮把 ClickHouse 数据源固定 uid（`ov-clickhouse`）后，Grafana 因"已 provision 的数据源不能改 uid"进入 crash loop（实测连崩 53 次、约 25 分钟无人察觉，因为当时只看了 `Up` 没看 health）。处置：provisioning 文件用 `deleteDatasources` 先按名字删旧记录再重建（幂等，已连测 3 次重启仍 healthy）。
- DLQ 告警**没有基线**：联调/演练期 DLQ 本就非空（发过畸形帧、跑过故障演练），判据是"无已知原因下持续增长"，不是"是否为 0"。

### 前两步缺陷审计整改（2026-09-18，第四轮）

> 起因：对第 1、2 步做整体评估时，对"已标 ✅"的结论逐条复验，发现 10 项实现层面缺陷。
> 修复明细见《接入层设计》§13 增补㉔；下表只记"改了什么、怎么验证的"。

| 类别 | 缺陷（修复前实测） | 处置 | 验证 |
|---|---|---|---|
| **P0 丢数据** | codec flush 写失败/提交失败后仍清空缓冲 → 下次成功 flush 提交更高位移，该批**永久静默丢失**（DLQ 与指标都不涨） | 改为"写出成功 == 提交成功才清空"，失败保留 + 有界退避重试；新增 `codec_flush_failures_total`/`codec_pending_messages` | 单测覆盖全部失败路径（`cmd/server` 0%→37%）；真实 Kafka 硬停实测：`pending_messages` 稳定保留 11 条、失败计数递增、恢复后补写且对账平衡 |
| **P0 假受理** | 网关 `Async:true` → 202/204 早于任何持久化，失败只计数；kafka-go 内部队列无上限（断连期 OOM） | 改**同步投递**（broker 确认后才 202/204）+ 有界重试 | `kafka_write_total{result=error}` 可达、handler 返回 5xx；单测断言"失败必须返回 error" |
| **P0 部署** | Kafka 数据落在容器可写层（`log.dirs=/tmp/kafka-logs`），挂载的卷是死配置 → `down`+`up` 丢全部 topic 与位移 | 显式 `KAFKA_LOG_DIRS=/var/lib/kafka/data` | `down`+`up` 与**引擎重启**后 topic/位移/标记消息全部存活 |
| **P1 安全** | 载荷 VIN 可覆盖 topic VIN（JSON 通道）、帧内 VIN 覆盖信封 VIN（codec）→ EMQX ACL 可被绕过，可伪造他人车辆数据 | 网关强制"载荷 VIN == topic VIN"，不一致 400 | 实测：越权请求由"204 且以他人 VIN 落 Kafka"变为 400 |
| **P1 安全** | 两条 webhook 通道**完全没挂限流**（文档却写"仅全局"）；webhook 密钥非常量时间比较 | 补全局令牌桶 `GlobalWrap` + `crypto/subtle` 比较 | 实测限流生效（20×429 / 34×204） |
| **P1 可用性** | `RATE_PER_DEVICE=0.5`（合法配置）→ 令牌桶容量 0 → x/time/rate 恒拒 → **全量 429** | `config.Load()` fail-fast + `burstFor()` 兜底 ≥1 | 单测覆盖小数速率与非法值 |
| **P1 部署** | 六个服务（当时）零 `restart:` 策略 → 引擎/宿主重启后容器不自愈（实测 Exited 137） | `restart: unless-stopped` + `mem_limit` + 日志轮转 | 引擎重启后无需人工干预即 6/6 healthy；第九轮加 MySQL/Redis 后为 8/8（两者同样带 restart 与 mem_limit） |
| **P1 安全** | 六个服务全部 `0.0.0.0` 发布，含弱口令组件（EMQX Dashboard/Grafana） | 宿主端口统一改绑 `127.0.0.1`（第九轮新增的 MySQL/Redis 一并遵守） | 容器间通信与文档命令不受影响 |
| **P1 安全** | EMQX 节点名随容器 IP 变化（镜像 entrypoint 覆盖 `node.name`）→ 换 IP 即换空 mnesia → 一车一密静默失效 | 固定 `EMQX_NODE__NAME=emqx@127.0.0.1` | 容器重建后凭证存活（201 条）；`security-check` **六项全过** |

### 前两步复评整改（2026-09-18，第九轮）

> 起因：对"已标 ✅"的第 1、2 步再做一次独立复评（不采信看板结论，逐条回源码核对）。
> **最重要的一条**：第四轮标为"已修"的 VIN 越权，实际上只修了 JSON 通道——二进制通道的同类缺陷仍在。
> 修复明细见《接入层设计》§13 增补㉙。

| 类别 | 复评发现（修复前实测） | 处置 | 验证 |
|---|---|---|---|
| **P1 安全（第四轮漏修）** | 二进制通道**帧内 VIN 可覆盖信封(topic) VIN**：网关按纪律不解帧故无法校验，而 codec 的 `process()` 直接采信帧内 VIN（`decode.go` 的 `VIN: f.VIN`）且从不与 `env.VIN` 比较 → 持合法凭证的设备可把帧内 VIN 填成他人车辆，**以他人身份写入平台数据**（EMQX ACL 被绕过）。原 `vin_mismatch` 指标只在网关侧产出，故这条路径**连告警都不会响**；测试用非法帧只断言了信封 VIN，从未覆盖"帧内 VIN ≠ topic VIN" | codec `process()` 在帧解析后、解码前加身份校验：`f.VIN != env.VIN` → DLQ（新 stage **`vin_mismatch`**，保留原始帧，两个 VIN 都写进 reason）；DLQ stage 枚举 4 处同步；新增告警 `CodecVINMismatch` | 3 条单测（一致放行 / 不一致拒绝且零产出 / 信封 VIN 为空也拒绝）；端到端回归不受影响（模拟器用同一 VIN 造帧与 topic，探针路径已核实） |
| **P1 安全** | HTTP 通道**只有认证没有身份**：`DEVICE_TOKENS` 只是 token 白名单，handler 直接采信载荷里的 `vin` → 任何持合法 token 的设备都能上报**任意车辆**。文档示例 `dev-x` 配 `vin=OV20260001` 正是这个洞的现场演示 | `DEVICE_TOKENS` 强制形如 **`token=VIN`**（未绑定即 fail-fast，两种模式都不放行）；`auth.Wrap` 解析身份并注入 context；handler 校验"载荷 VIN == 绑定 VIN"，复用 `vin_mismatch` 指标（现成告警⑧自动覆盖）；dev 模式改为 `dev-{VIN}` 且**仍校验**（旧实现放行任意 `dev-` 前缀，等于给校验留后门） | 单测覆盖：绑定解析 / 身份一致 202 / 冒充他人 400 且零投递 / `vin_mismatch` 指标存在 / 未绑定 token fail-fast / dev 模式越权仍拒绝；示例与 CI 里的 `dev-OVxxxx` 用法天然兼容 |
| **验证缺口** | 端到端 SLI 缺失；且原评审把"Prometheus 5s 抓取间隔"当成掩盖分位的原因（**误诊**：直方图聚积全部观测，抓取间隔只影响时间轴） | 用毫秒锚点补平台段：网关 `ingest_latency_seconds{channel}`（EMQX 毫秒时间戳已在信封里，此前**用完就扔**）+ 信封透传 `ingest_ts_ms` → codec `ingest_to_decode_seconds`；另加 `device_to_decode_seconds` 明确标注"1 秒分辨率，测陈旧度非性能"；面板 +1/+2、告警 +1 | 单测锁定"有锚点则观测 / 无锚点（旧信封）不观测 / 时间戳缺失不观测"；**残留**：设备侧毫秒端到端属契约改动，记为评审项 |
| **第 1 步缺口** | 《OceanVerse架构总览.md》§4.4 阶段 1 技术栈列了 MySQL/PG + Redis，但 compose 只有六个容器 → **第 4 步（Java×5，全部要 MySQL + Redis 缓存）的底座不存在**；另外技术栈行写了 gRPC 而全仓零实现，与《接入层设计》§11"gRPC 内部通道第 2 阶段"自相矛盾 | compose 加 **MySQL 8.4 + Redis 7**（沿用既有纪律：`restart: unless-stopped`、`mem_limit`、宿主端口回环绑定、healthcheck；宿主端口避让为 13306/16379）。**只建库不建表**——DDL 归第 4 步各服务。Redis 显式 `maxmemory 256mb + allkeys-lru`（不设上限会把 6GB 的 VM 吃穿，项目已因此崩过一次）。架构总览技术栈行标注 gRPC→第 2 阶段 | 8 容器结构校验通过（每服务均有 restart/mem_limit/healthcheck）；`deploy/README` §5 补 ⑦MySQL/⑧Redis 验证命令；**并如实记录内存算术**：八容器 mem_limit 合计 6.88 GiB > VM 6 GiB，给出"提内存到 8G 或压低 ClickHouse/MySQL 上限"两条对策 |

|---|---|---|---|---|
| 1 | `compose` / `security-e2e` 均在 `docker compose up` 阶段 8~13s 退出 | **Docker Hub 上的 `minio/minio` 已拒绝匿名拉取**（`pull access denied ... repository does not exist`）。同批拉取里其余 7 个镜像全部正常 → 是镜像源问题，不是限流 | 改用 `quay.io/minio/minio:<同一 tag>`（digest 与本地在跑的镜像**完全一致**，同一镜像换可匿名访问的仓库）；CI 拉取加退避重试；`deploy/README.md` §3 记录该坑与应急处置 | 第二次跑：`compose` 作业绿 |

**本轮沉淀**：① 本机绿 ≠ 干净环境绿（镜像可拉取性、凭证时序都属"只有 CI 才会问的问题"）；
② 安全自检的**负向判据必须配正向对照**，否则 `deny all` 也能让它们全绿；
③ 不可判定的信号（`EOF`）要尽早转成可判定的结论（前置自检 + 明确退出码），否则会白烧排障轮次。

**第十轮沉淀的教训**：① **"代码已合入" ≠ "跑的是新代码"**——进程生命周期与仓库状态之间需要一层"运行态体检"（本次是人工发现的）；
② **bind mount 不等于热载**——配置改动要有"新鲜度判据"（容器 healthy 只说明进程活着）；
③ **探针也是数据**——测试注入的东西必须有保留命名空间，否则会污染生产语义。

### CI 首跑排障记录（2026-09-18，四轮）

> 新加的门禁**第一次真跑**才发现的问题（此前只做本地等价复跑，掩盖了环境差异）。
> 4 次连续 failure 全部出在 `pipeline-health`，其余 12 个作业始终绿。

| 轮次 | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 两个服务都报"端口无监听（未运行?）" | **GitHub ubuntu runner 不预装 lsof**，而脚本 `2>/dev/null` 把 `command not found` 一并吞掉 → **"工具缺失"伪装成"服务没起来"** | CI 加 `install lsof`；脚本改为**实际可执行**判据并显式报错 |
| 2 | 前置检查报"无法 docker exec kafka" | **service container 的名字不是服务键**（实为 `<repo>-<hash>-kafka-1`），而 `services` 上下文只给容器 ID | 新增一步解析 `job.services.kafka.id` 并传入 `KAFKA_CONTAINER` |
| 3 | 报"端口无监听"，但容器日志显示已绑定、curl 可通 | runner 上（宿主 + 容器 `--network host`）**lsof 看不到容器进程的 socket** | 存活判据改用 **curl 探端点**（跨环境可靠）；lsof 降级为"孤儿检测最佳努力"，看不到时报**"无法判定"**而非误报故障 |
| 4 | 判据 3 报"端点可达"、判据 5 却报"不可达"，自相矛盾 | **CounterVec 在首个 series 出现前不导出** → 全新容器的 `gateway_requests_total` 为空，求和 0 被误判成不可达 | 先用 curl 判端点可达性，再解释 0 值（空闲态 = 正常） |

**沉淀的教训**：① 脚本里 `2>/dev/null` 是**危险默认**——会把"工具/环境缺失"伪装成"被测对象故障"；
② 存活判据要用**端到端可达性**（curl），不要用**本地进程视角**（lsof/ps），后者在容器化环境下不可靠；
③ "CounterVec 首个 series 前不导出"这条陷阱我在 CI 冒烟里踩过一次、又在健康脚本里重犯 —— 写进注释不够，需要更醒目的位置（本表即为索引）。
