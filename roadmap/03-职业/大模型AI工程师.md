# 大模型 AI 工程师：五个方向、能力矩阵与进入路径

> 一句话结论：**「大模型工程师」不是一个岗位，而是五个截面上的五类岗位**——模型生产层、模型层、应用层、产品层、交付层。同名 JD 落在不同截面，日常动作、核心指标和淘汰方式完全不同。
>
> 读法：§1 总表定方向 → §2 展开细节 → §4 按背景选 → §6 用 90 天验证。
>
> 口径：方向划分来自公开 JD 与工程实践归纳；**不引用薪酬数字**（样本偏差大、地区差异大），只给能力、产出物与判定标准。凡属经验判断而非统计结论的，正文会标注。

---

## 1. 五个方向：一张总表

| 方向 | 所在层 | 离模型的距离 | 主要产出 | 核心指标 | 典型失败模式 |
|---|---|---|---|---|---|
| **AI 算法** | 模型生产层 | 最近（造模型） | 权重、训练配方、评测结论 | 基准分数、消融是否可复现、数据配比收益 | 只调参不做消融，把最好一次当结论 |
| **AI Infra** | 模型层 | 近（让模型跑得动） | 训练/推理系统、性能报告 | MFU、tokens/s、TTFT/TPOT、P99、每百万 token 成本 | 只跑 benchmark 不定位瓶颈，吞吐好但尾延迟崩 |
| **AI 应用开发** | 应用层 | 远（调用模型） | RAG / Agent / 工具体系、评测集 | 正确率、引用准确率、越权拦截率、P95 延迟 | Demo 很炫、没有评测集、权限裸奔 |
| **AI 全栈** | 产品层 | 远（包装成产品） | 可交付的完整产品 | 留存、付费、交付周期 | 技术全栈但没人用，或交付后无法运维 |
| **FDE** | 交付层 | 远（打通最后一公里） | 驻场方案、POC、上线的业务系统 | 上线周期、业务指标达成、续约 | 停在 demo 不接管生产，被当成外包开发 |

一句话记法：**算法造模型，Infra 让模型便宜，应用让模型有用，全栈让用户能买，FDE 让客户敢用。**

## 2. 逐个方向展开

### 2.1 AI 算法：模型生产层

**做什么**：不调用模型，而是从**数据、架构、训练方法**三个维度把模型本身造出来、变强——设计 Transformer 变体结构、配比清洗训练数据、跑 SFT/DPO/RLHF 后训练对齐、通过消融实验和评测体系验证能力边界。关注的是「模型为什么聪明、还能不能更聪明」，产出是模型权重、训练配方和评测结论，而非功能或系统。

**日常一天**：读昨夜的训练曲线 → 看一批坏 case → 改数据配比或采样策略 → 小规模跑消融（几小时到一天）→ 全量重跑 → 写评测报告 → 决定是否进下一轮。**大部分时间在数据和实验设计上，不在改模型结构上。**

**硬技能**：

- PyTorch 与训练循环（不依赖高级封装也能写对反传、梯度累积、混合精度）
- Transformer 结构细节：attention 变体、位置编码、归一化位置、MoE 路由
- 数据管线：去重、去污染、配比、packing、分片与可复现（seed / 顺序 / 哈希）
- 后训练：SFT、DPO、RLHF 的损失与数据构造，知道各自适合解决什么问题
- 评测设计：heldout、显著性、消融对照、失败模式分类

**产出物**：checkpoint、训练配置与数据卡、消融表、评测报告（含失败案例），以及「下一版先改什么」的结论。

**怎么判断适不适合**：能忍受长反馈周期（一次实验几小时到几天）、喜欢读论文并复现、对数学和实验设计不排斥、愿意把「没提升」也当成结论写下来。

**常见误区**：把会调 API 当算法；把 loss 下降当能力提升；只报最好的一次 seed；不做数据侧消融就改结构。

**本仓库落点**：[`../../algorithms/p04-transformer/`](../../algorithms/p04-transformer/)（attention → BERT → GPT → T5 → ViT 的手写路线）、[`../../algorithms/p03-deep-learning/`](../../algorithms/p03-deep-learning/)（反传、CNN、RNN）、[`../../algorithms/docs/人工智能代表算法演进路线.md`](../../algorithms/docs/人工智能代表算法演进路线.md)。

### 2.2 AI Infra：模型层

**做什么**：解决「大模型怎么训得快、推理得便宜」。训练侧是并行策略、显存、通信、故障恢复；推理侧是调度、批处理、KV cache、量化、算子。产出是基础设施与性能数字，不是业务功能。

**日常一天**：拿到一个慢或 OOM 的任务 → profile（ncu / nsys / 日志）→ 定位是显存、通信还是算子 → 改并行切分或 kernel → 重跑 benchmark → 写清「哪个指标动了、动了多少、代价是什么」。

**硬技能**：

- 并行：DP / TP / PP / EP（含 MoE）、FSDP / ZeRO 的取舍
- 显存：activation checkpointing、FlashAttention、PagedAttention、KV cache 管理
- 通信：NCCL、RDMA、拓扑感知；知道什么规模下通信会成为瓶颈
- 推理引擎：vLLM / SGLang / TensorRT-LLM 的能力边界，连续批处理与调度策略
- 工程底座：K8s + GPU Operator + 队列/配额（Volcano 一类），能算 GPU·秒
- 会用数字说话：MFU、tokens/s、TTFT、TPOT、P99、每百万 token 成本

**产出物**：可复现的性能报告（硬件、模型、batch、序列长度、并发全写清）、容量与成本模型、故障恢复演练记录。

**怎么判断适不适合**：喜欢系统层、愿意读 C++/CUDA 与框架源码、对「把 20% 的性能抠出来」有耐心、不排斥看硬件手册。

**常见误区**：把「跑通 vLLM」当 Infra；只报吞吐不报尾延迟；benchmark 不复现（不写 batch/并发/序列长度）；把「加卡」当优化。

**本仓库落点**：[`../../engineering/ai-platform/AI平台建设路线.md`](../../engineering/ai-platform/AI平台建设路线.md) 的 D5（推理与服务）、D6（算力与调度）；[`../../engineering/compose/`](../../engineering/compose/)（底座）；[`../../languages/studies/c/`](../../languages/studies/c/)、[`../../languages/studies/rs/`](../../languages/studies/rs/) 补系统层基本功。

### 2.3 AI 应用开发：应用层

**做什么**：不训练模型，而是围绕现成的大模型搭好**上下文、知识库、工具调用、评测监控**，把模型能力包装成业务功能。这是当前招聘市场上最常见的入口（经验判断，非统计）。

**日常一天**：收一批线上 bad case → 判断是检索没召回、上下文太长、工具选错还是模型本身不行 → 改分块 / 改 rerank / 改提示 / 改工具描述 → 跑回归评测 → 灰度 → 看成本和延迟。

**硬技能**：

- 检索：分块策略、混合检索（BM25 + 向量）、rerank、引用定位
- 上下文工程：系统提示、few-shot、结构化输出、长上下文取舍
- 工具与协议：Function Calling、MCP、沙箱执行、超时与重试
- 评测：评测集构造、LLM-as-judge 的偏差、回归门禁
- 工程化：trace、成本计量、限流、越权拦截、人工确认点

**产出物**：一条可回归的问答/Agent 链路，带评测集、引用、权限和成本报表。

**怎么判断适不适合**：喜欢快速迭代、能同时跟业务和技术对话、对「答案对不对」有洁癖、愿意写评测而不是只写 prompt。

**常见误区**：没有评测集就上线；把 prompt 当系统设计；检索、生成、工具全链路不做权限；只优化平均延迟不管 P95。

**本仓库落点**：[`../../engineering/ai-platform/AI平台建设路线.md`](../../engineering/ai-platform/AI平台建设路线.md) 的 D3（检索与知识）、D8（Agent 与运行时）；[`../../algorithms/p05-generative/mini-rag/`](../../algorithms/p05-generative/mini-rag/)；[`02-能力/AI能力到企业底座-3-企业落地与Agent平台.md`](../02-能力/AI能力到企业底座-3-企业落地与Agent平台.md)（平台 × 开发双视角）。

### 2.4 AI 全栈：产品层

**做什么**：在应用开发基础上向前做用户交互、向后做后端服务与数据层，最终**独立交付一个用户能直接使用的完整产品**，常见于创业团队和独立开发者。

**日常一天**：用户反馈 → 判断是功能缺口还是体验问题 → 改前后端 → 部署 → 看留存与成本 → 决定下一个功能。技术只占一半，另一半是产品判断。

**硬技能**：前端（至少一个框架）、后端（API / 鉴权 / 队列）、数据（模型、检索、存储）、部署（容器、CI、监控）、计费与合规意识；外加**产品判断**：谁会用、为什么现在用。

**产出物**：一个真实用户能注册、付费（或持续使用）的产品，带监控、备份和故障预案。

**怎么判断适不适合**：愿意为「有没有人用」负责、能接受自己写 UI、对运维和成本有耐心、能独立做取舍。

**常见误区**：技术栈很全但没人用；把「上线」当「做完」，不做监控与备份；低估获客与支持成本。

**本仓库落点**：[`../../languages/`](../../languages/)（六语言是独立交付的地基）、[`../../engineering/`](../../engineering/)（D0–D10 即一个产品从底座到生产化的完整切片）、[`02-能力/AI能力到企业底座-5-OPC一人公司.md`](../02-能力/AI能力到企业底座-5-OPC一人公司.md)。

### 2.5 FDE：交付层

**做什么**：这是最特殊的一个。它源于 **Palantir 的驻场交付模式**，核心使命是打通 AI 落地的「最后一公里」：客户往往需求模糊、数据不全、流程复杂，FDE 要驻场访谈、翻译需求、搭建原型、接入系统，并对最终业务结果负责。它不是纯技术岗，而是「业务专家 + 工程师 + 交付者」的复合角色，行业共识是「**业务专家是 1，技术是后面的 0**」。

**日常一天**：客户现场访谈 → 把模糊诉求翻译成可验收的指标 → 用现有数据搭 POC → 接入客户系统（权限、网络、数据格式往往比模型难）→ 给业务方演示 → 推动上线 → 盯上线后的业务数字。

**硬技能**：业务建模（把流程画成实体/状态/指标）、快速原型、系统集成（SSO、API、数据库、消息）、数据清洗、干系人沟通、项目节奏管理。

**产出物**：POC、上线系统、业务指标改善的证据、可复用的交付方法论。

**怎么判断适不适合**：能在信息不全时推进、愿意出差/驻场、对「客户满意」而非「代码优雅」负责、能把技术讲给非技术人听。

**常见误区**：只做 demo 不接管生产；被客户当成外包开发；不定义验收指标，最后无法证明价值；技术方案不以客户现有系统为前提。

**本仓库落点**：[`02-能力/AI能力到企业底座-2-FDE岗位与方法.md`](../02-能力/AI能力到企业底座-2-FDE岗位与方法.md)；[`../../engineering/docs/车联网与机器人数据域需求.md`](../../engineering/docs/车联网与机器人数据域需求.md)（真实业务域的建模练习）。

### 2.6 方向之间怎么迁移

| 从 | 到 | 要补的 | 常见做法 |
|---|---|---|---|
| 应用开发 | AI 算法 | 训练、评测、数据配比 | 先能设计评测集，再进训练 |
| 应用开发 | Infra | 系统、性能、并行 | 先做一次推理压测与优化 |
| 算法 | Infra | 系统工程 | 做训练/推理的性能优化 |
| 全栈 | FDE | 业务建模、客户沟通 | 接一个真实客户做 POC |
| FDE | 全栈 | 产品判断、前端 | 独立交付一个小产品 |
| Infra | 应用开发 | 检索、评测 | 少见，通常是转向产品 |

> 迁移通常发生在「当前层已经能交付清楚」之后。跳层最常见的结果是两层都停在半成品。

## 4. 怎么选：按你现在的背景

| 起点 | 首选 | 次选 | 关键动作 |
|---|---|---|---|
| 后端 / Java / Go | 应用开发 | Infra | 先补检索与评测，再补 GPU 与推理引擎 |
| 数据工程 / 数仓 | 应用开发、FDE | Infra | 数据底座是优势，补模型与检索 |
| 算法 / 科研 | AI 算法 | Infra | 补工程化（可复现、数据卡、评测门禁） |
| 产品 / 咨询 / 售前 | FDE | 全栈 | 补原型能力与系统集成，别停在 PPT |
| 学生 / 转行 | 应用开发 | 全栈 | 先做一条可评测的端到端链路，再谈方向 |
| 独立开发者 | 全栈 | 应用开发 | 先验证付费意愿，再扩技术栈 |

**三条选择原则**：

1. **先选层，再选技术栈**。层决定日常动作，栈只是工具。
2. **选能拿到真实反馈的那一层**。没有数据和用户的方向，练不出判断力。
3. **入口可以低，天花板要看得到**。应用开发是常见入口，但要知道往上能到产品，往下能到 Infra。

## 5. JD 辨伪：同名岗位在招哪一层

| JD 关键词 | 实际方向 | 面试大概率问 |
|---|---|---|
| 预训练 / 后训练 / SFT / RLHF / DPO / 数据配比 / 评测体系 | AI 算法 | 消融怎么设、数据怎么去污染、评测怎么防泄漏 |
| CUDA / 算子 / 并行 / 显存 / 推理加速 / NCCL / MFU | AI Infra | 显存怎么省、通信瓶颈在哪、TTFT 怎么降 |
| RAG / Agent / Function Calling / 知识库 / 向量库 / 评测集 | 应用开发 | 召回怎么评、工具怎么选、越权怎么拦 |
| 独立负责 / 从 0 到 1 / 全栈 / 上线 / 增长 | 全栈 / 产品 | 产品判断、取舍、运维与成本 |
| 驻场 / 客户现场 / 需求调研 / POC / 解决方案 | FDE | 怎么定义验收、怎么接客户系统、怎么证明业务价值 |

**三条判定规则**：

1. **看产出物**：权重、性能报告、评测集、产品、上线系统——产出物决定层。
2. **看指标**：基准分、tokens/s、正确率、留存、业务指标——指标决定考核方式。
3. **看协作对象**：研究员、SRE、产品、客户——协作对象决定你每天跟谁吵。

## 6. 90 天验证路径

> 目的不是「90 天成为工程师」，而是**用最小成本验证这个方向适不适合你**。每个验收物都要能拿给别人看。

| 方向 | 第 1–2 周 | 第 3–6 周 | 第 7–12 周 | 验收物 |
|---|---|---|---|---|
| AI 算法 | 复现一个小模型（≤1B）的训练与评测 | 做一次数据配比或结构消融 | 跑一次 SFT + DPO 对比 | 消融表 + 评测报告（含失败案例） |
| AI Infra | 单卡跑通 vLLM 推理并压测 | 定位一个性能瓶颈（显存/批处理/算子） | 做一次吞吐与延迟优化对比 | 可复现的性能报告（硬件/并发/序列长度） |
| 应用开发 | 搭一条 RAG 链路 | 补 100 题评测集与引用 | 加权限、限流与成本报表 | 评测报告 + 越权拦截证据 |
| 全栈 | 定义一个问题与目标用户 | 做出可用的最小产品 | 上线并拿到 10 个真实用户 | 上线地址 + 留存/成本数据 |
| FDE | 找一个真实业务场景 | 访谈 + 定义验收指标 | 交付 POC 并接入真实数据 | POC + 业务指标前后对比 |

**放弃信号**（同样重要）：连续两周做不下去、每次都要靠外部催促、验收物只能给自己看——这三条出现任意两条，换方向比硬撑更划算。

## 7. 常见误区

1. **把「用过」当「会」**：装过 vLLM、调过 API、跑过 LoRA，都不等于能定位问题。
2. **用框架数量当深度**：会五个框架不如能说清一个框架的取舍。
3. **只做一个方向却宣称全栈**：矩阵里没有全能选手，面试官一眼能看出来。
4. **不做评测**：没有评测集的 AI 应用，等于没有测试的后端。
5. **忽略成本与延迟**：效果提升 2 分、成本涨 10 倍，在业务上是负分。
6. **不读源码、不看失败案例**：只看成功分享，等于只学了一半。
7. **把岗位名当能力**：「大模型工程师」是岗位名，不是技能清单。
8. **跳过数据与业务**：模型再强，数据不通、流程不接，价值为零。

## 9. 自检清单

- [ ] 能说清自己选的是哪一层，以及这一层的产出物是什么
- [ ] 有一个能拿给别人看的验收物（不是「我学过」）
- [ ] 做过的项目有评测集或性能报告，数字可复现
- [ ] 能解释至少一个框架/引擎的核心取舍，而不只是会调用
- [ ] 知道自己方向的典型失败模式，并能举出自己踩过的例子
- [ ] 能估算一次推理/训练的成本量级
- [ ] 读过至少一个核心项目的源码（vLLM、LangChain、PyTorch 均可）
- [ ] 有权限、安全、降级的意识，而不只是效果
- [ ] 能把技术方案讲给非技术人听（FDE/全栈必备）
- [ ] 有 90 天验证记录：做了什么、数字多少、结论是什么
- [ ] 明确知道自己下一步补哪一项，而不是「都学一点」
- [ ] 简历上的每个方向，都能对应到矩阵里的 ● 或 ○
