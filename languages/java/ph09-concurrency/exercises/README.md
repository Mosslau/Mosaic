## 练习 1：多线程计数器（★）

**目标**：写出 10 线程各加 1 万次的计数器，对比普通变量、`synchronized`、`AtomicInteger` 三种写法的正确性。
**要求**：

- 10 个线程各执行 1 万次 `count++`，三种计数器各一份：普通 `int`、`synchronized` 块保护、`AtomicInteger`
- 主线程必须等全部线程结束再输出（`join()`），否则读到的是半成品
- 不允许把普通变量那份去掉——它存在的意义就是暴露竞态
- 输出期望值、三个计数器的值，并断言 `synchronized` 与 `AtomicInteger` 等于期望值

**验收**：`synchronized` 与 `AtomicInteger` 计数稳定等于 100000；普通变量通常小于 100000（每次运行可能不同），并打印「通常小于期望值」的说明；计数不符时抛 `AssertionError`。

## 练习 2：生产者消费者（★★）

**目标**：用有界 `BlockingQueue` 解耦 2 个生产者与 3 个消费者，验证不重不漏。
**要求**：

- `ArrayBlockingQueue` 容量 5；2 个生产者共产 30 件（1..30），3 个消费者并发消费
- 每个消费者统计自己处理了几件；主线程汇总总数
- 消费者退出条件要明确：等**全部生产者结束**后放「哨兵消息」（如 -1，由主线程放入、每消费者一个），收到即退出——**不许用 `Thread.stop` 或靠 `sleep` 猜时间退出**（哨兵提前放会饿死未完成的生产者：消费者先退出、队列满时无人消费，生产者永远阻塞）
- 中断时恢复中断标志（`Thread.currentThread().interrupt()`）
- 断言：总消费数 == 30 且消费值之和 == 465（1+2+...+30）

**验收**：程序正常结束（无死锁、无消费者饿死）；输出每个消费者处理件数、总数 30、总和 465；计数不符抛 `AssertionError`。

## 练习 3：线程安全队列（★★★）

**目标**：不用任何 `BlockingQueue`，用 `ReentrantLock` + `Condition` 手写一个有界队列，再让 2 生产者 3 消费者并发使用。
**要求**：

- 手写 `BoundedQueue`：环形缓冲数组 + 两个 `Condition`（`notFull` / `notEmpty`）
- `await()` 必须放在 **while 循环**里检查条件（防虚假唤醒），`put`/`take` 都要在 `finally` 中 `unlock`
- 2 生产者各产 20 件（共 40 件），3 消费者并发消费；用 `boolean[]` 校验每件恰好消费一次
- 消费者退出仍用哨兵方案（等全部生产者结束后由主线程放入，每消费者一个；原因见练习 2）
- 断言：消费数 == 40、消费值之和 == 820（1+2+...+40）、无重复无丢失

**验收**：40 件全部被消费一次；总和 820；程序无死锁正常退出；手写队列源码中 `await` 均在 `while` 内、`unlock` 均在 `finally` 内。

## 练习 4：异步日志系统（★★★）

**目标**：多线程产生日志，塞进 `BlockingQueue`，单后台线程批量落盘——生产与写盘解耦，关闭时不丢最后几条日志。
**要求**：

- 3 个生产者线程各产 500 条消息（如 `producer-0 message-0`），入队
- 1 个后台写线程从队列取消息写入文件；**批量落盘**（可用 `drainTo` 一次取一批，减少锁竞争）
- 关闭流程：等全部生产者结束后，放入**哨兵消息**优雅收尾，写线程见哨兵即 flush 并退出——保证已入队日志全部落盘（对比 `shutdownNow` 强杀会丢队列尾部消息）
- 日志文件写到 `/tmp/async-logger-demo.log`，运行结束自动删除，不在仓库残留
- 断言：文件行数 == 1500，且每行格式匹配 `producer-[0-2] message-\d+`

**验收**：日志行数恰好 1500（一条不丢、不多）；行格式校验通过；运行后 `/tmp` 下的日志文件被清理。

## 练习 5：用虚拟线程实现高并发任务处理（★★，需 JDK 21+）

**目标**：对比固定线程池与虚拟线程处理 1 万个阻塞任务（各阻塞 10ms 模拟 IO）的耗时，验证「阻塞 IO 自动让出载体线程」。
**要求**：

- 固定线程池 200 线程 vs `Executors.newVirtualThreadPerTaskExecutor()`，各提交 1 万个任务
- 用 `Thread.sleep(Duration.ofMillis(10))` 模拟阻塞 IO；`ExecutorService` 用 try-with-resources 关闭（JDK 21+ 实现 `AutoCloseable`）
- 统计两者总耗时并输出；用 `AtomicInteger` 断言两种池的任务完成数都是 10000
- 换成一个纯 CPU 计算任务（如求质数）再跑一遍，观察虚拟线程是否还有优势——结论写进输出

**验收**：两池完成数均 == 10000；虚拟线程通常远快于 200 线程平台池（结论可复现，具体毫秒随机器而异）；输出能解释「虚拟线程适合 IO 密集、不适合计算密集」。
