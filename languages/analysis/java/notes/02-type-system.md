# 02 · 类型系统：基本类型、装箱与泛型擦除

> demo: `java demos/02_type_system.java`

## 1. 设计动机

Java 诞生时要做"比 C++ 更安全"的静态强类型语言，却面临一个工程现实：**纯对象太慢，
纯值类型不够"一切皆对象"**。于是 Java 走上一条折中路：8 个**基本类型**（int/double…）
走栈上值语义（快），其余全是**引用类型**（对象）；二者用**自动装箱**在语法上抹平差异。
多年后加泛型（JDK 5），又为兼容旧字节码选择**类型擦除**。这三步是 Java 类型系统
"安全与性能拔河"的全部历史。

## 2. 机制拆解

**基本类型 vs 引用类型**是 Java 类型系统的第一道分界线：

```java
int a = 42;          // 栈上值：42 直接存在变量里
Integer b = 42;      // 自动装箱：堆上 Integer 对象，变量存引用
int c = b;           // 自动拆箱：取回栈上值
Integer d = null;    // 引用类型可为 null —— 拆箱 d 会抛 NullPointerException！
```

装箱的代价在集合里放大：`List<Integer>` 每个元素都是一个堆对象 + 指针，
百万级整数的内存是 `int[]` 的数倍。

**泛型擦除（type erasure）**：`List<String>` 与 `List<Integer>` 编译后是同一个
`List`（存 `Object` 或边界类型），类型参数只在编译期检查：

```java
List<String> names = new ArrayList<>();
// 编译期：names.add(42) 报错
// 运行期：字节码里只有裸 List，元素以 Object 存取，取用时自动 cast
```

擦除换来**向后兼容**（JDK 5 泛型代码可直接跑在老 JVM 上），代价是：
- 运行时拿不到类型参数（`instanceof List<String>` 非法）；
- `new T[]` 建不了泛型数组（运行期没有 T）；
- 重载/桥方法出现编译器生成的"脏方法"。


## 4. 代价与取舍

| 代价 | 说明 |
|------|------|
| 值/引用分裂 | 两套语义（`==` 值 vs 引用）、两套性能，初学者反复踩坑 |
| 装箱对象膨胀 | 集合装基本类型开销数倍；Valhalla（inline class）至今未落地 |
| 泛型擦除 | 运行时无类型信息，泛型数组/重载受限，桥方法污染栈迹 |
| null 与拆箱 | 自动拆箱遇 null 抛 NPE——"十亿美元错误"的放大器 |

**换来的**：强静态类型让 IDE 补全/重构/编译期检查成为 Java 生产力核心；
基本类型保住数值性能；擦除保证 JDK 5 泛型零破坏兼容——企业 20 年技术债没断。

## 5. 对 Tenet 的启示

- ✅ **吸收"基本值类型 + 显式类型标注"**：Tenet 的 int/float/bool/string 值语义
  （见架构文档 §2.5）正是 Java"值走栈、无装箱"的最干净形态——**没有装箱层**
  就没有拆箱 NPE、没有 Integer 缓存陷阱
- ❌ **拒绝值/引用分裂**：Tenet 全部值语义——`==` 永远比内容，不引入"对象身份"
  第二套语义，Java 的 `==` 陷阱从根上不存在
- ❌ **拒绝泛型（现阶段）**：架构文档拒绝清单已记"泛型——复杂度远超当前收益"；
  Java 的擦除方案证明泛型要么复杂（擦除+桥方法）要么运行时膨胀，
  教学语言先把 `print` 的"接受任意类型"做对即可
- 💡 Java 的教训是**别为"语法糖的平等"引入隐式转换**：自动装箱看似方便，
  实则把性能与语义问题藏进角落——Tenet 若加字符串插值等糖，也要"显式优于隐式"

**一句话**：Java 用「基本类型 + 装箱」调和性能与对象模型、用「擦除」调和泛型与兼容，
两次调和都成功但都留下长期的坑；Tenet 用「全值语义 + 无泛型」直接绕开这两个问题域。
