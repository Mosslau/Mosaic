# Go 消息队列与事件驱动深入阶段

> 面向"请求之后怎么办"：ph17/ph18 教会你同步世界——服务内部怎么分层、对外契约怎么稳定；本阶段进入异步世界——服务之间不直接喊话，而是通过消息队列把"已发生的事实"广播出去。学习 Kafka/NATS/RabbitMQ 三种消息系统的消费模型，掌握消费者组、顺序性、幂等、重试/死信、积压监控与事件 schema 版本管理，最后用一辆"设备遥测消费服务"把整条消费链路串起来。

## 2. 来源与演变

消息中间件的历史比 Go 语言早得多，而且三条技术谱系各自回答不同问题。**设计哲学一句话加粗：消息队列把"服务间同步的强耦合喊话"变成"持久/即时的异步事件流"，代价是投递语义从"一次成功"退化为"至少一次"——可靠性的一半责任从此转移到消费端。** 

**Kafka** 源于 2011 年 LinkedIn 的日志/事件流需求（作者 Jay Kreps 等人），设计目标是**高吞吐的提交日志（commit log）**：数据按主题（topic）切成若干**分区（partition）**，每个分区是只追加的有序日志，offset 是分区内自增序号。这个"分区日志"模型带来两个决定性结果：其一，吞吐量随分区数线性扩展（不同分区可并行读写）；其二，同 key 进同分区 ⇒ 分区内保序。2012 年捐给 Apache，2016 年前后借"消费者组"与 log compaction 成为事件流平台，连接器生态（Connect/ksqlDB）又把它推向"流处理的事实标准"。

**NATS** 走的是另一条路：2012 年 Derek Collison（曾是 Cloud Foundry 架构师）为云原生"服务间轻量消息"设计的**极简发布-订阅系统**——核心不是持久日志而是**内存中的 subject 分层路由**（`fleet.car-001.telemetry`，支持 `*` 与 `>` 通配）。它以低延迟、简单、at-most-once 语义著称；2018 年加入 CNCF，同年推出的 JetStream 在保留简单性的前提下补上持久化、重放与消费者语义，让"NATS 只能做瞬态总线"的印象过时。

**RabbitMQ** 的血统最老：2007 年由 Rabbit Technologies（后被 Pivotal/VMware 收购）基于 **AMQP 0-9-1 协议**实现，核心心智是**队列（queue）+ 交换机（exchange）**——生产者把消息发给交换机，交换机按 binding/routing key 把消息路由进一个或多个队列，消费者从队列取走消息并显式 ack。它是最经典的"任务队列 + 灵活路由"型消息中间件，适合请求/任务分发，而不是大规模事件流。

Go 侧的客户端生态随各系统先后成熟：Kafka 早期社区客户端 sarama（2013 年出现）功能全但 API 较重，segmentio/kafka-go（2017 年）以更贴近标准库的 Reader/Writer API 流行；NATS 官方客户端 nats.go 一统；RabbitMQ 社区事实标准 streadway/amqp 长期维护（后转入 rabbitmq/amqp）。下表是三个系统与 Go 生态演进的里程碑：

| 版本/里程碑 | 年份 | 主要变化 |
|------|------|---------|
| AMQP 0-9-1 规范 | 2003~2006 | 金融界驱动的消息协议：交换机/队列/路由键成为标准化概念 |
| RabbitMQ 开源 | 2007 | AMQP 的明星实现；任务队列 + 灵活路由的代名词 |
| Kafka 诞生（LinkedIn 内部） | 2011 | 提交日志 + 分区 + offset 的现代事件流模型 |
| Kafka 捐给 Apache | 2012 | 社区化；成为大数据/日志管道默认组件 |
| sarama（Go Kafka 客户端） | 2013 | 首个主流 Go Kafka 客户端（重 API、功能全） |
| NATS 开源 | 2012~2014 | 云原生极简 pub/sub；`subject` 分层 + 通配路由 |
| JetStream（NATS 持久化） | 2019 | NATS core 之上补持久化/重放/消费者语义 |
| segmentio/kafka-go | 2017 | Reader/Writer 风格（贴近标准库）的 Go Kafka 客户端 |
| nats.go | 持续 | NATS 官方 Go 客户端，core/JetStream/队列组一等支持 |
| streadway/amqp → rabbitmq/amqp | 2013~ | Go AMQP 客户端事实标准（连接/信道/ack 语义映射） |

本文示例以 **Go 1.25** 为基线（本阶段全部示例/练习/项目的 go.mod 写 `go 1.25.0`，与 ph15/ph16/ph17/ph18 对齐的仓库工具链版本一致；本阶段用到的标准库——sync、errors.Is/As、time、encoding/json、context——在该基线上全部稳定可用），验证工具链 go1.25.6（darwin/arm64）。验证口径如实声明：**本机（macOS）无 Kafka/NATS/RabbitMQ broker 与 Docker，无法连真 broker 验证**——因此全部 examples/exercises/project 采用"内存假 broker / 协议语义模拟 + 客户端库可选"的离线可测策略（同仓库 ph18 Python 侧 FakeBroker 先例）：核心逻辑（消费者组分配语义、幂等消费、重试/死信状态机、积压水位）用纯标准库 + 接口抽象实现，`go vet ./... && go build ./... && go test ./...` **已在本机实测全绿并标注「已验证」**；真正连 Kafka/NATS/RabbitMQ 的客户端代码（kafka-go、nats.go、amqp）在文中如实标注「未在本环境验证」，并给出可复现命令（`go get` 依赖 + 本地 broker 或 docker 启动）。一个定心话：本阶段真正的"语法"很少——多是**并发原语与纯函数在消费者组/去重/状态机上的组合**，心智负担集中在"消息可能重复、可能乱序、可能失败，我该怎么设计消费端"。

一句话提炼三者的定位差异：**Kafka 为"流"而生（数据先存后算，可回放、可多路消费），NATS 为"云原生总线"而生（内存扇出、低延迟即时分发），RabbitMQ 为"任务"而生（一条消息一个工人，路由灵活、确认严谨）**。Go 服务里最常见的真实组合是"Kafka 做事件主干 + 内部用 NATS/请求应答做轻量通信"，RabbitMQ 多见于既有企业栈（它诞生最早、与 AMQP 生态绑定最深）。把这段历史记住，遇到"该上哪款"时就不会只看吞吐数字——**吞吐是工程的，语义是哲学的**：先想清楚你要的是流、总线还是任务。

## 3. 语法与参数

第 3 章按"从共性到特性、从投递到处理"的顺序展开：先立**消费模型共性**（3.1）与**三款 broker 的模型对照**（3.2）；再深入 Kafka 式核心——**消费者组与 offset**（3.3）、**顺序性**（3.4）、**重复消费与幂等**（3.5）、**重试与死信**（3.6）、**积压监控**（3.7）；最后进入事件驱动设计层——**事件 schema 版本管理**（3.8，兑现 ph18 预告）与**可靠事件流模式**（3.9），并以 **Go 客户端生态速查**（3.10）收尾。

### 3.1 消息系统的共性：生产者、消费者、消费语义

不同消息系统的术语各异，但骨架相同：**生产者（producer）发布"消息"到某个命名通道（topic/subject/queue），消费者（consumer）从通道取走消息**。真正的分水岭是通道对消息的三重态度：

| 维度 | Kafka | NATS core | RabbitMQ |
|------|-------|-----------|----------|
| 消息去向 | 追加进分区日志，**持久**，可重放（从任意 offset 读） | 内存中路由给当前订阅者，**不持久**（没人订阅就丢） | 进入队列，**持久**（或瞬态），直到被消费并 ack |
| 通道命名 | topic（再切 partitions） | subject（`.` 分层 + `*`/`>` 通配） | queue（+ exchange 做路由） |
| 一条消息谁收到 | 消费者组内**一个成员**（组间可各自读一份） | 普通订阅**全部**收到；队列组内只一人 | 队列内只有一个消费者收到（除非 competing consumers 按负载分摊） |
| 投递后确认 | 消费方提交 offset | 无确认（at-most-once 默认） | 消费方显式 ack/nack |

> 本阶段以 Kafka 的分区/组/offset 语义为主线（3.3~3.7），因为它是"消费模型纪律"最完整的一支；NATS/RabbitMQ 的对照（3.2、3.10）帮助建立"同一问题不同解法"的心智，不要求你把三者的管理命令都背下来——**真实工程"选型 + 读懂官方语义"远比"记 API"重要**。

**Go 里消费循环长什么样**：无论哪个客户端库，消费者本质是一段"拉取 → 处理 → 确认/提交"的循环。ex01 用内存日志把这段循环的骨架做出来了（分区内逐条、处理完提交），真实 kafka-go 只是把"拉取"换成 `ReadMessage`、"提交"换成 `CommitOffsets`。消费者进程崩溃时，未确认/未提交的消息会在重平衡后**重新投递**——这就是"至少一次投递（at-least-once）"的由来，也是 3.5 幂等消费存在的全部理由。

### 3.2 三种消费模型的细节对照

**Kafka：topic = N 个分区日志**。生产者按 key 散列（或指定分区器）选择分区追加；消费者组按"一个分区同一时刻只给组内一个成员"分配。它的心智是**存储层**：分区是文件日志、offset 是游标，所以消费可以"回溯"（重置到任意 offset 重放），这给了事件流"随时复盘"的能力。

**NATS：subject = 一种动态路由**。发布-订阅按 subject 模式匹配分发（`fleet.*.telemetry` 匹配任意一级，`fleet.>` 匹配任意尾部）；请求-应答用 `_INBOX` 临时主题实现；**队列组（queue group）**让同 subject 的一组订阅者轮询分摊（等价于 Kafka 消费者组在 NATS 世界的版本，但没有分区/offset 概念）。exercises/sol-02 用离线实现演示了这三件事。

**RabbitMQ：exchange + routing key + queue**。生产者的消息先进交换机，交换机按类型（direct/fanout/topic/headers）与绑定规则把消息放进一个或多个队列；消费者可以多个实例同时从一个队列取消息（默认轮询，叫 competing consumers），靠 **ack** 与 **prefetch** 控制可靠性。它和 Kafka 最大的哲学差：RabbitMQ 面向"任务队列"（一条消息完成一次工作），Kafka 面向"事件流"（同一条事件可被多个下游独立消费）。

下表把三者落在"同一条设备遥测该发到哪、谁收到"上：

| 诉求 | Kafka | NATS | RabbitMQ |
|------|-------|------|----------|
| 设备 A 的遥测要**按顺序**被消费 | topic 分区键用 deviceID，同 key 同分区 | 需要单消费者 + 单 subject（无分区内保序概念） | 单队列 + 单消费者（多消费者会打乱顺序） |
| 多个下游（存储/告警/大屏）各自消费同一份事件 | 各自独立消费者组 | 各自独立订阅（天然 fan-out） | exchange fanout 到多个队列 |
| 一次性任务分发（谁闲谁干） | 消费者组 + 分区（粒度是分区） | 队列组 | 多消费者共享队列 + ack |
| 某条消息失败要"留证重试" | 靠消费端逻辑重投/死信 topic | 靠消费端逻辑或 JetStream | 队列 + DLX（死信交换机） |

> RabbitMQ 的交换机/队列管理、JetStream 的 stream/consumer 配置都属"选型后按官方文档操作"的部分，本阶段目标是把**语义差异**讲清楚——为什么 Kafka 保序的前提是分区键、为什么 NATS 默认 at-most-once、为什么 RabbitMQ 的多消费者共享队列会破坏顺序。这些语义差会直接决定你写消费端代码时的假设。

### 3.3 消费者组与 offset 提交

Kafka 的消费者组（consumer group）是分区语义的执行者，两条硬规则构成了全部行为：

- **一个分区同一时刻只被组内一个成员消费**——组内并行度 = min(分区数, 成员数)，多出的成员空转；
- **组在 broker 侧记录每个分区的已提交 offset**——成员崩溃/被踢后，接管该分区的成员从上次提交处续读。

examples/ex01-consumer-group-semantics 把这两条规则做成离线可测的最小实现（`Assign` 纯函数 + 组级 `Commit`/`Committed`），它的演示输出展示了核心现象：

```text
== 当前分配（每分区恰好一个成员）==
   m1 ──▶ 分区 [0 2]          ← 3 分区 2 成员：轮询取模，各分区只归一个成员
   m2 ──▶ 分区 [1]
== m3 加入，重平衡 ==
   m1 ──▶ 分区 [0]
   m2 ──▶ 分区 [1]            ← 重平衡后每个分区仍恰好一个成员
   m3 ──▶ 分区 [2]
```

**offset 提交是可靠性的开关**，提交时机决定投递语义：

| 提交策略 | 行为 | 投递语义 | 适用 |
|---------|------|---------|------|
| 自动提交（如每 5s） | 处理与提交解耦，可能在处理前就提交了 | at-most-once（崩溃丢消息）或至少一次（提交前崩溃重放）——**语义含糊** | 丢几条可容忍的场景（日志展示） |
| 处理完手动提交 | 先处理成功、再提交 | at-least-once：崩溃一定发生在提交前 → 已处理的会重放 | 默认推荐（本阶段全部代码按此实现） |
| 幂等表 + 提交 | 见 3.5/3.6 | "效果恰好一次"的工程近似 | 扣款/下发等敏感副作用 |

**重平衡（rebalance）的代价**是理解消费者组行为的钥匙：任一成员加入/退出，组都要重新分配分区，期间受影响分区暂停消费。真实客户端里应避免"每处理一条就心跳超时"、避免组成员数量频繁抖动（这会让组反复重平衡、消费停滞）。离线实现里对应的是 `Assign` 的"可复现分配"——相同成员集合得到相同分配，重平衡才可预期（ex01 的单测钉住了这条）。

> 与 HTTP 重试的呼应（ph18 3.6）：REST 的 POST 幂等键与消息的 MsgID 去重是**同一个思想的两种载体**——同步世界客户端重试需要服务端认键，异步世界 broker 重投需要消费端认键。区别只在于：REST 幂等键由调用方生成一次，消息的 MsgID 是生产时就烙在事件上的。

**分区分配与成员数的心算**：给定 P 个分区、C 个成员，理想均衡是每个成员分到 ⌊P/C⌋ 或 ⌈P/C⌉ 个分区。三档特例值得一眼认出：

| 成员数 vs 分区数 | 会发生什么 | 工程含义 |
|-----------------|-----------|---------|
| C = 1 | 一个成员吃掉全部分区 | 串行消费：顺序最稳、吞吐最低；服务重启即全组停机 |
| 1 < C ≤ P | 每人 1+ 个分区，均摊 | 标准形态；C 越大单成员负担越小 |
| C > P | 多出的成员分到 0 个分区 | **加了实例不加吞吐**——扩容前先确认分区数够不够 |

所以"分区数定多大"要在建 topic 时就按**峰值吞吐 + 预留未来扩容**决定：分区太少，扩实例到顶就再无横向余地（只能重建 topic 或加分区，Kafka 允许在线扩分区但不支持缩）；分区太多则文件与协调开销上升。一个常用的工程经验是"按预估峰值单分区吞吐与目标实例数反推，再乘 1.5~2 余量"——但这只是启动值，最终以压测为准。

**成员生命周期与消费停滞**：真实客户端里，成员通过心跳向 group coordinator 保活；心跳超时或主动 LeaveGroup 都会触发重平衡。最容易踩的坑是"处理一条消息太久、心跳都超时了"——coordinator 以为你死了，把分区重平衡给别人，而你的进程其实还在慢慢处理旧数据，两边同时处理同一分区 → 重复消费窗口被拉大。对策与 3.5 的幂等表互为表里：**处理时长要有上限（超时的消息走 3.6 的死信），心跳/轮询不能停**；离线示例里看不到心跳，但"提交点"的行为完全一致——把处理循环写稳，比调任何心跳参数都重要。

### 3.4 顺序性保证与分区内有序

消息队列只承诺**分区内有序**，不承诺全局有序——这是吞吐与顺序的经典取舍。顺序性由**分区键（partition key）**圈定：同一个 key 的所有消息进同一个分区，在该分区内严格按写入序消费。examples/ex05-order-guarantee 把两种分区键策略摆在一起对比：

```text
稳定分区键（key=deviceID）          轮询分区键（同 key 每来一条换分区）
key=A 消费子序列 = [A-1 A-2 A-3]    key=A 消费子序列 = [A-1 A-3 A-2]  ← 乱序！
key=B 消费子序列 = [B-1 B-2 B-3]    key=B 消费子序列 = [B-2 B-1 B-3]
```

两条纪律：

| 纪律 | 说明 | 违例后果 |
|------|------|---------|
| **key 选"实体标识"**：deviceID、orderID、userID 这类稳定业务键 | 实体的事件天然需要顺序（扣款、状态机、轨迹） | 用时间戳/随机数当 key，同一实体的事件散落多分区，跨分区消费顺序不可信 |
| **顺序只在分区内**：不依赖跨分区的全局顺序 | 不同分区的消费可并行、交错 | 假设"A 事件一定先于 B 事件全局到达"，在高并发下必然出错 |

顺序性还有个隐蔽维度：**单分区内多线程处理也会乱序**。即使消费端从同一分区顺序读到消息，若把处理丢给 worker pool 并发执行（处理耗时不一），后读的先处理完，副作用顺序就乱了。要保序必须**串行处理或按 key 哈希分桶后桶内串行**。NATS/RabbitMQ 同理：NATS 单 subject 无分区保序概念，RabbitMQ 单队列多消费者是轮询分发——它们的"顺序"只能靠"单消费者 + 串行处理"硬扛，这也是 Kafka 在这类诉求上胜出的原因。

> 分区键冲突时的工程判断：既要设备级顺序又要全局可扩展时，用 `key=deviceID`；若同一业务动作涉及多台设备（如设备组调度单），需要"动作级"顺序，则 key 应取**动作 ID**——分区键粒度决定顺序粒度，这个决策发生在生产端，消费端只能服从。

**同一实体的乱序，实际有四个来源**——排查时按序怀疑：

| 乱序来源 | 在哪个环节 | 例子 |
|---------|-----------|------|
| 分区键不稳 | 生产端 | 同设备事件按时间戳/随机数取模，散到多个分区 |
| producer 重试顺序翻转 | 生产端 | 消息 A 发送超时重发，排在 B 之后到达（需要幂等 producer 的序号去重来缓解） |
| 跨分区并发消费 | 消费端 | 组内多个成员并行处理不同分区，全局到达顺序不可预期 |
| 单分区内并发处理 | 消费端 | 同一分区读出的消息丢给 worker pool，慢的处理晚于快的完成 |

第 1、4 类在自己的代码里可控（key 选对、处理串行或按 key 分桶）；第 2 类靠 broker/客户端的幂等机制缓解；第 3 类是**设计前提而非 bug**——只要不同实体的事件彼此无因果，就没必要等一个全局顺序。判断自己要不要"全局有序"的试金石：**A 事件必须看到 B 事件的结果吗？** 若必须，两者要么进同一分区，要么 A 等 B 的确认再发（回到请求-应答，ph11）——消息队列不解决跨分区因果，它只诚实地告诉你"我只保证分区内"。

> 顺序性还有一种被低估的成本形态：**为保序牺牲并行度**。所有事件挤进一个分区 = 顺序完美但吞吐受限。真实系统常做"双 topic"：保序关键流单分区低频，非关键流多分区高频——把"顺序的粒度"与"吞吐的诉求"分别建模，而不是全局一刀切。

### 3.5 重复消费与幂等消费

为什么一定会重复？两条路径：**producer 重试**（发出去没收到 ack，重发同一条）与 **consumer 崩溃重放**（处理完没来得及提交，重平衡后从旧 offset 重读）。这是 at-least-once 的必然代价。消费者能做的最坏假设就是：**任何一条消息都可能收到两遍**（examples/ex01 的 `TestCommitBeforeCrashRedelivers` 专门演了这条"提交前崩溃 → 原样重读"）。

幂等消费的标准答案：**每条消息带幂等键（MsgID），消费端用去重表记录"这个键已生效"**。examples/ex02-idempotent-consumer 的去重表形态是一个**容量受限的窗口**（map + FIFO 淘汰，等价于"最近 N 条内不重复"），exercises/sol-03 则用**时间窗（TTL）**版本（窗口内拦截、过期后允许再消费）。两者结合后的完整规则：

| 规则 | 说明 | 出处 |
|------|------|------|
| 幂等键由生产方生成，随事件走 | 一次业务动作一个 MsgID，重试/重投不变 | ex02 的 `NewEvent` |
| 查重必须在副作用**之前** | `if seen(id) skip; apply(...); mark(id)` | ex02 `ProcessOnce` |
| 去重表必须**共享**（跨实例） | 重平衡后新成员接管旧分区，若各自内存去重表，重复事件会漏网 | ex02 `TestDifferentConsumersShareDeduper` |
| 去重窗口要有界 | 全量记忆 = 内存无限膨胀；时间窗（Redis TTL）比容量窗更接近真实工程 | sol-03 `DedupeWindow` |
| **诚实标注边界**：mark 与 apply 之间的崩溃窗口 | 先 apply 后 mark，崩溃在中间 → 重放时副作用二次发生；先 mark 后 apply，崩溃在中间 → 效果丢失 | ex02 `TestCrashWindowDoubleEffect`、sol-03 注释 |

那条"诚实边界"引出本阶段最常被误解的结论：**单纯去重表 ≠ exactly-once**。消费端去重只能挡住"已成功投递的重复副本"，挡不住"第一次副作用与记账之间崩溃"的窗口。要做到"效果恰好一次"，必须让副作用与记账原子化——事务内"落库 + 记幂等键"（见 3.9 的 outbox），或副作用本身幂等（写同一状态、同值覆盖）。工程现实是：**能用幂等副作用就用幂等副作用，其次 outbox，把"真 exactly-once"当成少数场景才值得付的代价**（展开见 4 章）。

**幂等目标的三个实现层级**，按成本从低到高，多数系统停在第一或第二层：

| 层级 | 做法 | 谁负责 | 能挡住什么 | 挡不住什么 |
|------|------|--------|-----------|-----------|
| 幂等副作用 | 副作用本身"重复执行结果相同"（同值覆盖、状态机推进、唯一键 upsert） | 业务方 | 乱序旧值回退、重复 apply 同一结果 | 副作用带计数/追加类语义时无法幂等 |
| 幂等表/去重键 | 处理前查重、成功后记账（MsgID 窗口） | 消费端 | at-least-once 投递产生的重复副本 | mark 与 apply 之间的崩溃窗口 |
| outbox / 事务 | 副作用与记账在同一个 DB 事务 | 架构 | 上面两层叠加后仍剩的窗口期 | 跨多个独立系统（需要 saga，超本阶段范围） |

工程上最划算的组合往往是：**对"写状态/upsert"类副作用直接做幂等（第一层）**，把幂等表（第二层）留给"追加/计数/调用外部不可幂等接口"的事件；只有金额等强敏感场景才值得把 outbox（第三层）做成基础设施。反过来，把三层全压在"消费端多写几行 if"上是低估了窗口期的复杂度——诚实认识每一层的边界（本阶段 examples/ex02 与 sol-03 的注释反复强调这条），才不会在生产事故里发现"我以为去重了"。

> 幂等键的**生成端纪律**：MsgID 必须在业务动作发生时就确定（下单号、采样序号、UUID），并随事件完整传递；消费端若用"消息内容哈希"当幂等键，一旦字段演化（3.8）哈希就变，去重失效。幂等键是事件的出生证明，不是消费端的临时计算。

### 3.6 重试与死信队列

消费端的处理动作可能失败：下游超时（**可重试**）、数据损坏/语义永远不对（**毒消息，重试无意义**）。把两者混为一谈是消费端最常见的错误——毒消息重试 N 次只会空转浪费，可重试错误只试一次就放弃又会把"瞬时抖动"误判为永久失败。examples/ex03-retry-deadletter 实现了一个**有界重试 + 死信的有穷状态机**：

```text
Processing ──失败(可重试)──▶ RetryWait(退避) ──▶ Processing ──成功──▶ Done
     │                          ▲
     └──失败(毒消息/次数耗尽)──▶ Dead（进死信队列，附原因）
```

状态机的三条参数与两条分类纪律：

| 设计点 | 建议 | 出处 |
|--------|------|------|
| 最大尝试次数 | 有界（如 3~5），且**退避**（指数或线性）——重试不是立刻再来，是给下游喘息 | ex03 `Config.MaxAttempts/Backoff` |
| 错误分类 | 用哨兵错误 + `errors.Is`：毒消息（decode 失败/schema 不支持）立即死信；其余视为可重试 | ex03 `ErrPoison`/`Retryable`、project `ErrDecode/ErrSchema` |
| 死信带原因 | DLQ 条目记录原始消息 + reason + attempts——排查"上游质量"与"下游故障"走不同路径 | ex03 `DLQEntry` |
| attempts 随消息走 | 重投到 retry topic 时 payload 里 attempts+1，多实例接管能续算 | sol-04 `Job.Attempts` |
| 补偿可重放 | 死信队列保留原始载荷，修复后能把消息重投回主流程 | project `DeadLog` |

exercises/sol-04 换了一种落地形态：失败消息**重新入队**（attempts 随消息流转，等价于真实工程的重试 topic / 延迟队列），达到上限才进 DLQ。它与 ex03 的进程内重试互补——ex03 适合"一次拉取内的小抖动"，sol-04 适合"失败要离开当前批次、由专用重试队列接管"的场景。**真实工程里 retry topic 与 DLQ topic 往往是消息系统里最需要被监控的 topic**（3.7 的水位监控应覆盖它们）。

**重试的三个进阶注意**：① **退避要加抖动（jitter）**——组内 N 个成员同时处理失败，若无抖动，它们会在同一时刻一起重试，把刚缓过来的下游再次压垮（错峰重试是分布式的基本功）；② **重试与幂等不能互相抵消**——重试的每条消息仍是"同一条事件"，成功路径上幂等表（3.5）照常拦截它的重复副本；③ **重试次数是"额度"不是"承诺"**——超过上限进 DLQ 不是失败，是"把问题移交给更慢的补偿通道"，DLQ 的增长曲线应该挂上 3.7 的监控，长期只进不出的 DLQ 等于把故障藏起来。

### 3.7 积压处理与监控

积压（backlog）的本质是**生产速率 > 消费速率**，观测指标是**积压水位（consumer lag）**：对每个分区，`lag = 高水位(HighWater) − 已提交 offset`——即这个分区还有多少条没被消费。examples/ex06-backlog-watch 把"生产快于消费 → 积压爬升；上游停写 → 消费者追平"压成确定性模拟，并实现了一个带**边沿触发告警**的水位观测器：

```text
step  9  HW=[27 27] committed=[18 18] lag=[9 9] total=18  ⚠️ 有分区越过阈值
step 15  HW=[30 30] committed=[30 30] lag=[0 0] total=0   ← 上游停写，消费者追平
```

lag 指标回答了三个运维问题：

| 问题 | 答案 | 动作 |
|------|------|------|
| 消费是不是跟不上了？ | 单分区 lag 持续上升（而不是趋于 0） | 先看**单分区** lag——一个分区卡住（毒消息反复失败）会拖住整组 |
| 积压来自哪一侧？ | 上游涨得快（topic 高水位暴涨）还是下游处理慢（lag 在低水位时仍涨） | 上游限流/削峰；下游扩消费者组或加分区 |
| 积压要不要干预？ | 超过阈值（如"落后 X 分钟"）才告警 | 见下方降级策略表 |

**降级与扩容策略**：lag 达到阈值时按顺序尝试——① 扩消费者组实例数（并行度上限 = 分区数，**组内成员数超过分区数不增加吞吐**，只会空转——分区数在设计时就要按峰值吞吐预留）；② 排查单分区毒消息（进 DLQ 放行其余）；③ 对可降级的下游（告警/报表）临时关闭或降采样，保住关键路径。真实系统里"监控 lag"通常由 exporter 周期性读取 broker 的 group offset 元数据并暴露给 Prometheus（监控接线属 ph12 可观测性，语义与本例的 Watcher 一致）。

**lag 的两种标尺与两个邻居指标**：lag 条数要除以消费速率才等于"落后多少秒"——`lag(条) / 每秒消费速率 = 落后秒数`，告警阈值按"落后秒数"定比按条数定更贴近业务（数据处理有保鲜期）。跟 lag 一起看的还有两个邻居：**uncommitted 时间**（一条消息多久没被提交，抓"卡住的消费者"）与 **topic 保留期 vs 消费追赶耗时**——若追平时间超过消息保留期，积压等于永久丢失，那就不是"扩容能解决"而是"必须重建消费"了。ex06 的模拟只演示了单分区 lag 的数学关系，把它 ×分区数、÷速率，就是真实运维面板上的那张图。

### 3.8 事件 schema 版本管理（兑现 ph18 预告）

这是 ph18 埋得最正式的一条引子——**ph18 3.8 的 protobuf 兼容规则在消息队列里的同类问题**。REST/gRPC 的兼容纪律在异步世界的迁移：

| ph18 同步契约的纪律 | 迁移到消息队列后的形态 |
|---------------------|----------------------|
| 响应字段只增不删 | **事件字段只增不删**；老消费者用老结构解析新事件，多余字段被忽略（JSON）或按字段号跳过（protobuf） |
| 消费者是"客户端"，版本演进向前兼容 | 事件场景 producer 往往**先升级**（采集端先发新 schema），消费者可能滞后数月——必须保证老消费者读新事件不炸 |
| 版本载体：URI/头/媒体类型 | 事件用**信封（envelope）里的 `schemaVersion` 字段**显式声明，禁止靠"猜字段形状"推断版本 |
| OpenAPI/IDL 是唯一契约源 | schema registry（注册中心）登记每个事件类型的历史版本（Confluent Schema Registry / protobuf registry） |
| 未知错误/字段容忍 | 老消费者容忍**新增字段**；但遇到**未知的未来版本**要显式拒绝（见下） |

examples/ex04-event-schema-versioning 给出最小机制：事件载荷是 `{type, schemaVersion, data}` 信封，payload 用版本化结构编码，老消费者用 v1 结构解析 v2 数据时**新增字段被解码器忽略**：

```go
// examples/ex04-event-schema-versioning/schema.go —— 版本化载荷：v2 = v1 超集（截取）
// 验证环境：go1.25.6，零第三方依赖；验证状态：已验证（go1.25.6 本机实测全绿）

type TelemetryV1 struct {
	DeviceID string  `json:"deviceId"`
	TS        int64   `json:"ts"`
	Speed     float64 `json:"speed"`
}

// TelemetryV2 内嵌 v1：字段天然继承，v2 只是追加，不重写老字段。
type TelemetryV2 struct {
	TelemetryV1
	Lat float64 `json:"lat"`
	Lng float64 `json:"lng"`
}
```

与 ph18 3.8 的 protobuf 对照，事件演进的铁律可以写在同一张表里：

| 事件 schema 规则 | JSON 事件 | protobuf（ph18 3.8） | 违例后果 |
|-----------------|-----------|---------------------|---------|
| 加字段 = 非破坏 | 老消费者解码忽略未知键 | 老 reader 按 wire type 跳过未知字段号 | 无（正确姿势） |
| 删字段 = 破坏 | 老数据缺键 → 新消费者读零值/缺省 | 删号必须 reserved | 新消费者拿到空值还不自知 |
| **改名 = 删+加** | `lat` 改 `latitude`：解码"成功"但值丢失 | 字段名本来就不是契约（号才是） | JSON 事件里最阴险——语法成功、语义丢失，ex04 演示了 Lat=0 的静默场景 |
| 语义漂移 = 破坏 | `speed` 单位从 km/h 变 m/s，字段名没变 | 同左 | 编译不报错，全链路数值错 |
| 未知未来版本 | 显式拒绝，别用旧结构硬解析 | 同左 | 拿旧结构解释新语义 → 脏数据进库 |

ex04 的示范输出把"老消费者读 v2 无损"与"未知 v9 显式拒绝"摆在一起；project 把 schema 校验接进了真实消费链路——数据集里那条 `schemaVersion: 9` 的事件在 `process.Process` 里被判毒、进死信、reason 为 `schema`。**未来版本策略的工程答案**：不能解析 ≠ 丢弃——把原始消息（raw）转存（DLQ/归档 topic），等配套消费者上线后再补处理；schema registry 里登记"哪个 producer 从何时起发 vN"，消费端上线排期才能有理有据。

> 本阶段处理的是**事件字段/版本在消息侧的同一条纪律**；schema registry 的服务化部署（注册中心、兼容性检查 API、跨团队审批流）本质是把 ph18 的 spec-first 搬到消息世界，属于工程化展开，本阶段以最小机制（信封 + 版本化结构 + 显式拒绝）为核心。消息的发布治理（谁在灰度期间发新 schema）属 [ph20 配置管理与发布策略阶段](../ph20-config-release/20-config-release.md)。

**schema 演进的两种升级次序**，与同步 API 的"先改服务端还是先改客户端"同构但方向相反：

| 升级次序 | 谁先 | 兼容方向 | 风险 |
|---------|------|---------|------|
| producer 先行（先发新 schema） | 采集/上游先升级 | 老消费者用老结构读新事件（加字段）——3.8 主推形态 | 老消费者若需要新字段做正确性判断，会读到"缺失"的零值 |
| consumer 先行（先读新 schema） | 下游先升级 | 新消费者读老事件：新字段落零值/缺省 | 新逻辑若把"缺省"当"真实值"处理（把 0 速当静止），语义就错了 |

两条次序的共性纪律：**字段缺失的零值必须是无害的**——新消费者读老事件时，把"字段没出现"当作"该字段无意义"而不是"该字段取值 X"。project 的快照合并里专门按 `e.TS >= v.LastTS` 才覆盖，就是防止"缺字段的老事件回退新状态"这类零值陷阱。**topic 的保留策略与事件重放**（把整条流从头读一遍）也要放进版本规划：重放用的老事件可能与当前 schema 差了好几个版本，消费端必须能按信封里的 schemaVersion 逐条选择解码器，而不是假设"topic 里的消息都是最新格式"。

### 3.9 事件驱动架构与可靠事件流模式

事件驱动架构（EDA）的核心转移是：**服务不再"调用"别的服务，而是"发布它已经发生的事实"**——下单服务不调用库存服务扣库存，而是发布 `OrderPlaced` 事件，库存/支付/通知各自订阅、各自处理。这个转移带来解耦，也把两个问题甩给了架构师：

**问题一：本地事务与发消息不能原子**。经典陷阱：先写库 `INSERT order` 成功，再发 `OrderPlaced` 到队列，结果发消息瞬间进程崩溃 → 订单在库里、事件没发出去，下游永远不知道。反过来先发消息再写库，又可能消息到了下游、库没写成（脏事件）。解法是 **outbox 模式**：

```text
业务事务                       独立的投递器（relay）
┌───────────────┐  commit  ┌──────────────────┐
│ 业务表         │          │ outbox 表         │──定期扫描──▶ 消息队列
│ INSERT order  │◀────────▶│ INSERT event      │  （发完标记已投递）
└───────────────┘  同一事务 └──────────────────┘
```

业务表和 outbox 表在**同一个数据库事务**里写入：库提交成功，事件一定在 outbox 里；投递器（relay）扫描未投递行、发布到消息队列、标记已投递。崩溃恢复后重扫即可——**用"先落库、后投递、可重扫"把"本地提交"与"消息发布"变成最终一致**。CDC（变更数据捕获）是把 outbox 进一步外包给数据库 binlog 的形态（如 Debezium）。反模式对比：把"发消息失败"塞进 `defer` 或忽略错误返回 = 静默丢事件，是 outbox 要消灭的头号 bug。

**问题二：消费端处理失败时，事件流不能停**。3.6 的重试/死信在这里定形为**可靠消费模式**：处理成功才提交/ack；毒消息进 DLQ；DLQ 与重试 topic 都挂监控（3.7）。当一次消费需要更新多个系统的状态时，还引出**流程编排**问题（saga/编排）——那是分布式事务的专题，超出本阶段范围，本阶段只建立"单事件消费要有幂等、重试、死信三重护栏"的底线认知。

**两种触发式消费的边界**也要说清：请求-应答式（RPC，ph11/ph18）适合"我需要一个结果"；事件流式（本阶段）适合"我要广播事实"。混合使用时的常见错误是**把请求-应答塞进消息队列**——用 MQ 做 RPC 会同时失去 RPC 的超时/错误模型与 MQ 的吞吐优势（NATS 的 request-reply 是特意为轻量内部调用保留的例外）。选型判断见第 5 章。

**消息承载的两种内容要分清：事件 vs 命令**。这个区分决定消费端怎么处理失败与重试：

| 维度 | 事件（event）：描述已发生的事实 | 命令（command）：表达想让它发生的意图 |
|------|-------------------------------|--------------------------------------|
| 命名惯例 | 过去时/完成时：`OrderPlaced`、`DeviceTelemetryReported` | 祈使：`CancelOrder`、`DispatchCommand` |
| 失败后重试是否合理 | 事实已发生，重投的应是"同一事实"，消费端幂等即可 | 意图可以重试，但要小心"命令是否已被执行过"（同样靠幂等键） |
| 谁有权消费 | 任何关心该事实的下游 | 通常一个"该做这件事"的执行者 |
| 常见错误 | 把"我要你做什么"当事件发出去（事实还没发生就说它发生了） | 把"已完成"当命令（执行者收到两遍就再做两遍） |

> 事件驱动的建模深度（事件溯源、CQRS、领域事件设计）是进阶专题，本阶段只建立"发事件前先问：这是已发生的事实吗？"这条判断线；数据一致性的流程编排（saga/outbox 之上的分布式事务）超出本阶段范围，3.9 的 outbox 到"跨系统 saga"之间还有相当一段路，留给真实项目按需学习。

| 客户端 | 安装 | 消费核心 | 语义要点 |
|--------|------|---------|---------|
| segmentio/kafka-go | `go get github.com/segmentio/kafka-go@latest` | `kafka.Reader`（`ReadMessage` + `CommitOffsets`） | 组/offset 由 broker 管理；分区键决定保序 |

| rabbitmq/amqp | `go get github.com/rabbitmq/amqp091-go@latest` | `Channel.Consume` + `Ack`/`Nack` | ack 前崩溃消息回队；prefetch 控吞吐 |

```go
// kafka-go 消费循环示意（真实 broker 环境；本仓库离线形态见 examples/ex01）
// 验证环境：需本地 Kafka（docker run -d -p 9092:9092 apache/kafka:3.7.0）
// 验证状态：未在本环境验证（无 broker/Docker，命令可复现）

r := kafka.NewReader(kafka.ReaderConfig{
	Brokers: []string{"127.0.0.1:9092"},
	Topic:   "fleet.telemetry.v1",
	GroupID: "fleet-consumers",
})
for {
	m, err := r.ReadMessage(ctx) // 拉一条
	if err != nil {
		break // 网络/上下文错误：退出由上层重连
	}
	if err := processEvent(m.Value); err != nil { // 你的业务（幂等/重试/死信）
		handleFailure(err) // 进 DLQ 或重试 topic
	}
	if err := r.CommitMessages(ctx, m); err != nil { // 处理完再提交 = at-least-once
		handleCommitError(err)
	}

```

三条 Go 侧实践提醒：① **提交时机就是可靠性语义**——把 `CommitMessages` 放在副作用成功之后（对照 3.3 的表）；② 每个 Reader 内部自带重连/重平衡，你的代码只需要处理"处理失败"与"提交失败"两类错误，别在库之上再套一层脆弱的重连；③ 生产侧 `Writer` 的 `Balancer` 默认按 key 哈希——**想保序就不要覆盖它**。

> 客户端库的完整 API（Reader 的水位查询、NATS 的 JetStream 消费者、amqp 的信道复用规则）随版本演进较快，本阶段按需查阅官方文档即可；示例/练习/项目里离线实现的核心语义（提交、去重、分类、水位）在任何客户端上都是同一套，学的是"怎么设计消费端"而不是"某个库的按钮在哪"。

## 4. 底层原理

**Kafka：分区日志的存储与复制语义。** 一个分区的背后是一个目录下的多个**日志段（log segment）**文件：新消息先写活跃段，段满滚动为只读段并最终按保留策略清理——这就是"日志"在磁盘上的样子，offset 即段内字节偏移的抽象。高吞吐的秘密在顺序写与批量：producer 端攒批（batch）、broker 端顺序落盘、consumer 端顺序读。**副本与 ISR**：每个分区有 1 个 leader 与若干 follower，follower 从 leader 拉取日志追赶；跟不上（落后超时）的 follower 被踢出 **ISR（In-Sync Replica）**，leader 只在 ISR 内选。**ack 语义**是可靠性在写入侧的分级开关：

| ack 配置 | 行为 | 可能丢消息的场景 | 吞吐 |
|---------|------|----------------|------|
| acks=0 | 发完即认为成功 | broker 没收到/宕机 | 最高 |
| acks=1 | leader 落盘即确认 | leader 确认后、follower 复制前 leader 宕机 | 中 |
| acks=all（-1） | ISR 全部落盘才确认 | 无（ISR 全挂属于降级而非丢消息） | 最低 |

**"已提交"的水位语义**：consumer 能看到的消息上界是 **high watermark**（ISR 中最小的 LEO），leader 宕机切换后 follower 可能没有最后几条（未达高水位）——所以 consumer 从高水位读，天然只读到"已复制到 ISR 的消息"。`lag = high watermark − 提交 offset`（ex06 观测的就是这条式子）在底层对应：高水位由 broker 维护、提交 offset 由消费者组维护、两者之差即积压。

**吞吐的底层是"攒批 + 顺序"这对组合**：producer 端把多条消息攒成一个 batch 再发（减少网络往返），broker 把 batch 顺序追加进日志段（避免随机写），consumer 端按 batch 顺序读、自己再攒取（fetch.min.bytes/max.poll.records 等参数控制单次拉取量）。所以"一条一条同步发、等 ack"在 Kafka 上是最慢的用法——Go 侧 kafka-go 的 Writer 默认带 batch 缓冲，练习代码里理解"生产端可以攒批、消费端可以批量提交"就够了，不需要背参数。acks=all 之所以比 acks=1 慢，本质也在这：每批要等 ISR 全部落盘才返回，把"顺序写"变成了"顺序写 + 网络确认"。

**NATS core：内存中的主题路由。** NATS core 没有磁盘、没有 offset，broker 维护的是一棵 subject 树与订阅表：发布一条 `fleet.car-001.telemetry` 时，服务器沿 token 树做模式匹配（`*`/`>` 通配与订阅表求交），把消息**扇出**给所有命中订阅者；订阅者是**慢消费者**时，服务器按固定缓冲尽力投递，满了就丢（不背压生产者）——这就是 at-most-once 的物理含义。

**JetStream 把 NATS 从总线补成流存储**：每个 stream 是持久化日志（按 subject 过滤存储，类似 topic），消费者在 stream 上创建 deliver 位置（类似 Kafka 的 offset），支持 ack、重放、死信。心智可以这样对照：**NATS core = 内存扇出总线（RabbitMQ 瞬态队列的轻量版）；JetStream = 给 NATS 穿上 Kafka 的分区日志 + 消费者游标**。选型时想清楚要的是"低延迟即时分发"还是"可回放持久流"，前者 core 就够（还少一份存储成本），后者才上 JetStream。

**RabbitMQ：确认机制是可靠性的核心旋钮。** AMQP 0-9-1 的消费是**拉一条、ack 一条**的显式确认模型：消费者 `basic.consume` 后收到消息，处理完回 `basic.ack`，broker 才真正删除消息；若连接断开前未 ack，消息**重新入队**交给下一个消费者（这正是 at-least-once 的队列版）。三个旋钮各有语义：**prefetch（QoS）**限制信道上未 ack 的消息数（防止消费者内存被灌爆）；`basic.nack`/`reject` 可让消息重回队列或进死信交换机；**publisher confirms** 让生产侧知道消息真的进了 broker。对照 Kafka：Kafka 的"分区 + 提交 offset"把"消息归谁处理、处理到哪"变成持久状态；RabbitMQ 的"队列 + ack"把同一职责放在队列与连接的生命周期里——所以 RabbitMQ 消费者崩溃后消息回队，Kafka 消费者崩溃后靠 offset 续读，机制不同、at-least-once 的结论相同。

**exactly-once 的工程现实。** 三个层的"一次"分别可达成：producer 幂等（Kafka 幂等生产者用 PID+序号去重，防 producer 重试导致的重复）；broker 事务（跨分区的原子写入）；消费端"效果恰好一次"——**最难的一层**。消费端 exactly-once 需要"读消息 + 写结果"原子化：Kafka Streams/流处理器用"结果写进与 offset 提交同一个事务"达成；普通 Go 服务通常做不到跨系统事务，落地的近似方案有三：① **幂等副作用**（写同值覆盖/状态机，重复执行结果相同）；② **消费端幂等表**（3.5，挡住重复投递副本）；③ **outbox/事务内记账**（3.9，把"副作用 + 记键"放进同一 DB 事务，从根上消灭窗口期）。真实工程的口径是：**默认接受 at-least-once + 幂等消费，只有"下游无法幂等且金额/状态敏感"时才为 exactly-once 付出事务代价**。

## 5. 使用场景

**什么时候引入消息队列**（而不是继续用同步 HTTP/gRPC）：

| 场景 | 信号 | 不用它的替代 |
|------|------|------------|
| 削峰填谷：流量瞬时冲高、下游扛不住 | 采集峰值 >> 处理均值 | 限流 + 丢弃（ph09）若可接受少量丢 |
| 广播：一次业务动作多个下游各自反应 | 下单要同时触发库存/支付/通知/风控 | 同步逐个 RPC（延迟与耦合爆炸） |
| 解耦与独立伸缩：上下游发布节奏不同 | 上游发版不想等下游，下游要独立扩容 | 紧耦合接口（ph18 会放大契约问题） |
| 数据流管道：采集→清洗→存储→分析 | 持续不断的流水，天然按分区/顺序消费 | 批处理（周期脚本）若可容忍延迟 |
| 回放/审计：历史事件要能重放 | "当时的输入"值得永久保留 | 只留结果不留过程 |

**什么时候别上消息队列**：单个同步调用就能完成且不需要解耦（引入 MQ 只会增加"至少一次 + 积压 + 运维"三份复杂度）；需要"请求有明确响应与错误码"的交互（用 RPC/HTTP，ph11/ph18）；数据量小且延迟敏感（直接用缓存/直连）。**"用 MQ 做 RPC"**与**"所有服务间通信都走 MQ"**是两个高频反模式——前者失去错误模型，后者让调用链变成不可调试的事件因果网。

**三款选型决策表**：

| 你的核心诉求 | 选 | 理由 |
|------------|-----|------|
| 高吞吐事件流、多下游独立消费、按实体保序、可回放 | **Kafka** | 分区日志 + 消费者组是这个模型的唯一正统 |
| 云原生服务间的轻量即时消息、pub/sub/请求应答、低延迟 | **NATS** | 简单到极致；JetStream 再补持久化 |
| 任务队列、灵活路由（按 routing key 分发）、经典企业集成 | **RabbitMQ** | exchange + ack + DLX 是任务分发最成熟的组合 |
| 已用 Kafka 但只想跑批作业、对延迟不敏感 | Kafka（批） | 不要为批处理引入第二种 broker |

**与其它语言同类机制的对比**（为 analysis/ 与 Tenet 合成积累素材）：

- Java：Kafka 生态的原乡——Spring Kafka/Streams、Confluent 工具链最全，消费端习惯用框架注解；Go 无同等"框架化"传统，kafka-go/原生循环更接近"标准库风格"，消费语义（提交/重试）由你自己的代码显式表达——显式对可测试，但也要求纪律（这正是本阶段练习的意义）。
- Python：kafka-python/confluent-kafka 消费端惯用回调/后台线程，幂等与重试常交给库或框架；Go 的"拉取→处理→提交"显式循环与之对照鲜明。
- Rust（rdkafka）：API 与 C 库绑定，语义细节最接近底层；rskafka 等纯 Rust 实现方兴未艾——语言社区差异主要在"封装多少"而非"消息语义不同"。
- 所有语言共享同一套消息系统语义（分区/offset/ack/lag），差异全在客户端 API 封装度——**语义知识跨语言可迁移**，这是本阶段花大力气讲"模型"而不是"库函数"的原因。

**反模式清单**（看到即警惕）：消费端假设消息不重复（不设幂等）或把去重表放进程内（重平衡后失效）；把时间戳当分区键（同实体乱序，3.4）；毒消息与瞬时故障一起无限重试（队列被卡死，3.6）；无界死信（DLQ 只进不出、无监控，3.7）；改了事件字段不升 schemaVersion、甚至直接改名（3.8）；"先发消息后写库"的本地事务撕裂（3.9 outbox）；消息系统里的消息越做越大（把事件当 RPC 请求体使）。

```go
// examples/ex01-consumer-group-semantics/group.go —— 组级提交：只前进不回退（截取）
// 验证环境：go1.25.6，零第三方依赖；验证状态：已验证（go1.25.6 本机实测全绿）

// Commit 提交「已处理到 next」：只前进不回退。offset 单调是 at-least-once
// 落地的关键——处理完、提交成功，才算这一条真正"出账"。
func (g *Group) Commit(partition, next int) {
	g.mu.Lock()
	defer g.mu.Unlock()
	if next > g.committed[partition] {
		g.committed[partition] = next
	}
}
```

读懂一个消费服务的输出，也是本阶段的练习。project 的报表长这样，每个数字都能对上账本：

```text
读取 36 条：真实生效 31，重复投递拦截 3，内部重试 1 次
死信 2 条（毒消息 2 + 重试耗尽 0），最大积压 13 条
终态积压：0 条（应归零）
```

- `真实生效 31 = 5 台设备×6 条 + 1 条抖动设备`：重复投递与死信都没有污染副作用计数（幂等表生效）
- `拦截 3 = 数据集里 3 条同 MsgID 重放`：at-least-once 的重复被去重表挡住
- `死信 2 = 1 条坏载荷(decode) + 1 条未来 schema(schema)`：毒消息分类正确、未浪费重试
- `内部重试 1`：抖动设备先失败一次再成功（可重试路径被真实走到）
- `终态积压 0`：消费者追上高水位——lag 归零是"处理完了"的可检验定义

## 7. 总结

### 关键要点

- 消息系统共性是"生产者→通道→消费者"，分水岭在通道对消息的态度（持久/路由/确认）；Kafka 分区日志、NATS subject、RabbitMQ 队列是同一问题的三种解法（roadmap 学习内容：Kafka/NATS/RabbitMQ 的模型差异）
- **消费者组（roadmap 必会概念 1 的地基）**：一个分区同一时刻只归组内一个成员；组在 broker 记 offset；处理完再提交 = at-least-once，提交时机即可靠性语义；重平衡时成员抖动是消费停滞的常见元凶
- **消息至少一次投递意味着消费者要幂等（roadmap 必会概念 1）**：MsgID 幂等键 + 去重表（容量窗或时间窗），查重在副作用前、去重表跨实例共享、窗口有界；诚实边界：mark/apply 之间的崩溃窗口需要 outbox/事务才闭合
- **分区影响顺序性和并行度（roadmap 必会概念 2）**：分区内有序、全局无序；key 用稳定业务标识（实体 ID），用时间戳/随机数当 key 会让同实体乱序；组内并行度 = min(分区数, 成员数)
- 重试与死信：毒消息（decode/schema）不重试立即死信，可重试错误有界 + 退避，DLQ 带 reason 与原始载荷可重放；attempts 随消息走、多实例可续算
- **积压需要监控和降级策略（roadmap 必会概念 3）**：lag = 高水位 − 提交 offset，单分区 lag 才是定位线索；扩实例的并行度上限是分区数，分区数要按峰值吞吐预留
- **事件 schema 需要版本管理（roadmap 必会概念 4，兑现 ph18 预告）**：信封显式带 schemaVersion，字段只增不删、改名/删除/语义漂移是破坏，未知未来版本显式拒绝转存；消费者滞后于 producer 是常态，向前兼容是硬要求
- 可靠事件流：outbox 把"本地事务 + 发消息"做成可重扫的最终一致；exactly-once 的工程现实是"幂等副作用 > 幂等表 > 事务"，默认接受 at-least-once + 幂等消费

### 跨语言对比

- 消息系统语义（分区/offset/ack/lag/消费者组）跨语言完全共享，差异只在客户端 API 的封装度：Java 有框架化传统（Spring Kafka 注解消费），Go 保持"拉取→处理→提交"的显式循环——显式带来可测试与可控的提交时机，代价是纪律必须自己守（为 analysis/ 与 Tenet 合成积累素材）
- Kafka 把"消费进度"做成 broker 侧持久状态（offset），RabbitMQ 把同样职责放在"队列 + 连接 + ack"的生命周期里，NATS 干脆不承诺（除非 JetStream）——三个系统对"投递可靠到什么程度"的哲学取舍，正好映射三种工程文化：流处理（Kafka）、云原生轻量总线（NATS）、经典企业集成（RabbitMQ）
- 幂等与 schema 版本纪律与 ph18 完全同构：REST 幂等键 ↔ 消息 MsgID 去重、响应字段只增不删 ↔ 事件字段只增不删、OpenAPI ↔ schema registry——异步世界没有把同步世界的纪律推翻，只是把"客户端"换成了"消费者"
