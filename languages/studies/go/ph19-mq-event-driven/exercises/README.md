## 练习 1：Kafka 消费车辆数据（★★★）

**目标**：实现一个"Kafka 语义"的车辆遥测消费端并跑通全流程：一个 3 分区的 topic 里写入一批按 `vehicleID` 分区的遥测事件，消费者组并行消费后在按车统计表里聚合出每辆车的采样数/最大速度，且全程**无重复、无遗漏**。

**要求**：
- 自己实现最小分区模型（或复用笔记/示例的语义）：`key → 分区` 稳定散列、offset 单调、消费者组分配"每分区恰好一个成员"
- 消费者组至少 2 个成员并行消费各自分到的分区，共享同一统计表（考虑并发安全）
- 消费位置要提交（组级 offset），并提供一个测试证明：同一组内换一个成员接管后只读新增消息、不重放已提交消息
- 载荷用 JSON（含 vehicleID/ts/speed 等字段），解码失败必须以 error 浮出（不能静默丢弃）
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；测试断言①总消费条数=总生产条数、②每车 samples=该车生产条数、③分配不变量、④续读不重放、⑤坏载荷报错

**提示**：sol-01-kafka-consumer-vehicle-data 参考实现。分解建议：先写纯逻辑（散列/分配/提交），再写消费循环，最后写统计表——表用锁保护是因为组内成员并行写。真 broker 版：`go get github.com/segmentio/kafka-go@latest`，用 Reader(GroupID) 替代自己的分区消费循环，offset 提交语义不变。

## 练习 2：NATS 发布订阅 demo（★★）

**目标**：实现一个离线 NATS core：subject 分层与通配（`*` 单级、`>` 尾部任意）、发布-订阅扇出、队列组（queue group）任务分摊、请求-应答（`_INBOX`）。

**要求**：
- `Matches(subject, pattern)` 判定做成纯函数并配一张表格测试（精确 / `*` / `>` / 否定情形至少各 2 例）
- 普通订阅：同一条消息每个订阅者各收一份（fan-out）；队列组：同一 subject 多个成员只一人收到且轮询均摊（连发 N 条每个成员收到 N/成员数，误差不超过 1）
- 请求-应答：服务端订阅某 subject 回执，客户端经 reply 地址拿回应答，带 context 超时
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；测试断言扇出数量、队列组"一人一份+均摊"、请求-应答往返、退订后不再收到

**提示**：sol-02-nats-pubsub-demo 参考实现。注意通配语义：`*` 只匹配一级、`>` 只能放末尾且匹配剩余全部；队列组轮询需要按订阅者 id 排序，否则 map 遍历顺序会让分摊失去可复现性。真 broker 版：`go get github.com/nats-io/nats.go@latest` + `docker run -d -p 4222:4222 nats:2.10`，用 `SubscribeSync`/`QueueSubscribe`/`Request` 对照。

## 练习 3：实现幂等消费（★★★）

**目标**：实现一个时间窗去重的幂等消费者：broker 承诺 at-least-once（同一 MsgID 可能被重复投递），你的消费端保证**副作用只生效一次**。

**要求**：
- 去重表语义为"TTL 窗口"：窗口内重复键跳过，过期后同键可以再次消费（不是永久黑名单）；并发安全，`查重+记账` 必须原子（并发重复投递也只生效一次，可加 `-race` 验证）
- 时钟可注入：测试里能自由推进"现在"，不依赖真实时间
- 副作用失败时本次记账要能回滚（这样消息重投后可以重试成功），并在注释里诚实说明：预约与生效之间崩溃仍可能丢/重放，真 exactly-once 需要 outbox（见主文档 3.9）
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；测试断言①窗口内重复被拦、②过期后可再消费、③并发重复只生效一次、④失败回滚后可重试成功

**提示**：sol-03-idempotent-consumer 参考实现。难点在"记账时机"——先记账后副作用（失败回滚）与先副作用后记账（崩溃窗口重放）各有利弊，想清楚再写注释。真工程去重表落 Redis（SETNX+TTL）或 DB 唯一约束，本练习用进程内 map 即可。

## 练习 4：处理重试和死信（★★★）

**目标**：实现"重投 + attempts 计数"式的重试/死信处理：处理失败的消息带着已试次数重新入队，达到上限或遇到毒消息（poison）进死信队列，并给出 DLQ 条目的原因分类。

**要求**：
- 错误分两类：可重试（如下游超时）与毒消息（解码失败等重试无意义）——用哨兵错误 + `errors.Is` 区分，禁止字符串匹配
- attempts 随消息流转（重投不丢计数），同一 Job 重放给"另一个实例"能续算；每条消息的尝试次数互不干扰
- 退避等待器可注入（测试不真睡），并记录退避调用次数
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；测试断言①抖动后成功（重试次数正确）、②永久失败打满上限进 DLQ 且 attempts 正确、③毒消息一次即死信不浪费重试、④多条作业独立结算

**提示**：sol-04-retry-deadletter 参考实现。真实工程里"重投"通常是发回 retry topic / 延迟队列，payload 的 attempts 字段 +1——所以计数放消息里而不是进程内存里。毒消息与耗尽死信的 DLQ 条目要有不同 reason（两类问题的排查路径不同）。
