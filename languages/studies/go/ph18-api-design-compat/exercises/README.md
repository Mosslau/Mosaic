# ph18 API 设计与兼容性练习

> 先自己做，再对照 `sol-*` 参考实现。三题与 roadmap §18 对齐：练习 1 ↔「设计设备查询 API」、练习 2 ↔「设计统一错误结构」、练习 3 ↔「为接口补 OpenAPI 文档」。
> 参考实现零第三方依赖，验证环境 go1.25.6（darwin/arm64），每条验收都能用 `go build ./... && go test ./... && go vet ./...` 检查——注意：参考实现已标注「已验证」（go1.25.6 本机实测 vet/build/test 全绿）；练习验收以你自己本机跑出的结果为准。

## 练习 1：设计设备查询 API（★★★）

**目标**：从零设计并实现一个"经得起演进"的设备查询 REST 接口，覆盖过滤、分页、排序、单对象查询四种能力。领域自选（设备、传感器、IoT 网关……），但设计约束如下。

**要求**：
- 至少两个端点：列表（支持查询参数）+ 单对象查询（路径参数）
- 过滤：至少一个枚举精确过滤（值域写进注释，如 `online|offline|maintenance`）+ 一个文本模糊过滤
- 分页：offset + limit；必须定义并实现"缺省值 / 上限值"（如 limit 缺省 20、最大 100），非法参数（负数、超值域枚举）回 400
- 排序：白名单字段排序 + 同值决胜字段（保证翻页不重不漏）；白名单外的排序请求怎么处理，你要给出并注释理由
- 响应 envelope：`{items,total,offset,limit}`，total 是**过滤后**的总数
- 过滤先于分页（total 才语义正确）；所有规则集中在可脱离 HTTP 单测的纯函数/纯逻辑里

**验收**：
- 表驱动测试覆盖：翻页不重不漏（把全量数据翻完断言并集 = 全集）、过滤正确、排序稳定、limit 截断/缺省、非法参数 400
- 每个设计决策（为什么 status 值域是这三个、为什么决胜键是 id、为什么未知排序回退默认）都能在注释里找到一句话答案
- `go build ./... && go test ./... && go vet ./...` 通过

**提示**：sol-01-device-query-api 参考实现（设备 fleet 场景，57 辆数据、limit 默认 20/上限 100、sort 白名单 + id 决胜）。难点在"纯逻辑与 HTTP 解析分离"——把 `Apply(fleet, q) Page` 做成纯函数后，分页正确性不需要起服务器就能测。

## 练习 2：设计统一错误结构（★★）

**目标**：设计一套**能演进两年**的统一错误结构，并给出错误码文档表。核心约束是 roadmap 必会概念 2 与 ph17 3.6 的承诺："错误结构要稳定""错误码只增不删"。

**要求**：
- 对外 JSON 结构：code/message **必填永在**；requestId/details 作为 v2 追加的可选字段（可选字段缺失时客户端应容忍零值）
- 错误码注册表：集中一处登记，能回答"某个 code 哪一版发布、语义是什么"；用测试钉住"历史发布 code 永不可删"
- Go error 语义完整：错误类型实现 Unwrap，errors.Is/As 能沿链追根因（包装用 `%w`）
- code → HTTP 状态码的映射收进一个纯函数（含未知错误类型兜底 500）
- 写一份**错误码文档表**（code / 何时返回 / 调用方可做什么）——roadmap 验收 3 的"写错误说明"就是指它

**验收**：
- 测试覆盖：老客户端（只认识 code/message 的结构体）解析带新可选字段的响应不炸；注册表包含全部历史 code；包装链 errors.Is/As 可达
- 错误体结构测试：code/message 序列化后永远存在（不带 omitempty 的承诺被测试钉住）
- `go build ./... && go test ./... && go vet ./...` 通过

**提示**：sol-02-error-schema 参考实现（任务管理域：VALIDATION_ERROR/TASK_NOT_FOUND/TASK_CONFLICT/RATE_LIMITED/INTERNAL，errs 包 + httperr 映射包分层）。注意一个坑：code 一旦被客户端写进 if 分支，删除它 = 老客户端把错误当"未知错误"兜底处理——注册表测试就是这条纪律的保险丝。

## 练习 3：为接口补 OpenAPI 文档并锁定同步（★★★）

**目标**：把练习 1（或你自选的接口）的 API 规范补成一份 OpenAPI JSON 文档，并写契约测试让**文档与实现双向同步**——roadmap 必会概念 4：API 文档应和实现同步。

**要求**：
- 手写一份 `openapi.json`（OpenAPI 3.0 表示法；练习要求零第三方，用 JSON 形式即可，真实工程可用 YAML + 工具链）：覆盖全部端点；列表端点的 query 参数写全（名字/类型/枚举/默认值/上限）；所有 2xx 响应带 **example**（别人照抄就能联调）；统一错误结构抽成共享组件并被所有错误响应引用
- spec 中声明的每条路由、每个参数，实现里必须有；反之亦然
- 契约测试至少断言：① spec.paths ↔ 实现路由双向一一对应；② 每个 operation 有 summary；③ Error schema 的 code/message 必填、错误响应全部引用共享错误组件；④ query 参数声明与实现解析的集合一致；⑤ （加分）真实响应 JSON 的字段集合不越出 spec schema 的 properties
- 错误说明要写进文档（每个 code 的 description 或示例），让客户端不读代码也能知道每种错误怎么处理

**验收**：
- 故意做一个"破坏"实验并观察测试变红：给响应结构体加一个未声明字段 / 删一条路由 / 把某参数从实现去掉——契约测试应立即失败，然后还原
- `go build ./... && go test ./... && go vet ./...` 通过

**提示**：sol-03-openapi-sync 参考实现（设备查询 API 的完整 openapi.json + 最小 spec 解析器 + 契约测试）。写文档的次序建议：先列"这个接口承诺了什么"（字段、参数、错误），再动手写代码——spec-first 的价值在于让承诺先于实现存在。
