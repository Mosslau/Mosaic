# ph13 阶段项目：学生管理数据库版

> 对应 Roadmap「ph13 数据库阶段」推荐项目之「学生管理数据库版」；「设备状态存储服务」未落地（选 1 个即可）。把 ph12 的「用户服务」从内存存储升级为**连接池 + Flyway 迁移 + 事务批量导入 + 索引查询**的完整数据库应用。

## 需求

实现一个学生管理服务：注册（姓名/邮箱/年级校验 + 落库分配 id）、按 id / 邮箱查询、改年级、删除、**批量导入**（整批事务，任何一条失败整体回滚）。核心是用本阶段学的全部数据库手段把它做对、做快：**HikariCP 连接池**摊薄建连成本、**Flyway** 管理 schema 演进（V1 建表 / V2 加索引）、**事务**保证批量导入原子性、**索引**让按邮箱查询走 B+ 树而非全表扫描。

工程结构（标准 Maven 布局，纯 Java SE，无框架依赖）：

```text
src/main/java/com/example/students/
├── Student.java          # record：不可变学生实体
├── StudentDao.java       # HikariCP 连接池 + JDBC：CRUD / 按邮箱查 / 借连接（业务事务用）
└── StudentService.java   # 业务：校验 + 单条注册 + 批量导入事务（边界由业务定义）
src/main/resources/db/migration/
├── V1__create_students.sql   # 建表：IDENTITY 主键 + NOT NULL/UNIQUE/CHECK 约束
└── V2__add_email_index.sql   # 加 email 索引（schema 演进 = 新增迁移文件）
src/test/java/com/example/students/
├── StudentDaoTest.java       # 集成测试：池化 CRUD / UNIQUE 约束 / 连接复用 / 执行计划
└── StudentServiceTest.java   # 事务测试：批量导入整批成功 / 中途失败整批回滚 / 校验先于写库
```

## 功能清单

- [x] 注册：姓名非空、邮箱格式合法（含 @）、年级 1~6，落库返回带分配 id 的学生（Java 校验 + 数据库约束双层兜底）
- [x] 查询：`findById` 命中/未命中（`Optional`）、`findByEmail`（走索引）、`findAll` 按 id 有序
- [x] 改年级：返回受影响行数，0 行表示目标不存在
- [x] 删除：返回受影响行数，重复删除返回 0
- [x] 批量导入（事务）：整批「同生同死」——任何一条失败（重复邮箱触发 UNIQUE）整体回滚，不留半批数据
- [x] Flyway 迁移：`flyway_schema_history` 记录 V1/V2，重复运行幂等（已执行版本跳过）
- [x] HikariCP 连接池：串行 200 次借还物理连接数 ≤ 池上限 4（复用证据）

## 验收标准

- `mvn test` 全部通过：**Tests run: 9**（实测：StudentDaoTest 5 + StudentServiceTest 4），Failures 0 / Errors 0
- **事务回滚语义实测**：`importWithDuplicateEmail_rollsBackWholeBatch` —— 批次第 2 条重复邮箱触发 UNIQUE 约束 → rollback 撤销第 1 条已成功的插入，断言表中只留预先插入的那条（原子性直接证据）
- **连接复用实测**：`poolReusesConnections` —— 200 次操作后 `poolStats()` 物理连接总数 ≤ 4
- **索引生效实测**：`emailIndexIsUsedByPlanner` —— `EXPLAIN PLAN FOR` 输出含 `access=INDEX PRED` 且不含 `access=FULL SCAN`（教学点：email 同时有 UNIQUE 隐含索引与 V2 显式索引，优化器选了隐含索引——「见列就建索引」是浪费，UNIQUE/PRIMARY KEY 会自动建索引）

## 测试设计要点（本项目的教学增量）

- **测试顺序即生命周期**：`@BeforeAll` 先建池（常驻连接保住 HSQLDB 内存库——最后一个连接关闭时库才销毁）再 Flyway 迁移，`@AfterAll` 关池；`@BeforeEach` 清表保证隔离——这是「内存库 + 连接池」集成测试的标准姿势
- **事务边界由业务定义**：`importStudents` 里 `setAutoCommit(false)` 到 `commit()` 之间就是「一次批量导入」；先全量校验（快速失败、不触发任何 SQL）再开事务；`finally` 恢复 autoCommit 防池污染
- **业务校验与数据库约束分层**：Java 校验「输入合理」（快速失败、报错友好），数据库 `NOT NULL / UNIQUE / CHECK` 兜底「数据合法」（并发下也无法绕过）——重复邮箱的拒绝是 SQLException 不是 IllegalArgumentException，两层各司其职
- **每个测试一个行为**：测试方法名 `importWithDuplicateEmail_rollsBackWholeBatch` 读起来像句子；错误路径（UNIQUE 冲突、非法输入、目标不存在）与正常路径同样覆盖

## 扩展方向（可选）

- 接真实 MySQL/PostgreSQL：换 JDBC URL 与驱动即可（SQL 为标准 HSQLDB 兼容方言；MySQL 的 `GENERATED BY DEFAULT AS IDENTITY` 要换成 `AUTO_INCREMENT`）——可实测的替代路线是 examples/ex07 的 Testcontainers 概念（需要 Docker）
- 给批量导入补「部分成功」的业务选项：可回滚点（`Savepoint`，JDBC 3.0）让失败行之前的数据保留——对比「全部或全不」与「尽力而为」两种事务策略
- 加 Redis 缓存：`findByEmail` 高频查询先查缓存（Cache-Aside，见 examples/ex05），提升读吞吐
- 引入 MyBatis 接管数据访问（examples/ex06 思路），对比「手写 JDBC vs 半 ORM」的代码量
- Web 化（[ph14 Web 后端开发阶段](../../ph14-web-backend/14-web-backend.md)）：把 `StudentService` 包成 REST API，连接池/事务/校验全部复用——本项目的存储层直接成为 ph14 服务（project/ 的 `DeviceStore`）的数据层
