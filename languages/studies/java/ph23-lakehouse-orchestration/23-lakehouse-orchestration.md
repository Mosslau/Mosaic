## 2. 来源与演变

湖仓不是「数据湖 + 数仓」的营销词，它是**三条工程线索**叠加的结果：**存储要能改、口径要统一、任务要能重算**。**设计哲学一句话：湖仓的核心不是"存得多"，而是"同一份数据既能被反复重算、又能被随时追溯"——为此它必须同时具备不可变的快照、可裁剪的布局与幂等的编排。**

- **数据仓库时代（1990s）**：Inmon/Kimball 把「先清洗再分析」固化为分层（ODS/DWD/DWS/ADS）与口径纪律；ETL 任务用调度器串起来（cron/Control-M），**失败重跑要手工清数据**——这正是「幂等回填」问题的起点（本阶段 3.7）。
- **Hadoop 数据湖时代（2006-2015）**：HDFS 让「先存后算（schema-on-read）」成为可能，代价是**没有事务、没有 schema 演进、小文件灾难**：目录即表，一次失败的重跑留下半份数据，读者看到的是「半成品」。小文件问题（3.3/3.4）就是这一代留下的最大工程债。
- **湖仓一体时代（2018-2022）**：Iceberg（2018 由 Netflix 开源）、Delta Lake（2019）、Hudi 用**元数据层**给对象存储补上 ACID：表 = 快照 + 清单（manifest）列表，提交 = 原子替换当前快照指针，于是有了**时间旅行、增量读、schema 演进**（3.2）——数据湖第一次拥有数仓级的事务语义。
- **批流一体与声明式编排时代（2020-）**：Flink/Spark Structured Streaming 让「同一份口径跑批也跑流」成为主流（3.5 的水位线与迟到数据成为必备概念）；Airflow/Dagster/dbt 把编排从「脚本 + cron」升级为**声明式 DAG + 依赖 + 回填**（3.6/3.7）；数据质量（Great Expectations 类）与血缘/目录（DataHub/OpenMetadata）成为平台标配（3.8）。

| 里程碑 | 年份 | 主要变化 |
|--------|------|---------|
| 数仓分层与 ETL 调度 | 1990s | ODS/DWD/DWS/ADS 分层与口径纪律；重跑靠手工清数 |
| HDFS / MapReduce 数据湖 | 2006~ | schema-on-read 的灵活与「无事务、小文件」的代价 |
| Hive 元数据与分区表 | 2010 | 分区成为一等概念（分区裁剪的起点） |
| Spark / Structured Streaming | 2014~ | 同一 API 覆盖批与流，「批流一体」成为目标 |
| Iceberg / Delta / Hudi | 2018~ | 元数据层给数据湖补上 ACID、时间旅行与 schema 演进 |
| Airflow / Dagster / dbt | 2018~ | 声明式 DAG、依赖与回填成为编排标准形态 |
| 数据质量与血缘平台化 | 2020~ | 门禁、血缘、目录与治理进入数据平台默认能力 |

## 3. 语法与参数

第 3 章按「一份数据在湖仓里的一生」展开：先讲**建表与口径**（3.1），再讲**快照与布局**（3.2/3.3/3.4），然后讲**怎么算**（3.5），再讲**怎么调度与重算**（3.6/3.7），最后讲**怎么兜底**（3.8）。学习目标不是背 Iceberg API，而是建立三条判断线：**这份数据能不能被复算、这次重跑会不会重复计数、这次查询要扫多少数据**。

### 3.1 分层建模与口径：ODS / DWD / DWS / ADS

分层的价值不在命名，而在**依赖方向**：数据只能从上游流向下游，反向依赖（DWD 直接读 ADS）是口径失控的开始。

| 层 | 职责 | 粒度 | 允许的数据形态 |
|----|------|------|--------------|
| ODS（原始层） | 贴着源系统落原始数据，**不做业务解释** | 原始事件/行 | 全量字段、含脏数据（只做格式校验） |
| DWD（明细层） | 清洗、去重、维度退化后的**明细事实** | 一条业务事件 | 已清洗、一实体一行/一事件一行 |
| DWS（汇总层） | 按主题聚合的**轻度汇总**（天/实体/维度） | 主题 + 时间粒度 | 由 DWD 聚合而来，可回溯到明细 |
| ADS（应用层） | 面向具体看板/接口的**结果集** | 报表/接口粒度 | 由 DWS 或 DWD 聚合，可被替换重算 |

```java
// examples/ex01-warehouse-layers/Layer.java —— 依赖方向即编译期纪律
public enum Layer { ODS, DWD, DWS, ADS }          // 序号即层级：只允许 上游 <= 下游
public record TableRef(String table, Layer layer) {}
// 依赖校验：ADS 可以依赖 DWS/DWD/ODS；DWD 依赖 ADS → 抛 IllegalStateException（反向依赖）
```

**为什么口径要有唯一源**：同一指标（如「日活实例数」）在 ADS 里被两张看板各算一遍，早晚会出现「两个数都对不上」的经典事故。工程做法是：**口径写在 DWS 层**（可被多张 ADS 复用），ADS 只做展示态加工；配合 ph21 的「口径集中声明」与 ph22 的「台账即事实」，本阶段把它固化成**表级依赖约束**——口径漂移在建模阶段就被拦下，而不是等对账时才发现。

**为什么 ODS 不做业务解释**：ODS 的职责是「可追溯的原始凭证」。一旦在 ODS 里做业务清洗（丢掉自认为的脏数据），上游就再也无法复现原始事实；而清洗规则会变，**变了就要能从原始重算**（这正是 3.7 回填存在的意义）。

> 阶段内容隔离：SQL 语法、聚合与窗口函数属 ph13/ph17；pandas 层面的清洗与统计属 py/ph09；维度建模与指标业务定义属数据治理领域知识——本阶段只讲「分层职责与依赖纪律」这一控制面语义。

### 3.2 ACID 表与快照：时间旅行与增量读

湖仓的表不是「目录 + 文件」，而是**元数据层定义的不可变快照**：每次写入产生新快照，提交 = 原子替换当前快照指针。

```java
// examples/ex02-table-snapshots/TableFormat.java —— 快照链 + 原子提交
public record Snapshot(long snapshotId, long parentId, long tsMillis,
                       String operation, Map<String, Integer> filesByPartition) {}
// commit：CAS 当前快照指针（乐观并发）；失败者重读后重试 → 不会出现「两份当前快照」
// timeTravel(ts)：沿 parentId 链回溯到 ts 之前最近的一次快照（读旧数据不需要副本）
// incremental(sinceId)：只读出「自某快照以来新增/变更的分区」
```

| 能力 | 机制 | 工程价值 |
|------|------|---------|
| 原子提交 | 快照指针 CAS + 乐观重试 | 失败的重跑不会污染表（读到的永远是完整快照） |
| 时间旅行 | 快照链回溯（按 id 或时间戳） | 复算历史口径、排查「上周的数怎么变了」 |
| 增量读 | 比较两个快照的清单差异 | 下游只处理变化分区（省扫描量与计算量） |
| Schema 演进 | 提交时校验兼容性 | 加列可兼容；删列/改类型必须显式确认 |

**兼容性规则为什么必须 fail-fast**：`ALTER TABLE ADD COLUMN` 是安全的（旧数据该列为 null）；`DROP COLUMN` 与「`int` 改 `string`」是不安全的（历史文件读不出、下游类型断言全崩）。表格式层若允许静默通过，错误会推迟到**下游任务运行时**才炸，而那时数据可能已经被写进 ADS。所以校验必须在**提交阶段**拒绝，并给出「哪个列、什么变更、为什么不兼容」。

**为什么增量读比「按时间戳过滤」可靠**：时间戳是数据内容的一部分，会被时区、补数、乱序写入污染；而快照 id 是**元数据的单调序列**——「自 snapshot 1024 以来变了什么」是平台自己记账得出的确定答案。这是 ph21「判据取端到端事实」在表格式层的再现。

> 阶段内容隔离：并发控制与 CAS（`AtomicReference.compareAndSet`）属 ph09/ph18/ph20；文件系统原子 rename 属 ph19；存储引擎的 WAL/SSTable 实现属 cpp/ph22 与 rs/ph25——本阶段只讲「表格式如何用快照提供 ACID 语义」。

### 3.3 分区布局与扫描量：分区裁剪

分区是「物理布局对齐查询谓词」的手段：查询带分区谓词时，只扫命中分区的文件。

```java
// examples/ex03-partition-layout/PartitionLayout.java —— 裁剪即"跳过文件"
public record DataFile(String path, String partition, long rows, long bytes) {}
// scan(filter)：返回需要扫描的文件列表；scanBytes = Σ bytes（这就是"这次查询要付多少钱"）
// 检测小文件：分区内文件数 > 阈值 且 平均大小 < 阈值 → 标记该分区需要 compaction（3.4）
```

| 布局选择 | 适合 | 代价 |
|---------|------|------|
| 按日期分区 | 时间范围查询（绝大多数分析） | 单日数据量过大时分区内文件过多 |
| 按实体 + 日期 | 「某实例某天」的点查与增量 | 实体基数过大 → 分区爆炸（元数据压力） |
| 全表不分区 | 极小表 | 任何查询都全扫 |
| 分区 + 内部排序/聚簇 | 需要块级跳过（min/max 统计） | 写入要排序，写放大 |

**扫描量必须能被估算**：`scanBytes` 是数据平台最直接的**成本度量**（按扫描量计费的引擎、按 IO 计费的存储都以此为准）。示例把「裁剪前的全表字节数」与「裁剪后的字节数」同时打印——**分区设计的好坏，一眼就能从这两个数字看出**。这也是 3.8 成本一屏的基础。

**分区键为什么不能随便选**：分区键决定「哪些查询能裁剪」。用高基数列（如毫秒时间戳、UUID）分区会导致分区数爆炸；用低基数列（如状态枚举）分区则裁剪收益极低。工程判据：**分区键应该是查询谓词里最常用、且基数在数百到数千量级的那一列**。

> 阶段内容隔离：Hive/Iceberg 的分区目录布局与元数据文件格式属真实引擎（本阶段用内存模型表达）；对象存储的列举性能与生命周期策略属基础设施；表设计的业务维度选择属数据建模。

### 3.4 小文件治理：compaction 的读写放大权衡

流式写入与频繁提交会产出大量小文件：**读取要打开的文件数爆炸**（元数据与 IO 开销），而合并文件又带来**写放大**。

```java
// examples/ex04-compaction/Compaction.java —— 合并决策 + 收益测算
public record Plan(String partition, int fileCountBefore, int fileCountAfter,
                   long bytesBefore, long bytesAfter, double readSavedRatio) {}
// 判据：分区内平均文件大小 < targetSize 且 文件数 > minFiles → 合并到 targetSize 附近
```

| 决策 | 何时做 | 代价 |
|------|--------|------|
| 合并（compaction） | 小文件多、读多写少的分区 | 重写数据（写放大）+ 占用计算资源 |
| 不合并 | 写入极热、几乎不读的分区 | 查询越来越慢、元数据膨胀 |
| 增量/局部合并 | 只处理新产生的小文件 | 实现复杂（需要跟踪文件血缘） |

**为什么不能「随时合并」**：合并是一次**重写**——它消耗算力与 IO、产生新快照（时间旅行链变长）、与正在运行的写入/读取竞争。工程上通常：① 只在**读收益明显**（读多写少）的分区做；② 限制单次合并的数据量与频率；③ 合并本身幂等（同样输入合并两次结果一致）。

**收益要用数字说话**：示例打印 `readSavedRatio`（合并后扫描字节数下降比例）与 `fileCountBefore/After`。真实平台里这个数字直接决定「compaction 任务值不值得跑」——**没有度量的治理动作都是拍脑袋**。

> 阶段内容隔离：LSM 的 Compaction 策略（leveled/tiered、三放大模型）属 rs/ph25 与 cpp/ph22 的存储内核；本阶段讲的是**表格式层面的文件治理决策**（何时合、合到什么粒度、收益怎么算），不涉及 SSTable 合并算法本身。

### 3.5 批流一体：同一口径，两种执行

批流一体的核心不是「一套代码两处跑」的 API，而是**口径唯一**：同一份逻辑（过滤 + 去重 + 聚合）既能对历史全量跑批，也能对实时流增量跑。

```java
// examples/ex05-batch-stream-unified/Pipeline.java —— 同一口径两种执行
public record Window(String key, long windowStart, long windowEnd) {}
// batch(partitions)：对历史分区跑一次（幂等覆盖输出分区）
// stream(events, watermark)：按水位线聚合，迟到事件按策略处理
//   watermark = maxSeenTs - allowedLateness；evTs <= watermark 的迟到事件 → 丢弃或写入侧输出（补偿）
```

| 概念 | 含义 | 取舍 |
|------|------|------|
| 水位线（watermark） | 「认为这个时间点之前的数据已到齐」的界 | 太紧 → 迟到数据被丢；太松 → 结果延迟 |
| 迟到数据 | 事件时间 < 水位线才到达 | 丢弃（简单）/ 侧输出补偿（准确） |
| 幂等覆盖 | 按分区整体重写（而非追加） | 重跑不重复计数，代价是重写分区 |
| exactly-once | 幂等写 + 检查点（重放从检查点开始） | 复杂但结果确定 |

**为什么「幂等分区覆盖」是批流一体的关键**：流式作业重启必须从检查点重放，若输出是**追加**语义，重放就会重复计数；改成「**按 (分区+窗口) 整体覆盖**」后，重放同一窗口的结果与第一次完全一致——这就是「至少一次投递 + 幂等写 = 效果上的 exactly-once」。这与 ph21 的「幂等批」是同一条纪律，只是粒度从「批」变成「窗口分区」。

**迟到数据为什么不能用「丢弃」敷衍**：丢弃意味着**结果与历史批算不一致**（同一时间窗，批算有这条、流算没有），于是「批流一体」就退化成了「两套数」。工业做法是**侧输出**（把迟到事件写进单独表，由补偿任务按更宽水位线重算那个窗口）——本阶段用「迟到计数 + 侧输出分区」示范这条路径。

> 阶段内容隔离：Flink/Spark 的执行引擎（算子链、反压、状态后端、检查点存储）属真实引擎；Java 并发与异步属 ph09/ph18；本阶段只把**语义层**（水位线、迟到、幂等覆盖、检查点重放）模型化并用确定性内存执行验证。

### 3.6 数据编排：DAG、依赖与就绪判断

编排的本质是**依赖图 + 就绪条件**：一个任务能跑，当且仅当它所有上游在今天这个周期里都成功。

```java
// examples/ex06-orchestration-dag/Dag.java —— 拓扑 + 就绪 + 失败传播
public record TaskNode(String id, List<String> deps, int retries) {}
// topoOrder()：确定性拓扑序（同层按 id 排序，保证可重放）
// ready(successSet, runningSet)：所有 deps ∈ successSet 且自身未运行
// onFailure(id)：重试未耗尽 → 重新入队；耗尽 → 标记失败并阻塞所有下游
```

| 机制 | 规则 | 为什么 |
|------|------|-------|
| 拓扑序 | 同层按 id 排序（确定性） | 编排决策要能复盘（与 ph22 调度同一条纪律） |
| 就绪判断 | 上游**全部成功**才就绪 | 「部分上游成功」就跑 = 用了半份数据 |
| 失败重试 | 上限固定（示例 2 次） | 无限重试会占满执行槽 |
| 失败传播 | 耗尽后阻塞下游（而非跳过） | 下游若「跳过」，会产出缺口且没人发现 |
| 并发度 | 同时运行任务数上限 | 保护被依赖系统的负载 |

**为什么「跳过下游」比「阻塞下游」危险**：跳过看起来「跑完了」，但 ADS 里会出现一段没有数据的日期；值班看到的是「任务成功」，直到业务发现缺口——**静默缺口比显式失败贵得多**。所以正确做法是：失败任务阻塞下游，并让编排器把「阻塞中」显式暴露在状态里（3.8 一屏）。

**为什么拓扑序要确定性**：编排器每秒可能调度数百个任务，一旦顺序不稳定，同样输入会产出不同的执行顺序，让「昨天为什么慢」无法复盘。同层按 id 排序是成本最低的确定性来源。

> 阶段内容隔离：Airflow/Dagster/dbt 的部署与运维、调度器的分布式选主与任务队列实现属基础设施工程；本阶段只讲 DAG 语义、就绪条件与失败传播这三件事（用一个确定性内存编排器验证）。

### 3.7 幂等回填：分区级重跑与下游重算

回填（backfill）是湖仓最容易被做错的动作：重跑一天的数据，若下游没跟着重算，结果就是**新旧口径混在一起**。

```java
// examples/ex07-backfill-idempotent/Backfill.java —— 幂等重跑 + 下游传播
public record BackfillTask(String table, String partition, String reason) {}
// plan(from, to)：产出「待重算分区 + 受影响的下游分区」集合（按依赖图传播）
// run(task)：按分区整体覆盖（幂等）；断点续跑 = 已成功分区不重复执行
```

| 规则 | 说明 |
|------|------|
| 分区级幂等 | 重跑同一分区结果一致（整体覆盖，不追加） |
| 下游传播 | 重跑 DWD 某天 → DWS/ADS 对应天必须重算（否则口径混用） |
| 断点续跑 | 记录已成功分区，中断后从缺口继续（不重跑全部） |
| 原因留痕 | 每次回填记录 `reason`（上游修数/规则变更/故障补偿） | 

**为什么「整体覆盖」是回填的前提**：如果写入是追加，重跑一天的数据会让那一天翻倍；如果按主键 upsert，删除类变更（源里删掉的行）永远无法反映。**分区整体覆盖**同时解决这两点——代价是需要能按分区原子替换（正是 3.2 的快照提交提供的）。

**为什么下游传播不能省**：DWS 的「日活」由 DWD 明细聚合而来。只重算 DWD 而不重算 DWS，就会出现「明细改了、汇总没改」——这种不一致**没有任何自动告警能发现**（两边各自都自洽）。所以回填计划必须包含**依赖图上的传播闭包**。

> 阶段内容隔离：分布式任务的断点续跑与状态持久化属 ph19/ph22；调度器的任务队列与分布式锁属基础设施；本阶段讲的是**回填的正确性语义**（幂等、传播、断点、留痕）。

### 3.8 质量、血缘与成本：湖仓的三道兜底

数据平台的信任来自三件事：**数据是对的（质量）、来路清楚（血缘）、代价可见（成本）**。

| 能力 | 机制 | 失败时的动作 |
|------|------|-------------|
| 质量门禁 | 非空/唯一/量程/行数波动/鲜度五类检查 | **不发布快照**（fail-closed），下游不会读到坏数据 |
| 列级血缘 | 由变换推导「输出列 ← 输入列」 | 影响分析（改上游前知道谁受影响）、合规追溯 |
| 成本度量 | 扫描量、存储量、小文件数、compaction 收益 | 一屏暴露，作为治理动作的依据 |
| 目录与权限 | 表/列元数据 + 访问审计 | 「谁能看哪一列」可审计（合规硬要求） |

```java
// examples/ex08-quality-lineage-cost/QualityGate.java —— 门禁即发布前置条件
// check(rows) → List<GateResult>；任一 FAIL → 提交被拒（表保持上一个快照）
// 关键取舍：门禁失败不是"告警后继续"，而是"不发布"——坏数据进表比任务失败贵得多
```

**为什么门禁要 fail-closed**：告警是**异步**的（人可能没看到），而坏数据一旦提交，下游所有任务都会基于它产出错误结果，且**修复成本随时间指数上升**（下游要全链重算）。所以门禁必须挡在**提交之前**——这与 ph22 的「配额拒绝而非排队」是同一种工程直觉：**在最早的、代价最低的位置拦下错误**。

**血缘为什么是列级而不是表级**：表级血缘只能说「A 表来自 B 表」，而实际影响分析要回答「改 DWD 的 `latency_ms` 会影响哪些看板的哪一列」。列级血缘是**合规与变更评审的最小单位**，也是「别人问这个数怎么来的」能秒答的前提。

> 阶段内容隔离：数据质量规则的业务语义（什么算异常）属业务治理；血缘图谱的存储与可视化、目录服务（DataHub/OpenMetadata）的部署属平台工程；本阶段只做「门禁、血缘推导、成本估算」三件事的语义与最小实现。

## 4. 底层原理

### 4.1 表格式为什么需要「清单 + 快照」

对象存储只有「整对象 PUT」这一种原子操作，**没有目录级事务**。若表 = 目录，那么一次写入就是「往目录里丢一堆文件」——丢到一半失败，读者看到半份数据；并发写更糟，两个写者互相看不见对方，最终「当前数据」是两个写入的混合体。

Iceberg 类表格式的解法：**数据的「当前状态」不由目录决定，而由一份元数据（清单列表）决定**。

```text
table/
  metadata/snapshot-1024.json     ← 快照：本次提交的清单文件列表（不可变）
  metadata/snapshot-1025.json     ← 新快照：parent=1024（链式）
  metadata/current.json           ← 指针：原子替换（唯一的"可变"位置）
  data/part=2024-06-01/xxx.parquet
```

三个直接推论：① **提交原子**——只有指针替换是原子的，失败则指针不变（读者看到旧快照，完整且一致）；② **读一致性**——一次查询固定在一个快照上，写者提交新快照不影响它；③ **时间旅行免费**——旧快照文件还在，按 id 读即可。代价是**快照与清单会累积**，需要过期清理策略（保留 N 天 / N 个快照）——这也是「元数据膨胀」类运维问题的来源。

### 4.2 小文件的读写放大权衡

设分区内有 `n` 个小文件、每个大小 `s`，目标文件大小 `S`：

- **读代价** ≈ 打开文件数 `n`（元数据与 IO 开销）＋ 扫描字节 `n·s`（若查询要全分区）。
- **合并后**：文件数 ≈ `n·s/S`，读时打开开销按比例下降；但合并要**重写 `n·s` 字节**（写放大）。
- **判据**：若该分区在未来还会被查询 `k` 次，则合并收益 ≈ `k · (n - n·s/S) · 单文件打开开销`，成本 ≈ `n·s` 的读写。**读多写少**（`k` 大）才划算。

这就是为什么工程上「热写分区不合并、冷存分区定期合并」：合并的价值取决于**未来的读次数**，而不是文件多不多。示例 ex04 用确定性数字把这个权衡算出来（`readSavedRatio`），而不是凭感觉调参。

### 4.3 批流一体：为什么「同一口径」比「同一代码」重要

批与流的执行模型本质不同（有界 vs 无界、全量 vs 增量），所以「一份代码两处跑」永远是近似——真正的目标是**语义一致**：同一时间窗，批算与流算必须得出同一个数。三条保证：

1. **同一套逻辑**（同一份 SQL/算子定义，避免两套实现各自演化）；
2. **同一套时间语义**（都用事件时间 + 水位线；用处理时间的流算永远追不上批算）；
3. **同一套幂等写**（按窗口分区整体覆盖，重放不重复计数）。

只要有一条不满足，平台就会长出「流算的数」和「批算的数」两个版本——**而两个版本的值班成本远高于一套慢一点的批**。

### 4.4 回填的正确性：为什么必须传播到下游闭包

回填的正确性条件可以写成一句话：

> 对任意表 T 与分区 P，若 T 的输入发生变化，则**依赖 T 的、包含 P 的所有下游分区**都必须被重算，且重算必须幂等。

若只重算 T 而不传播，下游 DWS/ADS 会用「旧上游 + 新上游」的混合结果（各自都自洽，无法自动发现）；若重算不幂等，重跑会让数据翻倍或产生重复行。两者叠加就是湖仓最经典的事故形态——**「数变了但没人知道为什么变」**。所以回填计划 = `依赖图闭包(T, P)`，执行 = 「按分区覆盖 + 断点续跑 + 原因留痕」。

## 7. 总结

### 关键要点

1. **分层定职责、依赖定纪律**：ODS 不做业务解释、口径写在 DWS、禁止反向依赖（3.1）
2. **表的当前状态由元数据决定，而不是目录**：快照 + 清单 + 原子指针替换 = ACID 与时间旅行（3.2/4.1）
3. **schema 演进必须 fail-fast**：加列安全、删列/改类型必须在提交阶段拒绝（3.2）
4. **分区键要匹配查询谓词**：扫描字节数是成本的第一度量，裁剪收益要能被看到（3.3）
5. **小文件治理取决于未来的读次数**：读多写少才值得合并（3.4/4.2）
6. **批流一体的目标是语义一致，不是代码复用**：同口径、同事件时间、同幂等写（3.5/4.3）
7. **幂等分区覆盖是重放安全的前提**：追加与 upsert 都会在重跑时出错（3.5/3.7）
8. **迟到数据不能敷衍丢弃**：要么侧输出补偿，要么承认两套数（3.5）
9. **编排的就绪条件是"上游全部成功"**：失败要阻塞下游而不是跳过（3.6）
10. **回填必须传播到依赖闭包**：只重算上游会造成新旧口径混用，且无法自动发现（3.7/4.4）
11. **质量门禁要 fail-closed**：坏数据进表比任务失败贵得多（3.8）
12. **血缘要细到列**：变更影响分析与合规追溯的最小单位（3.8）
