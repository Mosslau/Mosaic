# Java AI 平台 / 训练与推理调度方向阶段

> Java 学习路线的 AI 平台收官阶段：把 ph01~ph21 的全部机制汇入 AI 平台的**控制面**——训练任务编排、算力资源池与配额、调度策略、模型注册与版本、推理服务灰度发布、数据集与特征版本台账，回答「一个 AI 平台的后台系统究竟由哪些状态机、台账与策略组成」。

## 1. 概述

roadmap 第 22 节（即本阶段）是 Java 路线的**最后一个编号阶段**，也是 ph21 数据平台后端的自然延续。ph21 解决了「数据怎么进来、怎么变成可查询可运营的事实」；本阶段解决**数据之上那一层**：「算力怎么被分配给训练任务、模型怎么从一次训练变成一个可发布的版本、推理服务怎么安全地滚动更新与回滚」。两者共享同一套 Java 机制（DDD 聚合与状态机、SPI 可插拔策略、CHM 实时状态、Kafka 事件、灰度发布与审计），区别只在**领域对象**：ph21 的对象是数据源与指标，本阶段的对象是**任务（job）、算力（GPU 秒）、模型版本（model version）与服务（service）**。

## 2. 来源与演变

AI 平台不是从「大模型」开始的，它是**集群调度 + 模型工程 + 服务发布**三条线合流的结果。**设计哲学一句话：AI 平台控制面的本质是「把稀缺的算力按时、按量、可追溯地交给任务，再把任务的产物安全地交给线上流量」——稀缺性带来调度，产物带来版本，线上带来发布纪律。**

- **单机脚本时代（2010 前）**：训练就是一台机器上的一个脚本，没有调度概念；「平台」仅指共享的文件系统与手工维护的实验记录。今天很多团队的第一反应仍是「起一台 GPU 机器跑脚本」——本阶段 3.1 的任务状态机正是把这件手工事固化成可审计的对象。
- **集群调度时代（2006-2015）**：Hadoop/YARN 把「队列 + 容量/公平调度」带进大数据，Mesos 提出两级调度，**优先级、抢占、回填**成为调度器标准词汇（本阶段 3.3 与 4.1）。这一代的经验是：**调度策略必须可解释**，否则容量纠纷无法复盘。
- **容器与编排时代（2015-2020）**：Kubernetes 用「期望状态 + 控制器循环」统一了部署语义（本阶段 4.2 的机制原型），GPU 从独占走向 device plugin 暴露；**声明式 + 收敛**取代了「跑命令」，模型服务第一次有了「副本数」这种一等概念（3.5）。
- **GPU 共享与平台化时代（2020-）**：A100/H100 让单卡成为稀缺资源，MIG/时间片共享/拓扑感知调度出现；训练平台（提交 → 排队 → 运行 → 产物登记）与推理平台（模型注册 → 灰度 → 自动扩缩）分工成型，**AI 平台**成为一个独立的工程岗位方向——Control plane（Java/Go 写的后台）与数据面（Python/C++ 写的执行器）分离，本阶段站在**控制面**这一侧。

| 里程碑 | 年份 | 主要变化 |
|--------|------|---------|
| Hadoop / YARN 容量调度 | 2008~ | 队列、容量/公平、优先级成为调度标准词汇 |
| Mesos 两级调度 | 2011 | 资源供给与调度策略解耦 |
| Kubernetes 控制器循环 | 2015 | 「期望状态 + 收敛」成为部署语义的事实标准 |
| GPU device plugin | 2017 | GPU 成为可编排资源；副本与配额进平台 |
| Kubeflow / MLflow 类平台 | 2018~ | 训练编排 + 实验/模型台账成为平台标配 |
| 大模型推理平台化 | 2022~ | 模型注册、灰度、自动扩缩与计费进入同一控制面 |

本文示例以 **OpenJDK 17.0.18（Homebrew）为基线**（与 ph14~ph21 同一工具链；本阶段全部代码只用标准库与 Java 17 稳定特性：record、sealed interface、switch 表达式、并发集合），验证工具链实测为 javac/java 17.0.18。**验证纪律**：① 全部 examples/exercises/project 采用**纯 Java + 确定性内存模型**（无 Kafka/Redis/GPU/K8s 依赖），`javac` 编译 + `java` 运行的自检断言已在本机实测并标注「已验证」；② 涉及真实集群的部分（K8s CRD、device plugin、NCCL、真实 GPU 计量）只给形态与命令，标注「未在本环境验证」；③ 与 ph21 一致，本阶段**没有新语法面**——它是纯应用层，学的是 AI 平台控制面的领域建模与调度纪律。

### 3.1 训练任务平台：聚合根与状态机

训练任务是 AI 平台的核心聚合根：一次提交产生一个**不可变定义**（JobSpec）+ 一条**可变生命周期**（状态机）。ph21 用同样的手法建模过数据源生命周期，这里换成任务。先把四类对象在各小节里的角色对齐（避免同一个词在不同小节指不同东西）：

| 小节 | 任务（job）在这里是什么 | 算力（GPU） | 模型（version） | 服务（service） |
|------|----------------------|------------|----------------|----------------|
| 3.1 任务状态机（本小节） | **有身份、有生命周期的聚合根** | 资源需求（gpuCount） | — | — |
| 3.2 资源池 | 一个占用者（jobId → gpus） | **被分配的稀缺资源** | — | — |
| 3.3 调度 | 排队与选中的单位 | 约束条件（freeGpus） | — | — |
| 3.4 注册表 | 血缘的一端（jobId） | — | **产物台账条目** | — |
| 3.5 推理服务 | — | 副本的资源需求 | 期望版本（spec.modelVersion） | **收敛对象** |

```java
// examples/ex01-training-job/JobState.java —— 状态机（sealed + switch 穷尽）
sealed interface JobState permits Queued, Running, Succeeded, Failed, Cancelled { }

// 合法迁移（其余一律 IllegalStateException：状态机必须把非法操作挡在聚合内）
// QUEUED → RUNNING | CANCELLED
// RUNNING → SUCCEEDED | FAILED | CANCELLED
// FAILED → QUEUED（重试，attempt+1，上限 3）
```

| 设计点 | 做法 | 为什么 |
|------|------|-------|
| 幂等提交 | `idempotencyKey = tenant + name + specHash`，重复提交返回原任务 | 客户端重试是常态，重复扣配额是事故 |
| 预估时长 | `JobSpec.estMinutes`：任务自报的预计运行分钟数（回填调度的输入） | 没有预估就无法回填，只能让大任务空等（4.1） |
| 重试语义 | 只对 `FAILED` 允许重试，`attempt` 单调递增、上限 3 | 无上限重试会吃掉整个池子 |
| 审计轨迹 | 每次迁移写 `(ts, from, to, reason, operator)` | 「谁把任务杀了」是值班第一问 |
| 终态不可变 | `SUCCEEDED/CANCELLED` 为终态 | 防止「已完成的任务又被拉回排队」 |

**为什么状态机必须收在聚合里**：如果允许 Service/Controller 直接改 `state` 字段，非法迁移（已完成的任务又被拉起、被取消的任务又跑起来）会散落在多处、无法统一拦截；收进聚合后所有迁移走同一组方法，**非法操作在同一个点爆炸**，错误信息一致，测试只需测聚合本身（ex01 的 7 项断言全部打在聚合上）。

**幂等键为什么不含 `submitTs`**：客户端重发时时间戳一定不同，若把时间戳写进指纹，「重试」就会被当成「新任务」而重复占配额。指纹只取业务字段（租户/名称/卡数/优先级/预估时长）。反过来，**被配额拒绝的提交不占幂等键**——用户把任务改小之后必须能重新提交。

> 阶段内容隔离：Java 并发的线程安全语义（`synchronized`/`AtomicX`/CHM）属 ph09/ph18/ph20；DDD 的聚合、领域事件、限界上下文理论属 ph20 3.11——本小节只演示「任务这一个聚合怎么建」，不重复这些机制本身。

### 3.2 算力资源池：台账、配额与队列

资源池是「一张卡的账本」：总量固定，分配与回收都必须过账，任何时刻 `allocated + free == total` 是硬不变量。

```java
// examples/ex02-gpu-pool/GpuPool.java —— 台账 + 不变量
public final class GpuPool {
    private final int total;
    private final Map<String, Integer> allocated = new ConcurrentHashMap<>();  // jobId → gpus
    public synchronized boolean tryAllocate(String jobId, int gpus) { ... }
    public synchronized void release(String jobId) { ... }
    public int free() { return total - allocated.values().stream().mapToInt(Integer::intValue).sum(); }
}
```

| 概念 | 含义 | 本阶段落点 |
|------|------|-----------|
| 配额（quota） | 租户在池子里最多能占多少 | 3.7：超限**拒绝提交**而不是排队 |
| 优先级（priority） | 任务的调度权重 | 3.3：高优先级先拿卡 |
| 队列深度 | 排队任务数（容量规划与告警依据） | 3.8：`aiplat_jobs_queued` |
| 资源碎片 | 有空卡但没有足够连续卡给大任务 | 4.1：为什么调度要感知「形状」 |

**为什么把不变量写成代码而不是注释**：台账类代码的 bug 几乎都是「漏释放 / 重复释放 / 部分分配」。ex02 在**每次写操作后自检** `allocated + free == total`，并让重复分配、释放不存在的 jobId 直接抛异常——**错账比拒绝服务更危险**，因为错账是静默的（后面所有调度决策都建立在错账上）。

**「空转的卡」是利用率的第一杀手**：池子里有 4 张空闲卡，但如果它们分散在不同节点、或队列头要 8 张卡，这 4 张就是**不可用的空闲**。这就是为什么平台同时需要「调度策略」（3.3）与「形状感知」（4.1），而不是简单按卡数排队。

> 阶段内容隔离：`synchronized` 与 CHM 的内部实现属 ph18/ph20；K8s 的 device plugin、MIG 切分、NUMA/拓扑感知调度属真实基础设施（本阶段用**确定性内存台账**模拟，见第 5 章分工表）。

### 3.3 调度策略：可插拔、可解释、确定性

调度是「在约束下做选择」：本阶段把策略抽成接口，用同一组输入对比三种策略的决策差异——**策略即数据**（与 ph21 的规则引擎同构）。

```java
// examples/ex03-scheduler/Policy.java —— 策略接口（SPI 同思路：引擎不变，策略可换）
public interface Policy {
    /** 从排队任务中选出本轮可运行的任务 id；输入固定 → 输出必须确定（可断言）。
     *  queue=排队任务，freeGpus=空闲卡，now=逻辑时钟，running=运行中任务，remainingMin=各运行中任务剩余分钟。 */
    List<String> select(List<JobSpec> queue, int freeGpus, long now,
                        List<Running> running, Map<String, Integer> remainingMin);
}
```

| 策略 | 规则 | 典型代价 |
|------|------|---------|
| FIFO | 按提交时间先到先得 | 大任务阻塞小任务（队头阻塞） |
| 优先级 | 高优先级先拿卡，同级 FIFO | 低优先级可能饿死（需老化/配额兜底） |
| 回填（backfill） | 大任务排队时，允许**放得下的小任务插队**（不推迟大任务的预计启动时间） | 需要预估运行时长（`JobSpec.estMinutes`），预估不准会推迟大任务 |
| 抢占（简化） | 高优先级任务可抢占低优先级运行中任务的卡 | 必须能安全中断（checkpoint 语义，本阶段只做决策不做中断） |

**为什么强调「确定性」**：调度决策必须能复盘——「为什么昨天那批任务排了 6 小时」只能靠「同一输入重放出同一决策」来回答。因此本阶段的策略实现全是**纯函数**，测试直接断言决策序列。

**回填的「等待窗口」从哪来**：示例用「运行中任务剩余分钟数的最大值」作为**保守上界**（池满时队头至少要等最后一个持有者释放）。真实平台会做可用性预测或分位数估计，但那需要真实时钟与运行时数据，与会「纯函数可重放」冲突——所以这里把口径显式写进签名并断言（`running`/`remainingMin` 是入参，不是全局状态）。这是刻意的简化，代价写在下表。

**回填装填顺序为什么不是纯 FIFO**：在保证队头优先的前提下，剩余卡按「卡数升序 + 同卡数回落 FIFO」装填。若按纯 FIFO，4 卡的空闲可能永远等不到能填满它的任务，而小任务又因前面有大任务而全部阻塞——回填的考点正是**消灭空转**。

**抢占为什么只做决策不做中断**：抢占会用「中断运行中任务」换取高优先级任务的及时性，前提是被抢占任务**可安全中断**（有 checkpoint 或可重跑）。本阶段把抢占建模为「决策」而不实现中断与恢复，因为后者依赖训练框架的 checkpoint 能力——那是数据面的职责（见第 5 章）。

> 阶段内容隔离：SPI 装载机制（`ServiceLoader`、动态代理）属 ph20 3.8，本阶段只复用「引擎不变、策略可换」这一形态；YARN/K8s 调度器的完整实现（DRF、队列层级、资源预留、拓扑感知）属基础设施工程，本阶段只讲清 FIFO/优先级/回填/抢占四种机制与它们的代价（4.1）。


### 3.4 模型注册与版本：产物台账与晋级

一次训练任务的产物是**模型版本**，它不是文件而是**带血缘的台账条目**：谁训练的、用了哪份数据、评估指标如何、当前处于哪个阶段。

```java
// examples/ex04-model-registry/ModelVersion.java —— 语义化版本 + 血缘
public record ModelVersion(String model, int major, int minor, int patch,
                           Stage stage, String datasetVersion, String jobId, double metric)
        implements Comparable<ModelVersion> { }
public enum Stage { STAGING, PROD, ARCHIVED }
```

| 规则 | 说明 |
|------|------|
| 语义化比较 | `2.10.0 > 2.9.0`；**禁止版本倒退**（与 ph21 发布平台同一条纪律） |
| 晋级门槛 | `STAGING → PROD` 要求指标不劣于当前 PROD 版本（可配置阈值） |
| 唯一 PROD | 同一模型同一时刻只有一个 PROD 版本（灰度期由 3.5 处理） |
| 血缘完整 | `datasetVersion + jobId` 必填，否则拒绝登记 |

**为什么「唯一 PROD」需要灰度配合**：注册表保证「台账里只有一个 PROD」，但**线上流量切换是有过程的**（10% → 50% → 100%）。两者必须配合：注册表负责「谁是官方版本」，推理服务负责「流量什么时候全部切过去」。反过来，如果允许台账里同时挂两个 PROD，值班时就无法回答「线上到底跑的是哪一版」——这是 3.5 必须存在的理由。

**晋级门槛为什么用「指标不劣于」而不是「时间最新」**：模型版本不是软件版本——新训练出来的模型完全可能更差（数据漂移、超参失误）。用指标做门槛把「能不能上」变成一次可复算的比较；阈值可配（示例取 0），但**门槛本身不能省**，否则注册表就退化成「文件名列表」。

**为什么要禁止版本倒退**：`2.9.0` 之后又登记 `2.8.0` 会让「最新版本」失去意义（选版、回滚点、审计全都依赖单调性）。要回到旧版本走**发布**（3.5 的回滚），而不是往台账里塞一个更小的版本号——这是 ph21 已经立过的纪律，这里原样继承。

> 阶段内容隔离：语义化版本比较、值对象与不变式属 ph02/ph08；发布批次状态机与回滚机制属 ph21 3.6，本阶段只把「发布对象」从软件包换成模型版本；模型训练与评估指标怎么算属 py/ph15（本阶段把 metric 当作**输入**）。

### 3.5 推理服务生命周期：期望状态与灰度

推理服务用**期望状态**描述（镜像/模型版本/副本数/资源），平台负责让实际状态收敛到期望状态——这是 K8s 控制器循环的最小复刻（原理见 4.2）。

```java
// examples/ex05-inference-rollout/InferenceService.java —— 观测 + 收敛
public record Spec(String image, String modelVersion, int replicas) { }
public record Status(int ready, int updated, String trafficVersion) { }
// reconcile(spec, status) → 下一步动作（扩容/缩容/滚动一批/切流量/回滚）
```

| 阶段 | 动作 | 失败处理 |
|------|------|---------|
| 滚动更新 | 逐批启动新版本副本，就绪后替换旧副本（`maxUnavailable/maxSurge`） | 新副本起不来 → 停止推进并保留旧副本 |
| 灰度切流 | 按百分比把流量切到新版本（10% → 50% → 100%） | 健康检查或指标劣化 → 回滚到旧版本 |
| 回滚 | 期望状态改回旧版本，重新收敛 | 回滚本身也走同一套收敛逻辑（不特殊化） |

**`Status.updated` 的口径**：「相对**当前期望版本**的副本数」。回滚把期望改回旧版本后，`updated` 会重新从 0 开始观测——这样「旧副本补齐 → 再切流量」的顺序不会被上一个版本的进度误判为已完成（examples/ex05 显式断言这条）。

**为什么一次只推一批（限速）**：如果控制面每轮都「把所有副本替换成新版本」，收敛就会变成雪崩——新版本一旦有问题，**旧版本已经没有副本可以承载流量**，回滚也来不及。`maxSurge/maxUnavailable` 的本质是「任何时刻都保留一部分旧版本容量」，这也是灰度能回滚的前提。

**探针 ≠ 业务健康**：副本「就绪」只说明进程活着（存活/就绪探针），不代表模型效果没退化。所以灰度推进要同时看两类信号：**基础设施信号**（就绪副本、错误率）与**业务信号**（延迟分位、评估指标、人工观察窗口）。示例把「健康失败」抽象成一个布尔输入（`healthOk`），真实平台里它是这两个信号与观察窗口的合成判断。

> 阶段内容隔离：容器编排、探针配置、滚动更新的 K8s 原生语义属 ph12/ph16/ph19；本阶段用**内存状态机**复刻「期望状态 + 收敛」的决策逻辑，不涉及真实调度与容器运行时；推理引擎内部的批处理/KV Cache 属 cpp/ph23。

### 3.6 数据集与特征版本台账

模型的可靠性最终取决于**数据可追溯**：这份数据集是什么时候、由哪个任务产出的、内容校验和是多少。

| 概念 | 落点 | 用途 |
|------|------|------|
| 数据集版本 | `DatasetVersion(name, version, checksum, rowCount, createdBy)` | 训练任务提交时绑定版本；模型血缘引用它 |
| 特征版本 | `FeatureVersion(featureSet, version, transformHash)` | 训练与推理**必须用同一版本**，否则训练/推理偏斜（training-serving skew） |
| 快照一致性 | 校验和比对：任务读到的数据与登记版本一致 | 防止「数据被就地覆盖」导致的不可复现 |

**版本号按数值比较而不是字符串比较**：`v10 > v9` 用字符串比较会得到相反结果；examples/ex06 用数值版本并断言登记版本单调递增。

**training-serving skew 的三种成因**（这是特征版本存在的全部理由）：① **代码不同步**——训练用 pandas 算特征、线上用另一套实现，浮点或缺失值处理不一致；② **数据不同步**——训练读的是昨天快照，线上读的是实时流，同一实体的特征值不同；③ **时间语义不同**——训练用「事件时间」聚合，线上用「到达时间」聚合。`transformHash` 正是用来锁住 ①：即使两个 `version` 相同，只要变换逻辑变了也要拦下来。

**为什么用校验和而不是「版本 + 时间戳」**：时间戳只能证明「登记过」，不能证明「内容没变」；数据被就地覆盖（同一个路径重跑覆盖）时，时间戳毫无帮助，而校验和会让快照比对立刻失败。这也是**fail-closed** 的取舍——宁可在训练提交时报错，也不要在两周后追查「为什么指标对不上」。

> 阶段内容隔离：文件与校验和计算（`hashlib`/`sha256`）属各语言标准库阶段；数据格式与存储（Parquet/Iceberg 表格式、快照隔离）属湖仓方向（见第 5 章分工与第 7 章下一阶段）；特征工程与数据泄漏防范的方法论属 py/ph15。

### 3.7 多租户配额与计量

平台要能回答「这个月谁用了多少卡时」。计量是**先有事件、后有汇总**：每次分配/释放写一条计量事件，按租户累计（与 ph21 的计数器同构）。

```java
// examples/ex07-quota-metering/QuotaGuard.java —— 配额校验（提交前）+ 计量（运行中）
public record Quota(int maxGpus, int maxQueuedJobs, long maxGpuSecondsPerDay) { }
// 超限 → 拒绝并给出可读原因（"配额不足：GPU 12/8"），而不是静默排队
```

**为什么拒绝而不是排队**：排队会让用户以为「等一等就有了」，而配额是不会因为等待而变大的——**快速失败比长时间等待更友好**，这也是平台可用性的一部分。

**三个配额维度为什么都要**：只限「同时占用卡数」挡不住**刷小任务**（每个占 1 卡但提交上千个）；只限「排队数」挡不住大任务饿死别人；只限「日卡时」挡不住**上午把池子占满**。三者是三道不同的闸门：并发闸（maxGpus）、压力闸（maxQueuedJobs）、预算闸（maxGpuSecondsPerDay）。

**计量为什么用事件而不是定时采样**：采样会漏掉短任务（提交后 30 秒结束的任务在分钟级采样里可能一次都采不到），也会把「跨采样点的运行时长」算歪。事件驱动（分配/释放各一条 + 时间戳）天然精确，写入量还更小——这与 ph21 的「判据取端到端事实」是同一条纪律：**账要能对上**（示例断言「释放结算的 GPU·秒 == 按事件时间差手算的值」）。

> 阶段内容隔离：计费/账单系统（定价、出账、对账）属业务系统设计，超出本阶段；Prometheus 计数器与告警规则配置属 ph12/ph16/ph21 3.9；本阶段只做「配额校验 + 计量事件台账」这两件控制面的事。


### 3.8 可观测性与运维一屏

AI 平台的运维视图只需要回答四个问题：**队列堵不堵、卡用没用满、模型是哪个版本、服务健康不健康**。

| 指标 | 类型 | 用途 |
|------|------|------|
| `aiplat_jobs_queued` | gauge | 队列深度（扩容与告警依据） |
| `aiplat_gpus_allocated` / `_free` | gauge | 资源利用率 |
| `aiplat_jobs_total{state}` | counter | 成功率与失败归因 |
| `aiplat_model_versions{stage}` | gauge | 版本分布 |
| `aiplat_service_replicas_ready{service}` | gauge | 推理服务健康 |

> 阶段内容隔离：Prometheus/Grafana 的部署与告警规则配置是 ph12/ph16 的内容，本阶段只示范「平台自己该暴露哪些指标」以及运维一屏如何把四类对象聚合起来（与 ph21 3.8 同法）。

**四个问题的值班语义**（指标不是给仪表盘看的，是给决策用的）：

| 值班看到 | 说明什么 | 第一步动作 |
|------|---------|-----------|
| `aiplat_jobs_queued` 持续上涨 | 算力不足或调度卡住（大任务队头阻塞） | 看 `gpus_free`：为 0 → 扩容/降优先级；不为 0 → 查策略与形状（4.1） |
| `aiplat_gpus_allocated/_free` 长期高位但队列不长 | 资源被低效占用（长尾任务、空转碎片） | 查任务时长分布与回填是否生效 |
| `aiplat_jobs_total{state="FAILED"}` 抬头 | 任务失败潮（代码/数据/配额） | 按 `state` 与死信原因归因，必要时冻结提交 |
| `aiplat_service_replicas_ready` < 期望 | 推理服务在发布中或已崩 | 看是否在灰度期（正常）还是异常退出（回滚） |

**为什么一屏必须与指标同源**：示例里 `OpsConsole` 的快照与 Prometheus 文本由**同一份状态**渲染（ex08 断言两者逐项一致）。如果一屏另算一遍，就会出现「看板说正常、告警说异常」的经典事故——**值班视图只能有一个事实来源**。

## 4. 底层原理

### 4.1 调度器原理：优先级、回填与抢占

调度器的输入是「一批资源请求 + 当前空闲资源」，输出是「这一轮让谁跑」。四种机制的直觉：

- **FIFO 的队头阻塞**：队列头是一个要 8 卡的任务，池子只剩 4 卡 → 后面所有 1 卡任务全部卡住。这是最容易被忽略的容量陷阱。
- **回填（backfill）的价值**：若能**预估**队头任务还要等多久（例如知道它要 8 卡、当前 4 卡任务平均 20 分钟释放），就可以让「20 分钟内能跑完的小任务」先跑——利用率显著提升。代价是预估不准会推迟队头任务（工程上通常限制回填任务的数量与时长）。
- **优先级与老化**：纯优先级会让低优先级饿死；工业做法是「优先级 + 等待时间老化 + 每租户配额」三者叠加，保证有界等待。
- **抢占的代价**：抢占用「中断运行中任务」换取高优先级任务的及时性，前提是被抢占任务**可安全中断**（有 checkpoint 或可重跑）。因此抢占是策略而非默认：只在有 SLA 的场景开启。

**DRF（Dominant Resource Fairness）直觉一句话**：多资源类型（GPU/CPU/内存）下，「谁的**主导资源占比**最低谁先拿」——避免一个用户用大量 CPU 挤占 GPU 公平性。

### 4.2 控制器循环：期望状态与实际状态的收敛

声明式的核心不是「命令」而是「**目标 + 循环**」：

```text
loop:
    observed = 读实际状态（副本数/就绪数/当前版本）
    desired  = 读期望状态（spec）
    if observed == desired: 什么都不做
    else: 采取一步最小动作（起一个副本 / 停一个旧副本 / 切一批流量）
```

三个工程含义：**① 幂等**——同一轮重复执行不会产生额外副作用（所以动作要设计成「达到目标即停」）；**② 水平**——不记录「已经做到第几步」，而是每轮重新比较期望与实际（进程重启后自然恢复）；**③ 限速**——一次只推进一批（`maxSurge/maxUnavailable`），否则「收敛」会变成「雪崩」。

### 4.3 灰度发布的三要素收敛

一次推理服务发布同时改动**版本、副本、流量**三样东西，三者收敛顺序错了就会炸：

1. **先有副本**：新版本副本就绪 ≥ `maxUnavailable` 之前，流量一点都不能切（否则 5xx）。
2. **再切流量**：按比例切流，观察期看**业务指标**（延迟/错误率/评估指标），而不只是「进程活着」。
3. **最后改版本**：流量 100% 且观察期通过，才把「当前版本」指针指向新版本并归档旧版本。

回滚就是把这三步**反过来**且必须能在任意一步执行——所以状态机里「回滚」不是特殊路径，而是「期望状态改回旧版本 + 重新收敛」。

### 4.4 GPU 计量与配额的取舍

- **按卡时（GPU·hour）而不是按任务计费**：任务大小差异巨大，按任务计费会让小任务补贴大任务。
- **计量的精度取决于采样频率**：按分钟采样会漏掉短任务，按秒采样写入压力大；工程折中是「分配/释放事件 + 秒级时间戳」——事件驱动天然精确且写入量小。
- **显存是二级稀缺**：卡数够但显存不够时任务仍会 OOM，因此真实平台常把 `(卡数, 显存)` 作为二维资源；本阶段用「卡数 + 显存需求」两字段示范这个模型，不做真实 MIG 切分。

## 5. 使用场景

| 场景 | 用什么 | 为什么合适 |
|------|--------|-----------|
| 团队共享 GPU 集群 | 资源池 + 配额 + 优先级调度 | 稀缺资源的分配必须可解释、可审计 |
| 训练任务全生命周期管理 | 任务状态机 + 幂等提交 + 重试上限 | 提交/失败/重试是日常，状态必须显式 |
| 实验到生产的模型晋级 | 模型注册表 + 血缘 + 晋级门槛 | 「这个线上模型是哪次训练出来的」必须秒答 |
| 推理服务安全上线 | 期望状态收敛 + 灰度 + 回滚 | 模型发布是高风险变更，必须可回退 |
| 数据可复现 | 数据集/特征版本台账 | 训练与推理特征版本不一致是事故高发点 |
| 成本核算与配额治理 | 计量事件 + 配额拒绝 | 「谁用了多少卡时」是预算与公平的基础 |
| 平台值班 | 四个核心指标 + 运维一屏 | 队列/利用率/版本/健康一屏可判 |

**不适合用 Java 的地方**：训练执行本身（PyTorch 训练循环、分布式通信、自定义 kernel——Python/C++ 的领域）；推理引擎内核（KV cache、连续批处理、量化——推理引擎与 CUDA 的领域）；单机数据预处理脚本（Python 更趁手）。Java 的位置是**控制面**：把上述执行体当作黑盒进程来编排、计量与发布。这与 ph21 的分工一致：**Java 管状态与台账，执行体管算力与数据。**

```text
用户/CI ──提交任务──▶ 控制面（本阶段）
                     ├─ 配额校验（3.7）
                     ├─ 排队 + 调度决策（3.3）
                     ├─ 资源池分配 GPU（3.2）──▶ 训练执行体（PyTorch 作业，黑盒）
                     ├─ 任务状态机推进（3.1）◀── 执行体上报状态/退出码
                     ├─ 模型登记 + 血缘（3.4/3.6）◀── 训练产物
                     └─ 推理服务收敛与灰度（3.5）──▶ 推理执行体（副本）
                                    │
                                    └─ 指标与运维一屏（3.8）
```

图中箭头即「数据走向」：控制面只做决策与台账，执行体只做计算——**两者的契约是「状态上报 + 产物登记」**，这条边界让平台可以替换任意训练/推理实现而不改控制面，也是本阶段全部示例的骨架。

**与其他语言同类机制的对比**（一句话级）：Java 的强项是**领域建模 + 生态**（状态机、配额、事务、Spring 生态），适合控制面与后台；Python 的强项是**执行与生态**（训练、数据处理、推理胶水）；Go/Rust 的强项是**高并发基础设施与性能敏感组件**（调度器数据面、代理、网关）。三者组合才是完整 AI 平台，本阶段只负责 Java 那一层。

**为什么控制面适合 Java（而不是 Python）**：控制面的负载特征是「**低频、强一致、逻辑复杂**」——一天几万次提交、每次都要过配额/状态机/台账/审计，单次请求要跨多个对象保证一致性；它不缺吞吐，缺的是**把领域规则写清楚的能力**（值对象、不变式、状态机、事务边界、可测的纯函数）。这恰好是 Java 企业后端的舒适区。反之，数据面是「**高频、可重试、逻辑简单**」——一次前向/反向传播里没有业务分支，只有算力，用 Python/C++ 更合适。

**两层的契约必须是显式接口**：控制面对执行体只做三件事——**分配资源**（给卡）、**接收状态**（running/failed/退出码）、**接收产物**（模型文件位置 + 指标）。执行体对控制面只做一件事——**按契约上报**。示例把执行体抽象成「状态输入 + 产物输入」，因此本阶段全部代码可以离线确定性运行；真实落地时这一层换成 K8s Job / CRD 或训练框架的 launcher 即可，**控制面的领域逻辑不用改**。

**与 ph21 的分工**（同一个 Java 后端技能树的上下半场）：ph21 管**数据**（接入、清洗、指标、告警、发布、运维一屏），本阶段管**算力与模型**（任务、配额、版本、服务灰度）。两者共享同一套机制（DDD 状态机、SPI、CHM、灰度发布、审计），区别只在领域对象；真实平台里它们通常就是**两个独立服务**（数据平台后端 + AI 平台后端），通过 Kafka 或 API 交换「数据集版本」与「任务状态」。

## 7. 总结

### 关键要点

1. **AI 平台控制面是四类对象的领域建模**：任务（job）、算力（GPU）、模型（version）、服务（service）——其余全是这四者的状态机与台账
2. **状态机要把非法操作挡在聚合内**：终态不可变、重试有上限、迁移必审计（3.1）
3. **资源账本必须有不变量**：`allocated + free == total` 是可断言的安全网（3.2）
4. **调度策略即可插拔数据**：同一输入必须给出确定决策，否则「为什么排队 6 小时」无法复盘（3.3/4.1）
5. **回填用预估换利用率**：代价是预估不准会推迟队头任务，因此要限制回填任务的时长与数量（4.1）
6. **声明式 = 期望状态 + 控制器循环**：幂等、水平、限速三条纪律缺一不可（3.5/4.2）
7. **灰度发布要按「副本→流量→版本」顺序收敛**：反了就会打出 5xx，回滚是同一逻辑反向执行（4.3）
8. **模型版本是带血缘的台账条目**，不是一堆文件；禁止版本倒退、晋级要有门槛（3.4）
9. **数据可追溯是模型可靠性的前提**：训练与推理必须用同一特征版本（3.6）
10. **计量用事件驱动**：分配/释放事件 + 秒级时间戳，比采样更准且写入更少（3.7/4.4）
11. **配额超限要快速失败**：「等一等也没有」的排队是对用户的欺骗（3.7）

| 角色 | Java | Python | Go / Rust |
