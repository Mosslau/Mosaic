## 2. 来源与演变

数据平台不是一天长成「指标驱动」的，这条演进史本身就是本阶段每一节的存在理由。**设计哲学一句话：原始字节与文本日志（日志/规约）→ 结构化指标（CSV/JSON）→ 清洗与分析（Pandas/规则/模型）→ 服务与采集（HTTP/MQTT），每一步都是"降噪 + 升维"，Python 正好每一层都有成熟的胶水。**

- **数据仓库时代（1990s-2000s）**：企业把业务库的数据定期抽到仓库做报表（ETL + 星型模型），指标由分析师手工定义、按天出数——「数据要清洗后再用」的纪律从此确立，本阶段 3.2 的清洗管线是它在 Python 侧的现代形态。
- **大数据与实时化（2006-2015）**：Hadoop 让海量日志可存，Kafka 与流处理把「T+1 报表」推进到分钟级指标。指标的种类随之爆发：延迟、吞吐、错误率、资源水位成为平台运营的第一语言——本阶段的指标 schema 正是这套语言的缩影。
- **云原生可观测性的成型（2015-2020）**：Prometheus/Grafana 把「指标（metric）/日志（log）/链路（trace）」三支柱固化，采集端（exporter/agent）与存储端解耦、拉取与推送并存；SLO/错误预算把指标变成决策依据。本阶段 3.8 的采集链路与 3.6 的服务出口就是这条分工线的两端。
- **AIOps 与分析化运维（2018-）**：指标规模超过人工阈值可维护的范围后，出现三类业务：**规则告警**（已知故障，3.4）、**无监督异常检测**（未知/复合形态，3.7）、**容量与健康度预测**（什么时候该扩容/换盘，3.3）。Pandas/scikit-learn 因「分析速度 > 吞吐速度」成为原型与工具层首选——这正是 Python 数据栈的主场。

| 里程碑 | 年份 | 主要变化 |
|------|------|---------|
| 数据仓库 / ETL | 1990s | 数据先清洗再分析成为纪律 |
| Hadoop 生态 | 2006- | 海量日志可存、可算 |
| Kafka 实时管道 | 2011 | 指标从 T+1 走向分钟级 |
| Prometheus / Grafana | 2015- | 指标/日志/链路三支柱与采集端解耦 |
| SLO 与错误预算 | 2017- | 指标成为运营决策依据 |
| 云原生可观测性标准化 | 2019- | OpenTelemetry 统一采集协议与语义约定 |
| AIOps 异常检测 | 2020- | 规则 + 模型双轨的告警体系成熟 |

本文示例以 **Python 3.13** 为基线（当前 CPython 稳定大版本，与 ph17 基线一致）。本阶段代码分为两档验证：**纯标准库路径**（examples/ex01、exercises/sol-01~sol-04 离线路径、ex05 的 pytest 基础设施）只依赖 Python 3.13；**数据科学/服务路径**依赖 ph09/ph15/ph10 已装的第三方库（numpy/pandas/matplotlib/scikit-learn/fastapi/httpx，pytest + ruff 做验证与 lint；paho-mqtt 已装但其真实 broker 通道未在本环境验证）。**验证纪律**：examples/exercises/project 的 main 自检与 pytest 断言已在上述环境本机实测通过（文件头标注「已验证」，命令见各文件头与第 6 章）；ex08/sol-04 的 paho 真实 broker 路径如实标注「未在本环境验证」。这个阶段是 Python 3.x 时代**最稳定的一层**——pandas/sklearn/FastAPI 的 API 偶有演进，但「清洗→分析→服务→采集」的流水线骨架十余年不变，学的是骨架而非某个版本细节。

### 3.1 平台日志与格式规约解析

平台数据的最原始形态是**采集侧文本日志**：一行一条记录，内容只有时间戳、采集节点、来源 ID 与数据字节。常用行格式：

```text
(1685527200.123456) node0 123#AABBCCDD11223344
 时间戳             |   采集节点 | 来源 ID(hex) + # + 最多 8 字节原始数据(hex)
```

解析 = 一行一条 + 正则分组（examples/ex01 的 `parse_log_line`）。**为什么强调逐行流式**：一次采集会话的原始日志几十 MB 起步，`readlines()` 整读直接爆内存——这正是 ph17 生成器纪律的现成场景，ph17 project/ 的 streamlog 管线在此原样升级（只换行格式与过滤条件）。

但「123#7D…」对人是不可读的。**格式规约（format spec）** 把位翻译成物理量：它声明某条记录（`REC`）含哪些字段（`FLD`），每个字段给定起始位、长度、字节序、因子与偏移：

```text
REC 400 ServiceLatency: 8 collector__XXX
 FLD LatencyMs : 0|16@0+ (0.01,0) [0|650] "ms" collector__XXX
```

| 参数位 | 含义 | 例 |
|------|------|----|
| `起始位\|长度` | 字段在记录里的位级位置与位宽 | `0\|16` = 从 bit0 起 16 位 |
| `@0 / @1` | 字节序：0=小端（Intel），1=大端（Motorola） | `@0` |
| `+ / -` | 有无符号 | `+` |
| `(因子, 偏移)` | 物理值 = 原始值 × 因子 + 偏移 | `(0.01,0)` |
| `"单位"` `[min\|max]` | 单位与量程（教学子集只解析前四者） | `"ms"` |

解码公式与三类真实坑（ex01 逐条演示）：

| 坑 | 表现 | 处理 |
|----|------|------|
| ID 是十六进制、规约编号是十进制 | 日志 `123#` 指 0x123，规约里 `REC 291` 才是 0x123——两个体系，先对齐再比对 | 解析器统一转 int 再查表 |
| 字节序不同，字节排列相反 | 大端 16bit 字段高字节在前、小端反之 | `@0/@1` 分支 + 主文档 4.1 的位号推导 |
| 规则行与注释混杂 | `VERSION`/`NS_`/`BU_`/空行/`#` 注释 | 只认 `REC`/`FLD`，其余行跳过不报错 |

| 处理策略 | 说明 |
|------|------|
| 流式逐行 | 生成器产出 `LogRecord`，内存与文件大小无关（ph17 纪律兑现） |
| 先统计后解码 | 真正工程是按来源 ID 预聚合（几万个 ID 中 99% 的记录只需计数），命中规约的记录才解码——省掉海量无谓换算 |
| 非记录行容忍 | 注释/空行/坏 hex 一律跳过并计数，不中断整批 |

**来源 ID 的两个现实细节**：同一套文本行格式里既有 11 位短 ID（0x000~0x7FF）也有 29 位扩展 ID——正则按 hex 解析天然兼容，但**别拿短 ID 掩码去比长 ID**（ex01 样例里同时放了 `0x7B` 与 `0x190` 两类，用来验证查表不越界）。

> 阶段内容隔离：**完整格式规约规范**（多路复用、取值表、跨字节任意位级的大端位序换算）不在教学子集内——完整实现属成熟解析工具库（pip 安装后开箱即用），本阶段只实现小端任意位宽 + 大端字节对齐两类，够读懂绝大多数真实规约文件；相关推导见 4.1。

### 3.2 指标时序清洗：时间序列与异常值

原始指标的脏法只有四类，清洗管线按固定顺序处理（examples/ex02，每一步都计数）：

```python
# 1. 排序：滚动窗口与差分都要求时间有序（采集乱序到达，先排好）
# 2. 去重：QoS/重传机制可能产生完全重复行
# 3. 物理量程：超出物理可能的行直接剔除（延迟 5000 ms、CPU -5%）
#    RANGES = {"latency_ms": (0, 2000), ...}  —— 用常量表声明，不散落在代码里
# 4. 孤立尖峰：与局部中位数偏差 > 该列的秒级物理跳变量级 → 毛刺
```

| 步骤 | 判据 | 计数落点 |
|------|------|---------|
| 去重 | 全列相同（真实场景按 `(ts, service_id)` 指纹） | `dup_removed` |
| 物理量程 | 常量表 `RANGES` 逐列 | `phys_removed[列名]` |
| 孤立尖峰 | 局部中位数 ± 秒级跳变阈值 | `spike_removed[列名]` |
| 时间对齐 | 1Hz 重采样 + 短缺口前向填充 | `filled_rows` / `dropped_gap_rows` |

**尖峰阈值为什么用「物理量纲常量」而不是统计量**：经典的 3σ/MAD 会把「真实趋势」误判成毛刺（延迟曲线在负载爬升段每秒变化是合法的，σ 法在噪声小的窗口会把它们全揪出来）。改用一个物理判据——**1 秒内延迟跳 200ms+、温度跳 10℃+ 不可能是真信号**——判据可解释、行为可预测，调参时讨论的是「物理上可能吗」而不是「σ 取几」。

**清洗必须可审计**（roadmap 必会概念）：`CleanReport` 把每步剔除了多少行写进报告并可断言（`dup_removed == 1`、`phys_removed["latency_ms"] == 服务实例数`）——「清洗改了什么」必须可复现、可写进测试，否则数据质量问题永远查不清。

> 阶段内容隔离：pandas 的 `resample/rolling/ffill` 语法在 ph09 已讲，本阶段讲的是**组合成管线**的纪律（顺序、计数、缺口语义，见 4.2）。

### 3.3 资源健康度与容量标定

节点资源（磁盘/内存池）是平台最需要提前预测的部件。**健康度（HEALTH）**回答「这个资源还剩多少可用容量」：`HEALTH = 当前可用容量 / 额定容量`。额定容量写在机型标定表里（本阶段样例按 60 GB）。

容量不是直接测的，而是**从一次负载段的计量积分反推**：水位从 `usage_lo` 升到 `usage_hi` 期间系统计量到 E GB 的读写，则该段时间的可用容量 ≈ `E / (Δusage/100)`。examples/ex03 用 pandas 完成估计：

| 概念 | 含义 | 来源 |
|------|------|------|
| 水位 usage | 当前使用比例（%） | 直接来自节点上报 |
| HEALTH | 健康度（容量/读写/延迟口径） | 容量口径 = 反推容量 / 额定 |
| 负载段 | 一次连续的高负载周期 | 用水位上行 + 时间切分 |

用最小数字把「为什么 Δusage 太小不能信」走一遍：一次负载段从 40% 涨到 100%（Δusage=60%），计量到 35.8 GB，则容量估计 = `35.8 / 0.6 ≈ 59.7 GB`，HEALTH ≈ 99.5%。如果同一节点某次只从 90% 涨到 100%（Δusage=10%），同样的 1% 水位读数误差会让容量估计误差放大 6 倍——这就是「小跨度段估计不可信」的算术原因。

**写透的工程细节**：单次负载段估计噪声很大（水位读数是估算值，Δusage 小则误差被放大），所以要用**滚动中位数平滑**再读趋势；每个服务实例独立做（不同实例的负载习惯不同）；ex03 用「容量随负载周期数线性衰减 + 噪声」自造数据，让「HEALTH 应随周期递减」成为一个可断言的验收。真正的生产口径还要配合基线标定与传感器漂移补偿。

> 阶段内容隔离：**精确容量估计**（水位-计量标定曲线、计量计+传感器漂移补偿、等效模型、卡尔曼滤波）涉及估计理论与硬件标定，属于 ph09/ph15 分析技能之外的领域知识，本阶段只给「计量积分 + 平滑」的最小可行口径与 4.3 的原理级描述；生产环境通常由节点自身固件与专业工具完成。

### 3.4 故障定位与报表：规则引擎

故障定位有两种腿：**告警码** 是服务/节点自报的（由组件内部诊断产生）；**数据侧规则引擎** 是平台的事——拿不到内部码时，靠指标模式的持续异常推断（磁盘温度持续 >75℃、CPU 60s 骤降 >15%、吞吐塌陷）。本阶段示范后者，核心是**把规则声明化、把检测通用化**（examples/ex04）：

```python
@dataclass(frozen=True, slots=True)
class FaultRule:
    name: str
    severity: str            # high / medium / low
    alert_code: str          # 平台告警码（可对账工单系统）
    description: str
    check: Callable[[pd.DataFrame], pd.Series]   # 输入 df，返回布尔 Series

FAULT_RULES = (
    FaultRule("overheat", "high", "P0A80", "节点磁盘持续高温（>75℃ 滚动均值）", _rule_temp_high),
    FaultRule("usage_cliff", "high", "P0AC4", "CPU 60s 内骤降 >15%", _rule_usage_fast_drop),
    ...
)
```

命中检测按服务实例做**连续段合并（runs）**：同一规则连续命中的若干秒合并成一条事件（含起止时刻与窗口内量级），避免 30s 过热刷出 30 条告警。规则库里 `_rule_sensor_stuck` 是教学增量——「延迟方差为 0 但功耗照常有输出 → 指标疑似冻结」，它示范**跨指标规则**：单看任一指标都合法，组合起来才是异常。事件直接落两类可交付物：Markdown 报表（按级别汇总 + 事件明细表）与 Matplotlib 分布图（Agg 后端 + 中文字体回退，服务器无显示环境也能出图）。

> **注意**：规则引擎的痛点是**漏报与误报的边界**——阈值写死会在「新实例正常运行」和「老实例性能衰减」间误报。工程解法是规则 + 统计基线双轨：规则抓已知故障，统计分布（如延迟分位数）识别群体偏移；后者是 3.7 异常检测的入口。规则「能解释」、模型「能覆盖」——两者互补而不是二选一。

数据平台的出口是服务：前端 Dashboard、运维后台、运营报表都打 API。ph10 讲过 FastAPI 路由与 pydantic、ph16 讲过 uvicorn 部署，本阶段示范**数据服务层**长什么样（examples/ex06）：


| 端点 | 干什么 |
|------|--------|
| `GET /health` | 存活探针（ph16 的部署检查用） |
| `GET /services` | 服务实例列表 |
| `GET /services/{sid}/summary` | 单实例统计摘要 |
| `GET /services/{sid}/series?field=&from_ts=&to_ts=` | 时间序列切片（画曲线用） |

一个架构取舍值得写透：**离线算 vs 实时算**。ex06 走「启动算好、请求只读」的缓存路径——对分钟级更新的看板统计是正确的，摘要/事件这类**可增量**的结果根本不该每次请求重算；而 `POST /services/{id}/metrics` 这类**实时入口**则相反，它不该落到 pandas 里做批处理，而是边校验边落存储（ex08 的 JSONL sink 就是它的雏形）。判据一句话：**数据变化频率 >> 查询频率，就预计算；查询频率 >> 数据变化频率（热数据/实时告警），才实时算**——把这条记住，服务层的"缓存还是实时"就不再是玄学。

### 3.7 AI 异常检测：Isolation Forest 落地

规则引擎抓已知故障，**未知/复合故障**要靠无监督异常检测。ph15 教过 sklearn 建模，本阶段示范它在指标上的落地形态（examples/ex07）：**特征不是原始指标，而是「指标 + 窗口形态」**——原始延迟、温度等 5 列 + 各自的 20s 滚动均值/标准差，让模型能识别「这段的形态不像平常」：

```python
model = IsolationForest(n_estimators=200, contamination=0.05, random_state=0)
model.fit(features)                      # 无监督：fit 只用 X，不带 label
scores = model.decision_function(features)
flagged = scores < 0.0                   # 校准阈值：负分 ≈ 离群
```

**为什么选 Isolation Forest**（对比选型表，直觉见 4.4）：

| 算法 | 特点 | 本场景取舍 |
|------|------|-----------|
| Isolation Forest | 随机切分、路径深度判异常；线性、免距离度量 | ✅ 默认首选：快、吃高维、`random_state` 可控 |
| One-Class SVM | 核方法找超球面边界 | 大数据慢、参数敏感，留作对比 |
| Local Outlier Factor | 邻居密度 | 高维下距离退化，弱于 IF |
| 深度时序模型（LSTM/Transformer 类） | 学时序结构 | 数据量门槛高，超出本阶段（ph15 之后的进阶方向） |

写透的工程点：① **contamination 参数校准阈值**——设 `contamination=0.05` 后模型会把训练集约 5% 的样本校准为负分，所以判别阈值取 `0.0` 而不是拍一个经验值（ex07 注释里写明了这个机制，见 4.4）；② **评估要埋点**——无监督没有标签，但工程上必须用「注入的已知异常」做 recall/误报率验收（ex07 生成数据时埋过热段与指标冻结段，label 列只用于评估、绝不进 fit）；③ **召回与误报的取舍是业务决策**——告警通道会打扰用户，`fp_rate ≤ 15%` 这类阈值要写进验收而不是放任默认。

窗口形态特征的具体长法（ex07 的 `build_features`，一段话讲清逻辑）：对每条原始指标列再追加两列派生特征——`rolling(20s).mean()` 表达"近 20 秒的常规水平"，`rolling(20s).std()` 表达"近 20 秒的波动幅度"。于是「延迟冻结在低位但功耗正常」这类故障，在原始值层面完全合法（延迟 15 ms 合法、功耗合法），但它的窗口 std 与"正常运行时的功耗-延迟联动形态"显著偏离，模型才有抓手。**头 19 行的窗口特征天然是 NaN（窗口没攒够）——直接 dropna 丢弃，训练与评分用同一套对齐**，ex07 主函数里特意做了与训练同序的对齐，避免「特征行数、结果行数」的长度错位。

> 阶段内容隔离：特征工程、模型评估（precision/recall/交叉验证）、数据泄漏防范等方法论细节在 ph15 已讲，本阶段不再展开；这里示范的是「把 IF 接进数据平台流水线」的工程形态——特征怎么从时序里来、阈值怎么校准、怎么证明它有用。

### 3.8 MQTT 采集

采集端数据上行常用 **MQTT**：发布/订阅模型 + 弱网优化（QoS、断线续传、遗嘱），一个 broker 扛成千上万个采集端。主题是**主题树**，路由信息天然编码在主题里：

```text
svc/V001/metrics       ← 单实例指标
svc/V001/event         ← 单实例事件
svc/+/metrics          ← 订阅所有实例的指标（+ = 单层通配）
```

| 维度 | 说明 |
|------|------|
| QoS 0 | 至多一次（尽力而为），最快 |
| QoS 1 | **至少一次**——可能重复投递 → 业务层必须去重（sol-04 的验收点） |
| QoS 2 | 恰好一次，最重，指标场景很少用 |
| retained | broker 保留最后一条消息，新订阅者立即收到（常给状态类主题） |

写透的两条工程注意：**retained 主题 ≠ 状态数据库**——订阅者上线瞬间收到的 retained 消息是"最近一次快照"，要处理"可能过期"的语义（配合消息里的 `ts` 判断新鲜度，比信 broker 时序更可靠）；**clean session 与离线缓冲**——采集端弱网重连时 broker 是否补发离线消息由会话标志决定，采集端因此既可能收到**重复帧**（QoS1 补发 + 去重解决）也可能收到**乱序帧**（以 `ts` 为准排序，不要以到达顺序为准）——这解释了为什么**业务层**必须把「去重」「按 ts 排序」内建（练习 4 sol-04 的去重窗口），而不是指望 broker 保证。

采集服务的正确组织方式是**把 broker 胶水与业务逻辑解耦**：paho 只负责「与 broker 的传输」，采集核心（主题路由 → JSON 解析 → 量程校验 → 落 sink）与 broker 无关，可以用一个 **FakeBroker**（内存里直接回调 `(topic, payload)`）离线全量单测——这正是「自动化测试要可重复」在采集环节的体现。examples/ex08 演示这条骨架（sink 可换 Memory/Jsonl），练习 4 的参考实现（sol-04）在骨架上补**去重窗口**与**按日分桶**（完整形态见下）：


写透的工程点：① **采集审计**——「有效/无效/重复」计数是采集服务的健康仪表盘：ex08 骨架记三类（`accepted`/`invalid_payload`/`invalid_topic`），sol-04 扩到四类（重复帧单列 `duplicate`、错主题路由单列 `bad_topic`），掉线/脏数据比例异常都能从这里看出来（roadmap「可审计」必会概念）；② **QoS1 的重复由业务层去重**——同一 `(service_id, ts)` 只收一次（sol-04 的去重窗口）；③ **按日分桶**——JSONL 文件名带日期，单文件无限增长是运维事故（sol-04 的 `data-YYYYMMDD.jsonl`）；④ **sink 可替换**——Memory（测试）/ JSONL（落地）/ 数据库（生产），采集核心不感知（ex08 已演示前两者）。

## 4. 底层原理

### 4.1 格式规约的位级布局与字节序

格式规约的 `start_bit|length@字节序` 是一段**位级寻址**。以 8 字节记录为例，把字节展开成位，位号约定为 `byte×8 + bit`（bit 从 0=LSB 数到 7=MSB）：

- **小端（规约 `@0`）**：`start_bit` 是字段 **LSB** 的位号，其余位向高位连续延伸。如 `0|16@0+`：取 bit0~15，原始值 = `data[0] + data[1]<<8`（小端）。实现上逐位读、`raw |= bit << k` 即可——这与 CPU 小端编码同构。
- **大端（规约 `@1`）**：字段以字节序摆放，**高字节在低地址字节**。任意位级的大端位号换算复杂（各家实现有细节差异）；教学子集只支持**字节对齐**字段（`length % 8 == 0` 且 `start_bit % 8 == 7`），按字节切片 `int.from_bytes(..., "big")` 即可。

**为什么有 factor/offset**：原始值通常是整数编码（如 0~16000 的速率），为了省 bit 用缩放映射到物理域——`物理值 = raw × factor + offset`。**offset 不为零的常见原因是负值用偏移编码**（如温度 -40℃ 编码为 0）。这层换算把「传输用的整数」与「分析用的物理量」解耦，是规约文件存在的全部意义。

**教学子集为什么敢裁大端任意位级**：字节对齐是实际规约文件里最常见的形态（8/16/32 位的延迟、速率、温度几乎都对齐），覆盖了 90% 的阅读场景；剩余部分交给成熟库即可，把精力留在「读懂链路」上。

### 4.2 时间序列的对齐、重采样与缺口语义

指标天然是**不规则时间序列**：上报受采集周期、网络拥塞影响，到达时刻并不整齐。把不规则流变成规则网格（对齐）的机制分两层：

1. **重采样（resample）**：按固定频率（如 1Hz）生成完整时间网格，原数据落到最近的网格点，没数据的位置成为 NaN。
2. **填充（fill）**：对 NaN 选择语义——前向填充（保持上一次的值）、线性插值、或丢弃。

| 语义选择 | 假设 | 什么时候用 |
|------|------|-----------|
| `ffill`（前向填充，短缺口） | 缺口内指标保持稳定 | 秒级丢包 |
| 丢弃长缺口 | 缺口本身是事实（断线/重启） | 超过阈值（如 3s）的缺口 |
| `interpolate` | 指标线性过渡 | 平滑连续量 |

- **填充语义要选对**：`ffill` 假设指标在缺口内保持（采集端短掉线时近似成立）；`interpolate` 假设线性过渡；`bfill` 反向。**短缺口补、长缺口不补**的理由是：3s 掉线大概率是丢包，30s 掉线可能意味着采集端重启/断网——后者是故障本身，补了会掩盖。ex02 用 `FFILL_LIMIT` 把这条约定写进常量并计数。
- **下游消费的隐含假设**：1Hz 网格让「画曲线、差分算变化率、窗口积分」都变成朴素操作，代价是**误差被网格化**（真实采样时刻与网格时刻的错位被忽略）。对温度这类慢变量无碍，对突发延迟这类快变量会有锯齿——需要时用原始时间戳 + 加权积分，本阶段不展开（这是时序库/专用分析引擎的领域）。

**什么时候不用 resample**：如果两类指标**周期不同**（如延迟 10Hz、温度 1Hz），要对齐的是「每个 10Hz 时刻最近的 1Hz 温度值」而不是强行重采样——pandas 的 `merge_asof`（最近邻 join）才是正解；而若只是要聚合（如按小时算平均温度），`resample().agg()` 直接给答案，不必先生成完整网格。判据：**要"逐点对齐"用 asof，要"分段汇总"用 agg，只有"等间隔序列本身"才需要 resample**。

### 4.3 资源容量标定原理

节点资源不是黑箱，而是**可标定的计量系统**。最小可解释模型有两块：

- **水位-计量关系**：水位（usage）与累计读写量之间近似线性，标定的斜率即容量。一次负载段的计量读数越完整，容量估计越准——而其误差来源正是「水位读数是估算值」：Δusage 越小，水位读数误差对容量估计的放大越厉害（ex03 用滚动中位数平滑正是对冲这一点）。
- **计量积分**：`Δusage = ∫速率 dt / 容量`，但速率读数有偏置，误差随时间**线性累积**——这是「为什么不能长期靠积分算水位」的机制答案，也是容量估计要回到**大跨度段**（Δusage 足够大以稀释偏置影响）的原因。

健康度的行业口径不止容量一种：容量口径（还能存多少）、读写口径（吞吐能力是否衰减，同样负载下延迟上升 30% 即显著老化）、延迟口径（能保证多快的响应）。本阶段用容量口径：`HEALTH = 反推容量 / 额定容量`。读写口径的机制一句话：同样负载下端到端延迟 = 基础延迟 + 排队项，把两次不同负载下的延迟对比即可反推服务能力衰减——本阶段不展开（属专业监控工具范畴）。

> 为什么要把「估计」讲成「标定」：真实平台里容量不是算出来的，是**标定出来的**——厂商给额定值、运行时用负载段不断校准，估计只是把标定做成持续过程。理解这一点，就不会把一次估计的偏差当事故。

### 4.4 异常检测的算法直觉：为什么"孤立"能当异常

Isolation Forest 的核心直觉一句话：**异常点更容易被随机切分"孤立"**。随机选一个特征、随机选一个切分点，重复切；正常点分布密集，需要很多刀才能被单独切出来（路径长）；异常点稀疏，几刀就落到单独区间（路径短）。

- **打分 = 路径长度的函数**：`score = 2^(-E[h(x)]/c(n))`，路径越短分越高（越异常）；`c(n)` 是 n 个样本的二叉搜索树平均路径，用来做归一化。
- **为什么不需要距离/密度**：它只依赖「切分次数」，因此在高维下不像 LOF 那样受距离退化影响，也不需要假设分布形状——这正是它在指标场景好用的原因。
- **contamination 的机制**：训练时按该比例把得分最低的样本校准为负分，因此判别阈值取 `0.0` 而不是经验值——参数一改，阈值语义不变，这是工程上最省心的一点。

模型的输出是**分数不是判决**：`flagged = score < 0.0` 之后要不要告警、告警合并窗口多大、误报预算多少，都是业务决策（3.7 的 fp_rate 验收就是把它显式化）。这也是「规则 + 模型双轨」的由来：规则给确定性与可解释性，模型给覆盖面。

把本阶段八件套放进一条端到端的数据平台链路，每一环都指向一个已交付的示例/练习（这也是"真实工程落点"的最终形态）：

图中箭头即"数据走向"：链路两端（采集、服务）是常驻进程，中间（清洗、分析、模型）是批处理——**两端用进程守护（ph16），中间用调度器触发**，这就是数据平台分析层的最小骨架，也是本阶段全部示例最终长成的样子。

## 7. 总结

### 关键要点

1. **流水线骨架即本阶段**：日志 → 清洗 → 分析 → 报表/服务/异常检测/采集，每一环都是前面某个 ph 的技能组合——应用整合层的价值在于**组装纪律**（边界、可审计、可离线测）
2. **日志/规约的翻译链**：文本行(hex) → 规约位级解码 → 物理量；解码公式 `物理值 = raw × factor + offset`（3.1/4.1）
3. **流式是原始数据的第一纪律**：采集日志几十 MB 起，逐行生成器 + 先统计后解码（3.1，ph17 承诺兑现）
4. **清洗的顺序与计数不可省**：排序 → 去重 → 量程 → 尖峰 → 对齐，每步计数让清洗可审计、可断言（3.2）
5. **尖峰阈值用物理常量而非统计量**：可解释、可预测，避免把真实趋势误判成毛刺（3.2/4.2）
6. **健康度 = 当前容量/额定**：负载段计量积分 + 滚动中位数平滑，是成本最低的容量口径（3.3）
7. **规则抓已知、模型抓未知**：规则给可解释性，Isolation Forest 给覆盖面，双轨并行而非二选一（3.4/3.7）
8. **测试分三层**：单测测逻辑、门禁测规格、golden 测输出漂移（3.5）
9. **服务层是编排层**：pydantic 守边界、纯函数算结果、缓存与实时按「变化频率 vs 查询频率」取舍（3.6）
10. **采集必须自带审计**：QoS1 会重复、主题会错、载荷会脏——业务层去重 + 计数 + 按日分桶（3.8）
