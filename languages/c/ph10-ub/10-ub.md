# C 语言未定义行为 UB 与常见坑阶段

> 面向系统底层、存储引擎方向，本阶段识别并避免 C 中最危险的一类错误——未定义行为（undefined behavior, UB）。

## 1. 概述

未定义行为与常见坑阶段是 C 学习路线中"从会写代码到写安全代码"的转折点。目标：**能识别并避免 C 中最危险的一类错误**——理解 UB 不是"结果不确定"，而是"编译器可做任何假设"；能解释至少 5 种 UB、用 ASan/UBSan/Valgrind 复现并定位、在代码评审中主动发现危险写法。

| 核心维度 | 覆盖内容 |
|----------|---------|
| 数组越界 | 越界读写的后果差异、ASan/UBSan 检测 |
| 指针类坑 | 空指针、野指针、悬空指针、use-after-free、double free |
| 整数运算 | 有符号溢出 vs 无符号回绕、除零、移位 |
| 未初始化变量 | 栈垃圾值、不确定值、编译期警告与 Valgrind 定位 |
| 严格别名与类型双关 | strict aliasing、memcpy 正解 |
| 对齐访问 | 未对齐访问的 UB、字节流解析 |
| 字符串与缓冲区 | 缺 \0、strcpy 类溢出、边界检查 |
| 检测工具 | ASan、UBSan、Valgrind 的定位思路（仅作演示工具） |

本阶段承接 ph09：ph09 讲清了标准、编译器与可移植性，并埋下 restrict、类型双关、有符号溢出三个伏笔——本阶段把它们系统化排查；同时把 ph03 的"指针越界访问是未定义行为"、ph04 的"越界/泄漏/double-free/use-after-free"提升到"能解释原理、能用工具复现、能在评审中识别"的层面。

## 2. 来源与演变

**未定义行为的概念随 C 标准化而诞生**。K&R 时代（1978）没有"未定义行为"这个分类，各编译器对同一段错误代码各做各的。1983 年 ANSI 成立 X3J11 委员会起草 C89 时，面对"8 位单片机到 64 位主机"的巨大硬件差异，必须给实现留出自由度——于是把程序行为分成**定义行为**（defined behavior）、**未指定行为**（unspecified behavior）、**实现定义行为**（implementation-defined behavior）与**未定义行为**（undefined behavior）四档。C89 对 UB 的权威定义是：**"使用不可移植或错误的程序构造、错误数据或不确定值对象时，本标准不施加任何要求的行为"**——注意用词：**不施加任何要求**（imposes no requirements），这是 UB 一切"离谱表现"的法理源头。

**编译器优化是 UB 威力放大的推手**。现代 GCC/Clang 的优化 pass 把"程序不含 UB"当作推理前提（as-if 规则 + 无 UB 假设）：有符号溢出被假设永不发生，于是循环可以被向量化、分支可以被判定为死代码删除；严格别名被假设成立，于是 load 可以缓存、store 可以重排。后果是：**同一份 UB 代码，-O0 下"碰巧能跑"，-O2 下行为突变甚至整段逻辑被删**——这正是 roadmap 必会概念"UB 可能在优化级别变化后暴露"的由来，也是本阶段实测反复出现的现象（见 4.1/4.2 与示例 6）。

**检测工具随漏洞产业一起演进**。2002 年 Valgrind 用动态二进制插桩检测未初始化读与越界；2011 年前后 Google 开源 **AddressSanitizer（ASan）**，用编译期插桩 + shadow memory 精确捕获越界与 use-after-free，GCC/Clang 直接内建 `-fsanitize=address`；随后 **UBSan**（`-fsanitize=undefined`）覆盖溢出、除零、移位、对齐等"逻辑型 UB"。如今 ASan/UBSan 已是 C 工程与 CI 的事实标配（工具链本身的工程化是 ph11 的内容，本阶段只把它们当复现工具用）。

| 里程碑 | 年份 | 意义 |
|--------|------|------|
| K&R C | 1978 | 无 UB 分类，同一段错误代码各编译器各做各的 |
| C89（ANSI X3J11） | 1989 | 首次把行为分为定义/未指定/实现定义/未定义四档，给出 UB 权威定义 |
| C99/C11 | 1999/2011 | 四档分类保持不变；C99/C11 均明确无符号整数按模 2^N 回绕是定义行为（C99 6.2.5p9 已有，C11 沿用） |
| Valgrind | 2002 | 动态二进制插桩检测未初始化读、越界与泄漏 |
| AddressSanitizer | 2011 | Google 开源，编译期插桩 + shadow memory，约 2 倍开销精确捕获越界与 UAF |
| UndefinedBehaviorSanitizer | 2012 起 | 覆盖溢出、除零、移位、对齐等逻辑型 UB，开销极小 |

| 行为类别 | 定义 | 例子 |
|---------|------|------|
| 定义行为 defined | 标准明确规定结果，所有实现一致 | 不溢出的整数算术、数组内下标访问 |
| 未指定行为 unspecified | 结果在某个合法取值集合中由实现任选，**无需文档** | 函数实参的求值顺序、结构体 padding 的内容 |
| 实现定义行为 implementation-defined | 实现必须**文档化**自己的选择 | `int` 的宽度、`char` 有无符号、负数右移 |
| 未定义行为 undefined | 标准完全不约束，任何结果都可能 | 越界访问、有符号溢出、解引用空指针 |

本文示例以 **C11** 为基线（C99 之后、C23 普及之前，GCC/Clang/MSVC 支持度最一致的公共子集；UB 的四档分类与各类别的定义在 C89~C23 之间没有实质变化），现代工具链（GCC 11+/Clang 16+）默认支持 C11，无需额外选项。验证工具链：Apple clang 21.0.0（macOS arm64，即 `cc`）；GCC 未在本环境提供（macOS 的 `gcc` 实为 Apple clang），涉及 GCC 特有行为的表述已标注。这个阶段的语法是 C 标准中最稳定的部分——四档行为分类从 C89 至今未变，本阶段讲的内容二十年不变。

## 3. 语法与参数

### 3.1 什么是未定义行为：四类行为对比

C 标准把程序行为分成四个等级（见第 2 章四类行为表），**未定义行为**的特权是：标准对结果不做任何要求——程序可能按预期运行、可能崩溃、可能打印垃圾，也可能"编译器认为这段代码不存在"。本阶段必会概念第一条：**UB 不是"结果不确定"，而是"编译器可做任何假设"**。

```c
/* 危险示例：勿运行 —— 有符号溢出是 UB, 行为随优化级别变化 */
#include <limits.h>
#include <stdio.h>
int main(void) {
    int i = INT_MAX;
    i = i + 1;                /* UB: 有符号整数溢出 */
    printf("i = %d\n", i);    /* -O0 下常见回绕, -O2 下结果完全不可预测 */
    return 0;
}
```

| 类别 | 对编译器的意义 | 检测手段 |
|------|--------------|---------|
| 定义行为 | 无假设空间，结果唯一 | 无需检测 |
| 未指定行为 | 在合法取值集合内任选（无需文档） | 读标准 |
| 实现定义行为 | 实现文档化选择即可 | 查编译器手册 |
| 未定义行为 | **可做任何假设，包括"这段代码不存在"** | ASan/UBSan/Valgrind + 代码评审 |

**要点（坑必背）**：UB 从你写下那一行起就"生效"，与运行时的表象无关——"我跑起来没问题"不能证明没有 UB，只能证明**当前优化级别下碰巧没暴露**；判断一段代码是否 UB 的唯一依据是 C 标准，不是实验结果。

### 3.2 数组越界读写

C 数组不携带长度信息、不检查边界（ph03 已埋下伏笔）：`arr[i]` 的 `i` 越界时编译器照常生成读写指令，读写的是数组**相邻内存**。roadmap 必会概念：**越界写通常比越界读更危险**——越界读最多读到垃圾值（信息泄漏），越界写会**破坏相邻对象**，甚至覆盖栈帧返回地址或堆元数据（见 4.3）。

```c
/* 危险示例：勿运行 —— 越界写覆盖相邻数据 */
#include <stdio.h>
int main(void) {
    int arr[3] = {1, 2, 3};
    int other = 42;
    arr[3] = 100;            /* UB: 越界 1 个元素, 常覆盖 other */
    arr[5] = 200;            /* UB: 越界更远, 可能踩坏返回地址 */
    printf("arr[0]=%d other=%d\n", arr[0], other); /* other 可能已被改成 100 */
    return 0;
}
```

**后果**：越界读 → 读到相邻对象/栈垃圾（信息泄漏、逻辑错乱）或访问未映射地址崩溃；越界写 → 相邻对象被篡改（静默数据损坏）或返回地址被覆盖（崩溃、任意代码执行）。
**工具**：ASan（`-fsanitize=address`）在对象四周布红区，越界即报 `stack-buffer-overflow`/`heap-buffer-overflow` 并给出行号；组合 Sanitizer（`-fsanitize=address,undefined`）下 UBSan 的越界检查会**先于** ASan 报告（实测先报 `index 3 out of bounds for type 'int[3]'`）；编译期 `-Wall` 的 `-Warray-bounds` 对常量下标也能直接警告（实测触发）——先听编译器的，再上工具。
**修复**：读写前检查索引（`0 <= i && i < len`）；把"长度"与数组一起封装（如 ph04 的 DynArray、示例 5 的 sstr）；遍历用 `i < len` 而非 `i <= len`——**off-by-one 是最常见的越界来源**。

### 3.3 空指针与野指针解引用

**空指针**（null pointer）解引用是 UB——实际平台上几乎总是段错误（SIGSEGV），但标准层面它和任何 UB 一样"无约束"。**野指针**（wild pointer）是"从未初始化过的指针"，值是栈垃圾（见 3.6），解引用可能落到任意地址：多数崩溃，少数"碰巧"落在合法内存上静默破坏数据——比空指针更难排查。

```c
/* 危险示例：勿运行 —— 空指针与野指针解引用 */
#include <stdio.h>
#include <stdlib.h>
int main(void) {
    int *p = NULL;
    *p = 1;                  /* UB: 解引用空指针 → 通常段错误 */
    int *q;                  /* 野指针: 未初始化 */
    *q = 2;                  /* UB: 写入随机地址, 行为不可预测 */
    (void)p; (void)q;
    return 0;
}
```

**后果**：空指针 → 段错误（至少会暴露）；野指针 → 随机地址读写，可能在千里之外破坏数据。
**工具**：UBSan 的 `-fsanitize=null`（属 undefined 组）报 `store to null pointer of type 'int'`（实测）；NULL 解引用也可用 GDB/core dump 直接定位；野指针几乎只能靠 ASan 的地址随机化 + 代码评审发现。
**修复**：`malloc` 后立即检查 NULL；**指针声明即初始化**（`int *p = NULL;`）；使用前判空；解引用前想清楚"这个指针的值从哪来、谁保证它此刻有效"。

### 3.4 悬空指针、use-after-free 与 double free

**悬空指针**（dangling pointer）指向已释放（free 过）的内存；继续在它身上读写就是 **use-after-free（UAF）**；对同一指针 free 两次是 **double free**。三者共同根因是内存生命周期管理失误（ph04 的"谁申请谁释放"）。

```c
/* 危险示例：勿运行 —— use-after-free 与 double free */
#include <stdio.h>
#include <stdlib.h>
int main(void) {
    int *p = malloc(sizeof(int));
    if (p == NULL) return 1;
    *p = 7;
    free(p);                 /* p 成为悬空指针 */
    *p = 8;                  /* UB: use-after-free, 改写已归还的内存 */
    free(p);                 /* UB: double free, 堆元数据损坏 */
    return 0;
}
```

**后果**：UAF 读 → 读到被复用/篡改的数据（经典安全漏洞类别，CVE 高发区）；UAF 写 → 覆盖分配器正在复用的块，数据损坏或任意代码执行；double free → 堆空闲链表被破坏，崩溃或堆利用。
**工具**：ASan 精确捕获，报告 `heap-use-after-free`（附分配栈与释放栈）与 `attempting double-free`（examples/ex03-uaf.c 实测两种报告）。
**修复**：free 后立即置 NULL（防当前别名误用，不能防其它别名；`free(NULL)` 合法，置 NULL 后"重复 free"无害）；文档化所有权（谁申请谁释放、释放后指针无效）；清理结构体时注意顺序（先释放成员再释放容器，别反了）。

### 3.5 有符号整数溢出（无符号回绕是定义行为）

**有符号整数溢出是 UB**（`INT_MAX + 1`、`INT_MIN - 1`）；**无符号整数运算按模 2^N 回绕，是定义行为**（`UINT_MAX + 1 == 0`）。区别在标准对无符号类型"永不溢出"的规定（C11 6.2.5p9）。这是 roadmap 学习内容，也是必会概念"UB 可能在优化级别变化后暴露"的主要案例。

```c
/* 危险示例：勿运行 —— 有符号溢出; 无符号回绕是安全的 */
#include <limits.h>
#include <stdio.h>
int main(void) {
    int a = INT_MAX;
    a = a + 1;               /* UB: 有符号溢出, -O2 下编译器假设永不发生 */
    printf("a = %d\n", a);
    unsigned int u = UINT_MAX;
    u = u + 1;               /* 定义行为: 回绕为 0 */
    printf("u = %u\n", u);   /* 稳定输出 0 */
    return 0;
}
```

**后果**：`-O0` 下常见"碰巧回绕"（像无符号一样，本环境实测打印 -2147483648），`-O2` 下编译器按"永不溢出"优化，结果可能是任意值（见 4.1 删分支的例子）。
**工具**：UBSan（`-fsanitize=undefined`）报 `signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'` 并给行号（实测）；同段代码里的无符号回绕 `0u - 1u` **不报错**（examples/ex02-overflow.c 实测）——"无符号回绕是定义行为"在此直观可见。
**修复**：先判断再运算（`if (a > INT_MAX - b) 报错; else sum = a + b;`）；用 `int64_t` 放大中间结果；GCC/Clang 提供 `__builtin_add_overflow(a, b, &out)` 返回是否溢出；计数器、长度、偏移这类"必然增长"的字段要主动防御。
**隐藏坑**：`int` 与 `unsigned` 混算时 `int` 隐式转成 `unsigned`——`-1 < 1u` 是**假**（`-1` 变成 `UINT_MAX`），这类"伪溢出"逻辑错误也是评审重点。

### 3.6 未初始化变量（栈垃圾值）

栈上局部变量不初始化 = 读**栈上残留的垃圾值**（上一次函数调用留下的数据）；`malloc` 返回的内存同样未初始化（`calloc` 才清零）。标准称其为**不确定值**（indeterminate value）：读取它至少"值不确定"，优化器还允许按任意值推理——所以 `if (x > 0)` 这样的分支在 -O0/-O2 下可能走向不同。

```c
/* 危险示例：勿运行 —— 读取未初始化局部变量 */
#include <stdio.h>
int main(void) {
    int x;                   /* 未初始化: 栈垃圾值 */
    if (x > 0)               /* UB: 条件依赖不确定值 */
        printf("正数: %d\n", x);
    else
        printf("非正数: %d\n", x);
    return 0;
}
```

**后果**：值是"不确定值"——本环境实测多次运行输出**相同的**垃圾值（栈布局恰好稳定），但这纯属偶然：换调用上下文、换编译器、换优化级别即变；严重时未初始化指针/索引直接导致崩溃或越界。
**工具**：编译期 `-Wall -Wextra` 的 `-Wuninitialized` 警告能直接指出 `x` 未初始化（Apple clang 实测 `-O0`~`-O2` 均触发；GCC 的同类警告部分场景需要优化级别才生效）；运行时用 Valgrind 报 `Conditional jump or move depends on uninitialised value(s)`，加 `--track-origins=yes` 追溯"这个值在哪创建"（本机无 Valgrind，未在本环境验证）；MSan（`-fsanitize=memory`）需全程序插桩，成本高。
**修复**：**声明即初始化**（`int x = 0;`）——这是 roadmap 必会概念"初始化和边界检查是 C 代码的生命线"的一半；结构体用 `= {0}` 或 `memset` 清零；需要零值内存用 `calloc`。

### 3.7 严格别名规则与类型双关

**严格别名规则**（strict aliasing rule，C11 6.5p7）：同一块内存只能通过**与其类型兼容**的左值访问（`char`/`unsigned char` 例外）。`*(float *)&uint32_t` 这种**类型双关**（type punning）是 UB——优化器假设"两个不兼容类型的指针不会指向同一内存"，据此重排/缓存读写（ph09 3.7 已埋下伏笔）。

```c
/* 危险示例：勿运行 —— 类型双关违反严格别名 */
#include <stdint.h>
#include <stdio.h>
int main(void) {
    uint32_t bits = 0x3F800000u;  /* float 1.0f 的位模式 */
    float f = *(float *)&bits;    /* UB: 通过不兼容类型访问 */
    printf("%g\n", f);
    return 0;
}
```

**后果**：标准层面是 UB——优化器可能先读 `bits` 再按旧值计算，结果变成垃圾。**但注意：本环境实测（Apple clang 21.0.0）`-O0`~`-O3` 均输出 1**，该模式未被优化坏——"碰巧正确"恰恰是 UB 最危险的地方：它不能证明代码安全，换编译器/编译器版本/代码形状就可能不同。判断依据永远是标准，不是实测结果。
**工具**：别名违规极难被工具捕获（UBSan 默认不查严格别名）；`-Wall` 的 `-Wstrict-aliasing` 只能提示部分模式；主要靠**代码评审与规范**。
**修复**：搬运位模式一律用 `memcpy(&f, &bits, sizeof f)`（编译器会优化成单指令，无性能损失）；`-fno-strict-aliasing` 可关闭该假设（缓解非根治）；序列化/网络代码（ph12）读字节流时**不要强转结构体指针**。

### 3.8 对齐访问违规

每种对象类型有**对齐要求**（int 通常 4 字节、double 8 字节）。通过未对齐地址访问对象是 UB：x86-64 容忍但慢（可能跨 cache line 分裂），部分架构（旧 32 位 ARM、SPARC 等）直接异常（SIGBUS）。常见触发场景：从字节流 buffer 中偏移读出字段后直接强转。

```c
/* 危险示例：勿运行 —— 未对齐访问 (部分架构 SIGBUS, x86/现代 arm64 上慢且是 UB) */
#include <stdint.h>
#include <stdio.h>
#include <string.h>
int main(void) {
    unsigned char buf[16] = {0};
    memcpy(buf + 1, "\x00\x00\x00\x01", 4);   /* 故意错开 1 字节 */
    uint32_t *p = (uint32_t *)(buf + 1);      /* p 未 4 字节对齐 */
    printf("%u\n", *p);                       /* UB: 未对齐读 */
    return 0;
}
```

**后果**：x86 上静默变慢（难察觉）；**现代 arm64（如 Apple Silicon）硬件也允许非对齐访问，实测无崩溃**——但仍是 UB，UBSan 一视同仁地报告；旧 32 位 ARM/SPARC 等则直接 SIGBUS。同一代码在不同架构行为不同（可移植性问题）。
**工具**：UBSan 报 `load of misaligned address ... for type 'uint32_t' ... which requires 4 byte alignment`（实测）。
**修复**：从字节流读字段用 `memcpy`（编译器优化为单条加载指令且保证对齐安全）；对齐敏感对象用 `_Alignas(8)`/`aligned_alloc`；二进制 record 解析（ph12 核心场景）的黄金法则：**先 memcpy 到对齐的本地变量，再读字段**。

### 3.9 除零、INT_MIN/-1 与移位问题

**整数除零是 UB**（C11 6.5.5p5 对 `/` 与 `%` 的除零一律是未定义行为，含浮点——IEEE 754 的 ±inf 仅在实现声明 `__STDC_IEC_559__`（Annex F）时才成为定义行为，本工具链未定义该宏，故浮点除零在本阶段语境仍是 UB：判断依据永远是标准，不是实测结果）；**`INT_MIN / -1` 也是 UB**（商 +2147483648 溢出 int）；移位规则：**移位位数等于或超过类型位宽是 UB，负移位是 UB**，右移负数属于实现定义行为（多数平台是算术右移）。

```c
/* 危险示例：勿运行 —— 除零与非法移位 */
#include <limits.h>
#include <stdio.h>
int main(void) {
    int d = 0;
    int q = 100 / d;         /* UB: 整数除零 → x86 上 SIGFPE; arm64 上实测静默得 0 */
    int m = INT_MIN / -1;    /* UB: 商溢出 int */
    int s = 1 << 31;         /* UB: 移位位数 == int 位宽 */
    int s2 = 1 << -1;        /* UB: 负移位 */
    printf("%d %d %d %d\n", q, m, s, s2);
    return 0;
}
```

**后果**：整数除零的"裸跑表现"随硬件不同——x86 上 SIGFPE 崩溃，**arm64 上实测静默算出 0**（sdiv 指令对零除返回 0），这正是实现/硬件差异的体现；`INT_MIN / -1` → 崩溃或垃圾值；移位越界 → 垃圾值（`1u << 31` 才是安全的，无符号回绕）。
**工具**：UBSan 统一报告 `division by zero`、`division of -2147483648 by -1 cannot be represented in type 'int'`、`left shift of 1 by 31 places cannot be represented in type 'int'`、`shift exponent -1 is negative`（四条均实测）；编译期 `-Wall` 对负移位有 `-Wshift-count-negative` 警告（实测触发）。
**修复**：除法前检查除数；`INT_MIN / -1` 先判断或用 `int64_t`；移位位数先检查 `n >= 0 && n < 32`；位运算字段一律用无符号类型（roadmap ph12 位运算基础）。

### 3.10 字符串处理坑（缺 \0、缓冲区溢出）

C 字符串以 `\0` 结尾，但**编译器不帮你保证**：字符数组缺 `\0` → `strlen` 越界读；`strcpy`/`strcat`/`sprintf`/`scanf("%s")` 不检查目标容量 → **缓冲区溢出**（历史上大量漏洞的根源，如 2003 年 Blaster 蠕虫利用 Windows RPC 的无界拷贝漏洞）。

```c
/* 危险示例：勿运行 —— 缺 \0 与缓冲区溢出 */
#include <stdio.h>
#include <string.h>
int main(void) {
    char buf[4];
    char no_nul[4] = {'a', 'b', 'c', 'd'};   /* 没有 \0 */
    size_t n = strlen(no_nul);               /* UB: 越界读, 直到碰巧遇到 0 */
    strcpy(buf, "hello world!");             /* UB: 目标仅 4 字节, 溢出写 */
    printf("%zu %s\n", n, buf);
    return 0;
}
```

**后果**：越界读（strlen 停不下来）读到垃圾或崩溃；溢出写覆盖相邻变量/返回地址——这是**最常被攻击者利用**的一类 UB。
**工具**：ASan 报 `stack-buffer-overflow`（`WRITE of size 13` 实测）；编译期 `-Wfortify-source` 对已知长度的 `strcpy` 也能直接警告（实测触发）；Valgrind 也能报越界读写。
**修复**（边界检查三件套）：

- `strncpy(dst, src, n-1); dst[n-1] = '\0';`——**strncpy 不保证 \0**，必须手动补；
- `strncat(dst, src, room-1)`——strncat 最多拷 n 个字符且**总是补 \0**（注意 n 不含 \0，要留 1 字节）；
- 最省心：`snprintf(dst, n, "%s", src)` 保证 \0；输入用 `fgets`/`scanf("%Ns")`，绝不用 `gets`/`scanf("%s")`。

封装成带容量的字符串类型（示例 5 的 sstr）后，业务代码不再直接碰裸缓冲区。

## 4. 底层原理

### 4.1 编译器如何在优化时假设无 UB

现代编译器（GCC 的 GIMPLE、LLVM 的 IR 优化 pass）把**"程序不含 UB"当作推理前提**：只要证明某段路径无 UB，就允许按数学规则改写代码。两个经典假设：

- **有符号溢出假设**：`a + 1` 永不溢出 → `(a + 1) > a` 恒为真 → `-O2` 下整个比较被常量折叠；
- **严格别名假设**：两个不兼容类型的指针不指向同一内存 → load 可以缓存、store 可以重排。

```c
/* 危险示例：勿运行(裸跑) —— 编译器的"无 UB"假设折叠比较(实测 -O0→0, -O2→1) */
#include <limits.h>
#include <stdio.h>
static int f(int a) {
    return (a + 1) > a;      /* 编译器假设: a+1 不会溢出 → 恒真 */
}
int main(void) {
    printf("%d\n", f(INT_MAX)); /* -O0 打印 0; -O2 打印 1 */
    return 0;
}
```

`-O0` 下按"字面意思"执行：`INT_MAX + 1` 回绕成 `INT_MIN`，`INT_MIN > INT_MAX` 为假，返回 0；`-O2` 下编译器假设加法不溢出，把 `(a + 1) > a` 折叠成恒真，返回 1。**同一个函数，两种输出**——这就是"UB 不是结果不确定，而是编译器可做任何假设"的活教材（examples/ex06-opt-levels.c 实测）。

### 4.2 优化级别如何改变 UB 的表现（-O0 vs -O2）

同一份 UB 代码，优化级别不同，表现天差地别——roadmap 必会概念"**UB 可能在优化级别变化后暴露**"。

| 优化级别 | 典型动作 | 对 UB 的影响 |
|---------|---------|-------------|
| `-O0` | 几乎不做优化 | UB 大多"碰巧"按直觉执行（溢出回绕、越界恰好没崩） |
| `-O1`/`-O2` | 常用优化全开 | 溢出/别名/未初始化假设生效，行为可能突变（如 `(a+1)>a` 从 0 变 1） |
| `-O3`/`-Ofast` | 激进优化 | 假设全面生效；`-Ofast` 的 `-ffast-math` 连浮点语义都放宽 |

```bash
# 用 4.1 的 f() 演示: 同一源码两种输出(Apple clang 21.0.0 实测)
cc -O0 -g ub_opt.c -o ub0 && ./ub0    # 打印 0
cc -O2 -g ub_opt.c -o ub2 && ./ub2    # 打印 1
```

**实践准则**：调试用 `-O0 -g`；发布用 `-O2`。**关于 Sanitizer 构建的优化级别，本环境实测有一个反直觉结论**：复现/演示 UB 用 `-O0` 更稳——`-O1` 下 clang 可能把"被测的那次内存访问"常量折叠或死代码消除掉，导致 ASan 漏报 `stack-buffer-overflow`（本阶段 project/ 的 Makefile 正是因此用 `-O0`）；真实项目的 Sanitizer CI 构建才建议 `-O1`（`-O0` 可能让部分 UB 不暴露，`-O2` 会因优化改变行号映射）。**排查思路**：程序在发布版崩溃/错乱、调试版正常 → 第一反应查 UB，而不是怀疑编译器 bug。

### 4.3 内存布局与越界写为何更危险

栈上局部变量**相邻排列**：越界写先覆盖"看起来合法"的邻居（数据静默损坏），再远一点就是**栈帧的返回地址**——覆盖后函数返回时跳到攻击者控制的地址（经典栈溢出攻击）。堆上 malloc 返回的指针前后是 **chunk header**（ph04 的"块头部"）与相邻 chunk：越界写篡改 header 后，`free` 时分配器按被篡改的 size 移动指针，形成**任意写原语**（经典堆利用）。

```text
栈(地址下降):
[ ... | other | arr[0] | arr[1] | arr[2] | 返回地址 | ... ]
                       arr[3]=100 → 覆盖 other(数据损坏)
                       arr[5]=200 → 覆盖返回地址(任意跳转)

堆: [ header | 用户数据A | header | 用户数据B ]
     越界写 A 的用户数据 → 篡改 B 的 header → free 时分配器行为失控
```

| 越界读 | 越界写 |
|--------|--------|
| 读垃圾值/相邻数据 | 篡改相邻对象状态 |
| 信息泄漏 | 覆盖元数据/返回地址 |
| 危害：逻辑错误为主 | 危害：**崩溃、提权、任意代码执行** |

所以 roadmap 必会概念"**越界写通常比越界读更危险**"——它不只是"写坏了数据"，而是"写坏了控制流与分配器的信任基础"。

### 4.4 检测工具的角色（边界声明）

本阶段把三类工具当**复现/定位工具**用，各管一类 UB：**ASan**（`-fsanitize=address`）抓越界、use-after-free、double free；**UBSan**（`-fsanitize=undefined`）抓溢出、除零、移位、未对齐、空指针等"逻辑型 UB"，加 `-fno-sanitize-recover=all` 让它在第一个错误处中止（本阶段全部演示都用这个组合）；**Valgrind** 抓未初始化读与泄漏（不需重新编译）。工具的实现原理（红区、shadow memory、动态二进制插桩）、开销指标、CI 接入、静态分析（cppcheck/clang-tidy）与单元测试框架，都是 **ph11 Sanitizer / 静态分析 / 单元测试阶段**的内容，本阶段只记一句：**能抓的用工具抓，抓不到的（严格别名、多数未初始化）靠代码评审与规范**——这正是 3.7/3.6 和 project/ 中"工具抓不到的坑"要传达的边界。

### 示例 1：数组越界写（ASan 复现）

对应 roadmap 学习内容"数组越界"与练习"用 ASan 检查越界和 use-after-free"。

> 运行前提：必须用 `-fsanitize=address` 编译运行，否则勿运行。

```c
// examples/ex01-oob.c —— 数组越界写（UB 演示，已验证）
// 验证环境：Apple clang 21.0.0（cc，macOS arm64）—— 编译/运行命令见下方命令块
#include <stdio.h>

int main(void) {
    int arr[3] = {1, 2, 3};
    int other = 42;
    printf("写前: arr[0]=%d other=%d\n", arr[0], other);
    arr[3] = 100;          /* UB: 故意越界写 1 个元素 —— ASan 应报 stack-buffer-overflow */
    printf("写后: arr[0]=%d other=%d\n", arr[0], other);
    return 0;
}
```

```bash
# 1. 编译（必须带 -fsanitize=address）
cc -Wall -Wextra -std=c11 -fsanitize=address -g examples/ex01-oob.c -o ex01
# 2. 运行
./ex01
```

实测报告关键行（编译期另触发 `-Warray-bounds` 警告）：

```text
ERROR: AddressSanitizer: stack-buffer-overflow on address ...
WRITE of size 4 at ... thread T0
```

要点：`stack-buffer-overflow` 说明对象在**栈**上（`arr` 是局部数组）；`WRITE of size 4` 说明是**写**操作（若是读则显示 `READ`）；`-g` 才能在报告里显示源码行号（本环境 ASan 无法启动外部符号器——llvm-symbolizer 存在但 spawn 失败 errno 9，栈帧未符号化，但错误类型与读写大小完整）。验证方法：把 `arr[3]` 改成 `arr[0]` 重编译，报告消失——"没有越界就没有报告"。

### 示例 2：整数溢出与 UBSan 复现

对应 roadmap 学习内容"有符号整数溢出"与必会概念"UB 随优化级别暴露"。

> 运行前提：必须用 `-fsanitize=undefined -fno-sanitize-recover=all` 编译运行，否则勿运行。

```c
// examples/ex02-overflow.c —— 有符号溢出 vs 无符号回绕（UB 演示，已验证）
// 验证环境：Apple clang 21.0.0（cc，macOS arm64）—— 编译/运行命令见下方命令块
#include <limits.h>
#include <stdio.h>

int main(void) {
    unsigned int u = 0u - 1u;      /* 无符号回绕: 定义行为, UBSan 不报 */
    printf("u = %u\n", u);         /* 稳定输出 4294967295 (UINT_MAX) */

    int a = INT_MAX;
    a = a + 1;                     /* UB: 有符号整数溢出 */
    printf("a = %d\n", a);         /* 到不了这行: -fno-sanitize-recover=all 在溢出处中止 */
    return 0;
}
```

```bash
# 1. 编译（必须带 -fsanitize=undefined -fno-sanitize-recover=all）
cc -Wall -Wextra -std=c11 -fsanitize=undefined -fno-sanitize-recover=all -g examples/ex02-overflow.c -o ex02
# 2. 运行
./ex02
```

实测报告关键行（退出码 134，Abort）：

```text
runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
SUMMARY: UndefinedBehaviorSanitizer: undefined-behavior examples/ex02-overflow.c:18:11
```

要点：程序先打印 `u = 4294967295`（`0u - 1u` 回绕为 `UINT_MAX` 但**不报错**——"无符号回绕是定义行为"直观可见），随后在溢出处**中止**（`-fno-sanitize-recover=all` 让 UBSan 从"报错后继续"变成"立即停止"）。想观察"报错后继续"的默认行为，去掉 `-fno-sanitize-recover=all` 重新编译即可。

### 示例 3：悬空指针与 use-after-free

对应 roadmap 练习"用 ASan 检查 use-after-free"与学习内容"悬空指针、重复释放"。

> 运行前提：必须用 `-fsanitize=address` 编译运行，否则勿运行。

```c
// examples/ex03-uaf.c —— use-after-free 与 double free（UB 演示，已验证）
// 验证环境：Apple clang 21.0.0（cc，macOS arm64）—— 编译/运行命令见下方命令块
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    int *p = malloc(sizeof(int));
    if (p == NULL) return 1;
    *p = 7;
    free(p);                 /* p 成为悬空指针 */
    printf("%d\n", *p);      /* UB: use-after-free —— 读取已释放的内存 */
    free(p);                 /* UB: double free —— 重复释放 */
    return 0;
}
```

```bash
# 1. 编译（必须带 -fsanitize=address）
cc -Wall -Wextra -std=c11 -fsanitize=address -g examples/ex03-uaf.c -o ex03
# 2. 运行
./ex03
```

实测报告关键行：

```text
ERROR: AddressSanitizer: heap-use-after-free on address ...
READ of size 4 at ... thread T0
```

要点：`heap-use-after-free` + `READ of size 4` 说明"释放后读取了 4 字节堆对象"；完整报告里同时打印**分配栈**与**释放栈**，两栈对照即可确认"分配 → 释放 → 误用"的完整链条。第一个错误（UAF）先被捕获并中止，`double free` 尚未执行——把 `printf` 那行删掉再编译，即可单独看到 `attempting double-free` 报告（已实测）。修复对照：`free(p)` 后置 `NULL` 且不再访问，报告消失。

### 示例 4：未初始化变量（编译期警告 + Valgrind 定位）

对应 roadmap 学习内容"未初始化变量"与练习"收集 10 个常见 UB 示例并修复"。

> 运行前提：这是"故意读未初始化变量"的演示——输出是垃圾值，不会崩溃但无意义；建议用 `-Wall -Wextra -O1` 编译看编译期警告。

```c
// examples/ex04-uninit.c —— 未初始化变量（UB 演示，部分验证）
// 验证环境：Apple clang 21.0.0（cc，macOS arm64）—— 编译/运行命令见下方命令块
#include <stdio.h>

int main(void) {
    int x;                   /* 未初始化: 栈垃圾值(不确定值) */
    if (x > 0)               /* UB: 条件依赖不确定值 */
        printf("正数: %d\n", x);
    else
        printf("非正数: %d\n", x);
    return 0;
}
```

### 示例 5：安全字符串工具库（strncpy/strncat 正确用法 + 边界检查封装）

对应 roadmap 推荐项目"安全字符串工具库"与练习"给字符串处理函数补边界检查"。核心思路：把"裸字符数组 + 容量"封装成一个类型，所有写入都带边界、**永远保证 \0 结尾**。本示例是安全代码，可直接编译运行。

```c
// examples/ex05-safe-str.c —— 安全字符串工具库 sstr（安全示例，已验证）
// 验证环境：Apple clang 21.0.0（cc，macOS arm64）—— 编译/运行命令见下方命令块
typedef struct {
    char  *buf;   /* 缓冲区指针(由调用方提供存储) */
    size_t cap;   /* 缓冲区总容量(含 \0) */
    size_t len;   /* 当前长度(不含 \0) */
} sstr_t;

void sstr_init(sstr_t *s, char *buf, size_t cap) {
    s->buf = buf; s->cap = cap; s->len = 0;
    if (cap > 0) buf[0] = '\0';
}

/* 安全拷贝: strncpy 不保证 \0, 必须手动补 —— 这是最常见的 strncpy 坑 */
int sstr_copy(sstr_t *s, const char *src) {
    if (s->cap == 0) return -1;
    strncpy(s->buf, src, s->cap - 1);   /* 至多拷 cap-1 字节, 绝不越界 */
    s->buf[s->cap - 1] = '\0';          /* 手动补 \0 */
    s->len = strlen(s->buf);
    return 0;
}

/* 安全追加: strncat 最多拷 n 个字符且总是补 \0, 但 n 不含 \0, 要留 1 字节 */
int sstr_append(sstr_t *s, const char *src) {
    if (s->len >= s->cap - 1) return -1;          /* 已满, 拒绝 */
    size_t room = s->cap - 1 - s->len;            /* 还能写多少字符 */
    strncat(s->buf, src, room);                   /* room 个字符 + 自动 \0 */
    s->len = strlen(s->buf);
    return 0;
}

int main(void) {
    char storage[16];
    sstr_t s;
    sstr_init(&s, storage, sizeof storage);
    sstr_copy(&s, "hello");
    sstr_append(&s, ", world! 0123456789"); /* 19 字符 > 剩余 10 → 被截断, 但不越界、不丢 \0 */
    printf("[%s] len=%zu cap=%zu\n", s.buf, s.len, s.cap);
    return 0;
}
```

```bash
# 1. 编译
cc -Wall -Wextra -std=c11 examples/ex05-safe-str.c -o ex05
# 2. 运行（输出 [hello, world! 0] len=15 cap=16 —— 追加被截断）
./ex05
```

要点：对比 3.10 的坏例子——同样的"超长输入"（本例 19 字符 > 剩余容量 10），这里被**截断而非溢出**：输出 `[hello, world! 0] len=15`，len 停在 cap-1=15，全程不越界、`\0` 结尾不丢；`strncat` 的 `room` 是"剩余可写字符数"（不含 \0），`strncpy` 则必须手动补 `\0`，两个函数的语义差异是必背点；`-fsanitize=address,undefined` 复跑零报告（已验证）。扩展方向（对应推荐项目）：自动扩容（接 ph04 的 DynStr）、`sstr_printf`、截断计数与错误码——带截断计数的完整版见 exercises 练习 5 的参考实现。

### 示例 6：优化级别改变 UB 表现（-O0 vs -O2）

对应必会概念"UB 可能在优化级别变化后暴露"与练习"用 -O0 与 -O2 编译同一段溢出代码对比两次输出"。

> 运行前提：建议用 `-fsanitize=undefined -fno-sanitize-recover=all` 编译观察 UBSan 报告；`-O0`/`-O2` 裸跑不会崩溃但输出随优化级别变化。

```c
// examples/ex06-opt-levels.c —— 优化级别改变 UB 表现（UB 演示，已验证）
// 验证环境：Apple clang 21.0.0（cc，macOS arm64）—— 编译/运行命令见下方命令块
#include <limits.h>
#include <stdio.h>

/* 编译器假设 a+1 不会溢出: 若 a == INT_MAX 则 a+1 是 UB, 而 UB 允许任意假设,
 * 于是 (a+1) > a 被当作恒真, -O2 下整个比较折叠成常量 1 */
static int f(int a) {
    return (a + 1) > a;
}

int main(void) {
    printf("%d\n", f(INT_MAX));
    return 0;
}
```

```bash
# 1. -O0 编译运行
cc -Wall -Wextra -std=c11 -O0 examples/ex06-opt-levels.c -o ex06o0 && ./ex06o0   # 输出 0
# 2. -O2 编译运行
cc -Wall -Wextra -std=c11 -O2 examples/ex06-opt-levels.c -o ex06o2 && ./ex06o2   # 输出 1
# 3. UBSan 证明: 两种输出都是 UB 的合法表现
cc -Wall -Wextra -std=c11 -O1 -fsanitize=undefined -fno-sanitize-recover=all -g examples/ex06-opt-levels.c -o ex06ub && ./ex06ub
```

实测结果（Apple clang 21.0.0）：`-O0` → 0，`-O1`/`-O2` → 1；UBSan 报告：

```text
runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
```

要点：这是 4.1/4.2 的活教材——**同一个函数、同一次调用，换优化级别输出从 0 变 1**，且 UBSan 证明这是"编译器可做任何假设"的 UB，而不是编译器 bug。对照自查：如果程序中还有类似 `(x + 1) > x` 这样的比较，先怀疑它有 UB 再谈优化。

## 7. 总结

### 关键要点

1. **UB 不是"结果不确定"，而是"编译器可做任何假设"**：可能正常、崩溃、删代码、任意行为——判断依据是标准，不是实验结果
2. **越界写通常比越界读更危险**：越界读泄漏数据，越界写破坏相邻对象、堆元数据与返回地址，可能被利用提权
3. **有符号溢出是 UB，无符号回绕是定义行为**：`UINT_MAX+1==0` 稳定；`INT_MAX+1` 随优化级别变化
4. **空指针/野指针/悬空指针要分清**：NULL 大多段错误（UBSan 可报）；野指针写入随机地址；use-after-free 与 double free 破坏堆，ASan 可精确定位
5. **未初始化变量是隐藏炸弹**：声明即初始化；`-Wall -Wextra -O1` 的 `-Wuninitialized` 提前拦，Valgrind `--track-origins=yes` 追来源
6. **严格别名禁止类型双关**：`*(float*)&u32` 是 UB，位模式搬运一律 memcpy；工具难查，靠评审与规范——即使实测"碰巧正确"也不能证明安全
7. **对齐是硬约束**：未对齐访问 x86 慢、部分架构崩、现代 arm64 也"只是容忍"；字节流解析先 memcpy 到对齐变量再读字段
8. **除零、`INT_MIN/-1`、移位越界全是 UB**：除法前查除数，移位位数必须非负且小于位宽；整数除零的裸跑表现还随硬件不同（x86 SIGFPE / arm64 静默得 0）
9. **UB 随优化级别暴露**：`-O0` 正常 `-O2` 异常 → 先怀疑 UB 而非编译器 bug（-O0/-O2 双编译是廉价自查）
10. **初始化和边界检查是 C 代码的生命线**（roadmap 必会概念）：所有输入、长度、索引都按"会错"来防御

### 跨语言对比：内存安全与 UB

| 维度 | C | C++ | Rust | Go | Java |
|------|---|-----|------|----|------|
| 未定义行为 | 广泛存在（越界/溢出/别名/悬垂） | 继承 C，另有生命周期/ODR UB | safe Rust 编译期排除（unsafe 块内同 C） | 无（运行时 panic） | 无（JVM 规范强约束） |
| 数组越界 | UB，不检查 | 同 C；`vector::at` 可检查 | 编译期检查或 panic | panic（越界即运行时错误） | 抛 ArrayIndexOutOfBoundsException |
| 有符号溢出 | UB | 同 C（可开 `-fwrapv`） | debug 构建 panic / release 回绕 | int64 溢出 wrap 或编译报错 | 回绕（规范明确定义） |
| 悬垂指针/UAF | 常见，靠工具检测 | 手动或 RAII/智能指针 | 借用检查器编译期拒绝 | GC 回收，无 UAF | GC 回收，无 UAF |
| 检测/兜底 | ASan/UBSan/Valgrind + 评审 | 同 C，工具更丰富 | cargo + miri（检测 unsafe UB） | go vet / race detector | JVM + 静态分析 |
| 安全定位 | 程序员负责 + 工具托底 | 程序员 + 智能指针 | 语言保证（unsafe 除外） | 运行时保证 | 运行时保证 |

C 是所有对比项里最"裸露"的：**没有语言机制兜底，UB 的后果全部落在程序员身上**——存储引擎恰好需要这种零成本控制，代价是必须把本阶段的 10 类坑刻进评审习惯。
