## 练习 1：写配置加载模块（★★★）

**目标**：写一个支持多环境（dev/test/prod）的分层配置加载模块，默认值 → profile 文件（`config.<env>.json`）→ 环境变量 → 命令行 flag 逐层覆盖，并返回"每个字段最终来自哪一层"的来源表。

**要求**：
- 必填项要 fail-fast：缺数据库 DSN 时返回一个能被 `errors.Is`/`errors.As` 精确命中的哨兵错误（如 `*RequiredError{Key:"DB_DSN"}`），不能悄悄用空值启动
- 环境变量的"未设置"与"设为空串"语义不同；类型解析失败要带字段上下文（如 `invalid port "abc"`）
- 来源可追溯：模块能回答"port 这个值来自 default/file/env/flag 哪一层"（发布排障核心）
- 注入式设计：文件目录、env 读取函数、flag 参数都可注入，测试不碰真实环境与磁盘
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；测试断言①缺必填报可识别错误、②文件/环境覆盖顺序正确、③来源表正确、④dev 与 prod 两份配置加载出不同结果

**提示**：`sol-01-config-loader` 参考实现。分解建议：先写默认值与文件层，再叠加 env 层（类型转换），最后做 flag 层（parse 前后对比判定"谁真的变了"）；必填校验放最后一步统一做。真实工程的 profile 由 CI/编排注入，别把它写死在代码里。

## 练习 2：注入构建版本信息（★★）

**目标**：让二进制在运行时能自报版本——ldflags `-X` 注入语义版本 + `runtime/debug.ReadBuildInfo` 兜底读 VCS 信息，提供文本摘要与 JSON 两种输出（JSON 供 `/version` 端点）。

**要求**：
- 版本变量（version/commit/date）默认值必须诚实（`dev`/`none`），未注入的构建一眼能看出"没走发布流水线"
- 用 `debug.ReadBuildInfo` 读 `vcs.revision`/`vcs.time`（go 命令构建时自动写入）
- 二进制支持 `-version` 单行输出且退出码 0；JSON 输出字段固定（接口契约，发布后不许乱改名）
- 逻辑与 `os.Exit` 分离（如 `run(args, out) int`），让 `-version` 行为可测
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；用 `go build -ldflags "-X main.version=v1.4.0 -X main.commit=<你的提交>"` 构建后运行，能看到注入值

**提示**：`sol-02-version-injection` 参考实现。注意：变量在 `main` 包时 `-X` 路径写 `main.version`；若放在子包则写 `路径/包名.变量名`。

## 练习 3：设计灰度开关（★★★）

**目标**：实现带优先级裁决的灰度开关模块：**紧急关闭（HardOff）> 白名单 > 百分比分桶 > 兜底**，并对"生命周期一致性"做静态校验。

**要求**：
- `Evaluate(user)` 对同一 (user, feature) 结果恒定（哈希分桶，可加 `-race` 验证多实例一致）
- 白名单与百分比可叠加：beta 阶段灰度组全员可见 + 对外按百分比探路
- 空身份（批量任务/服务端路径）要分桶时不猜——返回显式兜底值
- `Validate()` 拦截生命周期违例：removed（摘除）阶段的 feature 必须 HardOff，返回可被 `errors.Is` 命中的哨兵错误
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；测试断言①HardOff 越过白名单与 100% 放量、②白名单在 percent=0 仍可用、③放量单调不回退、④removed 未关被 `Validate` 拦截

**提示**：`sol-03-feature-flag` 参考实现。放量单调性是灰度的可预期底线——从 20% 抬到 50% 时，原本可见的用户必须保持可见；用 FNV 等内置哈希即可，不必密码学哈希。

## 练习 4：写发布检查清单（★★★）

**目标**：把"发布检查清单"固化成**可执行预检器**：定义检查项（版本/密钥/开关/迁移/回滚预案），对发布候选逐项自动检查并出报表，能卡在 CI 上阻止问题版本发布。

**要求**：
- 检查项至少覆盖：版本已注入（非 dev）、配置无明文密钥（扫 `password=`/`://user:pass@` 等模式）、摘除期 feature 已关、破坏性迁移已按 **expand-contract 两阶段**展开、回滚预案存在
- expand-contract：破坏性迁移（contract，如删列）必须声明其前置 expand 版本，且该版本必须出现在"已发布版本"列表里——旧服务没全部升级前不许删字段
- 检查结果分 PASS/FAIL/WARN（WARN 不阻塞但提醒），输出人类可读报表
- 检查项可插拔（能增删单项）
- **验收**：`go build ./... && go test ./... && go vet ./...` 通过；构造"合规候选"全 PASS，构造"坏候选"（dev 版本/明文密钥/removed 忘关/破坏迁移缺 expand）得到对应 FAIL

**提示**：`sol-04-release-checklist` 参考实现。README 里把检查清单写成 `[ ]` 是起点，本练习要求把它变成机器可判定的代码——这正是"发布要可回滚""数据库变更要兼容旧版本服务"（roadmap 必会概念）的自动化形态。
