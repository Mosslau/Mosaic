## 练习 1：采集压测 profile（★★）

**目标**：亲手走一遍「采集压测 profile」的最小闭环——对一个 CPU 密集程序施加并发压测，同时在压测窗口内采集 CPU profile，再用 `go tool pprof` 确认热点压在预期函数上。体会「profile 必须采在负载真正运行时」：采集窗口 ≠ 程序运行期，而是**压测真正打满 CPU 的那段窗口**。

**要求**：
- 程序自带压测循环：`-workers N` 个 goroutine 并发调用一个 CPU 密集函数（如对 4KB 块做逐字节混合），压测时长由 `-dur` 控制
- 压测进行中用 `runtime/pprof.StartCPUProfile/StopCPUProfile` 包住窗口（或 `net/http/pprof` 从外部采），产出一份 `.pprof` 文件到 /tmp
- 用 `go tool pprof -top` 验证：最热帧必须是预期的业务函数，占比 > 80%

**验收**：`go test ./... && go vet ./...` 通过；`-workers 4 -dur 2s -cpuprofile` 运行后，`pprof -top` 的 flat 第一行是你的业务函数（占绝对多数，参考实现实测 84.01%——见 sol-01-collect-profile/main.go 文件头验证块，±10~20% 波动）；能说出：为什么并发 worker 数 × 窗口时长会大于窗口本身的采样时长（多核并行采样）

**提示**：sol-01-collect-profile 目录；先想清楚 `compressBlock` 为什么必须零分配、结果为什么必须落地（sink）——否则编译器可能把整个热点优化没（ph13 的 sink 纪律）；对比 examples/ex01-profserver 的两种采集路径（常驻服务用 net/http/pprof、批处理用 runtime/pprof）

## 练习 2：用 PGO 构建服务（★★★）

**目标**：对一个"命令分发服务内核"完整走 PGO 四步——采集代表性 profile → `-pgo` 构建 → `go version -m` 验证印章 → 自计时对比。核心验收不是"快了多少"，而是**能用印章与编译决策证实 PGO 真的生效了**，并解释收益从哪来。

**要求**：
- 服务以接口注入命令处理器（至少两个实现，主流类型占 9 成以上、有配置字段——字段是"去虚拟化后能提升"的前提），热点是内层循环里的接口方法调用
- 代表性负载跑出 CPU profile；`go build -pgo=<profile>` 构建，`go version -m` 必须出现 `-pgo=<profile>` 印章
- `-gcflags='-m'` 对比基线与 PGO 构建的输出，找到 `PGO devirtualizing interface call …` 决策行
- 基线与 PGO 二进制的自计时对比（checksum/结果必须一致 = 优化不改语义）

**验收**：印章存在、基线二进制无印章；PGO 构建多出"去虚拟化 + 内联"决策行；checksum 前后一致；能解释"为什么去虚拟化的对象是 95% 那个类型而不是 5% 那个"（profile 权重）

**提示**：sol-02-pgo-build 目录（参考实现实测 ~2.0×，ns/op 0.75 → 0.37）；**坑**：热函数若被内联进 main（go1.25 内联器能内联含循环的小函数），PGO 收益可能消失——参考实现用 `//go:noinline` 保持热函数独立（注释里有本机实测对照）；本机若测不出收益，先检查去虚拟化目标与 profile 的代表性（采样太少会选错类型，如选到 5% 那个反而变慢）

## 练习 3：热点路径识别——top/peek/list 三件套（★★）

**目标**：把「热点代码更值得优化」落成可操作的流程：用 `go tool pprof` 的 top（谁最热）→ peek（谁调用它/它调用谁）→ list（热在哪一行）回答三个问题，并学会识破"假热点"。

**要求**：
- 程序同时埋三类热点：纯 CPU 热函数（内层循环重）、渲染函数的 `+=` 拼接（flat≈0%、症状全在 runtime.concatstring2）、一个"函数体看起来重但调用频率极低"的假热点
- 采集 profile 后依次回答：① top 第一是谁（占比 ~8~9 成）② peek render 类函数：它的 callee 是什么（病根在 runtime 的哪个帧）③ list 最热函数：热点行是哪一行、为什么热 ④ 假热点为什么不该先优化（用调用频率 × 单次成本解释）
- 若 render 类函数因采样太少没进 top，把 `-iters` 调大重采（这是 pprof 的常态操作，不是 bug）

**验收**：能给出三个问题的答案并写出依据输出；`go test ./... && go vet ./...` 通过；能解释"为什么 body 大的函数不一定是热点、为什么 top 里的 runtime 帧要先沿调用链找回业务函数"

**提示**：sol-03-pprof-list 目录（参考实现头部有完整三件套实测输出）；对照 examples/ex03-pprof-analyze 的流程，但本题的程序是另一份——不要背输出，练流程

## 练习 4：对比优化前后延迟和吞吐（★★★）

**目标**：产出 roadmap §16 要的"性能对比报告"——同一负载分别跑基线与 `-pgo` 二进制，报告**延迟分位数（p50/p95/p99/均值）与吞吐（req/s）**，并说明差异来源。这是「能产出性能对比报告」验收的直接训练。

**要求**：
- 负载要有"请求"形态：请求数 N、每请求负载大小有分布（延迟才有 p50 < p95 < p99 的意义）、热点在接口分派的逐字节循环上（90% 主流算法 / 10% 冷门算法）
- 逐请求计时收集延迟样本，排序后算 p50/p95/p99/均值；吞吐 = 总请求数 / 总墙钟
- 同一负载跑基线与 PGO 两个二进制（各自报告），digest/结果必须一致
- 至少各跑两遍再下结论（单次有 ±10~20% 抖动，方向与量级才可信）

**验收**：两份报告齐全（基线 vs PGO 的 p50/p95/p99/均值/吞吐）；能说清 p95/p99 为什么高于 p50（负载大小分布）；能解释 PGO 版快在哪（去虚拟化 + 字段提升）；能识别并剔除离群单次（如一次基线吞吐掉 25%）

**提示**：sol-04-latency-throughput 目录（参考实现实测 p50 1.63µs → 0.92µs、吞吐 ~590k → ~955k req/s；p99 3.25 → 3.75µs 微升属尾部离群/负载分布效应、落在 ±10~20% 波动内——主要收益在 p50 与吞吐，别误读为 PGO 变差）；**坑**：`-cpuprofile` 采集时跳过逐请求计时（参考实现已内置并注释原因）——本机实测逐请求 `time.Now` 会把 CPU 采样偏置到 main.main，PGO 拿到失真权重会选错去虚拟化目标（选到 10% 类型反而变慢）；先做练习 2 再来本题，机制相同、本题加"度量方法"
