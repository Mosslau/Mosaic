# GPU 调度平台 Demo

> 状态：⬜ 未开始
> 对应 roadmap 阶段：第 四 阶段
> 对应文档：`roadmap/大模型数据中心平台工程师.md`

## 目标

做一个**能提交、能排队、能监控、能算成本**的 GPU 调度平台 Demo：端到端输入是「训练/推理作业定义（镜像、资源需求、优先级、时长预估）+ 集群资源」」，输出是「作业被调度到某个节点并跑完，全过程有状态、有事件、有资源账本与成本归集」。

一句话可检验目标：**提交 N 个作业（含超额、优先级不同的场景）后，队列按策略出队、作业获得 GPU 并进入 Running/Succeeded/Failed，资源账本始终满足 `已分配 + 空闲 = 总量`，且每个作业的 GPU·秒可被归集到租户。**

（本项目是**基础设施编排**层：K8s 提供"容器与节点抽象"，GPU 调度策略与成本归集是本项目要补的部分。）

## 技术栈

- 容器与编排：Docker + Kubernetes（kind/minikube 单机起步）、Helm 打包
- 调度：Volcano（批调度：队列/优先级/gang scheduling）或 K8s 原生调度 + 自研策略对比（至少做一次对比）
- GPU 抽象：NVIDIA GPU Operator（无 GPU 机器时用 `nvidia-device-plugin` 的 mock 或 `gpu` 资源注入进行**逻辑验证**，真实卡部分如实标注）
- 作业定义：训练作业用 `Job`/`PyTorchJob`；或统一抽象成自研 CRD（更利于讲清"期望状态 + 控制器循环"）
- 监控：Prometheus（kube-state-metrics + DCGM exporter）+ Grafana 面板
- 成本：GPU·秒计量 → 按租户/项目归集（showback / chargeback 两种口径至少实现一种）
- 客户端：`kubectl` 或自研 CLI（`submit / status / queue / cost` 四个子命令）

## 系统架构

```text
   提交作业(CLI/API) ──▶ ┌───────────────┐
                        │ 准入与配额校验  │  超限拒绝(可读原因)
                        └───────────────┘
                                │ 入队
                                ▼
                     ┌────────────────────┐
                     │ 调度器(Volcano/自研) │  优先级 / 队列 / gang / 回填
                     └────────────────────┘
                                │ 绑定节点
                                ▼
   ┌─────────────┐   ┌───────────────────┐   ┌──────────────────┐
   │ 资源账本     │◀─▶│ K8s 节点与 GPU 设备 │──▶│ 作业运行时(Pod)   │
   │(分配/回收/不变量)│  │(device plugin/Operator)│  │ 训练/推理容器    │
   └─────────────┘   └───────────────────┘   └──────────────────┘
          │                     │                       │
          ▼                     ▼                       ▼
   成本归集(GPU·秒)      Prometheus 指标          作业状态机与事件
          │                     │                       │
          └─────────────┬───────┴───────────┬───────────┘
                        ▼                   ▼
                  Grafana 面板         审计与复盘(谁在何时占了什么)
```

模块边界与关键决策：

| 模块 | 职责 | 关键设计点 |
|------|------|-----------|
| 准入与配额 | 提交前校验租户配额 | **拒绝而非静默排队**；拒绝原因可读 |
| 调度 | 队列、优先级、gang、回填 | 决策要能解释（为什么这个作业先跑）；策略可替换 |
| 资源账本 | 分配/回收/不变量 | `已分配 + 空闲 == 总量`；错账比拒绝服务更危险 |
| 作业状态机 | Pending→Running→Succeeded/Failed | 状态变更写事件，供值班与复盘 |
| 监控 | 队列深度、GPU 利用率、作业成败率 | 指标与账本**同源**（避免大屏与告警对不上） |
| 成本 | GPU·秒 → 租户/项目 | 事件驱动计量（分配/释放各一条），口径写清 |

## 复用的算法实验

- **无直接复用**（本项目是基础设施编排，算法实验不提供前置原理）。但仍有两处**思想层面的呼应**，实施时在笔记中记录：
  - [A* 启发式搜索](../../algorithms/01-search/a-star/) —— 「用启发式评估决定搜索顺序」与调度器的优先级/回填决策同构：都需要一个**可解释的评估函数**，而不是黑盒打分
  - [蒙特卡洛树搜索 MCTS](../../algorithms/01-search/mcts/) —— 资源分配中的"试探 + 回滚"直觉（本阶段不做，列为阶段七的可选深入）
- 若实施中发现某个调度策略需要真实算法支撑（如基于作业时长预测的排程），应先回到 `algorithms/` 补对应实验，再落地到本项目——**不许在项目里塞未经验证的算法**

## 验收标准

- [ ] 能在单机 K8s（kind/minikube）上跑通「提交作业 → 排队 → 调度到节点 → 作业 Running → 结束」全流程
- [ ] 资源账本满足不变量 `已分配 + 空闲 == 总量`，超量申请被拒且状态不变
- [ ] 配额与优先级生效：超额提交被拒（原因可读）；高优先级作业在队列中**先于**低优先级获得资源（给出两次调度决策对比）
- [ ] 作业状态机与事件可查：任一作业能列出「何时入队/开始/结束/失败原因」
- [ ] 有 GPU 与无 GPU 两种环境都有明确说明：无 GPU 时用逻辑验证（资源注入/mock），**并如实标注哪部分未在真实卡上验证**
- [ ] Grafana 至少三块面板：队列深度、GPU 利用率、作业成败率；且面板数字与账本一致（同源可核对）
- [ ] 成本归集跑通：一次实验后能输出「租户 → GPU·秒 → 估算金额」表，计量事件数可对账
- [ ] 全流程有一份可复现的**分步命令清单**（`make up` / `submit` / `status` / `cost` / `make down`）

## 实施笔记

- **2026-09（梳理阶段）**：本项目受硬件约束最大（真实 GPU + K8s 集群），因此验收标准刻意分成两层：**逻辑层**（配额/调度决策/账本/成本，可在无卡环境验证）+ **真实层**（真卡上的 device plugin 与利用率，标注未验证）。这样即便暂时没有 GPU，也能推进到 🚧 并产出可核对成果。
- **2026-09（待验证假设）**：① Volcano 与本机 K8s 版本兼容性；② 无 GPU 时如何让调度器"看见" GPU —— 计划用 `nvidia.com/gpu` 资源的自定义注入或 `fake-gpu-operator` 一类方案，先验证策略逻辑，再等真实卡；③ kind 多节点是否必要（gang scheduling 需要可调度节点数 > 1 才能体现）。
- **与 phases 五/七 的接口约定**：本项目产出的「作业提交 + 资源账本 + 成本归集」三个能力，在阶段五（推理服务部署）与阶段七（整合）会被复用；因此接口要**先定契约**（如 `submit(jobSpec) -> jobId`、`cost(tenant) -> gpuSeconds`），避免阶段七重写。
