# OpenAI 兼容推理服务

> 状态：⬜ 未开始
> 对应 roadmap 阶段：第 五 阶段
> 对应文档：`roadmap/大模型数据中心平台工程师.md`

## 目标

做一个**接口兼容 OpenAI、可承载多模型（含 LoRA 适配器）、有真实压测数字、能算单位成本**的推理服务：端到端输入是「HTTP 请求（`/v1/chat/completions` 等）+ 模型/LoRA 路由」，输出是「流式或非流式响应 + 每次请求的 token 用量与耗时分解（TTFT / TPOT / 总时长）+ 可归集的成本」。

一句话可检验目标：**同一个客户端代码不改，只换 base_url 就能调用本服务；在多并发压测下给出 TTFT、TPOT、tokens/s、P95 延迟四个实测数字，并能说明瓶颈在哪（显存/批处理/量化）。**

（本项目讲的是**推理服务的工程形态**——批处理、显存账本、并发与限流、量化与 LoRA 服务化、压测与成本；不是教你写推理引擎内核。）

## 技术栈

- 推理引擎：vLLM（首选，自带 continuous batching）或 Triton Inference Server（二选一，记录选型理由）
- 微调与适配器：LoRA / QLoRA（PEFT）训练一次小模型或小数据集，产物作为 **LoRA Serving** 的输入
- 量化：GPTQ/AWQ 或 bitsandbytes 至少一种，给出「量化前后：显存、吞吐、质量抽样」三组对比
- 服务层：FastAPI（OpenAI 兼容协议实现：请求/响应 schema、流式 SSE、错误码）+ 令牌校验 + 限流
- 压测：`locust` 或 `k6`（固定并发梯度：1/4/8/16），记录 TTFT/TPOT/P95
- 观测：Prometheus 指标（QPS、排队请求数、批大小分布、显存占用）+ 结构化日志
- 成本：tokens 计费口径（prompt/completion 分别计价）+ GPU·秒折算

## 系统架构

```text
客户端(OpenAI SDK) ──▶ ┌─────────────────────────────┐
                      │ 服务层(FastAPI, OpenAI 兼容)  │
                      │ 鉴权 → 限流 → 请求校验 → 路由  │
                      └─────────────────────────────┘
                                    │
                    ┌───────────────┴────────────────┐
                    ▼                                ▼
        ┌────────────────────┐          ┌────────────────────┐
        │ 模型 A（基座）       │          │ 模型 B / LoRA 适配器 │
        │ 权重 + 量化         │          │ 按请求动态挂载        │
        └────────────────────┘          └────────────────────┘
                    │                                │
                    └───────────┬────────────────────┘
                                ▼
                    ┌─────────────────────────────┐
                    │ 推理引擎(vLLM/Triton)        │
                    │ continuous batching + KV Cache│
                    └─────────────────────────────┘
                                │
                                ▼
               指标(吞吐/延迟/显存) + 用量(tokens/成本) + 日志
                                │
                                ▼
                     压测报告（TTFT/TPOT/tokens/s/P95 对比表）
```

模块边界与关键决策：

| 模块 | 职责 | 关键设计点 |
|------|------|-----------|
| 协议兼容层 | 实现 OpenAI 协议子集 | 兼容性用**同一份客户端代码**验证（不改代码只换 base_url） |
| 调度与批处理 | 请求入批、KV Cache 复用 | 讲清「批大小 ↑ 吞吐 ↑ 但 TTFT ↑」这一对核心权衡，并用实测数字支撑 |
| 适配器路由 | 多模型 / LoRA 路由 | 适配器换入换出的成本要可测（否则"多租户"是空话） |
| 量化 | 权重压缩 | 必须给「质量抽样对比」——只报吞吐不报质量不算验收 |
| 压测与成本 | 并发梯度 + 计费 | 压测脚本可复现；成本口径写清（含空转与排队） |

## 复用的算法实验

- [迷你 GPT 字符级语言模型](../../algorithms/04-transformer/mini-gpt/) —— **本项目的原理底座**：自回归生成的采样过程、KV 逐 token 增长的内存形态，是理解 KV Cache 与 prefill/decode 的前提
- [迷你 Transformer Block](../../algorithms/04-transformer/mini-transformer/) —— 模型结构的最小完整形态；量化与批处理影响的是这些矩阵运算的显存与算力
- [注意力机制](../../algorithms/04-transformer/attention/) —— prefill（全序列注意力）与 decode（单 token 注意力）的算力差异来源，解释 TTFT 与 TPOT 为何是两种延迟
- 说明：本项目**不重写推理内核**（continuous batching / PagedAttention / kernel 融合属引擎领域），只做服务化与工程度量

## 验收标准

- [ ] OpenAI 兼容子集可用：**同一份官方 SDK 代码**只改 `base_url` 即可完成一次流式与非流式对话
- [ ] 至少两种模型/适配器（基座 + LoRA 或两个尺寸）可按请求路由，且换入换出成本有实测
- [ ] 量化对比完整：同一模型在量化前后给出**显存占用、吞吐（tokens/s）、质量抽样**三组数据
- [ ] 压测报告含并发梯度（≥3 档）的 **TTFT / TPOT / tokens/s / P95**，并给出瓶颈归因（显存、批大小或 CPU）
- [ ] 限流与超时生效：超过并发上限返回可预期的错误码（不是挂死），并写入日志
- [ ] 计量可对账：一次压测后能输出「请求数 / prompt tokens / completion tokens / GPU·秒 / 估算成本」表，与引擎侧计数一致
- [ ] 无 GPU 环境时有明确的降级验证路径（小模型 CPU 或 mock 引擎），并如实标注哪些数字**未在真实 GPU 上验证**

## 实施笔记

- **2026-09（梳理阶段）**：把「兼容性用同一份客户端验证」「量化必须报质量」「成本能对账」三条写进验收——它们是推理服务最容易糊弄过去的地方（协议"差不多"、只报吞吐、成本口径不清）。另外明确边界：**不写推理内核**，引擎用 vLLM/Triton，本项目的价值在服务化与度量。
- **2026-09（待验证假设）**：① 本机有无 GPU——无卡时先用 CPU 小模型（如 TinyLlama 级）跑通协议与计量，把 TTFT/TPOT 当作**相对指标**验证压测框架，真实 GPU 数字标注未验证；② vLLM vs Triton——vLLM 开箱即用且自带 continuous batching，优先；③ LoRA Serving 是否需要独立进程——先做同进程挂载，再评估多适配器隔离。
- **与 04/07 的接口约定**：本项目的服务需要 04 提供「推理作业的部署与 GPU 配额」（可以由 04 的调度器起 Pod）；本项目产出的用量与成本要能被 07 的平台统一归集——因此计量口径（tokens ↔ GPU·秒）在阶段五就要定死。
