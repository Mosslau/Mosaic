# C++ 性能优化与 Profiling 阶段

> 面向「程序为什么慢、慢在哪、怎么用数据裁决」方向：从剖析工具（perf/gprof/VTune/Tracy）起步，经由 CPU/内存 profile、cache locality、拷贝消除与分配次数优化，到 SIMD 友好布局与查询执行热点分析——先测量，再优化，用证据而不是直觉管理性能。

## 1. 概述

本阶段是学习路线的第 18 步（roadmap ph18 目标：能基于数据定位性能瓶颈，而不是凭感觉优化）。前面 17 步把「写对」讲完了：ph02 的虚函数多态、ph12 的移动语义与值类别、ph13 的 RAII、ph15 的内存安全、ph17 的接口与分层（每层抽象都有代价）——**本阶段就是回答 ph17 留下的问题：模式与结构引入的间接、拷贝与分配，到底贵不贵、贵在哪、值不值**。它把 ph17 的「先写对结构，再用数据决定要不要为性能绕开结构」落成可执行的工作流。

## 2. 来源与演变

性能工程的工具史几乎是计算机工程史本身。1967 年 Amdahl 提出 Amdahl's law（加速比受串行部分限制），1960 年代起插桩式计数与执行轨迹（tracing）是主流；1982 年 Susan Graham、Peter Kessler 与 Marshall Kirk McKusick 在 Berkeley 开发 **gprof**，第一次把「统计采样」引入主流剖析——它周期性地打断程序、记录程序计数器（PC），用少量样本推断耗时分布，从此「剖析不必插桩每行代码」成为常识。**设计哲学一句话：剖析器的价值在于用最少的侵入得到时间花在哪的证据——先测量，再优化**。

1980~2000 年代编译器优化与 CPU 微架构（缓存、分支预测、超标量、乱序执行）飞速演进，「编译器替你优化」与「程序员必须理解机器」两条线并行；2000 年代 VTune（Intel）、OProfile、Linux **perf**（2009 年前后集成 perf events 子系统）让硬件性能计数器（缓存缺失、分支误预测）进入寻常命令行；2010 年代 Valgrind、heaptrack、AddressSanitizer 把内存剖析做成日常；Tracy 与各种火焰图工具把剖析可视化推向交互时代。C++ 侧语言层面的「免费午餐」也在变：C++11 引入移动语义与右值引用，C++17 把复制消除（copy elision）从「允许的优化」升级为「语言保证」——**性能不只是查工具，更是语言设计在帮你消除不必要工作**。

| 版本/里程碑 | 年份 | 主要变化 |
|------|------|---------|
| Amdahl's law | 1967 | 加速比被串行部分封顶——先找对瓶颈再优化 |
| gprof（Berkeley） | 1982 | 统计采样剖析：周期中断 + PC 记录，gprof 至今仍是入门工具 |
| 缓存/分支预测进消费级 CPU | 1980s~1990s | 「内存局部性」与「分支代价」成为程序员必修课 |
| Intel VTune | 1990s~ | 硬件性能计数器进入工程实践；2017 后免费 |
| Valgrind | 2002 | memcheck/massif 让内存错误与堆剖析平民化 |
| Linux perf events | 2009~ | perf record/report：内核采样 + 硬件计数器一体 |
| C++11 | 2011 | 移动语义/右值引用/`std::function`：拷贝成本第一次有「廉价替代」 |
| C++17 | 2017 | 复制消除成语言保证；`std::string_view`（C++17）/ `std::from_chars`（C++17）为解析类优化供弹药 |
| Tracy / 火焰图 | 2017~ | 可视化剖析：时间线、采样聚合，性能调优进入「看得见」时代 |
| Apple Silicon（arm64） | 2020~ | NEON 与 big.LITTLE 成为 C++ 性能课的新默认平台（本环境即 arm64） |
| C++20/23 | 2020~2023 | `std::span`/ranges/`std::format`；`std::chrono` 完善让计时代码可移植 |

本文示例以 **C++20** 为基线（性能讨论依赖「现代编译器的优化行为」与可移植计时/视图设施，主线 ph11~ph16 也以 C++20 演示语言前沿；本阶段的语法面集中在移动语义（C++11）、复制消除（C++17）、`string_view`/`from_chars`（C++17）——它们自定型后多年未变，是 **C++ 最稳定、也最该吃透的语法部分之一**），验证工具链 **Apple clang 21.0.0（`c++`）+ Homebrew clang 21.1.8（`clang++`）**，macOS arm64 + libc++，统一 `-std=c++20 -Wall -Wextra`，优化级别按示例主题取 `-O1/-O2/-O3` 并在各文件头注明。本笔记引用的全部实测数字都在该环境下测得；**另一条铁律：性能数字是环境的函数，换 CPU/编译器/优化级别必须重测**。

### 3.1 先测量，再优化：四步工作流

roadmap 四个必会概念其实是同一句话的四次强调：**先测量，再优化**；算法复杂度优先于微优化；连续内存通常更利于缓存；过早优化会破坏结构。把「优化」当成有纪律的四步循环，而不是灵光一现的改写：

| 步骤 | 动作 | 常见错误 |
|------|------|----------|
| 1 定基线 | 写对功能、留基准输入，量出当前耗时/分配数 | 没基线就开改，改了不知道快没快 |
| 2 找热点 | 剖析（采样/插桩/计数器）定位耗时与分配集中处 | 凭直觉猜热点（通常是错的） |
| 3 改一处 | 一次只改一个变量，保留可验证结果 | 一把梭改十处，回归了不知道怪谁 |
| 4 复测证 | 同一输入重测，确认变快且结果一致 | 优化后不重测就宣布胜利 |

一条重要的元纪律（roadmap 必会概念「算法复杂度优先于微优化」）：**先检查量级（O(n) vs O(n²)），再做常数级优化**。ex04 里 `result = result + tok` 的悲剧不是「多分配了几次」，而是每轮把整段串拷一遍的 O(n²) 字符搬运——优化 `reserve` 后它同时变成 O(n)。顺序反过来（先抠 `+=` 的常数、不修量级）是新手最常见的无效努力。

测时本身的坑，初学阶段最值得先记住三件：**① 别用调试构建测速**（`-O0` 测的是"没优化的程序"）；**② 别把输出 IO 混进被测区**（`std::cout` 的缓冲/刷新波动能淹没真实差距，ex03 因此把打印全部移到循环外）；**③ 别拿一次测量当结论**（单次被调度噪声/频率爬升污染，取多轮最优才稳）。这三条与「先测量」是同一纪律的组成部分——**测量不严谨，等于没测量**。

> 注意：优化对象永远是被**数据点名**的热点。别优化冷路径——冷路径上的 10 倍提速对总耗时毫无贡献（Amdahl's law 的工程面）。

### 3.2 profiling 工具族：采样 vs 插桩，以及谁用在哪

profiling 工具按「侵入程度」分两类：

| 维度 | 统计采样（sampling） | 插桩/代码植入（instrumentation） |
|------|---------------------|-------------------------------|
| 原理 | 周期性打断程序、记录 PC/调用栈，统计样本占比 | 编译期或运行期在函数入口/出口埋计时与计数 |
| 开销 | 低（通常 <5%），可跟生产 | 高（数倍），只宜测试/诊断构建 |
| 精度 | 统计近似，热点要样本够多 | 精确到函数级次数 |
| 代表 | perf、VTune、Tracy 采样、macOS `sample` | gprof、`-pg` 插桩、ScopeTimer、Tracy 手动标记 |

选型常识表（**perf/gprof/VTune/Tracy 均为本环境（macOS，无 Linux perf、未装 Intel 工具、Tracy 需集成构建）未实测工具，下列命令格式来自官方文档，未在本环境验证**）：

| 工具 | 平台 | 一句话定位 | 典型命令（未在本环境验证） |
|------|------|-----------|--------------------------|
| perf | Linux | 内核采样 + 硬件计数器，命令行性能事实标准 | `perf record ./app && perf report` |
| gprof | 类 Unix（现代 macOS 已移除） | 经典插桩剖析，编译加 `-pg` | `gcc -pg app.cpp -o app && ./app && gprof ./app gmon.out` |
| VTune | x86（Intel/AMD） | 硬件事件深度分析（缓存、分支、热点） | GUI/命令行 `vtune -collect hotspots -target-application=./app` |
| Tracy | 跨平台 | 客户端-服务器可视化剖析，需把库集成进程序 | CMake 集成后连 `Tracy.exe` GUI |
| macOS `sample` / `xctrace` / Instruments | macOS | Apple 平台采样剖析/时间线 | `sample <pid> 3`；Instruments 走 GUI（本机存在可执行文件，未自动化实测） |

**sampling 是默认选择**：开销小、贴近真实负载。什么时候用插桩：sampling 解不开的阶段级归因（ex03 的场景）、要看某函数被调多少次、或要统计某段代码的精确时长分布。

### 3.3 CPU profile：从热点证据到「改哪一行」

采样式 CPU profile 的产物是**热点函数表**：哪些函数占总样本的百分之几。perf 的教科书流程（Linux）：

```bash
# 1. 用调试符号编译（-O2 -g；-O0 剖析的是"没优化的程序"，不是你的程序）
clang++ -std=c++20 -O2 -g app.cpp -o /tmp/app
# 2. 采样（未在本环境验证——macOS 无 perf；等价物是 sample / Instruments）
perf record -g /tmp/app < args >
# 3. 看热点：函数视角报告；-g 展开调用链 → 火焰图数据源
perf report
```

**没有剖析器时的替代品：插桩式阶段计时**（本阶段 examples/ex03 的完整实现）。把程序切成可解释的阶段，每个阶段一个 RAII 计时器，多轮累计后打印占比表——这是「先测量」的最低配，也是理解任何剖析器输出的心智起点：

```cpp
// examples/ex03-profiling-demo.cpp —— 节选：ScopeTimer 把管线切成阶段分别计时
class ScopedTimer {  // 进入作用域计时，退出时累加进 PhaseAccum
    PhaseAccum& acc_;
    Clock::time_point t0_;
public:
    explicit ScopedTimer(PhaseAccum& acc) : acc_(acc), t0_(Clock::now()) {}
    ~ScopedTimer() {
        acc_.seconds += std::chrono::duration<double>(Clock::now() - t0_).count();
        ++acc_.calls;
    }
};
```

读热点表的三条纪律：① **先看自顶向下的调用链**，别只看单函数样本——某个函数慢往往因为它是被调 1 亿次的「分母」；② **小心假热点**：内联/分配器/系统调用会让样本聚到出乎意料的函数上（例如大量小对象分配把时间聚到 `operator new`——那不是 new 慢，是分配次数多，见 3.7）；③ **优化后用同一输入复测**，样本分布应整体下移，而不是把热点从 A 挪到 B。一份典型的热点表这样读：

| 函数 | 自占样本 | 累计样本（含子调用） | 判读 |
|------|----------|----------------------|------|
| `filter_and_aggregate` | 12% | 41% | 真热点：自占 + 子树占大头，先开它 |
| `Row::parse_row` | 3% | 38% | 分母嫌疑：被调几百万次，每次不贵但总量惊人 |
| `operator new` | 17% | 17% | 假热点信号：往上看谁在疯狂分配（3.7） |
| `memcpy` | 9% | 9% | 同上：谁在反复拷大对象（3.6） |

表里最该警惕的是后两行——它们几乎从不是「自己慢」，而是调用方设计问题的投影；顺着调用链回看，答案通常是「分配次数太多」或「拷贝太频繁」，而不是「new/memcpy 实现差」。

### 3.4 内存 profile：分配次数与内存增长是两件事

内存问题分两类，工具与对策完全不同：

| 问题 | 症状 | 定位手段 | 对策 |
|------|------|----------|------|
| 分配次数爆炸 | 跑得慢、但 RSS 稳定 | 全局 `operator new` 计数 / Tracy 分配统计 | reserve、复用、零中间态（3.7） |
| 内存持续增长/泄漏 | RSS 随时间单调上涨 | Valgrind memcheck、`leaks`、heaptrack 快照 | RAII/智能指针（ph13）、查漏 |

本阶段的可移植技巧：**重载全局 `operator new` 数次数**（examples/ex04 的完整实现，按区域清零/读出）：

```cpp
// examples/ex04-alloc-optim.cpp —— 节选：全进程分配计数，区域前后取差
void* operator new(std::size_t size) {   // 只计数，不拦分配（示例为教学重载了全局分配）
    ++g_alloc_count;
    if (void* p = std::malloc(size)) { return p; }
    throw std::bad_alloc();
}
// 用法：g_alloc_count = 0; 跑被测区; allocs = g_alloc_count;
```

> 注意 ex04 的重载是**教学演示**：真实工程重载全局分配符要极其谨慎（影响整个进程、要与所有 dealloc 配对）；生产环境数分配首选剖析器内建分配统计或 `malloc` 钩子。roadmap 练习 3（sol-03）展示了同一手法在真实词频统计里「数出 15 万次 → 11 次」的差距。

内存 profile 最常见的三幕「剧情」，都值得先在心里过一遍：**① 慢但不涨内存**——多半是分配次数（不是内存量）的问题，对策见 3.7；**② 内存随时间匀速上涨**——多半是生命周期问题：某处把「新对象」当「旧对象」存、或容器只增不清，先查 RAII/所有权（ph13 的手法），再上 Valgrind/heaptrack 看快照差；**③ 峰值暴涨又回落**——往往是单次构建了超大中间物（如把整份日志拼成一个字符串再切），对策是流式/分块处理，而不是调大内存。判定「要不要为内存优化」和「要不要为 CPU 优化」用同一把尺：**先测出证据**（RSS 曲线 / 分配计数），再动手。

### 3.5 cache locality：访问顺序决定内存带宽用在哪

现代 CPU 以 64 B 缓存行（cache line）为单位搬运内存。**连续访问 = 每取一行 16 个 float 全部用上 + 硬件预取器按顺序提前拉取；跨步访问 = 每次只用一个、还打乱预取**。examples/ex01 用同一块 64 MiB 矩阵（超出本机 L2 4 MB）实测三种遍历：

```cpp
// examples/ex01-cache-line.cpp —— 节选：同一数据，仅访问顺序不同
sum += data[i * k + j];        // 行主序：相邻两次访问相差 4 B → 连续、可预取、可向量化
sum += data[i * k + j];        // 列主序（j 在外层）：相邻两次相差 k*4 B（16 KB）→ 逐元素错过缓存行
// 完整版本还包含 64×64 分块遍历（blocked）：把跨步从 16 KB 缩到 256 B，局部性折中
```

本机实测（Apple clang 21，`-O3`，5 轮取最优）：行主序 10.4 ms、列主序 58.8 ms（**慢 5.6 倍**）、分块 10.2 ms——同样的求和、同样的数据，只是换访问顺序。**数据布局与访问顺序是比指令更贵的资源**，这是 roadmap「连续内存通常更利于缓存」的量化版。

把这一课用到结构体数组上就是 AoS vs SoA：`vector<Point3>` 里每隔 12 B 取一个 x，是「按字段切片」的隐式跨步；把 x 单独放一张连续 float 表（SoA）才谈得上向量加载（3.8 展开）。

### 3.6 拷贝消除与移动语义：让「按值返回」免费

C++17 起有一条**语言保证**：prvalue 按值返回时不再拷贝也不再移动——复制消除（copy elision）从优化升级为语义。examples/ex02 用带计数器的 Probe 把每次拷贝/移动都数出来：

```cpp
// examples/ex02-copy-elision-move.cpp —— 节选：三种返回形态的拷贝/移动计数
Probe make_direct(int id) { return Probe(id); }  // prvalue：C++17 保证消除，拷贝 0 移动 0
Probe make_named(int id) { Probe local(id); return local; }  // NRVO：通常消除（允许非强制）
Probe make_conditional(bool high) {              // 两个具名分支返回 → 无法 NRVO
    Probe a(1); Probe b(2);
    return high ? a : b;                         // 退化为一次移动，而不是拷贝
}
```

本机实测计数：直返与 NRVO 均 0 拷贝 0 移动；条件返回 0 拷贝 + 1 移动。这组数字回答了两个 ph12/ph13 遗留问题：**① 「返回大对象很贵」在 C++17 下大半是过时恐惧**（现代编译器对返回路径的消除能力极强）；② 消除不了的路径上，移动（搬 4 B 头）比拷贝（搬 64 B 载荷）便宜一个量级，所以**让类可移动（noexcept move）、让临时对象走移动**是第二道保险。

vector 增长是同一主题的另一面：不 reserve 时重分配会移动全部存量元素（ex02 实测 257 个元素触发 10 次重分配、元素被移动 511 次；`reserve` 后 0 次）。`push_back(临时)` 走移动、`push_back(左值)` 走拷贝（ex02 场景 3 各计 1 次）——**接口写法（传值/const&/右值）直接决定拷贝还是移动**，这是 ph14 const 正确性之后的性能面。

拷贝陷阱速查（多数是「编译器比你想象的勤快，也比你想象的保守」两类错误的混合）：

| 陷阱 | 现象 | 修法 |
|------|------|------|
| 循环内把大对象当 const& 传错、被迫拷贝 | 每次迭代深拷贝 | 输入参数按 const&（F.16），输出用返回值 |
| 返回条件分支里的具名对象 | 消除不了，退化为移动 | 接受一次移动（已是最优），别用输出参数绕 |
| 容器不 reserve 反复扩容 | 指数级重分配 + 全员移动 | 预算容量 `reserve` |
| `push_back(左值)` 而非 `emplace`/临时 | 走拷贝不走移动 | 临时直接传 / `emplace_back` 原地构造 |
| 返回 `const T` | `const` 抑制移动（F.49 反模式） | 返回非 const 值，让移动/消除生效 |
| 值语义类手写了拷贝构造 | 编译器无法保证消除 | 优先 Rule of Zero（ph13）；确需手写则 Rule of Five 全配齐 |

### 3.7 分配次数优化：把「堆分配」当可量化指标

一次堆分配 ≈ 分配器走查空闲链表 + 可能的系统调用/锁 + 后续释放开销。**少一次分配往往比少一次乘法值钱**——优化分配的第一步是数出来。examples/ex04 对「拼接 20k 词条」数出：基线 24k 次分配（53 ms）vs `reserve + append` 1 次分配（0.26 ms），**约 200 倍差距**：

```cpp
// examples/ex04-alloc-optim.cpp —— 节选：问题写法与对策写法
result = result + ascii_upper(tok) + ',';   // 每轮两次 operator+：两次分配 + 一次整段拷贝（O(n²)）
// ……
result.reserve(total);                       // 预算总长，一次分配
result.push_back(/* 逐字符大写追加 */);       // 预分配充足后零分配
```

| 分配热点模式 | 对策 | 出处 |
|--------------|------|------|
| 容器反复增长 | `reserve` 预算容量 | ex02/ex04 |
| 每词/每字段一个临时 string | 零中间态解析：`string_view` + `std::from_chars` | sol-02 |
| 短字符串每词一次拷贝入表 | SSO 装不下的长词改 `string_view` 键（前提：输入活得比表久） | sol-03 |
| 循环里重复造相同对象 | 提到循环外复用 | 3.3/ex03 |
| 字符串拼接整段拷贝 | `reserve + append` | ex04 |
| 逐字段构造字符串再转数值 | `std::from_chars` 从字符区间直读，无中间态 | sol-02 |

「零中间态」是解析优化的核心姿势——把「切字符串再转」改成「从原始缓冲直接转」：

```cpp
// sol-02 的优化路径（节选）：定位字段边界后，from_chars 直接从缓冲解析，不建 std::string
const auto id_res = std::from_chars(line.data(), line.data() + c1, id);   // 整数直读
const auto sc_res = std::from_chars(sc.data(), sc.data() + sc.size(), score);  // 浮点直读
// from_chars 无 locale、无状态对象、无分配——它只做一件事：把字符区间转成数值
```

为什么 `istringstream`/`stod` 慢（sol-02 基线，实测快 3.6 倍）：每行构造一个流对象（内部要建 locale 相关状态）、每个字段先造 `std::string`、再走一遍格式化解析；而 `from_chars` 是「把区间给你，别的我都不管」的最小实现——**省掉的每一步都是分配或状态构造**。

> 本阶段只做「用 STL 的正确姿势减少分配」；**手写内存池、自定义 allocator、arena 属于 roadmap 第 21 节数据结构与算法阶段**——那是「STL 姿势到头了还要再快」时才值得的复杂度，过早引入属于 roadmap 必会概念里的「过早优化」。

### 3.8 SIMD 友好布局：布局 × 并行累加，缺一不可

SIMD（NEON/SSE/AVX）让一条指令同时处理多个 float。但**宽指令能吃几口，取决于数据怎么摆**。examples/ex05 用 6M 个三维点求 Σx²，四档实测给出阶梯式结论：

| 实现 | 本机耗时 (ms) | 相对① | 教学点 |
|------|--------------|-------|--------|
| ① AoS 切片取 x（12 B 步长） | 3.53 | 1.00x | 布局不适合向量加载 |
| ② SoA 连续 float，单累加器 | 3.38 | 1.04x | 布局到位 ≠ 变快：单累加器串行依赖链卡住吞吐 |
| ③ SoA + 4 路独立累加器 | 0.98 | 3.6x | 纯标量改写拆依赖链就快 3.6 倍 |
| ④ SoA + NEON 8 宽 | 0.66 | 5.3x | 布局与并行度同时到位 |

```cpp
// examples/ex05-simd-layout.cpp —— 节选：③ 的做法（不碰 intrinsics）
float s0=0, s1=0, s2=0, s3=0;          // 4 条独立依赖链
for (; d + 4 <= n; d += 4) { s0 += x[d]*x[d]; s1 += x[d+1]*x[d+1]; /* …s2 s3… */ }
// ④ NEON（__aarch64__ 门控）：vld1q_f32 一次装 4 个 float，vmlaq_f32 乘加，双累加器
```

为什么 ② 单独不奏效：编译器对浮点累加的「可交换重组」持保守态度（改加法顺序会改变结果），单累加器循环难以自动向量化——**它想保证你写的顺序**。所以要么你亲手把依赖链拆开（③ 的多条链正是编译器自动向量化最喜欢的形状），要么直接 intrinsics（④，编译器不给力时的保底）。诊断输出用 `-Rpass=loop-vectorize` 看编译器到底向量化没有（README 有命令）。跨架构（x86 AVX）与 GPU 的 SIMD 工程化属 roadmap 第 23 节向量检索与 AI 推理引擎方向 C++ 阶段，本阶段不展开。

### 3.9 向量距离计算 benchmark：一套可信的测时方法

「先测量」的前提是**测量本身可信**。examples/ex06 给出一个可复用的微型 benchmark 工具骨架，project/ 把它放大成完整项目。测时五条纪律（缺一条数字就可能失真）：

| 纪律 | 为什么 | 实现 |
|------|--------|------|
| 预热 | 冷缓存/频率爬升让首轮失真 | 计时前先完整跑一遍 |
| 多轮取最优 | 最小值对调度噪声最稳（取均值会被偶发打扰） | 5 轮 `std::min` |
| 结果必须被消费 | `-O2` 会把「算完不用」整段删掉 | 结果写 `volatile` sink 或参与断言 |
| 输入逐轮微变 | 防止编译器把计算外提到计时循环外（LICM/CSE） | 每轮微调被测数据一个元素 |
| 明确被测语义 | 同语义才可对比 | 各实现跑同一数据、输出须一致 |

```cpp
// examples/ex06-bench-harness.cpp —— 节选：防优化计时骨架
for (int r = 0; r < samples; ++r) {
    data[r % data.size()] += 1e-7f;          // 输入微变 → 结果逐轮不同 → 无法外提
    const auto t0 = Clock::now();
    volatile double sink = kernel();          // volatile 落盘：真实执行、不可消除
    (void)sink;
    best = std::min(best, duration(t1 - t0)); // 取最优
}
```

project/（向量距离计算性能对比）在本机 100k 向量 × 6 查询 × 128 维实测：朴素标量 29 ms → 4 路累加 23 ms → NEON 8 宽 5.3 ms（**约 5.5 倍**），且三实现的最近邻结果逐查询一致——**快的前提是先证明一样**。

两个工程细节补充：**① 被测规模怎么定**——要让测的是「你要优化的东西」而不是「缓存容量」：数据量应超过 L2/L3，否则整块常驻缓存，测出来的是缓存命中率上限而不是真实路径（ex01 注释就说明了为什么矩阵必须 64 MiB）；**② 结果波动怎么判读**——同机同参数重复跑，最好的两轮通常差在 ±2~5%，优化改动若没超过这个波动，先别宣布胜利；跨机器/编译器对比时，绝对值不可移植，**相对趋势（几倍、谁快谁慢）才可移植**。project 的 `bench_one`（预热 + 3 轮取最优 + 输入逐轮微扰）就是这两条的完整落地。

### 3.10 查询执行热点分析：ph17 的执行器管道，成了剖析对象

ph17 的「下一阶段」预告在此兑现：它引入的抽象（虚接口、pull 模型执行器、每行一次虚调用的管道）到底贵不贵？examples/ex06 用**同一语义**的过滤聚合（扫 400 万行、保留 y>0.5 累加 x）做对照：

```cpp
// examples/ex06-bench-harness.cpp —— 节选：pull 虚管道 vs 裸写，两段语义相同的过滤聚合
// 裸写：单循环 if (r.y > 0.5) sum += r.x;
// 管道：ScanStep ──▶ FilterStep，每取一行穿越 Filter::next()（虚）→ Scan::next()（虚）
```

本机实测：裸写 5.2 ms，pull 虚管道 29 ms，**慢约 5.6 倍**。同时段的派发微基准（400 万次一元调用）给出另一条互补结论：当所有实现都在同一翻译单元、调用点全可见时，直调 / 函数指针 / `std::function` / 虚函数被内联与去虚化收敛到 0.6~0.8 ns/op（最慢/最快 1.27x）——**编译器看得见的间接几乎免费**。

两条合读，就是 ph17 悬念的完整答案：**「模式 vs 裸写」的差距不存在统一数字**——成本显形需要两个条件同时成立：间接真正发生了（信息被藏起来，编译器无法去虚化）+ 间接在热路径上被高频摊薄（每行一次调用，而不是每批一次）。工程含义很具体：

| 观察 | 启示 |
|------|------|
| 每行一次虚 `next()` 比每批一次昂贵得多 | pull 模型按行拉取时，把调用粒度放大（按块/按批拉取、返回数组）是查询引擎的经典优化 |
| 同 TU 内可见的多态几乎被去虚化 | 跨翻译单元/插件边界的多态才保留完整代价（那部分属 roadmap 第 19 节 ABI、动态库与插件机制阶段） |
| 过滤器是纯数据流变换 | 与扫描融合成单循环（裸写形态）是编译器最爱的形状——「下推/融合」的动机 |
| 输出行拷贝进 `Record& out` | 减少行级拷贝：就地构造、或让结果消费方直接读缓冲 |

补充一条方向性观察（roadmap 第 22/23 节是完整实现与设计）：查询引擎里这类「按行拉取」的热点，公认解法是把接口粒度从「每行」抬到「每批」（chunk/batch：`next(batch[64])`），让每批只付一次调用/虚开销，内部用 SIMD 友好的连续布局跑——这正是 roadmap 第 23 节「列式 + 向量化执行」的动机源头，也是 ex06 里「每行 5.6 倍」到「每批趋近 1 倍」的桥。

> 本阶段只在**单线程、行式内存表**上示范热点分析；**列式存储、向量化执行（batch 语义）、下推与物化的完整设计属于 roadmap 第 23 节向量检索与 AI 推理引擎方向与第 22 节存储引擎与数据库内核专项阶段**——这里给出的是「怎么把热点找出来并量化代价」的方法。

## 4. 底层原理

### 4.1 现代 CPU 与内存层次：为什么「内存访问顺序」是性能第一课

从寄存器到主存的每一级都是「更慢、更大」的缓存。本机容量可直接读取（`sysctl hw.l1icachesize hw.l1dcachesize hw.l2cachesize`）：

| 层级 | 本机容量（sysctl 实测） | 典型延迟量级（跨架构参考，非本机实测） | 谁在用 |
|------|------------------------|----------------------------------------|--------|
| 寄存器 | ~128~512 B（每条指令操作） | ~1 周期 | 当前计算 |
| L1（i/d） | L1i 128 KiB / L1d 64 KiB | ~4 周期 | 最近指令与数据 |
| L2 | 4 MiB | ~12~20 周期 | 中近期工作集 |
| L3（部分平台） | 本机无独立 L3 读数 | ~30~60 周期 | 多核共享 |
| 主存 | 24 GiB（`hw.memsize`） | ~80~120 ns（约 200~400 周期） | 装不下的一切 |

两个推论直接解释 ex01 的 5.6 倍：① 一次主存访问 ≈ 数百周期的等待，**能不访存就不访存**——访问同一缓存行内的数据是免费的；② 硬件预取器只对**规则模式**有效（顺序最灵、固定跨步次之、随机最差），列主序遍历恰好破坏了预取的规则性。CPU 为什么需要缓存行而不是单字节？因为 DRAM 按行突发传输，64 B 一跳是带宽与功耗的折中——**这个折中塑造了所有数据布局规则**。

把单位换算成直觉：64 B 一行装 16 个 float（或 8 个 double），顺序遍历意味着「取一行 → 连吃 16 个有用值」；按 16 KB 跨步遍历则是「取一行 → 只用 1 个 → 下一行已在 16 KB 外」——同一块数据，前者是 1 次行搬运喂 16 个计算，后者是 16 次行搬运喂 16 个计算。这正是「连续内存通常更利于缓存」的物理含义。局部性还有第二个维度：**时间局部性**（刚用过的数据马上再用——小循环体、寄存器变量）与**空间局部性**（刚用过的地址附近的数据马上会用——顺序数组），代码里多数局部性优化本质是在喂养这两个维度中的某一个。

> 本阶段只把缓存当「容量 + 行」两级模型来用，足够解释与指导 ex01~ex05 的全部现象；**多核间的缓存一致性协议（cache coherence）与 false sharing（伪共享）属于 ph08 并发编程阶段**（共享缓存行被多核交替写会引发整行失效广播），这里只在需要并发时才触发，不展开。

### 4.2 分支预测与超标量：为什么数据依赖比分支更值得警惕

现代核心是**超标量 + 乱序 + 深度流水**（数条指令同时执行、数十条在飞）。分支靠预测器猜方向，猜错要冲刷流水线——错误预测代价通常 15~20 周期（量级参考）。于是性能直觉要更新三点：

- **可预测的分支便宜**：循环、稳定的 if 分支被预测器轻松拿捏；代价集中在**数据相关、模式随机**的分支（如对哈希值做二分）——把随机分支换成查表/无分支选择（如 `cmp+select`）是数据驱动代码（data-oriented design）的老把戏。
- **流水线真正怕的是长依赖链**：ex05 的 ② 比 ① 没快多少，就是因为单累加器 fma 链把每拍吞吐卡死在算数延迟上——**不是内存慢、也不是分支错，是数据依赖**。这也是 ex05 ③ 纯标量拆链就快 3.6 倍的原因。
- **编译器帮你摆平多数琐碎分支**：`min/max`、边界检查、三元表达式通常被编译成无分支指令；手写汇编式的分支体操在现代编译器面前多半是负优化（先测再说）。

分支预测器内部是三组分工：**方向预测器**（猜 if 走哪边，靠历史/模式学习，循环与稳定分支几乎零成本）、**目标预测器**（猜间接跳转/虚函数去哪，间接调用的「两跳」之一就耗在这）、**返回栈**（猜函数返回地址，嵌套调用链因此便宜）。对程序员只有一条可操作的结论：**让「该分支走哪边」变得可预测**——数据有序/分布均匀时用查找替代随机 if；把热循环里的分支移到循环外；分支要按数据模式优化时，先测量确认它确实是瓶颈（误预测 15~20 周期 vs 一次分支判断 1 周期，量级差摆在那里，别为 1% 误预测率写丑代码）。

### 4.3 编译器优化与 as-if 规则：为什么计时代码要「防编译器」

编译器只受一条约束：**as-if 规则**——只要程序的「可观察行为」不变，它可以把代码换成任何等价形式。可观察行为 = 对 volatile 的访问、文件/IO、程序结束状态等；**纯计算的结果如果没人用，编译器有权整个删掉**。这解释了两件事：

- 为什么 -O2 下「算完不用的循环」能快成 0 ns（ex01 首版实测的翻车现场）：它不是 bug，是 as-if 规则的正常行使。
- 为什么本阶段所有计时代码都坚持「volatile sink + 输入逐轮微变」：那是在告诉编译器「这个结果我用得着、每次还不一样」，逼它真实执行。

as-if 规则的另一面是**乐观假设**：编译器假设程序没有未定义行为（UB），并以该假设自由变换代码——例如指针别名分析假设两个不同对象不重叠（ph15 的类型别名规则就是为这类假设立法），越界/悬空/数据竞争一旦出现，优化器有权「按没发生」优化，这是 C++ 性能与安全的根本张力。所以性能工程的底线永远在 ph15/ph16：**先在 Sanitizer + 静态分析下保证无 UB，再谈优化**——在 UB 之上优化的每一步都是地基上的沙堡。

`volatile` 在计时代码里的意义也要说清：它**不是**线程同步工具（ph08 明确禁止用 volatile 做同步），它的语义只是「每次读写都必须真实发生，不许缓存进寄存器」——正是计时代码想要的「别把这次访问优化掉」，也正是生产代码几乎用不到它的原因（生产里你要的是并发正确，不是防优化）。

优化级别的分工也要心里有数：

| 级别 | 定位 | 说明 |
|------|------|------|
| `-O0` | 调试 | 变量不优化掉、可断点；剖析/计时必须避开（它测量的是"没优化"） |
| `-O1` | 常规 | 基本优化，教学演示复制消除通常已够 |
| `-O2` | 工程默认 | 本阶段示例与练习主力 |
| `-O3` | 激进向量化/内联 | cache locality 与 SIMD 示例用；易增大代码体积 |
| `-Os` | 体积优先 | 嵌入式/缓存紧张场景 |

再往外一步的免费午餐：**LTO**（跨翻译单元内联，让 ex06 那种「同 TU 可见才免费」的效果放大到整个程序）、**PGO**（用真实运行数据反馈分支/内联决策）。两者都是「把信息喂给编译器」的工程实践，成本是构建时间，属 roadmap ph10 工具链范畴的自然延伸，本阶段只提原理不展开。

### 4.4 内存分配器视角：一次分配到底贵在哪

`malloc`/`::operator new` 的实现通常是：小对象走线程本地空闲链表（tlsf/slab 类），空闲链表 miss 才回到更大的堆结构、必要时 `mmap`/`brk` 向内核要内存。于是分配的成本谱是：

| 场景 | 成本 | 对策 |
|------|------|------|
| 命中线程本地缓存（热分配/热释放交替） | 很便宜（几十 ns 内） | 大量短暂小对象也未必是瓶颈——先测 |
| 空闲链表 miss / 跨线程迁移 | 中（可能要锁、要搜更大池） | 复用缓冲、减少分配频率 |
| 触达内核（首次/大块） | 贵（系统调用 + 页表） | 一次性 `reserve` 大块，别反复要 |
| 释放不及时/生命周期与分配错配 | RSS 上涨、碎片 | RAII（ph13）把释放绑定析构 |

加上 **SSO（小字符串优化）**：libc++ 里 ≤22 B 的 `std::string` 根本不碰堆（sol-03 首版因此翻车——短词全走 SSO，分配计数两边一样）。结论：**「少分配」是对的，但要对症**——先数（operator new 计数/剖析器分配统计），再按上表的成本谱决定是 reserve、复用、还是改用视图。

分配器本身的演进方向值得一提：glibc malloc 的 per-thread arena、tcmalloc/jemalloc 的 per-thread cache，都在把「分配」做成「大部分时候不碰锁、不碰内核」的快路径——**这意味着在你的进程里，热点分配的绝对成本可能已经很便宜，分配次数才是变量**。判断「这次要不要为分配优化」，先回答：分配次数有没有上表右侧的治理空间（reserve/复用/视图）？有，就值得做；没有（已经是每对象一次、生命周期天然），分配器已替你优化到接近免费，别再造自定义池（那个复杂度留给 roadmap 第 21 节）。

## 5. 使用场景

| 真实工程场景 | 用什么 | 为什么 / 注意 |
|--------------|--------|--------------|
| 服务延迟毛刺、吞吐不达标 | 先采样剖析找热点，再谈优化 | 别猜——热点证据优先（3.3） |
| 数据库/检索引擎热路径 | cache locality + SIMD 布局 + 按批处理 | 行级抽象每行付代价，按批才摊薄（3.10） |
| 解析/序列化在 IO 密集路径 | `string_view` + `from_chars` 零中间态 | 一次解析少 2~3 次分配/字段（sol-02 实测 3.6x） |
| 字符串拼接、容器构建 | reserve + append / emplace | 分配次数下降两个量级（ex04 实测） |
| 距离计算/矩阵热点 | 连续布局 + 拆依赖链 + intrinsics | 布局与并行度缺一不可（ex05/project） |
| 需要说服团队/评审「要不要优化」 | 一份可复现的 benchmark | 预热/多轮/防消除缺一不可（3.9） |

**什么时候不优化**（与上面同等重要）：① 正确性、可测试性、可读性没有先立住时（ph16 的工程纪律优先于性能）；② 冷路径——Amdahl 之下 10 倍提速对总量无贡献；③ 优化会破坏结构、而热点尚不确定时（roadmap 必会概念「过早优化会破坏结构」）；④ 编译器能免费做时——先确认 `-O2`、`string_view`、`emplace` 这些默认姿势已用上，再谈手写；⑤ 需要引入自定义分配器/汇编/跨 TU 拆分的重武器前，先问一句「能不能用标准库姿势解决」。

把「什么时候不优化」变成可执行的守门动作：**给每个优化提案配一张「证据卡」**——优化对象（哪个函数/哪段分配，用 profile 或分配计数点名）、当前基线数字、优化后的数字、结果一致性如何验证。四格填不满的提案，无论听起来多合理，按「过早优化」处理。这套守门在团队评审里尤其有用：**性能讨论从「我觉得/我听说」变成「数据表对数据表」**，正是本阶段贯穿始终的测量纪律在协作层面的落地。

**与其他语言的对比**（为 analysis/ 与 Tenet 合成积累素材）：

| 维度 | C++ | C | Rust | Go | Python |
|------|-----|----|------|-----|--------|
| 剖析生态 | perf/VTune/Tracy + 自研计数（可全手动） | 同 C++（perf/gprof） | perf + `#[inline]`/criterion | `pprof`/`trace` 内建 | `cProfile`/`py-spy` 采样 |
| 分配默认 | 手动值语义 + RAII；STL 帮你 | 全手动 | 所有权驱动，基本零隐藏拷贝 | GC（分配频率不敏感） | GC + 解释器，多数热点在 C 层 |
| 布局控制 | 完全可控（内存即真相） | 同 C++ | 安全前提下可控（无别名 UB） | struct 可控但 GC 移动对象 | 无 |
| SIMD 主流路径 | intrinsics + 自动向量化 | 同 C++ | `std::simd`（实验）/intrinsics | `math/bits` 少量 + 汇编 | numpy/SIMD 库 |
| 「先测量」文化 | 强（工具古老且自由） | 强 | 强（criterion 生态） | 中 | 弱（先优化开发速度） |

一句话：**C++ 是「编译器 + 内存 + CPU」三层信息都能看见、也都需要你自己负责的语言**——别的语言把分配（GC）、布局（VM）、优化决策（JIT/解释器）收走一部分，C++ 全留给你，所以「先测量、懂底层」不是选修而是基本功。

## 7. 总结

### 关键要点

1. **先测量，再优化**（roadmap 必会概念）：四步循环——定基线 → 找热点 → 改一处 → 复测证；热点由数据点名，不由直觉指定（3.1）
2. **剖析选采样默认**：perf/VTune/Tracy 采样开销低；没有剖析器时 ScopeTimer 插桩是替代品（ex03），两者互补（3.2/3.3）
3. **分配次数与内存增长是两件事**：前者用 operator new 计数（ex04/sol-03），后者查泄漏（ph13 的 RAII 收口）（3.4）
4. **cache locality 是性能第一课**：连续访问 vs 16 KB 跨步，同一求和差 5.6 倍（ex01）；连续内存利于缓存不是口号是数字（3.5）
5. **复制消除 C++17 起是语言保证**：prvalue 按值返回零拷贝零移动；NRVO 通常消除；消除不了的路径移动比拷贝便宜一个量级（ex02）（3.6）
6. **reserve/emplace/零中间态解析**把分配次数降两三个量级（ex04 24k→1；sol-03 15 万→11）（3.7）
7. **SIMD = 布局 × 并行累加**：SoA 连续布局是前提，拆依赖链（4 路累加）就快 3.6 倍，NEON 快 5.3 倍（ex05）（3.8）
8. **可信测时五纪律**：预热、多轮取最优、结果被消费、输入逐轮微变、同语义对比（ex06/3.9）——否则编译器按 as-if 规则给你看假数字
9. **「模式 vs 裸写」没有统一答案**（ph17 预告兑现）：编译器看得见的间接几乎免费（同 TU 去虚化），信息被藏起来的按行虚管道慢 5.6 倍——成本 = 间接真发生 × 热路径高频摊薄（3.10）
10. **算法复杂度优先于微优化**：先修 O(n²)，再做常数优化；过早优化破坏结构，冷路径不值得优化（3.1/5）
