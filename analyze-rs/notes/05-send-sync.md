# 05 · Send/Sync 并发安全

> demo: `cargo run --bin 05_send_sync`

## 1. 设计动机

并发 bug 里最危险的是**数据竞争**（data race）：两个线程同时读写同一块内存，
行为未定义。C/C++ 靠程序员用锁保证，漏一个锁就出事故且难复现。
Rust 的命题：**让"能否跨线程共享/转移"成为类型属性，数据竞争在编译期就不可能**。

## 2. 机制拆解

两个 marker trait 标记"线程安全性"：

```rust
unsafe trait Send {}    // 该类型可以安全地 move 到另一个线程
unsafe trait Sync {}    // 该类型可以被多个线程共享引用（&T 是 Send）
```

编译器自动为类型推导 Send/Sync，规则直观：

| 类型 | Send | Sync |
|------|------|------|
| `i32`、`String`、`Vec<T>` | ✅ | ✅ |
| `Rc<T>`（引用计数，非原子） | ❌ | ❌ |
| `Arc<T>`（原子引用计数） | ✅ | ✅ |
| `Mutex<T>`、`RefCell<T>` | 视内部而定 | 锁保护的 ✅ |

于是出现经典的编译错误：

```rust
let rc = Rc::new(5);
thread::spawn(move || { ... rc ... });  // ❌ Rc 不是 Send，不能跨线程
```

**这不是限制，是救命**：`Rc` 的引用计数是非原子的，跨线程会数据竞争——
编译器在你写出 bug 之前就拦住了。

**正确姿势**：`Arc<Mutex<T>>`（原子计数 + 锁）或 channel（消息传递）。

## 3. 代码验证（demos/05_send_sync.rs）

demo 演示：`Arc<Mutex>` 安全共享、channel 消息传递，以及被注释掉的
"Rc 跨线程"编译错误。

## 4. 代价与取舍

| 代价 | 说明 |
|------|------|
| 心智负担 | 要理解 Send/Sync 的推导规则 |
| 写法受限 | 跨线程共享必须 Arc/Mutex，比"裸共享"啰嗦 |
| 保守 | 某些安全但编译器无法证明的用法被拒绝 |

**换来的**：数据竞争从"最难查的运行时 bug"变成"编译错误"——
Go 的 race detector 是运行时工具，Rust 是编译期保证。

## 5. 对 Tenet 的启示

- ✅ **吸收"共享状态要显式、要受控"**：Tenet 目前是单线程解释器，没有并发——
  但环境的 `Rc`/引用计数设计（`env.rs`）正是"共享需显式"思想的雏形
- ✅ **吸收"错误在最早阶段暴露"**：Send/Sync 是编译期检查，Tenet 的错误也在
  尽可能早的阶段（词法→语法→语义）暴露，而非运行时崩溃
- ❌ **拒绝把并发引入 Tenet**：教学语言单线程足够；并发是"未来演进"里
  最靠后的方向
- 💡 若未来做并发扩展，参照"channel 优先、共享需加锁"的 Rust 路线

**一句话**：Rust 把"数据竞争不可能"变成编译期保证；
Tenet 用「单线程 + 引用计数」在最小形态下继承了"共享状态必须安全"的原则。
